데이터 구성

Doris는 데이터를 어떻게 구성 하나요?

먼저 논리적 계층 구조를 살펴봅니다. 이어서 테이블이 클러스터 전체에 어떻게 나뉘어 분산되는지 알아봅니다.

  1. Catalog데이터 소스
  2. 데이터베이스업무 영역
  3. 테이블스키마 + 속성
  4. 파티션논리적 범위
  5. 버킷물리적 분산
학습 도움말

테이블에서는 논리 구조가 실제 저장 방식으로 이어집니다.

Catalog는 데이터 소스를 식별하고, 데이터베이스는 논리적 경계를 만들며, 테이블은 스키마와 속성을 정의합니다. 테이블 안에서는 파티션이 데이터 범위를 구분하고 버킷이 병렬 처리를 위해 데이터를 분산합니다.

이 차이를 기억하세요

파티션은 “어느 데이터 범위인가?”에, 버킷은 “어디에 어떻게 분산되는가?”에 답합니다.

날짜 범위를 기준으로 데이터를 걸러내는 데 쓰이는 계층은 무엇인가요?

답을 선택하여 이해도를 확인하세요.

열 지향 저장

값을 열별로 저장하는 이유는 무엇일까요?

분석 쿼리는 많은 행에서 일부 열만 참조하는 경우가 많습니다. 열 지향 저장을 사용하면 Doris는 쿼리에 필요한 데이터만 읽고 처리할 수 있습니다.

I/O읽기량 감소

쿼리가 참조하는 열만 스캔합니다.

ZIP압축 효율 향상

자료형이 같고 비슷한 값은 더 작은 크기로 인코딩하기 쉽습니다.

CPU일괄 처리

연속된 벡터는 캐시 활용도를 높이고 SIMD를 사용할 수 있게 합니다.

학습 도움말

열 지향 배치는 불필요한 작업을 줄입니다.

같은 열의 값은 자료형이 같고 분포도 비슷한 경우가 많습니다. 따라서 인코딩, 압축, CPU 캐시 지역성, 일괄 처리에 유리합니다.

이렇게 이해하세요

행 지향 저장은 완전한 레코드를 한데 모으고, 열 지향 저장은 같은 필드의 값을 한데 모읍니다.

쿼리가 80개 열 중 3개만 읽는다면 가장 큰 이점은 무엇인가요?

답을 선택하여 이해도를 확인하세요.

테이블 모델

키가 중복되면 무엇이 달라질까요?

테이블 모델은 Doris가 모든 행을 보존할지, 값을 결합할지, 각 Key마다 하나의 논리적 행을 유지할지를 결정합니다.

DUPDuplicate Key

이벤트 상세 데이터와 로그에 적합하며, 입력된 모든 행을 보존합니다.

AGGAggregate Key

선언된 집계 함수를 사용해 Value 열을 병합합니다.

UNIUnique Key

업데이트와 CDC를 위해 각 Key마다 하나의 논리적 행을 유지합니다.

학습 도움말

데이터를 적재하기 전에 행의 처리 방식을 선택하세요.

Duplicate Key는 변경되지 않는 상세 데이터에 적합하고, Aggregate Key는 선언된 방식에 따라 사전 집계한 값을 저장하며, Unique Key는 UPSERT 방식으로 변경되는 레코드를 지원합니다.

운영 환경에서의 원칙

테이블을 만든 뒤에는 테이블 모델을 변경할 수 없습니다. 선택하기 전에 필요한 업데이트 동작을 확인하세요.

CDC로 고객 프로필을 업데이트할 때 적합한 모델은 무엇인가요?

답을 선택하여 이해도를 확인하세요.

통합 아키텍처

전통적인 FE + BE 클러스터를 살펴봅시다.

통합 아키텍처에서는 Frontend 노드가 시스템을 조정하고, Backend 노드가 쿼리를 실행하며 tablet 복제본을 로컬 저장소에 영구 저장합니다.

  1. SQL 클라이언트MySQL 프로토콜
  2. Frontend파싱 + 계획 수립 + 조정
  3. Backend저장 + 실행
학습 도움말

제어와 데이터 처리의 역할이 구분됩니다.

FE는 인증, SQL 파싱과 계획 수립, 메타데이터 관리, 조정을 담당합니다. BE는 tablet을 저장하고 벡터화 연산자를 실행하며 데이터를 압축 정리하고 복구와 균형 조정에 참여합니다.

고가용성

운영 환경에서는 여러 FE 노드를 사용하고 tablet 복제본 수를 설정할 수 있습니다. FE 메타데이터 복제에는 BDB JE를 사용하며 ZooKeeper는 필요하지 않습니다.

분산 쿼리 계획을 만드는 노드는 무엇인가요?

답을 선택하여 이해도를 확인하세요.

스토리지와 컴퓨팅 분리 아키텍처

스토리지와 컴퓨팅이 분리되면 무엇이 달라질까요?

영구 데이터는 공유 저장소에 두고, 상태를 유지하지 않는 컴퓨팅 그룹은 독립적으로 확장하거나 축소할 수 있습니다.

  1. 01
    SQL 및 메타데이터 계층

    FE는 SQL 요청을 처리하고, Meta Service는 데이터 계층의 메타데이터를 관리합니다.

  2. 02
    컴퓨팅 그룹

    상태를 유지하지 않는 BE 노드는 작업을 실행하고 자주 사용하는 데이터를 캐시합니다.

  3. 03
    공유 저장소

    객체 저장소 또는 지원되는 분산 파일 시스템에 데이터를 영구 저장합니다.

학습 도움말

탄력적인 확장에는 운영해야 할 계층이 하나 더 필요합니다.

FE는 요청과 SQL 계층의 메타데이터를 처리하고, Meta Service는 데이터 계층의 메타데이터를 관리합니다. 상태를 유지하지 않는 BE 노드는 자주 사용하는 데이터를 캐시하면서 공유 영구 저장소의 데이터를 대상으로 연산합니다.

운영상의 절충점

공유 저장소는 안정적이어야 합니다. 캐시에 없는 데이터를 읽으면 지연이 늘어날 수 있으며, 플랫폼 팀은 추가 서비스도 운영해야 합니다.

데이터의 영구 복사본은 어디에 있나요?

답을 선택하여 이해도를 확인하세요.

아키텍처 선택

실제 제약 조건에서 출발하세요. 단지 더 새롭다는 이유로 선택하지 마세요.

통합형 배포와 분리형 배포는 각각 다른 운영 환경에 최적화되어 있습니다. 어느 아키텍처가 항상 더 나은 것은 아닙니다.

통합형

상태를 유지하는 BE 노드가 컴퓨팅을 수행하고 데이터를 로컬에 영구 저장합니다.

  • 운영 복잡도 감소
  • 로컬 스토리지 접근
  • 컴퓨팅과 스토리지를 함께 확장
분리형

상태를 유지하지 않는 컴퓨팅 그룹이 영구 스토리지를 공유합니다.

  • 독립적인 탄력적 확장
  • 워크로드가 격리된 컴퓨팅 그룹
  • 더 많은 플랫폼 구성 요소에 의존
학습 도움말

단순성과 탄력적 확장성 사이에는 절충이 필요합니다.

대체로 통합형 배포가 시작하기 더 쉽습니다. 공유 스토리지, 플랫폼 팀의 운영 책임, 컴퓨팅 자원의 독립적인 확장, 격리된 컴퓨팅 그룹이 실제 요구사항이라면 분리형 배포가 적합합니다.

선택 기준

단지 더 새로운 방식이라는 이유로 분리형 아키텍처를 선택하지 마세요. 추가되는 구성 요소가 구체적인 제약을 해결해야 합니다.

로컬 디스크를 사용할 수 있고 컴퓨팅 자원을 스토리지와 함께 확장할 수 있다면, 어떤 아키텍처로 시작해야 할까요?

답을 선택하여 이해도를 확인하세요.

핵심 엔진 모듈

두 엔진이 협력해 작업을 줄이고 처리 속도를 높입니다.

스토리지 엔진은 데이터와 접근 경로를 구성합니다. 쿼리 엔진은 SQL을 분산형 벡터화 파이프라인으로 변환합니다.

COL열 기반 스토리지

필요한 열을 읽고 분석 데이터를 압축합니다.

IDX인덱스

Prefix, Min/Max, Bloom, 역색인은 스캔 범위를 줄입니다.

MPP분산 처리

여러 Backend 노드에 쿼리 실행을 분산합니다.

OPT옵티마이저

규칙, 비용, 이력에 기반한 전략을 적용합니다.

학습 도움말

최적화는 실행 전에 시작됩니다.

정렬 키, 파티션, 인덱스, 테이블 모델은 접근해야 할 데이터의 양을 줄입니다. MPP, 벡터화, Pipeline 스케줄링, 옵티마이저는 남은 데이터를 처리하는 비용을 줄입니다.

MPP와 Pipeline 비교

MPP는 작업을 여러 노드에 분산합니다. Pipeline 실행은 각 노드에서 여러 코어에 걸쳐 연산자 작업을 스케줄링합니다.

여러 BE 노드에 작업을 분산하는 메커니즘은 무엇인가요?

답을 선택하여 이해도를 확인하세요.

쿼리 실행

SQL 텍스트가 분산 파이프라인으로 이어지는 과정을 살펴보세요.

쿼리는 검증과 최적화를 거쳐 프래그먼트와 인스턴스로 나뉘고, 여러 BE 노드에서 실행된 뒤 하나의 결과로 합쳐집니다.

  1. 파싱SQL 검증
  2. 계획 수립재작성 + 비용 추정
  3. 프래그먼트분산 작업 분할
  4. 실행벡터화 파이프라인 실행
  5. 반환결과 취합
학습 도움말

프래그먼트는 작업을 정의하고, 인스턴스는 그 작업을 수행합니다.

프래그먼트는 분산 실행 계획의 논리적 부분입니다. 인스턴스는 BE에서 실행되는 물리적 복사본입니다. 데이터를 다시 분산해야 할 때 Exchange 연산자가 인스턴스 사이에서 행을 이동합니다.

벡터화 실행

연산자는 행을 하나씩 처리하는 대신 열 단위의 배치를 처리합니다. 이를 통해 행마다 발생하는 오버헤드를 줄이고 CPU 효율을 높입니다.

프래그먼트 인스턴스 사이에서 행을 이동하는 것은 무엇인가요?

답을 선택하여 이해도를 확인하세요.

최적화와 요약

가장 빠른 작업은 Doris가 생략할 수 있는 작업입니다.

Doris는 사전 계산, 논리적 재작성, 통계 기반 계획 수립, 런타임 필터링을 결합해 실행 전과 실행 중에 처리할 데이터의 양을 줄입니다.

MV구체화된 뷰

쿼리 재작성을 통해 사전 계산된 결과를 재사용합니다.

RBO규칙 기반

결정적인 논리 변환을 적용합니다.

CBO비용 기반

통계 정보를 사용해 물리 실행 계획을 비교합니다.

RF런타임 필터

필터를 스캔 단계로 밀어 넣어 행을 일찍 걸러냅니다.

학습 도움말

최적화는 여러 단계에서 이루어집니다.

구체화된 뷰는 반복 계산을 대체할 수 있고, RBO는 실행 계획을 단순화하며, CBO는 추정 비용을 비교합니다. 런타임 필터는 조인 중에 행을 일찍 걸러냅니다.

다음 학습으로 넘어가기 전에

데이터 구성 계층, FE와 BE의 역할 구분, 두 가지 아키텍처 선택지, 계획 수립부터 분산 실행까지의 흐름을 기억하세요.

CBO가 대안 실행 계획을 정확하게 비교하는 데 도움이 되는 것은 무엇인가요?
