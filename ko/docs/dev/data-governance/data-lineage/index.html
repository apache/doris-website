데이터 계보 기술 가이드

데이터 계보는 지원되는 Doris DML 문에서 테이블 수준 및 컬럼 수준의 의존성을 추출하여 LineagePlugin을 통해 외부 거버넌스 시스템으로 전송합니다. Doris는 계보를 생성하는 역할을 합니다. 이벤트를 보관하지 않으며, 계보 쿼리 API나 계보 시각화 기능을 제공하지 않습니다.

이 기능은 Dev 버전에서 사용할 수 있습니다. Apache Doris 4.0.6에서 처음 출시되었습니다.

기능 및 제한 사항​

프레임워크는 다음 문 중 하나가 성공한 경우에만 이벤트를 생성합니다.

지원되는 문이벤트 동작
INSERT INTO ... SELECTInsert가 성공하면 이벤트를 하나 생성합니다.
INSERT OVERWRITE TABLE ... SELECTOverwrite가 성공하면 이벤트를 하나 생성합니다.
CREATE TABLE AS SELECT내부 Insert가 성공하면 이벤트를 하나 생성합니다.

현재 구현에서는 SELECT, UPDATE, DELETE, 데이터 적재 작업, VALUES만 사용하는 Insert 또는 대상이 __internal_schema인 쓰기 작업에 대해 이벤트를 생성하지 않습니다. 일부 UPDATE 및 DELETE 실행 경로는 내부적으로 Insert 명령을 재사용하지만, 원래 명령 유형을 검사하여 계보 이벤트 제출 대상에서 제외합니다.

전달 보장

계보 전달은 비동기 방식이며 최선형으로 동작합니다. 이벤트 수집이나 플러그인 전달이 실패하더라도 성공한 DML 문은 롤백되지 않습니다. 큐가 가득 차면 이벤트가 폐기될 수 있으며, Doris는 이벤트를 재시도하거나 영구 저장하지 않습니다.

기술 설계​

수집 흐름​

지원되는 문의 경우 Doris는 afterAnalyze 플래너 훅에서 분석된 Nereids 논리 계획을 기록합니다. DML이 성공하면 해당 계획에서 계보를 추출하여 FE별 로컬 큐에 이벤트를 제출합니다. 단일 데몬 워커가 로드된 모든 플러그인을 확인하고, eventFilter()가 true를 반환하는 각 플러그인에 이벤트를 전달합니다.

추출 전에 Doris는 로드된 플러그인의 eventFilter()를 호출합니다. 이벤트를 수신하려는 플러그인이 없으면 추출을 생략합니다. 워커는 이벤트를 전달하기 전에 eventFilter()를 다시 확인합니다.

계보 내용​

각 LineageInfo 이벤트에는 테이블 계보, 직접 컬럼 계보, 두 종류의 간접 계보, 쿼리 컨텍스트가 포함됩니다. 아래의 전체 SQL 예제에서는 이후 절에서 사용할 소스 테이블과 대상 테이블을 생성하고 결과를 확인합니다.

SQL 예제 및 결과​

현재 사용자에게는 데이터베이스와 테이블 생성, 데이터 쓰기, 데이터 쿼리 권한이 있어야 하며, FE에는 계보 플러그인이 로드되어 있어야 합니다. 이 예제에서는 두 소스 테이블을 사용하며, CTE, Join, 필터, 집계, 윈도 함수, 조건식, 정렬을 거쳐 고객 요약을 생성합니다.

CREATE DATABASE IF NOT EXISTS lineage_demo;
USE lineage_demo;

CREATE TABLE lineage_orders (
    order_id BIGINT,
    customer_id BIGINT,
    region VARCHAR(16),
    amount DECIMAL(18, 2),
    status VARCHAR(16)
)
DUPLICATE KEY(order_id)
DISTRIBUTED BY HASH(order_id) BUCKETS 1
PROPERTIES ("replication_num" = "1");

CREATE TABLE lineage_customers (
    customer_id BIGINT,
    customer_name VARCHAR(64),
    customer_level VARCHAR(16)
)
DUPLICATE KEY(customer_id)
DISTRIBUTED BY HASH(customer_id) BUCKETS 1
PROPERTIES ("replication_num" = "1");

CREATE TABLE lineage_customer_summary (
    customer_id BIGINT,
    region_label VARCHAR(16),
    total_amount DECIMAL(18, 2),
    customer_seq BIGINT,
    region_group VARCHAR(16)
)
DUPLICATE KEY(customer_id)
DISTRIBUTED BY HASH(customer_id) BUCKETS 1
PROPERTIES ("replication_num" = "1");

INSERT INTO lineage_customers VALUES
    (1, 'Alice', 'VIP'),
    (2, 'Bob', 'VIP'),
    (3, 'Carol', 'REGULAR');

INSERT INTO lineage_orders VALUES
    (101, 1, 'east', 100.00, 'PAID'),
    (102, 1, 'east',  50.00, 'PAID'),
    (103, 2, 'west',  80.00, 'PAID'),
    (104, 2, 'west',  30.00, 'CANCELLED'),
    (105, 3, 'north', 200.00, 'PAID');

INSERT INTO lineage_customer_summary
WITH customer_totals AS (
    SELECT
        o.customer_id,
        UPPER(o.region) AS region_label,
        SUM(o.amount) AS total_amount
    FROM lineage_orders o
    JOIN lineage_customers c
        ON o.customer_id = c.customer_id
    WHERE o.status = 'PAID'
      AND c.customer_level = 'VIP'
    GROUP BY o.customer_id, UPPER(o.region)
    HAVING SUM(o.amount) >= 50
)
SELECT
    customer_id,
    region_label,
    total_amount,
    ROW_NUMBER() OVER (ORDER BY customer_id) AS customer_seq,
    CASE
        WHEN region_label = 'EAST' THEN 'CORE'
        ELSE 'OTHER'
    END AS region_group
FROM customer_totals
ORDER BY total_amount DESC;

SELECT customer_id, region_label, total_amount, customer_seq, region_group
FROM lineage_customer_summary
ORDER BY customer_id;

쿼리는 다음 결과를 반환합니다.

+-------------+--------------+--------------+--------------+--------------+
| customer_id | region_label | total_amount | customer_seq | region_group |
+-------------+--------------+--------------+--------------+--------------+
|           1 | EAST         |       150.00 |            1 | CORE         |
|           2 | WEST         |        80.00 |            2 | OTHER        |
+-------------+--------------+--------------+--------------+--------------+

VALUES만 사용하는 두 Insert는 계보 이벤트를 생성하지 않습니다. INSERT INTO lineage_customer_summary ... SELECT 문은 LineageInfo 이벤트를 하나 생성하며, 그 내용은 아래에서 설명합니다.

테이블 계보​

테이블 계보는 대상 테이블 하나와 분석된 논리 계획에서 스캔하는 모든 소스 테이블을 기록합니다. lineage_customer_summary에 쓰는 쿼리는 lineage_orders와 lineage_customers를 모두 스캔하므로, 두 소스 테이블 모두 대상 테이블과 테이블 수준의 관계를 갖습니다. CTE는 기반 테이블로 해석되며, 모든 UNION 분기가 소스 테이블 집합에 포함됩니다.

이 예제는 다음 테이블 계보를 생성합니다.

소스 테이블대상 테이블
lineage_orderslineage_customer_summary
lineage_customerslineage_customer_summary

직접 컬럼 계보​

직접 컬럼 계보는 각 대상 컬럼의 값을 생성하는 소스 표현식을 나타냅니다. 별칭과 CTE를 해석한 후 Doris는 다음 순서로 표현식을 분류합니다. 집계 함수를 포함하는 표현식은 AGGREGATION, 단순한 소스 컬럼 참조는 IDENTITY, 나머지 표현식은 모두 TRANSFORMATION입니다.

유형의미예제
IDENTITY함수나 연산 없이 소스 컬럼에서 대상 값을 직접 가져옵니다.lineage_customer_summary.customer_id는 lineage_orders.customer_id에서 직접 가져옵니다.
TRANSFORMATION산술 연산, 문자열 함수, 윈도 함수, 조건식과 같은 비집계 표현식으로 대상 값을 변환합니다.region_label은 UPPER(lineage_orders.region)에서 파생되며, customer_seq는 ROW_NUMBER()에서 파생됩니다.
AGGREGATION집계 함수를 포함하는 표현식으로 대상 값을 생성합니다. 다른 표현식이 집계를 감싸더라도 이 유형을 유지합니다.total_amount는 SUM(lineage_orders.amount)에서 파생됩니다.

이 예제는 다음 직접 컬럼 계보를 생성합니다.

대상 컬럼소스 표현식유형
lineage_customer_summary.customer_idlineage_orders.customer_idIDENTITY
lineage_customer_summary.region_labelUPPER(lineage_orders.region)TRANSFORMATION
lineage_customer_summary.total_amountSUM(lineage_orders.amount)AGGREGATION
lineage_customer_summary.customer_seqROW_NUMBER() OVER (ORDER BY lineage_orders.customer_id)TRANSFORMATION
lineage_customer_summary.region_groupCASE WHEN UPPER(lineage_orders.region) = 'EAST' ... ENDTRANSFORMATION

데이터셋 간접 계보​

데이터셋 간접 계보는 대상 컬럼 값을 직접 생성하지 않으면서 전체 결과 집합에 영향을 미치는 표현식을 기록합니다. 이러한 의존성은 이벤트 수준의 맵에 저장되며, 필요에 따라 모든 대상 출력 컬럼에 적용할 수 있습니다.

유형의미예제
JOINJoin 조건은 결합할 수 있는 소스 행을 결정합니다.lineage_orders.customer_id = lineage_customers.customer_id.
FILTERWHERE 또는 HAVING 조건은 결과에 포함될 행이나 그룹을 결정합니다.status = 'PAID', customer_level = 'VIP', HAVING SUM(amount) >= 50.
GROUP_BY그룹화 표현식은 집계 결과의 단위를 결정합니다.customer_id와 UPPER(region)으로 그룹화합니다.
SORTORDER BY 또는 TopN 표현식은 결과 순서를 결정합니다.total_amount DESC로 정렬하며, 이는 SUM(amount)로 해석됩니다.

이 예제는 다음 데이터셋 간접 계보를 생성합니다.

유형이벤트에 포함되는 소스 표현식 예제영향
JOINlineage_orders.customer_id = lineage_customers.customer_id주문과 고객을 연결하는 방식을 결정합니다.
FILTERstatus = 'PAID', customer_level = 'VIP', SUM(amount) >= 50WHERE와 HAVING 조건식이 함께 결과에 포함될 행과 그룹을 결정합니다.
GROUP_BYlineage_orders.customer_id와 UPPER(lineage_orders.region)고객별, 지역별 집계 단위를 결정합니다.
SORTtotal_amount DESC, SUM(lineage_orders.amount)로 해석됨Insert 쿼리 결과의 순서를 결정합니다.

출력 간접 계보​

출력 간접 계보는 영향을 받는 대상 컬럼에만 연결되며, 다른 출력 컬럼에는 적용되지 않습니다.

유형의미예제
WINDOW윈도 함수의 PARTITION BY 및 ORDER BY 입력은 해당 출력 컬럼에 영향을 미칩니다.customer_seq는 ROW_NUMBER() OVER (ORDER BY customer_id)로 생성되며, 이 표현식의 WINDOW 의존성은 customer_id입니다.
CONDITIONALCASE나 IF의 조건 또는 COALESCE의 후보 표현식은 해당 출력 컬럼에 영향을 미칩니다.region_group은 CASE WHEN region_label = 'EAST' ...로 결정되며, 이 표현식의 CONDITIONAL 의존성은 해당 조건식입니다.

윈도 표현식이나 조건식 자체도 직접 컬럼 계보에 계속 포함됩니다. 예를 들어 customer_seq의 직접 유형은 TRANSFORMATION이며, WINDOW 간접 계보도 갖습니다. region_group의 직접 유형도 TRANSFORMATION이며, CONDITIONAL 간접 계보도 갖습니다.

이 예제는 다음 출력 간접 계보를 생성합니다.

대상 컬럼유형이벤트에 포함되는 소스 표현식영향
customer_seqWINDOWlineage_orders.customer_idROW_NUMBER()의 윈도 정렬 입력으로 사용되며, customer_seq에만 영향을 미칩니다.
region_groupCONDITIONALUPPER(lineage_orders.region) = 'EAST'CASE WHEN 조건으로 사용되며, region_group에만 영향을 미칩니다.

나머지 세 대상 컬럼에는 출력 간접 계보가 없습니다. 데이터셋 수준의 JOIN, FILTER, GROUP_BY, SORT 의존성은 여전히 전체 결과 집합에 영향을 미칩니다.

쿼리 컨텍스트​

쿼리 컨텍스트는 누가 어떤 세션에서 어떤 DML 문을 통해 계보 이벤트를 생성했는지 식별합니다.

필드예제 또는 의미
소스 명령InsertIntoTableCommand는 이벤트가 Insert에서 생성되었음을 나타냅니다.
Query ID 및 원본 SQLQuery ID와 전체 INSERT INTO lineage_customer_summary ... 텍스트입니다.
사용자 및 클라이언트 IP예를 들어 lineage_user와 192.0.2.10입니다.
세션 데이터베이스 및 Catalog이 예제에서는 lineage_demo와 internal입니다. 세션 컨텍스트를 나타내며, 반드시 대상 테이블의 위치를 식별하는 것은 아닙니다.
실행 상태성공한 DML 문은 일반적으로 OK를 기록합니다.
타임스탬프 및 소요 시간이벤트 생성 시각과 쿼리 시작부터 이벤트 생성까지 걸린 시간(밀리초)입니다. 값을 확인할 수 없으면 -1입니다.
외부 Catalog 속성쿼리가 참조하는 외부 Catalog의 민감하지 않은 속성입니다. 비밀번호, 키, 숨겨진 속성은 제거됩니다. internal Catalog만 사용하면 맵은 비어 있습니다.

이 예제에서 원본 SQL은 위의 복잡한 Insert이며, 소스 명령은 InsertIntoTableCommand, 세션 데이터베이스는 lineage_demo, 세션 Catalog는 internal, 성공 상태는 OK입니다. Query ID, 사용자, 클라이언트 IP, 타임스탬프, 소요 시간은 실제 실행 컨텍스트의 값을 사용합니다. 이 예제는 Internal Catalog만 사용하므로 외부 Catalog 속성 맵은 비어 있습니다.

플러그인의 다운스트림 시스템에서 이벤트가 수신되었는지 확인합니다. 초기 배포 시에는 fe.log에서 Loaded lineage plugin, 플러그인별 오류, 큐가 가득 찼다는 경고도 확인합니다.

추출기는 이벤트가 전달되기 전에 CTE 생성자 표현식을 해석하고 UNION 분기를 확장합니다. 다운스트림 플러그인은 TableIf, SlotReference, Expression과 같은 Doris Java 객체를 안정적인 식별자나 자체 이벤트 스키마로 변환해야 합니다.

이벤트 처리 동작​

lineage_event_queue_size는 각 FE별 로컬 큐에서 대기할 수 있는 계보 이벤트의 최대 개수를 설정합니다. 바이트 수가 아니라 이벤트 수를 셉니다. 큐가 가득 차면 새 이벤트는 폐기되며 DML은 정상적으로 계속됩니다. 워커는 플러그인을 순차적으로 호출하므로, 느린 플러그인은 이후 이벤트를 지연시키고 부하가 지속될 때 이벤트 폐기를 유발할 수 있습니다. 플러그인에서 발생한 예외는 로그에 기록되며, 워커를 중단시키거나 DML에 영향을 미치지 않습니다.

플러그인 검색과 초기화는 FE가 시작될 때만 수행됩니다. 동적 다시 로드와 언로드는 지원되지 않습니다.

설정 및 사용​

사전 요구 사항​

  1. 외부 계보 플러그인을 준비합니다. Doris는 내장 싱크를 제공하지 않습니다. SPI 규약, JAR 패키징, 최소 구성의 전체 플러그인 예제는 데이터 계보 플러그인 개발을 참조하세요.
  2. 플러그인 JAR와 필요한 모든 타사 의존성 JAR를 모든 FE에 복사합니다.
  3. 플러그인이 외부 거버넌스 서비스로 이벤트를 전송하는 경우, DML을 실행할 수 있는 모든 FE에서 해당 서비스에 접근할 수 있는지 확인합니다.

플러그인 배포​

FE_HOME은 bin/, conf/, lib/를 포함하는 단일 FE 설치 디렉터리를 나타냅니다. 모든 FE에서 다음 디렉터리 구조를 사용합니다. 로더는 lineage/ 바로 아래의 하위 디렉터리와 각 플러그인 디렉터리 및 해당 lib/ 디렉터리에 있는 JAR만 스캔합니다.

$FE_HOME/plugins/
└── lineage/
    └── example-lineage/
        ├── example-lineage.jar
        └── lib/
            └── downstream-client.jar

모든 FE에서 fe.conf를 설정합니다. example-lineage를 플러그인 팩토리의 name() 메서드가 반환하는 값으로 바꿉니다.

plugin_dir = /opt/apache-doris/fe/plugins
activate_lineage_plugin = example-lineage
lineage_event_queue_size = 50000
설정유형 및 기본값필수 여부설명
plugin_dir문자열; $FE_HOME/plugins아니요플러그인 루트 디렉터리입니다. 계보 로더는 이 디렉터리의 lineage/ 바로 아래에 있는 하위 디렉터리를 스캔합니다. 기본 디렉터리를 사용하면 이 설정을 생략합니다.
activate_lineage_plugin문자열 배열; 비어 있음명시적 설정 권장인스턴스화할 Factory 이름을 쉼표로 구분합니다. 값이 비어 있으면 이름 필터링을 비활성화하고 검색된 모든 팩토리를 인스턴스화합니다.
lineage_event_queue_size양의 정수; 50000아니요현재 FE에서 대기할 수 있는 계보 이벤트의 최대 개수입니다. 큐가 가득 차면 새 이벤트는 폐기됩니다.

세 설정은 모두 각 FE의 $FE_HOME/conf/fe.conf에 지정하며, 해당 FE 프로세스에만 적용됩니다. FE 시작 시에만 읽으므로, 변경 후에는 해당 FE를 다시 시작해야 합니다.

플러그인 활성화​

activate_lineage_plugin을 모든 FE의 $FE_HOME/conf/fe.conf에 설정합니다. 이 설정은 검색된 팩토리 중 어떤 팩토리를 인스턴스화할지 제어합니다. JAR 검색이나 큐 용량은 제어하지 않습니다. 각 이름은 대소문자를 구분하며, LineagePluginFactory.name()과 정확히 일치해야 합니다. LineagePlugin.name() 구현도 같은 이름을 반환해야 합니다. 플러그인 디렉터리 이름은 일치 여부를 판단하는 데 사용하지 않습니다. 여러 플러그인 이름은 쉼표로 구분합니다. FE 설정 파서는 쉼표로 구분된 각 항목의 앞뒤 공백을 제거하지만, 이름을 비교할 때는 여전히 대소문자를 구분합니다.

activate_lineage_plugin = example-lineage,governance-lineage

시작 시 FE는 내장 팩토리와 외부 팩토리를 검색한 다음, 설정된 이름에 대해서만 인스턴스를 생성합니다. 각 FE는 자체 설정을 읽으므로 DML을 실행할 수 있는 모든 FE에서 동일한 플러그인 구성을 사용해야 합니다. 변경 후에는 FE를 다시 시작합니다. 이 설정은 ADMIN SET FRONTEND CONFIG로 동적으로 변경할 수 없습니다.

값이 비어 있을 때의 동작

현재 구현에서 activate_lineage_plugin 값이 비어 있어도 계보 플러그인이 비활성화되지 않습니다. 이름 필터링을 건너뛰고 검색된 모든 팩토리를 인스턴스화합니다. 활성화할 플러그인을 명시적으로 나열하고, 비활성화하기 위해 빈 값을 사용하지 마세요. 플러그인이 로드된 후에도 추출 전과 전달 전에 eventFilter()가 이벤트 수신 여부를 결정합니다.

이벤트 큐 설정​

lineage_event_queue_size를 모든 FE의 $FE_HOME/conf/fe.conf에 설정합니다. 값은 양의 정수여야 합니다. DML을 실행할 수 있는 각 FE는 독립적인 큐를 가지며, 별도로 설정해야 합니다.

이 항목은 FE 시작 설정이므로 ADMIN SET FRONTEND CONFIG로 동적으로 변경할 수 없습니다. 변경 후에는 해당 FE를 다시 시작합니다. 값을 늘리면 대기 이벤트 용량과 FE 메모리 사용량이 증가합니다. 소비자 스레드가 추가되거나 플러그인 처리량이 증가하지는 않습니다. 이벤트가 누락되면 먼저 fe.log에서 the lineage event queue is full을 검색하고, 플러그인의 exec() 메서드 지연 시간을 줄입니다. 그런 다음 최대 적체량과 사용 가능한 FE 메모리에 맞춰 큐 크기를 정합니다.

다른 플러그인 설정을 변경하거나 플러그인 JAR를 교체한 후에는 모든 FE를 다시 시작합니다. 플러그인 설정과 디렉터리는 FE 시작 시에만 읽습니다.

운영 및 문제 해결​

쓰기 후 이벤트가 생성되지 않음​

일반적인 원인으로는 지원되지 않는 문, 실패한 DML 문, 현재 FE에 로드된 플러그인이 없는 경우, eventFilter()가 false를 반환하는 경우가 있습니다.

다음 순서로 확인합니다.

  1. 해당 문이 성공한 INSERT INTO ... SELECT, INSERT OVERWRITE TABLE ... SELECT 또는 CREATE TABLE AS SELECT인지 확인합니다. VALUES만 사용하는 Insert는 이벤트를 생성하지 않습니다.
  2. DML을 실행한 FE에 플러그인이 설정되고 로드되어 있는지 확인합니다. fe.log에서 Loaded lineage plugin을 검색합니다.
  3. 플러그인의 eventFilter()가 쿼리 스레드와 워커 스레드 모두에서 true를 반환하는지 확인합니다.
  4. 플러그인 로그와 다운스트림 서비스를 확인하여 FE 외부에서 처리가 실패하지 않았는지 확인합니다.

플러그인이 로드되지 않음​

플러그인 디렉터리에 JAR가 있고, 해당 JAR에 META-INF/services/org.apache.doris.nereids.lineage.LineagePluginFactory가 포함되어 있는지 확인합니다. 각 플러그인 디렉터리는 하나의 Factory만 노출할 수 있습니다. Factory 이름은 전역적으로 고유해야 하며 activate_lineage_plugin과 일치해야 합니다. 디렉터리, JAR 또는 설정을 수정한 후 해당 FE를 다시 시작합니다.

높은 부하에서 이벤트 누락​

fe.log에서 the lineage event queue is full과 플러그인 예외를 검색합니다. 큐가 가득 찼다면 먼저 exec()의 동기 블로킹을 줄이고, 다운스트림 전달이 제한된 횟수의 재시도와 함께 멱등성을 갖도록 구현합니다. 그런 다음 lineage_event_queue_size를 늘릴지 검토합니다. 이벤트 크기는 SQL 문에 따라 달라지므로, 값을 늘리기 전에 FE 메모리를 고려해야 합니다.

DML을 실행할 수 있는 모든 FE에 동일한 플러그인과 설정이 적용되어 있는지도 확인합니다. 각 FE는 독립적인 로컬 큐를 사용하며, 플러그인과 큐 상태는 FE 간에 동기화되지 않습니다.

플러그인 업데이트가 적용되지 않음​

플러그인 디렉터리는 FE가 시작될 때만 스캔됩니다. 동적 다시 로드와 언로드는 지원되지 않습니다. 플러그인 JAR, 의존성 또는 설정을 교체한 후에는 관련된 모든 FE를 다시 시작하고 Loaded lineage plugin을 다시 확인합니다.

Query ID와 대상 테이블을 사용하여 다운스트림 이벤트 식별자를 구성합니다. 이렇게 하면 플러그인이 프레임워크 외부에서 재시도를 구현하더라도 거버넌스 시스템에서 이벤트 중복을 제거할 수 있습니다.
