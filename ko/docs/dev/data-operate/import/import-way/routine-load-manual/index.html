Routine Load

Routine Load는 Kafka 토픽의 데이터를 지속적으로 소비하여 Doris 테이블에 기록하는 Apache Doris의 스트리밍 데이터 적재 작업입니다. Routine Load 작업을 제출하면 Doris는 데이터 적재 작업을 계속 실행하면서 Kafka 클러스터의 지정된 토픽에서 메시지를 소비하는 데이터 적재 태스크를 실시간으로 생성합니다. 또한 Exactly-Once 의미론을 제공하여 데이터 유실과 중복을 방지합니다.

빠른 탐색​

필요에 따라 해당 섹션으로 바로 이동할 수 있습니다.

필요한 작업섹션
최소 예제를 바로 실행하기빠른 시작
원리, 상태 머신 및 자동 복구 메커니즘 이해하기기본 원리
설정 가능한 모든 매개변수(FE/BE/작업/Kafka) 찾아보기참조 매뉴얼
시나리오별 예제 찾기(내결함성, 필터링, JSON, Kerberos 등)데이터 적재 예제
작업이 PAUSED 상태로 전환되거나 out of range 또는 SSL 오류가 발생한 경우자주 묻는 질문(FAQ)

사용 사례​

Routine Load는 다음과 같은 상황에 적합합니다.

  • Kafka 토픽의 실시간 데이터를 Doris로 지속적으로 동기화해야 하는 경우.
  • 데이터 유실이나 중복을 방지하기 위해 Exactly-Once 의미론이 필요한 경우.
  • 적재할 데이터에 컬럼 매핑, 필터링, 파생 컬럼 계산 등의 변환을 수행해야 하는 경우.
  • 단일 Kafka 토픽의 데이터를 여러 Doris 테이블로 동적으로 분배해야 하는 경우(단일 스트림, 다중 테이블).

지원하는 데이터 소스 및 형식​

Routine Load는 Kafka 클러스터의 데이터 소비만 지원하며, 다음 두 가지 메시지 형식을 지원합니다.

형식설명
CSV각 메시지는 한 줄이며, 줄 끝에 줄바꿈 문자가 포함되지 않습니다.
JSON단일 JSON 객체 또는 여러 객체가 포함된 JSON 배열입니다.

CSV 형식의 데이터를 적재할 때는 null 값과 빈 문자열을 명확히 구분해야 합니다.

  • null 값은 \n으로 표현합니다. 예를 들어 a,\n,b는 가운데 컬럼이 null 값임을 나타냅니다.
  • 빈 문자열은 해당 데이터를 비워 둡니다. 예를 들어 a,,b는 가운데 컬럼이 빈 문자열('')임을 나타냅니다.

제한 사항​

Routine Load로 Kafka의 데이터를 소비할 때는 다음과 같은 제한 사항이 적용됩니다.

제한 사항설명
메시지 형식CSV 및 JSON 텍스트 형식만 지원합니다. 각 CSV 메시지는 한 줄이며, 줄 끝에 줄바꿈 문자가 포함되지 않습니다.
Kafka 버전기본적으로 Kafka 0.10.0.0 이상을 지원합니다. 0.10.0.0 미만의 Kafka 버전(0.9.0, 0.8.2, 0.8.1, 0.8.0)을 사용하려면 BE 설정 kafka_broker_version_fallback을 호환하려는 이전 버전으로 변경하거나, 작업 생성 시 property.broker.version.fallback을 직접 설정합니다. 이전 버전을 사용하면 시간 기준으로 Kafka 파티션 오프셋을 설정하는 기능 등 Routine Load의 일부 새 기능을 사용할 수 없을 수 있습니다.

기본 원리​

Routine Load는 Kafka 토픽의 데이터를 지속적으로 소비하여 Doris에 기록합니다. Doris에서 Routine Load 작업을 생성하면 여러 데이터 적재 태스크로 구성된 장기 실행 데이터 적재 작업이 생성됩니다.

  • Load Job: Routine Load Job은 데이터 소스의 데이터를 지속적으로 소비하는 장기 실행 데이터 적재 작업입니다.
  • Load Task: 데이터 적재 작업은 실제 데이터 소비를 수행하는 여러 데이터 적재 태스크로 나뉩니다. 각 태스크는 독립적인 트랜잭션입니다.

Routine Load의 자세한 처리 흐름은 다음 그림과 같습니다.

전체 흐름은 다음과 같습니다.

  1. 클라이언트가 FE에 Routine Load 작업 생성 요청을 제출합니다. FE는 Routine Load Manager를 통해 장기 실행 데이터 적재 작업(Routine Load Job)을 생성합니다.
  2. FE는 Job Scheduler를 통해 Routine Load Job을 여러 Routine Load Task로 나눕니다. 그런 다음 Task Scheduler가 이를 BE 노드에 할당합니다.
  3. BE에서 Routine Load Task의 데이터 적재가 완료되면 트랜잭션을 FE에 커밋하고 작업의 메타데이터를 업데이트합니다.
  4. Routine Load Task가 커밋되면 새 태스크를 생성하거나 시간 초과된 태스크를 재시도합니다.
  5. 새로 생성된 Routine Load Task는 Task Scheduler를 통해 계속해서 스케줄링됩니다.

자동 복구 메커니즘​

Routine Load는 작업의 고가용성을 보장하기 위해 자동 복구 메커니즘을 제공합니다. 작업이 예기치 않게 일시 중지되면 Routine Load Scheduler 스레드가 작업의 자동 복구를 시도합니다. Kafka 측의 예기치 않은 장애나 그 밖의 실행 불가 상황이 발생하더라도 Kafka가 복구되면 이 메커니즘을 통해 수동 개입 없이 데이터 적재 작업을 정상적으로 계속 실행할 수 있습니다.

다음 표는 자동으로 복구되는 경우와 수동 개입이 필요한 경우를 보여 줍니다.

일시 중지 원인자동 복구권장 조치
Kafka broker에 일시적으로 연결할 수 없거나 네트워크가 불안정한 경우예Scheduler가 period_of_auto_resume_min 간격으로 자동 재시도합니다.
사용자가 PAUSE ROUTINE LOAD를 수동으로 실행한 경우아니요RESUME ROUTINE LOAD를 수동으로 실행합니다.
데이터 품질 문제(max_filter_ratio 또는 max_error_number 초과)아니요ErrorLogUrls를 확인하고 데이터나 매개변수를 조정한 다음 RESUME을 실행합니다.
데이터베이스나 테이블 삭제 등 복구할 수 없는 메타데이터 예외아니요테이블을 다시 생성하거나 작업을 다시 만듭니다.

빠른 시작​

이 섹션에서는 실행 가능한 최소 예제를 통해 Kafka에서 데이터를 적재하는 Routine Load 작업을 생성하는 방법과 작업 조회, 일시 중지, 재개, 수정 및 중지의 기본 작업을 설명합니다.

데이터 적재 작업 생성​

CREATE ROUTINE LOAD 명령으로 장기 실행 Routine Load 데이터 적재 태스크를 생성할 수 있습니다. Routine Load는 CSV 및 JSON 데이터를 소비할 수 있습니다.

CSV 데이터 적재​

  1. Kafka 샘플 데이터를 준비합니다.

    kafka-console-consumer.sh --bootstrap-server localhost:9092 --topic test-routine-load-csv --from-beginning
    1,Emily,25
    2,Benjamin,35
    3,Olivia,28
    4,Alexander,60
    5,Ava,17
    6,William,69
    7,Sophia,32
    8,James,64
    9,Emma,37
    10,Liam,64

  2. 데이터 적재 대상 테이블을 생성합니다.

    CREATE TABLE testdb.test_routineload_tbl(
        user_id            BIGINT       NOT NULL COMMENT "user id",
        name               VARCHAR(20)           COMMENT "name",
        age                INT                   COMMENT "age"
    )
    DUPLICATE KEY(user_id)
    DISTRIBUTED BY HASH(user_id) BUCKETS 10;

  3. Routine Load 데이터 적재 작업을 생성합니다.

    CREATE ROUTINE LOAD testdb.example_routine_load_csv ON test_routineload_tbl
    COLUMNS TERMINATED BY ",",
    COLUMNS(user_id, name, age)
    FROM KAFKA(
        "kafka_broker_list" = "192.168.88.62:9092",
        "kafka_topic" = "test-routine-load-csv",
        "property.kafka_default_offsets" = "OFFSET_BEGINNING"
    );

JSON 데이터 적재​

  1. Kafka 샘플 데이터를 준비합니다.

    kafka-console-consumer.sh --bootstrap-server localhost:9092 --topic test-routine-load-json --from-beginning
    {"user_id":1,"name":"Emily","age":25}
    {"user_id":2,"name":"Benjamin","age":35}
    {"user_id":3,"name":"Olivia","age":28}
    {"user_id":4,"name":"Alexander","age":60}
    {"user_id":5,"name":"Ava","age":17}
    {"user_id":6,"name":"William","age":69}
    {"user_id":7,"name":"Sophia","age":32}
    {"user_id":8,"name":"James","age":64}
    {"user_id":9,"name":"Emma","age":37}
    {"user_id":10,"name":"Liam","age":64}

  2. 데이터 적재 대상 테이블을 생성합니다.

    CREATE TABLE testdb.test_routineload_tbl(
        user_id            BIGINT       NOT NULL COMMENT "user id",
        name               VARCHAR(20)           COMMENT "name",
        age                INT                   COMMENT "age"
    )
    DUPLICATE KEY(user_id)
    DISTRIBUTED BY HASH(user_id) BUCKETS 10;

  3. Routine Load 데이터 적재 작업을 생성합니다.

    CREATE ROUTINE LOAD testdb.example_routine_load_json ON test_routineload_tbl
    COLUMNS(user_id,name,age)
    PROPERTIES(
        "format"="json",
        "jsonpaths"="[\"$.user_id\",\"$.name\",\"$.age\"]"
    )
    FROM KAFKA(
        "kafka_broker_list" = "192.168.88.62:9092",
        "kafka_topic" = "test-routine-load-json",
        "property.kafka_default_offsets" = "OFFSET_BEGINNING"
    );
참고

JSON 파일의 루트에 있는 JSON 객체를 적재하려면 jsonpaths를 $.으로 설정합니다. 예: PROPERTIES("jsonpaths"="$.").

데이터 적재 상태 조회​

Routine Load의 상태는 두 가지 수준에서 확인할 수 있습니다.

  • 데이터 적재 작업: 데이터 적재 작업의 대상 테이블, 하위 태스크 수, 데이터 적재 지연 상태, 데이터 적재 설정 및 데이터 적재 결과를 조회합니다.
  • 데이터 적재 태스크: 데이터 적재 하위 태스크의 상태, 소비 진행 상황 및 태스크가 할당된 BE 노드를 조회합니다.

데이터 적재 작업 일시 중지​

PAUSE ROUTINE LOAD 명령으로 데이터 적재 작업을 일시 중지할 수 있습니다. 일시 중지된 작업은 PAUSED 상태로 전환되지만 종료되지는 않습니다. RESUME ROUTINE LOAD 명령으로 다시 시작할 수 있습니다.

PAUSE ROUTINE LOAD FOR testdb.example_routine_load_csv;

데이터 적재 작업 재개​

PAUSED 상태의 데이터 적재 작업은 RESUME ROUTINE LOAD 명령으로 재개할 수 있습니다.

RESUME ROUTINE LOAD FOR testdb.example_routine_load_csv;

데이터 적재 작업 수정​

ALTER ROUTINE LOAD 명령으로 생성된 데이터 적재 작업을 수정할 수 있습니다. 수정하기 전에 먼저 PAUSE ROUTINE LOAD로 작업을 일시 중지합니다. 수정을 마치면 RESUME ROUTINE LOAD로 재개합니다.

예를 들어, 목표 동시 실행 수 매개변수 desired_concurrent_number와 Kafka 토픽 정보를 수정하려면 다음과 같이 실행합니다.

ALTER ROUTINE LOAD FOR testdb.example_routine_load_csv
PROPERTIES(
    "desired_concurrent_number" = "3"
)
FROM KAFKA(
    "kafka_broker_list" = "192.168.88.60:9092",
    "kafka_topic" = "test-topic"
);

데이터 적재 작업 취소​

STOP ROUTINE LOAD 명령으로 Routine Load 데이터 적재 작업을 중지하고 삭제할 수 있습니다. 삭제된 데이터 적재 작업은 복구할 수 없으며, SHOW ROUTINE LOAD 명령으로 조회할 수도 없습니다.

STOP ROUTINE LOAD FOR testdb.example_routine_load_csv;

Compute Group 바인딩​

스토리지와 컴퓨팅 분리 모드에서 Routine Load의 Compute Group 선택은 다음 우선순위를 따릅니다.

  1. use db@cluster 문으로 지정한 Compute Group을 선택합니다.
  2. 사용자 속성 default_compute_group으로 지정한 Compute Group을 선택합니다.
  3. 현재 사용자에게 접근 권한이 있는 Compute Group 중 하나를 선택합니다.

스토리지와 컴퓨팅 통합 모드에서는 사용자 속성 resource_tags.location으로 지정한 Compute Group을 선택합니다. 사용자 속성에 Compute Group이 지정되어 있지 않으면 이름이 default인 Compute Group을 사용합니다.

참고

Routine Load 작업의 Compute Group은 작업 생성 시에만 지정할 수 있습니다. 작업을 생성한 후에는 바인딩된 Compute Group을 변경할 수 없습니다.

데이터 적재 명령 구문​

장기 실행 Routine Load 데이터 적재 작업을 생성하는 구문은 다음과 같습니다.

CREATE ROUTINE LOAD [<db_name>.]<job_name> [ON <tbl_name>]
[merge_type]
[load_properties]
[job_properties]
FROM KAFKA [data_source_properties]
[COMMENT "<comment>"]

각 모듈의 설명은 다음과 같습니다.

모듈설명
db_name데이터 적재 태스크를 생성할 데이터베이스를 지정합니다.
job_name생성할 데이터 적재 태스크의 이름을 지정합니다. 동일한 데이터베이스 내에 이름이 같은 태스크가 존재할 수 없습니다.
tbl_name데이터를 적재할 테이블의 이름을 지정합니다. 선택 사항입니다. 지정하지 않으면 동적 테이블 방식을 사용하며, Kafka 데이터에 테이블 이름이 포함되어 있어야 합니다.
merge_type데이터 병합 유형입니다. 기본값은 APPEND입니다.

다음 세 가지 옵션이 있습니다.

- APPEND: 추가 방식의 데이터 적재.

- MERGE: 병합 방식의 데이터 적재.

- DELETE: 적재할 데이터를 모두 삭제.

comment데이터 적재 작업에 대한 설명을 지정합니다.

데이터 적재 설정 매개변수​

Routine Load 작업을 생성할 때 CREATE ROUTINE LOAD 명령으로 각 모듈의 데이터 적재 설정 매개변수를 지정할 수 있습니다.

tbl_name 절​

데이터를 적재할 테이블의 이름을 지정합니다. 선택 사항입니다.

지정하지 않으면 동적 테이블 방식을 사용하며, Kafka 데이터에 테이블 이름이 포함되어 있어야 합니다. 현재는 Kafka Value에서 동적 테이블 이름을 추출하는 방식만 지원하며, 데이터는 다음 형식을 따라야 합니다. JSON의 경우 table_name|{"col1": "val1", "col2": "val2"} 형식을 사용합니다. 여기서 tbl_name은 테이블 이름이고, |는 테이블 이름과 테이블 데이터 사이의 구분자입니다. CSV 형식의 데이터도 이와 유사합니다. 예: table_name|val1,val2,val3.

참고

여기서 table_name은 Doris의 테이블 이름과 정확히 일치해야 하며, 그렇지 않으면 데이터 적재에 실패합니다. 동적 테이블은 column_mapping을 지원하지 않습니다.

merge_type 절​

merge_type 모듈로 데이터 병합 유형을 지정할 수 있습니다. 다음 세 가지 옵션이 있습니다.

  • APPEND: 추가 방식의 데이터 적재입니다.
  • MERGE: 병합 방식의 데이터 적재입니다. Unique Key 모델에만 적용할 수 있습니다. Delete Flag 컬럼을 표시하려면 반드시 [DELETE ON] 모듈과 함께 사용해야 합니다.
  • DELETE: 적재할 데이터를 모두 삭제합니다.
load_properties 절​

load_properties 모듈로 적재할 데이터의 속성을 설명할 수 있습니다. 구문은 다음과 같습니다.

[COLUMNS TERMINATED BY <column_separator>,]
[COLUMNS (<column1_name>[, <column2_name>, <column_mapping>, ...]),]
[WHERE <where_expr>,]
[PARTITION(<partition1_name>, [<partition2_name>, <partition3_name>, ...]),]
[DELETE ON <delete_expr>,]
[ORDER BY <order_by_column1>[, <order_by_column2>, <order_by_column3>, ...]]

각 모듈에 해당하는 매개변수는 다음과 같습니다.

하위 모듈매개변수설명
COLUMNS TERMINATED BY<column_separator>컬럼 구분자를 지정합니다. 기본값은 \t입니다. 예를 들어 쉼표를 구분자로 지정하려면 COLUMN TERMINATED BY ","를 사용합니다. null 처리 시 유의 사항:

- null 값은 \n으로 표현합니다. a,\n,b는 가운데 컬럼이 null 값임을 나타냅니다.

- 빈 문자열은 해당 데이터를 비워 둡니다. a,,b는 가운데 컬럼이 빈 문자열('')임을 나타냅니다.

COLUMNS<column_name>대응하는 컬럼 이름을 지정합니다. 예를 들어 데이터 적재 컬럼을 (k1, k2, k3)로 지정하려면 COLUMNS(k1, k2, k3)를 사용합니다. 다음과 같은 경우에는 COLUMNS 절을 생략할 수 있습니다.

- CSV의 컬럼이 테이블의 컬럼과 일대일로 대응하는 경우.

- JSON의 키 이름이 테이블의 컬럼 이름과 같은 경우.

 <column_mapping>데이터 적재 중 컬럼 매핑을 통해 컬럼을 필터링하고 변환할 수 있습니다. 예를 들어 대상 컬럼 k4를 k3 컬럼에서 k3+1 수식으로 계산하려면 COLUMNS(k1, k2, k3, k4 = k3 + 1)을 사용합니다. 자세한 내용은 데이터 변환을 참조하세요.
WHERE<where_expr>적재할 원본 데이터를 조건에 따라 필터링합니다. 예를 들어 age > 30인 데이터만 적재하려면 WHERE age > 30을 사용합니다.
PARTITION<partition_name>데이터를 적재할 대상 테이블의 파티션을 지정합니다. 지정하지 않으면 해당 파티션에 데이터가 자동으로 적재됩니다. 예를 들어 p1 및 p2 파티션에 적재하려면 PARTITION(p1, p2)를 사용합니다.
DELETE ON<delete_expr>MERGE 데이터 적재 모드에서 delete_expr로 삭제할 컬럼을 표시합니다. 예를 들어 MERGE 중 age > 30인 컬럼을 삭제하려면 DELETE ON age > 30을 사용합니다.
ORDER BY<order_by_column>Unique Key 모델에서만 유효합니다. 데이터의 순서를 보장하기 위해 적재할 데이터의 Sequence Column을 지정합니다. 예를 들어 create_time을 Sequence Column으로 지정하려면 ORDER BY create_time을 사용합니다. 자세한 내용은 데이터 업데이트 / Sequence Column을 참조하세요.
job_properties 절​

Routine Load 데이터 적재 작업을 생성할 때 job_properties 절로 데이터 적재 작업의 속성을 지정할 수 있습니다. 구문은 다음과 같습니다.

PROPERTIES ("<key1>" = "<value1>"[, "<key2>" = "<value2>" ...])

job_properties 절의 구체적인 매개변수 옵션은 다음과 같습니다.

매개변수설명
desired_concurrent_number

기본값: 256

단일 데이터 적재 태스크의 목표 동시 실행 수입니다. 데이터 적재 중 목표 하위 태스크 동시 실행 수는 실제 동시 실행 수와 다를 수 있습니다. 실제 동시 실행 수는 다음과 같이 계산합니다.

min(topic_partition_num, desired_concurrent_number, max_routine_load_task_concurrent_num). 각 항목의 의미는 다음과 같습니다.

- topic_partition_num: Kafka 토픽의 파티션 수.

- desired_concurrent_number: 이 매개변수의 값.

- max_routine_load_task_concurrent_num: FE에 설정된 Routine Load의 최대 태스크 병렬 처리 수.

max_batch_interval각 하위 태스크의 최대 실행 시간입니다. 단위는 초이며, 0보다 커야 합니다. 기본값은 60입니다. max_batch_interval, max_batch_rows 및 max_batch_size는 함께 하위 태스크의 실행 임계값을 구성합니다. 이 중 하나에 도달하면 데이터 적재 하위 태스크가 종료되고 새 하위 태스크가 생성됩니다.
max_batch_rows각 하위 태스크가 읽을 수 있는 최대 행 수입니다. 200000 이상이어야 합니다. 기본값은 20000000입니다. max_batch_interval, max_batch_rows 및 max_batch_size는 함께 하위 태스크의 실행 임계값을 구성합니다. 이 중 하나에 도달하면 데이터 적재 하위 태스크가 종료되고 새 하위 태스크가 생성됩니다.
max_batch_size각 하위 태스크가 읽을 수 있는 최대 바이트 수입니다. 단위는 바이트이고, 범위는 100 MB부터 1 GB까지이며, 기본값은 1 GB입니다. max_batch_interval, max_batch_rows 및 max_batch_size는 함께 하위 태스크의 실행 임계값을 구성합니다. 이 중 하나에 도달하면 데이터 적재 하위 태스크가 종료되고 새 하위 태스크가 생성됩니다.
max_error_number샘플링 구간에서 허용되는 최대 오류 행 수입니다. 0 이상이어야 합니다. 기본값은 0으로, 오류 행을 허용하지 않습니다. 샘플링 구간은 max_batch_rows * 10입니다. 샘플링 구간 내 오류 행 수가 max_error_number를 초과하면 Routine Load 작업이 일시 중지됩니다. 데이터 품질 문제를 확인하려면 수동 개입이 필요합니다. 데이터 품질 문제는 ErrorLogUrls 필드를 통해 확인할 수 있으며, 이 필드는 SHOW ROUTINE LOAD 명령의 결과에 표시됩니다. where 조건으로 필터링된 행은 오류 행으로 계산하지 않습니다.
strict_mode엄격 모드의 활성화 여부입니다. 기본적으로 비활성화되어 있습니다. 엄격 모드는 데이터 적재 중 컬럼 타입 변환을 엄격하게 필터링합니다. 활성화하면 원본 데이터의 null이 아닌 값이 컬럼 타입 변환 후 NULL이 되는 경우 해당 데이터를 필터링합니다.

필터링 정책:

- 엄격 모드는 파생 컬럼(함수 변환으로 생성된 컬럼)에 영향을 주지 않습니다.

- 컬럼 타입을 변환해야 하는 경우 타입이 잘못된 데이터를 필터링합니다. 해당 데이터는 ErrorLogUrls에서 확인할 수 있으며, 이 필드는 SHOW ROUTINE LOAD 결과에 표시됩니다.

- 적재할 컬럼 타입에 범위 제한이 있는 경우, 원본 데이터가 타입 변환은 통과하지만 범위 제한을 통과하지 못하면 엄격 모드는 영향을 주지 않습니다. 예를 들어 타입이 decimal(1,0)이고 원본 데이터가 10이면, 데이터는 타입 변환을 통과하지만 컬럼에 선언된 범위에는 속하지 않습니다. 자세한 내용은 엄격 모드를 참조하세요.

timezone데이터 적재 작업에서 사용할 시간대를 지정합니다. 기본값은 세션의 timezone 매개변수입니다. 이 매개변수는 데이터 적재에 사용되는 모든 시간대 관련 함수의 결과에 영향을 줍니다.
format적재할 데이터의 형식을 지정합니다. 기본값은 CSV입니다. JSON 형식도 지원합니다.
jsonpaths적재할 데이터의 형식이 JSON이면 jsonpaths로 JSON 데이터에서 추출할 필드를 지정할 수 있습니다. 예: "jsonpaths" = "[\"$.userid\",\"$.username\",\"$.age\",\"$.city\"]"
json_root적재할 데이터의 형식이 JSON이면 json_root로 JSON 데이터의 루트 노드를 지정할 수 있습니다. Doris는 json_root로 지정된 루트 노드에서 요소를 추출하고 파싱합니다. 기본값은 비어 있습니다. 예: "json_root" = "$.RECORDS"
strip_outer_array적재할 데이터의 형식이 JSON이고 strip_outer_array가 true이면, JSON 데이터가 배열 형태이며 배열의 각 요소를 하나의 행으로 처리한다는 의미입니다. 기본값은 false입니다. Kafka의 JSON 데이터는 배열 형태인 경우가 많으며, 이때 가장 바깥쪽은 대괄호 []로 둘러싸여 있습니다. 이 경우 "strip_outer_array" = "true"를 지정할 수 있습니다. 예를 들어 다음 데이터는 두 행으로 파싱됩니다. [{"user_id":1,"name":"Emily","age":25},{"user_id":2,"name":"Benjamin","age":35}]
send_batch_parallelism배치 데이터를 전송할 때의 병렬 처리 수를 설정합니다. 이 값이 BE 설정 max_send_batch_parallelism_per_job을 초과하면 coordinator 역할을 하는 BE가 max_send_batch_parallelism_per_job의 값을 사용합니다.
load_to_single_tablet태스크의 데이터를 해당 파티션의 단일 tablet에만 적재할 수 있도록 지원합니다. 기본값은 false입니다. 이 매개변수는 무작위 버킷 분할을 사용하는 OLAP 테이블에 데이터를 적재할 때만 설정할 수 있습니다.
partial_columns부분 컬럼 업데이트의 활성화 여부를 지정합니다. 기본값은 false입니다. 테이블 모델이 Unique이고 Merge on Write를 사용하는 경우에만 설정할 수 있습니다. 단일 스트림 다중 테이블 데이터 적재에서는 이 매개변수를 지원하지 않습니다. 자세한 내용은 부분 컬럼 업데이트를 참조하세요.
unique_key_update_modeUnique Key 테이블의 업데이트 모드를 지정합니다. 옵션:
  • UPSERT(기본값): 표준 전체 행 삽입 또는 업데이트.
  • UPDATE_FIXED_COLUMNS: 모든 행이 동일한 컬럼을 업데이트하는 부분 컬럼 업데이트. partial_columns=true와 동일합니다.
  • UPDATE_FLEXIBLE_COLUMNS: 각 행이 서로 다른 컬럼을 업데이트할 수 있는 유연한 부분 컬럼 업데이트. JSON 형식이 필요하며 테이블에 enable_unique_key_skip_bitmap_column=true가 설정되어 있어야 합니다. jsonpaths, fuzzy_parse, COLUMNS 절 또는 WHERE 절과 함께 사용할 수 없습니다.
자세한 내용은 부분 컬럼 업데이트를 참조하세요.
partial_update_new_key_behaviorUnique Merge on Write 테이블에서 부분 컬럼 업데이트를 수행할 때 새로 삽입되는 행의 처리 방식을 지정합니다. APPEND와 ERROR의 두 가지 유형이 있습니다.
- APPEND: 새 행의 삽입을 허용합니다.
- ERROR: 새 행을 삽입하면 데이터 적재가 실패하고 오류가 보고됩니다.
max_filter_ratio샘플링 구간에서 허용되는 최대 필터링 비율입니다. 0 이상 1 이하여야 합니다. 기본값은 1.0으로, 모든 오류 행을 허용합니다. 샘플링 구간은 max_batch_rows * 10입니다. 샘플링 구간의 오류 행 수 / 전체 행 수가 max_filter_ratio를 초과하면 Routine Load 작업이 일시 중지됩니다. 데이터 품질 문제를 확인하려면 수동 개입이 필요합니다. where 조건으로 필터링된 행은 오류 행으로 계산하지 않습니다.
enclose필드 감싸기 문자를 지정합니다. CSV 데이터 필드에 행 구분자나 컬럼 구분자가 포함되어 있으면 단일 바이트 문자를 필드 감싸기 문자로 지정하여 의도하지 않은 분리를 방지할 수 있습니다. 예를 들어 컬럼 구분자가 ,이고 필드 감싸기 문자가 '이면, 데이터 a,'b,c'에서 b,c를 하나의 필드로 파싱합니다.
escape이스케이프 문자를 지정합니다. 필드 내에서 필드 감싸기 문자와 동일한 문자를 이스케이프하는 데 사용합니다. 예를 들어 데이터 a,'b,'c'의 필드 감싸기 문자가 '일 때 b,'c를 하나의 필드로 파싱하려면 단일 바이트 이스케이프 문자(예: \)를 지정하고 데이터를 a,'b,\'c'로 수정해야 합니다.

data_source_properties 절​

Routine Load 데이터 적재 작업을 생성할 때 data_source_properties 절로 Kafka 데이터 소스의 속성을 지정할 수 있습니다. 구문은 다음과 같습니다.

FROM KAFKA ("<key1>" = "<value1>"[, "<key2>" = "<value2>" ...])

data_source_properties 절의 구체적인 매개변수 옵션은 다음과 같습니다.

매개변수설명
kafka_broker_listKafka broker 연결 정보를 지정합니다. 형식은 <kafka_broker_ip>:<kafka port>입니다. 여러 broker는 쉼표로 구분합니다. 예: "kafka_broker_list" = "<broker1_ip>:9092,<broker2_ip>:9092"
kafka_topic구독할 Kafka 토픽을 지정합니다. 단일 데이터 적재 작업은 하나의 Kafka 토픽만 소비할 수 있습니다.
kafka_partitions구독할 Kafka 파티션을 지정합니다. 지정하지 않으면 기본적으로 모든 파티션을 소비합니다.
kafka_offsets소비할 Kafka 파티션의 소비 시작 오프셋입니다. 시간을 지정하면 해당 시간 이상인 가장 최근 오프셋부터 소비를 시작합니다. 오프셋은 0 이상의 구체적인 오프셋 값 또는 다음 형식 중 하나로 지정할 수 있습니다.

- OFFSET_BEGINNING: 데이터가 존재하는 위치부터 구독합니다.

- OFFSET_END: 끝부분부터 구독합니다.

- 시간 형식. 예: "2021-05-22 11:00:00".

지정하지 않으면 기본적으로 토픽의 모든 파티션을 OFFSET_END부터 구독합니다. 여러 소비 시작 오프셋을 쉼표로 구분하여 지정할 수 있습니다. 예: "kafka_offsets" = "101,0,OFFSET_BEGINNING,OFFSET_END" 또는 "kafka_offsets" = "2021-05-22 11:00:00,2021-05-22 11:00:00".

참고: 시간 형식과 OFFSET 형식을 혼용할 수 없습니다.

property사용자 지정 Kafka 매개변수를 지정합니다. kafka shell의 --property 매개변수와 동일합니다. 매개변수 값이 파일이면 값 앞에 FILE: 키워드를 붙입니다. 파일 생성 방법은 CREATE FILE 명령을 참조하세요. 지원되는 사용자 지정 매개변수에 대한 자세한 내용은 공식 librdkafka CONFIGURATION 문서의 클라이언트 측 설정을 참조하세요. 예: "property.client.id" = "12345", "property.group.id" = "group_id_0", "property.ssl.ca.location" = "FILE:ca.pem".

data_source_properties의 kafka property 매개변수로 보안 접근 옵션을 설정할 수 있습니다. Doris는 현재 plaintext(기본값), SSL, PLAIN 및 Kerberos 등 여러 Kafka 보안 프로토콜을 지원합니다.

단일 스트림 다중 테이블 데이터 적재​

이름이 test1인 Kafka 정기 동적 다중 테이블 데이터 적재 태스크를 example_db에 생성합니다. group.id와 client.id를 지정하고, 기본적으로 모든 파티션을 자동으로 소비하며, 데이터가 존재하는 위치(OFFSET_BEGINNING)부터 구독합니다.

Kafka의 데이터를 tbl1 및 tbl2 테이블에 적재하고, 이 테이블들이 example_db에 있다고 가정합니다. 이름이 test1인 Routine Load 태스크를 생성하여 Kafka 토픽 my_topic의 데이터를 tbl1 및 tbl2 모두에 적재할 수 있습니다.

CREATE ROUTINE LOAD example_db.test1
FROM KAFKA
(
    "kafka_broker_list" = "broker1:9092,broker2:9092,broker3:9092",
    "kafka_topic" = "my_topic",
    "property.kafka_default_offsets" = "OFFSET_BEGINNING"
);

이 경우 Kafka 데이터에 테이블 이름이 포함되어 있어야 합니다. 현재는 Kafka Value에서 동적 테이블 이름을 추출하는 방식만 지원하며, 데이터는 다음 형식을 따라야 합니다. JSON의 경우 table_name|{"col1": "val1", "col2": "val2"} 형식을 사용합니다. 여기서 tbl_name은 테이블 이름이고, |는 테이블 이름과 테이블 데이터 사이의 구분자입니다. CSV 형식의 데이터도 이와 유사합니다. 예: table_name|val1,val2,val3.

참고

여기서 table_name은 Doris의 테이블 이름과 정확히 일치해야 하며, 그렇지 않으면 데이터 적재에 실패합니다. 동적 테이블은 column_mapping을 지원하지 않습니다.

자주 묻는 질문(FAQ)​

Routine Load 작업이 자동으로 PAUSED 상태로 전환되면 어떻게 해야 하나요?​

일반적으로 데이터 품질 문제나 Kafka 측 예외가 원인입니다.

  1. SHOW ROUTINE LOAD FOR <job_name>을 실행하여 ReasonOfStateChanged와 ErrorLogUrls를 확인합니다.
  2. 잘못된 데이터가 원인이면 max_filter_ratio와 max_error_number를 적절히 높입니다.
  3. Kafka 예외가 원인이면 broker와 토픽에 접근할 수 있는지 확인한 후 RESUME ROUTINE LOAD를 실행하여 복구합니다.

Offset out of range 또는 out of range 오류는 어떻게 처리하나요?​

일반적으로 기록된 오프셋이 Kafka에서 이미 삭제되었음을 의미합니다(보존 정책에 따라 제거됨).

  1. 작업을 일시 중지합니다. PAUSE ROUTINE LOAD FOR <job_name>.
  2. ALTER ROUTINE LOAD를 사용하여 kafka_offsets를 유효한 위치(예: OFFSET_BEGINNING 또는 구체적인 오프셋)로 재설정합니다.
  3. RESUME ROUTINE LOAD를 실행하여 작업을 복구합니다.

Server kafka/xxx@EXAMPLE.COM not found in Kerberos database 오류가 발생하면 어떻게 하나요?​

Kerberos 인증을 사용하는 경우 rdnbs=true를 krb5.conf에 설정합니다.

Server certificate verification failed 또는 기타 SSL 오류가 발생하면 어떻게 하나요?​

BE 측에 신뢰할 수 있는 CA 인증서가 설정되어 있지 않으면 "property.enable.ssl.certificate.verification" = "false"로 설정하거나, "property.ssl.ca.location" = "/path/to/ca-cert.pem"을 명시적으로 지정합니다.

목표 동시 실행 수(desired_concurrent_number)가 적용되지 않는 이유는 무엇인가요?​

실제 동시 실행 수는 다음 세 값 중 최솟값으로 결정됩니다.

min(topic_partition_num, desired_concurrent_number, max_routine_load_task_concurrent_num)

Kafka 토픽의 파티션 수와 FE 설정 max_routine_load_task_concurrent_num을 확인하세요.

이전 Kafka 버전(< 0.10.0.0)은 어떻게 사용하나요?​

BE 설정에서 kafka_broker_version_fallback을 설정하거나, 작업 생성 시 property.broker.version.fallback으로 호환 버전을 지정합니다.

단일 스트림 다중 테이블 데이터 적재의 대상 테이블은 어떻게 지정하나요?​

Kafka 메시지 Value에 table_name|<data> 형식으로 테이블 이름이 포함되어 있어야 하며, 테이블 이름은 Doris의 테이블 이름과 정확히 일치해야 합니다. 동적 테이블은 column_mapping을 지원하지 않습니다.

적재에 실패한 잘못된 데이터는 어떻게 확인하나요?​

SHOW ROUTINE LOAD FOR <job_name>을 실행하고 결과의 ErrorLogUrls 필드를 확인합니다. 브라우저나 wget으로 해당 URL에 접근하면 필터링된 오류 데이터의 샘플과 오류 원인을 확인할 수 있습니다.

Routine Load 작업을 수정하기 전에 반드시 일시 중지해야 하나요?​

예. ALTER ROUTINE LOAD 명령을 실행하려면 작업이 PAUSED 상태여야 합니다. 수정 순서는 PAUSE ROUTINE LOAD -> ALTER ROUTINE LOAD -> RESUME ROUTINE LOAD입니다.
