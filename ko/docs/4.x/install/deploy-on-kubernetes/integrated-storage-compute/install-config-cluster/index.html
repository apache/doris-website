02 Doris 클러스터 구성

클러스터 계획​

기본 DorisCluster 리소스의 FE 및 BE 이미지는 최신 버전이 아닐 수 있으며, 기본 복제본 수는 모두 3개입니다. 기본적으로 FE는 6c 12Gi의 컴퓨팅 리소스를, BE는 8c 16Gi를 사용합니다. 다음 절에서는 필요에 맞게 이러한 기본값을 조정하는 방법을 설명합니다.

이미지 설정​

Doris Operator는 Doris 버전과 독립적으로 동작합니다. Doris Operator는 Doris 2.0 이상 버전의 배포를 지원합니다.

FE 이미지 설정

FE 이미지를 지정하려면 다음과 같이 구성합니다:

spec:
  feSpec:
    image: ${image}

${image}를 배포할 이미지 이름으로 바꾼 다음, 배포할 DorisCluster 리소스의 구성을 업데이트합니다. Doris에서 제공하는 공식 FE 이미지를 사용할 수 있습니다.

BE 이미지 설정

BE 이미지를 지정하려면 다음과 같이 구성합니다:

spec:
  beSpec:
    image: ${image}

${image}를 배포할 이미지 이름으로 바꾼 다음, 배포할 DorisCluster 리소스의 구성을 업데이트합니다. Doris에서 제공하는 공식 BE 이미지를 사용할 수 있습니다.

복제본 설정​

FE 복제본 수 변경

기본 FE 복제본 수를 3개에서 5개로 변경하려면 다음과 같이 구성합니다:

spec:
  feSpec:
    replicas: 5

배포할 DorisCluster 리소스의 구성을 업데이트합니다.

BE 복제본 수 변경

기본 BE 복제본 수를 3개에서 5개로 변경하려면 다음과 같이 구성합니다:

spec:
  beSpec:
    replicas: 5

배포할 DorisCluster 리소스의 구성을 업데이트합니다.

컴퓨팅 리소스 설정​

FE 컴퓨팅 리소스 설정

기본 FE 컴퓨팅 리소스는 6c 12Gi입니다. 이를 8c 16Gi로 변경하려면 다음과 같이 구성합니다:

spec:
  feSpec:
    requests:
      cpu: 8
      memory: 16Gi
    limits:
      cpu: 8
      memory: 16Gi

배포할 DorisCluster 리소스의 구성을 업데이트합니다.

BE 컴퓨팅 리소스 설정

기본 BE 컴퓨팅 리소스는 8c 16Gi입니다. 이를 16c 32Gi로 변경하려면 다음과 같이 구성합니다:

spec:
  beSpec:
    requests:
      cpu: 16
      memory: 32Gi
    limits:
      cpu: 16
      memory: 32Gi

배포할 DorisCluster 리소스의 구성을 업데이트합니다.

팁

FE와 BE를 시작하는 데 필요한 최소 리소스는 4c 8Gi입니다. 일반적인 기능 테스트에는 8c 8Gi를 권장합니다.

사용자 지정 시작 구성​

Kubernetes에서 Doris는 ConfigMap을 사용하여 구성 파일을 서비스와 분리합니다. 기본적으로 서비스는 이미지의 기본 구성을 시작 매개변수로 사용합니다. FE 구성 문서와 BE 구성 문서를 참고하여 사용자 지정 시작 매개변수를 특정 ConfigMap에 미리 준비합니다. 구성이 완료되면 대상 DorisCluster 리소스가 있는 네임스페이스에 배포합니다.

FE 사용자 지정 시작 구성​

1단계: ConfigMap 구성 및 배포​

다음 예는 Doris FE에서 사용할 수 있는 fe-conf라는 이름의 ConfigMap을 정의합니다:

  name: fe-conf
  labels:
    app.kubernetes.io/component: fe

    LOG_DIR = ${DORIS_HOME}/log
    # For jdk 8
    JAVA_OPTS="-Dfile.encoding=UTF-8 -Djavax.security.auth.useSubjectCredsOnly=false -Xss4m -Xmx8192m -XX:+UnlockExperimentalVMOptions -XX:+UseG1GC -XX:MaxGCPauseMillis=200 -XX:+PrintGCDateStamps -XX:+PrintGCDetails -XX:+PrintClassHistogramAfterFullGC -Xloggc:$LOG_DIR/log/fe.gc.log.$CUR_DATE -XX:+UseGCLogFileRotation -XX:NumberOfGCLogFiles=10 -XX:GCLogFileSize=50M -Dlog4j2.formatMsgNoLookups=true"

    enable_fqdn_mode = true

ConfigMap을 사용하여 FE 시작 구성을 마운트할 때 구성의 키는 반드시 fe.conf여야 합니다. 구성 파일을 준비한 후 다음 명령으로 DorisCluster 리소스를 배포할 네임스페이스에 배포합니다.

kubectl -n ${namespace} apply -f ${feConfigMapFile}.yaml

여기서 ${namespace}는 대상 DorisCluster 리소스를 배포할 네임스페이스이고, ${feConfigMapFile}은 위 구성이 들어 있는 파일의 이름입니다.

2단계: DorisCluster 리소스 구성​

fe-conf에 해당하는 ConfigMap을 예로 들면, 배포된 DorisCluster 리소스에 다음 정보를 추가합니다:

spec:
  feSpec:
    configMapInfo:
      configMapName: fe-conf
      resolveKey: fe.conf
팁

Kubernetes 배포에는 FQDN 모드를 권장합니다. 시작 구성에 enable_fqdn_mode=true를 추가합니다. IP 모드를 사용하려고 하며 Kubernetes 클러스터에서 재시작 후에도 Pod IP가 변경되지 않음을 보장할 수 있다면, 이슈 #138을 참고하여 IP 모드 시작을 구성합니다.

kubectl -n ${namespace} apply -f ${beConfigMapFile}.yaml

여기서 ${namespace}는 DorisCluster 리소스를 배포할 네임스페이스이고, ${beConfigMapFile}은 위 구성이 들어 있는 파일의 이름입니다.

2단계: DorisCluster 리소스 구성​

be-conf에 해당하는 ConfigMap을 예로 들면, 배포된 DorisCluster 리소스에 다음 정보를 추가합니다:

spec:
  beSpec:
    configMapInfo:
      configMapName: be-conf
      resolveKey: be.conf
팁

시작 구성과 같은 디렉터리에 파일을 마운트하려면 시작 구성이 들어 있는 ConfigMap에 해당 구성도 넣습니다. ConfigMap의 키는 파일 이름이고 값은 구성 내용입니다.

여러 ConfigMap 마운트​

Doris Operator는 ConfigMap을 통한 구성 파일 마운트뿐 아니라 여러 ConfigMap을 컨테이너의 서로 다른 디렉터리에 마운트하는 기능도 제공합니다.

FE에 여러 ConfigMap 마운트

다음 예는 ConfigMap test-fe1과 test-fe2를 FE 컨테이너의 /etc/fe/config1/ 및 /etc/fe/config2 디렉터리에 각각 마운트하는 방법을 보여 줍니다:

spec:
  feSpec:
    configMaps:
    - configMapName: test-fe1
      mountPath: /etc/fe/config1
    - configMapName: test-fe2
      mountPath: /etc/fe/config2

위 구성에서 yourstorageclass는사용할[StorageClass](https://kubernetes.io/docs/concepts/storage/storage−classes/)의이름이고,{your_storageclass}는 사용할 [StorageClass](https://kubernetes.io/docs/concepts/storage/storage-classes/)의 이름이고, yours​torageclass는사용할[StorageClass](https://kubernetes.io/docs/concepts/storage/storage−classes/)의이름이고,{storageSize}는 사용할 스토리지 크기입니다. ${storageSize}의 형식은 K8s 수량 표현식을 따르며, 예를 들어 100Gi로 지정합니다. 필요에 맞게 바꿉니다.

BE에 여러 ConfigMap 마운트

다음 예는 ConfigMap test-be1과 test-be2를 BE 컨테이너의 /etc/be/config1/ 및 /etc/be/config2 디렉터리에 각각 마운트하는 방법을 보여 줍니다:

spec:
  beSpec:
    configMaps:
    - configMapName: test-be1
      mountPath: /etc/be/config1
    - configMapName: test-be2
      mountPath: /etc/be/config2

위 구성에서 yourstorageclass는사용할[StorageClass](https://kubernetes.io/docs/concepts/storage/storage−classes/)의이름이고,{your_storageclass}는 사용할 [StorageClass](https://kubernetes.io/docs/concepts/storage/storage-classes/)의 이름이고, yours​torageclass는사용할[StorageClass](https://kubernetes.io/docs/concepts/storage/storage−classes/)의이름이고,{storageSize}는 사용할 스토리지 크기입니다. ${storageSize}의 형식은 K8s 수량 표현식을 따르며, 예를 들어 100Gi로 지정합니다. 필요에 맞게 바꿉니다.

영구 스토리지 구성​

Doris 클러스터의 FE 및 BE 구성 요소는 데이터를 영구 저장해야 합니다. Kubernetes는 데이터를 물리적 스토리지에 영구 저장하기 위한 Persistent Volume 메커니즘을 제공합니다. Kubernetes 환경에서 Doris Operator는 StorageClass를 사용하여 적합한 PersistentVolume에 바인딩되는 PersistentVolumeClaim을 자동으로 생성합니다.

FE 영구 스토리지 구성​

Kubernetes에 Doris 클러스터를 배포할 때는 기본적으로 /opt/apache-doris/fe/doris-meta 마운트 지점의 데이터를 영구 저장하도록 구성하는 것이 좋습니다. 이 경로가 FE 메타데이터의 기본 저장 경로이기 때문입니다. Doris는 기본적으로 모든 로그 정보를 표준 출력(콘솔)으로 출력합니다. 클러스터에 로그 수집 기능이 없다면 로그를 영구 저장할 수 있도록 /opt/apache-doris/fe/log 마운트 지점의 데이터를 영구 저장하는 것이 좋습니다.

FE 메타데이터 영구 저장​

기본 구성 파일을 사용하는 경우 배포된 DorisCluster 리소스에 다음 내용을 추가합니다:

spec:
  feSpec:
    persistentVolumes:
    - mountPath: /opt/apache-doris/fe/doris-meta
      name: meta
      persistentVolumeClaimSpec:
        # when use specific storageclass, the storageClassName should reConfig, example as annotation.

Kubernetes에 Doris 클러스터를 배포할 때는 /opt/apache-doris/be/storage 마운트 지점의 데이터를 영구 저장하도록 구성하는 것이 좋습니다. 이 경로가 BE 노드의 기본 데이터 저장 경로이기 때문입니다. Kubernetes에 배포된 Doris는 기본적으로 모든 로그 정보를 표준 출력(콘솔)으로 출력합니다. 클러스터에 로그 수집 기능이 없다면 /opt/apache-doris/be/log 마운트 지점의 데이터를 영구 저장하는 것이 좋습니다.

접근 구성​

Kubernetes는 Service를 사용하여 vip와 부하 분산 기능을 제공합니다. Service에는 외부 노출 모드로 ClusterIP, NodePort, LoadBalancer의 세 가지가 있습니다.

ClusterIP​

Kubernetes의 Doris는 기본적으로 ClusterIP 접근 모드를 사용합니다. ClusterIP 접근 모드는 Kubernetes 클러스터 내부에 주소를 제공하며, 이 주소는 Kubernetes 내에서 서비스에 접근하는 주소로 사용됩니다.

1단계: Service 유형을 ClusterIP로 구성​

Doris는 Kubernetes에서 기본적으로 ClusterIP 접근 모드를 활성화합니다. 별도로 수정하지 않고 이 모드를 사용할 수 있습니다.

NodePort​

Kubernetes 클러스터 외부에서 Doris에 접근하려면 NodePort 모드를 선택할 수 있습니다. NodePort 모드는 정적 호스트 포트 매핑과 동적 호스트 포트 할당이라는 두 가지 구성 방법을 제공합니다.

  • 동적 호스트 포트 할당: 포트 매핑을 명시적으로 설정하지 않으면 Kubernetes는 Pod를 생성할 때 호스트에서 사용하지 않는 포트를 자동으로 할당합니다(기본 범위 30000-32767).

  • 정적 호스트 포트 할당: 포트 매핑을 명시적으로 지정하면 Kubernetes는 해당 호스트 포트가 사용 중이 아니고 충돌이 없을 때 그 고정 포트를 할당합니다.

정적 할당을 사용하려면 포트 매핑을 계획해야 합니다. Doris는 외부 상호 작용을 위해 다음 포트를 제공합니다:

관리자 사용자 이름 및 비밀번호 구성​

Doris 노드를 관리하려면 사용자 이름과 비밀번호를 사용하여 MySQL 프로토콜로 실행 중인 FE 노드에 연결해야 합니다. Doris는 RBAC와 유사한 권한 관리 메커니즘을 구현합니다. 노드를 관리하려면 사용자에게 Node_priv 권한이 있어야 합니다. 기본적으로 Doris Operator는 모든 권한이 있고 비밀번호가 없는 root 사용자를 사용하여 DorisCluster 리소스에 구성된 클러스터를 배포하고 관리합니다. root 사용자에 비밀번호를 설정한 후에는 Doris Operator가 클러스터를 자동으로 관리할 수 있도록 DorisCluster 리소스에 Node_Priv 권한이 있는 사용자 이름과 비밀번호를 명시적으로 구성해야 합니다.

DorisCluster 리소스는 클러스터 노드를 관리하는 데 사용할 사용자 이름과 비밀번호를 구성하는 두 가지 방법을 제공합니다. 환경 변수로 구성하거나 Secret으로 구성할 수 있습니다. 클러스터 관리자 사용자 이름과 비밀번호를 구성하는 시나리오는 다음 3가지입니다:

  • 클러스터 배포 중 root 사용자 비밀번호를 초기화합니다.

  • 비밀번호 없는 root 사용자로 배포할 때 관리자 권한이 있는 root 이외의 사용자를 자동으로 설정합니다.

  • 비밀번호 없는 root 사용자로 클러스터를 배포한 후 root 사용자 비밀번호를 설정합니다.

클러스터 배포 중 root 사용자 비밀번호 구성​

Doris는 fe.conf에 root 사용자 비밀번호를 암호화된 형태로 구성하는 기능을 지원합니다. Doris를 처음 배포할 때 root 사용자 비밀번호를 구성하면 Doris Operator가 클러스터 노드를 자동으로 관리할 수 있습니다. 다음 단계를 따릅니다:

1단계: 암호화된 root 비밀번호 생성​

Doris는 FE 구성 파일에 root 사용자 비밀번호를 암호화된 형태로 설정하는 기능을 지원합니다. 비밀번호는 두 단계 SHA-1 암호화로 암호화됩니다. 코드 예는 다음과 같습니다:

Java 코드 구현:

import org.apache.commons.codec.digest.DigestUtils;

public static void main( String[] args ) {
      //the original password
      String a = "123456";
      String b = DigestUtils.sha1Hex(DigestUtils.sha1(a.getBytes())).toUpperCase();
      //output the 2 stage encrypted password.
      System.out.println("*"+b);
  }

Golang 코드 구현:

import (
"crypto/sha1"
"encoding/hex"
"fmt"
"strings"
)

func main() {
	//original password
	plan := "123456"
	//the first stage encryption.
	h := sha1.New()
	h.Write([]byte(plan))
	eb := h.Sum(nil)

	//the two stage encryption.
	h.Reset()
	h.Write(eb)
	teb := h.Sum(nil)
	dst := hex.EncodeToString(teb)
	tes := strings.ToUpper(fmt.Sprintf("%s", dst))
	//output the 2 stage encrypted password. 
	fmt.Println("*"+tes)
}

fe.conf에 구성 파일의 요구 사항에 따라 암호화된 비밀번호를 넣습니다. 클러스터 매개변수 구성 절을 참고하여 구성 파일을 Kubernetes 클러스터에 ConfigMap으로 배포합니다.

2단계: DorisCluster 리소스 작성​

구성 파일에 root 초기 비밀번호를 설정하면 첫 번째 Doris FE 노드가 시작될 때 root 비밀번호가 즉시 적용됩니다. 이후 노드가 클러스터에 합류할 때 Doris Operator는 root 사용자 이름과 비밀번호를 사용하여 노드를 추가합니다. 따라서 Doris Operator가 클러스터 노드를 관리할 수 있도록 배포된 DorisCluster 리소스에 사용자 이름과 비밀번호를 지정해야 합니다.

  • 환경 변수 방식

    DorisCluster 리소스의 ".spec.adminUser.name" 및 ".spec.adminUser.password" 필드에 root 사용자 이름과 비밀번호를 구성합니다. Doris Operator는 이를 컨테이너 환경 변수로 자동 변환하며, 컨테이너 내부의 보조 서비스는 이 환경 변수를 사용하여 클러스터에 노드를 추가합니다. 구성 형식은 다음과 같습니다:

    spec:
      adminUser:
        name: root
        password: ${password}

    여기서 ${password}는 암호화하지 않은 root 비밀번호입니다.

  • Secret 방식

    Doris Operator는 기본 인증 Secret을 사용하여 관리용 사용자 이름과 비밀번호를 지정하는 기능을 지원합니다. Doris Operator는 Secret을 컨테이너의 특정 위치에 파일로 자동 마운트합니다. 컨테이너의 보조 서비스는 파일에서 사용자 이름과 비밀번호를 읽고 이를 사용하여 클러스터에 노드를 자동으로 추가합니다. basic-authentication-secret의 stringData에는 username과 password의 2개 필드만 포함됩니다. Secret을 사용하여 관리용 사용자 이름과 비밀번호를 구성하는 절차는 다음과 같습니다:

    a. 사용할 Secret 구성

    사용할 기본 인증 Secret을 다음 형식으로 구성합니다:

    stringData:
      username: root
      password: ${password}

    여기서 ${password}는 root에 설정한 암호화되지 않은 비밀번호입니다. 다음 명령을 사용하여 업데이트한 Secret을 Kubernetes 클러스터에 배포합니다.

    kubectl -n ${namespace} apply -f ${secretFileName}.yaml

    여기서 ${namespace}는 DorisCluster 리소스를 배포할 네임스페이스이고, ${secretFileName}은 배포할 Secret의 파일 이름입니다.

    b. DorisCluster 리소스 구성

    배포할 DorisCluster 리소스에 사용할 Secret을 지정합니다. 구성은 다음과 같습니다:

    spec:
      authSecret: ${secretName}

    여기서 ${secretName}은 root 사용자 이름과 비밀번호가 들어 있는 Secret의 이름입니다.

배포 중 root 이외의 관리자 사용자 및 비밀번호 자동 생성(권장)​

처음 배포할 때 root 초기 비밀번호를 설정하지 않는 경우, 환경 변수나 Secret으로 root 이외의 사용자와 로그인 비밀번호를 구성합니다. Doris 컨테이너의 보조 서비스는 Doris에 해당 사용자를 자동으로 생성하고 비밀번호를 설정한 후 Node_priv 권한을 부여합니다. 그러면 Doris Operator는 자동으로 생성된 사용자 이름과 비밀번호를 사용하여 클러스터 노드를 관리합니다.

  • 환경 변수 방식

    배포할 DorisCluster 리소스를 다음 형식으로 구성합니다:

    spec:
      adminUser:
        name: ${DB_ADMIN_USER}
        password: ${DB_ADMIN_PASSWD}

    여기서 ${DB_ADMIN_USER}는 관리자 권한으로 새로 생성할 사용자 이름이고, ${DB_ADMIN_PASSWD}는 새 사용자의 비밀번호입니다.

  • Secret 방식

    a. 사용할 Secret 구성

    사용할 기본 인증 Secret을 다음 형식으로 구성합니다:

    stringData:
      username: ${DB_ADMIN_USER}
      password: ${DB_ADMIN_PASSWD}

    여기서 ${DB_ADMIN_USER}는 새로 생성할 사용자 이름이고, ${DB_ADMIN_PASSWD}는 새 사용자 이름에 설정할 비밀번호입니다.

    다음 명령을 사용하여 Secret을 Kubernetes 클러스터에 배포합니다:

    kubectl -n ${namespace} apply -f ${secretFileName}.yaml

    여기서 ${namespace}는 DorisCluster 리소스가 배포된 네임스페이스이고, ${secretFileName}은 배포할 Secret의 파일 이름입니다.

    b. DorisCluster 리소스 업데이트

    DorisCluster 리소스에 사용할 Secret을 다음과 같이 지정합니다:

    spec:
      authSecret: ${secretName}

    여기서 ${secretName}은 배포된 기본 인증 Secret의 이름입니다.

팁
  • 배포 후 root 비밀번호를 설정합니다. Doris Operator는 새 사용자와 비밀번호를 사용하여 클러스터 노드를 관리하도록 전환합니다. 새로 생성된 사용자를 삭제하지 마세요.

클러스터 배포 후 root 사용자 비밀번호 설정​

Doris 클러스터를 배포한 후 root 사용자에 비밀번호가 설정되어 있지 않다면, Doris Operator가 클러스터 노드를 자동으로 관리할 수 있도록 Node_priv 권한이 있는 사용자를 구성해야 합니다. root 사용자를 사용하지 않는 것이 좋습니다. 사용자 생성 및 권한 부여 절을 참고하여 새 사용자를 생성하고 Node_priv 권한을 부여합니다. 사용자를 생성한 후 환경 변수나 Secret으로 새 관리자 사용자와 비밀번호를 구성하고 DorisCluster 리소스에 설정합니다.

1단계: Node_priv 권한이 있는 사용자 생성​

MySQL 프로토콜로 데이터베이스에 연결한 후 다음 명령을 실행하여 Node_priv 권한만 가진 사용자를 생성하고 비밀번호를 설정합니다.

CREATE USER '${DB_ADMIN_USER}' IDENTIFIED BY '${DB_ADMIN_PASSWD}';

여기서 DBADMINUSER는생성할사용자이름이고,{DB_ADMIN_USER}는 생성할 사용자 이름이고, DBA​DMINU​SER는생성할사용자이름이고,{DB_ADMIN_PASSWD}는 설정할 비밀번호입니다.

2단계: 새 사용자에게 Node_priv 권한 부여​

MySQL 프로토콜로 데이터베이스에 연결한 후 다음 명령을 실행하여 새 사용자에게 Node_priv 권한을 부여합니다.

GRANT NODE_PRIV ON *.*.* TO ${DB_ADMIN_USER};

여기서 ${DB_ADMIN_USER}는 새로 생성한 사용자 이름입니다.

사용자 생성, 비밀번호 설정 및 권한 부여에 대한 자세한 내용은 공식 CREATE-USER 문서를 참고하세요.

3단계: DorisCluster 리소스 구성​

  • 환경 변수 방식

    DorisCluster 리소스에 새로 생성한 사용자와 비밀번호를 다음과 같이 구성합니다:

    spec:
      adminUser:
        name: ${DB_ADMIN_USER}
        password: ${DB_ADMIN_PASSWD}

    여기서 DBADMINUSER는새로생성한사용자이름이고,{DB_ADMIN_USER}는 새로 생성한 사용자 이름이고, DBA​DMINU​SER는새로생성한사용자이름이고,{DB_ADMIN_PASSWD}는 새 사용자에 설정한 비밀번호입니다.

  • Secret 방식

    a. Secret 구성

    기본 인증 Secret을 다음 형식으로 생성합니다:

    stringData:
      username: ${DB_ADMIN_USER}
      password: ${DB_ADMIN_PASSWD}

    여기서 DBADMINUSER는새로생성한사용자이름이고,{DB_ADMIN_USER}는 새로 생성한 사용자 이름이고, DBA​DMINU​SER는새로생성한사용자이름이고,{DB_ADMIN_PASSWD}는 새 사용자 이름에 설정한 비밀번호입니다.

    다음 명령을 사용하여 Secret을 Kubernetes 클러스터에 배포합니다:

    kubectl -n ${namespace} apply -f ${secretFileName}.yaml

    여기서 ${namespace}는 DorisCluster 리소스가 배포된 네임스페이스이고, ${secretFileName}은 배포할 Secret의 파일 이름입니다.

    b. Secret을 사용하는 DorisCluster 리소스 업데이트

    DorisCluster 리소스에 사용할 Secret을 다음과 같이 지정합니다:

    spec:
      authSecret: ${secretName}

    여기서 ${secretName}은 배포된 기본 인증 Secret의 이름입니다.

팁
  • 배포 후 root 비밀번호를 설정하고 새 관리자 사용자 이름과 비밀번호를 구성하면 기존 서비스의 롤링 재시작이 한 번 실행됩니다.

시작 구성 변경 사항을 적용하기 위한 서비스 자동 재시작​

Doris는 구성 파일로 시작 매개변수를 지정합니다. 대부분의 매개변수는 해당 웹 인터페이스에서 수정할 수 있으며 실시간으로 적용됩니다. 웹 인터페이스에서 수정할 수 없는 일부 매개변수는 서비스를 재시작해야 적용됩니다. Doris Operator는 25.1.0 버전부터 서비스를 자동으로 재시작하여 서비스 시작 매개변수의 변경 사항을 적용하는 기능을 제공합니다. DorisCluster 리소스에서 다음과 같이 이 기능을 활성화합니다:

spec:
  enableRestartWhenConfigChange: true

DorisCluster 리소스에 위 구성이 포함되어 있으면 Doris Operator는 다음과 같이 처리합니다:

  1. DorisCluster 리소스로 배포한 클러스터가 사용하는 시작 구성(ConfigMap으로 마운트하며, 자세한 내용은 사용자 지정 시작 구성 절 참고)이 변경되었는지 모니터링합니다.
  2. 시작 구성이 변경되면 해당 서비스를 자동으로 재시작하여 구성을 적용합니다.

사용 예​

ConfigMap 모니터링 및 재시작은 FE와 BE 노드 유형에서 지원됩니다. 다음은 FE를 예로 설명합니다.

  1. DorisCluster 배포 사양은 다음과 같습니다: 
    spec:
      enableRestartWhenConfigChange: true
      feSpec:
        image: apache/doris:fe-2.1.8
        replicas: 1
        configMapInfo:
          configMapName: fe-configmap
  2. fe-configmap에 지정된 FE 서비스 시작 구성을 업데이트합니다. 키가 fe.conf인 fe-configmap의 값(FE 서비스 시작 구성)을 업데이트하면 Doris Operator가 FE 서비스의 롤링 재시작을 자동으로 수행하여 구성을 적용합니다.

Kerberos 인증 사용​

Doris Operator는 25.2.0 버전부터 Kubernetes에서 Doris(2.1.9 및 3.0.4 이상 버전)의 Kerberos 인증을 지원합니다. Doris Kerberos 인증에는 krb5.conf와 keytab 파일이 필요합니다. Doris Operator는 ConfigMap 리소스를 사용하여 krb5.conf 파일을 마운트하고, Secret 리소스를 사용하여 keytab 파일을 마운트합니다. Kerberos 인증을 사용하는 절차는 다음과 같습니다:

  1. krb5.conf 파일이 포함된 ConfigMap을 생성합니다: 
    kubectl create -n ${namespace} create configmap ${name} --from-file=krb5.conf
    namespace는‘DorisCluster‘가배포된네임스페이스이고,{namespace}는 `DorisCluster`가 배포된 네임스페이스이고, namespace는‘DorisCluster‘가배포된네임스페이스이고,{name}은 ConfigMap에 지정할 이름입니다.
  2. keytab이 포함된 Secret을 생성합니다: 
    kubectl create -n ${namespace} secret generic ${name} --from-file= ${xxx.keytab}
    namespace는‘DorisCluster‘가배포된네임스페이스이고,{namespace}는 `DorisCluster`가 배포된 네임스페이스이고, namespace는‘DorisCluster‘가배포된네임스페이스이고,{name}은 Secret에 지정할 이름입니다. 여러 keytab 파일을 마운트하려면 kubectl create Secret 문서를 참고하여 여러 keytab 파일을 하나의 Secret에 넣습니다.
  3. DorisCluster 리소스를 구성하고 krb5.conf가 포함된 ConfigMap과 keytab 파일이 포함된 Secret을 지정합니다. 
    spec:
      kerberosInfo:
        krb5ConfigMap: ${krb5ConfigMapName}
        keytabSecretName: ${keytabSecretName}
        keytabPath: ${keytabPath}
    krb5ConfigMapName은사용할‘krb5.conf‘파일이포함된ConfigMap의이름입니다.{krb5ConfigMapName}은 사용할 `krb5.conf` 파일이 포함된 ConfigMap의 이름입니다. krb5ConfigMapName은사용할‘krb5.conf‘파일이포함된ConfigMap의이름입니다.{keytabSecretName}은 keytab 파일이 포함된 Secret의 이름입니다. ${keytabPath}는 Secret이 컨테이너에 마운트되는 경로입니다. 이 경로는 Catalog를 생성할 때 hadoop.kerberos.keytab으로 지정하는 keytab 파일이 있는 디렉터리입니다. Catalog를 생성하는 방법은 Hive Catalog 문서를 참고하세요.

공유 스토리지 구성​

Doris Operator는 25.4.0 버전부터 ReadWriteMany 공유 스토리지를 여러 구성 요소의 모든 Pod에 마운트하는 기능을 지원합니다. 사용하기 전에 공유 스토리지의 PersistentVolume 및 PersistentVolumeClaim 리소스를 미리 생성합니다. Doris 클러스터를 배포하기 전에 DorisCluster 리소스를 다음과 같이 구성합니다:

spec:
  sharedPersistentVolumeClaims:
  - mountPath: ${mountPath}
    persistentVolumeClaimName: ${sharedPVCName}
    supportComponents:
    - fe
    - be
  • ${mountPath}는 컨테이너에 마운트할 절대 경로를 지정합니다.
  • ${sharedPVCName}은 마운트할 PersistentVolumeClaim의 이름입니다.
  • supportComponents는 이 공유 스토리지를 마운트해야 하는 구성 요소의 이름을 지정합니다. 위 예에서는 FE와 BE가 공유 스토리지를 마운트하도록 지정되어 있습니다. supportComponents 배열이 비어 있으면 배포된 모든 구성 요소가 공유 스토리지를 마운트합니다.
팁

mountPath는 ${DORIS_HOME}을 경로 접두사로 사용할 수 있습니다. mountPath가 ${DORIS_HOME}을 접두사로 사용하면 FE 컨테이너에서 ${DORIS_HOME}은 /opt/apache-doris/fe를 가리키고, BE 컨테이너에서 ${DORIS_HOME}은 /opt/apache-doris/be를 가리킵니다.

프로브 타임아웃 구성​

DorisCluster는 각 서비스에 대해 시작 프로브 타임아웃과 활성 상태 프로브 타임아웃이라는 두 가지 프로브 타임아웃 구성을 제공합니다. 서비스 시작 시간이 구성된 시작 프로브 타임아웃을 초과하면 서비스 시작이 실패한 것으로 간주하고 서비스를 재시작합니다. 서비스가 활성 상태 프로브 타임아웃 내에 응답하지 않으면 Pod를 자동으로 재시작합니다.

시작 프로브 타임아웃 구성​

  • FE 서비스 시작 프로브 타임아웃 구성 
    spec:
      feSpec:
        startTimeout: 3600
    위 구성은 FE 시작 타임아웃을 3600초로 설정합니다.
  • BE 서비스 시작 프로브 타임아웃 구성 
    spec:
      beSpec:
        startTimeout: 3600
    위 구성은 BE 시작 타임아웃을 3600초로 설정합니다.

활성 상태 프로브 타임아웃 구성​

  • FE 서비스 활성 상태 프로브 타임아웃 구성 
    spec:
      feSpec:
        liveTimeout: 60
    위 구성은 FE 활성 상태 타임아웃을 60초로 설정합니다.
  • BE 서비스 활성 상태 프로브 타임아웃 구성 
    spec:
      beSpec:
        liveTimeout: 60
    위 구성은 BE 활성 상태 타임아웃을 60초로 설정합니다.
