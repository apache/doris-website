Lance Catalog

노트

이 기능은 실험적 기능입니다.

Lance Catalog는 Apache Doris 4.1.4부터 지원됩니다.

Lance는 분석 및 AI 워크로드를 위해 설계된 열 지향 데이터 형식입니다. Doris는 Lance Catalog를 사용하여 Lance Namespace의 데이터베이스와 테이블을 탐색하고, 로컬 파일 시스템, S3 호환 객체 스토리지 또는 Alibaba Cloud OSS에 저장된 Lance 데이터세트를 직접 쿼리할 수 있습니다.

현재 Doris는 Lance에 대한 읽기 전용 접근을 제공합니다. Lance 테이블 생성, 쓰기, 업데이트, 삭제는 지원하지 않습니다.

사용 사례​

사용 사례설명
Lance 데이터 직접 쿼리데이터를 먼저 마이그레이션하거나 가져오지 않고 Doris SQL로 기존 Lance 데이터세트를 분석합니다.
AI 벡터 검색Lance에 이미 있는 벡터 인덱스를 재사용하고, vector_search()로 검색을 실행하며, 스칼라 필터링 및 Doris SQL 분석과 결합합니다.
전문 검색Lance에 이미 있는 FTS 역색인을 재사용하고, full_text_search()로 BM25 검색을 실행하며, 스칼라 필터링 및 Doris SQL 분석과 결합합니다.
데이터 통합추가 처리, 조인 또는 장기 저장을 위해 Lance 데이터를 Doris 내부 테이블로 읽어 들입니다.
Namespace 관리간단한 디렉터리 기반 구조에는 Filesystem Catalog를 사용합니다. Namespace, 테이블 위치 또는 임시 스토리지 자격 증명을 중앙에서 관리해야 할 때는 REST Catalog를 사용합니다.

기능 개요​

기능지원 내용
Filesystem Catalog로컬 파일 시스템, file://, s3:// 또는 oss://의 warehouse 지원
REST Catalog인증 없음, Bearer Token, API Key 또는 사용자 지정 HTTP 헤더를 사용하는 Lance REST Namespace 지원
메타데이터 접근SHOW DATABASES, SHOW TABLES, DESC, SHOW INDEX 및 lance_index_entries TVF 지원(마지막 두 항목은 Filesystem Catalog에서만 지원)
시스템 테이블(table$...)지원하지 않음. 인덱스 메타데이터에는 SHOW INDEX와 lance_index_entries TVF 사용
데이터 쿼리열 가지치기, 병렬 Lance Fragment 스캔 및 현재 버전의 일관된 스냅샷 읽기 지원
조건자 푸시다운호환되는 정적 스칼라 조건자와 조인 Runtime Filter를 Lance로 푸시다운하는 기능 지원
파일 TVFs3() 및 local()을 통한 Lance 데이터세트 직접 쿼리 지원
벡터 검색단일 벡터 및 다중 벡터 열 지원. 물리적 Lance 인덱스 세그먼트를 병렬 분할 단위로 사용하고, 인덱스가 포함하지 않는 Fragment는 Flat Search 분할 단위로 유지하며, Doris 전역 Top-K 병합 수행
전문 검색full_text_search()를 통해 기존 Lance FTS 역색인을 사용하고, Match OR/AND 및 Phrase 쿼리를 지원하며, Doris 전역 Top-K 병합 수행
Lance Cache각 BE 내에서 인덱스 및 메타데이터 캐시와 로컬 디스크 데이터 캐시 공유
두 단계 TopN 읽기벡터 검색과 전문 검색에서 조건에 맞는 출력 열에 기본적으로 활성화되며, enable_lance_lazy_materialization로 독립적으로 제어
Lance에 쓰기지원하지 않음
Time TravelREST Namespace가 버전을 관리하는 테이블을 포함하여 FOR VERSION AS OF, FOR TIME AS OF, @tag(...) 및 @branch(...) 지원
Hybrid Search지원하지 않음

Lance 버전 및 호환성​

Doris BE 데이터 리더는 lance-c v0.1.9에 Doris 패치를 적용하여 빌드됩니다. 이 패치는 다중 벡터 검색 지원을 추가하고 내장된 Lance Rust crate를 11.0.0(커밋 ab6b5bbe)으로 업그레이드합니다. Doris FE는 org.lance:lance-core:12.0.0으로 Namespace 및 데이터세트 메타데이터를 읽습니다. FE는 메타데이터만 읽고 데이터세트에 쓰지 않으므로, FE의 더 최신 Lance 릴리스는 BE가 읽을 수 있는 범위를 바꾸지 않습니다. Dataset은 FE의 메타데이터 로딩과 BE의 데이터 읽기 모두와 호환되어야 합니다. 이러한 구현 버전은 데이터세트에 기록된 Lance data_storage_version과 다릅니다.

다음 표는 이 리더의 파일 형식 호환성을 설명합니다.

data_storage_version읽기 지원참고
0.1 / legacy지원최초의 Lance 파일 형식입니다.
2.0(writer 옵션 별칭 0.3)지원Lance v2 파일 형식의 초기 버전입니다.
2.1 / stable지원. 기본 안정 형식내장된 Lance 버전에서 stable writer 옵션과 새 데이터세트의 기본 형식은 모두 2.1로 해석됩니다.
2.2지원내장된 Lance 버전은 이를 안정 형식으로 취급하지만, 기본 writer 형식은 아닙니다.
2.3 / next실험적 지원. 보장하지 않음내장된 Lance 버전은 2.3을 불안정 형식으로 표시하며, next writer 옵션은 2.3으로 해석됩니다.
이후 버전 또는 알 수 없는 버전지원하지 않음데이터세트를 열거나 스캔할 때 지원하지 않는 스토리지 버전 오류가 발생할 수 있습니다.

Lance SDK 릴리스 번호와 파일 형식 버전은 서로 독립적입니다. 이전 또는 이후 Lance SDK로 작성한 데이터세트는 스토리지 형식, 필수 테이블 기능 플래그, 인덱스 형식 및 Arrow/Lance 데이터 타입을 Doris에 내장된 버전이 모두 이해할 수 있을 때만 읽을 수 있습니다. 따라서 다음 사항을 고려해야 합니다.

  • 아래에 설명된 타입 제한을 전제로, Doris는 0.1, 2.0, 2.1, 2.2 스토리지 형식으로 작성된 데이터세트를 읽을 수 있습니다.
  • 상위 호환성은 보장되지 않습니다. 이후 Lance 릴리스로 작성하거나 수정한 데이터세트가 더 새로운 스토리지 형식, 알 수 없는 필수 manifest 기능, 더 새로운 인덱스 형식 또는 지원하지 않는 확장 타입을 사용하면 읽지 못할 수 있습니다.
  • 이 Doris 릴리스에서 계속 읽을 수 있어야 하는 데이터세트에는 현재 기본 안정 형식인 2.1을 사용하고, next는 사용하지 마세요. 더 새로운 writer나 선택적 Lance 기능을 도입할 경우, 프로덕션에서 사용하기 전에 대상 Doris 릴리스로 결과 데이터세트를 검증하세요.

Catalog 구성​

구문​

CREATE CATALOG [IF NOT EXISTS] catalog_name PROPERTIES (
    "type" = "lance",
    "lance.catalog.type" = "<filesystem|rest>",
    {CatalogProperties},
    {StorageProperties},
    {CommonProperties}
);

공통 속성​

속성필수 여부기본값설명
type예-lance여야 합니다.
lance.catalog.type아니요filesystemCatalog 유형입니다. 유효한 값은 filesystem과 rest입니다.
lance.namespace.parent아니요비어 있음지정된 Lance Namespace와 그 하위 Namespace로 접근을 제한합니다. 예를 들어 기본 구분자를 사용할 때 production$analytics는 두 단계 Namespace를 나타냅니다.
lance.namespace.delimiter아니요$lance.namespace.parent를 파싱하는 데 사용하는 구분자입니다. REST Namespace 클라이언트에도 전달됩니다. 이 속성은 Doris에서 다단계 Namespace를 표시하는 방식을 바꾸지 않습니다.
lance.namespace.root_database아니요default루트 Lance Namespace에 매핑되는 Doris 데이터베이스 이름입니다.
lance.table_access_cache_ttl_seconds아니요60음이 아닌 정수입니다. FE 테이블 접근 캐시의 최대 수명(초)이며, 0이면 비활성화됩니다. Filesystem 및 REST Catalog에 적용됩니다. Namespace가 버전을 관리하는 테이블과, 제공된 스토리지 옵션 또는 자격 증명이 포함된 URI가 있는 결과는 캐시하지 않습니다. FE 테이블 접근 캐시를 참조하세요.

Filesystem Catalog​

Filesystem Catalog는 warehouse 디렉터리에서 Lance Namespace와 테이블을 직접 탐색합니다.

속성필수 여부설명
warehouse예Lance warehouse의 루트 경로입니다. 로컬 절대 경로, file:// URI, s3:// URI 및 oss:// URI를 지원합니다.

다음 두 속성은 용도가 다릅니다.

  • fs.s3.support=true는 S3 구성 파싱을 명시적으로 선택합니다. AWS S3는 보통 속성으로 감지할 수 있습니다. MinIO, 사용자 지정 엔드포인트 또는 S3 호환 API로 접근하는 OSS의 경우, 감지 실패나 도메인에 따른 다른 스토리지 유형 선택을 방지하도록 이 속성을 명시적으로 설정하세요. 아래의 모든 S3 예제에는 바로 사용할 수 있도록 이 속성이 포함되어 있습니다.
  • use_path_style은 요청 URL에서 버킷이 나타나는 위치를 제어하며 기본값은 false입니다. true로 설정하면 endpoint/bucket/object-path를 사용하고, false로 설정하면 virtual-hosted-style 접근을 사용합니다. Lance의 현재 기본 S3 클라이언트에서 명시적으로 구성하는 virtual-hosted-style 엔드포인트에는 버킷이 포함되어야 합니다. 서비스가 지원하는 접근 방식에 맞춰 이 속성과 엔드포인트를 함께 설정하세요.
접근 시나리오스토리지 유형 설정use_path_style엔드포인트 형식
AWS S3권장: fs.s3.support=truefalse. 생략 가능https://my-bucket.s3.us-east-1.amazonaws.com과 같이 버킷을 포함합니다.
MinIO(서비스 도메인 또는 IP로 접근)fs.s3.support=true 설정true를 명시적으로 설정http://minio.example.com:9000과 같이 버킷을 제외한 서비스 주소입니다.
OSS S3 호환 APIfs.s3.support=true 설정false. 예제에서 명시적으로 설정https://my-bucket.oss-cn-beijing.aliyuncs.com과 같이 버킷을 포함합니다.
네이티브 OSS API권장: fs.oss.support=true. fs.s3.support는 설정하지 않음일반 속성인 use_path_style을 설정할 필요 없음버킷이 없는 oss.endpoint를 사용합니다. 예: https://oss-cn-beijing.aliyuncs.com.

이 S3 엔드포인트 규칙은 Lance의 기본 S3 접근 경로에 적용됩니다. 단일 스토리지 유형을 사용하는 Filesystem Catalog에서는 해당하는 fs.*.support=true만 설정하세요. “호환성을 활성화”하려고 여러 스토리지 유형을 활성화하지 마세요. 이 속성은 구성 파싱을 선택하며, 스토리지 서비스에 프로토콜 지원을 추가하지 않습니다.

warehouse를 호스팅하는 스토리지 시스템에 맞는 예제를 선택하고 버킷, 경로, 주소 및 자격 증명을 바꾸세요.

  • AWS S3
  • MinIO(경로 방식)
  • Alibaba Cloud OSS(S3 호환 접근)
  • Alibaba Cloud OSS(네이티브 접근)
  • 로컬 파일 시스템
CREATE CATALOG lance_fs_s3 PROPERTIES (
    "type" = "lance",
    "lance.catalog.type" = "filesystem",
    "warehouse" = "s3://my-bucket/lance",
    "fs.s3.support" = "true",
    "use_path_style" = "false",
    "s3.endpoint" = "https://my-bucket.s3.us-east-1.amazonaws.com",
    "s3.region" = "us-east-1",
    "s3.access_key" = "<ak>",
    "s3.secret_key" = "<sk>"
);

이 예제는 버킷이 포함된 AWS S3 엔드포인트와 use_path_style=false를 사용합니다. 현재 Doris의 S3 속성 검증에는 엔드포인트가 필요합니다. 여기에 표시된 s3://my-bucket/... URI를 사용할 때는 리전만 설정해서는 충분하지 않습니다. 버킷이나 리전을 변경할 때마다 엔드포인트를 업데이트하세요.

CREATE CATALOG lance_fs_minio PROPERTIES (
    "type" = "lance",
    "lance.catalog.type" = "filesystem",
    "warehouse" = "s3://my-bucket/lance",
    "fs.s3.support" = "true",
    "s3.endpoint" = "http://minio.example.com:9000",
    "s3.region" = "us-east-1",
    "use_path_style" = "true",
    "s3.access_key" = "<ak>",
    "s3.secret_key" = "<sk>"
);

이 예제는 path-style 요청으로 서비스 도메인을 통해 MinIO에 접근하므로, 버킷마다 하위 도메인이 필요하지 않습니다. 엔드포인트에 버킷을 포함하지 말고, 리전을 서비스에 구성된 값으로 바꾸세요. TLS가 활성화되어 있다면 해당하는 https:// 엔드포인트를 사용하고 FE와 BE 모두 접근할 수 있는지 확인하세요.

S3 호환 API로 OSS에 접근하려면 s3:// warehouse와 s3.* 연결 속성을 사용하세요.

CREATE CATALOG lance_fs_oss_s3 PROPERTIES (
    "type" = "lance",
    "lance.catalog.type" = "filesystem",
    "warehouse" = "s3://my-bucket/lance",
    "fs.s3.support" = "true",
    "s3.endpoint" = "https://my-bucket.oss-cn-beijing.aliyuncs.com",
    "s3.region" = "cn-beijing",
    "use_path_style" = "false",
    "s3.access_key" = "<ak>",
    "s3.secret_key" = "<sk>"
);

이 예제는 virtual-hosted-style 접근을 위해 use_path_style=false를 설정합니다. Lance의 현재 기본 S3 클라이언트는 명시적으로 구성된 엔드포인트에 버킷을 자동으로 추가하지 않으므로, s3.endpoint에는 버킷이 포함되어야 합니다. 예: https://my-bucket.oss-cn-beijing.aliyuncs.com. warehouse는 s3://my-bucket/lance로 유지하세요. 내부 네트워크 접근에는 https://my-bucket.oss-cn-beijing-internal.aliyuncs.com을 사용하고 FE와 BE 모두 접근할 수 있는지 확인하세요.

임시 STS 자격 증명에는 "s3.session_token" = "<token>"을 추가하세요. 이 모드는 데이터를 옮기지 않고 S3 호환 API를 통해 기존 OSS 데이터를 읽습니다. 네이티브 OSS 접근은 옆의 네이티브 OSS 예제를 참조하세요.

CREATE CATALOG lance_fs_oss PROPERTIES (
    "type" = "lance",
    "lance.catalog.type" = "filesystem",
    "warehouse" = "oss://my-bucket/lance",
    "fs.oss.support" = "true",
    "oss.endpoint" = "https://oss-cn-beijing.aliyuncs.com",
    "oss.region" = "cn-beijing",
    "oss.access_key" = "<ak>",
    "oss.secret_key" = "<sk>"
);

임시 STS 자격 증명에는 "oss.session_token" = "<token>"을 추가하세요. 정규화된 형식인 oss://my-bucket.oss-cn-beijing.aliyuncs.com/lance도 허용되며 버킷 경로로 정규화됩니다. 현재 OSS-HDFS는 지원하지 않습니다.

CREATE CATALOG lance_fs_local PROPERTIES (
    "type" = "lance",
    "lance.catalog.type" = "filesystem",
    "warehouse" = "/data/lance"
);

warehouse는 절대 경로여야 합니다. FE와 쿼리를 실행하는 모든 BE가 같은 경로에 접근할 수 있어야 합니다. 다중 노드 배포에서는 관련된 모든 노드에 같은 공유 디렉터리를 마운트하세요.

S3와 OSS의 경우 warehouse에는 s3://bucket/path 또는 oss://bucket/path와 같이 버킷이 포함되어야 합니다.

REST Catalog​

REST Catalog는 Lance REST Namespace를 통해 Namespace, 테이블 위치 및 스토리지 접근 매개변수를 가져옵니다. REST Catalog에는 warehouse 속성이 필요하지 않으며, 지정할 수도 없습니다.

속성필수 여부기본값설명
lance.rest.uri예-REST 서비스 URI입니다. http:// 또는 https://를 사용해야 합니다.
lance.rest.security.type아니요none인증 유형입니다. 유효한 값은 none, bearer, api_key입니다.
lance.rest.bearer-tokenBearer 인증 시 필수-Bearer Token입니다.
lance.rest.api-keyAPI Key 인증 시 필수-x-api-key 헤더로 전송하는 API Key입니다.
lance.rest.header.<header-name>아니요-REST 서비스로 전송하는 사용자 지정 HTTP 헤더입니다. 인증 헤더에는 위의 전용 인증 속성을 사용하세요.

REST 서비스 인증과 객체 스토리지 인증은 별개입니다. lance.rest.*는 Namespace 서비스에 연결하고, s3.* / oss.*는 FE와 BE가 테이블 데이터를 읽도록 합니다. Namespace가 반환하는 테이블 URI가 접근 경로를 결정합니다. s3://는 S3를 사용하고, oss://는 네이티브 OSS 접근을 사용합니다. 반환되는 테이블 URI에 따라 기본 스토리지 속성을 선택하세요.

  • AWS S3
  • MinIO(경로 방식)
  • Alibaba Cloud OSS(S3 호환 접근)
  • Alibaba Cloud OSS(네이티브 접근)

    "fs.s3.support" = "true",

    "s3.endpoint" = "https://my-bucket.s3.us-east-1.amazonaws.com",

인증 없이 REST에 접근하려면 lance.rest.security.type과 인증 속성을 생략하세요. API Key 인증에는 이를 "lance.rest.security.type" = "api_key"와 "lance.rest.api-key" = "<api-key>"로 바꾸세요.

REST Namespace가 각 테이블의 storage_options에 자격 증명이나 엔드포인트를 제공하면, Doris는 해당하는 Catalog 기본값을 옵션별로 덮어쓰고 병합된 구성을 FE와 BE 모두에서 사용합니다. 자격 증명만 제공되는 경우에도 Catalog의 엔드포인트와 접근 방식은 계속 적용됩니다. Namespace가 전체 접근 구성을 제공하는 경우에만 모든 Catalog 스토리지 속성을 생략할 수 있습니다.

S3의 경우 Namespace는 aws_endpoint, aws_region, aws_access_key_id, aws_secret_access_key, aws_session_token, aws_virtual_hosted_style_request를 사용할 수 있습니다. 마지막 옵션은 Doris의 use_path_style과 반대입니다. virtual-hosted-style 접근에는 aws_virtual_hosted_style_request=true를 사용하고, path-style 접근에는 false를 사용합니다. fs.s3.support는 Doris Catalog 속성이며 Lance storage_options 매개변수가 아닙니다.

네이티브 OSS 접근의 경우 Namespace는 oss_endpoint, oss_access_key_id, oss_secret_access_key, oss_region, oss_security_token을 제공하거나, 이에 대응하는 네이티브 이름인 endpoint, access_key_id, access_key_secret, region, security_token을 제공할 수 있습니다.

테이블이 서로 다른 버킷에 있다면 예제처럼 my-bucket으로 고정된 S3 virtual-hosted-style 엔드포인트를 공유하지 마세요. Namespace가 각 테이블에 맞는 엔드포인트와 접근 방식을 제공하도록 하거나, 버킷별로 별도의 Catalog를 구성하세요. path-style 접근을 지원하는 서비스에서는 버킷이 없는 서비스 엔드포인트를 사용하고 use_path_style=true를 설정하여 클라이언트가 각 테이블 URI에서 버킷을 읽도록 할 수도 있습니다.

REST Namespace가 테이블 버전을 관리하는 경우(managed_versioning = true가 DescribeTable에 설정된 경우), Doris는 Namespace의 버전 API를 통해 최신 버전과 Time Travel 선택자를 해석하고 스토리지에서 해당 manifest를 읽습니다. 자세한 내용과 제한 사항은 Time Travel을 참조하세요.

Lance는 다단계 Namespace를 지원하며, Doris Catalog는 각 Namespace를 하나의 데이터베이스 이름으로 표현합니다.

Lance 테이블 쿼리​

Catalog를 생성한 후에는 다른 외부 테이블과 같은 방식으로 Lance 테이블을 탐색하고 쿼리할 수 있습니다.

SHOW DATABASES FROM lance_catalog;

SHOW TABLES FROM lance_catalog.default;

DESC lance_catalog.default.user_profiles;

SELECT user_id, name, age
FROM lance_catalog.default.user_profiles
WHERE age >= 18
ORDER BY user_id
LIMIT 100;

Lance의 데이터를 Doris 내부 테이블에 적재할 수도 있습니다.

INSERT INTO internal.demo.user_profiles
SELECT user_id, name, age
FROM lance_catalog.default.user_profiles;

일반적인 Catalog 쿼리에서는 Doris가 계획 단계에서 Lance 데이터세트 버전을 고정하고 Fragment별로 스캔 작업을 생성합니다. 따라서 쿼리는 일관된 스냅샷을 읽으며, 여러 Scanner가 서로 다른 Fragment를 병렬로 읽을 수 있습니다. 각 Scanner가 전체 데이터세트를 반복해서 스캔하지 않습니다.

Time Travel​

Lance 데이터세트에 커밋할 때마다 1부터 번호가 매겨지는 새 버전이 생성됩니다. 쿼리는 최신 버전 대신 과거 버전을 읽을 수 있습니다.

-- Read version 2 of the table.
SELECT * FROM lance_catalog.db.tbl FOR VERSION AS OF 2;

-- Read the latest version committed at or before the given time.
SELECT * FROM lance_catalog.db.tbl FOR TIME AS OF '2026-09-19 13:06:10';
  • FOR VERSION AS OF는 양의 정수 버전을 받거나, Paimon 테이블 및 Iceberg의 태그 이름과 마찬가지로 따옴표로 묶인 태그 이름을 받습니다(FOR VERSION AS OF 'v2'는 @tag(v2)와 같습니다).
  • FOR TIME AS OF는 세션 시간대의 타임스탬프를 초 또는 밀리초 정밀도로 받습니다(yyyy-MM-dd HH:mm:ss 또는 yyyy-MM-dd HH:mm:ss.SSS). Doris는 타임스탬프 이전 또는 같은 시각에 커밋된 버전 중 manifest에 기록된 커밋 시간이 가장 늦은 버전을 선택합니다. 같은 시각에 커밋된 버전 중에서는 더 새로운 버전을 선택합니다. Iceberg가 시간으로 스냅샷을 선택할 때와 마찬가지로, 기록된 커밋 시간을 그대로 비교하며 버전 번호에 따라 시간이 증가한다고 가정하지 않습니다. Lance는 밀리초보다 세밀한 커밋 시간을 기록하며 전체 정밀도로 비교합니다. 따라서 요청한 밀리초 내에서 더 늦게 커밋된 버전은 선택되지 않습니다. 정리 작업으로 버전이 제거되면 커밋 시간도 함께 제거됩니다. Iceberg가 만료된 스냅샷 이전의 스냅샷 로그를 삭제하는 것처럼, Doris는 가장 최근에 제거된 버전보다 새로운 버전만 고려합니다. 타임스탬프가 이 모든 버전보다 이르면 오류가 발생합니다. 첫 버전보다 이르거나, 정리 작업으로 제거된 이력에 속하기 때문입니다. 예를 들어 태그로 유지된 버전과 그다음으로 남아 있는 버전 사이의 시점이라면 당시 테이블 상태를 알 수 없습니다.
  • 선택한 버전은 문 전체에서 고정됩니다. 스키마, Fragment 계획, 조건자 푸시다운 및 BE 스캔이 모두 이 버전을 사용합니다. 한 문에서 같은 테이블을 두 번 참조할 때 서로 다른 버전을 선택할 수 있습니다. EXPLAIN은 선택한 버전을 lanceVersion으로 표시합니다.
  • Lance의 cleanup_old_versions로 제거된 버전은 읽을 수 없으며, 존재한 적 없는 버전과 같은 방식으로 보고됩니다. REST Namespace가 버전을 관리하는 테이블은 아래의 REST Namespace 관리형 버전 관리를 참조하세요.
  • vector_search()와 full_text_search()는 자체 매개변수인 version, timestamp, tag, branch로 버전, 시간, 태그 또는 브랜치를 선택합니다. 과거 버전 또는 브랜치 검색을 참조하세요. 이 함수들의 table 인수에는 FOR VERSION AS OF, @tag 또는 @branch를 넣을 수 없습니다.
  • 인덱스 조회(SHOW INDEX, lance_index_entries())는 항상 main의 최신 버전을 사용하며, 과거 버전이나 브랜치의 인덱스는 표시하지 않습니다.

Lance 태그와 브랜치는 Iceberg 및 Paimon 테이블과 같은 구문으로 선택합니다.

-- Read the version the tag "v2" points at.
SELECT * FROM lance_catalog.db.tbl@tag(v2);

-- Read the latest version of the branch "dev".
SELECT * FROM lance_catalog.db.tbl@branch(dev);

-- Read version 2 of the branch "dev".
SELECT * FROM lance_catalog.db.tbl@branch(dev) FOR VERSION AS OF 2;
  • 태그는 특정 브랜치의 버전을 가리키며, 태그를 읽으면 해당 브랜치의 해당 버전이 선택됩니다. dev에서 생성한 태그는 dev를 읽으며, 같은 버전 번호를 가진 main의 버전을 읽지 않습니다. @tag는 FOR VERSION AS OF 또는 FOR TIME AS OF와 함께 사용할 수 없습니다.
  • @branch(main)은 main을 읽으며, @branch를 생략한 것과 같습니다.
  • 각 브랜치에는 생성의 기반이 된 버전부터 시작하는 고유한 버전 시퀀스가 있습니다. FOR VERSION AS OF / FOR TIME AS OF가 @branch 뒤에 있으면 해당 브랜치의 버전 중에서만 선택하므로, 브랜치 생성 이전의 타임스탬프는 아무 버전도 선택하지 않습니다. @branch 뒤에서는 @branch(main)을 포함하여 FOR VERSION AS OF에 태그 이름을 지정할 수 없습니다. 태그 자체가 이미 브랜치를 결정하기 때문입니다.
  • 브랜치는 <table>/tree/<branch>/ 아래에 테이블의 얕은 복제본으로 저장되며, manifest는 테이블 위치를 절대 URI로 기록합니다. 따라서 브랜치는 생성된 위치에서만 읽을 수 있습니다. 데이터세트를 다른 곳으로 복사하거나 이동하면 main은 계속 읽을 수 있지만 브랜치는 읽을 수 없습니다.
  • 메타데이터가 삭제되었거나 생성이 도중에 중단된 브랜치도 @branch를 통해 계속 읽을 수 있습니다. tree/ 아래의 디렉터리가 정리되기 전까지는 Lance SDK가 디렉터리로 브랜치를 체크아웃하기 때문입니다. REST Namespace가 버전을 관리하는 테이블에서는 Namespace가 브랜치의 존재 여부를 결정하며, 브랜치는 main을 읽지 않고 해당 디렉터리에서 읽습니다.
  • EXPLAIN은 읽는 브랜치를 lanceBranch로 표시합니다. 존재하지 않는 태그나 브랜치를 지정하면 오류가 발생합니다.

REST Namespace 관리형 버전 관리​

REST Namespace는 테이블 버전을 직접 관리할 수 있습니다(managed_versioning = true가 DescribeTable 응답에 설정된 경우). 이러한 테이블에서는 Namespace가 어떤 버전이 존재하고 어떤 버전이 최신인지 결정합니다. 최신 버전과 FOR VERSION AS OF는 Namespace의 기록(ListTableVersions, DescribeTableVersion)을 따릅니다. FOR TIME AS OF는 Namespace가 나열한 버전 중에서만 manifest에 기록된 커밋 시간으로 선택합니다. 태그는 일반 Lance 테이블과 마찬가지로 데이터세트의 _refs/tags/에서 읽으며, Namespace가 기록한 버전을 가리켜야 합니다. 브랜치의 버전도 Namespace를 따릅니다. 버전이 선택되면 FE와 BE는 다른 Lance 테이블과 마찬가지로 테이블 위치와 버전 번호를 사용해 스토리지에서 해당 버전을 읽습니다.

  • Namespace가 기록하지 않은 버전은 스토리지에 manifest가 남아 있어도 찾을 수 없다고 보고됩니다. 스토리지에 더 새로운 manifest가 있어도 최신 버전은 Namespace의 최신 버전입니다.
  • Namespace가 기록한 버전들 사이에서 더 이상 기록하지 않는 버전은, 정리 작업으로 제거된 버전과 마찬가지로 FOR TIME AS OF에서 제거된 이력으로 취급됩니다. 해당 버전이 적용되었을 수 있는 타임스탬프를 지정하면 더 오래된 버전을 선택하는 대신 오류가 발생합니다.
  • Namespace가 기록한 버전이 없는 테이블이나 브랜치는 스토리지에 manifest가 있어도 오류가 발생합니다.
  • EXPLAIN은 이러한 테이블에 대해 lanceManagedVersioning=true를 표시합니다.

제한 사항:

  • Doris는 table_uri(DescribeTable이 반환한 값)가 가리키는 데이터세트를 읽고, location은 table_uri가 없을 때 대신 사용합니다. 어느 쪽이든 완전한 스토리지 URI여야 합니다. location이 비어 있거나, 함께 반환된 table_uri가 다른 위치를 가리키면 쿼리는 오류로 실패하고 아무것도 읽지 않습니다. 단, 사전 서명된 자격 증명과 같은 쿼리 문자열 차이는 제외합니다. s3+ddb URI도 거부됩니다. 해당 DynamoDB 커밋 핸들러가 읽기 시 버전을 기록하고 확정하기 때문입니다. Doris는 관리형 테이블을 캐시하지 않고 읽을 때마다 describe를 수행하며, FE와 BE는 해당 describe가 반환한 위치와 스토리지 구성으로 읽습니다.
  • Doris는 테이블 디렉터리의 정규 경로인 _versions/<u64::MAX - version>.manifest에서 버전 번호로 버전을 읽습니다. 브랜치의 경우 tree/<branch>/ 아래에서 읽으며, Lance의 이전 명명 규칙에서는 _versions/<version>.manifest를 사용합니다. Namespace가 선택한 버전에 대해 기록한 manifest는 해당 경로이거나 그 옆의 스테이징된 manifest(<canonical path>-<id>)여야 합니다. FOR TIME AS OF에서는 해당 main 또는 브랜치에 기록된 모든 버전의 manifest도 이 조건을 충족해야 합니다. 커밋 시간이 선택을 결정하기 때문입니다. 다른 위치에 기록된 버전은 읽을 수 없습니다. 쿼리가 오류로 실패하며 기록된 경로와 정규 경로를 표시합니다. 쿼리 실행 중 Namespace가 테이블을 이동해도 같은 방식으로 실패할 수 있으며, 다시 시도하면 성공합니다.
  • Namespace가 스테이징된 manifest에만 기록하고 정규 manifest는 존재하지 않는 버전은 읽을 수 없습니다. 커밋이 확정되지 않았거나 정리 작업으로 버전이 제거된 경우입니다. 쿼리는 실패하며 두 원인을 모두 표시합니다. FOR TIME AS OF를 해당 main 또는 브랜치에 사용하면 그 버전이 적용되었을 수 있는 모든 타임스탬프에서 실패합니다. 커밋 시간을 알 수 없기 때문입니다. 최신 버전의 경우에는 writer 또는 Namespace를 사용하는 다른 리더가 이를 확정할 때까지 모든 타임스탬프에서 실패합니다. 이 경우 FOR VERSION AS OF 없이 테이블을 읽거나 스키마를 로딩하는 작업도 실패합니다. Lance 자체 Namespace 구현은 버전을 기록하기 전에 확정하므로, 미확정 버전은 커밋이 중단되었거나 스테이징된 manifest를 기록하는 Namespace에서만 나타납니다. Doris는 테이블을 읽는 동안 절대 쓰지 않습니다.

Lance 인덱스 조회​

Filesystem Catalog의 테이블에서 SHOW INDEX는 Lance 데이터세트에 기록된 논리적 스칼라 인덱스(FTS 역색인 포함)와 벡터 인덱스를 표시합니다. 동등한 문인 SHOW INDEXES, SHOW KEY, SHOW KEYS도 같은 결과를 반환합니다.

SHOW INDEX FROM lance_catalog.default.items;

Doris는 실행 시점의 최신 데이터세트 스냅샷에서 인덱스 메타데이터를 읽고 인덱스 이름과 열 위치를 기준으로 결과를 정렬합니다. Lance가 내부적으로 관리하는 시스템 인덱스인 __lance_frag_reuse, __lance_mem_wal 등은 표시하지 않습니다. 인덱스가 없는 테이블은 빈 결과를 반환합니다.

SHOW INDEX는 표준 13열 결과 집합을 반환합니다. Lance 테이블에서는 다음 열에만 값이 있으며, 나머지 열은 항상 비어 있습니다.

열Lance 테이블의 값
Table테이블 이름입니다.
Key_nameLance 논리 인덱스 이름입니다.
Seq_in_index인덱스에서 열의 위치이며 1부터 시작합니다. 여러 필드의 인덱스는 필드마다 한 행을 생성합니다.
Column_name인덱싱된 필드입니다. 중첩 필드의 인덱스는 필드 경로를 .으로 연결하여 표시하며, 문자, 숫자 및 _ 이외의 문자가 포함된 경로 세그먼트는 백틱으로 묶습니다. 예: attributes.`child.with.dot`.
Index_typeLance SDK가 보고하는 인덱스 유형입니다. 예: BTree, INVERTED, IVF_FLAT, IVF_SQ, IVF_PQ, IVF_HNSW_FLAT, IVF_HNSW_SQ, IVF_HNSW_PQ.
Properties고정된 인덱스 상세 정보 집합을 담은 JSON 객체입니다. metric_type과 target_partition_size는 최상위에, type, num_bits, num_sub_vectors, rotation_type은 compression 아래에, construction_ef, max_connections, max_level은 hnsw 아래에 있습니다. 키는 정렬되며, 인덱스 상세 정보에 이러한 필드가 하나도 없으면 값은 {}입니다.

다음 행은 IVF_PQ 벡터 인덱스와 중첩 필드의 BTree 인덱스를 보여줍니다.

Table          Key_name              Seq_in_index  Column_name                  Index_type  Properties
vs_ivf_pq_f32  embedding_ivf_pq_f32  1             embedding                    IVF_PQ      {"compression":{"num_bits":4,"num_sub_vectors":4,"type":"pq"},"metric_type":"L2"}
nested_index   nested_label_btree    1             attributes.`child.with.dot`  BTree       {}

SHOW INDEX는 기존 인덱스만 조회하며 인덱스를 생성하지 않습니다. Lance 인덱스는 Doris 외부에서 Lance SDK 또는 다른 Lance writer로 생성하세요. 기록된 인덱스 메타데이터가 일관되지 않으면, 예를 들어 인덱스가 알 수 없는 필드를 참조하거나 두 인덱스의 이름이 같으면, 이 문은 부분적인 메타데이터를 반환하는 대신 실패합니다.

SHOW INDEX에는 테이블의 SHOW 권한이 필요합니다. REST Catalog에서는 SHOW INDEX is not supported for Lance REST catalogs 오류와 함께 이 문이 거부됩니다.

lance_index_entries로 물리적 인덱스 항목 나열​

노트

lance_index_entries는 Apache Doris 4.1.5부터 지원됩니다.

SHOW INDEX는 Lance 테이블 인덱스의 논리적 뷰를 제공합니다. 고정된 MySQL 방식의 13열 결과 집합에 인덱스 이름, 인덱싱된 열, 인덱스 유형 및 속성을 표시합니다. 인덱스 항목의 물리적 식별 정보인 UUID와 데이터세트 버전은 이 고정 스키마에 담을 수 없습니다. 읽기 전용 테이블 반환 함수인 lance_index_entries는 이러한 물리적 뷰를 제공합니다. 최신 데이터세트 스냅샷에 기록된 각 물리적 인덱스 항목에 대해 한 행을 반환합니다.

SELECT *
FROM lance_index_entries("table" = "lance_catalog.default.vs_ivf_pq_f32");

table은 세 부분으로 구성된 정규화된 catalog.database.table 이름이어야 합니다. 식별자는 백틱 인용을 지원하므로, 다단계 Namespace가 .이 포함된 데이터베이스 이름에 매핑되면 데이터베이스 부분을 백틱으로 묶으세요.

TVF는 다음의 고정된 열을 반환합니다.

열타입설명
CatalogNameSTRINGCatalog 이름입니다.
DatabaseNameSTRING데이터베이스 이름입니다.
TableNameSTRING테이블 이름입니다.
IndexNameSTRINGLance 논리 인덱스 이름입니다. 하나의 논리 인덱스에 서로 다른 UUID를 가진 물리적 항목이 여러 개 있으면 여러 행을 생성합니다.
IndexUuidSTRING이 물리적 인덱스 항목의 UUID입니다.
DatasetVersionBIGINT이 물리적 인덱스 항목에 기록된 데이터세트 버전, 즉 항목이 작성된 데이터세트 버전입니다. 같은 논리 인덱스의 물리적 항목도 서로 다른 데이터세트 버전을 가질 수 있습니다. 항상 1 이상입니다.

다음 행은 위에 표시한 IVF_PQ 인덱스의 결과 예제입니다. IndexUuid와 DatasetVersion은 예시 값입니다.

CatalogName    DatabaseName  TableName      IndexName             IndexUuid                             DatasetVersion

lance_index_entries는 Dataset.getIndexes()를 통해 인덱스 메타데이터만 읽습니다. 행 수나 통계는 읽지 않으며 데이터세트를 수정하지 않습니다. 결과는 일반 조건자로 필터링할 수 있습니다. 예: WHERE IndexName = .... 행은 (IndexName, IndexUuid) 순으로 정렬됩니다. 읽기는 전체를 검증하여 모두 반환하거나 오류를 냅니다. 이름이 비어 있거나 너무 길거나, UUID가 없거나, DatasetVersion이 양수가 아니거나, UUID가 중복되거나, 원시 항목 수가 16,384를 초과하면 결과를 잘라 반환하는 대신 전체 쿼리가 실패합니다. Lance가 내부적으로 관리하는 예약된 시스템 인덱스인 __lance_frag_reuse와 __lance_mem_wal은 검증하지만 표시하지 않습니다.

lance_index_entries에는 테이블의 SHOW 권한이 필요합니다. REST Catalog에서는 lance_index_entries is not supported for Lance REST catalogs 오류와 함께 이 TVF가 거부됩니다.

타입 매핑​

Doris 4.2의 전체 매핑 표, 정밀도 규칙 및 지원되지 않는 타입은 Lance에서 Doris로의 데이터 타입 매핑을 참조하세요.

조건자 푸시다운​

Doris는 의미적으로 호환되는 조건자를 Substrait 표현식으로 변환하고, 읽기 중 평가하도록 Lance에 전달합니다. 조건 전체가 푸시다운되면 Doris BE는 해당 조건을 다시 평가하지 않습니다. 안전하게 푸시다운할 수 없는 조건은 Doris에 남습니다.

다음 형태는 일반적으로 푸시다운하지 않습니다.

  • 지원되는 내장 문자열 함수와 배열 포함 여부 함수 이외의 함수 또는 열에 적용된 산술 표현식. like, starts_with, ends_with, array_contains라는 이름의 사용자 정의 함수는 해당 내장 함수로 취급하지 않습니다.
  • 패턴에 NUL 문자가 포함된 문자열 조건자. LIKE와 NOT LIKE 패턴이 백슬래시 이스케이프 또는 명시적 ESCAPE 절을 사용하는 경우에도 Doris에 남습니다.
  • 비어 있는 IN 목록 또는 IN 목록에 NULL이 포함된 경우.
  • 일부만 변환할 수 있는 OR 또는 NOT 표현식.
  • 손실 없이 Lance로 변환할 수 없는 데이터 타입이나 상수 값.

lancePushdownPredicate를 EXPLAIN에서 확인하여 실제로 푸시다운되는 조건을 조회하세요.

EXPLAIN
SELECT user_id
FROM lance_catalog.default.user_profiles
WHERE active
  AND starts_with(name, 'A')
  AND country LIKE 'C%';

배열 레이블 조건자​

Apache Doris 4.1.5부터 배열 레이블 푸시다운은 array_contains를 지원합니다. 대상은 직접적인 Lance list<utf8> 열과 NULL이 아닌 문자열 리터럴입니다. 이전 빌드에서는 이러한 조건이 Doris에 남을 수 있습니다. 이 최적화에 의존하기 전에 EXPLAIN을 확인하세요. NULL 배열은 여전히 NULL을 반환하고, 빈 배열은 일치하지 않으며, 중복 레이블이 있어도 결과 행이 중복되지 않습니다.

id 열과 labels 열(list<utf8> 타입)이 있는 Lance 테이블의 예제입니다.

EXPLAIN
SELECT id
FROM lance_catalog.default.items
WHERE array_contains(labels, 'red')
  AND array_contains(labels, 'blue');

이는 두 레이블을 모두 포함하는 배열과 일치하며, 레이블의 순서나 인접 여부는 관계없습니다. AND를 OR로 바꾸면 어느 한 레이블만 있어도 일치합니다. NOT (array_contains(labels, 'red'))도 변환할 수 있으며 SQL NULL 의미를 유지합니다. 이 예제는 일반 테이블 스캔에 적용됩니다. 검색 TVF의 filter 매개변수와 외부 WHERE 조건의 차이를 바꾸지는 않습니다.

다음은 Doris의 잔여 조건자로 남습니다.

  • array_contains(labels, NULL): Doris는 NULL 요소와 일치할 수 있지만, Lance의 포함 여부 함수는 검색 대상이 NULL일 때의 의미가 다릅니다.
  • array_contains_all(labels, ['red', 'blue']): Doris는 순서가 있고 연속된 부분 시퀀스를 검사합니다. 이를 Lance의 집합 포함 함수나 독립적인 두 포함 여부 조건자로 바꿀 수 없습니다.
  • 동적인 검색 대상, 배열 열을 감싸는 표현식이나 캐스트, 그리고 large_list, 고정 크기 리스트, list<large_utf8>를 비롯한 다른 배열 요소/컨테이너 타입.

조건자 푸시다운과 스칼라 인덱스 사용​

조건자 푸시다운은 Lance가 조건을 평가한다는 뜻이며, 인덱스 사용을 보장하지는 않습니다. 일반 스캔에서는 Doris가 각 스캔 작업에 물리적 BTree, Bitmap 또는 LabelList 세그먼트를 할당할 수 있습니다. 같은 열에 대한 IN, AND, OR, NOT 조합은 Lance가 전체 표현식을 지원할 때 선택된 인덱스를 사용할 수 있습니다. OR에는 양쪽 분기의 안전한 후보가 필요하고, NOT은 불완전하게 평가된 하위 트리를 부정할 수 없습니다. 지원하지 않는 인덱스 표현식은 할당된 Fragment 범위 내의 스캔으로 대체됩니다.

각 작업은 하나의 논리적 스칼라 인덱스를 선택합니다. 레이블, 범주 및 숫자 조건자를 결합한 쿼리라고 해서 Doris가 세 인덱스 모두의 교집합을 구하는 것은 아닙니다. 스캔 제한을 적용하기 전에 푸시다운된 전체 조건을 다시 검사하며, 인덱스가 포함하지 않는 Fragment도 읽습니다. 사용할 수 있는 인덱스가 없어도 호환되는 조건자는 푸시다운하여 Lance 스캔에서 평가할 수 있습니다.

다음 근거를 함께 확인하세요.

근거의미
lancePushdownPredicate(EXPLAIN 출력)Lance로 전송되는 조건입니다. 남은 predicates: 조건은 Doris가 평가합니다.
lanceScalarIndexScan=SEGMENT 및 lanceGroupingIndex(EXPLAIN 출력)스칼라 세그먼트 스캔이 계획되었음을 나타내며 선택된 논리 인덱스를 식별합니다. 이것만으로 실행 시 인덱스를 사용했다고 입증할 수는 없습니다.

Runtime Filter 푸시다운​

일반 Lance 테이블이 조인에 참여하면 Doris는 조인의 빌드 측에서 생성한 일부 Runtime Filter를 Lance SQL 조건으로 변환하여 Lance가 데이터를 읽는 동안 적용할 수 있습니다. 특히 큰 테이블과 선택도가 높은 빌드 측 테이블을 조인할 때 Doris로 반환되는 데이터 양을 줄일 수 있습니다.

SELECT l.user_id, l.name
FROM lance_catalog.default.user_profiles l
JOIN internal.demo.allowed_users a
  ON l.user_id = a.user_id;

현재 다음 Runtime Filter를 푸시다운할 수 있습니다.

Runtime FilterLance로 푸시다운되는 형태
IN Filtercolumn IN (...)
Min/Max Filtercolumn >= min_value, column <= max_value 또는 둘 다

Runtime Filter의 열과 값은 Lance SQL이 지원하는 스칼라 타입으로 안전하게 변환할 수 있어야 합니다. 다른 Runtime Filter 유형, NULL이 포함된 IN Filter, 안전하게 변환할 수 없는 데이터 타입이나 값은 푸시다운하지 않습니다. 푸시다운되지 않은 Runtime Filter도 Doris가 계속 평가하므로 쿼리 정확성은 유지됩니다. Lance에서 조기에 필터링하여 얻는 성능 이점만 사라집니다.

Lance Scanner를 생성하기 전에 준비된 Runtime Filter만 해당 Scanner의 푸시다운 조건에 포함할 수 있습니다. 나중에 도착한 Runtime Filter도 Doris가 평가하지만, 이미 생성된 Scanner에는 푸시다운되지 않을 수 있습니다.

Runtime Filter 조건은 일반 SQL 조건자에서 생성한 Substrait 조건과 결합되며, 어느 한쪽이 다른 쪽을 대체하지 않습니다. runtime filters 항목(EXPLAIN 출력)은 계획된 Runtime Filter를 보여줍니다. Runtime Filter가 하나 이상 푸시다운되면 Runtime Profile의 LanceRuntimeFilterPushedIds와 LanceRuntimeFilterSkippedIds가 푸시다운된 Filter ID와 건너뛴 Filter ID를 식별합니다.

현재 Runtime Filter 푸시다운은 일반 Lance 테이블 스캔에만 적용됩니다. vector_search() 또는 전문 검색이 후보를 생성하는 동안에는 사용하지 않습니다.

파일 TVF로 Lance 쿼리​

알고 있는 경로의 Lance 데이터세트만 읽으면 되는 경우, Catalog를 생성하지 않고 s3() 또는 local() TVF를 사용할 수 있습니다. uri 또는 file_path는 내부 데이터 파일이 아니라 Lance 데이터세트의 루트 디렉터리를 가리켜야 합니다.

S3 TVF​

s3() TVF는 S3 호환 API를 사용합니다. OSS의 경우 s3.* 속성과 버킷이 포함된 virtual-hosted-style 엔드포인트를 사용하세요. 네이티브 OSS 접근은 위의 OSS Catalog 예제를 사용하세요. 다음 SQL은 예제 데이터세트의 처음 10개 행을 읽습니다. 실행하기 전에 주소, 자격 증명 및 열 이름을 바꾸세요.

  • AWS S3
  • MinIO(경로 방식)
  • Alibaba Cloud OSS(S3 호환 접근)
SELECT user_id, name
FROM s3(
    "uri" = "s3://my-bucket/lance/user_profiles.lance",
    "format" = "lance",
    "fs.s3.support" = "true",
    "use_path_style" = "false",
    "s3.endpoint" = "https://my-bucket.s3.us-east-1.amazonaws.com",
    "s3.region" = "us-east-1",
    "s3.access_key" = "<ak>",
    "s3.secret_key" = "<sk>"
)
ORDER BY user_id
LIMIT 10;

AWS S3에서도 엔드포인트를 명시적으로 설정하세요. 이 예제는 virtual-hosted-style 접근을 사용합니다. 엔드포인트의 버킷과 리전은 URI 및 s3.region과 일치해야 합니다.

SELECT user_id, name
FROM s3(
    "uri" = "s3://my-bucket/lance/user_profiles.lance",
    "format" = "lance",
    "fs.s3.support" = "true",
    "s3.endpoint" = "http://minio.example.com:9000",
    "s3.region" = "us-east-1",
    "use_path_style" = "true",
    "s3.access_key" = "<ak>",
    "s3.secret_key" = "<sk>"
)
ORDER BY user_id
LIMIT 10;

버킷이 없는 MinIO 서비스 엔드포인트를 사용하고 use_path_style=true를 설정하세요. FE와 쿼리를 실행하는 BE 모두 서비스에 접근할 수 있어야 합니다. FE 호스트에서만 접근할 수 있는 주소는 피하세요.

SELECT user_id, name
FROM s3(
    "uri" = "s3://my-bucket/lance/user_profiles.lance",
    "format" = "lance",
    "fs.s3.support" = "true",
    "s3.endpoint" = "https://my-bucket.oss-cn-beijing.aliyuncs.com",
    "s3.region" = "cn-beijing",
    "use_path_style" = "false",
    "s3.access_key" = "<ak>",
    "s3.secret_key" = "<sk>"
)
ORDER BY user_id
LIMIT 10;

이 예제는 Filesystem Catalog와 같은 OSS S3 호환 설정을 사용하지만, uri는 특정 .lance 데이터세트를 가리키고 warehouse는 데이터세트가 들어 있는 디렉터리를 가리킵니다. fs.s3.support=true와 use_path_style=false를 유지하고, 엔드포인트의 버킷이 URI와 일치하는지 확인하세요.

OSS의 경우 예제의 uri를 oss://my-bucket/lance/user_profiles.lance로 작성하면서 같은 s3.* 속성과 fs.s3.support=true를 유지할 수도 있습니다. TVF는 URI를 s3://로 정규화하며 네이티브 OSS 공급자로 전환하지 않습니다. 네이티브 OSS Catalog의 oss.* 구성을 그대로 복사하지 마세요. 버킷이 없는 엔드포인트와 virtual-hosted-style 접근을 결합하면 데이터세트가 존재하지 않는다고 보고할 수 있으며, path-style 접근으로 전환하면 OSS가 SecondLevelDomainForbidden으로 거부할 수 있습니다.

S3 TVF에서는 FE가 Schema, 현재 버전 및 Fragment 목록을 가져옵니다. Doris는 해당 버전을 고정하고 Fragment를 병렬로 스캔합니다. EXPLAIN은 VTVF_SCAN_NODE를 표시합니다. 여러 분할 단위가 데이터세트 URI를 공유할 수 있으며 Fragment ID로 구분됩니다. totalFileSize=0 또는 length=0은 Lance 분할 단위의 자리표시자이며, 빈 데이터세트나 각 분할 단위의 반복적인 전체 테이블 스캔을 뜻하지 않습니다.

Local TVF​

SELECT user_id, name
FROM local(
    "file_path" = "/data/lance/user_profiles.lance",
    "backend_id" = "10001",
    "format" = "lance"
);

file_path는 작성된 그대로 대상 BE의 Lance Reader에 전달됩니다. Doris는 앞에 user_files_secure_path를 붙이거나 이 경로를 Glob으로 확장하지 않습니다. 따라서 대상 BE가 접근할 수 있는 단일 Lance 데이터세트의 루트 디렉터리를 직접 가리켜야 합니다. 절대 경로를 권장합니다.

Local TVF의 Schema 탐색과 실행은 각각 독립적으로 최신 데이터세트 버전을 엽니다. 현재 Schema 탐색 중에 결정된 버전은 후속 스캔에 고정되지 않습니다. 쿼리 분석과 실행 사이에 데이터세트가 변경되면 탐색된 Schema와 스캔된 스냅샷이 다를 수 있습니다. Local TVF 쿼리가 분석되고 실행되는 동안에는 데이터세트를 수정하지 마세요. 현재 Local Lance TVF는 하나의 Scanner를 사용합니다.

Lance 파일 TVF에는 다음과 같은 추가 제한이 있습니다.

  • s3()와 local()만 지원합니다. HDFS 및 HTTP 등 다른 파일 TVF는 현재 지원하지 않습니다.
  • path_partition_keys는 지원하지 않습니다.
  • 하나의 TVF 경로는 하나의 Lance 데이터세트만 나타낼 수 있습니다.
  • DESC FUNCTION은 지원하지 않는 타입이 포함된 Schema를 표시할 수 있지만, SQL은 지원하지 않는 열을 프로젝션할 수 없습니다.

벡터 검색​

Doris 4.2의 Lance 자동 검색 기능이 포함된 빌드에서는 조건에 맞는 일반 SQL도 네이티브 벡터 Top-N 및 MATCH/BM25 검색을 사용할 수 있습니다. 다섯 가지 근사 함수, 메트릭 변환, 입력 의미 체계, JOIN/EXISTS 적용 범위는 일반 SQL에서 자동 검색을 참조하세요. 아래 TVF는 검색을 명시적으로 조정하거나 자동 재작성 범위 밖에서 지원되는 쿼리 형태를 사용할 때 계속 활용할 수 있는 인터페이스입니다.

vector_search()는 Lance 테이블의 벡터 열에서 Top-K 검색을 수행하는 관계형 TVF입니다. 기존 Lance 벡터 인덱스를 사용하거나 Flat Search를 수행할 수 있습니다.

구문 및 예제​

SELECT user_id, label, _distance
FROM vector_search(
    "table" = "lance_catalog.default.items",
    "column" = "embedding",
    "query_vector" = "[0.1, 0.2, 0.3, 0.4]",
    "top_k" = "10",
    "offset" = "3",
    "metric" = "l2",
    "nprobes" = "20",
    "refine_factor" = "10",
    "prefilter" = "true",
    "filter" = "category = 'book'",
    "use_index" = "true"
)
ORDER BY _distance ASC, user_id;

vector_search()의 관계 스키마에는 Lance 원본 테이블의 모든 열과, 최근접 이웃 쿼리를 위해 Lance Scanner가 생성한 _distance 열이 포함됩니다. 최종 SQL 결과에는 SELECT로 프로젝션한 열만 포함됩니다. Doris는 _distance를 FLOAT로 노출합니다. 이는 일반적인 유사도 점수가 아니라 거리이며, 값이 작을수록 두 벡터가 가깝다는 뜻입니다. 원본 테이블에는 _distance라는 열이 이미 있어서는 안 됩니다. SQL 관계는 최종 표시 순서를 보장하지 않으므로, 결정적인 최근접 이웃 순서가 필요하면 ORDER BY _distance ASC를 명시하세요. 거리가 같은 행의 순서를 결정하도록 고유한 열을 추가하는 것이 좋습니다.

table은 정확히 세 부분의 catalog.database.table 이름으로 파싱되어야 합니다. 다단계 Lance Namespace는 .이 포함된 하나의 Doris 데이터베이스 이름에 매핑되므로 데이터베이스 부분을 백틱으로 묶으세요. 예를 들어 items 테이블(doris.analytics Namespace)에는 다음 값을 사용합니다.

"table" = "lance_catalog.`doris.analytics`.items"

따옴표로 묶지 않은 형태인 lance_catalog.doris.analytics.items는 사용하지 마세요. 네 부분으로 파싱되어 거부됩니다. 테이블 이름만 지정하거나 database.table 이름을 지정해도 거부됩니다.

refine_factor아니요단일 벡터: 비활성화. 다중 벡터: 1후보 정제 배수입니다. 양의 정수여야 합니다. 단일 벡터 검색에서 설정하지 않으면 Lance는 원본 벡터로 거리를 다시 계산하지 않으므로, 양자화 인덱스의 _distance는 근삿값일 수 있습니다. N으로 설정하면 Lance는 먼저 (top_k + offset) × N개의 후보를 가져오고, 원본 벡터로 정확한 거리를 다시 계산한 뒤 순서를 다시 정합니다. 정제 과정은 이 후보들의 원본 벡터 데이터를 읽습니다. N이 증가할수록 더 많은 후보를 읽고 평가하므로 I/O가 크게 증가하고 쿼리 성능이 저하될 수 있습니다. 단일 벡터 검색에서 1로 설정하면 정제가 활성화되며, 설정하지 않은 경우와 다릅니다. 다중 벡터 검색은 항상 원본 값으로 후보를 정제하며 기본 배수는 1입니다.
ef아니요floor(1.5 × (top_k + offset))HNSW 그래프 검색 중 유지하는 후보 폭입니다. 양의 정수여야 합니다. refine_factor도 설정하면 기본값은 floor(1.5 × (top_k + offset) × refine_factor)입니다. HNSW가 아닌 인덱스에는 영향을 주지 않습니다.
use_index아니요truetrue이면 Doris는 벡터 열 및 거리 메트릭과 호환되는 Lance 벡터 인덱스를 우선 사용하고, 사용 가능한 인덱스가 없으면 자동으로 Flat Search를 사용합니다. false이면 Doris는 벡터 인덱스를 비활성화하고 데이터에 Flat Search를 수행합니다.
version, timestamp, tag, branch아니요-main의 최신 버전 대신 과거 버전, 특정 시점의 버전, 태그 또는 브랜치를 검색합니다. 과거 버전 또는 브랜치 검색을 참조하세요.

metric을 생략하면 인덱스 경로와 Flat Search 경로 모두에서 l2가 선택됩니다. uint8 열에서는 "metric" = "hamming"을 명시적으로 설정하세요. 기본값인 l2는 지원하지 않습니다. 다중 벡터 검색에는 아래에 설명된 후보 처리 한도도 적용됩니다.

반경 및 범위 검색​

반경 쿼리에는 distance_upper_bound를 설정하고, 구간 [lower, upper)에는 양쪽 경계를 함께 설정하세요. 생략한 경계에는 제한이 없습니다. 거리는 선택한 메트릭을 사용합니다. l2는 유클리드 거리의 제곱이므로 기하학적 반경 r은 상한 r * r에 해당합니다. 음수 경계도 허용되며, 이는 dot과 같은 메트릭에 유용합니다. 저장된 벡터가 Float64를 사용해도 경계는 FLOAT 정밀도를 사용합니다. 유한하지 않은 경계, 오버플로, 같은 경계 및 역전된 구간은 거부됩니다.

예를 들어 기존 Lance Catalog 테이블인 lance_catalog.default.items에 user_id와 삼차원 Float32 embedding 열이 있다고 가정합니다.

user_idembedding[0, 0, 0]까지의 L2 거리 제곱
1[0, 0, 0]0
2[1, 0, 0]1
3[2, 0, 0]4
SELECT user_id, _distance
FROM vector_search(
    "table" = "lance_catalog.default.items",
    "column" = "embedding",
    "query_vector" = "[0, 0, 0]",
    "metric" = "l2",
    "top_k" = "10",
    "use_index" = "false",
    "distance_lower_bound" = "1",
    "distance_upper_bound" = "4"
)
ORDER BY _distance;
+---------+-----------+
| user_id | _distance |
+---------+-----------+
|       2 |         1 |
+---------+-----------+

하한을 제거하면 행 1도 반환됩니다. 상한 0만 사용하면 아무 행도 반환되지 않습니다. prefilter=true이면 filter가 벡터 검색 전에 후보를 제한하고, 기본값인 prefilter=false이면 후보 생성 후에 필터링합니다. offset은 거리 범위를 적용한 후 결과를 건너뜁니다. 출력 스키마는 바뀌지 않으며, 테이블 열에 _distance(FLOAT 타입)가 추가됩니다. EXPLAIN은 lanceDistanceRange=[1.0, 4.0)를 표시합니다.

거리 경계는 준비된 문에서 ? 매개변수를 지원합니다. 각 실행은 자체 경계 값을 검증하고 사용하며, NULL 경계는 거부됩니다. 한쪽에 제한을 두지 않으려면 해당 속성을 생략하세요.

이 기능은 여전히 Top-K 쿼리이며 반경 안의 모든 행을 반환하는 API가 아닙니다. 결과 수는 top_k로 제한되며 더 적은 행이 반환될 수 있습니다.

범위 쿼리에서 Doris는 양쪽 경계가 모두 제공되고 선택한 인덱스가 IVF_FLAT으로 명시적으로 식별될 때만 인덱스 검색을 사용합니다. 단방향 범위, 양자화 인덱스 및 하위 유형을 알 수 없는 인덱스는 use_index=true여도 정확한 Flat Search로 대체됩니다. 범위 안전성 때문에 인덱스 선택이 차단되면 EXPLAIN은 lanceVectorIndexStatus=DISTANCE_RANGE_FALLBACK을 보고합니다. 이 대체 동작은 스캔 비용을 늘릴 수 있습니다.

인덱스를 사용하는 IVF_FLAT 쿼리도 nprobes로 선택한 파티션에 의존합니다. 모든 후보를 빠짐없이 평가하려면 use_index=false를 사용하세요. 인덱싱되지 않은 추가 데이터는 Flat Search로 검색합니다. 다중 벡터 열은 거리 경계를 지원하지 않습니다.

지원되는 벡터 인덱스 유형​

단일 벡터 열에서 Doris는 다음 Lance 벡터 인덱스 조합을 지원합니다. 다중 벡터 인덱스의 제한은 다중 벡터 검색에 설명되어 있습니다.

인덱스 유형설명주요 쿼리 매개변수
IVF_FLAT각 파티션 내부에서 원본 벡터 거리를 계산하는 IVF 파티션nprobes
IVF_SQScalar Quantization을 사용하는 IVFnprobes, refine_factor
IVF_PQProduct Quantization을 사용하는 IVFnprobes, refine_factor

vector_search()는 Lance에 이미 존재하는 벡터 인덱스만 사용합니다. 인덱스를 생성하거나 사용자가 인덱스 유형이나 이름을 지정하도록 하지는 않습니다. use_index=true이면 Doris는 벡터 열과 거리 메트릭에 호환되는 인덱스를 자동으로 선택합니다. 선택된 인덱스가 포함하지 않는 데이터를 비롯하여 사용 가능한 인덱스가 없는 데이터는 자동으로 Flat Search를 사용하며 누락되지 않습니다. use_index=false이면 모든 데이터가 Flat Search를 사용합니다.

열에 호환되는 인덱스가 여러 개 있으면 Doris는 쿼리마다 인덱스 이름순으로 첫 번째 인덱스를 선택합니다. 해당 인덱스가 포함하지 않는 Fragment는 다른 인덱스가 포함하더라도 Flat Search를 사용하므로, 실행은 항상 EXPLAIN이 보고하는 인덱스 범위와 일치합니다. Doris가 계획에 사용할 수 없는 인덱스는 전혀 사용하지 않고 전체 검색을 Flat Search로 실행합니다. 예를 들어 Fragment 범위 메타데이터가 없는 인덱스(lanceVectorIndexStatus=UNKNOWN_COVERAGE), 메트릭이 기록되지 않은 인덱스(METRIC_MISMATCH), 또는 인덱스 상세 정보가 없고 Lance도 파일에서 추론할 수 없어 Doris가 건너뛰는 이전 인덱스(NO_MATCH)가 이에 해당합니다. Lance가 상세 정보를 추론할 수 있는 이전 인덱스는 정상적으로 사용합니다.

단일 벡터 열에서 벡터 인덱스가 지원하는 거리 메트릭은 벡터 요소 타입에 따라 달라집니다. 다음 표에서 지원되는 조합을 선택하세요. 지원되지 않는 조합은 벡터 인덱스를 사용할 수 없습니다.

  1. l2 인덱스를 값이 큰 float16 데이터에 구축하면 시간이 너무 오래 걸리거나 실패할 수 있습니다. 벡터 값을 관리 가능한 범위로 유지하세요. 인덱스 생성이 실패하면 Flat Search를 사용하거나, 애플리케이션에 적합한 경우 cosine을 대신 사용하세요.
  2. Lance는 uint8 벡터를 이진 벡터로 취급하며 hamming 메트릭만 지원합니다. Product Quantization과 Scalar Quantization은 uint8을 지원하지 않으므로 IVF_FLAT과 IVF_HNSW_FLAT만 사용할 수 있습니다.

쿼리 메트릭과 인덱스 메트릭의 일치​

쿼리의 metric은 인덱스를 구축할 때 사용한 메트릭과 일치해야 합니다. 그렇지 않으면 요청한 메트릭이 해당 열 타입에서 지원되는 경우 Doris는 Flat Search를 사용합니다. 결과는 정확하지만 벡터를 직접 스캔해야 하므로 일반적으로 성능이 낮아집니다.

metric을 생략하면 Doris는 인덱스 선택 시 이를 l2로 취급합니다. 따라서 metric은 cosine, dot 또는 hamming으로 구축한 인덱스를 사용할 때 명시적으로 설정하세요. 예를 들어 uint8 벡터 인덱스에는 "metric" = "hamming"이 필요합니다. 그렇지 않으면 지원하지 않는 l2 메트릭을 사용하여 쿼리가 실패합니다.

EXPLAIN으로 인덱스 사용 여부를 확인하세요. lanceSearchIndexSegments 값이 0보다 크면 인덱스 검색을 나타내고, 0이면 Flat Search를 나타냅니다.

Doris는 벡터 열마다 하나의 벡터 인덱스만 고려합니다. 서로 다른 메트릭으로 구축한 인덱스 사이의 선택이 모호해지지 않도록 각 벡터 열에 벡터 인덱스를 최대 하나만 유지하세요.

다중 벡터 검색​

다중 벡터 열은 각 테이블 행에 여러 하위 벡터를 저장합니다. 예를 들어 문서의 토큰 임베딩이 이에 해당합니다. 쿼리 행렬은 순위가 매겨진 하나의 테이블 행 집합을 생성합니다. 독립적인 벡터 검색을 일괄 실행하거나 여러 열을 검색하는 기능이 아닙니다.

데이터 준비 및 쿼리 실행​

위의 AWS S3 Filesystem Catalog 예제를 사용하며, Catalog는 lance_fs_s3, warehouse는 s3://my-bucket/lance입니다. writer 환경에 Lance Python SDK(pylance)와 pyarrow를 설치하세요. 예를 들어 AWS_ACCESS_KEY_ID, AWS_SECRET_ACCESS_KEY, AWS_DEFAULT_REGION을 통해 S3 자격 증명과 리전을 구성합니다. writer에는 쓰기 권한이, Doris에는 같은 위치에 대한 읽기 권한이 필요합니다. 사용자 지정 엔드포인트나 다른 인증 방식을 사용하는 경우 SDK의 object-store 옵션을 Catalog와 일치하도록 구성하세요.

documents.lance를 warehouse 바로 아래에 생성하여 Doris가 lance_fs_s3.default.documents로 탐색하도록 하세요. Catalog와 Python 예제 양쪽에서 버킷을 바꾸세요. 새 데이터세트 위치를 사용하세요.

import lance
import pyarrow as pa

vector_type = pa.list_(pa.float32(), 2)
schema = pa.schema([
    pa.field("id", pa.int64()),
    pa.field("embeddings", pa.list_(
        pa.field("item", vector_type, nullable=False)
    )),
])
data = pa.Table.from_pylist([
    {"id": 1, "embeddings": [[1.0, 0.0], [0.0, 1.0]]},
    {"id": 2, "embeddings": [[1.0, 0.0]]},
    {"id": 3, "embeddings": []},
    {"id": 4, "embeddings": None},
], schema=schema)
lance.write_dataset(
    data,
    "s3://my-bucket/lance/documents.lance",
    data_storage_version="2.1",
)

외부 리스트를 사용하면 행마다 하위 벡터 수가 달라도 됩니다. 내부의 nullable=False는 필수입니다. 하위 벡터 자체는 null일 수 없습니다. 이차원 JSON 배열로 테이블을 쿼리하세요.

SELECT id, _distance
FROM vector_search(
    "table" = "lance_fs_s3.default.documents",
    "column" = "embeddings",
    "query_vector" = "[[1,0],[0,1]]",
    "top_k" = "2",
    "metric" = "l2",
    "use_index" = "false"
)
ORDER BY _distance, id;

행 단위 점수 계산​

쿼리 하위 벡터를 Q, 행에 저장된 하위 벡터를 V라고 하면 다음과 같습니다.

_distance = sum(q in Q, min(v in V, distance(q, v)))
metric두 하위 벡터 사이의 거리
l2(기본값)유클리드 거리의 제곱
cosine1 - cosine_similarity
dot 또는 dot_product1 - dot_product. 값이 음수일 수 있음

_distance가 작을수록 좋습니다. 각 쿼리 하위 벡터는 한 번씩 기여하며, 저장된 하나의 하위 벡터가 여러 쿼리 하위 벡터와 일치할 수 있습니다. 점수는 평균이 아니라 합계이므로, 쿼리 하위 벡터를 반복하면 기여도도 반복됩니다. _distance의 Doris 타입은 Float64 입력에서도 FLOAT입니다. top_k와 offset은 하위 벡터가 아니라 테이블 행을 셉니다. Top-K 경계에서 동점인 행은 포함 여부나 순서가 보장되지 않습니다. 외부 ORDER BY는 반환된 행의 순서만 정합니다.

지원하지 않는 형태와 타입외부 large_list 또는 fixed_size_list, 가변 길이 내부 리스트, 정수 다중 벡터 요소, 확장/dictionary 인코딩 및 hamming 다중 벡터 검색은 지원하지 않습니다.

매개변수 제한​

M을 쿼리 하위 벡터 수, K = top_k, O = offset, R = refine_factor(다중 벡터 검색의 기본값은 1)라고 정의합니다.

제약 조건제한
쿼리 하위 벡터 수1 <= M <= 128
결과 수 및 오프셋K > 0, O >= 0
쿼리 후보 처리 한도M × (K + O) <= 100000
정제 후보 처리 한도R × (K + O) <= 100000, R > 0
명시적 nprobes, ef 또는 refine_factor양의 32비트 부호 있는 정수이며 최대 2147483647. 후보 처리 한도는 refine_factor를 추가로 제한함

두 후보 처리 한도는 use_index=false일 때도 각각 독립적으로 적용됩니다. 예를 들어 M=128, K=1000, O=0은 쿼리 후보 처리 한도를 초과하므로 거부됩니다. M=4, K=1000, O=0, R=10은 두 한도를 모두 충족합니다. 이 제한은 후보 처리 작업량을 한정하며, 특정 메모리 사용량이나 쿼리 지연 시간을 보장하지 않습니다.

인덱스 사용 및 정제​

통합된 Lance 버전은 cosine 메트릭의 다중 벡터 인덱스를 지원합니다. cosine IVF_FLAT 또는 IVF_PQ 인덱스와 같이 호환되는 기존 인덱스를 사용하려면 "metric" = "cosine"을 설정하고 use_index=true를 유지하세요. metric을 생략하면 l2가 선택됩니다. L2 및 dot 검색은 호환되는 인덱스가 없으면 Flat Search를 사용합니다. Doris는 이 함수로 인덱스를 생성하지 않습니다. SHOW INDEX(Filesystem Catalog만 지원)로 인덱스 메타데이터를 조회하고, EXPLAIN으로 lanceSearchIndexSegments > 0인지 확인하세요.

인덱스 검색의 후보 선택은 근사 방식입니다. 다중 벡터 후보는 refine_factor를 생략하거나 1로 설정한 경우에도 항상 원본 벡터로 정제되므로, 인덱싱된 행과 인덱싱되지 않은 행이 같은 행 단위 점수를 사용합니다. refine_factor를 높이면 후보 풀이 확장되어 벡터 읽기와 계산이 추가되지만, 완전한 재현율을 보장하지는 않습니다. nprobes는 IVF 탐색을 제어하고 ef는 HNSW 인덱스에 적용됩니다. 재현율과 지연 시간을 측정한 후에만 조정하세요. 인덱스 생성 후 추가된 행은 Flat Search를 통해 포함됩니다.

선택한 행을 빠짐없이 채점하려면 "use_index" = "false"를 사용하세요. 검색 전에 후보를 제한하려면 TVF filter와 prefilter=true를 사용하세요. 기본값인 prefilter=false는 후보 생성 후 조건을 적용합니다. 외부 SQL WHERE는 항상 Doris가 생성된 후보에 대해 평가하며, 분할 단위의 결과를 보충하지 않습니다. 다음 절의 필터링 규칙은 단일 벡터와 다중 벡터 검색 모두에 적용됩니다.

Prefilter 및 Post-filter​

Prefilter와 Post-filter는 같은 쿼리에서 사용할 수 있습니다.

SELECT user_id, category, _distance
FROM vector_search(
    "table" = "lance_catalog.default.items",
    "column" = "embedding",
    "query_vector" = "[0.1, 0.2, 0.3, 0.4]",
    "top_k" = "10",
    "prefilter" = "true",
    "filter" = "category = 'book'"
)
WHERE user_id > 100
ORDER BY _distance ASC, user_id;
필터 유형조건 예제실행 시점결과에 미치는 영향
TVF PrefilterTVF 매개변수 "filter" = "category = 'book'" 및 "prefilter" = "true"Lance가 벡터 후보를 생성하기 전category = 'book'인 행 중에서만 최근접 이웃을 검색합니다.
TVF Post-filterTVF 매개변수 "filter" = "category = 'book'", prefilter는 생략하거나 false로 설정Lance가 후보를 생성한 후생성된 후보에서 조건에 맞지 않는 행을 제거합니다. 후보를 보충하지 않으므로 결과가 top_k개 행보다 적을 수 있습니다.
Doris Scan Post-filter외부 WHERE user_id > 100Lance가 후보를 생성한 후, Doris가 최종 TopN을 적용하기 전생성된 후보에서 조건에 맞지 않는 행을 제거합니다. 후보를 보충하지 않으므로 최종 결과가 top_k개 행보다 적을 수 있습니다.

user_id > 100도 후보 생성에 참여해야 한다면 TVF filter에 포함하고 prefilter=true를 설정하세요. 예: "filter" = "category = 'book' AND user_id > 100". 기본값인 prefilter=false에서는 해당 조건이 후보 생성 후에 적용됩니다. 옵티마이저가 외부 WHERE를 Doris Lance Scan으로 이동하더라도 Doris Scan Post-filter로 유지되며 Lance Prefilter로 변환되지 않습니다.

Lance는 filter에서만 참조하는 열을 내부적으로 읽고 평가합니다. 해당 열을 SELECT나 다른 Doris 표현식에서 참조하지 않으면 Doris로 반환할 필요가 없습니다.

FE 테이블 접근 캐시​

이 설정에는 테이블 접근 캐시 변경이 포함된 Doris 빌드가 필요합니다.

각 FE는 Catalog 내에서 해석된 테이블의 Dataset URI와 접근 옵션을 캐시하여 쿼리 계획 중 파일 시스템 탐색이나 REST describeTable 요청의 반복을 줄일 수 있습니다. 각 Catalog 클라이언트는 최대 10,000개의 항목을 유지합니다. lance.table_access_cache_ttl_seconds의 기본값은 60이며, 캐시 적중은 수명을 연장하지 않습니다. 이 캐시는 Dataset 버전을 저장하지 않습니다. 각 읽기는 여전히 Dataset을 열고 스냅샷을 선택합니다.

Namespace가 버전을 관리하는 테이블은 읽을 때마다 다시 해석하므로, 두 리더 모두 해당 읽기에 대해 Namespace가 반환한 위치와 스토리지 옵션을 사용합니다. 제공된 스토리지 옵션이 포함된 응답도 expires_at_millis를 보고하더라도 읽을 때마다 다시 해석합니다. 사용자 정보, 쿼리 매개변수(사전 서명/SAS 자격 증명 포함) 또는 Fragment가 포함된 URI도 캐시하지 않습니다. 고정된 자격 증명 만료 여유 시간으로는 스캔 내내 자격 증명이 유효하다고 보장할 수 없고, BE는 스캔 중 이러한 자격 증명을 갱신할 수 없습니다. 이러한 응답 필드가 없는 REST Catalog는 캐시를 사용할 수 있습니다.

테이블이나 데이터베이스를 명시적으로 새로 고치면 해당 Catalog의 모든 테이블 접근 항목이 지워집니다. 해당 로컬 데이터베이스/테이블 객체가 제거된 상태에서 새로 고침을 재생하는 follower FE도 포함됩니다. 일상적인 로컬 데이터베이스 객체 제거는 접근 캐시를 지우지 않습니다. 캐시 무효화를 포함한 Catalog 새로 고침, Namespace 제거 또는 Catalog 구성 변경도 접근 항목을 무효화합니다. 인덱스 조회 및 인덱스 작업 대상 검증은 항상 접근 정보를 새로 해석합니다.

원격 테이블 URI 또는 접근 구성이 변경되면 TTL 만료를 기다리지 않도록 명시적으로 새로 고치세요. 기존 테이블 example_lance.default.items의 예제입니다.

REFRESH TABLE example_lance.default.items;

다음 읽기에서는 테이블 접근 정보를 다시 해석합니다. 이 작업은 네이티브 Lance Session 캐시를 지우지 않습니다. 같은 URI의 Dataset을 교체한 후에는 캐시 무효화를 포함한 Catalog 새로 고침을 사용하세요. 이 새로 고침은 FE의 Lance Session만 지우며 BE의 캐시는 지우지 않습니다. 과거 버전 또는 브랜치 검색을 참조하세요.

기존 Catalog의 테이블 접근 캐시를 비활성화하려면 다음을 실행합니다.

ALTER CATALOG example_lance SET PROPERTIES (
    "lance.table_access_cache_ttl_seconds" = "0"
);

Lance Cache​

Lance Cache는 인덱스, 메타데이터 및 데이터 파일 내용을 재사용하여 반복 읽기를 줄입니다. 각 BE는 자체 캐시를 관리하며 해당 BE의 Lance 쿼리가 공유합니다. 캐시 용량과 내용은 BE 간에 공유되지 않습니다. 일반 스캔, 벡터 검색, 전문 검색 및 두 번째 단계의 가져오기는 추가 CREATE CATALOG 속성 없이 해당 캐시를 재사용할 수 있습니다.

데이터 캐시BE 로컬 디스크. 메모리 계층의 크기는 읽기 블록 하나에 해당.lance로 끝나는 파일(Dataset의 data/ 디렉터리 바로 아래)의 데이터를 블록 단위로 캐시합니다.

데이터 캐시는 Lance 리더 내부에서 Foyer를 사용하며, 자체 디렉터리와 용량은 아래의 lance_* BE 매개변수로 구성합니다. Doris의 일반 File Cache 디렉터리나 용량 설정은 사용하지 않습니다. 인덱스 파일, manifest 및 삭제 파일은 이 디스크 데이터 캐시를 거치지 않으며 기존 Lance 읽기 및 캐시 경로를 계속 사용합니다.

데이터 캐시는 전체 Dataset을 미리 다운로드하지 않고 필요에 따라 채워집니다. 캐시 미스가 발생하면 원본 스토리지에서 읽고, 백그라운드 디스크 캐시 쓰기를 위해 데이터를 큐에 넣습니다. 첫 읽기에는 원본 I/O와 캐시 채우기 오버헤드가 여전히 발생합니다. 캐시 적중은 이후 원본 읽기를 줄일 수 있지만 디코딩, 필터링 또는 정렬 비용을 없애지는 않습니다.

아래의 모든 매개변수는 선택 사항입니다. 각 BE의 be.conf에 설정하고 해당 BE를 다시 시작해야 변경 사항이 적용됩니다. 용량은 BE별이며 바이트 단위입니다.

BE가 다시 시작된 후 첫 Lance Dataset이 열릴 때 공유 캐시가 초기화됩니다. 데이터 캐시가 활성화된 상태에서 디렉터리를 사용할 수 없거나 용량 또는 블록 크기가 유효하지 않으면 초기화가 실패하고 Lance 쿼리가 오류를 보고합니다. 데이터 캐시 없이 실행하는 방식으로 자동 대체되지 않습니다. 디스크 데이터 캐시를 비활성화하려면 enable_lance_data_cache를 false로 설정하고 BE를 다시 시작하세요.

쿼리 작업 메모리와 함께 인덱스 및 메타데이터 캐시의 메모리도 산정하세요. 이 용량은 전체 Lance 쿼리 메모리나 BE 프로세스 메모리를 제한하지 않습니다. 디스크 캐시는 로컬 디스크 공간과 파일 디스크립터도 사용합니다. 읽기 블록이 크면 블록 수는 줄지만 작은 읽기의 추가 I/O가 늘어날 수 있습니다. 읽기 블록 크기나 디스크 레이아웃을 변경할 때는 새 캐시 디렉터리를 사용하세요.

워크로드별 용량 산정 공식, 구성 예제, 공유 캐시 경합 및 인덱스 세그먼트의 세분성은 Lance 쿼리 모범 사례를 참조하세요. 필터링과 검색을 함께 사용하는 경우 Lance Hybrid Search 성능 모범 사례를 참조하세요.

캐시 효과 확인​

완료된 쿼리 Profile에서 LanceReader → LanceIndex 아래의 인덱스 캐시 카운터와 LanceReader → LanceDataCache 아래의 데이터 파일 캐시 카운터를 확인하세요.

카운터의미
LanceIndexCacheHits, LanceIndexCacheMisses이번 실행에서 계측된 인덱스 경로가 보고한 캐시 조회입니다. BE 전체 Session 메트릭과는 별개입니다.
LanceIndexObjectLoads, LanceIndexComponentsLoaded로딩된 최상위 인덱스 객체와 내부 구성 요소입니다. 어느 쪽도 캐시 미스와 같은 의미로 사용할 수 없습니다.
LanceDataCacheBytesReadFromCache이 Dataset 핸들에 대해 데이터 파일 캐시가 제공한 논리적 요청 바이트입니다.
LanceDataCacheBytesReadFromRemote캐시 미스 또는 캐시 대체 경로 이후 원본 스토리지가 제공한 논리적 요청 바이트입니다. 원본이 로컬 파일일 수도 있습니다.

두 데이터 캐시 바이트 카운터는 블록 읽기 증폭과 인덱스 및 manifest 읽기처럼 데이터 캐시를 우회하는 I/O를 제외합니다. 완전한 원격 트래픽 카운터가 아니며, 합계가 LanceIOReadBytes와 같을 필요도 없습니다. 데이터 캐시가 비활성화되면 둘 다 0이지만, 원본 읽기가 없었다는 뜻은 아닙니다. Doris는 Dataset 핸들을 닫기 전에 누적 스냅샷을 기록합니다. 두 번째 단계의 가져오기는 별도의 리더 통계를 가지며 Row ID Fetch/Materialization Profile 정보로도 내보냅니다. 스캔 카운터만으로는 전체 쿼리의 가져오기 I/O를 포괄하지 못합니다. 수집 시점과 메트릭 범위는 Lance 쿼리 Profile 참조를 참조하세요.

BE /metrics 엔드포인트는 doris_be_lance_session_index_cache_ 및 doris_be_lance_session_metadata_cache_ 접두사가 붙은 메트릭도 노출합니다. 접미사 capacity_bytes, usage_bytes, entries, hits_total, misses_total은 각각 구성된 용량, 현재 사용량, 항목 수, 누적 적중 수 및 누적 미스 수를 나타냅니다. 이 메트릭은 공유 Lance Session이 초기화된 후 등록되며 개별 쿼리가 아닌 BE 전체 캐시를 설명합니다.

캐시 효과를 비교하려면 같은 Dataset 버전과 쿼리 매개변수를 사용하고, 쿼리가 실제로 같은 BE에서 실행되는지 확인하며, 첫 읽기와 반복 읽기의 지연 시간, 캐시 카운터 및 원본 I/O를 기록하세요. 전체 지연 시간만으로는 캐시의 이점과 인덱스 검색, 디코딩 또는 두 번째 단계의 가져오기 비용을 구분할 수 없습니다.

두 단계 TopN 읽기 및 지연 구체화​

vector_search()와 full_text_search()는 일반적으로 최종 top_k보다 많은 후보 행을 생성합니다. 검색 중 title이나 payload처럼 넓은 출력 열을 읽으면 대부분의 후보 행이 TopN에서 버려지므로 작업이 낭비됩니다. 두 단계 읽기는 이러한 열의 읽기를 미룹니다. 단계 1에서는 필터링, 정렬 및 TopN에 필요한 열만 읽고, 전역 TopN 이후 단계 2에서는 남겨진 행에 대해서만 나머지 출력 열을 읽습니다.

이는 스토리지 I/O, 네트워크 전송 및 메모리 사용량을 줄입니다. 일반적으로 top_k가 작거나, 검색이 많은 후보를 생성하거나, 쿼리가 넓은 문자열, JSON 또는 유사한 열을 반환할 때 효과가 가장 큽니다.

단계읽는 데이터
단계 1검색에서 내부적으로 사용하는 열, _distance 또는 _score, Post-filter나 정렬에 필요한 열 및 내부 Row Location.
단계 2최종 프로젝션에서만 사용하는 최상위 열. 전역 TopN에서 남겨진 행에 대해서만 읽습니다.

적용 조건​

Doris는 다음 조건이 모두 충족될 때만 두 단계 읽기를 사용합니다.

  1. 쿼리가 vector_search() 또는 full_text_search()로 Lance를 읽으며, 계획에 지연 구체화를 적용할 수 있는 TopN이 포함되어 있습니다. 이러한 검색 TVF로 재작성된 일반 SQL 쿼리도 적용 대상이 될 수 있습니다. 재작성되지 않은 스칼라 테이블 스캔과 Lance 파일 TVF에는 적용되지 않습니다.
  2. Boolean 세션 변수 enable_lance_lazy_materialization이 기본값인 true입니다.
  3. 읽기를 미룰 수 있는 최상위 열이 하나 이상 있습니다. 최종 SELECT 프로젝션에서만 사용하는 열은 읽기를 미룰 수 있습니다. Post-filter, ORDER BY 또는 TopN 이전의 다른 표현식에서 사용하는 열은 단계 1에서 읽어야 합니다. 중첩 하위 열은 현재 읽기를 미룰 수 없습니다.

enable_lance_lazy_materialization은 topn_lazy_materialization_threshold와 독립적입니다. 후자가 -1이거나 top_k가 해당 임계값을 초과해도 Lance는 두 단계 읽기를 사용할 수 있습니다. 지연 구체화를 지원하는 다른 테이블은 계속 일반 임계값을 따릅니다. 스위치를 활성화하면 최적화가 허용되지만, 실제 적용 여부는 계획 구조와 적합한 열에 따라 결정됩니다.

다음 쿼리에서 category는 Post-filter를 위해 단계 1에서 읽어야 하며, user_id, title, payload는 TopN 이후에 가져올 수 있습니다.

SET enable_lance_lazy_materialization = true;

SELECT user_id, title, payload, _distance
FROM vector_search(
    "table" = "lance_catalog.default.items",
    "column" = "embedding",
    "query_vector" = "[0.1, 0.2, 0.3, 0.4]",
    "top_k" = "10",
    "offset" = "3"
)
WHERE category = 'book';

TVF filter에서 참조하는 열은 Lance가 내부적으로 사용합니다. filter 문자열에 있다는 이유만으로 Doris에 반환되는 단계-1 결과 열이 되지는 않습니다. prefilter는 후보 생성을 기준으로 조건의 적용 시점만 바꿉니다.

계획 확인​

위 쿼리 앞에 EXPLAIN VERBOSE를 붙이세요. 두 단계 읽기가 활성화되면 계획에 VMaterializeNode가 포함되며, 해당 노드의 column_descs_lists에 단계 2에서 가져올 열이 나열됩니다. 스위치를 비활성화하고 같은 단순 검색 쿼리에 대해 EXPLAIN VERBOSE를 다시 실행하면 해당 구체화 노드가 사라져야 합니다. 스위치가 활성화되어 있는데도 노드가 없다면 출력 열이 TopN 이전의 필터링, 정렬 또는 다른 계산에 사용되는지, 계획이 이 최적화를 지원하는지 확인하세요.

두 단계 읽기 비활성화​

다음 세션 설정으로 두 단계 읽기를 비활성화합니다.

SET enable_lance_lazy_materialization = false;

읽기를 미룰 열이 없거나 계획이 최적화를 지원하지 않으면 Doris는 단일 단계 읽기를 사용합니다. Lance에서는 top_k가 크다는 이유만으로 두 단계 읽기가 자동으로 비활성화되지는 않습니다. 다음 경우에는 비활성화하여 성능을 비교해 보세요.

  • top_k가 커서 단계 2에서도 대부분의 후보 행을 읽는 경우.
  • 쿼리가 소수의 좁은 열만 반환하여 두 단계 읽기로 절약할 I/O가 적은 경우.
  • 기반 스토리지의 임의 Row-ID 읽기 지연 시간이 길고, 추가 단계-2 Fetch 비용이 읽기를 미뤄 절약하는 비용보다 큰 경우.

이 최적화를 비활성화하면 출력 열을 읽는 시점만 바뀝니다. 벡터 또는 FTS 인덱스를 비활성화하거나 Prefilter, Post-filter, TopN의 의미를 바꾸지는 않습니다. 대표적인 쿼리와 스토리지 조건에서 두 설정을 비교하세요.

전문 검색​

full_text_search()는 Lance 테이블의 기존 FTS 역색인을 통해 BM25 검색을 수행하는 관계형 TVF입니다. 분석된 쿼리 용어를 OR 또는 AND로 결합하고, Phrase 쿼리로 순서와 거리를 일치시키는 기능을 지원합니다. Doris는 물리적 인덱스 세그먼트의 후보를 전역 Top-K로 병합하고 원본 열에 _score를 추가합니다. 점수가 높을수록 관련성이 높습니다.

TVF를 사용하기 전에 Lance SDK 또는 다른 Lance writer로 대상 문자열 열에 FTS 역색인을 생성하세요. Phrase 쿼리에는 인덱스 생성 시 토큰 위치도 활성화해야 합니다. 예를 들어 Lance 인덱스 매개변수에 with_position=true를 설정합니다. Doris는 이 인덱스를 생성하지 않으며, 사용 가능한 FTS 인덱스가 없을 때 행별 전문 스캔으로 대체하지 않습니다.

구문 및 예제​

다음 쿼리는 lance database를 검색하되 범주가 storage인 문서로 한정한 후, published = true를 Doris Post-filter로 적용합니다.

SELECT document_id, title, _score
FROM full_text_search(
    "table" = "lance_catalog.default.documents",
    "column" = "body",
    "query" = "lance database",
    "query_type" = "match",
    "operator" = "and",
    "top_k" = "10",
    "offset" = "0",
    "prefilter" = "true",
    "filter" = "category = 'storage'",
    "coverage_mode" = "strict"
)
WHERE published = true
ORDER BY _score DESC, document_id;

이 예제는 Match AND를 사용하므로 문서에 분석된 두 용어인 lance와 database가 모두 있어야 합니다. prefilter=true이면 Lance는 FTS 후보를 생성하기 전에 filter를 평가합니다. prefilter를 생략하면 기본값은 false이며, Lance는 후보 생성 후에 filter를 적용하므로 결과가 top_k개 행보다 적을 수 있습니다. 외부 WHERE는 Doris Post-filter이며 제거된 후보를 보충하지 않습니다. published = true가 후보 생성에 영향을 주어야 한다면 filter에 포함하고 prefilter=true를 설정하세요.

다음 Phrase 쿼리는 인접한 쿼리 용어 사이에 최대 하나의 토큰이 끼어 있는 것을 허용합니다. 예를 들어 lance search engine과 일치할 수 있습니다.

SELECT document_id, title, _score
FROM full_text_search(
    "table" = "lance_catalog.default.documents",
    "column" = "body",
    "query" = "lance engine",
    "query_type" = "phrase",
    "slop" = "1",
    "top_k" = "10"
)
ORDER BY _score DESC, document_id;

반환되는 관계에는 원본 Lance 테이블의 모든 열과 nullable FLOAT 열인 _score가 포함됩니다. 원본 테이블에 이 이름의 열이 이미 있어서는 안 됩니다. TVF는 _score 내림차순으로 Top-K를 선택하지만, SQL 관계는 최종 표시 순서를 보장하지 않습니다. 안정적인 순서가 필요하면 ORDER BY _score DESC를 명시하고, 같은 점수의 순서를 결정할 고유한 열을 추가하세요.

매개변수​

매개변수필수 여부기본값설명

column예-FTS 역색인이 있는 문자열 열입니다. Arrow utf8와 large_utf8를 지원하며, 이 타입은 Doris TEXT에 매핑됩니다.
query예-비어 있지 않은 검색 텍스트입니다. FTS 인덱스를 생성할 때 구성한 토크나이저로 처리합니다.
query_type아니요match쿼리 유형입니다. 유효한 값은 match와 phrase입니다.
operator아니요orMatch 쿼리 전용입니다. or는 하나 이상의 쿼리 용어가 일치해야 하고, and는 모든 쿼리 용어가 일치해야 합니다. Phrase 쿼리에서는 이 매개변수를 설정할 수 없습니다.
slop아니요0Phrase 쿼리 전용입니다. 0부터 2147483647까지의 정수여야 합니다. 0은 정확한 구문 일치를 요구하며, 양수 값은 인접한 쿼리 용어 사이에 허용되는 중간 토큰의 최대 수입니다. Match 쿼리에서는 이 매개변수를 설정할 수 없습니다.
top_k아니요10offset만큼 건너뛴 후 반환할 결과 수입니다. 양의 정수여야 합니다.
offset아니요0관련성 순으로 건너뛸 결과 수입니다. 음이 아닌 정수여야 하며, top_k + offset은 부호 없는 32비트 정수의 최댓값을 초과할 수 없습니다.
filter아니요-Lance SQL 조건입니다. 실행 시점은 prefilter로 제어합니다.
prefilter아니요falseTVF filter의 실행 시점을 제어합니다. true는 전문 검색 후보 생성 전에 필터링하고, false(기본값)는 후보 생성 후에 필터링하므로 결과가 top_k개 행보다 적을 수 있습니다. 이 매개변수는 외부 Doris WHERE에 영향을 주지 않습니다.
coverage_mode아니요strictFTS 인덱스가 현재 스냅샷의 모든 Fragment를 포함하지 않을 때의 동작입니다. 유효한 값은 strict와 index_only입니다.
version, timestamp, tag, branch아니요-main의 최신 버전 대신 과거 버전, 특정 시점의 버전, 태그 또는 브랜치를 검색합니다. 과거 버전 또는 브랜치 검색을 참조하세요.

쿼리 유형​

쿼리 유형일치 동작관련 매개변수인덱스 요구 사항
Match OR분석된 쿼리 용어 중 하나 이상과 일치합니다. 기본 동작입니다.query_type=match, operator=or표준 FTS 역색인.
Match AND분석된 모든 쿼리 용어와 일치합니다.query_type=match, operator=and표준 FTS 역색인.

Boolean, Boost, Prefix, Wildcard, Regex 및 여러 필드에 걸친 복합 FTS 쿼리는 현재 지원하지 않습니다.

인덱스 범위 모드​

모드동작사용 시점
strict선택한 FTS 인덱스가 고정된 쿼리 스냅샷의 모든 Fragment를 포함해야 합니다. 포함되지 않은 Fragment가 하나라도 있으면 쿼리가 실패합니다.기본값이며, 결과에서 데이터가 누락되어서는 안 될 때 권장합니다. 데이터를 추가한 후에는 쿼리 전에 FTS 인덱스를 업데이트하거나 다시 구축하세요.
index_onlyFTS 인덱스가 포함하는 Fragment만 검색하고 포함되지 않은 데이터는 무시합니다.불완전한 결과를 허용할 수 있으며 인덱스 업데이트를 기다리는 동안에도 검색을 사용할 수 있어야 할 때만 사용하세요.

두 모드 모두 대상 열에 완전한 범위 메타데이터를 가진 커밋된 FTS 인덱스가 필요합니다. 사용 가능한 인덱스가 없으면 쿼리가 실패합니다. 열에는 논리적 FTS 인덱스를 하나만 유지하세요. 여러 인덱스가 일치하면 Doris는 모호함 없이 하나를 선택할 수 없어 쿼리를 거부합니다.

EXPLAIN으로 실행을 확인하세요. lanceFtsQueryType은 Match 또는 Phrase, lanceFtsMatchOperator는 Match OR/AND 연산자, lanceFtsPhraseSlop은 Phrase 거리를 표시합니다. lanceFtsCoverageMode는 범위 모드, lanceSearchIndexSegments는 사용한 물리적 FTS 인덱스 세그먼트 수, lanceSearchUnindexedFragments는 현재 스냅샷에서 인덱스가 포함하지 않는 Fragment 수를 표시합니다.

과거 버전 또는 브랜치 검색​

기본적으로 vector_search()와 full_text_search()는 main의 최신 버전을 검색합니다. 선택적 매개변수 네 개로 다른 스냅샷을 선택할 수 있으며, 의미는 테이블의 Time Travel 구문과 같습니다.

매개변수값동등한 테이블 구문함께 사용할 수 있는 매개변수
version양의 정수 버전FOR VERSION AS OF Nbranch
timestamp세션 시간대의 yyyy-MM-dd HH:mm:ss 또는 yyyy-MM-dd HH:mm:ss.SSSFOR TIME AS OF '...'branch

-- Search version 3.
SELECT id, _distance
FROM vector_search(
    "table" = "lance_catalog.db.documents",
    "column" = "embedding",
    "query_vector" = "[0.1, 0.2, 0.3]",
    "version" = "3")
ORDER BY _distance;

-- Search the branch "dev" as it was at a point in time.
SELECT id, _score
FROM full_text_search(
    "table" = "lance_catalog.db.documents",
    "column" = "content",
    "query" = "database",
    "branch" = "dev",
    "timestamp" = "2026-09-20 12:00:00")
ORDER BY _score DESC;
  • 스냅샷은 테이블 구문과 같은 규칙으로 선택됩니다. 브랜치를 가리키는 태그와 REST Namespace가 버전을 관리하는 테이블도 포함됩니다. version은 버전 번호만 받습니다. FOR VERSION AS OF와 달리 태그 이름은 받지 않습니다. tag가 태그를 모호함 없이 지정하기 때문입니다. 이름이 123인 태그는 "tag" = "123"으로 선택합니다.
  • version과 timestamp는 함께 사용할 수 없으며, tag는 나머지 세 매개변수 중 어느 것과도 함께 사용할 수 없습니다. 매개변수를 빈 값으로 설정하면 무시되지 않고 오류가 발생합니다.
  • 출력 스키마, 검색 열, 벡터 인덱스 및 FTS 인덱스 메타데이터, Fragment는 모두 선택한 스냅샷에서 가져옵니다. 후보 생성, 필터링, Top-K 및 두 단계 읽기는 모두 해당 스냅샷을 읽습니다. 과거 버전은 그 버전에 커밋된 인덱스를 사용합니다. 벡터 인덱스 생성 전 버전은 Flat Search를 사용하고, FTS 인덱스 생성 전 버전은 full_text_search()로 검색할 수 없으며, coverage_mode는 해당 버전의 Fragment를 검사합니다.
  • 선택할 수 없거나 인덱스 파일이 누락된 스냅샷은 오류가 발생합니다. 검색은 최신 버전으로 대체되지 않습니다. Lance의 정리 작업으로 제거된 버전은 찾을 수 없다고 보고됩니다. 태그로 유지되는 버전은 정리 작업 중에도 인덱스 파일을 유지합니다. 다른 방식으로 삭제된 인덱스 파일은 실행 시 실패를 일으키며, 오류에 데이터세트 버전이 표시됩니다.
  • 준비된 문의 모든 EXECUTE를 포함하여 실행할 때마다 스냅샷을 다시 선택하므로, 최신 버전, 미래 시점, 브랜치 및 이동된 태그는 매번 다른 버전을 선택할 수 있습니다. 네 매개변수는 상수여야 합니다. 준비된 문에서 vector_search()는 자리표시자(?)를 query_vector, top_k, offset, filter에만 허용하고, full_text_search()는 허용하지 않습니다.
  • 각 검색 관계는 자체 스냅샷을 선택합니다. 한 문에서 같은 테이블에 대한 두 관계, 예를 들어 vector_search()와 테이블 자체를 조인하는 경우, 그 사이에 새 버전이 커밋되면 서로 다른 버전을 읽을 수 있습니다. 같은 버전을 읽으려면 양쪽 모두 고정하세요. 검색 함수에는 version, 테이블에는 FOR VERSION AS OF를 사용합니다.
  • CREATE TABLE AS SELECT는 새 테이블의 스키마를 위해 한 번, 행을 위해 한 번 쿼리를 두 번 계획하므로, 변경되는 선택자는 매번 다른 버전을 선택할 수 있습니다. 하나의 버전을 정확히 복사하려면 version을 설정하세요.
  • EXPLAIN은 선택한 버전을 lanceVersion, 브랜치를 lanceBranch, REST Namespace의 버전 관리 여부를 lanceManagedVersioning으로 표시합니다. EXPLAIN도 스냅샷을 다시 선택하므로, 실제 실행에서 읽은 정보는 쿼리 Profile에 기록됩니다. LanceDatasetVersion과 LanceDatasetUri가 LanceSearchType 등 Lance Scanner의 다른 정보와 함께 표시됩니다. URI에는 브랜치 디렉터리가 포함되고 쿼리 문자열과 비밀번호는 제외됩니다.
  • 다른 브랜치 또는 얕은 복제본에서 생성된 브랜치는 상속받은 인덱스 파일을 찾지 못할 수 있습니다. 버전 13 이전의 Lance writer가 이를 중간 브랜치 아래에 기록하기 때문입니다. 이 경우 검색은 오류로 실패하며 브랜치 자체 인덱스에는 영향을 주지 않습니다.
  • 브랜치를 삭제하고 같은 이름으로 다시 생성하거나 같은 URI의 Dataset을 교체하면 새 데이터가 이전 버전 번호를 재사용합니다. BE는 항목이 제거되거나 BE가 다시 시작될 때까지 해당 버전 번호에 대해 캐시한 내용을 계속 사용할 수 있습니다. 안정적인 행 ID를 사용하는 Dataset에서는 벡터 검색과 전문 검색이 이전 데이터의 유효 행으로 필터링할 수 있으므로, 결과에 새 데이터에서 삭제된 행이 포함되거나 유효한 행이 누락될 수 있습니다. manifest가 Lance의 이전 명명 규칙(_versions/<version>.manifest)을 사용하거나 객체 스토리지가 ETag를 반환하지 않으면 BE와 FE가 이전 인덱스 메타데이터를 사용할 수도 있습니다. FE는 Catalog를 새로 고친 후 이전 메타데이터 사용을 중단합니다. 다시 생성하는 브랜치에 새 이름을 부여하거나 BE를 다시 시작하세요. Catalog 새로 고침은 이러한 BE 캐시를 지우지 않습니다.
  • 토큰 위치 없이 구축한 FTS 인덱스는 Phrase 쿼리를 실행할 수 없습니다. 과거 버전에서 계속 사용될 수 있는 이전 writer의 인덱스에는 위치 정보가 없는 경우가 많습니다.

현재 실행 모델​

vector_search()와 full_text_search()의 실행 순서는 다음과 같습니다.

Dataset snapshot selected by version / timestamp / tag / branch, or the latest version of main
  -> FE search Split planning
       -> Vector search: physical vector Index Segments + Flat Search for uncovered Fragments
       -> Full-text search: physical FTS Index Segments (coverage checked by coverage_mode)
  -> Per Split: vector/full-text search; the TVF `filter` runs before candidate generation when `prefilter=true`, and after candidate generation when `prefilter` is omitted or `false`
       -> at most K+n candidates
  -> Doris Scan Post-filter
  -> Doris local TopN
  -> Exchange
  -> Doris global TopN (applies offset=n and limit=K)
  -> Optional lazy-materialization Fetch

쿼리 Profile​

Profile 수집 및 조회는 쿼리 Profile 분석 가이드를 참조하세요. Lance 전용 그룹, 카운터, 시간 측정 범위 및 두 번째 단계의 가져오기 통계는 Lance 쿼리 Profile 참조를 참조하세요.

현재 제한 사항 및 권장 사항​

  • Lance Catalog와 Lance TVF는 읽기 전용입니다. CREATE TABLE, INSERT, UPDATE, DELETE, TRUNCATE TABLE 및 Lance로 데이터를 다시 쓰는 작업은 지원하지 않습니다.
  • 지원하지 않는 열 타입이 포함된 테이블에서는 SELECT *로 지원하지 않는 열을 프로젝션하는 대신 읽을 열을 명시적으로 나열하세요.
  • 일반 스캔에서는 lancePushdownPredicate를 EXPLAIN에서 확인하여 어떤 조건이 푸시다운되었는지 검증하세요.
  • 인덱스를 사용하는 벡터 검색을 실행하기 전에 의도한 쿼리에 맞는 벡터 인덱스를 Lance에 생성하세요. 작은 데이터세트나 검증에는 "use_index" = "false"를 설정하여 Flat Search를 수행하세요.
  • 전문 검색 전에 Lance에 FTS 역색인을 생성하세요. 기본 strict 모드는 인덱스가 현재 스냅샷의 모든 Fragment를 포함하지 않으면 쿼리를 거부합니다. 데이터 누락을 허용할 수 있을 때만 index_only를 사용하세요.
  • Phrase 쿼리에는 FTS 인덱스가 토큰 위치를 저장해야 합니다. Phrase 쿼리가 필요하다면 인덱스 생성 시 with_position=true를 설정하세요.
  • Filesystem Catalog 테이블에서 SHOW INDEX를 사용하여 논리적 Lance 인덱스를 조회하세요. 예를 들어 벡터 검색이나 전문 검색 전에 인덱스 이름, 유형 및 인덱싱된 필드를 확인할 수 있습니다. REST Catalog에서는 SHOW INDEX를 지원하지 않습니다.
  • 결정적인 벡터 결과 순서를 위해 ORDER BY _distance ASC를 명시하고 동점 순서를 결정할 고유한 열을 추가하세요.
  • 결정적인 전문 검색 결과 순서를 위해 ORDER BY _score DESC를 명시하고 동점 순서를 결정할 고유한 열을 추가하세요.
  • 벡터 또는 전문 검색 후보가 생성되기 전에 필터링하려면 TVF filter와 prefilter=true를 설정하세요. 기본값인 prefilter=false에서는 TVF filter가 후보 생성 후 적용됩니다. 외부 WHERE는 전역 TopN 이전에 각 검색 Split이 생성한 후보에 대해 Doris가 평가하므로, 최종 결과가 top_k개 행보다 적을 수 있습니다.
  • EXPLAIN으로 lanceSearchFragments와 lanceSearchIndexSegments를 확인하세요. 전자는 고정된 스냅샷에서 보이는 Fragment 수이며, 후자는 FE가 선택한 물리적 Index Segment 분할 단위 수입니다. 벡터 검색에는 대체 경로인 Flat Search Fragment 분할 단위도 포함될 수 있습니다. 전문 검색은 Flat Search로 대체되지 않습니다.
