TOPN 쿼리 최적화: ORDER BY LIMIT 가속 원리와 설정

한 문장으로 보는 정의​

TOPN 쿼리 최적화는 Doris가 ORDER BY ... LIMIT n 쿼리를 자동으로 가속하는 기능입니다. 동적 필터링, 범위 가지치기, 지연 구체화를 통해 스캔과 정렬에 드는 오버헤드를 크게 줄입니다.

읽기 전 체크리스트​

  • SQL이 SELECT ... FROM t WHERE ... ORDER BY c1, c2 ... LIMIT n 형식입니다.
  • 테이블 유형이 Duplicate 테이블 또는 Unique MOW 테이블입니다(MOR 제외).
  • n이 작습니다(topn_opt_limit_threshold보다 작으며, 기본값은 1024).
  • EXPLAIN과 Profile을 통해 최적화 적용 여부를 확인하려고 합니다.

일반적인 SQL 패턴​

TOPN 쿼리는 로그 검색과 같은 상세 조회 시나리오에서 자주 사용됩니다. Doris는 이러한 쿼리를 자동으로 인식하고 최적화합니다.

SELECT * FROM tablex WHERE xxx ORDER BY c1, c2 ... LIMIT n

세 가지 최적화 항목​

번호최적화원리주요 이점
최적화 1동적 범위 필터링(RuntimePredicate)정렬 중에 정렬 열의 범위 조건(예: c1 >= 10000)을 동적으로 생성하여 스캔 단계로 푸시다운Zonemap 인덱스를 사용하여 대량의 데이터뿐 아니라 파일 전체도 필터링
최적화 2키 접두사 기반 단축 읽기정렬 필드 c1, c2가 테이블 키의 접두사와 정확히 일치하면 데이터 파일의 처음 또는 마지막 n개 행만 읽음디스크 읽기를 크게 줄임
최적화 3두 단계 지연 구체화첫 번째 단계에서는 정렬 열만 읽어 정렬을 완료하고 행 번호를 얻으며, 두 번째 단계에서는 나머지 열을 읽음읽고 정렬해야 하는 열의 수를 크게 줄임

적용 제약 사항​

  1. 테이블 유형 제약: Duplicate 테이블과 Unique MOW 테이블만 지원합니다. Unique MOR 테이블에 이 최적화를 사용하면 잘못된 결과가 나올 수 있습니다.
  2. n 값 제약: n이 너무 크면 최적화에 필요한 메모리 사용량이 크게 증가합니다. n이 세션 변수 topn_opt_limit_threshold를 초과하면 최적화가 활성화되지 않습니다.
  1. 두 단계 읽기 제약: 4.1.5부터 Doris 내부 테이블의 TopN 지연 구체화에는 light_schema_change가 필요하며, Aggregate Key 테이블은 지원하지 않습니다. 이 조건을 충족하지 않으면 Doris는 일반 TopN 실행 경로를 사용하며 쿼리는 계속 실행할 수 있습니다.

설정 매개변수​

다음 네 개의 매개변수는 모두 세션 변수입니다. 단일 SQL 문에 적용하거나 전역으로 설정할 수 있습니다.

매개변수기본값효과튜닝 권장 사항
topn_opt_limit_threshold1024LIMIT n이 이 값보다 작을 때만 TOPN 최적화를 활성화0으로 설정하면 TOPN 최적화 전체를 비활성화
enable_two_phase_read_opttrue최적화 3(두 단계 지연 구체화)의 활성화 여부false로 설정하면 최적화 3만 비활성화
topn_filter_ratio0.5전체 테이블 데이터에 대한 LIMIT n의 비율 임계값LIMIT 개수가 테이블 데이터의 절반을 초과하면 필터를 생성하지 않음
enable_topn_lazy_mat_phase2_no_write_file_cachefalse스토리지와 컴퓨팅 분리 모드에서 Doris 내부 테이블의 지연 구체화 2단계에 File Cache 미스가 발생했을 때 캐시 쓰기를 생략할지 제어2단계에서 읽은 데이터의 재사용률이 낮고 캐시를 오염시킬 가능성이 있을 때만 활성화

TOPN 최적화 활성화 여부 확인​

목적: 실행 계획을 통해 현재 SQL에 어떤 최적화 항목이 활성화되어 있는지 확인합니다.

명령어:

EXPLAIN <your_sql>;

설명: 쿼리 실행 계획에서 다음 표시를 확인합니다.

  • TOPN OPT: 최적화 1(동적 범위 필터링)이 활성화됨
  • SORT LIMIT가 VOlapScanNode 아래에 표시됨: 최적화 2(키 접두사 기반 단축 읽기)가 활성화됨
  • MaterializeNode(이전 실행 계획에서는 OPT TWO PHASE): 최적화 3(두 단계 지연 구체화)이 활성화됨

지연 구체화 2단계의 File Cache 쓰기 제어​

스토리지와 컴퓨팅이 분리된 클러스터에서 TOPN 지연 구체화의 2단계는 1단계에서 선택한 행 ID를 기준으로 나머지 열을 읽습니다. 소수의 결과 행이 여러 Segments에 흩어져 있으면 이러한 산발적인 읽기로 채워진 캐시 블록은 재사용이 거의 되지 않으면서 자주 사용하는 데이터를 캐시에서 밀어낼 수 있습니다. 이 경우 enable_topn_lazy_mat_phase2_no_write_file_cache를 활성화하면 2단계에서 캐시 미스가 발생한 데이터를 원격 스토리지에서 직접 읽고 File Cache에는 쓰지 않습니다.

이 변수는 쿼리 결과를 변경하지 않습니다. 2단계에서 File Cache 미스를 처리하는 방식만 변경합니다.

설정2단계 읽기 동작
false(기본값)일반적인 읽기 및 캐시 쓰기 정책을 사용합니다. 캐시 미스가 발생하면 Doris가 원격 데이터를 읽고 해당 데이터를 File Cache에 씁니다.
trueDOWNLOADED 상태의 캐시 블록이 현재 읽기 범위를 완전히 포함할 때만 로컬 캐시를 읽습니다. 어느 부분이라도 캐시되지 않았거나 아직 다운로드 중이면 Doris는 캐시 블록을 생성하거나 쓰지 않고 현재 범위 전체를 원격 스토리지에서 읽습니다.

이 변수를 활성화하기 전에 다음 적용 범위를 확인하세요.

  • 스토리지와 컴퓨팅 분리 모드에서만 적용되며, Doris 내부 테이블의 TOPN 지연 구체화 2단계만 제어합니다. 현재 외부 테이블의 2단계 읽기는 제어하지 않습니다.
  • Doris 내부 테이블에서 행 저장소 활성화 여부와 관계없이 지원합니다.
  • 기존 캐시 항목을 제거하지 않으며, 1단계, 다른 쿼리 또는 다른 연산자가 수행하는 캐시 쓰기를 변경하지 않습니다. 따라서 쿼리 전체의 File Cache 쓰기량은 여전히 영보다 클 수 있습니다.
  • File Cache가 비활성화되어 있거나 실행 계획에 MaterializeNode가 없으면 추가 효과가 없습니다.

기본 사용법​

다음 예시에는 스토리지와 컴퓨팅이 분리된 클러스터, BE에서 활성화된 File Cache, 대상 데이터베이스에서 테이블 생성 및 삭제와 데이터 삽입 및 조회 권한이 있는 사용자가 필요합니다. 먼저 Duplicate Key 내부 테이블을 생성합니다.

DROP TABLE IF EXISTS topn_file_cache_demo;

CREATE TABLE topn_file_cache_demo (
    id BIGINT NOT NULL,
    event_time DATETIME NOT NULL,
    payload VARCHAR(128) NOT NULL
)
ENGINE=OLAP
DUPLICATE KEY(id)
DISTRIBUTED BY HASH(id) BUCKETS 1
PROPERTIES (
    "replication_num" = "1",
    "light_schema_change" = "true"
);

INSERT INTO topn_file_cache_demo VALUES
    (1, '2026-01-01 10:00:00', 'alpha'),
    (2, '2026-01-02 10:00:00', 'beta'),
    (3, '2026-01-03 10:00:00', 'gamma');

Profile과 2단계 캐시 쓰기 생략 정책을 활성화하고 실행 계획을 확인한 후 쿼리를 실행합니다.

SET enable_profile = true;
SET profile_level = 2;
SET enable_sql_cache = false;
SET enable_query_cache = false;
SET enable_topn_lazy_mat_phase2_no_write_file_cache = true;

EXPLAIN SELECT id, payload
FROM topn_file_cache_demo
ORDER BY event_time DESC
LIMIT 2;

SELECT id, payload
FROM topn_file_cache_demo
ORDER BY event_time DESC
LIMIT 2;

실행 계획에 MaterializeNode가 있어야 합니다. 변수의 활성화 여부와 관계없이 쿼리는 다음 결과를 반환합니다.

+----+---------+
| id | payload |
+----+---------+
|  3 | gamma   |
|  2 | beta    |
+----+---------+
2 rows in set

기본 캐시 쓰기 동작으로 복원하려면 다음을 실행합니다.

SET enable_topn_lazy_mat_phase2_no_write_file_cache = false;

Profile에서 캐시 정책 확인​

profile_level을 2로 설정한 후 Query Profile에서 MaterializeNode에 해당하는 실행 연산자 아래의 다음 2단계 전용 지표를 확인합니다.

측정 항목집계 지표의미
읽기 규모TopNLazyMaterializationSecondPhaseRowsRead, TopNLazyMaterializationSecondPhaseSegmentsRead2단계에서 읽은 행 수와 접근한 Segments 수
로컬 캐시 읽기TopNLazyMaterializationSecondPhaseLocalIOCount, TopNLazyMaterializationSecondPhaseLocalIOBytes, TopNLazyMaterializationSecondPhaseLocalIOTimeFile Cache에서 읽은 횟수, 바이트 수 및 소요 시간
원격 읽기TopNLazyMaterializationSecondPhaseRemoteIOCount, TopNLazyMaterializationSecondPhaseRemoteIOBytes, TopNLazyMaterializationSecondPhaseRemoteIOTime원격 스토리지에서 읽은 횟수, 바이트 수 및 소요 시간
캐시 우회TopNLazyMaterializationSecondPhaseSkipCacheIOCountFile Cache에 쓰지 않은 원격 읽기 횟수
캐시 쓰기TopNLazyMaterializationSecondPhaseWriteCacheBytes, TopNLazyMaterializationSecondPhaseWriteCacheIOTimeFile Cache에 쓴 바이트 수와 쓰기에 걸린 시간

캐시 쓰기 생략 정책을 활성화한 경우 다음 패턴으로 동작을 확인합니다.

캐시 상태예상 지표 패턴
현재 읽기 범위가 완전히 캐시되지 않음RemoteIOCount, RemoteIOBytes, SkipCacheIOCount가 0보다 크고, WriteCacheBytes는 0
다운로드된 캐시 블록이 현재 읽기 범위를 완전히 포함함LocalIOCount와 LocalIOBytes가 0보다 크고, RemoteIOCount, RemoteIOBytes, WriteCacheBytes는 0

Profile은 BE별 지표도 제공합니다. TopNLazyMaterializationSecondPhasePerBackend는 BE 목록을 나타냅니다. 다른 지표 이름에는 PerBackend가 SecondPhase 뒤에 추가됩니다. 예를 들면 TopNLazyMaterializationSecondPhasePerBackendRowsRead와 TopNLazyMaterializationSecondPhasePerBackendWriteCacheBytes입니다. 배열 요소는 인덱스에 따라 BE 목록에 대응하며, 동일한 쿼리 내에서 여러 차례 수행된 2단계 데이터 가져오기의 데이터를 누적합니다.

노트

TopNLazyMaterializationSecondPhaseWriteCacheBytes는 지연 구체화의 2단계만 포함합니다. 일반 File Cache 지표에서 여전히 쓰기가 보고되면 먼저 해당 쓰기가 1단계 또는 다른 연산자에서 발생했는지 확인하세요. Profile을 얻는 방법은 쿼리 Profile 분석을 참조하세요.

TOPN 최적화의 실행 효과 확인​

목적: 실행 시간과 Profile 지표를 비교하여 TOPN 최적화의 실제 필터링 효과를 확인합니다.

단계:

  1. topn_opt_limit_threshold를 0으로 설정하여 최적화를 비활성화하고 실행 시간을 기록합니다.
  2. 기본값으로 복원하여 최적화를 활성화한 후 실행 시간을 기록하고 비교합니다.
  3. Query Profile에서 RuntimePredicate를 검색하고 아래 표의 주요 지표를 확인합니다.

주요 지표:

지표의미기대 추세
RowsZonemapRuntimePredicateFilteredRuntimePredicate로 필터링된 행 수클수록 좋음
NumSegmentFiltered필터링된 데이터 파일(Segments) 수클수록 좋음
BlockConditionsFilteredZonemapRuntimePredicateTimeRuntimePredicate가 데이터를 필터링하는 데 걸린 시간작을수록 좋음

참고: 2.0.3 이전 버전에서는 RuntimePredicate 지표가 별도로 집계되지 않습니다. 일반 Zonemap 지표를 통해 대략적으로 확인할 수 있습니다.

자주 묻는 질문(FAQ / 문제 해결)​

Q1: EXPLAIN에 TOPN OPT가 없습니다. 가능한 원인은 무엇인가요?

  • LIMIT n이 topn_opt_limit_threshold(기본값 1024)보다 큽니다.
  • 테이블 전체 행 수에 대한 LIMIT n의 비율이 topn_filter_ratio(기본값 0.5)를 초과합니다.
  • 테이블이 Unique MOR 테이블이므로 이 최적화를 사용할 수 없습니다.

Q2: 최적화를 활성화한 후 SQL이 더 느려졌습니다. 이유가 무엇인가요?

  • n이 너무 커서 메모리 오버헤드가 증가했는지 확인하세요. topn_opt_limit_threshold를 적절히 낮출 수 있습니다.
  • Profile의 RowsZonemapRuntimePredicateFiltered로 필터링 효과를 확인하세요. 필터링된 행 수가 0이면 최적화의 이점이 없습니다.

Q3: 최적화 3(두 단계 읽기)만 비활성화하고 최적화 1과 2는 유지하려면 어떻게 해야 하나요?

enable_two_phase_read_opt = false로 설정하세요.

Q4: MOR 테이블의 ORDER BY LIMIT 쿼리가 잘못된 결과를 반환합니다. 이유가 무엇인가요?

MOR 테이블에서 TOPN 최적화가 활성화되어 있지 않은지 확인하세요. MOR 테이블의 경우 MOW 모델을 사용하거나 이 최적화 경로가 실행되지 않도록 하세요.

Q5: 2단계 캐시 쓰기 생략 정책을 활성화한 후에도 쿼리가 File Cache에 쓰는 이유는 무엇인가요?

이 정책은 Doris 내부 테이블의 TOPN 지연 구체화 2단계만 제어합니다. 1단계, 다른 연산자, 외부 테이블 읽기는 여전히 File Cache에 쓸 수 있습니다. 쿼리의 전체 쓰기량에 의존하지 말고 TopNLazyMaterializationSecondPhaseWriteCacheBytes를 사용하여 2단계에서 캐시 쓰기가 수행되었는지 확인하세요.

TOPN 최적화 전체 비활성화SET topn_opt_limit_threshold = 0;
