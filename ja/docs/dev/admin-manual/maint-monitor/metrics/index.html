監視メトリクス

DorisのFEとBEのプロセスには監視メトリクスが組み込まれており、デフォルトでPrometheus互換形式で公開されます。このドキュメントでは、観測できるすべてのメトリクスを体系的に一覧化し、優先度（Priority）を示します。PrometheusとGrafanaを連携させた後、監視とアラートの仕組みをすばやく構築できます。

適用シナリオ​

シナリオ目的
クラスタの健全性監視P0メトリクスを使ってFE/BEノードの異常をすばやく検出する
アラート設定QPS、エラー率、Compaction Scoreなどのメトリクスにしきい値ベースのアラートを設定する
パフォーマンスのトラブルシューティングクエリのレイテンシ、スレッドプールのキュー滞留、メモリ使用量のメトリクスを使ってボトルネックを特定する
容量計画ディスク使用量、tablet数、接続数を使ってクラスタの負荷を評価する
障害の振り返りマシンのメトリクス（CPU、IO、ネットワーク）とプロセスのメトリクスを組み合わせて障害の根本原因を分析する

メトリクスの分類​

Dorisの監視メトリクスは、観測対象によって次の2種類に分かれます。

  1. プロセス監視：クエリ数、トランザクション数、Compactionの状態など、Dorisプロセス自体の実行時メトリクスを示します。
  2. ノード監視：CPU、メモリ、IO、ネットワークなど、Dorisプロセスが稼働するマシンのリソースメトリクスを示します。

監視メトリクスの取得​

Prometheus互換形式（デフォルト）​

FEまたはBEノードのHTTPポートに直接アクセスします。

curl http://fe_host:http_port/metrics
curl http://be_host:webserver_port/metrics

レスポンス例：

doris_fe_cache_added{type="partition"} 0
doris_fe_cache_added{type="sql"} 0
doris_fe_cache_hit{type="partition"} 0
doris_fe_cache_hit{type="sql"} 0
doris_fe_connection_total 2

JSON形式​

type=jsonパラメータを使用して、メトリクスをJSON形式で取得します。

curl http://fe_host:http_port/metrics?type=json
curl http://be_host:webserver_port/metrics?type=json

bvarメトリクス​

BEおよびMeta Service / Recyclerのプロセスは、それぞれのbrpcサービスからbvarメトリクスも公開します。Prometheus互換の出力には/brpc_metricsを、名前を指定した診断情報の確認には/varsを使用します。

curl http://be_host:brpc_port/brpc_metrics
curl http://be_host:brpc_port/vars
curl http://cloud_host:brpc_listen_port/brpc_metrics

これらのエンドポイントは、BEのbrpc_port（デフォルトは8060）またはMeta Service / Recyclerのbrpc_listen_port（デフォルトは5000）を使用します。前述のFE / BEのHTTP監視ポートとは異なります。以下のbvar名は登録名に従っており、すべてにdoris_be_プレフィックスが付くわけではありません。

バージョンの識別​

バージョン4.1.5以降、BEとMeta Service / Recyclerのバージョンメトリクスには、/brpc_metricsで次のラベルが含まれます。

メトリクス型ラベル意味
doris_be_versionGaugeversion、major、minor、patch、hotfix、short_hashBEのビルドバージョンとコミット識別子
doris_cloud_versionGauge上記と同じMeta Service / Recyclerのビルドバージョンとコミット識別子

各プロセスはバージョンのサンプルを1つ公開します。メトリクス値には従来のバージョンエンコーディングが保持されます。完全なバージョンはversionラベル、コミット識別子はshort_hashラベルで確認してください。doris_cloud_versionでは、そのプロセスがMeta Service、Recycler、または両方のどれを実行しているかを区別できません。役割を識別するには、スクレイプターゲットのラベルを追加してください。

プロセスのbvar_max_dump_multi_dimension_metric_num設定は、多次元bvarサンプルの数を制限します。デフォルトは5000で、0にするとバージョンメトリクスなどのサンプルが無効になります。BEではバージョン4.1.5以降にこの設定を使用でき、変更を反映するには再起動が必要です。BE設定を参照してください。

監視の優先度とベストプラクティス​

  • 各メトリクステーブルの最後の列は優先度（Priority）です。P0が最も重要で、値が大きいほど重要度は低くなります。まずP0メトリクスを連携させてください。

  • 監視メトリクスの大半はCounter型（累積値）です。有用な情報を得るには、一定間隔（たとえば15秒ごと）でサンプリングし、単位時間あたりの傾きを計算する必要があります。

    たとえば、doris_fe_query_errの傾きを計算すると、クエリのエラー率（1秒あたりのエラー数）が得られます。

より網羅的で有用な監視メトリクスを提供するため、この表への貢献を歓迎します。

以下のメトリクスはバージョン4.1.5以降でサポートされ、前述のbrpcポートを使用します。Counterはプロセス起動時から累積し、Gaugeは現在値を示します。

名前またはプレフィックスプロセス型意味
sync_tablets_meta_numコンピュートとストレージの分離モードのBECounterバックグラウンドでtabletメタデータの同期を試みた累積回数。呼び出し前にカウントされるため、成功した呼び出し数を表すものではありません
sync_tablets_rowsets_numコンピュートとストレージの分離モードのBECounterバックグラウンドでtabletのrowsetの同期を試みた累積回数。呼び出し前にカウントされるため、成功した呼び出し数を表すものではありません
vertical_compaction_active_segment_contextsBEGaugevertical Compactionが保持する、現在アクティブなSegment context数
hdfs_get_path_infoBEレイテンシ統計、マイクロ秒HDFSファイルのメタデータアクセスを診断するためのhdfsGetPathInfoレイテンシメトリクスのプレフィックス
ms_repair_tablet_indexMeta ServiceCounterトランザクションのコミット時に、不足していたdb_idを追加するために修復された過去のTablet Indexレコードの累積数。コミットが成功した後にのみカウントされます

FAQ​

Q: 監視エンドポイントが404を返します。どうすればよいですか？​

FEのhttp_portまたはBEのwebserver_portにアクセスしていることを確認し、fe.conf / be.confで実際のポート番号を確認してください。

Q: Counterメトリクスは増えるだけで減りません。正常ですか？​

正常です。Counterは累積値を表します。瞬間的なレートを得るには、一定間隔でサンプリングして傾きを計算する必要があります（たとえばPromQLのrate()を使用します）。

Q: 複数のFE間でdoris_fe_max_journal_idの差が大きすぎます。どうすればよいですか？​

メタデータの同期遅延を示しています。Master FEに対するFollower / Observer FEのネットワーク接続とリプレイ速度を確認してください。

Q: Compaction Scoreが高いままです。どう調査すればよいですか？​

doris_be_tablet_base_max_compaction_scoreとdoris_be_tablet_cumulative_max_compaction_scoreを重点的に確認し、ディスクIOとCompactionタスク数を併せてボトルネックを特定してください。

Q: クエリやデータロードが滞留しています。どう調査すればよいですか？​

fragment_thread_pool_queue_size、doris_be_scanner_thread_pool_queue_size、doris_be_send_batch_thread_pool_queue_sizeなど、スレッドプールのキュー滞留メトリクスを確認してください。
