Routine Load

Routine Load は、Apache Doris が提供するストリーミングデータロードジョブです。Kafka トピックからデータを継続的に読み取り、Doris のテーブルに書き込みます。Routine Load ジョブを送信すると、Doris はジョブを継続して実行し、Kafka クラスター内の指定されたトピックからメッセージを読み取るデータロードタスクをリアルタイムで生成します。また、Exactly-Once セマンティクスにより、データの欠落や重複を防ぎます。

ユースケース​

Routine Load は、次のシナリオに適しています。

  • Kafka トピックから Doris にリアルタイムデータを継続的に同期する。
  • データの欠落や重複を避けるため、Exactly-Once セマンティクスが必要な場合。
  • 取り込むデータに列のマッピング、フィルタリング、派生列の計算などの変換を適用する。
  • 単一の Kafka トピックから複数の Doris テーブルにデータを動的に振り分ける（単一ストリーム、複数テーブル）。

対応するデータソースと形式​

Routine Load が読み取り元としてサポートするのは Kafka クラスターのみで、次のメッセージ形式に対応します。

形式説明
CSV各メッセージは単一行で、行末に改行文字を含めません。
JSON単一の JSON オブジェクト、または複数のオブジェクトを含む JSON 配列。

CSV 形式でデータを取り込む場合は、NULL 値と空文字列を明確に区別してください。

  • NULL 値は \n で表します。たとえば、a,\n,b は中央の列が NULL 値であることを示します。
  • 空文字列は、そのまま空のデータとして設定されます。たとえば、a,,b は中央の列が空文字列（''）であることを示します。

制限事項​

Routine Load で Kafka からデータを読み取る場合、次の制限があります。

制限説明
メッセージ形式CSV と JSON のテキスト形式のみをサポートします。各 CSV メッセージは単一行で、行末に改行文字を含めません。
Kafka のバージョンデフォルトでは Kafka 0.10.0.0 以降をサポートします。0.10.0.0 より前の Kafka バージョン（0.9.0、0.8.2、0.8.1、0.8.0）を使用するには、BE 設定の kafka_broker_version_fallback を互換性が必要な旧バージョンに変更するか、ジョブ作成時に property.broker.version.fallback を直接設定します。旧バージョンを使用すると、時刻による Kafka パーティションオフセットの設定など、Routine Load の一部の新機能を利用できない場合があります。

基本原理​

Routine Load は Kafka トピックからデータを継続的に読み取り、Doris に書き込みます。Doris で Routine Load ジョブを作成すると、複数のデータロードタスクを含む、長時間実行されるデータロードジョブが生成されます。

  • データロードジョブ: Routine Load Job は、データソースからデータを継続的に読み取る、長時間実行されるデータロードジョブです。
  • データロードタスク: 実際の読み取り処理のため、データロードジョブは複数のタスクに分割されます。各タスクは独立したトランザクションです。

Routine Load の詳細な流れを次の図に示します。

全体の流れは次のとおりです。

  1. クライアントが FE に Routine Load ジョブの作成リクエストを送信します。FE は Routine Load Manager を通じて、長時間実行されるデータロードジョブ（Routine Load Job）を生成します。
  2. FE は Job Scheduler を通じて Routine Load Job を複数の Routine Load Task に分割します。その後、Task Scheduler がタスクを BE ノードに割り当てます。
  3. BE で Routine Load Task のデータロードが完了すると、FE にトランザクションをコミットし、ジョブのメタデータを更新します。
  4. Routine Load Task がコミットされると、新しいタスクが生成されるか、タイムアウトしたタスクが再試行されます。
  5. 新しく生成された Routine Load Task は、Task Scheduler によって継続的にスケジュールされます。

自動復旧の仕組み​

ジョブの高可用性を確保するため、Routine Load には自動復旧の仕組みがあります。ジョブが予期せず一時停止すると、Routine Load Scheduler スレッドが自動復旧を試みます。Kafka 側の予期しない停止などで処理を続行できなくなっても、Kafka が復旧すれば、手動操作なしでデータロードジョブを正常に再開できます。

自動復旧されるケースと、手動操作が必要なケースを次に示します。

一時停止の原因自動復旧推奨される対応
Kafka broker に一時的に接続できない、ネットワークが不安定ありScheduler が period_of_auto_resume_min の間隔で自動的に再試行します。
ユーザーが PAUSE ROUTINE LOAD を手動で実行したなしRESUME ROUTINE LOAD を手動で実行します。
データ品質の問題（max_filter_ratio または max_error_number の超過）なしErrorLogUrls を調査し、データまたはパラメータを調整してから RESUME します。
データベースやテーブルの削除など、復旧できないメタデータの例外なしテーブルを再作成するか、ジョブを作り直します。

クイックスタート​

このセクションでは、Kafka から Routine Load ジョブを作成する最小限の実行例と、ジョブの表示、一時停止、再開、変更、停止の基本操作を説明します。

データロードジョブを作成する​

CREATE ROUTINE LOAD コマンドを使用すると、長時間実行される Routine Load データロードタスクを作成できます。Routine Load は CSV と JSON のデータを読み取れます。

CSV データを取り込む​

  1. Kafka のサンプルデータを用意します。

    kafka-console-consumer.sh --bootstrap-server localhost:9092 --topic test-routine-load-csv --from-beginning
    1,Emily,25
    2,Benjamin,35
    3,Olivia,28
    4,Alexander,60
    5,Ava,17
    6,William,69
    7,Sophia,32
    8,James,64
    9,Emma,37
    10,Liam,64

  2. データロード先のテーブルを作成します。

    CREATE TABLE testdb.test_routineload_tbl(
        user_id            BIGINT       NOT NULL COMMENT "user id",
        name               VARCHAR(20)           COMMENT "name",
        age                INT                   COMMENT "age"
    )
    DUPLICATE KEY(user_id)
    DISTRIBUTED BY HASH(user_id) BUCKETS 10;

  3. Routine Load ジョブを作成します。

    CREATE ROUTINE LOAD testdb.example_routine_load_csv ON test_routineload_tbl
    COLUMNS TERMINATED BY ",",
    COLUMNS(user_id, name, age)
    FROM KAFKA(
        "kafka_broker_list" = "192.168.88.62:9092",
        "kafka_topic" = "test-routine-load-csv",
        "property.kafka_default_offsets" = "OFFSET_BEGINNING"
    );

JSON データを取り込む​

  1. Kafka のサンプルデータを用意します。

    kafka-console-consumer.sh --bootstrap-server localhost:9092 --topic test-routine-load-json --from-beginning
    {"user_id":1,"name":"Emily","age":25}
    {"user_id":2,"name":"Benjamin","age":35}
    {"user_id":3,"name":"Olivia","age":28}
    {"user_id":4,"name":"Alexander","age":60}
    {"user_id":5,"name":"Ava","age":17}
    {"user_id":6,"name":"William","age":69}
    {"user_id":7,"name":"Sophia","age":32}
    {"user_id":8,"name":"James","age":64}
    {"user_id":9,"name":"Emma","age":37}
    {"user_id":10,"name":"Liam","age":64}

  2. データロード先のテーブルを作成します。

    CREATE TABLE testdb.test_routineload_tbl(
        user_id            BIGINT       NOT NULL COMMENT "user id",
        name               VARCHAR(20)           COMMENT "name",
        age                INT                   COMMENT "age"
    )
    DUPLICATE KEY(user_id)
    DISTRIBUTED BY HASH(user_id) BUCKETS 10;

  3. Routine Load ジョブを作成します。

    CREATE ROUTINE LOAD testdb.example_routine_load_json ON test_routineload_tbl
    COLUMNS(user_id,name,age)
    PROPERTIES(
        "format"="json",
        "jsonpaths"="[\"$.user_id\",\"$.name\",\"$.age\"]"
    )
    FROM KAFKA(
        "kafka_broker_list" = "192.168.88.62:9092",
        "kafka_topic" = "test-routine-load-json",
        "property.kafka_default_offsets" = "OFFSET_BEGINNING"
    );
注

JSON ファイルのルートにある JSON オブジェクトを取り込むには、jsonpaths を $. に設定します。例: PROPERTIES("jsonpaths"="$. ")。

データロードジョブを一時停止する​

PAUSE ROUTINE LOAD コマンドでデータロードジョブを一時停止できます。一時停止したジョブは PAUSED 状態になりますが、終了はしません。RESUME ROUTINE LOAD コマンドで再開できます。

PAUSE ROUTINE LOAD FOR testdb.example_routine_load_csv;

データロードジョブを再開する​

RESUME ROUTINE LOAD コマンドで、PAUSED 状態のデータロードジョブを再開できます。

RESUME ROUTINE LOAD FOR testdb.example_routine_load_csv;

データロードジョブを変更する​

ALTER ROUTINE LOAD コマンドで、作成済みのデータロードジョブを変更できます。変更前に PAUSE ROUTINE LOAD でジョブを一時停止し、変更後に RESUME ROUTINE LOAD で再開します。

たとえば、目標並列数のパラメータ desired_concurrent_number と Kafka トピック情報を変更するには、次のようにします。

ALTER ROUTINE LOAD FOR testdb.example_routine_load_csv
PROPERTIES(
    "desired_concurrent_number" = "3"
)
FROM KAFKA(
    "kafka_broker_list" = "192.168.88.60:9092",
    "kafka_topic" = "test-topic"
);

データロードジョブを取り消す​

STOP ROUTINE LOAD コマンドで Routine Load ジョブを停止し、削除できます。削除したデータロードジョブは復元できず、SHOW ROUTINE LOAD コマンドでも表示できません。

STOP ROUTINE LOAD FOR testdb.example_routine_load_csv;

Compute Group をバインドする​

ストレージとコンピューティングを分離したモードでは、Routine Load が使用する Compute Group は次の優先順位で選択されます。

  1. 4.1.5 以降では、ジョブプロパティ "compute_group" = "<compute_group_name>" で明示的にバインドされた Compute Group を優先します。
  2. このプロパティを省略した場合は、use db@cluster で指定された Compute Group を選択します。
  3. ユーザープロパティ default_compute_group で指定された Compute Group を選択します。
  4. 現在のユーザーにアクセス権限がある Compute Group を選択します。

compute_group は、デフォルトのバインド先を持たない任意の文字列プロパティです。コンピューティングとストレージを分離したモードでのみサポートされます。グループが存在し、作成者がそのグループに対する USAGE 権限を持っている必要があります。DEFAULT は大文字と小文字を区別せずに予約されており、バインドできません。明示的なバインドはセッションでの選択より優先されます。各タスクは実行前に、グループの存在とジョブ所有者の権限を再確認します。グループが存在しない場合、復旧までジョブが一時停止することがあります。権限が取り消された場合は、権限を復元してからジョブを手動で再開してください。

以下の CREATE ROUTINE LOAD の例では、PROPERTIES にこのプロパティを追加します。

PROPERTIES (
    "compute_group" = "cg_ingest",
    "desired_concurrent_number" = "3"
)

ストレージとコンピューティングが統合されたモードでは、ユーザープロパティ resource_tags.location で指定された Compute Group を選択します。ユーザープロパティで Compute Group が指定されていない場合は、default という名前の Compute Group を使用します。

注意

Routine Load ジョブの Compute Group は、作成時にのみ指定できます。ジョブの作成後、バインドされた Compute Group は変更できません。

リファレンスマニュアル​

データロードコマンドの構文​

長時間実行される Routine Load ジョブの作成構文は次のとおりです。

CREATE ROUTINE LOAD [<db_name>.]<job_name> [ON <tbl_name>]
[merge_type]
[load_properties]
[job_properties]
FROM KAFKA [data_source_properties]
[COMMENT "<comment>"]

各要素の説明は次のとおりです。

要素説明
db_nameデータロードタスクを作成するデータベースを指定します。
job_name作成するデータロードタスクの名前を指定します。同じデータベース内に同名のタスクは存在できません。
tbl_nameデータロード先のテーブル名を指定します。省略可能です。指定しない場合は動的テーブル方式が使用され、Kafka のデータにテーブル名を含める必要があります。
merge_typeデータのマージ方式です。デフォルト値は APPEND です。

次の方式があります。

- APPEND: 追加して取り込みます。

- MERGE: マージして取り込みます。

- DELETE: 取り込んだデータをすべて削除対象とします。

load_propertiesデータロードの指定項目です。次の要素が含まれます。

- column_separator 句

- columns_mapping 句

- preceding_filter 句

- where_predicates 句

- partitions 句

- delete_on 句

- order_by 句

job_propertiesRoutine Load 共通のデータロードパラメータを指定します。
data_source_propertiesKafka データソースのプロパティを指定します。
commentデータロードジョブのコメントを指定します。

データロードパラメータの説明​

FE 設定パラメータ​

パラメータデフォルト値動的変更FE Master のみ説明
max_routine_load_task_concurrent_num256可はいRoutine Load ジョブのサブタスクの最大並列数を制限します。デフォルト値の維持を推奨します。大きすぎる値を設定すると、同時実行タスクが増えすぎてクラスターのリソースを消費する可能性があります。
max_routine_load_task_num_per_be1024可はい各 BE で同時実行できる Routine Load タスクの最大数です。max_routine_load_task_num_per_be は routine_load_thread_pool_size より小さくする必要があります。
max_routine_load_job_num100可はいNEED_SCHEDULED、RUNNING、PAUSE 状態のジョブを含めた、Routine Load ジョブの最大数を制限します。

max_consumer_num_per_group3可単一のサブタスクが読み取りのために起動できる consumer の最大数です。

データロード設定パラメータ​

Routine Load ジョブの作成時に、CREATE ROUTINE LOAD コマンドで各要素の設定パラメータを指定できます。

tbl_name 句​

データロード先のテーブル名を指定します。省略可能です。

指定しない場合は動的テーブル方式が使用され、Kafka のデータにテーブル名を含める必要があります。現在、動的テーブル名は Kafka Value から抽出する方法のみがサポートされており、データは所定の形式に従う必要があります。JSON の場合は table_name|{"col1": "val1", "col2": "val2"} で、tbl_name がテーブル名、| がテーブル名とテーブルデータの区切り文字です。CSV 形式のデータも同様で、たとえば table_name|val1,val2,val3 とします。

注意

ここでの table_name は Doris のテーブル名と完全に一致する必要があります。一致しない場合、データロードは失敗します。動的テーブルは column_mapping をサポートしません。

merge_type 句​

merge_type でデータのマージ方式を指定できます。次の方式があります。

  • APPEND: 追加して取り込みます。
  • MERGE: マージして取り込みます。Unique Key モデルにのみ適用できます。Delete Flag 列を指定するため、[DELETE ON] と併用する必要があります。
  • DELETE: 取り込んだデータをすべて削除対象とします。
load_properties 句​

load_properties で取り込むデータのプロパティを指定できます。構文は次のとおりです。

[COLUMNS TERMINATED BY <column_separator>,]
[COLUMNS (<column1_name>[, <column2_name>, <column_mapping>, ...]),]
[WHERE <where_expr>,]
[PARTITION(<partition1_name>, [<partition2_name>, <partition3_name>, ...]),]
[DELETE ON <delete_expr>,]
[ORDER BY <order_by_column1>[, <order_by_column2>, <order_by_column3>, ...]]

各要素のパラメータは次のとおりです。

要素パラメータ説明
COLUMNS TERMINATED BY<column_separator>列の区切り文字を指定します。デフォルトは \t です。たとえば、カンマを区切り文字にするには COLUMN TERMINATED BY "," と指定します。NULL 値の扱いには注意してください。

- NULL 値は \n で表します。a,\n,b は中央の列が NULL 値であることを示します。

- 空文字列はそのまま空のデータとして設定されます。a,,b は中央の列が空文字列（''）であることを示します。

COLUMNS<column_name>対応する列名を指定します。たとえば、取り込み列 (k1, k2, k3) を指定するには COLUMNS(k1, k2, k3) とします。次の場合、COLUMNS 句は省略できます。

- CSV の列とテーブルの列が対応している。

- JSON のキー名とテーブルの列名が一致している。

 <column_mapping>データロード時に列のマッピングによるフィルタリングや変換を行えます。たとえば、取り込み先の列 k4 を k3+1 という式で k3 列から計算するには、COLUMNS(k1, k2, k3, k4 = k3 + 1) とします。詳細はデータ変換を参照してください。
WHERE<where_expr>条件に基づいて取り込むデータをフィルタリングします。たとえば、age > 30 のデータのみを取り込むには WHERE age > 30 とします。
PARTITION<partition_name>データロード先テーブルの対象パーティションを指定します。指定しない場合、データは対応するパーティションに自動的に取り込まれます。たとえば、p1 と p2 に取り込むには PARTITION(p1, p2) とします。
DELETE ON<delete_expr>MERGE 方式では、delete_expr で削除対象を指定します。たとえば、MERGE 時に age > 30 の行を削除するには DELETE ON age > 30 とします。
ORDER BY<order_by_column>Unique Key モデルでのみ有効です。データの順序を保証するため、取り込むデータの Sequence Column を指定します。たとえば、create_time を Sequence Column にするには ORDER BY create_time とします。詳細はデータ更新 / Sequence Columnを参照してください。
job_properties 句​

Routine Load ジョブの作成時に、job_properties 句でジョブのプロパティを指定できます。構文は次のとおりです。

PROPERTIES ("<key1>" = "<value1>"[, "<key2>" = "<value2>" ...])

job_properties 句で指定できるパラメータは次のとおりです。

パラメータ説明
desired_concurrent_number

デフォルト値: 256

min(topic_partition_num, desired_concurrent_number, max_routine_load_task_concurrent_num)。各項目の意味は次のとおりです。

- topic_partition_num: Kafka トピックのパーティション数。

- desired_concurrent_number: このパラメータの値。

- max_routine_load_task_concurrent_num: FE で設定された Routine Load タスクの最大並列数。

max_batch_interval各サブタスクの最大実行時間です。単位は秒で、0 より大きい値を指定する必要があります。デフォルト値は 60 です。max_batch_interval、max_batch_rows、max_batch_size がサブタスクの実行しきい値を構成します。いずれかに達すると、現在のサブタスクが終了し、新しいサブタスクが生成されます。

max_batch_size各サブタスクが読み取れる最大バイト数です。単位はバイト、範囲は 100 MB から 1 GB、デフォルト値は 1 GB です。max_batch_interval、max_batch_rows、max_batch_size がサブタスクの実行しきい値を構成します。いずれかに達すると、現在のサブタスクが終了し、新しいサブタスクが生成されます。
max_error_numberサンプリングウィンドウ内で許容されるエラー行の最大数です。0 以上にする必要があります。デフォルト値は 0 で、エラー行は許容されません。サンプリングウィンドウは max_batch_rows * 10 です。ウィンドウ内のエラー行数が max_error_number を超えると、Routine Load ジョブは一時停止します。データ品質の問題を確認するには手動操作が必要です。SHOW ROUTINE LOAD コマンドの ErrorLogUrls フィールドで問題を確認できます。where 条件によって除外された行は、エラー行に数えません。
strict_modestrict mode を有効にするかどうかを指定します。デフォルトでは無効です。strict mode では、データロード時の列の型変換を厳格に判定します。有効な場合、元の値が NULL ではないのに型変換後に NULL になった行は除外されます。

フィルタリングの方針:

- Strict Mode は派生列（関数による変換で生成された列）には影響しません。

- 列の型変換が必要な場合、型が不正なデータは除外されます。SHOW ROUTINE LOAD の ErrorLogUrls で確認できます。

- 取り込み先の列の型に範囲制限があり、元のデータが型変換には成功しても範囲制限を満たさない場合、strict mode は影響しません。たとえば、型が decimal(1,0) で元のデータが 10 の場合、型変換には成功しますが、列で宣言された範囲には収まりません。詳細は Strict Mode を参照してください。

timezoneデータロードジョブで使用するタイムゾーンを指定します。デフォルトはセッションのタイムゾーンパラメータです。このパラメータは、データロードに関係するすべてのタイムゾーン関連関数の結果に影響します。
format取り込むデータの形式を指定します。デフォルトは CSV です。JSON 形式もサポートします。
compute_group4.1.5 以降でサポートします。省略可能な文字列で、デフォルトでは指定されません。コンピューティングとストレージを分離したモードでのみサポートされ、実行に使用する Compute Group を明示的にバインドします。対象グループの USAGE 権限が必要で、予約値 DEFAULT は指定できません。
jsonpathsデータ形式が JSON の場合、jsonpaths で JSON データから抽出するフィールドを指定できます。例: "jsonpaths" = "[\"$.userid\",\"$.username\",\"$.age\",\"$.city\"]"

send_batch_parallelismバッチデータ送信時の並列数を設定します。この値が BE 設定の max_send_batch_parallelism_per_job を超える場合、coordinator として動作する BE は max_send_batch_parallelism_per_job の値を使用します。
load_to_single_tabletタスクのデータを、対応するパーティション内の単一の tablet のみに取り込めるようにします。デフォルトは false です。このパラメータは、ランダムバケットを使用する OLAP テーブルに取り込む場合にのみ設定できます。
partial_columns列の部分更新を有効にするかどうかを指定します。デフォルトは false です。テーブルモデルが Unique で、Merge on Write を使用する場合にのみ設定できます。単一ストリームから複数テーブルへのデータロードでは、このパラメータをサポートしません。詳細は列の部分更新を参照してください。
unique_key_update_modeUnique Key テーブルの更新モードを指定します。選択肢:
  • UPSERT（デフォルト）: 行全体を通常どおり挿入または更新します。
  • UPDATE_FIXED_COLUMNS: すべての行で同じ列を更新する部分更新です。partial_columns=true と同等です。
  • UPDATE_FLEXIBLE_COLUMNS: 行ごとに異なる列を更新できる柔軟な部分更新です。JSON 形式が必要で、テーブルでは enable_unique_key_skip_bitmap_column=true を設定する必要があります。jsonpaths、fuzzy_parse、COLUMNS 句、WHERE 句とは併用できません。
詳細は列の部分更新を参照してください。

- APPEND: 新規行の挿入を許可します。
- ERROR: 新規行を挿入しようとするとデータロードが失敗し、エラーが報告されます。
max_filter_ratioサンプリングウィンドウ内で許容する最大フィルタリング比率です。0 以上、1 以下にする必要があります。デフォルト値は 1.0 で、エラー行をすべて許容します。サンプリングウィンドウは max_batch_rows * 10 です。ウィンドウ内のエラー行数を総行数で割った値が max_filter_ratio を超えると、Routine Load ジョブは一時停止します。データ品質の問題を確認するには手動操作が必要です。where 条件によって除外された行は、エラー行に数えません。
enclose囲み文字を指定します。CSV データのフィールドに行区切り文字や列区切り文字が含まれる場合、意図しない分割を防ぐため、単一バイトの文字を囲み文字として指定できます。たとえば、列区切り文字が ,、囲み文字が ' の場合、データ a,'b,c' の b,c は単一フィールドとして解析されます。
escapeエスケープ文字を指定します。フィールド内に囲み文字と同じ文字がある場合、その文字をエスケープするために使用します。たとえば、囲み文字が ' でデータが a,'b,'c' の場合、b,'c を単一フィールドとして解析するには、単一バイトのエスケープ文字（\ など）を指定し、データを a,'b,\'c' に変更する必要があります。

単一ストリームから複数テーブルに取り込む​

example_db に対して、test1 という名前の Kafka Routine Load 動的複数テーブルタスクを作成します。group.id と client.id を指定し、デフォルトですべてのパーティションを自動的に読み取り、データが存在する位置（OFFSET_BEGINNING）から購読します。

Kafka から example_db の tbl1 テーブルと tbl2 テーブルにデータを取り込む場合を考えます。test1 という Routine Load タスクを作成し、Kafka トピック my_topic のデータを両方のテーブルに取り込めます。

CREATE ROUTINE LOAD example_db.test1
FROM KAFKA
(
    "kafka_broker_list" = "broker1:9092,broker2:9092,broker3:9092",
    "kafka_topic" = "my_topic",
    "property.kafka_default_offsets" = "OFFSET_BEGINNING"
);

この場合、Kafka のデータにテーブル名を含める必要があります。現在、動的テーブル名は Kafka Value から抽出する方法のみがサポートされており、データは所定の形式に従う必要があります。JSON の場合は table_name|{"col1": "val1", "col2": "val2"} で、tbl_name がテーブル名、| がテーブル名とテーブルデータの区切り文字です。CSV 形式のデータも同様で、たとえば table_name|val1,val2,val3 とします。

注意

ここでの table_name は Doris のテーブル名と完全に一致する必要があります。一致しない場合、データロードは失敗します。動的テーブルは column_mapping をサポートしません。

Strict Mode で取り込む​

example_db の example_tbl に対して、strict mode を有効にした test1 という名前の Kafka Routine Load タスクを作成します。

CREATE ROUTINE LOAD example_db.test1 ON example_tbl
COLUMNS(k1, k2, k3, v1, v2, v3 = k1 * 100),
PRECEDING FILTER k1 = 1,
WHERE k1 < 100 and k2 like "%doris%"
PROPERTIES
(
    "strict_mode" = "true"
)
FROM KAFKA
(
    "kafka_broker_list" = "broker1:9092,broker2:9092,broker3:9092",
    "kafka_topic" = "my_topic"
);

よくある質問（FAQ）​

Routine Load ジョブが自動的に PAUSED 状態になった場合はどうすればよいですか？​

通常は、データ品質の問題または Kafka 側の例外が原因です。

  1. SHOW ROUTINE LOAD FOR <job_name> を実行し、ReasonOfStateChanged と ErrorLogUrls を確認します。
  2. 不正データが原因の場合は、必要に応じて max_filter_ratio と max_error_number を増やします。
  3. Kafka 側の例外が原因の場合は、broker とトピックに接続できることを確認してから、RESUME ROUTINE LOAD を実行して復旧します。

Offset out of range または out of range エラーにはどう対処しますか？​

通常は、記録されているオフセットが Kafka の保持期間によってすでに削除されていることを意味します。

  1. ジョブを一時停止します: PAUSE ROUTINE LOAD FOR <job_name>。
  2. ALTER ROUTINE LOAD を使用して、kafka_offsets を有効な位置（OFFSET_BEGINNING や具体的なオフセットなど）に設定し直します。
  3. RESUME ROUTINE LOAD を実行してジョブを復旧します。

Server kafka/xxx@EXAMPLE.COM not found in Kerberos database と表示された場合は？​

Kerberos 認証を使用する場合は、krb5.conf に rdnbs=true を設定します。

Server certificate verification failed などの SSL エラーが発生した場合は？​

BE 側に信頼できる CA 証明書が設定されていない場合は、"property.enable.ssl.certificate.verification" = "false" を設定するか、"property.ssl.ca.location" = "/path/to/ca-cert.pem" を明示的に指定します。

希望する並列数（desired_concurrent_number）が反映されない場合は？​

実際の並列数は、次の値の最小値で決まります。

min(topic_partition_num, desired_concurrent_number, max_routine_load_task_concurrent_num)

Kafka トピックのパーティション数と FE 設定の max_routine_load_task_concurrent_num を確認してください。

古い Kafka バージョン（< 0.10.0.0）を使用するには？​

BE 設定で kafka_broker_version_fallback を設定するか、ジョブ作成時に property.broker.version.fallback で互換バージョンを指定します。

単一ストリームから複数テーブルへのデータロードで、取り込み先テーブルを指定するには？​

Kafka メッセージの Value に table_name|<data> の形式でテーブル名を含める必要があります。テーブル名は Doris のテーブル名と厳密に一致させてください。動的テーブルは column_mapping をサポートしません。

データロードに失敗した不正データを確認するには？​

SHOW ROUTINE LOAD FOR <job_name> を実行し、結果の ErrorLogUrls フィールドを確認します。ブラウザーまたは wget でその URL にアクセスすると、除外されたエラーデータのサンプルとエラーの原因を取得できます。

Routine Load ジョブを変更する前に一時停止する必要がありますか？​

はい。ALTER ROUTINE LOAD コマンドを実行するには、ジョブが PAUSED 状態である必要があります。変更手順は PAUSE ROUTINE LOAD → ALTER ROUTINE LOAD → RESUME ROUTINE LOAD です。

その他のヘルプ​

  • SQL マニュアルのリファレンス: CREATE ROUTINE LOAD
  • クライアントのコマンドラインで HELP ROUTINE LOAD を実行すると、詳細なヘルプを確認できます。
