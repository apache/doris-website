Section 1 — 7-10 min

JOINs — 9 Types & 4 Distributed Shuffle Strategies

Apache Doris supports nine JOIN types and two physical implementations (Hash Join and Nest Loop Join). Under the MPP architecture, four Shuffle strategies determine how data moves across nodes during JOIN execution.

Supported JOIN Types

TypeDescription
INNER JOINReturns rows from both tables that satisfy the join condition
LEFT JOINReturns all rows from the left table, with NULLs for unmatched right rows
RIGHT JOINReturns all rows from the right table, with NULLs for unmatched left rows
FULL JOINReturns all rows from both tables, filling NULLs where no match exists
CROSS JOINReturns the Cartesian product of the two tables
LEFT SEMI JOINReturns left rows that have at least one match in the right table
RIGHT SEMI JOINReturns right rows that have at least one match in the left table
LEFT ANTI JOINReturns left rows that have no match in the right table
RIGHT ANTI JOINReturns right rows that have no match in the left table

Physical Implementations

⚡ Hash Join

Builds a hash table on the right table and streams the left table through it. Only applies to equi-JOIN conditions. This is the default and most efficient implementation.

🔄 Nest Loop Join

Uses two nested loops — for each left row, scans all right rows. Applies to all JOIN scenarios including non-equi conditions (>, <) and Cartesian products. May underperform compared to Hash Join.

Four Shuffle Strategies

StrategyNetwork OverheadPhysical OperatorBest For
BroadcastN × T(R)Hash Join / Nest LoopSmall right table broadcast to all nodes
Shuffle (Partition)T(S) + T(R)Hash JoinGeneral purpose, both sides shuffled
Bucket ShuffleT(R)Hash JoinJOIN condition includes left bucket column
Colocate0Hash JoinBoth tables in same Colocate Group
Key insight: As data distribution requirements increase (Broadcast → Shuffle → Bucket Shuffle → Colocate), network overhead decreases but flexibility decreases. In most cases, stricter data distribution means better JOIN performance.
⚠
Caution: If the number of buckets in a table is small, Bucket Shuffle Join or Colocate Join may suffer from low parallelism and perform worse than Shuffle Join. This is because the Shuffle operation can balance data distribution more effectively.

Subqueries

Subqueries in Doris can appear in SELECT, FROM, WHERE, or HAVING clauses. They are classified by returned data (scalar vs. non-scalar) and by outer-column reference (correlated vs. uncorrelated).
TypeReturned ResultReturn When EmptyAllowed Positions
Scalar subquerySingle value (one row, one column)NULLAnywhere a single-value expression is allowed
Non-scalar subqueryRelation (multiple rows and columns)Empty set (0 rows)Anywhere a relation (set) is allowed
Correlated subqueryDepends on outer queryDependsWHERE/HAVING/SELECT (with limitations)
Uncorrelated subqueryIndependent of outer queryDependsAll clauses
Key limitations: Correlated scalar subqueries require equality conditions and single aggregate output. Correlated IN subqueries must return a single column without LIMIT or GROUP BY. Nested subqueries only support correlation to the immediate parent.
-- Scalar subquery
SELECT * FROM t1
WHERE t1.c1 > (SELECT MAX(t2.c1) FROM t2);

-- Non-scalar subquery (IN)
SELECT * FROM t1
WHERE t1.c1 IN (SELECT t2.c1 FROM t2);

-- Correlated subquery
SELECT * FROM t1
WHERE t1.c1 IN (
    SELECT t2.c1 FROM t2
    WHERE t2.c2 = t1.c2
);

-- EXISTS subquery
SELECT * FROM t1
WHERE EXISTS (
    SELECT t2.c1 FROM t2
    WHERE t1.c2 = t2.c2
    LIMIT 2
);
ⓘ
Supported scope: All uncorrelated subqueries are fully supported. Correlated scalar subqueries, IN/EXISTS/NOT EXISTS in WHERE/HAVING, and SELECT-list scalar subqueries are supported. Cross-level correlation is not supported.
Section 3 — 2-3 min

Multi-Dimensional Analytics

Doris supports standard SQL multi-dimensional analysis operators including CUBE, ROLLUP, and GROUPING SETS for generating aggregate result sets at multiple grouping levels in a single query.
-- GROUP BY with CUBE (all combinations)
SELECT year, month, region, SUM(revenue)
FROM sales
GROUP BY CUBE(year, month, region);

-- GROUP BY with ROLLUP (hierarchical)
SELECT year, month, region, SUM(revenue)
FROM sales
GROUP BY ROLLUP(year, month, region);

-- GROUPING SETS (custom combinations)
SELECT year, month, region, SUM(revenue)
FROM sales
GROUP BY GROUPING SETS (
    (year, month),
    (year, region),
    (month, region),
    ()
);

-- GROUPING function to distinguish levels
SELECT
    year,
    month,
    GROUPING(year) AS is_year_total,
    GROUPING(month) AS is_month_total,
    SUM(revenue)
FROM sales
GROUP BY ROLLUP(year, month);
Tip: Use GROUPING SETS for fine-grained control over which aggregation levels to compute. ROLLUP is best for hierarchical drill-downs. CUBE computes all possible combinations and is the most comprehensive but also the most expensive.
Section 4 — 2-3 min

Window Functions

Window functions perform calculations across a set of rows related to the current row without collapsing them into a single output. They support ranking, analytic, and aggregate operations within configurable window frames.
CategoryFunctionDescription
RankingROW_NUMBER, RANK, DENSE_RANKAssign sequential ranks within a partition
AnalyticLEAD, LAG, FIRST_VALUE, LAST_VALUEAccess rows at a physical offset
AggregateSUM, AVG, COUNT, MIN, MAXRunning/rolling aggregates over a window
-- Ranking within department
SELECT
    name,
    department,
    salary,
    ROW_NUMBER() OVER (
        PARTITION BY department
        ORDER BY salary DESC
    ) AS rank_in_dept
FROM employees;

-- Running total with window frame
SELECT
    date,
    amount,
    SUM(amount) OVER (
        ORDER BY date
        ROWS BETWEEN UNBOUNDED PRECEDING
                 AND CURRENT ROW
    ) AS running_total
FROM sales;

-- LAG to compare with previous row
SELECT
    date,
    amount,
    LAG(amount, 1) OVER (
        ORDER BY date
    ) AS prev_day_amount,
    amount - LAG(amount, 1) OVER (
        ORDER BY date
    ) AS day_over_day_change
FROM daily_sales;
Tip: The default window frame is RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW. Use ROWS instead of RANGE for physical row offsets. Window functions can only appear in SELECT or ORDER BY clauses.
Section 5 — 2-3 min

CTE — Common Table Expressions

CTEs (Common Table Expressions) provide a way to define temporary named result sets within a query. They improve SQL readability and enable recursive queries for hierarchical data.
-- Basic CTE
WITH sales_summary AS (
    SELECT
        region,
        SUM(amount) AS total_sales
    FROM orders
    GROUP BY region
)
SELECT * FROM sales_summary
WHERE total_sales > 10000;

-- Multiple CTEs
WITH
region_sales AS (
    SELECT region, SUM(amount) AS total
    FROM orders GROUP BY region
),
top_regions AS (
    SELECT region FROM region_sales
    WHERE total > 50000
)
SELECT o.*
FROM orders o
JOIN top_regions tr
ON o.region = tr.region;

-- Recursive CTE (for hierarchical data)
WITH RECURSIVE org_tree AS (
    SELECT id, name, manager_id, 1 AS level
    FROM employees
    WHERE manager_id IS NULL
    UNION ALL
    SELECT e.id, e.name, e.manager_id, ot.level + 1
    FROM employees e
    JOIN org_tree ot ON e.manager_id = ot.id
)
SELECT * FROM org_tree;
💡
Tip: CTEs are evaluated once and can be referenced multiple times in the main query. Use CTEs to break down complex queries into manageable steps. Recursive CTEs are useful for traversing tree structures like organizational charts or bill-of-materials.

User-Defined Functions — Alias, Java, Python

Doris supports three categories of user-defined functions: alias functions for transparent SQL migration, Java UDF/UDAF/UDWF/UDTF for custom business logic, and Python UDF for data science workflows.

6.1 Alias Functions

Register a new signature for an existing function or expression. Supports LOCAL (current database) and GLOBAL scopes. Ideal for heterogeneous database migration and complex query simplification.
-- Create alias for heterogeneous migration
CREATE ALIAS FUNCTION my_abs(INT)
WITH PARAMETER(foo) AS abs(foo);

-- Alias for complex expression
CREATE ALIAS FUNCTION date_group(DATETIMEV2(3), INT)
WITH PARAMETER(foo, bar)
AS date_trunc(days_sub(foo, bar), 'day');

-- Usage: transparent migration
-- Old system uses MY_ABS(x), now it works in Doris
⚠
Constraint: The root node of the underlying expression must be a function expression (not an arithmetic operator). Variable-length parameters are not supported. At least one parameter is required.

6.2 Java UDF / UDAF / UDWF / UDTF

TypeBehaviorExampleVersion
UDFOne output per input rowABS, LENGTHAll
UDAFMultiple rows → one rowMIN, MAX, COUNTAll
UDWFValue per row in a windowROW_NUMBER, RANKAll
UDTFOne row → multiple rowsEXPLODE3.0+
-- Create Java UDF
CREATE FUNCTION java_udf_add_one(int)
RETURNS int PROPERTIES (
    "file" = "file:///path/to/udf.jar",
    "symbol" = "org.apache.doris.udf.AddOne",
    "type" = "JAVA_UDF"
);

-- Use it
SELECT id, java_udf_add_one(id)
FROM test_table;
-- id=1 returns 2, id=6 returns 7

-- Drop when no longer needed
DROP FUNCTION java_udf_add_one(int);
Data type mapping: TINYINT → Byte, INT → Integer, BIGINT → Long, STRING → String, DECIMAL → BigDecimal, DATE → LocalDate, ARRAY → ArrayList, MAP → HashMap.

6.3 Python UDF

Write custom functions in Python for data science and ML inference workflows. Supports scalar UDF and UDAF. Uses Python 3.7+ syntax.
-- Register Python UDF
CREATE FUNCTION py_udf_add_one(int)
RETURNS int PROPERTIES (
    "file" = "file:///path/udf.py",
    "symbol" = "add_one",
    "type" = "PYTHON_UDF"
);

-- Python code (udf.py):
# class add_one(UDF):
#     def evaluate(self, val):
#         return None if val is None else val + 1

-- Use it
SELECT id, py_udf_add_one(id) FROM test_table;

Complex Types — ARRAY, MAP, STRUCT, JSON

Apache Doris supports four complex data types that enable nested and semi-structured data processing directly in SQL, reducing the need for ETL flattening.
ARRAY

Ordered collections of elements with the same type.

SELECT ARRAY(1,2,3);
SELECT * FROM t
WHERE ARRAY_CONTAINS(
  arr, 'val');
MAP

Key-value pairs with typed keys and values.

SELECT MAP(
  "k1", 1, "k2", 2);
SELECT m["k1"] FROM t;
STRUCT

Named fields with potentially different types.

SELECT NAMED_STRUCT(
  "name", "Alice",
  "age", 30);
SELECT s.name FROM t;
-- Nested complex types
CREATE TABLE events (
    event_id INT,
    properties MAP,
    tags ARRAY,
    location STRUCT<
        city:STRING,
        coordinates:ARRAY>
);

-- Query with lambda functions
SELECT
    event_id,
    ARRAY_FILTER(tags, x -> x LIKE '%important%')
FROM events;

-- JSON functions
SELECT
    json_extract_string(
        '{"a": "value"}', '$.a'
    );

SELECT
    parse_json('{"x": 1, "y": 2}');
Tip: Complex types can be nested (e.g., ARRAY<MAP<STRING,INT>>). Use lambda functions (since 2.1) for array transformations. JSON functions enable semi-structured data processing without schema pre-definition.

Materialized Views — Sync & Async

Materialized Views in Doris precompute and store query results for transparent query acceleration. Two types exist: synchronous views (single-table, strong consistency) and asynchronous views (multi-table, flexible refresh).

8.1 Synchronous Materialized View

A special table that precomputes and stores a SELECT result on a single base table. Doris maintains it automatically with strong consistency. At query time, Doris transparently rewrites to the optimal view.
ScenarioDescription
Accelerate aggregationPrecompute SUM/COUNT/BITMAP_UNION for faster queries
Match prefix indexesCreate views with different sort key prefixes
Pre-filterUse WHERE conditions to reduce scanned data
Precompute expressionsCompute abs(k1)+k2+1 once and reuse
-- 1. Create base table
CREATE TABLE sales_records (
    record_id INT,
    seller_id INT,
    store_id INT,
    sale_date DATE,
    sale_amt BIGINT
)
DISTRIBUTED BY HASH(record_id)
PROPERTIES("replication_num" = "1");

INSERT INTO sales_records VALUES
(1,1,1,"2020-02-02",1),
(2,1,1,"2020-02-02",2);

-- 2. Create sync MV (group by store_id)
CREATE MATERIALIZED VIEW store_amt AS
SELECT store_id, SUM(sale_amt)
FROM sales_records GROUP BY store_id;

-- 3. Check creation status (async)
SHOW ALTER TABLE MATERIALIZED VIEW
FROM test_db;

-- State = FINISHED means ready

-- 4. Query (automatic rewrite)
SELECT store_id, SUM(sale_amt)
FROM sales_records GROUP BY store_id;

-- Verify with EXPLAIN
EXPLAIN SELECT store_id, SUM(sale_amt)
FROM sales_records GROUP BY store_id;

-- 5. View MVs on a table
DESC sales_records ALL;

-- 6. Cancel creation / Drop
CANCEL ALTER TABLE MATERIALIZED VIEW
FROM test_db.sales_records;

DROP MATERIALIZED VIEW store_amt
ON sales_records;
⚠
Limitations: Single-table only (no JOIN, HAVING, LIMIT). Materialized view column names must not conflict with base table columns. On Unique Key models, views can only reorder columns — no aggregation. Too many views slow down load performance.

8.2 Asynchronous Materialized View

Supports multi-table JOIN, complex expressions, and user-defined refresh strategies. Data can be refreshed on-demand or periodically. Does not provide strong consistency with base tables.
⚡ Sync MV
  • ✅ Single table only
  • ✅ Strong consistency
  • ✅ Automatic maintenance
  • ⚠ No user-defined refresh
  • ⚠ Limited to simple aggregations
🔄 Async MV
  • ✅ Multi-table JOIN support
  • ⚠ Eventual consistency
  • ✅ Custom refresh schedule
  • ✅ Partition-level refresh
  • ✅ Can be queried directly
-- Create async MV with JOIN
CREATE MATERIALIZED VIEW mv_async
BUILD DEFERRED REFRESH AUTO ON MANUAL
DISTRIBUTED BY RANDOM BUCKETS 10
AS
SELECT o.order_id, o.amount,
       c.name, c.region
FROM orders o
JOIN customers c
ON o.customer_id = c.id;

-- Refresh on demand
REFRESH MATERIALIZED VIEW mv_async;

-- Query directly (async MVs can be
-- queried like regular tables)
SELECT * FROM mv_async
WHERE region = 'East';

-- Schedule periodic refresh
ALTER MATERIALIZED VIEW mv_async
REFRESH EVERY 1 HOUR;

-- Check MV status
SHOW MATERIALIZED VIEWS
WHERE name = 'mv_async';
💡
Tip: Use sync MVs for simple single-table aggregation with strong consistency requirements. Use async MVs for complex multi-table JOINs, star schema acceleration, and scenarios where eventual consistency is acceptable.
