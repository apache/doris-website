Section 1

Data Import — 7 Methods for Every Scenario

Apache Doris provides multiple data load and integration methods to handle everything from real-time streaming to massive batch imports. Choose the right approach for your data source and timeliness requirements.

Quick Reference by Scenario

ScenarioRecommended Method
Real-time write (low volume, every 5 min)JDBC INSERT
High-concurrency / high-frequency writesGroup Commit + JDBC INSERT or Stream Load
High-throughput application writeStream Load (HTTP)
Real-time Flink streamingFlink Doris Connector
Kafka message queueRoutine Load or Kafka Connector
HDFS / S3 batch load (GB-TB)Broker Load or INSERT INTO SELECT
Local file batch loadStream Load or Doris Streamloader
External data source (Hive/Iceberg)Catalog + INSERT INTO SELECT
ⓘ
Transaction Guarantee: Each load in Doris is by default an implicit transaction. For more transaction-related information, see the Transaction documentation.

→ 1.1 Stream Load — HTTP Synchronous Import
Synchronous import method for local files or data streams. Supports CSV, JSON, Parquet, ORC. Guarantees atomicity: all rows succeed or all fail. Best for files <10 GB.
# Create target table
CREATE TABLE testdb.test_streamload(
    user_id  BIGINT       NOT NULL,
    name     VARCHAR(20),
    age      INT
)
DUPLICATE KEY(user_id)
DISTRIBUTED BY HASH(user_id) BUCKETS 10;

# Submit Stream Load via curl
curl --location-trusted -u : \
    -H "Expect:100-continue" \
    -H "column_separator:," \
    -H "columns:user_id,name,age" \
    -T streamload_example.csv \
    -XPUT http://:/api/testdb/test_streamload/_stream_load

# Response includes status, rows loaded, filtered rows
{"Status": "Success", "NumberLoadedRows": 10}
→ 1.2 Broker Load — Async Remote Storage Import
Asynchronous import from S3, HDFS, or object storage. Suitable for GB to TB level data. Doris pulls data from remote storage according to the LOAD statement.
⚠
Note: This method is deprecated and will be removed in version 5.0. Use INSERT INTO SELECT with TVF or Catalog instead.
LOAD LABEL broker_load_2022_04_01
(
    DATA INFILE("s3://your_bucket/brokerload_example.csv")
    INTO TABLE test_brokerload
    COLUMNS TERMINATED BY ","
    FORMAT AS "CSV"
    (user_id, name, age)
)
WITH S3
(
    "provider" = "S3",
    "AWS_ENDPOINT" = "https://s3.us-west-2.amazonaws.com",
    "AWS_ACCESS_KEY" = "",
    "AWS_SECRET_KEY" = "",
    "AWS_REGION" = "us-west-2",
    "compress_type" = "PLAIN"
)
PROPERTIES ("timeout" = "3600");

# Check progress
SHOW LOAD WHERE label = "broker_load_2022_04_01";
→ 1.3 Routine Load — Kafka Streaming Import
A long-running streaming import job that continuously consumes data from Kafka topics. Provides Exactly-Once semantics. Supports column mapping and filtering.
CREATE ROUTINE LOAD testdb.test_routine_load
ON test_routine_load
COLUMNS TERMINATED BY ","
COLUMNS(user_id, name, age)
PROPERTIES ("desired_concurrent_number" = "3")
FROM KAFKA (
    "kafka_broker_list" = "broker1:9092,broker2:9092",
    "kafka_topic" = "test-topic",
    "property.group.id" = "test-group",
    "property.kafka_default_offsets" = "OFFSET_BEGINNING"
);

-- View job status
SHOW ROUTINE LOAD FOR test_routine_load\G

-- Pause / Resume / Stop
PAUSE ROUTINE LOAD FOR test_routine_load;
RESUME ROUTINE LOAD FOR test_routine_load;
STOP ROUTINE LOAD FOR test_routine_load;
💡
Auto-recovery: When Kafka becomes temporarily unavailable, Routine Load automatically retries. For data quality issues (exceeding max_filter_ratio), manual intervention is needed — investigate ErrorLogUrls then RESUME.
→ 1.4 INSERT INTO SELECT — ETL & TVF Import
Synchronous import via MySQL protocol. Supports inter-table ETL, external table import via Catalog, and direct file import via TVF. Guarantees atomicity.
-- Inter-table ETL
INSERT INTO testdb.target_table
SELECT * FROM testdb.source_table WHERE age < 30;

-- Import via TVF (S3 file)
INSERT INTO testdb.target_table
SELECT * FROM S3(
    "uri" = "s3://bucket/data.csv",
    "ACCESS_KEY" = "...",
    "SECRET_KEY" = "...",
    "format" = "csv"
);

-- Check result: {"label":"...", "status":"visible", "txnId":"..."}
-- View import jobs
SHOW LOAD FROM testdb;
→ 1.5 INSERT INTO VALUES & MySQL Load
INSERT INTO VALUES
INSERT INTO test_table (user_id, name, age)
VALUES (1, "Emily", 25),
       (2, "Benjamin", 35),
       (3, "Olivia", 28);

-- Supports WITH LABEL
INSERT INTO test_table
WITH LABEL my_label
VALUES (4, "Ava", 17);

-- Session vars:
SET insert_timeout = 7200;
SET enable_insert_strict = true;
MySQL Load
# Load local CSV via MySQL client
LOAD DATA LOCAL
INFILE "/path/to/data.csv"
INTO TABLE test_table
COLUMNS TERMINATED BY ","
LINES TERMINATED BY "\n"
(user_id, name, age);

# Requires LOCAL capability enabled
# Synchronous, returns result directly
💡
Best Practices: For high-throughput writes, use Stream Load. For Kafka, use Routine Load. For S3/HDFS batch, use Broker Load. For ETL and Catalog integration, use INSERT INTO SELECT.
Section 2

Data Update — 4 Approaches

Doris supports multiple update strategies depending on the table model. Unique Key tables use UPSERT semantics, while Aggregate tables support REPLACE-based updates. Partial column updates allow modifying specific fields without rewriting entire rows.
→ 2.1 UPDATE Statement (Unique Model)
The UPDATE statement supports synchronous updates on Unique Key tables with merge-on-write. It internally executes a read-then-write cycle: reads matching rows, modifies them, and writes back.
-- Step 1: Create table with Unique Key (merge-on-write)
CREATE TABLE test_update (
    user_id    BIGINT       NOT NULL,
    name       VARCHAR(20),
    age        INT,
    city       VARCHAR(20)
)
UNIQUE KEY(user_id)
DISTRIBUTED BY HASH(user_id) BUCKETS 10
PROPERTIES (
    "enable_unique_key_merge_on_write" = "true"
);

-- Step 2: Insert initial data
INSERT INTO test_update VALUES
(101, 'Tom', 26, 'BJ'),
(102, 'Jason', 27, 'SH');

-- Step 3: UPDATE statement
UPDATE test_update
SET age = 28, city = 'GZ'
WHERE user_id = 101;

-- Step 4: Check result
SELECT * FROM test_update WHERE user_id = 101;
-- 101, Tom, 28, GZ
→ 2.2 Full-Row & Partial Update (Unique Model)
Full-Row Update
-- Via INSERT (UPSERT semantics)
INSERT INTO test_update VALUES
(101, 'Tom', 30, 'SZ');

-- Same Key = overwrite entire row
-- Unspecified columns = NULL/default

-- Via Stream Load (same key = update)
curl -T data.csv \
  http://fe:8030/api/db/table/_stream_load

-- Via Broker Load
LOAD LABEL label1
( DATA INFILE("s3://bucket/data")
  INTO TABLE test_update )
WITH S3 (...);
Partial Column Update
-- Stream Load: set partial_columns=true
-- Header:
-H "partial_columns:true"
-H "columns:user_id,city"

-- Data only contains: user_id,city
-- Other columns remain unchanged

-- Routine Load: set same property
PROPERTIES (
  "partial_columns" = "true"
)
COLUMNS(user_id, city)

-- INSERT: specify only target columns
INSERT INTO test_table (user_id, city)
VALUES (101, 'GZ');
→ 2.3 Update on Aggregate Model
In the Aggregate model, whole-row updates use REPLACE aggregation. Partial updates modify a subset of Value columns with new aggregation.
-- Aggregate table with REPLACE for updateable columns
CREATE TABLE test_agg_update (
    user_id   LARGEINT NOT NULL,
    date      DATE NOT NULL,
    cost      BIGINT SUM DEFAULT "0",
    status    INT REPLACE DEFAULT "0"
)
AGGREGATE KEY(user_id, date)
DISTRIBUTED BY HASH(user_id) BUCKETS 10;

-- Full row: insert with same Key, REPLACE column overwrites
INSERT INTO test_agg_update VALUES
(101, '2024-01-01', 50, 1);

-- Status REPLACEs: old=1, cost SUMs: 50
INSERT INTO test_agg_update VALUES
(101, '2024-01-01', 30, 2);

-- Result: cost=80 (50+30), status=2 (replaced)
→ 2.4 Partial Column Update — Deep Dive
ⓘ
Capability Overview: Partial column update is supported on both Unique Key (merge-on-write) and Aggregate Key (REPLACE) models. It allows updating only specified columns without providing values for the entire row.
📄

Unique Model Partial Update

Enable via partial_columns=true in Stream Load, Routine Load, or Broker Load. Specify only the columns to update in the load configuration.

📊

Aggregate Model Partial Update

Define Value columns with REPLACE aggregation type. When loading data with same Key, REPLACE columns are overwritten while SUM columns accumulate.

⚡

Performance Note

Partial column update incurs a ~20% performance overhead compared to full-row import. Use it specifically for wide-table scenarios where only a few columns need updating.

⚠
Important: For merge-on-read (MOR) tables, partial column update is not supported. The implementation is fixed at table creation and cannot be changed later.
Section 3

Data Delete — 3 Methods

Doris provides three approaches for removing data: conditional DELETE with filter predicates, batch DELETE with a special table, and TRUNCATE for fast full-table or partition clearing.
🔎 DELETE Statement

Conditional deletion using filter predicates on Key columns. Supports FROM and USING syntax. Atomic execution.

📋 Batch Delete

Dedicated table-based delete using hidden columns. High-performance batch deletion. Does not support Unique merge-on-write.

⚡ TRUNCATE

Fastest way to clear data. Drop partitions or entire tables. No filter predicates. Instant, cannot be rolled back (unless forced).

→ 3.1 DELETE Statement
-- Delete by predicate (recommended for Key columns)
DELETE FROM test_table
WHERE user_id = 101;

-- Delete with multiple conditions
DELETE FROM test_table
WHERE user_id = 101
  AND date >= "2024-01-01";

-- Delete using JOIN (USING clause)
DELETE FROM t1
    USING t2
WHERE t1.key = t2.key
  AND t2.flag = true;

-- Check result (returns number of deleted rows)
Query OK, 1 row affected (0.05 sec)
⚠
Limitations: On Unique merge-on-write tables, the WHERE condition must filter on primary keys. On Duplicate tables, only Key columns can be used in WHERE. DELETE on Aggregate tables is not supported.
→ 3.2 Batch Delete
Batch deletion uses a special table (same schema + hidden column __DORIS_DELETE_SIGN__) to mark rows for deletion. Suitable for high-volume delete operations.
-- Step 1: Create the "delete flag" table
CREATE TABLE delete_batch (
    user_id  BIGINT,
    date     DATE,
    cost     BIGINT SUM DEFAULT "0",
    __DORIS_DELETE_SIGN__ TINYINT REPLACE DEFAULT "0"
)
AGGREGATE KEY(user_id, date)
DISTRIBUTED BY HASH(user_id) BUCKETS 10
PROPERTIES ("replication_num" = "1");

-- Step 2: Load data with __DORIS_DELETE_SIGN__=1
INSERT INTO delete_batch VALUES
(101, '2024-01-01', 0, 1);

-- Now rows with user_id=101 are marked deleted
-- Query-time filter:
SELECT * FROM delete_batch
WHERE __DORIS_DELETE_SIGN__ = 0;
→ 3.3 TRUNCATE
Fastest way to remove data. Drops partitions or entire tables instantly. Cannot filter — removes everything in the table or specified partitions.
-- Truncate entire table (recoverable by default)
TRUNCATE TABLE test_table;

-- Truncate specific partitions
TRUNCATE TABLE test_table
PARTITION (p20240101, p20240102);

-- Force truncate (non-recoverable)
TRUNCATE TABLE test_table FORCE;

-- Non-recoverable with multiple partitions
TRUNCATE TABLE test_table
PARTITION (p20240101, p20240102) FORCE;
💡
Tip: By default, TRUNCATE creates an empty partition with the same name, making the operation recoverable. Use FORCE to permanently drop partitions when data recovery is not needed.
Section 4

Data Export — 3 Methods

Doris offers three ways to export data: SELECT INTO OUTFILE for flexible data extraction, EXPORT for asynchronous large-volume batch export, and MySQL Dump for schema and logical data export.
MethodFormatLocationModeBest For
SELECT INTO OUTFILECSV, Parquet, ORCS3, HDFS, localSyncFlexible data extraction with transforms
EXPORTCSV, ParquetS3, HDFSAsyncLarge-volume batch export
mysql dumpSQLLocal/remoteSyncSchema export, logical backup
→ 4.1 SELECT INTO OUTFILE
A synchronous export method via SELECT ... INTO OUTFILE. Supports data transformation through SQL, parallel export, and multiple file formats.
-- Export to S3 as CSV
SELECT user_id, name, age
FROM test_table
WHERE age > 30
INTO OUTFILE "s3://bucket/export_"
FORMAT AS CSV
PROPERTIES (
    "AWS_ENDPOINT" = "https://s3.us-east-1.amazonaws.com",
    "AWS_ACCESS_KEY" = "",
    "AWS_SECRET_KEY" = "",
    "AWS_REGION" = "us-east-1"
);

-- Export as Parquet
SELECT * FROM test_table
INTO OUTFILE "s3://bucket/parquet_"
FORMAT AS PARQUET
PROPERTIES ("AWS_ENDPOINT" = "...", ...);

-- Enable parallel export (multiple files)
SET enable_parallel_outfile = true;
SELECT * FROM test_table
INTO OUTFILE "s3://bucket/parallel_";
→ 4.2 EXPORT — Async Batch Export
Asynchronous export method for large datasets. Submit via EXPORT TABLE, check progress with SHOW EXPORT. Supports partitioning and data filtering.
-- Submit export job
EXPORT TABLE test_table
PARTITION (p202401)
WHERE age > 30
TO "s3://bucket/export_data/"
PROPERTIES (
    "label" = "export_job_001",
    "format" = "csv"
);

-- Check progress
SHOW EXPORT WHERE label = "export_job_001";

-- Cancel export
CANCEL EXPORT WHERE label = "export_job_001";
→ 4.3 mysql dump — Schema & Data Export
Uses the standard mysqldump tool to export Doris table schemas or data. Compatible with standard MySQL dump syntax.
# Export table structure only
mysqldump -h  -P  \
    -u  -p \
    --no-data database_name table_name

# Export data as INSERT statements
mysqldump -h  -P  \
    -u  -p \
    --no-create-info database_name table_name

# Export both schema and data
mysqldump -h  -P  \
    -u  -p \
    database_name table_name

# Import exported data into Doris
mysql -h  -P  \
    -u  -p \
    database_name < export.sql
→ 4.4 Best Practices
⚡

Parallel Export

Enable enable_parallel_outfile=true for SELECT INTO OUTFILE. Each BE node exports a portion of data simultaneously, improving speed proportionally to cluster size.

📈

Export Speed

Use OUTFILE for small-medium datasets. Use EXPORT for large-scale async operations. For schema-only backup, use mysqldump with --no-data.

📄

File Format Choice

Use Parquet for analytics and data lake integration. Use CSV for interoperability with other systems. Use ORC for Hive/Spark compatibility.

💡
Key Difference: SELECT INTO OUTFILE is synchronous and supports data transforms via SQL. EXPORT is asynchronous and better for very large datasets. Mysqldump is best for schema export and logical backup of small tables.
