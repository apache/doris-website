Section 1

Table Models — Choosing the Right Foundation

Every Doris table requires a data model. This decision determines how data is stored, deduplicated, aggregated, and updated. The model cannot be changed after table creation, so getting it right is critical.
Core Decision: The three models cover three scenarios: retaining all raw data (Duplicate), updating by primary key (Unique), and pre-aggregated analysis (Aggregate).
Business ScenarioRecommended ModelKey Characteristic
Logs, events, behavior analysisDuplicateKey columns may repeat; ad-hoc queries on any dimension
Real-time dim tables, orders, user profilesUniqueKey columns unique; only latest data kept per Key
Report rollups, traffic stats, pre-aggregationAggregatePre-aggregates by Key columns to reduce scan volume
📋 Duplicate Model

Default model. Retains every row without deduplication. Key columns used only for sorting.

Append-only
🔑 Unique Model

Primary-key uniqueness guaranteed. UPSERT semantics: new data overwrites existing rows with the same Key.

Update by Key
📊 Aggregate Model

Pre-aggregates Value columns by Key. Stores only aggregated results to save space and accelerate queries.

Pre-aggregation

Sort Key & Key Columns

Key columns serve dual purposes: sorting all models, plus uniqueness (Unique/Aggregate). A well-designed sort key accelerates queries, improves compression, and reduces deduplication cost.
ModelRole of Key Columns
DuplicateSorting only; uniqueness not enforced
UniqueSorting + uniqueness constraint; deduplication by primary key
AggregateSorting + uniqueness + pre-aggregation by Key
ⓘ
Sort Key Design Tips: Key columns must come before all Value columns. Prefer integer types (far more efficient than strings). Use the shortest sufficient integer length. For VARCHAR/STRING, use the minimum length needed.

CREATE TABLE IF NOT EXISTS example_tbl_agg
(
    user_id         LARGEINT    NOT NULL,
    load_date       DATE        NOT NULL,
    city            VARCHAR(20),
    last_visit_dt   DATETIME    REPLACE DEFAULT "1970-01-01 00:00:00",
    cost            BIGINT      SUM     DEFAULT "0",
    max_dwell       INT         MAX     DEFAULT "0"
)
AGGREGATE KEY(user_id, load_date, city)
DISTRIBUTED BY HASH(user_id) BUCKETS 10;

DUPLICATE MODEL — Deep Dive

The default model. Every written row is retained with no deduplication or aggregation. Ideal for append-only logs and events.

📄

Retain All Data

Every row is stored as-is. Even identical rows are fully retained on each insert.

🔍

Flexible Queries

Full original data enables ad-hoc analysis and fine-grained auditing on any dimension.

⚡

Best Performance

Reads only relevant columns. No aggregation constraints. Fully leverages columnar storage.

CREATE TABLE IF NOT EXISTS example_tbl_duplicate
(
    log_time        DATETIME       NOT NULL,
    log_type        INT            NOT NULL,
    error_code      INT,
    error_msg       VARCHAR(1024),
    op_id           BIGINT,
    op_time         DATETIME
)
DUPLICATE KEY(log_time, log_type, error_code)
DISTRIBUTED BY HASH(log_type) BUCKETS 10;
-- Append 4 rows, then 2 more: all 6 are retained
INSERT INTO example_tbl_duplicate VALUES
('2024-11-01 00:00:00', 2, 2, 'timeout', 12, '2024-11-01 01:00:00'),
('2024-11-02 00:00:00', 1, 2, 'success', 13, '2024-11-02 01:00:00'),
('2024-11-03 00:00:00', 2, 2, 'unknown', 13, '2024-11-03 01:00:00'),
('2024-11-04 00:00:00', 2, 2, 'unknown', 12, '2024-11-04 01:00:00');

INSERT INTO example_tbl_duplicate VALUES
('2024-11-01 00:00:00', 2, 2, 'timeout', 12, '2024-11-01 01:00:00'),
('2024-11-01 00:00:00', 2, 2, 'unknown', 13, '2024-11-01 01:00:00');

SELECT * FROM example_tbl_duplicate;
-- Returns 6 rows
UNIQUE MODEL — Deep Dive

Primary-key uniqueness with UPSERT semantics. Supports UPDATE/DELETE, whole-row upsert, and partial column updates.

CREATE TABLE IF NOT EXISTS example_tbl_unique
(
    user_id         LARGEINT        NOT NULL,
    user_name       VARCHAR(50)     NOT NULL,
    city            VARCHAR(20),
    age             SMALLINT,
    sex             TINYINT
)
UNIQUE KEY(user_id, user_name)
DISTRIBUTED BY HASH(user_id) BUCKETS 10;
-- Insert original data
INSERT INTO example_tbl_unique VALUES
(101, 'Tom', 'BJ', 26, 1),
(102, 'Jason', 'BJ', 27, 1),
(103, 'Juice', 'SH', 20, 2),
(104, 'Olivia', 'SZ', 22, 2);

-- Re-insert same Keys with new values
INSERT INTO example_tbl_unique VALUES
(101, 'Tom', 'BJ', 27, 1),
(102, 'Jason', 'SH', 28, 1);

SELECT * FROM example_tbl_unique;
-- Tom age=27 (updated), Jason city=SH (updated)
-- 102 and 103 unchanged
⚠
Limitations: The implementation (merge-on-write / merge-on-read) cannot be changed after creation. Partition keys must be a subset of Key columns. Whole-row UPSERT fills unspecified columns with NULL/default values.
KEY INSIGHTS & LIMITATIONS
📈 Aggregate Model Pitfalls
  • ⚠ count(*) is expensive — must scan all AGGREGATE KEY columns
  • ⚠ Inconsistent aggregation: SELECT MIN(cost) returns 5, not 1 on unmerged batches
  • 💡 Fix: add a SUM column with value=1 for fast count(*)
  • 💡 Or use REPLACE type + value=1 for equivalent semantics
⚡ Unique Merge-on-Write
  • ✅ count(*) is 10x faster than Aggregate model
  • ✅ No aggregation needed at query time — uses delete bitmap
  • ✅ Duplicate model has no aggregation semantics → scan any single column for correct count(*)
  • 💡 Merge-on-write is the default — works for most workloads
💡
Partial Column Update: Both Unique and Aggregate models support partial column updates. See the dedicated documentation for usage recommendations.
Section 2

Partitioning — Logical Data Organization

Partitioning divides table data into smaller, manageable segments. Doris supports three approaches: manual, dynamic, and auto partitioning — each suited to different data patterns and lifecycle needs.

2.1 Manual Partitioning

User explicitly defines partition rules at table creation. Four forms of Range partitioning and List partitioning.

Range FormUse Case
FIXED RANGEPrecise control over upper and lower bounds of each partition
LESS THANAppend partitions in chronological order; only upper bound needed
BATCH RANGEBatch create numeric/time partitions with equal step size
MULTI RANGEDifferent step sizes for different time ranges in one statement
FIXED RANGE
PARTITION BY RANGE(`date`)
(
 PARTITION `p201701`
   VALUES [("2017-01-01"), ("2017-02-01")),
 PARTITION `p201702`
   VALUES [("2017-02-01"), ("2017-03-01"))
)
LESS THAN
PARTITION BY RANGE(`date`)
(
 PARTITION `p201701`
   VALUES LESS THAN ("2017-02-01"),
 PARTITION `p201702`
   VALUES LESS THAN ("2017-03-01"),
 PARTITION `other`
   VALUES LESS THAN (MAXVALUE)
)

List Partitioning

-- Single-column List
PARTITION BY LIST(city)
(
    PARTITION `p_cn` VALUES IN ("Beijing", "Shanghai", "Hong Kong"),
    PARTITION `p_usa` VALUES IN ("New York", "San Francisco")
)

-- Multi-column List
PARTITION BY LIST(id, city)
(
    PARTITION p1_city VALUES IN (("1", "Beijing"), ("1", "Shanghai")),
    PARTITION p2_city VALUES IN (("2", "Beijing"), ("2", "Shanghai"))
)

2.2 Dynamic Partitioning

Rolls partitions forward automatically by creating and dropping them on a schedule. Provides partition TTL lifecycle management for time-series data.
💡
Tip: Auto Partitioning is the recommended successor to Dynamic Partitioning. Dynamic works only with Range on DATE/DATETIME columns, single partition key only.
CREATE TABLE test_dynamic_partition(
    order_id    BIGINT,
    create_dt   DATE,
    username    VARCHAR(20)
)
DUPLICATE KEY(order_id)
PARTITION BY RANGE(create_dt) ()
DISTRIBUTED BY HASH(order_id) BUCKETS 10
PROPERTIES(
    "dynamic_partition.enable" = "true",
    "dynamic_partition.time_unit" = "DAY",
    "dynamic_partition.start" = "-1",
    "dynamic_partition.end" = "2",
    "dynamic_partition.prefix" = "p",
    "dynamic_partition.create_history_partition" = "true"
);
ParameterRequiredDescription
dynamic_partition.time_unitYesHOUR, DAY, WEEK, MONTH, YEAR
dynamic_partition.startNoNegative offset; partitions before this are dropped
dynamic_partition.endYesPositive offset; pre-create partitions into the future
dynamic_partition.prefixYesPartition name prefix

2.3 Auto Partitioning

Creates partitions automatically during data ingestion based on partition column values. Solves the problem of unpredictable value ranges and large partition counts.
AUTO RANGE
CREATE TABLE `DAILY_TRADE_VALUE`
(
    `TRADE_DATE` datev2 NOT NULL,
    `TRADE_ID`   varchar(40) NOT NULL
)
UNIQUE KEY(`TRADE_DATE`, `TRADE_ID`)
AUTO PARTITION BY RANGE
  (date_trunc(`TRADE_DATE`, 'year'))
()
DISTRIBUTED BY HASH(`TRADE_DATE`)
  BUCKETS 10
PROPERTIES
  ("replication_num" = "1");

-- Insert creates partitions automatically
INSERT INTO `DAILY_TRADE_VALUE`
VALUES ('2012-12-13', 1),
       ('2008-02-03', 2),
       ('2014-11-11', 3);
AUTO LIST
CREATE TABLE `str_table` (
    `str` varchar not null
)
DUPLICATE KEY(`str`)
AUTO PARTITION BY LIST (`str`)
()
DISTRIBUTED BY HASH(`str`) BUCKETS 10
PROPERTIES
  ("replication_allocation"
    = "tag.location.default: 1");

-- Each new value creates a partition
INSERT INTO `str_table`
VALUES ('beijing'), ('shanghai');

Partition functiondate_trunc onlyNot supported
Column typesDATE, DATETIMEBOOLEAN, INT, BIGINT, DATE, VARCHAR, etc.
Multi-columnNoYes
NULL supportNot supportedSupported
ⓘ
Lifecycle: AUTO RANGE supports lifetime management via partition.retention_count — retains only the N most recent historical partitions. Can also be used with dynamic partitioning, though this combination is no longer recommended.
Section 3

Data Bucketing — Physical Data Distribution

Each partition is further divided into buckets (Tablets). The bucketing strategy controls data distribution, query parallelism, and I/O efficiency.
Follow this decision path: Choose method → Select bucket key (Hash only) → Determine count → Plan maintenance
🔎 Hash Bucketing
  • ✅ Supports bucket pruning for filtered queries
  • ✅ Requires bucket key (1+ columns)
  • ⚠ Risk of data skew if key poorly chosen
  • ✅ Works with all table models
  • ✅ Perfect for point queries on specific columns
🔀 Random Bucketing
  • ✅ No bucket key needed
  • ✅ Even distribution, low skew risk
  • ⚠ No bucket pruning support
  • ⚠ DUPLICATE model only
  • 💡 Best for arbitrary-dimension analysis
-- Hash bucketing
CREATE TABLE demo.hash_bucket_tbl (
    oid     BIGINT, dt DATE,
    region  VARCHAR(10), amount INT
)
DUPLICATE KEY(oid)
PARTITION BY RANGE(dt) (
    PARTITION p250101 VALUES LESS THAN("2025-01-01"),
    PARTITION p250102 VALUES LESS THAN("2025-01-02")
)
DISTRIBUTED BY HASH(region) BUCKETS 8;

-- Random bucketing
CREATE TABLE demo.random_bucket_tbl (
    oid     BIGINT, dt DATE,
    region  VARCHAR(10), amount INT
)
DUPLICATE KEY(oid)
PARTITION BY RANGE(dt) (
    PARTITION p250101 VALUES LESS THAN("2025-01-01"),
    PARTITION p250102 VALUES LESS THAN("2025-01-02")
)
DISTRIBUTED BY RANDOM BUCKETS 8;

Bucket Count Guidelines

⚠
Caution: The number of buckets for a partition cannot be changed after creation. Plan ahead for future scaling.
Compressed Partition SizeRecommended Buckets
< 1 GB1
1 - 10 GB10
10 - 200 GB10 - 20
> 200 GBPartition the table first
Key rules: Each Tablet compressed data should be 1-20 GB (≤10 GB for Unique). Tablet count should slightly exceed total cluster disks. Buckets must be an integer multiple of BE count. Max 128 buckets per partition.
-- Auto bucketing (since 2.0)
DISTRIBUTED BY HASH(region) BUCKETS AUTO
PROPERTIES("estimate_partition_size" = "20G")

-- Modify for new partitions
ALTER TABLE demo.hash_bucket_tbl
ADD PARTITION p250103 VALUES LESS THAN("2025-01-03")
DISTRIBUTED BY HASH(region) BUCKETS 16;

-- Dynamic partition bucket override
ALTER TABLE demo.dynamic_partition_tbl
SET ("dynamic_partition.buckets"="16");
💡
Tip: Only Hash bucketing requires a bucket key. For DUPLICATE tables, any Key or Value column qualifies. For AGGREGATE/UNIQUE, bucket keys must be Key columns.

Best Practices — POC-Ready Table Design

Four key decisions determine ingestion and query performance: data model, sort key, partitioning, and bucketing. This section provides concrete templates and verification steps.
💡
Quick Checklist (5 minutes): Does the table use the right data model? Is the bucket count an integer multiple of BE count? Do time-based queries include the partition column? Is Data Cache enabled for lake queries?

Common Pitfalls & Solutions

⚠

Too Many Small Tablets

Excessive buckets create scheduling overhead, reducing query performance by up to 50%. Keep compressed data per Tablet between 1-20 GB.

⚠

Data Skew

Uneven tablet sizes hurt parallelism. Use SHOW TABLETS to diagnose. Switch to Random bucketing or choose a higher-cardinality bucket key.

📈

count(*) Performance

In the Aggregate model, count(*) must scan all Key columns. Fix: add a SUM column with value=1. Unique merge-on-write is 10x faster.

🔧

Sort Key Best Practices

Put high-frequency filter columns first. Use fixed-length types (INT, BIGINT, DATE) before VARCHAR. Add inverted indexes for columns the prefix index does not cover.

💡
Ingestion Best Practices: Don't use INSERT INTO VALUES for bulk data. Use Stream Load or Broker Load. Merge writes client-side first. Split large ingestions into smaller batches. For Duplicate + Random bucketing, enable load_to_single_tablet to reduce write amplification.
