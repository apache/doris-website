Section 1

Data Organization

Apache Doris organizes data through a three-tier hierarchy of Catalog, Database, and Table — enabling logical isolation and unified cross-source access. Partitions and buckets further refine how data is stored and distributed.

Catalog → Database → Table

Three-tier hierarchy for logical isolation and cross-source access.

ⓘ
Why a three-tier design? The tiered design balances logical isolation with unified cross-source access. Business teams own independent Databases, while platform teams can directly query external data sources through External Catalogs.

Internal vs. External Catalog

📂 Internal Catalog
  • ✅ Name fixed as internal
  • ✅ Doris internal columnar format
  • ✅ Full DDL/DML support (Stream Load, etc.)
  • ✅ High query performance (local data)
🌐 External Catalog
  • ✅ User-defined name
  • ✅ External formats: Parquet, ORC
  • ✅ Iceberg/Paimon: full DDL/DML; Hive/JDBC: query only
  • ⚠ Performance depends on external source

Partition & Bucket

Partitions define logical boundaries (e.g., daily ranges), while buckets define physical distribution (hash-based placement across nodes).

Division basisValue range of a columnHash computation

Section 2

Storage Model

How Apache Doris organizes data on disk determines query performance, compression ratios, and concurrency behavior. The two pillars are columnar storage and the three data models.

Columnar Storage

Data is organized by column instead of row — the foundation of high I/O efficiency.

⚡

High I/O Efficiency

A query reads only the columns it needs, avoiding full table scans. For report queries touching a few columns, I/O can drop by tens of times.

📈

High Compression Ratio

Data in the same column shares one type, ideal for dictionary encoding, bitmap compression, and RLE — significantly reducing storage space.

⚙

Vectorization-friendly

Same-column data stored contiguously in memory yields high CPU cache hit rates and enables SIMD-accelerated computation.

Data Models

Three data models handle different merging needs: Duplicate retains everything, Aggregate merges by function, and Primary Key supports row-level overwrites.
ModelDescriptionUse Cases
DuplicateRetains all original data; multiple records with same key are all preservedDetail storage of fact tables, log analytics
AggregateRecords with same key are merged via SUM, MAX, MINMetric statistics, report pre-aggregation
Primary KeyKeys are unique; records with same key overwrite previous onesReal-time updates, CDC data ingestion

Integrated Storage-Compute Architecture

The classic deployment mode: FE + BE. Data storage and computation are co-located, offering simplicity, low latency, and high availability without external dependencies.

🔧

Simple & Easy

Only two process types: FE and BE. No external dependencies like ZooKeeper. BDB JE handles metadata transactions natively.

⚡

High Performance

Compute nodes access local storage directly with low network overhead. Vectorized execution + SIMD delivers 5–10x on aggregations.

🛡

High Availability

Multiple replicas with quorum protocol. Automatic fault isolation. FE uses Paxos-like consensus for metadata consistency.

Section 4

Decoupled Storage-Compute Architecture

Introduced in version 3.0, this architecture fully separates the compute layer from the storage layer, enabling independent elastic scaling and workload isolation.
↕

Elastic Compute

Resources scale on demand, suitable for workloads with peaks and troughs. Minute-level scaling of compute resources.

👥

Workload Isolation

Different business teams share data while keeping compute resources independent. No noisy-neighbor interference.

💰

Low Storage Cost

Object storage dramatically reduces storage expenditure vs. all-SSD deployments. BE uses LRU cache for hot data.

Core Technical Modules

Two engines form the heart of Apache Doris: the Storage Engine with columnar storage, indexes, and data models; and the Query Engine with MPP, vectorized execution, and pipeline parallelism.

Storage Engine

📄

Columnar & Compression

Data by column, reducing I/O. Dictionary encoding, bitmap compression, and RLE achieve high compression ratios.

🔎

Index Structures

Sorted composite key, Min/Max pruning, BloomFilter, and inverted index for fast full-text search.

📈

Three Data Models

Duplicate, Aggregate, and Primary Key handle detail retention, pre-aggregation, and row-level updates.

Sorted composite key (up to 3 columns)Pruning for high-concurrency reports

Query Engine

MPP

Massively Parallel Processing. Queries decomposed into stages, executed across multiple BE nodes.

Distributed
Vectorized

Columnar batches + SIMD. 5–10x improvement on wide-table aggregations vs. row-based.

Hardware Acceleration

Multi-core parallelism with thread limits; operator-chain scheduling prevents thread explosion.

CPU Efficiency

Overview: MPP handles inter-node parallelism; Pipeline handles intra-node multi-core utilization. Together they provide end-to-end parallelism.

Query Execution

When a SQL query arrives, it flows through a well-defined pipeline: parsing → planning → fragmentation → distributed execution → result aggregation.
📃 Row-based
  • One row at a time
  • Low CPU cache hit rate
  • Hard to leverage SIMD
  • Baseline performance
⚡ Vectorized
  • One column batch at a time
  • High cache hit rate
  • Fully utilizes SIMD
  • 5–10x on aggregations
ConceptDescription
FragmentLogical execution unit. A query plan consists of multiple Fragments.
InstancePhysical execution unit composed of operators (Scan, Agg, Join) running on a BE node.
ExchangeThe operator that performs network data exchange between Instances.
Section 8

Query Optimization

Doris employs a multi-layered optimization strategy: Materialized Views for precomputation, CBO and RBO for plan selection, and Runtime Filters for dynamic data reduction.
📈

Materialized View

Precomputed results stored as physical tables. Automatically updated and transparently rewritten.

🔬

CBO

Cost-based optimizer. Estimates I/O, CPU, and network for each plan, selects the cheapest. Uses ANALYZE statistics.

📜

RBO

Rule-based optimizer. Constant folding, predicate pushdown, subquery rewriting. Deterministic, no statistics needed.

🔥

Runtime Filter

Dynamic filter generated during execution, pushed down to scan nodes. Reduces large-table scan volume by several to tens of times.

CBO vs. RBO

📜 RBO
  • Rule-driven, deterministic
  • No statistics required
  • Constant folding: 1 + 2 → 3
  • Predicate pushdown before JOIN
  • Subquery rewriting → JOIN
🔬 CBO
  • Cost-driven, data-aware
  • Requires accurate ANALYZE stats
  • Join order optimization
  • Join algorithm selection
  • Distributed execution planning
ⓘ
How they work together: RBO handles deterministic optimizations first. CBO then evaluates the remaining space with cost estimates. Both are enabled by default.

Section 9

FAQ & Summary

Common questions about partitions vs. buckets, data model selection, MPP vs. Pipeline, External Catalogs, materialized views, and high availability.
What is the difference between partitions and buckets?
A partition divides data by value range (time-based). It manages data lifecycle and enables partition pruning. A bucket distributes data by hash for parallel processing. Partition = logical boundary; bucket = physical distribution.
When should I choose Primary Key over Duplicate?
Choose Primary Key when you need row-level updates (CDC). Choose Duplicate for log analytics where every record must be preserved.
How are MPP and Pipeline related?
They operate at two different dimensions. MPP is distributed parallelism across nodes. Pipeline is intra-node multi-core parallelism. Together they deliver "parallelism between nodes plus pipelining within a node."
Where do CBO and RBO statistics come from?
Doris collects statistics with the ANALYZE command: row count, column cardinality (NDV), NULL ratio. Run ANALYZE again after significant data changes.
External Catalog vs. regular Database?
A regular Database stores data inside Doris. An External Catalog is a logical mapping — data stays in the external source (Hive, Iceberg, etc.) with no ETL migration required.
Materialized view vs. regular view?
A regular view stores only SQL logic and computes every time. A materialized view physically stores results, stays synchronized, and transparently accelerates queries.
What is the core difference between the two architectures?
In the integrated architecture, BE nodes handle both storage and computation on local disks. In the decoupled architecture, data lives in shared storage (S3, HDFS) and BE nodes are stateless compute nodes with local caching. The decoupled architecture supports independent elastic scaling.
How is high availability implemented?
Through multiple replicas (default 3) and a quorum protocol. Failed nodes are automatically isolated and replicas rebuilt from healthy ones. FE uses a Paxos-like consensus protocol with automatic master election.
