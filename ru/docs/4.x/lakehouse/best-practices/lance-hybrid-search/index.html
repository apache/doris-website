Рекомендации по оптимизации производительности гибридного поиска в Lance

Используйте это руководство, когда при векторном или полнотекстовом поиске по данным Lance применяются скалярные условия. В нём объясняется, где размещать фильтры, как организовывать сегменты индексов и выявлять повторную работу по фильтрации. Здесь под гибридным поиском понимается поиск в сочетании со скалярной фильтрацией; раздельный вызов TVF для векторного и полнотекстового поиска сам по себе не объединяет результаты их ранжирования.

примечание

Lance Catalog находится на экспериментальной стадии и поддерживается начиная с Apache Doris 4.2. Сначала настройте доступ и проверьте требования к совместимости средств чтения и записи в разделе Lance Catalog. Doris читает существующие индексы Lance; создавайте и обслуживайте их совместимыми инструментами Lance. Наличие возможности в последней версии Lance SDK или в предложении upstream-проекта не гарантирует её поддержку механизмом чтения, входящим в вашу сборку Doris.

Автоматический поиск из обычных SQL-запросов​

В сборках Doris 4.2 с автоматическим поиском Lance подходящие обычные SQL-запросы могут использовать тот же нативный механизм поиска, что и явные TVF. Эта возможность не зависит от прямого вызова TVF: работающий vector_search() сам по себе не означает, что она поддерживается в более ранней сборке. Отдельно включать автоматический поиск на уровне сеанса не требуется.

Примеры векторного поиска и BM25​

После настройки Catalog предположим, что таблица lance_catalog.default.items содержит id, category, content, четырёхмерный embedding типа Float32 fixed-size-list и трёхбайтовый binary_embedding типа UInt8 fixed-size-list. Если требуется ускорение за счёт индексов, создайте совместимые векторные индексы и зафиксированный индекс FTS для content средствами Lance.

SELECT id, cosine_distance_approximate(embedding, [0.1,0.2,0.3,0.4]) AS distance
FROM lance_catalog.default.items
WHERE category = 'book'
ORDER BY distance ASC LIMIT 10 OFFSET 5;

SELECT id, cosine_similarity_approximate(embedding, [0.1,0.2,0.3,0.4]) AS similarity
FROM lance_catalog.default.items
ORDER BY similarity DESC LIMIT 10;

SELECT id, hamming_distance_approximate(binary_embedding, [0,255,170]) AS distance
FROM lance_catalog.default.items
ORDER BY distance ASC LIMIT 10;

SELECT id, score() AS relevance
FROM lance_catalog.default.items
WHERE content MATCH_ALL 'storage engine' AND category = 'book'
ORDER BY relevance DESC LIMIT 10;

Первый запрос ищет строки с category = 'book' до отсечения кандидатов. Каждый сплит запрашивает 15 кандидатов с нулевым смещением; Doris объединяет кандидатов и применяет итоговое OFFSET 5 LIMIT 10. Остальные запросы возвращают до 10 соседей или совпадений BM25 в соответствующем порядке. Поиск с использованием индекса может быть приближённым и вернуть меньше строк, чем запрошено. Существующие совместимые индексы используются повторно; для данных, не покрытых индексами, применяется существующий механизм Flat Search. Для BM25 требуется существующий индекс FTS.

Условия применения и резервный вариант​

  • Запрос должен содержать прямое сканирование таблицы Lance Catalog, необязательный фильтр, проекцию и Top-N с одним ключом сортировки по результату поиска и положительным LIMIT. JOIN/EXISTS, дополнительные ключи сортировки, DISTINCT, выборка из таблицы по образцу и выражения проекции, которые нельзя перенести, препятствуют этому переписыванию.
  • Для метрик с плавающей точкой требуются физические векторы типа Float32 fixed-size-list, а для Hamming — физические векторы типа UInt8 fixed-size-list. Векторы запроса должны быть константными массивами соответствующей размерности. Float16/Float64, многовекторные столбцы и произвольные приведения типов, изменяющие элементы, автоматически не переписываются. UInt8 в Doris представлен как SMALLINT; его расширение до BIGINT для аргументов функции Hamming безопасно.
  • Векторные запросы с неподдерживаемыми остаточными предикатами, обратным порядком сортировки результатов поиска, отсутствующими нативными метаданными или не прошедшие нативную проверку вектора либо схемы продолжают вычисляться скалярно. Для переписывания значение LIMIT + OFFSET должно укладываться в нативный лимит числа кандидатов UINT32; обычные скалярные SQL-запросы этим лимитом не ограничены.
  • Для BM25 требуются один поддерживаемый предикат MATCH верхнего уровня для непосредственного строкового столбца, литеральный поисковый запрос, сохранённый в индексе анализатор и сортировка по score() по убыванию. Остальные скалярные предикаты должны полностью проталкиваться. Условия score() > literal и score() >= literal поддерживаются как остаточные нижние границы; верхние границы и другие предикаты по оценке отклоняются. Неподдерживаемые формы запросов с оценкой вызывают ошибку, а не переходят незаметно к скалярному вычислению score().
  • Оценки рассчитываются на основе сохранённого анализатора и индекса Lance, а также статистики по всему снимку. Численно они могут не совпадать с оценками отдельно проиндексированной внутренней таблицы Doris. Это переписывание не поддерживает нечёткий поиск, переопределение анализатора и выражения SEARCH() по нескольким столбцам. Для поддерживаемых многовекторных запросов и настройки параметров, таких как nprobes, refine_factor или ef, используйте явные TVF.

Семантика нативного приближённого поиска​

Суффикс _approximate позволяет подходящему запросу Top-N использовать семантику отбора кандидатов нативным поиском Lance. Если переписывание не применяется, функции выполняют скалярные вычисления. Не используйте приближённые функции, когда требуется исчерпывающее ранжирование или скалярная проверка каждой сохранённой строки.

Результаты нативных вычислений и оценок индекса для косинусной метрики могут отличаться от результатов скалярных вычислений. Hamming считает различающиеся биты, а не байты: hamming_distance([0,255,170], [255,0,85]) возвращает 24. Hamming отклоняет массивы с числами с плавающей точкой, десятичными числами и LARGEINT до неявного приведения типов, а значения вне допустимого диапазона — до преобразования в байты. Для скалярного выполнения по-прежнему доступны точные функции.

Предварительная фильтрация WHERE и граница JOIN​

Предикаты таблицы Lance, которые можно полностью протолкнуть, вычисляются перед поиском на одном и том же закреплённом снимке. Doris сначала пытается выполнить сканирование только идентификаторов строк и передаёт полный список разрешённых идентификаторов всем поисковым считывателям в запросе. Пустой список не выбирает ни одной строки. Если идентификаторов больше 65,536, Doris отбрасывает частичный список и сохраняет полную нативную предварительную фильтрацию по предикату. Объём как временного, так и кэшированного списка учитывается в лимитах памяти запроса; сбор списков, прерванный или завершившийся ошибкой, не кэшируется. Этот механизм отличается от проталкивания Runtime Filter при соединении в обычных сканированиях.

В этом примере с ACL предположим, что таблица internal.auth.allowed_items содержит item_id и principal_id.

SELECT d.id,
       l2_distance_approximate(d.embedding, [0.1,0.2,0.3,0.4]) AS distance
FROM lance_catalog.default.items d
WHERE EXISTS (
    SELECT 1 FROM internal.auth.allowed_items a
    WHERE a.item_id = d.id AND a.principal_id = 42
)
ORDER BY distance ASC
LIMIT 10;

При этом сохраняются соединение, скалярное вычисление расстояния и глобальный Top-N. Переписывание не пересекает полусоединение ACL и не сопоставляет бизнес-идентификаторы с нативным _rowid Lance. Если выбрать Top-K без фильтрации до применения ACL, можно пропустить ближайшие строки, к которым есть доступ. Добавление второго ключа сортировки также препятствует автоматическому переписыванию.

Выполните EXPLAIN для конкретного запроса и проверьте наличие externalSearchType=VECTOR с lanceMetric=l2|dot|cosine|hamming либо externalSearchType=FULL_TEXT. Метрики LanceRowIdPrefilterTime, LanceRowIdPrefilterRows, LanceRowIdPrefilterCacheHits и LanceRowIdPrefilterFallbacks отражают работу Doris со списком разрешённых идентификаторов; они отличаются от приведённых ниже метрик нативного загрузчика идентификаторов строк. Для настройки поиска или поддерживаемых форм запросов, не подпадающих под это правило, используйте явные TVF. Переписанные поисковые запросы могут использовать существующее двухэтапное чтение выходных данных, если выполняются его собственные условия применения.

1. Задавайте фильтры отбора кандидатов внутри поиска​

Для настроенной таблицы с целочисленным столбцом id, строковыми столбцами category и content и четырёхмерным вектором embedding используйте параметр filter в TVF для условий, которые должны влиять на формирование кандидатов. Векторный индекс должен соответствовать размерности и метрике; для текстового столбца должен быть зафиксирован FTS-индекс.

SELECT id, _distance
FROM vector_search(
    "table" = "lance_catalog.default.items",
    "column" = "embedding",
    "query_vector" = "[0.1,0.2,0.3,0.4]",
    "metric" = "l2",
    "top_k" = "20",
    "filter" = "category = 'book'",
    "use_index" = "true"
)
ORDER BY _distance ASC, id;

Этот запрос ищет до 20 соседей среди строк, удовлетворяющих условию. Это приближённый поиск: возврат 20 строк не подтверждает полноту поиска (recall). Для полнотекстового поиска с фильтрацией:

SELECT id, _score
FROM full_text_search(
    "table" = "lance_catalog.default.items",
    "column" = "content",
    "query" = "storage engine",
    "query_type" = "match",
    "operator" = "and",
    "top_k" = "20",
    "filter" = "category = 'book'",
    "coverage_mode" = "strict"
)
ORDER BY _score DESC, id;

Этот запрос возвращает до 20 подходящих документов, ранжированных по BM25. Внешнее условие WHERE category = 'book' имеет другую семантику: Doris фильтрует кандидатов, уже сформированных Lance, перед глобальным TopN. Удалённые кандидаты автоматически не восполняются. За пределами TVF оставляйте только те условия, которые намеренно применяются после поиска, даже если EXPLAIN показывает их внутри оператора Scan в Doris.

2. Учитывайте единицу параллельной работы​

lance_fragments_per_split управляет группировкой фрагментов при обычном сканировании, а не количеством физических сегментов векторного индекса. Увеличение числа экземпляров pipeline или параллелизма сканеров не создаёт больше задач по векторным сегментам, чем сформировал планировщик. Сканер Lance также может выполнять работу параллельно внутри себя, поэтому один сканер Doris не равнозначен одному потоку CPU.

При S поисковых задачах каждая может вернуть не более top_k + offset кандидатов. Поэтому верхняя граница числа кандидатов до слияния равна S * (top_k + offset), до остаточной фильтрации и глобального TopN. Увеличение числа сегментов может улучшить распределение работы, одновременно увеличивая затраты на подготовку каждого сегмента, фильтрацию, слияние кандидатов и память для параллельного выполнения.

3. Согласуйте покрытие фрагментов, а не количество сегментов​

Фрагмент представляет собой единицу данных. Сегмент индекса представляет собой самостоятельный индекс, покрывающий набор фрагментов. Логический индекс объединяет физические сегменты под одним именем индекса. Раздел IVF, страница BTree или блок списков вхождений FTS являются внутренними единицами индекса; ни одна из них не определяет поисковую задачу Doris.

В следующем примере используются восемь фрагментов данных:

Одинаковое количество, но границы пересекаютсяКак вышеB0={0,1,4,5}, B1={2,3,6,7}Оба скалярных сегмента пересекаются с обеими задачами векторного поиска. Равное количество не обеспечивает согласованности.

Отсечение по фрагментам пропускает скалярные сегменты без пересечений. При частичном пересечении сегмент сохраняется: это не приводит к автоматическому построению меньшего BTree или обрезке каждого списка вхождений перед вычислением предиката. Повторные запросы могут повторно использовать содержимое индекса из кэша, но при этом снова выполнять поиск и строить множества идентификаторов строк. Поиск в BTree не обязательно сканирует все страницы сохранённого сегмента; стоимость зависит от предиката и числа совпадений.

important

Эта возможность зависит от фактического пути чтения. В пути чтения с фильтрацией V2 в Lance, где скалярные индексы загружаются с учётом фрагментов, не относящиеся к нужным фрагментам скалярные сегменты могут исключаться до поиска. Устаревшие пути чтения файлов данных V1 могут обрабатывать логический скалярный индекс в более широкой области, а затем ограничивать идентификаторы строк. V1/V2 здесь относятся к формату файлов данных, а не к версии Doris или типу векторного индекса. Не предполагайте, что отсечение одинаково работает во всех версиях механизма чтения или в пути FTS; проверяйте план и профиль каждой группы запросов.

Для столбцов, которые часто используются совместно, применяйте одинаковые группы фрагментов при построении векторных, скалярных и FTS-индексов. Скалярные сегменты могут быть мельче, если каждый из них целиком находится внутри обслуживаемого им поискового сегмента. Если векторным и FTS-сегментам нужны разные размеры, рассмотрите объединение общих базовых групп в более крупные и следите, чтобы скалярные сегменты не пересекали границы ни в одном из вариантов. Такая политика размещения уменьшает возможные пересечения, но не гарантирует, что каждый путь выполнения использует это преимущество.

Выберите начальную гранулярность​

Универсального оптимального числа строк или размера сегмента в байтах нет. Начните с BE, которые могут обслуживать эту нагрузку, а затем сравните один сбалансированный поисковый сегмент на BE с несколькими сегментами на BE при фиксированном recall и целевом числе одновременных запросов. Это варианты для эксперимента, а не обязательные соотношения.

4. Стройте связанные индексы по единому плану группировки​

В Doris нет параметра, который автоматически согласует индексы разных столбцов. Используйте API распределённого построения Lance, если они поддерживаются вашей совместимой версией SDK. Ниже приведена схема оркестрации, а не готовый к запуску генератор набора данных или конфигурация для тестирования производительности:

# ds is an existing LanceDataset at the chosen build snapshot.
# groups contains non-empty, disjoint lists of actual fragment IDs.
# vector_params and fts_params are validated for the schema and SDK version.
# Keep writes and compaction paused for this simple coordinator example.
visible = {fragment.fragment_id for fragment in ds.get_fragments()}
assigned = [fragment_id for group in groups for fragment_id in group]
assert groups and all(groups)
assert len(assigned) == len(set(assigned))
assert set(assigned) == visible

specs = [
    ("embedding_idx", "embedding", "IVF_PQ", vector_params),
    ("category_idx", "category", "BTREE", {}),
    ("content_idx", "content", "INVERTED", fts_params),
]
segments = {name: [] for name, _, _, _ in specs}
for fragment_ids in groups:
    for name, column, index_type, params in specs:
        segment = ds.create_index_uncommitted(
            column,
            index_type,
            name=name,
            fragment_ids=fragment_ids,
            **params,
        )
        segments[name].append(segment)

# These are three separate commits, not an atomic multi-index publication.
for name, column, _, _ in specs:
    ds.commit_existing_index_segments(name, column, segments[name])

Подготовьте и проверьте входные данные следующим образом:

  1. Зафиксируйте план построения. Получите фактические идентификаторы фрагментов из одного снимка; идентификаторы не обязательно идут подряд. Сбалансируйте группы по числу строк и оценочному размеру индексов в байтах. Используйте именно эти группы для каждого связанного столбца. Все распределённые рабочие процессы должны открывать одну и ту же версию для построения.
  2. Выберите совместимые конфигурации. Для IVF_PQ задайте подходящую метрику, num_partitions и num_sub_vectors с учётом размерности вектора и размера выборки. Поддерживайте единообразие конфигураций в пределах логического индекса. Для FTS используйте одинаковые настройки анализатора и токенизатора и включайте with_position, если нужен фразовый поиск.
  3. Выберите стратегию работы с векторными моделями. Поддерживаемые варианты построения нескольких сегментов могут обучать каждый сегмент независимо. Если последующее физическое слияние требует общих моделей, передайте рабочим процессам одинаковые центроиды IVF и кодовую книгу PQ. Не объединяйте независимо обученные сегменты без проверки и не предполагайте, что графы HNSW сохраняются при слиянии; проверьте поддерживаемый SDK порядок действий.
  4. Сначала постройте индексы, затем опубликуйте. Каждое построение возвращает физический сегмент с собственным UUID. Соберите успешные результаты и проверьте покрытие и совместимость перед фиксацией каждого логического индекса. Не назначайте один общий физический UUID разным столбцам или результатам разных рабочих процессов. В примере предполагается использование новых имён логических индексов; замена, повторные попытки и очистка после сбоев требуют отдельной политики координатора.
  5. Проверьте полученный манифест. Для каждого индекса сравните фактическое покрытие фрагментов сегментами с запланированными группами и проверьте, нет ли пропусков или пересечений покрытия. Одного совпадения количества сегментов недостаточно. Используйте метаданные индексов Lance; команда Doris SHOW INDEX для таблиц Filesystem Catalog помогает проверить имена, типы и поля логических индексов, но не заменяет проверку покрытия.

Единый план группировки не требует слияния результатов всех рабочих процессов в один сегмент. Такое слияние удалило бы границы, которые вы намеревались сохранить. Сведения об API построения и фиксации и поддерживаемых процессах слияния см. в разделе Распределённое построение индексов Lance.

Сохраняйте согласованность при обслуживании​

  • Добавляйте связанные векторные, скалярные и FTS-сегменты для одних и тех же новых групп фрагментов. После каждой публикации проверяйте покрытие снимка, используемого запросом. Режим FTS strict может отклонять запросы в промежутке между добавлением данных и завершением публикации индекса.
  • Рассматривайте уплотнение, перезапись и оптимизацию индексов как изменения схемы размещения. В зависимости от операции и версии механизма чтения индексы могут переназначаться или перестраиваться; проверяйте полученное покрытие, не предполагая, что прежние границы сохраняются.
  • Объединяйте мелкие группы по единому плану размещения. Не оптимизируйте каждый индекс независимо, создавая несогласованные группы, если производительность смешанных запросов зависит от согласованности.
  • Для обслуживания без остановки работы используйте координатор с обработкой снимков, конфликтов и восстановлением. Отдельные фиксации индексов не обеспечивают атомарного переключения всех столбцов. TVF читают последний снимок main; их аргумент table не позволяет выбрать историческую версию или тег.

Логические индексы и планы развития upstream-проекта​

Формат индексов Lance определяет логические индексы и физические сегменты. В задаче по распределённому построению индексов отслеживается общий жизненный цикл сегментов для разных семейств индексов. Эта модель не требует одинаковых границ фрагментов у разных столбцов. Группировка между столбцами и обслуживание остаются задачами оркестрации; не считайте планы upstream-проекта автоматически доступной возможностью согласования индексов в Doris.

Отсутствующие или нулевые значения сами по себе не доказывают, что индекс или фильтр не использовался. Если эти метрики не объясняют длительность чтения, соберите трассировку CPU и ввода-вывода, прежде чем относить оставшееся время к хранилищу.

Для векторного запроса без фильтрации механизм чтения с оптимизацией области сегмента может избежать перечисления всех идентификаторов строк, если выбранный сегмент индекса целиком находится в области фрагментов сканирования. Фактические скалярные предикаты всё равно требуют вычисления; обработка удалений и видимости также может сохраняться. Согласование уменьшает лишнюю работу, но не гарантирует нулевых затрат на Prefilter при поиске с фильтрацией.
