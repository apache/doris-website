Lance Catalog

примечание

Это экспериментальная функция.

Lance Catalog поддерживается начиная с Apache Doris 4.1.4.

Lance — это колоночный формат данных, предназначенный для аналитических нагрузок и задач AI. Doris может использовать Lance Catalog для обнаружения баз данных и таблиц в Lance Namespace и напрямую запрашивать наборы данных Lance, хранящиеся в локальной файловой системе, объектном хранилище, совместимом с S3, или Alibaba Cloud OSS.

В настоящее время Doris предоставляет для Lance доступ только на чтение. Создание, запись, обновление и удаление таблиц Lance не поддерживаются.

Варианты использования​

Вариант использованияОписание
Прямой запрос данных LanceАнализ существующих наборов данных Lance с помощью SQL Doris без предварительной миграции или импорта данных.
Векторный поиск AIПовторное использование векторных индексов, уже имеющихся в Lance, выполнение поиска через vector_search() и сочетание его со скалярной фильтрацией и аналитикой SQL Doris.
Полнотекстовый поискПовторное использование инвертированных FTS-индексов, уже имеющихся в Lance, выполнение поиска BM25 через full_text_search() и сочетание его со скалярной фильтрацией и аналитикой SQL Doris.
Интеграция данныхЧтение данных Lance во внутренние таблицы Doris для дальнейшей обработки, соединений или долговременного хранения.
Управление NamespaceДля простой структуры каталогов используйте Filesystem Catalog. REST Catalog используйте, когда требуется централизованно управлять Namespace, расположением таблиц или временными учётными данными хранилища.

Версия Lance и совместимость​

Средство чтения данных Doris BE собрано с lance-c v0.1.9 и патчами Doris, которые добавляют поддержку поиска по нескольким векторам и обновляют встроенные Rust crates Lance до 11.0.0 (commit ab6b5bbe). Doris FE читает метаданные Namespace и наборов данных с помощью org.lance:lance-core:12.0.0; FE читает только метаданные и никогда не записывает набор данных, поэтому более новый выпуск Lance на FE не меняет диапазон данных, которые может читать BE. Dataset должен быть совместим одновременно с загрузкой метаданных FE и чтением данных BE. Эти версии реализации отличаются от data_storage_version Lance, записанной в наборе данных.

Следующая таблица описывает совместимость формата файлов этого средства чтения:

data_storage_versionПоддержка чтенияПримечания
0.1 / legacyПоддерживаетсяИсходный формат файлов Lance.
2.0 (псевдоним параметра записи 0.3)ПоддерживаетсяБолее ранняя версия формата файлов Lance v2.
2.1 / stableПоддерживается; стабильный формат по умолчаниюВо встроенной версии Lance параметр записи stable и формат по умолчанию для новых наборов данных оба разрешаются в 2.1.
2.2ПоддерживаетсяВстроенная версия Lance рассматривает его как стабильный формат, но это не формат записи по умолчанию.
2.3 / nextЭкспериментальный; гарантий нетВстроенная версия Lance помечает 2.3 как нестабильный, а параметр записи next разрешается в 2.3.
Более поздняя или неизвестная версияНе поддерживаетсяОткрытие или сканирование набора данных может завершиться ошибкой неподдерживаемой версии хранилища.

Номера выпусков Lance SDK и версии формата файлов независимы. Набор данных, записанный более старым или более новым Lance SDK, читается только тогда, когда его формат хранения, требуемые флаги функций таблицы, формат индекса и типы данных Arrow/Lance понятны версиям, встроенным в Doris. Поэтому:

  • Ожидается, что Doris сможет читать наборы данных, записанные в форматах хранения 0.1, 2.0, 2.1 и 2.2, с учётом ограничений типов, описанных ниже.
  • Обратная совместимость вперёд не гарантируется. Набор данных, записанный или изменённый более новым выпуском Lance, может быть нечитаемым, если он использует новый формат хранения, неизвестную обязательную функцию manifest, новый формат индекса или неподдерживаемый extension type.
  • Для наборов данных, которые должны оставаться читаемыми этим выпуском Doris, используйте текущий стабильный формат по умолчанию 2.1 и не используйте next. После появления нового средства записи или необязательной функции Lance проверьте полученный набор данных целевым выпуском Doris перед использованием в production.

Настройка Catalog​

Синтаксис​

CREATE CATALOG [IF NOT EXISTS] catalog_name PROPERTIES (
    "type" = "lance",
    "lance.catalog.type" = "<filesystem|rest>",
    {CatalogProperties},
    {StorageProperties},
    {CommonProperties}
);

Filesystem Catalog​

Filesystem Catalog обнаруживает Lance Namespace и таблицы непосредственно из каталога warehouse.

СвойствоОбязательноОписание
warehouseДаКорневой путь warehouse Lance. Поддерживаются локальные абсолютные пути, URI file://, URI s3:// и URI oss://.

Эти два свойства служат разным целям:

  • fs.s3.support=true явно выбирает разбор конфигурации S3. AWS S3 обычно можно определить по свойствам. Для MinIO, пользовательских endpoint или OSS, доступного через его S3-совместимый API, задайте свойство явно, чтобы избежать ошибки определения или выбора другого типа хранилища по домену. Все примеры S3 ниже включают это свойство для непосредственного использования.
  • use_path_style управляет расположением bucket в URL запросов и по умолчанию имеет значение false. Значение true использует endpoint/bucket/object-path; значение false использует доступ в стиле virtual-hosted. В текущем клиенте S3 по умолчанию в Lance явно заданный endpoint в стиле virtual-hosted должен содержать bucket. Устанавливайте это свойство вместе с endpoint в соответствии со стилем доступа, поддерживаемым сервисом.
Сценарий доступаНастройка типа хранилищаuse_path_styleФормат endpoint
AWS S3Рекомендуется: fs.s3.support=truefalse; можно опуститьВключает bucket, например https://my-bucket.s3.us-east-1.amazonaws.com.
MinIO (доступ через домен сервиса или IP)Задайте fs.s3.support=trueЯвно задайте trueАдрес сервиса без bucket, например http://minio.example.com:9000.
S3-совместимый API OSSЗадайте fs.s3.support=truefalse; в примере задан явноВключает bucket, например https://my-bucket.oss-cn-beijing.aliyuncs.com.
Нативный API OSSРекомендуется: fs.oss.support=true; не задавайте fs.s3.supportОбщий use_path_style задавать не нужноИспользуйте oss.endpoint без bucket, например https://oss-cn-beijing.aliyuncs.com.

Эти правила endpoint S3 применяются к пути доступа S3 по умолчанию в Lance. Для Filesystem Catalog с одним типом хранилища задавайте только соответствующий fs.*.support=true; не включайте несколько типов хранилища, чтобы «включить совместимость». Это свойство выбирает разбор конфигурации, но не добавляет сервису хранилища поддержку протокола.

Выберите пример, соответствующий системе хранения warehouse, и замените bucket, путь, адрес и учётные данные:

  • AWS S3
  • MinIO (Path Style)
  • Alibaba Cloud OSS (S3-Compatible Access)
  • Alibaba Cloud OSS (Native Access)
  • Local File System
CREATE CATALOG lance_fs_s3 PROPERTIES (
    "type" = "lance",
    "lance.catalog.type" = "filesystem",
    "warehouse" = "s3://my-bucket/lance",
    "fs.s3.support" = "true",
    "use_path_style" = "false",
    "s3.endpoint" = "https://my-bucket.s3.us-east-1.amazonaws.com",
    "s3.region" = "us-east-1",
    "s3.access_key" = "<ak>",
    "s3.secret_key" = "<sk>"
);

В этом примере используется endpoint AWS S3, содержащий bucket, с use_path_style=false. Текущая проверка свойств S3 в Doris требует endpoint; при использовании показанного URI s3://my-bucket/... указать только region недостаточно. При изменении bucket или region обновляйте endpoint.

CREATE CATALOG lance_fs_minio PROPERTIES (
    "type" = "lance",
    "lance.catalog.type" = "filesystem",
    "warehouse" = "s3://my-bucket/lance",
    "fs.s3.support" = "true",
    "s3.endpoint" = "http://minio.example.com:9000",
    "s3.region" = "us-east-1",
    "use_path_style" = "true",
    "s3.access_key" = "<ak>",
    "s3.secret_key" = "<sk>"
);

В этом примере доступ к MinIO осуществляется через домен сервиса с запросами в стиле path, без отдельного поддомена для каждого bucket. Не включайте bucket в endpoint и замените region значением, настроенным для сервиса. Если включён TLS, используйте соответствующий endpoint https:// и убедитесь, что FE и все BE могут его достичь.

Для доступа к OSS через его S3-совместимый API используйте warehouse s3:// и свойства подключения s3.*:

CREATE CATALOG lance_fs_oss_s3 PROPERTIES (
    "type" = "lance",
    "lance.catalog.type" = "filesystem",
    "warehouse" = "s3://my-bucket/lance",
    "fs.s3.support" = "true",
    "s3.endpoint" = "https://my-bucket.oss-cn-beijing.aliyuncs.com",
    "s3.region" = "cn-beijing",
    "use_path_style" = "false",
    "s3.access_key" = "<ak>",
    "s3.secret_key" = "<sk>"
);

В этом примере задано use_path_style=false для доступа в стиле virtual-hosted. Текущий клиент S3 по умолчанию в Lance не добавляет bucket автоматически к явно заданному endpoint, поэтому s3.endpoint должен содержать bucket, например https://my-bucket.oss-cn-beijing.aliyuncs.com; warehouse оставьте как s3://my-bucket/lance. Для доступа через внутреннюю сеть используйте https://my-bucket.oss-cn-beijing-internal.aliyuncs.com и убедитесь, что FE и BE могут его достичь.

Для временных учётных данных STS добавьте "s3.session_token" = "<token>". Этот режим читает существующие данные OSS через S3-совместимый API без перемещения данных. Для нативного доступа OSS см. соседний пример нативного OSS.

CREATE CATALOG lance_fs_oss PROPERTIES (
    "type" = "lance",
    "lance.catalog.type" = "filesystem",
    "warehouse" = "oss://my-bucket/lance",
    "fs.oss.support" = "true",
    "oss.endpoint" = "https://oss-cn-beijing.aliyuncs.com",
    "oss.region" = "cn-beijing",
    "oss.access_key" = "<ak>",
    "oss.secret_key" = "<sk>"
);

Для временных учётных данных STS добавьте "oss.session_token" = "<token>". Квалифицированная форма oss://my-bucket.oss-cn-beijing.aliyuncs.com/lance также принимается и нормализуется к пути bucket. OSS-HDFS в настоящее время не поддерживается.

CREATE CATALOG lance_fs_local PROPERTIES (
    "type" = "lance",
    "lance.catalog.type" = "filesystem",
    "warehouse" = "/data/lance"
);

warehouse должен быть абсолютным путём. FE и каждый BE, выполняющий запрос, должны обращаться к одному и тому же пути. В мног узловом развёртывании подключите один общий каталог на всех соответствующих узлах.

Для S3 и OSS warehouse должен содержать bucket, например s3://bucket/path или oss://bucket/path.

REST Catalog​

REST Catalog получает Namespace, расположение таблиц и параметры доступа к хранилищу через Lance REST Namespace. REST Catalog не требует и не допускает свойство warehouse.

СвойствоОбязательноПо умолчаниюОписание
lance.rest.uriДа-URI REST-сервиса. Должен использовать http:// или https://.
lance.rest.security.typeНетnoneТип аутентификации. Допустимые значения: none, bearer и api_key.
lance.rest.bearer-tokenДа для Bearer-аутентификации-Bearer Token.
lance.rest.api-keyДа для аутентификации API Key-API Key, отправляемый в заголовке x-api-key.
lance.rest.header.<header-name>Нет-Пользовательский HTTP-заголовок, отправляемый REST-сервису. Для заголовков аутентификации используйте специальные свойства аутентификации выше.

Аутентификация REST-сервиса и аутентификация объектного хранилища разделены: lance.rest.* подключает сервис Namespace, а s3.* / oss.* позволяют FE и BE читать данные таблиц. Путь доступа определяется URI таблицы, возвращённым Namespace: s3:// использует S3, а oss:// — нативный доступ OSS. Выберите свойства хранилища по умолчанию в соответствии с возвращаемыми URI таблиц:

  • AWS S3
  • MinIO (Path Style)
  • Alibaba Cloud OSS (S3-Compatible Access)
  • Alibaba Cloud OSS (Native Access)
CREATE CATALOG lance_rest_s3 PROPERTIES (
    "type" = "lance",
    "lance.catalog.type" = "rest",
    "lance.rest.uri" = "https://lance.example.com",
    "lance.rest.security.type" = "bearer",
    "lance.rest.bearer-token" = "<token>",
    "fs.s3.support" = "true",
    "use_path_style" = "false",
    "s3.endpoint" = "https://my-bucket.s3.us-east-1.amazonaws.com",
    "s3.region" = "us-east-1",
    "s3.access_key" = "<ak>",
    "s3.secret_key" = "<sk>"
);

Для таблиц AWS s3://my-bucket/..., возвращаемых Namespace. Endpoint по умолчанию должен содержать этот bucket и соответствовать region. Таблицам в разных bucket нужны соответствующие endpoint, как описано ниже.

CREATE CATALOG lance_rest_minio PROPERTIES (
    "type" = "lance",
    "lance.catalog.type" = "rest",
    "lance.rest.uri" = "https://lance.example.com",
    "lance.rest.security.type" = "bearer",
    "lance.rest.bearer-token" = "<token>",
    "fs.s3.support" = "true",
    "s3.endpoint" = "http://minio.example.com:9000",
    "s3.region" = "us-east-1",
    "use_path_style" = "true",
    "s3.access_key" = "<ak>",
    "s3.secret_key" = "<sk>"
);

Для таблиц MinIO s3://, возвращаемых Namespace. Используйте endpoint сервиса, доступный и FE, и BE, без bucket. use_path_style=true помещает bucket каждой таблицы в путь запроса. Region должен соответствовать конфигурации сервиса MinIO.

CREATE CATALOG lance_rest_oss_s3 PROPERTIES (
    "type" = "lance",
    "lance.catalog.type" = "rest",

Для нативного доступа OSS Namespace может выдавать oss_endpoint, oss_access_key_id, oss_secret_access_key, oss_region и oss_security_token либо соответствующие нативные имена endpoint, access_key_id, access_key_secret, region и security_token.

Если REST Namespace управляет версиями таблицы (managed_versioning = true в DescribeTable), Doris разрешает последнюю версию и любой селектор time travel через API версий Namespace и читает соответствующий manifest из хранилища. Подробности см. в разделе Time Travel.

Time Travel​

Каждая фиксация набора данных Lance создаёт новую версию, нумерация начинается с 1. Запрос может читать историческую версию вместо последней:

-- Read version 2 of the table.
SELECT * FROM lance_catalog.db.tbl FOR VERSION AS OF 2;

-- Read the latest version committed at or before the given time.
SELECT * FROM lance_catalog.db.tbl FOR TIME AS OF '2026-09-19 13:06:10';
  • FOR VERSION AS OF принимает положительное целое — номер версии или, как для таблиц Paimon и имён tag в Iceberg, имя tag в кавычках (FOR VERSION AS OF 'v2' эквивалентно @tag(v2)).
  • FOR TIME AS OF принимает timestamp в часовом поясе сеанса с точностью до секунды или миллисекунды (yyyy-MM-dd HH:mm:ss или yyyy-MM-dd HH:mm:ss.SSS). Среди версий, зафиксированных не позднее timestamp, Doris выбирает версию с самым поздним временем фиксации, записанным в её manifest (если версии зафиксированы в один момент, выбирается более новая). Как и при выборе снимка по времени в Iceberg, сравниваются записанные времена фиксации; не предполагается, что они растут вместе с номерами версий. Lance записывает время фиксации с точностью меньше миллисекунды и сравнивает его полностью: версия, зафиксированная позже в пределах запрошенной миллисекунды, не выбирается. Версия, удалённая очисткой, удаляет и своё время фиксации, поэтому Doris, как Iceberg при удалении журнала снимков перед просроченным снимком, рассматривает только версии новее последней удалённой. Timestamp, более ранний, чем все такие версии, вызывает ошибку: он может быть раньше первой версии или находиться в истории, удалённой очисткой (например, между версией, сохранённой tag, и следующей оставшейся версией), где состояние таблицы неизвестно.
  • Выбранная версия фиксируется для всего оператора: schema, планирование Fragment, передача предикатов и сканирование BE используют её. Две ссылки на одну таблицу в одном операторе могут выбрать разные версии. EXPLAIN показывает выбранную версию как lanceVersion.
  • Версии, удалённые cleanup_old_versions Lance, нельзя читать; они сообщаются так же, как версии, которых никогда не существовало. Для таблицы, версии которой управляются REST Namespace, см. раздел ниже.
  • vector_search() и full_text_search() выбирают версию, время, tag или branch собственными параметрами version, timestamp, tag и branch; см. Поиск исторической версии или branch. Аргумент table не может содержать FOR VERSION AS OF, @tag или @branch.
  • Проверка индексов (SHOW INDEX, lance_index_entries()) всегда использует последнюю версию main и не показывает индексы исторической версии или branch.

Tag и branch Lance выбираются тем же синтаксисом, что и для таблиц Iceberg и Paimon:

-- Read the version the tag "v2" points at.
SELECT * FROM lance_catalog.db.tbl@tag(v2);

-- Read the latest version of the branch "dev".
SELECT * FROM lance_catalog.db.tbl@branch(dev);

-- Read version 2 of the branch "dev".
SELECT * FROM lance_catalog.db.tbl@branch(dev) FOR VERSION AS OF 2;
  • Tag указывает на версию в branch, и чтение tag выбирает эту версию branch: tag, созданный в dev, читает dev, а не версию с тем же номером в main. @tag нельзя сочетать с FOR VERSION AS OF или FOR TIME AS OF.
  • @branch(main) читает main, то же самое, что отсутствие @branch.
  • Каждый branch имеет собственную последовательность версий, начиная с версии, от которой он создан. FOR VERSION AS OF / FOR TIME AS OF после @branch выбирают только среди версий этого branch, поэтому timestamp до создания branch не выбирает на нём ничего. После @branch, включая @branch(main), FOR VERSION AS OF не может задавать tag, поскольку tag уже определяет branch.
  • Branch хранится в <table>/tree/<branch>/ как shallow clone таблицы, manifest которой записывает расположение таблицы как абсолютный URI. Поэтому branch читается только в месте, где он был создан: после копирования или перемещения набора данных main остаётся читаемым, а branch — нет.
  • Branch с удалёнными метаданными или прерванным созданием остаётся читаемым через @branch, пока его каталог под tree/ не очищен, потому что Lance SDK проверяет branch по его каталогу. Для таблицы с версиями, управляемыми REST Namespace, существование branch определяет Namespace, а branch читается из собственного каталога без чтения main.
  • EXPLAIN показывает читаемый branch как lanceBranch. Несуществующий tag или branch вызывает ошибку.

Версионирование, управляемое REST Namespace​

REST Namespace может самостоятельно управлять версиями таблицы (managed_versioning = true в ответе DescribeTable). Для такой таблицы Namespace определяет существующие версии и последнюю версию: последняя версия и FOR VERSION AS OF следуют записям Namespace (ListTableVersions, DescribeTableVersion), FOR TIME AS OF разрешается по временам фиксации, записанным manifest, и выбирается только среди версий, перечисленных Namespace, tag читается из _refs/tags/ набора данных как для любой таблицы Lance и должен указывать на версию, записанную Namespace, а версии branch также следуют Namespace. После выбора версии FE и BE читают её из хранилища по расположению таблицы и номеру версии, как для любой другой таблицы Lance.

  • Версия, не записанная Namespace, считается отсутствующей, даже если её manifest всё ещё существует в хранилище; последняя версия — это последняя версия Namespace, даже если в хранилище уже есть более новый manifest.
  • Версия, которую Namespace больше не записывает, но между ней есть записанные версии, считается удалённой историей для FOR TIME AS OF, как версия, удалённая очисткой: timestamp, который может относиться к этой версии, вызывает ошибку вместо выбора более старой версии.
  • Таблица или branch, для которых Namespace не записывает ни одной версии, вызывают ошибку, даже если в хранилище существуют manifest.
  • Для таких таблиц EXPLAIN показывает lanceManagedVersioning=true.

Ограничения:

  • Doris читает набор данных по table_uri, возвращённому DescribeTable, или по location, если table_uri отсутствует; любое из них должно быть полным URI хранилища. Если location пуст, либо возвращённый вместе с ним table_uri указывает в другое место (за исключением строки запроса, например подписанных учётных данных), запрос завершается ошибкой и ничего не читает. URI s3+ddb также отклоняется: его обработчик фиксаций DynamoDB записывал бы и завершал версии при чтении. Doris описывает управляемую таблицу при каждом чтении вместо кэширования, а FE и BE читают с расположением и конфигурацией хранилища, возвращёнными этим описанием.
  • Doris читает версию по её номеру по каноническому пути _versions/<u64::MAX - version>.manifest в каталоге таблицы (или в tree/<branch>/ для branch), либо по _versions/<version>.manifest в старой схеме именования Lance. Manifest, который Namespace записывает для выбранной версии, должен находиться по этому пути или быть staged manifest рядом с ним (<canonical path>-<id>); при FOR TIME AS OF manifest каждой версии, записанной на main или branch, также должен соответствовать этому правилу, поскольку времена фиксации определяют выбор. Версию, записанную в другом месте, прочитать нельзя: запрос завершается ошибкой с указанием записанного и канонического путей. Если Namespace перемещает таблицу во время выполнения запроса, запрос может завершиться такой же ошибкой и пройти после повторной попытки.
  • Версия, которую Namespace записывает только в staged manifest, когда канонический manifest отсутствует, не читается: фиксация не завершена либо очистка удалила версию. Запрос завершается ошибкой и называет обе причины. FOR TIME AS OF на этом main или branch завершается ошибкой для любого timestamp, который может охватывать версию, поскольку её время фиксации неизвестно; для самой новой версии это любой timestamp до тех пор, пока writer или другой reader, использующий Namespace, не завершит её. Чтение таблицы без FOR VERSION AS OF и загрузка её schema также завершаются ошибкой. Собственные реализации Namespace Lance завершают версию до её записи, поэтому незавершённая версия появляется только после прерванной фиксации или в Namespace, записывающем staged manifest. Doris никогда не записывает таблицу при чтении.

Проверка индексов Lance​

Для таблицы в Filesystem Catalog SHOW INDEX отображает логические скалярные индексы (включая инвертированные FTS-индексы) и векторные индексы, записанные в наборе данных Lance. Варианты SHOW INDEXES, SHOW KEY и SHOW KEYS дают тот же результат:

SHOW INDEX FROM lance_catalog.default.items;

Doris читает метаданные индексов из последнего снимка набора данных во время выполнения и сортирует результат по имени индекса и позиции столбца. Системные индексы, которые Lance поддерживает внутри, например __lance_frag_reuse и __lance_mem_wal, не отображаются. Таблица без индексов возвращает пустой результат.

SHOW INDEX возвращает стандартный набор из 13 столбцов. Для таблицы Lance значения имеют только следующие столбцы; остальные всегда пусты:

СтолбецЗначение для таблицы Lance

Key_nameИмя логического индекса Lance.
Seq_in_indexПозиция столбца в индексе, начиная с 1. Индекс по нескольким полям даёт одну строку для каждого поля.
Column_nameИндексируемое поле. Индекс вложенного поля отображает путь, соединённый через ., а сегмент пути с символами, отличными от букв, цифр и _, заключает в обратные кавычки, например attributes.`child.with.dot`.

примечание

lance_index_entries поддерживается начиная с Apache Doris 4.1.5.

lance_index_entries читает метаданные индексов только через Dataset.getIndexes(). Она не читает количество строк или статистику и не изменяет набор данных. Результат можно фильтровать обычными предикатами, например WHERE IndexName = .... Строки сортируются по (IndexName, IndexUuid). Чтение полностью проверяется по принципу all-or-error: пустое или слишком длинное имя, отсутствующий UUID, неположительное DatasetVersion, дублирующийся UUID или количество необработанных записей более 16,384 приводят к сбою всего запроса вместо усечённого результата. Зарезервированные системные индексы Lance __lance_frag_reuse и __lance_mem_wal проверяются, но не отображаются.

Для lance_index_entries требуется привилегия SHOW на таблицу. Для REST Catalog TVF отклоняется с ошибкой lance_index_entries is not supported for Lance REST catalogs.

Передача предикатов​

SELECT user_id
FROM lance_catalog.default.user_profiles
WHERE active
  AND starts_with(name, 'A')
  AND country LIKE 'C%';

Предикаты меток массивов​

Начиная с Apache Doris 4.1.5 передача меток массива поддерживает array_contains для прямого столбца Lance list<utf8> с не-NULL строковым литералом. Более старые сборки могут оставить эти условия в Doris; перед использованием оптимизации проверьте EXPLAIN. NULL-массив по-прежнему даёт NULL, пустой массив не соответствует, а повторяющиеся метки не дублируют строки результата.

Для таблицы Lance со столбцом id и столбцом labels типа list<utf8>:

EXPLAIN
SELECT id
FROM lance_catalog.default.items
WHERE array_contains(labels, 'red')
  AND array_contains(labels, 'blue');

Это соответствует массивам, содержащим обе метки, независимо от порядка и соседства. Замена AND на OR соответствует любой из меток. NOT (array_contains(labels, 'red')) также преобразуется и сохраняет семантику SQL NULL. Эти примеры относятся к обычному сканированию таблицы и не изменяют различие между параметром filter поисковой TVF и внешним условием WHERE.

Следующие условия остаются остаточными предикатами Doris:

  • array_contains(labels, NULL): Doris может сопоставить элемент массива NULL; функция проверки принадлежности Lance имеет другую семантику NULL-needle.
  • array_contains_all(labels, ['red', 'blue']): Doris проверяет упорядоченную непрерывную подпоследовательность. Её нельзя заменить функцией проверки включения множества Lance или двумя независимыми предикатами принадлежности.
  • Динамические needle, выражения или приведения вокруг столбца массива и другие типы элементов/контейнеров массивов, включая large_list, списки фиксированного размера и list<large_utf8>.

Передача предикатов и использование скалярного индекса​

Передача предиката означает, что условие вычисляет Lance; она не гарантирует использование индекса. Для обычных сканирований Doris может назначить каждому заданию физический сегмент BTree, Bitmap или LabelList. Комбинации IN, AND, OR и NOT для одного столбца могут использовать выбранный индекс, если Lance поддерживает полное выражение. Для OR нужны безопасные кандидаты из обеих ветвей; NOT не может инвертировать частично вычисленное поддерево. Неподдерживаемые индексные выражения возвращаются к сканированию внутри назначенного домена Fragment.

Каждая задача выбирает один логический скалярный индекс. Запрос, объединяющий условия по метке, категории и числу, не означает, что Doris пересечёт все три индекса. Полное переданное условие перепроверяется до применения ограничения сканирования, а Fragment вне покрытия индекса всё равно читаются. Без пригодного индекса совместимые предикаты всё равно могут быть переданы и вычислены сканированием Lance.

Используйте вместе следующие признаки:

ПризнакЗначение
lancePushdownPredicate в EXPLAINУсловия, отправленные в Lance. Оставшиеся условия predicates: вычисляет Doris.
lanceScalarIndexScan=SEGMENT и lanceGroupingIndex в EXPLAINСпланировано сканирование скалярного сегмента и указан выбранный логический индекс. Само по себе это не доказывает использование индекса во время выполнения.
LanceScalarIndexSegmentsSearched в ProfileФактические поиски на инструментированном пути скалярного сегмента.
LanceScalarIndexCandidateRows в ProfileКандидатные строки, сообщённые этим путём, не обязательно конечные строки результата. Маски дополнения, например некоторые выражения NOT, могут не сообщать количество кандидатов.
LanceScalarIndexSegmentFallbacks в ProfileЗадачи, перешедшие с запланированного пути скалярного сегмента на резервный.

Включите enable_profile, чтобы просматривать эти счётчики. При измерении оптимизации сравнивайте один и тот же SQL, проекцию, версию набора данных и состояние кэша. Эти счётчики описывают обычные сканирования скалярных сегментов и не должны использоваться отдельно для вывода об использовании скалярного индекса внутри предварительной фильтрации ANN или полнотекстового поиска.

Передача Runtime Filter​

Когда обычная таблица Lance участвует в соединении, Doris может преобразовать некоторые Runtime Filter, созданные на стороне построения соединения, в условия SQL Lance и применять их во время чтения данных Lance. Это может уменьшить объём данных, возвращаемых Doris, особенно при соединении большой таблицы с таблицей стороны построения с высокой селективностью.

SELECT l.user_id, l.name
FROM lance_catalog.default.user_profiles l
JOIN internal.demo.allowed_users a
  ON l.user_id = a.user_id;

В настоящее время могут передаваться следующие Runtime Filter:

Runtime FilterФорма, передаваемая в Lance
IN Filtercolumn IN (...)
Min/Max Filtercolumn >= min_value, column <= max_value или оба условия

Столбец и значения Runtime Filter должны безопасно преобразовываться в скалярные типы, поддерживаемые SQL Lance. Другие типы Runtime Filter, IN Filter с NULL и типы или значения, которые нельзя безопасно преобразовать, не передаются. Doris по-прежнему вычисляет Runtime Filter, который не был передан, поэтому корректность запроса сохраняется; теряется только выигрыш ранней фильтрации в Lance.

Только Runtime Filter, готовый до создания Lance Scanner, может быть включён в условия, переданные этому Scanner. Runtime Filter, прибывший позже, всё равно вычисляется Doris, но может не попасть в уже созданный Scanner.

Условия Runtime Filter объединяются с условиями Substrait, созданными из обычных SQL-предикатов; одно не заменяет другое. Запись runtime filters в EXPLAIN показывает запланированные Runtime Filter. Когда передан хотя бы один Runtime Filter, LanceRuntimeFilterPushedIds и LanceRuntimeFilterSkippedIds в Runtime Profile показывают идентификаторы переданных и пропущенных Filter.

Передача Runtime Filter применяется только к сканированию обычных таблиц Lance. Она не используется при генерации кандидатов vector_search() или полнотекстового поиска.

Запрос Lance с файловыми TVF​

Если нужно только прочитать набор данных Lance по известному пути, можно использовать TVF s3() или local() без создания Catalog. uri или file_path должны указывать на корневой каталог набора данных Lance, а не на внутренний файл данных.

S3 TVF​

TVF s3() использует S3-совместимый API. Для OSS используйте свойства s3.* и endpoint в стиле virtual-hosted, содержащий bucket. Для нативного доступа OSS используйте пример OSS Catalog выше. Следующий SQL читает первые 10 строк примерного набора данных; перед выполнением замените адрес, учётные данные и имена столбцов:

  • AWS S3
  • MinIO (Path Style)
  • Alibaba Cloud OSS (S3-Compatible Access)
SELECT user_id, name
FROM s3(
    "uri" = "s3://my-bucket/lance/user_profiles.lance",
    "format" = "lance",
    "fs.s3.support" = "true",
    "use_path_style" = "false",
    "s3.endpoint" = "https://my-bucket.s3.us-east-1.amazonaws.com",
    "s3.region" = "us-east-1",
    "s3.access_key" = "<ak>",
    "s3.secret_key" = "<sk>"
)
ORDER BY user_id
LIMIT 10;

Явно задайте endpoint также для AWS S3. В этом примере используется доступ в стиле virtual-hosted; bucket и region в endpoint должны соответствовать URI и s3.region.

SELECT user_id, name
FROM s3(
    "uri" = "s3://my-bucket/lance/user_profiles.lance",
    "format" = "lance",
    "fs.s3.support" = "true",
    "s3.endpoint" = "http://minio.example.com:9000",
    "s3.region" = "us-east-1",
    "use_path_style" = "true",
    "s3.access_key" = "<ak>",
    "s3.secret_key" = "<sk>"
)
ORDER BY user_id
LIMIT 10;

Используйте endpoint сервиса MinIO без bucket и задайте use_path_style=true. И FE, и BE, выполняющие запрос, должны иметь доступ к сервису; не используйте адрес, доступный только с хоста FE.

SELECT user_id, name
FROM s3(
    "uri" = "s3://my-bucket/lance/user_profiles.lance",
    "format" = "lance",
    "fs.s3.support" = "true",
    "s3.endpoint" = "https://my-bucket.oss-cn-beijing.aliyuncs.com",
    "s3.region" = "cn-beijing",
    "use_path_style" = "false",
    "s3.access_key" = "<ak>",
    "s3.secret_key" = "<sk>"
)
ORDER BY user_id
LIMIT 10;

В этом примере используются те же настройки S3-совместимого OSS, что и для Filesystem Catalog, но uri указывает на конкретный набор данных .lance, тогда как warehouse указывает на каталог с наборами данных. Сохраните fs.s3.support=true и use_path_style=false и убедитесь, что bucket endpoint соответствует URI.

Для OSS uri из примера также можно записать как oss://my-bucket/lance/user_profiles.lance, сохранив те же свойства s3.* и fs.s3.support=true. TVF нормализует URI в s3:// и не переключается на нативный провайдер OSS. Не копируйте напрямую конфигурацию oss.* из нативного Catalog OSS: endpoint без bucket в сочетании с доступом virtual-hosted может сообщить, что набор данных не существует, а переход к стилю path может быть отклонён OSS с ошибкой SecondLevelDomainForbidden.

Для S3 TVF FE получает Schema, текущую версию и список Fragment. Doris фиксирует эту версию и параллельно сканирует её Fragment. EXPLAIN показывает VTVF_SCAN_NODE; несколько split могут совместно использовать URI набора данных и различаются идентификаторами Fragment. totalFileSize=0 или length=0 — это заполнитель для split Lance, а не признак пустого набора данных или повторного сканирования всей таблицы каждым split.

Local TVF​

SELECT user_id, name
FROM local(
    "file_path" = "/data/lance/user_profiles.lance",
    "backend_id" = "10001",
    "format" = "lance"
);

file_path передаётся в Lance Reader на целевом BE без изменений. Doris не добавляет user_files_secure_path и не раскрывает этот путь как Glob, поэтому он должен напрямую указывать на корневой каталог одного набора данных Lance, доступный целевому BE. Рекомендуется использовать абсолютный путь.

Обнаружение Schema и выполнение Local TVF независимо открывают последнюю версию набора данных. Версия, разрешённая при обнаружении Schema, в настоящее время не фиксируется для последующего сканирования. Если набор данных изменится между анализом и выполнением запроса, обнаруженная Schema и сканируемый снимок могут различаться. Не изменяйте набор данных во время анализа и выполнения запроса Local TVF. Текущий Local Lance TVF использует один Scanner.

Файловые TVF Lance имеют следующие дополнительные ограничения:

  • Поддерживаются только s3() и local(). Другие файловые TVF, такие как HDFS и HTTP, в настоящее время не поддерживаются.
  • path_partition_keys не поддерживается.
  • Один путь TVF может представлять только один набор данных Lance.
  • DESC FUNCTION может показать Schema с неподдерживаемыми типами, но SQL не может проецировать неподдерживаемые столбцы.

Векторный поиск​

В сборках с автоматическим поиском Lance Doris 4.2 подходящий обычный SQL также может использовать нативный векторный Top-N и поиск MATCH/BM25. Пять приближённых функций, преобразование метрик, семантика входных данных и границы JOIN/EXISTS описаны в разделе Автоматический поиск из обычного SQL. Приведённые ниже TVF остаются интерфейсом для явной настройки поиска и поддерживаемых форм, не охватываемых автоматической переписью.

vector_search() — реляционная TVF, выполняющая поиск Top-K по векторному столбцу таблицы Lance. Она может использовать существующий векторный индекс Lance или выполнять Flat Search.

Синтаксис и пример​

SELECT user_id, label, _distance
FROM vector_search(
    "table" = "lance_catalog.default.items",
    "column" = "embedding",
    "query_vector" = "[0.1, 0.2, 0.3, 0.4]",
    "top_k" = "10",
    "offset" = "3",
    "metric" = "l2",
    "nprobes" = "20",
    "refine_factor" = "10",
    "prefilter" = "true",
    "filter" = "category = 'book'",
    "use_index" = "true"
)
ORDER BY _distance ASC, user_id;

Схема отношения vector_search() содержит все столбцы исходной таблицы Lance и столбец _distance, созданный Lance Scanner для запроса ближайших соседей. Конечный SQL-результат содержит только столбцы, выбранные в SELECT. Doris предоставляет _distance как FLOAT. Это расстояние, а не общий показатель сходства: меньшее значение означает большую близость векторов. Исходная таблица не должна уже содержать столбец _distance. SQL-отношение не гарантирует порядок отображения, поэтому для детерминированного порядка ближайших соседей явно задавайте ORDER BY _distance ASC. Для строк с одинаковым расстоянием рекомендуется добавить уникальный столбец как tie-breaker.

table должен разбираться ровно как три части имени catalog.database.table. Многоуровневый Lance Namespace отображается в одно имя базы данных Doris, содержащее ., поэтому часть базы данных заключайте в обратные кавычки. Например, для таблицы items в Namespace doris.analytics используйте:

"table" = "lance_catalog.`doris.analytics`.items"

Не используйте форму без кавычек lance_catalog.doris.analytics.items: она разбирается как четыре части имени и отклоняется. Имя только таблицы или имя database.table также отклоняется.

Если не задано, Lance начинает с одного раздела и может проверять дополнительные, когда prefilter=true оставляет слишком мало кандидатов. Явная установка N фиксирует и минимальное, и максимальное число проверок равным N.
refine_factorНетОдин вектор: отключено; несколько векторов: 1Множитель уточнения кандидатов. Должен быть положительным целым. Для поиска по одному вектору при отсутствии параметра Lance не пересчитывает расстояния по исходным векторам, поэтому _distance квантованного индекса может быть приближённым. При значении N Lance сначала получает (top_k + offset) × N кандидатов, вычисляет для них точные расстояния по исходным векторам и переупорядочивает их. Уточнение читает исходные векторные данные для этих кандидатов. При увеличении N читается и вычисляется больше кандидатов, что может значительно увеличить I/O и снизить производительность запроса. Для поиска по одному вектору значение 1 включает уточнение и отличается от отсутствия параметра. Поиск по нескольким векторам всегда уточняет кандидатов по исходным значениям с множителем по умолчанию 1.

approx_modeНетНативное значение по умолчанию, сейчас normalСтроковая политика приближённого поиска: fast, normal или accurate; регистр и внешние пробелы игнорируются. Другие значения, включая числовые строки, отклоняются. Применяется к запросам с одним и несколькими векторами. См. Выбор режима приближения.

version, timestamp, tag, branchНет-Поиск исторической версии, версии на момент времени, tag или branch вместо последней версии main. См. Поиск исторической версии или branch.

Если metric не задана, для индексированного пути и Flat Search выбирается l2. Для столбцов uint8 явно задавайте "metric" = "hamming"; значение l2 по умолчанию не поддерживается. Поиск по нескольким векторам также подчиняется описанным ниже бюджетам кандидатов.

Выбор режима приближения​

Начните с normal как базовой линии. approx_mode изменяет политику нативного алгоритма поиска; эффект зависит от выбранного индекса и пути выполнения. Он не изменяет nprobes, ef, refine_factor, сохранённый индекс или план split. Если параметр опущен, сохраняется значение Lance по умолчанию, сейчас normal.

примечание

Эта опция требует сборки Doris, содержащей реализацию режима приближения. Подробности ниже описывают нативную ревизию Lance, использованную этой реализацией. Более старые FE отклоняют свойство, а более старые BE игнорируют необязательное поле. Во время плавного обновления FE отклоняет явно заданные fast или accurate, если любой BE в пуле кандидатов запроса помечен как старый источник обновления, предотвращая использование разных политик в разных split. Ошибка указывает BE и запрошенный режим. Завершите обновление этих BE либо опустите параметр/используйте normal; отсутствие параметра и явное normal сохраняют нативное значение по умолчанию и совместимы с такими источниками обновления. Перед использованием режимов, отличных от значения по умолчанию, обновите все участвующие FE и BE; эта проверка не обнаруживает произвольные старые сборки, не помеченные как источники плавного обновления.

Рекомендуемый порядок настройки:

  1. Зафиксируйте один и тот же снимок набора данных, набор запросов, metric, фильтры и покрытие индекса. Используйте use_index=false, чтобы получить точный Top-K по тем же подходящим строкам; условия отбора поместите в filter TVF и задайте prefilter=true.
  2. Установите базовую линию normal. Измерьте Recall@K, количество результатов, ошибку оценки при необходимости и медианную задержку/p95.
  3. Если recall недостаточен, настройте IVF nprobes и HNSW ef. Если нужны оценки по исходным векторам или больше кандидатов для переранжирования, задайте refine_factor, учитывая дополнительные чтения и вычисления.
  4. Зафиксировав остальные параметры, сравните fast для отфильтрованного HNSW или accurate для точности оценки RabitQ. Выбирайте режим только при достижении целевого качества и измеримой полезной выгоде. Отдельно измеряйте холодный и тёплый кэш.

Включение ACORN для отфильтрованного HNSW​

Выбранный совместимый индекс должен содержать граф HNSW. Задайте approx_mode="fast" и поместите предикат внутрь TVF с prefilter="true". Внешнее WHERE Doris не обеспечивает такую предварительную фильтрацию, а одного use_index=true недостаточно для принудительного выбора индекса HNSW.

Для четырёхмерного embedding, user_id и строкового category из примера синтаксиса, при существующем совместимом индексе L2 HNSW и привилегии SELECT:

SELECT user_id, _distance
FROM vector_search(
    "table" = "lance_catalog.default.items",
    "column" = "embedding",
    "query_vector" = "[0.1,0.2,0.3,0.4]",
    "metric" = "l2",
    "top_k" = "10",
    "filter" = "category = 'book'",
    "prefilter" = "true",
    "use_index" = "true",
    "approx_mode" = "fast",
    "ef" = "64"
)
ORDER BY _distance, user_id;

Этот запрос возвращает до 10 подходящих строк, ранжированных по расстоянию; фактические ID и recall зависят от данных и ANN-поиска. Выполнение EXPLAIN для запроса включает lanceApproxMode=FAST, подтверждая запрошенную политику. Это не доказывает, что каждый подындекс выполнил ACORN.

Текущая нативная реализация отдельно выбирает путь внутри каждого подындекса HNSW (раздела IVF), используя число узлов, прошедших предварительную фильтрацию:

Условие выполненияПуть

Проходит менее примерно 10% узловПлоская оценка оставшихся узлов.

Порог применяется внутри каждого подындекса, а не ко всей таблице. В этом интерфейсе нет отдельного свойства принудительного ACORN. В Doris правила безопасности диапазона расстояния также могут выбрать Flat Search до нативного обхода графа; см. Радиусный и диапазонный поиск.

Радиусный и диапазонный поиск​

Задайте distance_upper_bound для радиусного запроса или обе границы для интервала [lower, upper). Пропущенные границы не ограничивают расстояние. Значение зависит от выбранной метрики: l2 — это квадрат евклидова расстояния, поэтому геометрическому радиусу r соответствует верхняя граница r * r. Допускаются отрицательные границы, что полезно для метрик вроде dot. Границы используют точность FLOAT, даже если сохранённые векторы имеют Float64; не конечные значения, переполнение, равные и обратные границы отклоняются.

Например, для существующей таблицы Lance Catalog lance_catalog.default.items со столбцами user_id и трёхмерным embedding Float32:

user_idembeddingКвадрат расстояния L2 до [0, 0, 0]
1[0, 0, 0]0
2[1, 0, 0]1
3[2, 0, 0]4
SELECT user_id, _distance
FROM vector_search(
    "table" = "lance_catalog.default.items",
    "column" = "embedding",
    "query_vector" = "[0, 0, 0]",
    "metric" = "l2",
    "top_k" = "10",
    "use_index" = "false",
    "distance_lower_bound" = "1",
    "distance_upper_bound" = "4"
)
ORDER BY _distance;
+---------+-----------+
| user_id | _distance |
+---------+-----------+
|       2 |         1 |
+---------+-----------+

Удаление нижней границы также возвращает строку 1. Использование только верхней границы 0 возвращает пустой результат. При prefilter=true filter ограничивает кандидатов до векторного поиска; при значении по умолчанию prefilter=false он фильтрует после генерации кандидатов. offset пропускает результаты после применения диапазона расстояния. Схема результата не меняется: столбцы таблицы плюс _distance типа FLOAT. EXPLAIN показывает lanceDistanceRange=[1.0, 4.0).

Границы расстояния поддерживают параметры ? в подготовленных операторах. Каждое выполнение проверяет и использует собственные значения границ; NULL-границы отклоняются. Чтобы оставить сторону неограниченной, опустите соответствующее свойство.

Это по-прежнему запрос Top-K, а не API для возврата всех строк в радиусе: результаты ограничены top_k и могут содержать меньше строк.

Для диапазонных запросов Doris использует поиск по индексу только тогда, когда заданы обе границы и выбранный индекс явно определён как IVF_FLAT. Односторонние диапазоны, квантованные индексы и индексы с неизвестными подтипами переходят к точному Flat Search даже при use_index=true. EXPLAIN сообщает lanceVectorIndexStatus=DISTANCE_RANGE_FALLBACK, если безопасность диапазона препятствует выбору индекса. Такой переход может увеличить стоимость сканирования.

Запросы по индексированному IVF_FLAT зависят от разделов, выбранных nprobes; для исчерпывающей оценки кандидатов используйте use_index=false. Данные, добавленные вне покрытия индекса, ищутся через Flat Search. Столбцы с несколькими векторами не поддерживают границы расстояния.

Для столбцов с одним вектором Doris поддерживает следующие комбинации векторных индексов Lance. Ограничения для нескольких векторов описаны в разделе Поиск по нескольким векторам.

vector_search() использует только уже существующие в Lance векторные индексы. Он не создаёт индексы и не позволяет задавать тип или имя индекса. При use_index=true Doris автоматически выбирает индекс, совместимый с векторным столбцом и метрикой расстояния. Данные без пригодного индекса, включая данные вне покрытия выбранного индекса, автоматически используют Flat Search и не исключаются. При use_index=false все данные используют Flat Search.

Если совместимы несколько индексов столбца, Doris выбирает один за запрос, первый по имени индекса. Fragment, которые этот индекс не покрывает, используют Flat Search, даже если их покрывает другой индекс, поэтому выполнение всегда соответствует покрытию индекса, показанному EXPLAIN. Индекс, который Doris не может спланировать, например без метаданных покрытия Fragment (lanceVectorIndexStatus=UNKNOWN_COVERAGE), без записанной метрики (METRIC_MISMATCH) или старый индекс без сведений, которые Lance не может вывести из файлов, пропускается (NO_MATCH) и вообще не используется; весь поиск выполняется как Flat Search. Старый индекс, сведения о котором Lance может вывести, используется обычным образом.

Если сноска не говорит иное, «поддерживается» означает работу со всеми шестью типами индексов выше. «Только Flat Search» означает, что векторы можно запрашивать, но векторный индекс не используется.

  1. Построение индекса l2 по данным float16 с большими значениями может быть слишком долгим или завершиться ошибкой. Держите значения векторов в контролируемом диапазоне. Если создание индекса завершается ошибкой, используйте Flat Search или, если это подходит приложению, cosine.
  2. Lance трактует векторы uint8 как бинарные и поддерживает только метрику hamming. Product Quantization и Scalar Quantization не поддерживают uint8, поэтому доступны только IVF_FLAT и IVF_HNSW_FLAT.
  3. Векторы int8 в настоящее время не могут использовать векторный индекс и ограничены Flat Search.

Метрика запроса должна соответствовать метрике индекса​

Метрика metric запроса должна совпадать с метрикой, использованной при построении индекса. В противном случае, если запрошенная метрика поддерживается типом столбца, Doris использует Flat Search. Результаты остаются корректными, но производительность обычно ниже, поскольку векторы сканируются напрямую.

Если metric опущена, Doris учитывает l2 при выборе индекса. Поэтому явно задавайте metric при использовании индекса, построенного с cosine, dot или hamming. Например, для индекса векторов uint8 требуется "metric" = "hamming"; иначе запрос использует неподдерживаемую метрику l2 и завершается ошибкой.

Используйте EXPLAIN для подтверждения использования индекса. Значение lanceSearchIndexSegments, большее 0, означает индексированный поиск, а 0 — Flat Search.

Doris учитывает только один векторный индекс на столбец. Храните не более одного векторного индекса на каждом столбце, чтобы избежать неоднозначного выбора между индексами с разными метриками.

Поиск по нескольким векторам​

Столбец с несколькими векторами хранит несколько подвекторов в каждой строке таблицы, например embeddings токенов документа. Матрица запроса создаёт один ранжированный набор строк таблицы. Это не пакет независимых векторных поисков и не поиск по нескольким столбцам.

Подготовка данных и выполнение запроса​

Используйте приведённый выше пример AWS S3 Filesystem Catalog с Catalog lance_fs_s3 и warehouse s3://my-bucket/lance. Установите Lance Python SDK (pylance) и pyarrow в среде записи. Настройте учётные данные и region S3, например через AWS_ACCESS_KEY_ID, AWS_SECRET_ACCESS_KEY и AWS_DEFAULT_REGION. Writer нужен доступ на запись, а Doris — доступ на чтение в том же месте. Для пользовательских endpoint или других способов аутентификации настройте опции object-store SDK в соответствии с Catalog.

Создайте documents.lance непосредственно под warehouse, чтобы Doris обнаружил его как lance_fs_s3.default.documents. Замените bucket и в Catalog, и в примере Python. Используйте новое расположение набора данных:

import lance
import pyarrow as pa

vector_type = pa.list_(pa.float32(), 2)
schema = pa.schema([
    pa.field("id", pa.int64()),
    pa.field("embeddings", pa.list_(
        pa.field("item", vector_type, nullable=False)
    )),
])
data = pa.Table.from_pylist([
    {"id": 1, "embeddings": [[1.0, 0.0], [0.0, 1.0]]},
    {"id": 2, "embeddings": [[1.0, 0.0]]},
    {"id": 3, "embeddings": []},
    {"id": 4, "embeddings": None},
], schema=schema)
lance.write_dataset(
    data,
    "s3://my-bucket/lance/documents.lance",
    data_storage_version="2.1",
)

Внешний список позволяет каждой строке иметь разное число подвекторов. Внутренний nullable=False обязателен: сам подвектор не может быть null. Выполните запрос к таблице с двумерным JSON-массивом:

SELECT id, _distance
FROM vector_search(
    "table" = "lance_fs_s3.default.documents",
    "column" = "embeddings",
    "query_vector" = "[[1,0],[0,1]]",
    "top_k" = "2",
    "metric" = "l2",
    "use_index" = "false"
)
ORDER BY _distance, id;

Ожидаемый результат:

id_distance
10.0
22.0

Строка 1 содержит идеальное совпадение для каждого подвектора запроса. Строка 2 совпадает с первым подвектором запроса с расстоянием 0, а со вторым имеет квадрат расстояния L2 2. Пустые и null-внешние списки не ранжируются. Добавление "offset" = "1" и изменение "top_k" = "1" возвращает только строку 2. Добавление "filter" = "id > 1" и установка "prefilter" = "true" ограничивает поиск кандидатов подходящими строками и для этого набора данных также возвращает только строку 2.

Оценка на уровне строки​

Для подвекторов запроса Q и сохранённых подвекторов строки V:

_distance = sum(q in Q, min(v in V, distance(q, v)))
metricРасстояние между двумя подвекторами
l2 (по умолчанию)Квадрат евклидова расстояния
cosine1 - cosine_similarity
dot или dot_product1 - dot_product; значение может быть отрицательным

Меньшее _distance лучше. Каждый подвектор запроса вносит вклад один раз, а один сохранённый подвектор может сопоставляться с несколькими подвекторами запроса. Оценки суммируются, а не усредняются; повтор подвектора запроса повторяет его вклад. Тип _distance в Doris — FLOAT, в том числе для входа Float64. top_k и offset считают строки таблицы, а не подвекторы. Строки с одинаковыми значениями на границе Top-K не имеют гарантированного включения или порядка; внешнее ORDER BY упорядочивает только возвращённые строки.

Пусть M — число подвекторов запроса, K = top_k, O = offset, а R = refine_factor (по умолчанию 1 для многовекторного поиска).

Использование индекса и уточнение​

Интегрированная версия Lance поддерживает многовекторные индексы с метрикой cosine. Для использования существующего совместимого индекса, например cosine IVF_FLAT или IVF_PQ, задайте "metric" = "cosine" и оставьте use_index=true. Если metric опущена, выбирается l2; запросы L2 и dot используют Flat Search, когда совместимого индекса нет. Doris не создаёт индексы через эту функцию. Используйте SHOW INDEX (только Filesystem Catalog) для проверки метаданных индекса и EXPLAIN, чтобы убедиться, что lanceSearchIndexSegments > 0.

При индексированном поиске выбор кандидатов приближённый. Кандидаты многовекторного поиска всегда уточняются по исходным векторам, включая случаи, когда refine_factor опущен или равен 1, поэтому индексированные и неиндексированные строки используют одинаковую оценку на уровне строки. Увеличение refine_factor расширяет пул кандидатов, добавляя чтение и вычисления; исчерпывающий recall не гарантируется. nprobes управляет проверкой IVF, а ef применяется к индексам HNSW. Настраивайте их только после измерения recall и задержки. Строки, добавленные после создания индекса, включаются через Flat Search.

Для исчерпывающей оценки выбранных строк используйте "use_index" = "false". Чтобы ограничить кандидатов до поиска, используйте filter TVF с prefilter=true; по умолчанию prefilter=false применяет условие после генерации кандидатов. Внешнее SQL WHERE всегда вычисляет Doris по сгенерированным кандидатам и не пополняет результаты split. Правила фильтрации следующего раздела применяются к поиску и по одному, и по нескольким векторам.

Prefilter и Post-filter​

Prefilter и Post-filter можно использовать в одном запросе:

SELECT user_id, category, _distance
FROM vector_search(
    "table" = "lance_catalog.default.items",
    "column" = "embedding",
    "query_vector" = "[0.1, 0.2, 0.3, 0.4]",
    "top_k" = "10",
    "prefilter" = "true",
    "filter" = "category = 'book'"
)
WHERE user_id > 100
ORDER BY _distance ASC, user_id;
Тип фильтраУсловие примераКогда выполняетсяВлияние на результаты
TVF PrefilterПараметры TVF "filter" = "category = 'book'" и "prefilter" = "true"До генерации Lance векторных кандидатовБлижайшие соседи ищутся только среди строк, где category = 'book'.
TVF Post-filterПараметр TVF "filter" = "category = 'book'", при опущенном prefilter или значении falseПосле генерации Lance кандидатовУдаляет неподходящие строки из сгенерированных кандидатов. Кандидаты не пополняются, поэтому результат может содержать меньше top_k строк.
Doris Scan Post-filterВнешнее WHERE user_id > 100После генерации Lance кандидатов и до применения Doris финального TopNУдаляет неподходящие строки из сгенерированных кандидатов. Кандидаты не пополняются, поэтому результат может содержать меньше top_k строк.

Если user_id > 100 также должно участвовать в генерации кандидатов, включите его в filter TVF и задайте prefilter=true, например "filter" = "category = 'book' AND user_id > 100". При значении prefilter=false по умолчанию условие применяется после генерации кандидатов. Даже если оптимизатор переместит внешнее WHERE в Doris Lance Scan, оно остаётся Doris Scan Post-filter и не преобразуется в Lance Prefilter.

Lance внутренне читает и вычисляет столбцы, на которые ссылается только filter. Если такой столбец не используется в SELECT или другом выражении Doris, возвращать его в Doris не нужно.

Кэш доступа FE к таблицам​

Для этой настройки требуется сборка Doris, содержащая изменение кэша доступа к таблицам.

Каждый FE может кэшировать разрешённый URI Dataset и параметры доступа к таблице внутри Catalog, избегая повторного обнаружения файловой системы или запросов REST describeTable при планировании. Каждый клиент Catalog хранит не более 10,000 записей. lance.table_access_cache_ttl_seconds по умолчанию равен 60; попадания в кэш не продлевают срок жизни. Этот кэш не хранит версии Dataset: каждое чтение по-прежнему открывает Dataset и выбирает его снимок.

Таблица с версионированием, управляемым Namespace, разрешается заново при каждом чтении, поэтому оба reader используют расположение и параметры хранилища, которые Namespace возвращает для этого чтения. Ответ с выданными параметрами хранилища также разрешается заново при каждом чтении, даже если содержит expires_at_millis. URI с userinfo, параметрами запроса (включая presigned/SAS-учётные данные) или fragment также не кэшируются. Фиксированный запас до истечения учётных данных не гарантирует их действительность на протяжении всего сканирования, а BE не может обновить эти учётные данные во время сканирования. REST Catalog без этих полей ответа может использовать кэш.

Явное обновление таблицы или базы данных очищает все записи доступа к таблицам в этом Catalog, включая follower FE, воспроизводящие обновление после вытеснения соответствующего локального объекта базы данных/таблицы. Обычное вытеснение локального объекта базы данных не очищает кэш доступа. Обновление Catalog с инвалидированием кэша, удаление Namespace или изменение конфигурации Catalog также инвалидируют записи доступа. Проверка индекса и проверка цели задания индекса всегда заново разрешают доступ.

После изменения удалённого URI таблицы или конфигурации доступа используйте явное обновление, чтобы не ждать истечения TTL. Для существующей таблицы example_lance.default.items:

REFRESH TABLE example_lance.default.items;

Следующее чтение снова разрешит доступ к таблице. Это не очищает нативный кэш Lance Session; после замены Dataset по тому же URI выполните обновление Catalog с инвалидированием кэша. Оно очищает только Lance Session FE, но не кэши BE; см. Поиск исторической версии или branch.

Чтобы отключить кэш доступа к таблицам для существующего Catalog:

ALTER CATALOG example_lance SET PROPERTIES (
    "lance.table_access_cache_ttl_seconds" = "0"
);

Последующие чтения каждый раз разрешают доступ заново. Кэши BE, описанные ниже, настраиваются независимо.

Lance Cache​

Lance Cache повторно использует содержимое индексов, метаданных и файлов данных, чтобы уменьшить повторные чтения. Каждый BE управляет собственным кэшем, которым пользуются запросы Lance на этом BE. Ёмкость и содержимое кэша между BE не разделяются. Обычные сканирования, векторный поиск, полнотекстовый поиск и выборка второй фазы могут повторно использовать соответствующие кэши без дополнительных свойств CREATE CATALOG.

Кэш метаданныхПамять BEМетаданные, используемые reader Lance, уменьшающие повторное чтение и разбор.

Кэш данных использует Foyer внутри reader Lance, с отдельным каталогом и ёмкостью, настроенными параметрами BE lance_* ниже. Он не использует общий каталог или настройки ёмкости File Cache Doris. Первое чтение всё равно несёт I/O исходного хранилища и накладные расходы заполнения. Попадания в кэш могут уменьшить последующие чтения источника, но не устраняют затраты на декодирование, фильтрацию или сортировку.

Планируйте ёмкость кэшей индексов и метаданных вместе с рабочей памятью запросов. Эти ёмкости не ограничивают общую память запроса Lance или память процесса BE. Дисковый кэш также использует локальное дисковое пространство и файловые дескрипторы. Большие блоки чтения уменьшают число блоков, но могут увеличить лишний I/O для малых чтений. При изменении размера блока чтения или схемы диска используйте новый каталог кэша.

Формулы размера для конкретных нагрузок, примеры конфигурации, конкуренцию за общий кэш и гранулярность сегментов индексов см. в разделе Лучшие практики запросов Lance. Для совместной фильтрации и извлечения см. Лучшие практики производительности гибридного поиска Lance.

Проверка эффективности кэша​

В завершённом Profile запроса счётчики кэша индексов находятся в LanceReader → LanceIndex, а счётчики кэша файлов данных — в LanceReader → LanceDataCache:

Два счётчика байтов кэша данных не включают увеличение объёма блочного чтения и I/O, обходящий кэш данных, например чтение индексов и manifest. Время сбора и границы метрик см. в разделе Справочник профиля запросов Lance.

Endpoint BE /metrics также предоставляет метрики с префиксами doris_be_lance_session_index_cache_ и doris_be_lance_session_metadata_cache_. Суффиксы capacity_bytes, usage_bytes, entries, hits_total и misses_total обозначают настроенную ёмкость, текущее использование, число записей, накопленные попадания и накопленные промахи. Эти метрики регистрируются после инициализации общего Lance Session и описывают кэш всего BE, а не отдельный запрос.

Для сравнения эффективности кэша используйте одну и ту же версию Dataset и параметры запроса, убедитесь, что запросы фактически выполняются на тех же BE, и записывайте задержку первого и повторного чтения, счётчики кэша и I/O источника. Общая задержка сама по себе не различает эффект кэша, поиск индекса, декодирование и стоимость выборки второй фазы.

Двухфазное чтение TopN и отложенная материализация​

vector_search() и full_text_search() обычно создают больше строк-кандидатов, чем конечный top_k. Чтение широких выходных столбцов, таких как title или payload, во время поиска тратит ресурсы, поскольку большинство кандидатов отбрасывается TopN. Двухфазное чтение откладывает эти столбцы: фаза 1 читает только столбцы, необходимые для фильтрации, сортировки и TopN; после глобального TopN фаза 2 читает остальные выходные столбцы только для сохранённых строк.

Это уменьшает I/O хранилища, сетевую передачу и использование памяти. Выгода обычно максимальна при небольшом top_k, большом числе кандидатов или широких строковых, JSON и подобных столбцах.

ФазаЧитаемые данные
Фаза 1Столбцы, используемые поиском внутри, _distance или _score, столбцы для Post-filter или сортировки и внутреннее расположение строки.
Фаза 2Столбцы верхнего уровня, используемые только конечной проекцией, читаются лишь для строк, оставленных глобальным TopN.

Условия запуска​

Doris использует двухфазное чтение только при выполнении всех условий:

  1. Запрос читает Lance через vector_search() или full_text_search(), а план содержит TopN, подходящий для отложенной материализации. Обычный SQL, переписанный в эти поисковые TVF, также может соответствовать; незаменённые скалярные сканирования таблиц и файловые TVF Lance не подходят.
  2. Логическая переменная сеанса enable_lance_lazy_materialization равна true, значению по умолчанию.
  3. Хотя бы один столбец верхнего уровня можно отложить. Можно отложить столбец, используемый только в конечной проекции SELECT. Столбец, используемый Post-filter, ORDER BY или другим выражением до TopN, должен читаться в фазе 1. Вложенные подстолбцы пока отложить нельзя.

enable_lance_lazy_materialization независим от topn_lazy_materialization_threshold: Lance может использовать двухфазное чтение, даже если последний равен -1 или top_k превышает этот порог. Другие таблицы, поддерживающие ленивую материализацию, по-прежнему следуют общему порогу. Включение переключателя разрешает оптимизацию; структура плана и подходящие столбцы всё ещё определяют её применение.

В следующем запросе category нужно прочитать в фазе 1 для Post-filter, тогда как user_id, title и payload можно получить после TopN:

SET enable_lance_lazy_materialization = true;

SELECT user_id, title, payload, _distance
FROM vector_search(
    "table" = "lance_catalog.default.items",
    "column" = "embedding",
    "query_vector" = "[0.1, 0.2, 0.3, 0.4]",
    "top_k" = "10",
    "offset" = "3"
)
WHERE category = 'book';

Столбцы, указанные в filter TVF, используются внутри Lance. Одного присутствия столбца в строке filter недостаточно, чтобы он стал выходным столбцом фазы 1, возвращаемым Doris; prefilter лишь меняет момент применения условия относительно генерации кандидатов.

Проверка плана​

Добавьте EXPLAIN VERBOSE перед запросом выше. При активном двухфазном чтении план содержит VMaterializeNode, а его column_descs_lists перечисляет столбцы, извлечённые во фазе 2. Отключите переключатель и снова выполните EXPLAIN VERBOSE для того же простого поискового запроса; соответствующий узел материализации должен исчезнуть. Если при включённом переключателе его нет, проверьте, используются ли выходные столбцы в фильтрации, сортировке или других вычислениях до TopN и поддерживает ли план эту оптимизацию.

Отключение двухфазного чтения​

Используйте следующую настройку сеанса:

SET enable_lance_lazy_materialization = false;

Doris использует однофазное чтение, если нельзя отложить ни один столбец или план не поддерживает оптимизацию. Большой top_k сам по себе не отключает двухфазное чтение Lance. Рассмотрите отключение и сравнение производительности в случаях:

  • top_k велик, поэтому фаза 2 всё равно читает большую часть строк-кандидатов.
  • Запрос возвращает только несколько узких столбцов, и двухфазное чтение экономит мало I/O.
  • Случайные чтения по Row-ID на базовом хранилище имеют высокую задержку, и дополнительные затраты Fetch фазы 2 превышают выгоду от отложенного чтения.

Отключение этой оптимизации меняет только момент чтения выходных столбцов. Оно не отключает векторные или FTS-индексы и не меняет семантику Prefilter, Post-filter или TopN. Сравнивайте обе настройки на репрезентативных запросах и в реальных условиях хранилища.

Полнотекстовый поиск​

full_text_search() — реляционная TVF, выполняющая извлечение BM25 через существующий инвертированный FTS-индекс таблицы Lance. Она поддерживает объединение анализированных терминов запроса через OR или AND, а также сопоставление их порядка и расстояния запросами Phrase. Doris объединяет кандидатов физических сегментов индекса в глобальный Top-K и добавляет _score к исходным столбцам. Больший score означает большую релевантность.

Перед использованием TVF создайте инвертированный FTS-индекс по целевому строковому столбцу с помощью Lance SDK или другого writer Lance. Запросы Phrase также требуют включённых позиций токенов при создании индекса, например with_position=true в параметрах индекса Lance. Doris не создаёт индекс и не переходит к построчному полнотекстовому сканированию, если FTS-индекса нет.

Синтаксис и пример​

Следующий запрос ищет lance database среди документов категории storage, а затем применяет published = true как Doris Post-filter:

SELECT document_id, title, _score
FROM full_text_search(
    "table" = "lance_catalog.default.documents",
    "column" = "body",
    "query" = "lance database",
    "query_type" = "match",
    "operator" = "and",
    "top_k" = "10",
    "offset" = "0",
    "prefilter" = "true",
    "filter" = "category = 'storage'",
    "coverage_mode" = "strict"
)
WHERE published = true
ORDER BY _score DESC, document_id;

В этом примере используется Match AND, поэтому документ должен содержать оба анализированных термина: lance и database. При prefilter=true Lance вычисляет filter до генерации FTS-кандидатов. Если prefilter опущен, значение по умолчанию — false, и Lance применяет filter после генерации кандидатов; результат может содержать меньше top_k строк. Внешнее WHERE — это Doris Post-filter, он не пополняет удалённые кандидаты. Если published = true должно влиять на генерацию кандидатов, включите его в filter и задайте prefilter=true.

Следующий запрос Phrase допускает не более одного промежуточного токена между соседними терминами. Например, он может сопоставить lance search engine:

SELECT document_id, title, _score
FROM full_text_search(
    "table" = "lance_catalog.default.documents",
    "column" = "body",
    "query" = "lance engine",
    "query_type" = "phrase",
    "slop" = "1",
    "top_k" = "10"
)
ORDER BY _score DESC, document_id;

Возвращаемое отношение содержит каждый столбец исходной таблицы Lance и nullable-столбец FLOAT с именем _score. Исходная таблица не должна уже содержать столбец с этим именем. TVF выбирает Top-K по убыванию _score, но SQL-отношение не гарантирует порядок отображения. Для стабильного порядка явно задавайте ORDER BY _score DESC и добавляйте уникальный tie-breaker для одинаковых score.

Поиск исторической версии или branch​

По умолчанию vector_search() и full_text_search() ищут последнюю версию main. Четыре необязательных параметра выбирают другой снимок с тем же смыслом, что и синтаксис таблицы Time Travel:

-- Search version 3.
SELECT id, _distance
FROM vector_search(
    "table" = "lance_catalog.db.documents",
    "column" = "embedding",
    "query_vector" = "[0.1, 0.2, 0.3]",
    "version" = "3")
ORDER BY _distance;

-- Search the branch "dev" as it was at a point in time.
SELECT id, _score
FROM full_text_search(
    "table" = "lance_catalog.db.documents",
    "column" = "content",
    "query" = "database",
    "branch" = "dev",
    "timestamp" = "2026-09-20 12:00:00")
ORDER BY _score DESC;
  • Снимок выбирается по тем же правилам, что и синтаксис таблицы, включая tag, указывающие в branch, и таблицы с версиями, управляемыми REST Namespace. version принимает только номер версии. В отличие от FOR VERSION AS OF, он не принимает имя tag, потому что tag однозначно обозначает tag: tag с именем 123 выбирается как "tag" = "123".
  • version и timestamp нельзя сочетать, а tag нельзя сочетать с любым из остальных трёх. Пустое значение параметра является ошибкой, а не игнорируется.
  • Выходная schema, столбец поиска, метаданные векторного и FTS-индексов и Fragment берутся из выбранного снимка. Генерация кандидатов, фильтрация, Top-K и двухфазное чтение также используют этот снимок. Историческая версия использует индексы, зафиксированные в ней: версия до создания векторного индекса использует Flat Search, версия до создания FTS-индекса не может использоваться с full_text_search(), а coverage_mode проверяет Fragment этой версии.
  • Невыбираемый снимок или отсутствующие файлы индекса вызывают ошибку. Поиск никогда не переключается на последнюю версию. Версия, удалённая очисткой Lance, сообщается как отсутствующая. Версия, сохранённая tag, сохраняет файлы индекса при очистке; если файлы индекса удалены другим способом, ошибка возникает при выполнении и содержит версию Dataset.
  • Снимок выбирается заново при каждом выполнении, включая каждое EXECUTE подготовленного оператора, поэтому последняя версия, время в будущем, branch и перемещённый tag могут каждый раз выбирать другую версию. Эти четыре параметра должны быть константами: в подготовленном операторе vector_search() допускает placeholders (?) только для query_vector, top_k, offset и filter, а full_text_search() не допускает их ни для одного параметра.
  • Каждое поисковое отношение выбирает собственный снимок. Два отношения одной таблицы в одном операторе, например vector_search() и сама таблица, могут читать разные версии, если между ними зафиксирована новая версия. Чтобы читать одну и ту же, зафиксируйте обе: version в поисковой функции и FOR VERSION AS OF в таблице.
  • CREATE TABLE AS SELECT планирует запрос дважды: один раз для schema новой таблицы и один раз для строк, поэтому изменяющийся селектор может каждый раз выбрать другую версию. Для точного копирования одной версии задайте version.
  • EXPLAIN показывает выбранную версию как lanceVersion, branch как lanceBranch, а управление версиями REST Namespace — как lanceManagedVersioning. Поскольку EXPLAIN выбирает снимок заново, Profile выполнения записывает фактически прочитанное: LanceDatasetVersion и LanceDatasetUri вместе с другой информацией Lance scanner, например LanceSearchType. URI включает каталог branch и не содержит строки запроса или пароля.
  • Branch, созданный из другого branch или shallow clone, может не найти унаследованные файлы индекса, потому что writers Lance до версии 13 записывали их в промежуточный branch. Поиск завершается ошибкой, а собственные индексы branch не затрагиваются.
  • После удаления и повторного создания branch с тем же именем или замены Dataset по тому же URI новые данные повторно используют старые номера версий. BE может продолжать использовать кэш для этих номеров до вытеснения записей или перезапуска BE. В Dataset со стабильными row ID векторный и полнотекстовый поиск может фильтровать по живым строкам старых данных, поэтому результаты могут содержать строки, удалённые в новых данных, или пропускать живые строки. Если manifest использует старое именование Lance (_versions/<version>.manifest) или объектное хранилище не возвращает ETag, BE и FE также могут использовать старые метаданные индексов; FE прекращает это после обновления Catalog. Дайте пересозданному branch новое имя либо перезапустите BE. Обновление Catalog не очищает эти кэши BE.
  • FTS-индекс, созданный без позиций токенов, не может выполнять запросы Phrase. Индексам, созданным старыми writers, которые может использовать историческая версия, часто не хватает позиций.

Текущая модель выполнения​

Порядок выполнения vector_search() и full_text_search():

Dataset snapshot selected by version / timestamp / tag / branch, or the latest version of main
  -> FE search Split planning
       -> Vector search: physical vector Index Segments + Flat Search for uncovered Fragments
       -> Full-text search: physical FTS Index Segments (coverage checked by coverage_mode)
  -> Per Split: vector/full-text search; the TVF `filter` runs before candidate generation when `prefilter=true`, and after candidate generation when `prefilter` is omitted or `false`
       -> at most K+n candidates
  -> Doris Scan Post-filter
  -> Doris local TopN
  -> Exchange
  -> Doris global TopN (applies offset=n and limit=K)
  -> Optional lazy-materialization Fetch

Текущие ограничения и рекомендации​

  • Lance Catalog и Lance TVF доступны только для чтения. CREATE TABLE, INSERT, UPDATE, DELETE, TRUNCATE TABLE и запись данных обратно в Lance не поддерживаются.
  • Для таблиц с неподдерживаемыми типами столбцов явно перечисляйте читаемые столбцы вместо проекции неподдерживаемых столбцов через SELECT *.
  • Для обычных сканирований проверяйте в EXPLAIN lancePushdownPredicate, чтобы убедиться, какие условия переданы.
  • Перед индексированным векторным поиском создайте в Lance векторный индекс, соответствующий предполагаемому запросу. Для небольших наборов данных или проверки задайте "use_index" = "false", чтобы выполнить Flat Search.
  • Перед полнотекстовым поиском создайте в Lance инвертированный FTS-индекс. Режим strict по умолчанию отклоняет запрос, если индекс не покрывает каждый Fragment текущего снимка; используйте index_only только когда пропуск данных приемлем.
  • Запросы Phrase требуют, чтобы FTS-индекс хранил позиции токенов. Если нужны запросы Phrase, задайте with_position=true при создании индекса.
  • Используйте SHOW INDEX для таблицы Filesystem Catalog, чтобы проверить логические индексы Lance, например имя, тип и индексируемые поля перед векторным или полнотекстовым поиском. REST Catalog не поддерживает SHOW INDEX.
  • Для детерминированного порядка результатов векторного поиска явно используйте ORDER BY _distance ASC и добавьте уникальный tie-breaker.
  • Для детерминированного порядка результатов полнотекстового поиска явно используйте ORDER BY _score DESC и добавьте уникальный tie-breaker.
  • Чтобы фильтровать до генерации кандидатов векторного или полнотекстового поиска, задайте filter TVF и prefilter=true; при prefilter=false по умолчанию TVF filter применяется после генерации кандидатов. Внешнее WHERE вычисляется Doris по кандидатам, созданным каждым поисковым Split, до глобального TopN, поэтому итоговый результат может содержать меньше top_k строк.
  • Используйте EXPLAIN для проверки lanceSearchFragments и lanceSearchIndexSegments. Первое — число видимых Fragment в зафиксированном снимке, второе — число физических split Index Segment, выбранных FE. Векторный поиск также может включать резервные Flat Search Fragment split; полнотекстовый поиск никогда не переходит к Flat Search.
