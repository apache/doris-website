Hive Catalog

Подключаясь к Hive Metastore или совместимым с ним сервисам метаданных, Doris может автоматически получать информацию о базах данных и таблицах Hive для выполнения запросов к данным.

Помимо Hive, многие другие системы используют Hive Metastore для хранения метаданных. Поэтому через Hive Catalog можно обращаться не только к таблицам Hive, но и к другим форматам таблиц, использующим Hive Metastore для хранения метаданных, например Iceberg и Hudi.

Сценарии использования​

СценарийОписание
Ускорение запросовИспользование распределённого вычислительного движка Doris для прямого доступа к данным Hive и ускорения запросов.
Интеграция данныхЧтение данных Hive и их запись во внутренние таблицы Doris или выполнение операций ZeroETL с помощью вычислительного движка Doris.
Обратная запись данныхОбработка данных из любого источника, поддерживаемого Doris, и их обратная запись в таблицы Hive.

Настройка Catalog​

Синтаксис​

CREATE CATALOG [IF NOT EXISTS] catalog_name PROPERTIES (
    'type'='hms', -- required
    'hive.metastore.type' = '<hive_metastore_type>', -- optional
    'hive.version' = '<hive_version>', -- optional
    'fs.defaultFS' = '<fs_defaultfs>', -- required for write, optional for read-only
    {MetaStoreProperties},
    {StorageProperties},
    {HiveProperties},
    {CommonProperties}
);

  • <hive_metastore_type>

    Указывает тип Hive Metastore.

    • hms: стандартный сервис Hive Metastore.
    • glue: доступ к сервису метаданных AWS Glue через интерфейс, совместимый с Hive Metastore.
    • dlf: доступ к сервису метаданных Alibaba Cloud DLF через интерфейс, совместимый с Hive Metastore.

  • <fs_defaultfs>

    Этот параметр обязателен при записи данных из Doris в таблицы этого Hive Catalog. Пример:

    'fs.defaultFS' = 'hdfs://namenode:port'

  • {MetaStoreProperties}

    Раздел MetaStoreProperties предназначен для указания параметров подключения и аутентификации в сервисе метаданных Metastore. Подробности см. в разделе «Поддерживаемые сервисы метаданных».

  • {StorageProperties}

    Раздел StorageProperties предназначен для указания параметров подключения и аутентификации в системе хранения. Подробности см. в разделе «Поддерживаемые системы хранения».

  • {HiveProperties}

    Раздел HiveProperties предназначен для указания свойств Hive Catalog.

    • get_schema_from_table: значение по умолчанию — false. По умолчанию Doris получает информацию о схеме таблицы из Hive Metastore. Однако в некоторых случаях могут возникать проблемы совместимости, например ошибка Storage schema reading not supported. В таком случае можно задать этому параметру значение true, и схема таблицы будет получена непосредственно из объекта Table. Обратите внимание: при таком способе информация о значениях столбцов по умолчанию игнорируется. Это свойство поддерживается начиная с версий 2.1.10 и 3.0.6.

    • hive.recursive_directories: определяет, следует ли рекурсивно обходить подкаталоги при получении списка каталогов партиций. Этот параметр поддерживается начиная с версии 3.0.2. До версии 4.0 значение по умолчанию было false; в более поздних версиях оно равно true. Пути партиций некоторых таблиц Hive могут не соответствовать информации о партициях в схеме таблицы. Чтобы получать файлы данных из подкаталогов, необходимо задать этому параметру значение true.

    • hive.ignore_absent_partitions: определяет, следует ли игнорировать несуществующие партиции. Значение по умолчанию — true. Если задано значение false, при обнаружении несуществующей партиции запрос завершится ошибкой. Этот параметр поддерживается начиная с версии 3.0.2.

    • hive.staging_dir: задаёт корневой каталог для временного размещения данных при записи в Hive. В процессе записи данные сначала записываются в этот каталог, а после завершения перемещаются в конечный каталог таблицы Hive. Путь может быть относительным, отсчитываемым от корневого каталога таблицы Hive, или абсолютным. Значение по умолчанию — /tmp/.doris_staging. В некоторых случаях при записи в таблицы Hive каталог /tmp и каталог таблицы могут принадлежать разным пространствам имён, что приводит к ошибкам записи. Чтобы устранить эту проблему, можно задать в этом параметре относительный путь. Этот параметр поддерживается начиная с версии 4.0.3.

    • hive.parquet.time-zone: часовой пояс совместимости, используемый для восстановления временных меток Parquet INT96 старого формата при чтении таблиц Hive через FileScannerV2. По умолчанию значение пустое: поля локальной даты и времени, сохранённые в INT96, сохраняются без преобразования часового пояса. Задавайте это свойство, только если файлы INT96 в Catalog были нормализованы при записи с использованием известного часового пояса. Таблицы Hudi намеренно игнорируют это свойство и сохраняют существующее поведение, зависящее от часового пояса сессии SQL. Подробности см. в разделе Совместимость временных меток Parquet INT96.

  • {CommonProperties}

    Раздел CommonProperties предназначен для указания общих свойств. См. раздел «Общие свойства» в Обзоре Catalog.

Кэш метаданных​

Чтобы повысить производительность доступа к внешним источникам данных, Apache Doris кэширует метаданные Hive. Метаданные включают объекты таблиц, имена партиций, объекты партиций, статистику столбцов, списки файлов и производные структуры для отсечения партиций.

подсказка

В версиях до Doris 4.1.x кэширование метаданных в основном управляется глобальными параметрами конфигурации FE. Подробности см. в разделе Кэш метаданных. Начиная с Doris 4.1.x внешний кэш метаданных Hive Catalog настраивается с помощью унифицированных ключей meta.cache.*. Ниже описаны параметры текущей версии; в Doris 4.1.x и 4.2.x используется другой набор параметров, описанный в версии 4.x этой страницы.

Настройка свойств кэша​

Для каждого компонента кэша используется унифицированный формат ключей конфигурации: meta.cache.<engine>.<entry>.{enable,ttl-second,capacity,max-weight}. Для Hive параметр <engine> имеет значение hive. Catalog на основе Hive Metastore, содержащий таблицы Iceberg, также использует компоненты iceberg, описанные в разделе Iceberg Catalog.

СвойствоПримерЗначение
enabletrue/falseОпределяет, включён ли этот компонент кэша.
ttl-second600, 0, -10 отключает компонент (вступает в силу немедленно и позволяет видеть актуальные данные); -1 означает отсутствие срока действия; другие положительные целые числа задают TTL в секундах с момента обращения.
capacity10000Максимальное количество записей в кэше. 0 отключает компонент.
max-weight1GBПоддерживается начиная с Doris 4.1.4. Необязательное ограничение оценочного объёма памяти, удерживаемой компонентом кэша. Должно быть положительным; 0 не допускается. Принимается только компонентами, отмеченными ниже.

Условия работы: компонент кэша работает, когда enable=true, ttl-second != 0 и capacity > 0. Ограничение памяти на уровне всего FE, Catalog или отдельного компонента дополнительно определяет возможность добавления записей на основе оценочного объёма памяти; см. Управление памятью внешнего кэша метаданных.

Сопоставление и преобразование устаревших параметров​

Рекомендуется использовать унифицированные ключи. Следующие устаревшие свойства Catalog по-прежнему принимаются и сопоставляются с новыми ключами:

Рекомендации​

  • Доступ к актуальным данным в реальном времени: чтобы каждый запрос видел последние изменения партиций или файлов во внешнем источнике данных, задайте соответствующему параметру ttl-second значение 0. 
    -- Disable the file listing cache to see file changes in real time
    ALTER CATALOG hive_ctl SET PROPERTIES ("meta.cache.hive.file.ttl-second" = "0");
    -- Disable the partition name cache to see new partitions in real time
    ALTER CATALOG hive_ctl SET PROPERTIES ("meta.cache.hive.partition_names.ttl-second" = "0");
  • Оптимизация производительности: если метаданные меняются редко, увеличьте capacity и ttl-second, чтобы снизить нагрузку на Hive Metastore и файловые системы. Используйте max-weight, чтобы ограничить кэши списков файлов и структур отсечения партиций для очень больших таблиц.
предупреждение

Успешное изменение свойств Catalog сбрасывает затронутые кэши метаданных и пересоздаёт их с новой конфигурацией при следующем обращении. Изменение meta.cache.max-weight или schema.cache.ttl-second сбрасывает все кэши Catalog; изменение meta.cache.<engine>.<entry>.* сбрасывает кэши соответствующего движка. Уже выполняющиеся запросы не затрагиваются.

Наблюдаемость​

Метрики кэша доступны в системной таблице information_schema.catalog_meta_cache_statistics. В ENTRY_NAME указаны имена из таблицы выше, а строка движка default соответствует общему кэшу схем таблиц:

SELECT engine_name, entry_name,
       effective_enabled, ttl_second, capacity,
       estimated_size, hit_rate, max_weight, estimated_weight
FROM information_schema.catalog_meta_cache_statistics
WHERE catalog_name = 'hive_ctl'
ORDER BY engine_name, entry_name;

См. документацию этой системной таблицы: catalog_meta_cache_statistics.

Совместимость временных меток Parquet INT96​

Таблицы Hive могут содержать файлы с временными метками, созданные разными движками. Необходимость преобразования часового пояса зависит от физического кодирования и поведения компонента записи. Doris не определяет часовой пояс компонента записи по значению Parquet INT96, поскольку INT96 не содержит аннотации часового пояса.

Начиная с 4.1.5, hive.parquet.time-zone принимает часовой пояс IANA или смещение относительно UTC от -12:00 до +14:00. Значения UTC и GMT допускаются; короткие псевдонимы, такие как CST и PRC, отклоняются. См. Parquet.

Временные метки Parquet INT96​

FileScannerV2 обрабатывает временные метки Parquet следующим образом:

Физическое кодированиеПоведение по умолчаниюВлияние hive.parquet.time-zone
INT96, сопоставленный с DATETIMEV2Сохраняются поля даты и времени, записанные в файле. Часовой пояс сессии SQL не сдвигает значение.Исходное значение INT96 интерпретируется как момент времени UTC и преобразуется в настроенный часовой пояс совместимости, восстанавливая временные метки, нормализованные устаревшим компонентом записи.
INT64 с логическим типом временной меткиИспользуется семантика логического типа Parquet.Не влияет.

Например, предположим, что ожидаемая локальная временная метка — 2021-01-01 10:11:00 в часовом поясе Asia/Shanghai:

  • Если файл напрямую хранит поля локального времени как 10:11:00, оставьте hive.parquet.time-zone незаданным. Doris вернёт 10:11:00, даже если сессия SQL использует Asia/Shanghai.
  • Если устаревший компонент записи нормализует значение в UTC перед сохранением в INT96, файл может содержать 02:11:00. Задайте для hive.parquet.time-zone значение Asia/Shanghai, чтобы Doris восстановил 10:11:00.

Задайте часовой пояс совместимости при создании Catalog:

CREATE CATALOG hive_legacy_int96 PROPERTIES (
    'type' = 'hms',
    'hive.metastore.uris' = 'thrift://127.0.0.1:9083',
    'hive.parquet.time-zone' = 'Asia/Shanghai'
);

Значением может быть имя часового пояса IANA, например Asia/Shanghai, или смещение относительно UTC от -12:00 до +14:00. Недопустимое значение приводит к ошибке создания Catalog.

предупреждение

hive.parquet.time-zone применяется ко всем столбцам временных меток INT96, сопоставленным с DATETIMEV2, в таблицах Hive этого Catalog. Оно не влияет на таблицы Iceberg в том же Hive Metastore, поскольку Iceberg определяет собственную семантику временных меток. Hudi также намеренно игнорирует это свойство: и нативное сканирование базовых файлов, и сканирование JNI merge-on-read сохраняют прежнее поведение, при котором временные метки интерпретируются с использованием часового пояса сессии SQL. Метаданные Parquet не позволяют Doris надёжно определить, какое соглашение использовал компонент записи INT96. Не задавайте это свойство только для того, чтобы оно совпадало с часовым поясом сессии SQL. Если один Hive Metastore содержит таблицы Hive с файлами INT96, записанными по разным соглашениям, по возможности предоставляйте доступ к ним через отдельные Catalog.

Это же свойство принимают табличные функции, читающие файлы Parquet. Преобразование совместимости применяется только при декодировании Parquet INT96 в FileScannerV2. Поведение FileScannerV1 намеренно оставлено прежним, поэтому он может возвращать другие результаты; переключение на FileScannerV1 не является механизмом совместимости для этого изменения. Логические временные метки Parquet INT64 не затрагиваются. Если столбец INT96 сопоставлен с TIMESTAMPTZ, Doris игнорирует это свойство и сохраняет момент времени UTC; отображение этого значения по-прежнему определяется семантикой TIMESTAMPTZ и часового пояса сессии.

Рекомендации по миграции​

  • По умолчанию Doris записывает логические временные метки Parquet INT64. Задавайте enable_int96_timestamps = true, только если устаревший компонент чтения, например Hive 2 или Hive 3, требует INT96.
  • При обновлении до версии с таким поведением FileScannerV2 проверьте существующие таблицы Hive перед развёртыванием. Catalog, содержащий файлы INT96, нормализованные устаревшим компонентом записи, после обновления может возвращать другое значение локального времени. Сравните характерные значения и задайте для hive.parquet.time-zone часовой пояс компонента записи, если требуется преобразование. Для Hudi миграция в связи с этим изменением не требуется, поскольку сохраняется существующее поведение, зависящее от часового пояса сессии.
  • Перед настройкой hive.parquet.time-zone изучите характерные файлы и сравните известные значения временных меток. Ненужная настройка создаёт такое же смещение, которое она призвана исправлять.
  • Храните файлы, записанные по разным соглашениям INT96, в отдельных Catalog или перезапишите их с единым кодированием INT64.
  • Когда Doris явно экспортирует INT96 с enable_int96_timestamps = true, он нормализует временные метки с использованием часового пояса сессии экспорта. Чтобы прочитать файл обратно через FileScannerV2, задайте для hive.parquet.time-zone часовой пояс этой сессии экспорта. См. Обзор экспорта.

Операции запросов​

Базовый запрос​

После настройки Catalog можно запрашивать данные его таблиц следующими способами:

-- 1. switch to catalog, use database and query
SWITCH hive_ctl;
USE hive_db;
SELECT * FROM hive_tbl LIMIT 10;

-- 2. use hive database directly
USE hive_ctl.hive_db;
SELECT * FROM hive_tbl LIMIT 10;

-- 3. use full qualified name to query
SELECT * FROM hive_ctl.hive_db.hive_tbl LIMIT 10;

Запрос информации о партициях Hive​

Информацию о партициях Hive можно запросить следующими двумя способами:

  • SHOW PARTITIONS FROM [catalog.][db.]hive_table

    Эта инструкция выводит все партиции и их значения для указанной таблицы Hive.

    SHOW PARTITIONS FROM hive_table;

    +--------------------------------+
    | Partition                      |
    +--------------------------------+
    | pt1=2024-10-10/pt2=beijing     |
    | pt1=2024-10-10/pt2=shanghai    |
    | pt1=2024-10-11/pt2=beijing     |
    | pt1=2024-10-11/pt2=shanghai    |
    | pt1=2024-10-12/pt2=nanjing     |
    +--------------------------------+

  • Использование таблицы метаданных table$partitions

    Начиная с версий 2.1.7 и 3.0.3 информацию о партициях Hive можно запрашивать через таблицу метаданных table$partitions. Эта таблица по своей сути реляционная: каждый столбец партиционирования представлен отдельным столбцом, что позволяет использовать её в любой инструкции SELECT.

    SELECT * FROM hive_table$partitions;

    +------------+-------------+
    | pt1        | pt2         |
    +------------+-------------+
    | 2024-10-10 | beijing     |
    | 2024-10-10 | shanghai    |
    | 2024-10-12 | nanjing     |
    | 2024-10-11 | beijing     |
    | 2024-10-11 | shanghai    |
    +------------+-------------+
Изменение поведения (4.1.4)

Начиная с версии 4.1.4 маркер партиции по умолчанию __HIVE_DEFAULT_PARTITION__, используемый при партиционировании Hive на основе каталогов, преобразуется в настоящее значение NULL, а не кодируется строкой \N. При этом буквальное значение \N, действительно сохранённое в пути партиции, сохраняется как данные.

До 4.1.4 эти два случая были неразличимы и оба отображались как \N в результатах запросов. После обновления WHERE <partition_col> IS NULL корректно находит партицию Hive по умолчанию.

Запросы к представлениям Hive​

Можно выполнять запросы к представлениям Hive, но есть некоторые ограничения:

  • Определение представления Hive (HiveQL) должно быть совместимо с инструкциями SQL, поддерживаемыми Doris. В противном случае возникнет ошибка синтаксического анализа.

  • Некоторые функции HiveQL могут иметь такие же имена, как функции Doris, но отличаться поведением. Это может приводить к расхождениям между результатами Hive и Doris. Если вы столкнулись с такой проблемой, сообщите о ней сообществу.

Операции записи​

Данные можно записывать в таблицы Hive с помощью инструкции INSERT. Поддерживаются таблицы Hive, созданные Doris, и существующие таблицы Hive с совместимыми форматами.

Для партиционированных таблиц данные автоматически записываются в соответствующую партицию, либо на основе данных создаётся новая партиция. Начиная с 4.1.5, PARTITION (column = literal) поддерживает статические партиции и сочетание статических и динамических столбцов партиционирования. Исключите статические столбцы партиционирования из списка целевых столбцов INSERT и из выходных данных SELECT или VALUES; остальные динамические столбцы партиционирования передавайте во входных данных.

INSERT INTO​

Операция INSERT добавляет данные в целевую таблицу.

INSERT INTO hive_tbl VALUES (val1, val2, val3, val4);
INSERT INTO hive_ctl.hive_db.hive_tbl SELECT col1, col2 FROM internal.db1.tbl1;

INSERT INTO hive_tbl(col1, col2) VALUES (val1, val2);
INSERT INTO hive_tbl(col1, col2, partition_col1, partition_col2) VALUES (1, 2, "beijing", "2023-12-12");

Начиная с 4.1.5 запись поддерживает статические партиции или сочетание статических и динамических партиций:

-- Full Static Partition
INSERT INTO hive_tbl PARTITION (partition_col1='2026-07-30', partition_col2='beijing')
VALUES (val1, val2);
INSERT INTO hive_tbl PARTITION (partition_col1='2026-07-30', partition_col2='beijing')
SELECT col1, col2 FROM source_table;

-- Hybrid Partition Mode: "partition_col1" is static, "partition_col2" comes from SELECT dynamically
INSERT INTO hive_tbl PARTITION (partition_col1='2026-07-30')
VALUES (val1, val2, partition_val2);
INSERT INTO hive_tbl PARTITION (partition_col1='2026-07-30')
SELECT col1, col2, partition_col2 FROM source_table;

INSERT OVERWRITE​

INSERT OVERWRITE полностью заменяет существующие данные таблицы новыми.

INSERT OVERWRITE TABLE hive_tbl VALUES (val1, val2, val3, val4);
INSERT OVERWRITE TABLE hive_ctl.hive_db.hive_tbl(col1, col2) SELECT col1, col2 FROM internal.db1.tbl1;

Начиная с 4.1.5 запись поддерживает статические партиции или сочетание статических и динамических партиций:

-- Full Static Partition
INSERT OVERWRITE TABLE hive_tbl PARTITION (partition_col1='2026-07-30', partition_col2='beijing')
VALUES (val1, val2);
INSERT OVERWRITE TABLE hive_tbl PARTITION (partition_col1='2026-07-30', partition_col2='beijing')
SELECT col1, col2 FROM source_table;

-- Hybrid Partition Mode: "partition_col1" is static, "partition_col2" comes from SELECT dynamically
INSERT OVERWRITE TABLE hive_tbl PARTITION (partition_col1='2026-07-30')
VALUES (val1, val2, partition_val2);
INSERT OVERWRITE TABLE hive_tbl PARTITION (partition_col1='2026-07-30')
SELECT col1, col2, partition_col2 FROM source_table;

Семантика INSERT OVERWRITE согласуется с Hive и имеет следующие особенности:

  • Если целевая таблица партиционирована, а исходная таблица пуста, операция не оказывает эффекта. Целевая таблица остаётся без изменений.

  • Если целевая таблица не партиционирована, а исходная таблица пуста, целевая таблица очищается.

  • Начиная с 4.1.5 поддерживается указание статических партиций для записи, а также смешанный режим, сочетающий статические и динамические партиции. Однако даже при указании статических партиций они не будут очищены, если исходный запрос возвращает пустой результат.

Полный пример со статическими партициями (начиная с 4.1.5)

Настройте Hive Catalog, описанный на этой странице, подготовьте существующую базу данных hive_ctl.hive_db и предоставьте права на создание таблиц, запись и выполнение запросов. Для Catalog, используемого для записи, должен быть настроен fs.defaultFS. В этом примере статическая дата сочетается с динамическими регионами, после чего перезаписывается одна полностью заданная статическая партиция:

CREATE TABLE hive_ctl.hive_db.static_write_demo (
    id INT,
    dt STRING,
    region STRING
)
ENGINE=HIVE
PARTITION BY LIST (dt, region) ()
PROPERTIES ("file_format" = "parquet");

INSERT INTO hive_ctl.hive_db.static_write_demo PARTITION (dt='2026-10-01')
VALUES (1, 'beijing'), (2, 'shanghai');

INSERT OVERWRITE TABLE hive_ctl.hive_db.static_write_demo
PARTITION (dt='2026-10-01', region='beijing') VALUES (3);

SELECT id, dt, region FROM hive_ctl.hive_db.static_write_demo ORDER BY id;
+----+------------+----------+
| id | dt         | region   |
+----+------------+----------+
|  2 | 2026-10-01 | shanghai |
|  3 | 2026-10-01 | beijing  |
+----+------------+----------+

Значения статических партиций должны быть литералами. Не указывайте один ключ партиционирования несколько раз и не повторяйте статический столбец партиционирования в явном списке столбцов INSERT. Имена статических ключей сопоставляются без учёта регистра; указание несуществующего столбца партиционирования вызывает ошибку.

CTAS​

Можно создать таблицу Hive и вставить в неё данные с помощью инструкции CTAS (CREATE TABLE AS SELECT):

CREATE TABLE hive_ctas ENGINE=hive AS SELECT * FROM other_table;

CTAS поддерживает указание форматов файлов, способов партиционирования и других параметров, как показано ниже:

CREATE TABLE hive_ctas ENGINE=hive
PARTITION BY LIST (pt1, pt2) ()
AS SELECT col1, pt1, pt2 FROM part_ctas_src WHERE col1 > 0;
    
CREATE TABLE hive_ctl.hive_db.hive_ctas (col1, col2, pt1) ENGINE=hive
PARTITION BY LIST (pt1) ()
PROPERTIES (
    "file_format"="parquet",
    "compression"="zstd"
)
AS SELECT col1, pt1 AS col2, pt2 AS pt1 FROM test_ctas.part_ctas_src WHERE col1 > 0;

Управление базами данных и таблицами​

Пользователи могут создавать и удалять базы данных и таблицы в Hive Metastore через Doris. Обратите внимание: для этих операций Doris только вызывает API Hive Metastore и сам не хранит и не сохраняет метаданные Hive.

Создание и удаление баз данных​

Можно переключиться на нужный Catalog с помощью инструкции SWITCH и выполнить инструкцию CREATE DATABASE:

SWITCH hive_ctl;
CREATE DATABASE [IF NOT EXISTS] hive_db;

Также можно создать базу данных, указав полное имя или расположение, например:

CREATE DATABASE [IF NOT EXISTS] hive_ctl.hive_db;

CREATE DATABASE [IF NOT EXISTS] hive_ctl.hive_db
PROPERTIES ('location'='hdfs://172.21.16.47:4007/path/to/db/');

Посмотреть информацию о расположении базы данных можно с помощью команды SHOW CREATE DATABASE:

mysql> SHOW CREATE DATABASE hive_db;
+----------+---------------------------------------------------------------------------------------------+
| Database | Create Database                                                                             |
+----------+---------------------------------------------------------------------------------------------+
| hive_db  | CREATE DATABASE hive_db LOCATION 'hdfs://172.21.16.47:4007/usr/hive/warehouse/hive_db.db'   |
+----------+---------------------------------------------------------------------------------------------+

Чтобы удалить базу данных:

DROP DATABASE [IF EXISTS] hive_ctl.hive_db;
предупреждение

Перед удалением базы данных Hive необходимо удалить все её таблицы; в противном случае возникнет ошибка. Эта операция также удаляет соответствующую базу данных в Hive.

Создание и удаление таблиц​

  • Создание таблиц

    Doris поддерживает создание как партиционированных, так и непартиционированных таблиц в Hive.

    -- Create unpartitioned hive table
    CREATE TABLE unpartitioned_table (
      `col1` BOOLEAN COMMENT 'col1',
      `col2` INT COMMENT 'col2',
      `col3` BIGINT COMMENT 'col3',
      `col4` CHAR(10) COMMENT 'col4',
      `col5` FLOAT COMMENT 'col5',
      `col6` DOUBLE COMMENT 'col6',
      `col7` DECIMAL(9,4) COMMENT 'col7',
      `col8` VARCHAR(11) COMMENT 'col8',
      `col9` STRING COMMENT 'col9'
    )  ENGINE=hive
    PROPERTIES (
      'file_format'='parquet'
    );

    -- Create partitioned hive table
    -- The partition columns must be in table's column definition list
    CREATE TABLE partition_table (
      `col1` BOOLEAN COMMENT 'col1',
      `col2` INT COMMENT 'col2',
      `col3` BIGINT COMMENT 'col3',
      `col4` DECIMAL(2,1) COMMENT 'col4',
      `pt1` VARCHAR COMMENT 'pt1',
      `pt2` VARCHAR COMMENT 'pt2'
    )  ENGINE=hive
    PARTITION BY LIST (pt1, pt2) ()
    PROPERTIES (
      'file_format'='orc',
      'compression'='zlib'
    );

    -- Create text format table(Since 2.1.7 & 3.0.3)
    CREATE TABLE text_table (
        `id` INT,
        `name` STRING
    ) PROPERTIES (
        'file_format'='text',
        'compression'='gzip',
        'field.delim'='\t',
        'line.delim'='\n',
        'collection.delim'=';',
        'mapkey.delim'=':',
        'serialization.null.format'='\\N',
        'escape.delim'='\\'
    );

    После создания таблицы можно просмотреть инструкцию создания таблицы Hive с помощью команды SHOW CREATE TABLE.

    Обратите внимание: в отличие от синтаксиса создания таблиц Hive, при создании партиционированной таблицы в Doris столбцы партиционирования должны быть включены в схему таблицы. Кроме того, они должны находиться в конце схемы и сохранять тот же порядок.

    подсказка

    В кластерах Hive, где транзакционные возможности ACID включены по умолчанию, у таблиц, созданных Doris, свойство transactional будет установлено в true. Поскольку Doris поддерживает только часть возможностей транзакционных таблиц Hive, это может привести к тому, что Doris не сможет читать созданные им таблицы Hive. Чтобы избежать этого, явно задайте "transactional" = "false" в свойствах таблицы для создания нетранзакционных таблиц Hive:

    CREATE TABLE non_acid_table(
      `col1` BOOLEAN COMMENT 'col1',
      `col2` INT COMMENT 'col2',
      `col3` BIGINT COMMENT 'col3'
    ) ENGINE=hive
    PROPERTIES (
      'transactional'='false'
    );

  • Удаление таблиц

    Таблицу Hive можно удалить с помощью инструкции DROP TABLE. При удалении таблицы также удаляются все её данные, включая данные партиций.

  • Сопоставление типов столбцов

    Подробности см. в разделе [Сопоставление типов столбцов]. Учитывайте следующие ограничения:

    • Столбцы должны допускать NULL, как предусмотрено по умолчанию; NOT NULL не поддерживается.
    • Hive 3.0 поддерживает задание значений по умолчанию. Для их задания явно добавьте "hive.version" = "3.0.0" в свойства Catalog.
    • Если типы вставляемых данных несовместимы (например, при вставке 'abc' в числовой тип), значение преобразуется в null.

  • Партиционирование

    Партиции Hive соответствуют партициям List в Doris. Поэтому при создании партиционированной таблицы Hive в Doris используйте синтаксис партиционирования List, но явно перечислять каждую партицию не требуется. Во время вставки данных Doris автоматически создаёт соответствующие партиции Hive на основе значений данных. Поддерживается партиционирование по одному или нескольким столбцам.

  • Форматы файлов

    • ORC (по умолчанию)

    • Parquet

      Обратите внимание: при записи типа DATETIME в файл Parquet используется физический тип INT96 вместо INT64. Это обеспечивает совместимость с логикой версий Hive до 4.0.

    • Text (поддерживается начиная с версий 2.1.7 и 3.0.3)

      Формат Text поддерживает следующие свойства таблиц:

      • field.delim: разделитель столбцов. Значение по умолчанию — \1.
      • line.delim: разделитель строк. Значение по умолчанию — \n.
      • collection.delim: разделитель элементов сложных типов. Значение по умолчанию — \2.
      • mapkey.delim: разделитель ключа и значения в парах map. Значение по умолчанию — \3.
      • serialization.null.format: формат хранения значений NULL. Значение по умолчанию — \N.
      • escape.delim: символ экранирования. Значение по умолчанию — \.

  • Форматы сжатия

    • Parquet: snappy (по умолчанию), zstd, plain (без сжатия)
    • ORC: snappy, zlib (по умолчанию), zstd, plain (без сжатия)
    • Text: gzip, deflate, bzip2, zstd, lz4, lzo, snappy, plain (по умолчанию, без сжатия)

  • Среда хранения

    • HDFS
    • Объектное хранилище

Подписка на события Hive Metastore​

Узлы FE периодически считывают события уведомлений (Notification Events) из HMS, благодаря чему Doris может обнаруживать изменения метаданных таблиц Hive в реальном времени и поддерживать их актуальность. В настоящее время поддерживаются следующие события:

СобытиеДействие и соответствующее поведение
CREATE DATABASEСоздаёт базу данных в соответствующем каталоге данных.
DROP DATABASEУдаляет базу данных из соответствующего каталога данных.
ALTER DATABASEВ основном затрагивает изменения свойств базы данных, комментариев и расположения хранения по умолчанию. Эти изменения не влияют на возможность Doris запрашивать внешние каталоги данных, поэтому в настоящее время это событие игнорируется.
CREATE TABLEСоздаёт таблицу в соответствующей базе данных.
DROP TABLEУдаляет таблицу из соответствующей базы данных и аннулирует кэш таблицы.
ALTER TABLEПри переименовании удаляет старую таблицу и создаёт новую с новым именем; в остальных случаях аннулирует кэш таблицы.
ADD PARTITIONДобавляет партицию в кэшированный список партиций соответствующей таблицы.
DROP PARTITIONУдаляет партицию из кэшированного списка партиций и аннулирует кэш партиции.
ALTER PARTITIONПри переименовании удаляет старую партицию и создаёт новую с новым именем; в остальных случаях аннулирует кэш партиции.
подсказка

  1. Когда импорт данных приводит к изменению файлов, партиционированные таблицы вызывают событие ALTER PARTITION, а непартиционированные — событие ALTER TABLE.

  2. Если изменять файловую систему напрямую в обход HMS, HMS не создаст соответствующие события, и Doris не обнаружит изменения метаданных.

С этой возможностью связаны следующие параметры в fe.conf:

  1. enable_hms_events_incremental_sync: включает автоматическую инкрементальную синхронизацию метаданных. По умолчанию отключена.

  2. hms_events_polling_interval_ms: интервал чтения событий, по умолчанию — 10000 миллисекунд.

  3. hms_events_batch_size_per_rpc: максимальное количество событий, считываемых за один RPC, по умолчанию — 500.

Для использования этой возможности (за исключением Huawei Cloud MRS) необходимо изменить hive-site.xml сервиса HMS и перезапустить HMS и HiveServer2.

<property>
    <name>hive.metastore.event.db.notification.api.auth</name>
    <value>false</value>
</property>
<property>
    <name>hive.metastore.dml.events</name>
    <value>true</value>
</property>
<property>
    <name>hive.metastore.transactional.event.listeners</name>
    <value>org.apache.hive.hcatalog.listener.DbNotificationListener</value>
</property>

Для Huawei Cloud MRS необходимо изменить hivemetastore-site.xml и перезапустить HMS и HiveServer2.

<property>
    <name>metastore.transactional.event.listeners</name>
    <value>org.apache.hive.hcatalog.listener.DbNotificationListener</value>
</property>

Механизм транзакций​

Операции записи в Hive выполняются в отдельной транзакции. До фиксации транзакции данные не видны извне. Только после её фиксации результаты соответствующих операций с таблицами становятся видны другим пользователям.

Транзакции обеспечивают атомарность операций: все операции внутри транзакции либо завершаются успешно вместе, либо вместе завершаются неудачей.

Транзакции не могут полностью гарантировать изоляцию операций, но позволяют свести несогласованность к минимуму за счёт разделения операций файловой системы и операций с метаданными Hive Metastore.

Например, если в транзакции требуется изменить несколько партиций таблицы Hive и задача разделена на две группы, первая группа может стать видна извне до завершения второй. Это означает, что первую группу партиций уже можно прочитать, а вторую — ещё нельзя.

Если в процессе фиксации транзакции возникают исключения, транзакция полностью откатывается, включая изменения файлов HDFS и метаданных Hive Metastore, без дополнительных действий со стороны пользователя.

Механизм параллельной записи​

В настоящее время Apache Doris поддерживает параллельную запись с помощью нескольких инструкций insert. Однако пользователи должны следить за тем, чтобы параллельные операции записи не вызывали конфликтов.

Поскольку обычные нетранзакционные таблицы Hive не имеют полноценного механизма транзакций, механизм транзакций Apache Doris стремится сократить периоды несогласованности, но не может гарантировать полноценные свойства ACID. Поэтому параллельная запись в таблицы Hive через Apache Doris может приводить к проблемам согласованности данных.

  1. Параллельные операции INSERT

  2. Операции INSERT добавляют данные и при параллельном выполнении не конфликтуют, обеспечивая ожидаемые результаты.

  3. Параллельные операции INSERT OVERWRITE

  4. Параллельные операции INSERT OVERWRITE над одной таблицей или партицией могут приводить к потере или повреждению данных и непредсказуемым результатам.

  5. Распространённые решения:

    • Для партиционированных таблиц записывайте данные в разные партиции. Параллельные операции над разными партициями не конфликтуют.

    • Для непартиционированных таблиц используйте INSERT вместо INSERT OVERWRITE, чтобы избежать конфликтов.

    • Для потенциально конфликтующих операций обеспечьте на уровне бизнес-логики выполнение только одной операции записи в каждый момент времени.

Файловые операции HDFS​

Данные таблиц Hive в HDFS обычно сначала записываются во временный каталог, а затем размещаются окончательно с помощью операций файловой системы, таких как rename. Ниже подробно описаны файловые операции HDFS для разных операций с данными.

Формат временного каталога данных: /tmp/.doris_staging/<username>/<uuid>

Формат имён записываемых файлов данных: <query-id>_<uuid>-<index>.<compress-type>.<file-type>

Ниже приведены примеры файловых операций для различных сценариев:

  1. Непартиционированная таблица

    • Добавление данных

      • Каталог целевой таблицы: hdfs://ns/usr/hive/warehouse/example.db/table1

      • Временный файл: hdfs://ns/tmp/.doris_staging/root/f02247cb662846038baae272af5eeb05/b35fdbcea3a4e39-86d1f36987ef1492_7e3985bf-9de9-4fc7-b84e-adf11aa08756-0.orc

      • На этапе фиксации все временные файлы перемещаются в каталог целевой таблицы.

    • Перезапись (замена данных)

      • Каталог целевой таблицы: hdfs://ns/usr/hive/warehouse/example.db/table1

      • Временный файл: hdfs://ns/tmp/.doris_staging/root/f02247cb662846038baae272af5eeb05/b35fdbcea3a4e39-86d1f36987ef1492_7e3985bf-9de9-4fc7-b84e-adf11aa08756-0.orc

      • Шаги этапа фиксации:

        1. Переименовать каталог целевой таблицы во временный каталог: hdfs://ns/usr/hive/warehouse/example.db/_temp_b35fdbcea3a4e39-86d1f36987ef1492_table1

        2. Переименовать временный каталог в каталог целевой таблицы.

        3. Удалить временный каталог целевой таблицы.

  2. Партиционированная таблица

    • Добавление в новую партицию

      • Каталог целевой таблицы: hdfs://ns/usr/hive/warehouse/example.db/table2/part_col=2024-01-01

      • Временный файл: hdfs://ns/tmp/.doris_staging/root/a7eac7505d7a42fdb06cb9ef1ea3e912/par1=a/d678a74d232345e0-b659e2fb58e86ffd_549ad677-ee75-4fa1-b8a6-3e821e1dae61-0.orc

      • На этапе фиксации временный каталог переименовывается в каталог целевой таблицы.

    • Добавление данных в существующую партицию

      • Каталог целевой таблицы: hdfs://ns/usr/hive/warehouse/example.db/table2/part_col=2024-01-01

      • Временный файл: hdfs://ns/tmp/.doris_staging/root/a7eac7505d7a42fdb06cb9ef1ea3e912/par1=a/d678a74d232345e0-b659e2fb58e86ffd_549ad677-ee75-4fa1-b8a6-3e821e1dae61-0.orc

      • На этапе фиксации файлы из временного каталога перемещаются в каталог целевой таблицы.

    • Перезапись (замена существующей партиции)

      • Каталог целевой таблицы: hdfs://ns/usr/hive/warehouse/example.db/table2/part_col=2024-01-01

      • Временный файл: hdfs://ns/tmp/.doris_staging/root/a7eac7505d7a42fdb06cb9ef1ea3e912/par1=a/d678a74d232345e0-b659e2fb58e86ffd_549ad677-ee75-4fa1-b8a6-3e821e1dae61-0.orc

      • Шаги этапа фиксации:

        1. Переименовать каталог целевой партиции во временный каталог партиции: hdfs://ns/usr/hive/warehouse/example.db/table2/_temp_d678a74d232345e0-b659e2fb58e86ffd_part_col=2024-01-01

        2. Переименовать временный каталог партиции в каталог целевой партиции.

        3. Удалить временный каталог целевой партиции.
