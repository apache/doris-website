HNSW

HNSW (Hierarchical Navigable Small World, Malkov & Yashunin, 2016) стал фактическим стандартом высокопроизводительного векторного поиска в реальном времени благодаря высокой полноте и низкой задержке при умеренных затратах ресурсов в промышленной эксплуатации. Apache Doris поддерживает индексы ANN (Approximate Nearest Neighbor, приближённый поиск ближайших соседей) на основе HNSW начиная с версии 4.0. В этой статье рассматриваются принципы работы алгоритма, его параметры и практические аспекты использования и настройки индексов HNSW в промышленном кластере Apache Doris.

До появления HNSW​

Алгоритм HNSW был предложен в статье Эффективный и надёжный приближённый поиск ближайших соседей с использованием иерархических графов навигируемого малого мира. До появления HNSW уже существовало множество алгоритмов приближённого поиска KNN, но у каждого были свои недостатки.

Граф близости​

Основные этапы алгоритма на основе графа близости:

  1. Начать с некоторой точки входа в граф (случайной вершины или вершины, выбранной по определённой стратегии) и итеративно обходить граф.
  2. На каждом шаге вычислять расстояние между вектором запроса и всеми соседями текущего базового узла, затем выбирать соседа с наименьшим расстоянием в качестве следующего базового узла.
  3. Поддерживать множество лучших соседей-кандидатов, найденных к текущему моменту.
  4. Остановиться при выполнении условия остановки (например, если за одну итерацию не найден более близкий узел) и выбрать Top K из множества кандидатов в качестве окончательного результата.

Алгоритм на основе графа близости по сути является приближением графа Делоне, поскольку граф Делоне обладает важным свойством: жадный поиск всегда находит ближайшего соседа.

Однако у такого алгоритма есть два очевидных недостатка:

НедостатокПоследствие
Число итераций на этапе маршрутизации запроса растёт полиномиально с объёмом данныхНа больших объёмах данных затраты на выполнение запроса резко возрастают
Построить качественный граф близости сложно, часто возникают локальные скопления узловГрафу не хватает глобальной связности, и до некоторых узлов трудно добраться

На рисунке выше показан граф близости неудовлетворительного качества: чем темнее точки, тем хуже их связность. Некоторые точки с трудом находят собственных соседей, поэтому на этапе поиска до них трудно добраться.

Навигируемый малый мир​

Для решения этих проблем были предложены два подхода:

  1. Гибридные алгоритмы: перед поиском по графу смежности выполнить предварительное грубое ранжирование, чтобы найти более подходящую точку входа, а затем запустить жадный поиск.
  2. Структуры навигируемого малого мира: ограничить сложность поиска за счёт хорошей связности и ограничения максимального числа соседей у каждого узла.

NSW (Navigable Small World) использует второй подход.

Модель NSW впервые предложил J. Kleinberg в рамках социальных экспериментов для изучения связей между людьми в обществе, то есть известной теории шести рукопожатий.

В контексте алгоритмов на основе графов K-NN все сети малого мира с логарифмической или полилогарифмической сложностью поиска называют сетями навигируемого малого мира. Существует множество их реализаций, которые здесь не рассматриваются.

В своё время NSW показывал передовую производительность поиска на некоторых наборах данных. Однако из-за того, что его сложность не является строго логарифмической, он уступает другим подходам на таких тестовых наборах, как векторные пространства низкой размерности.

Иерархический навигируемый малый мир​

Поиск в алгоритме NSW состоит из двух этапов:

ЭтапПоведение
zoom-out (укрупнение масштаба)В качестве точки входа случайным образом выбирается вершина с низкой степенью. Во время поиска предпочтение отдаётся узлам с высокой степенью, пока среднее расстояние от узла до его соседей не превысит расстояние от этого узла до вектора запроса
zoom-in (детализация)После нахождения подходящего узла с высокой степенью выполняется жадный поиск до получения наилучшего TopN

Сложность NSW полилогарифмическая, поскольку общее число вычислений расстояния примерно пропорционально произведению «числа переходов x средней степени пройденных вершин». И среднее число переходов, и средняя степень растут логарифмически с объёмом данных, поэтому общая сложность получается полилогарифмической.

HNSW снижает временную сложность запроса до логарифмической за счёт ускорения этапа zoom-out.

В HNSW «иерархия» означает, что вершины графа NSW распределены по слоям в соответствии с характерным радиусом их рёбер. Поиск выполняется следующим образом:

  1. Выбрать точку входа на самом верхнем слое.
  2. Выполнить жадный поиск на текущем слое, чтобы найти ближайшую точку этого слоя.
  3. Спуститься на слой ниже и повторить жадный поиск.
  4. Продолжать до достижения нижнего слоя, где формируется окончательный результат.

Поскольку максимальное число связей у каждого узла ограничено на каждом слое, общая временная сложность остаётся логарифмической.

Для построения иерархии при вставке каждого узла HNSW вычисляет его слой l в соответствии с геометрическим распределением, что ограничивает общее число слоёв. HNSW не требует перемешивания данных перед загрузкой (в NSW перемешивание обязательно, иначе качество графа снижается), поскольку случайное назначение слоя при построении индекса само по себе обеспечивает рандомизацию. Благодаря этому HNSW также поддерживает полноценные инкрементальные обновления.

HNSW в Apache Doris​

Doris поддерживает построение индексов ANN на основе алгоритма HNSW начиная с версии 4.0.

Построение индекса​

Создать индекс ANN можно двумя способами:

СпособМомент построенияПреимуществаНедостатки
Указать при создании таблицыСтроится синхронно при создании сегмента во время загрузки данныхИндекс доступен для ускорения запросов сразу после завершения загрузкиСинхронное построение замедляет загрузку, а при компактации индекс многократно перестраивается
CREATE/BUILD INDEXСтроится асинхронно после загрузки данныхНе влияет на скорость загрузки и упрощает настройку параметровПока индекс строится, ускорение ANN недоступно

Способ 1: указать индекс при создании таблицы​

Подходит для стабильных сценариев, когда параметры индекса известны и не требуют частой настройки.

CREATE TABLE sift_1M (
    id int NOT NULL,
    embedding array<float>  NOT NULL  COMMENT "",
    INDEX ann_index (embedding) USING ANN PROPERTIES(
        "index_type"="hnsw",
        "metric_type"="l2_distance",
        "dim"="128"
    )
) ENGINE=OLAP
DUPLICATE KEY(id) COMMENT "OLAP"
DISTRIBUTED BY HASH(id) BUCKETS 1
PROPERTIES (
    "replication_num" = "1"
);

Выполнение запросов​

Индекс ANN поддерживает ускорение как поиска TopN, так и диапазонного поиска.

При высокой размерности векторного столбца сама строка, описывающая вектор запроса, создаёт дополнительные затраты на синтаксический разбор. В промышленной среде, особенно при большом числе параллельных запросов, не выполняйте векторный поиск напрямую через обычные SQL-запросы. Используйте подготовленные выражения, чтобы выполнить синтаксический разбор SQL заранее.

Doris официально предоставляет библиотеку Python для векторного поиска. Она инкапсулирует операции для работы с подготовленными выражениями и включает конвейер преобразования данных, который сразу превращает результаты запроса в pandas DataFrame, упрощая разработку приложений ИИ на основе Doris.

from doris_vector_search import DorisVectorClient, AuthOptions

auth = AuthOptions(
    host="localhost",
    query_port=9030,
    user="root",
    password="",
)

client = DorisVectorClient(database="demo", auth_options=auth)

tbl = client.open_table("sift_1M")

query = [0.1] * 128  # Example 128-dimensional vector

# SELECT id FROM sift_1M ORDER BY l2_distance_approximate(embedding, query) LIMIT 10;
result = tbl.search(query, metric_type="l2_distance").limit(10).select(["id"]).to_pandas()

print(result)

Оптимизация полноты​

Важнейшая метрика векторного поиска — полнота. Показатели производительности имеют смысл только при достижении определённого уровня полноты. На полноту в основном влияют следующие факторы:

  1. Параметры HNSW на этапе построения индекса (max_degree, ef_construction) и на этапе выполнения запроса (ef_search)
  2. Квантование векторов индекса
  3. Размер и количество сегментов

В этом разделе рассматриваются пункты 1 и 3. Квантование векторов описано в других статьях.

Гиперпараметры индекса​

Индекс HNSW организует векторы в виде иерархического графа. Этап построения состоит главным образом из трёх шагов:

  1. Случайное распределение по нескольким слоям: каждый вектор случайным образом назначается нескольким слоям. Верхние слои более разрежены и используются для быстрой навигации.
  2. Поиск соседей-кандидатов с помощью ef_construction: на каждом слое HNSW выполняет локальный поиск в ширину с очередью кандидатов, максимальная длина которой равна ef_construction. Чем больше значение, тем точнее выбираются соседи и тем лучше структура графа, но тем дольше длится построение.
  3. Ограничение связей с помощью max_degree: число соседей у каждого узла ограничивается параметром max_degree, чтобы граф не становился слишком плотным.

Этап выполнения запроса состоит из двух шагов:

  1. Жадный поиск на верхних слоях (грубый поиск): начиная с точки входа, жадный поиск проходит верхние слои сверху вниз и быстро приближается к целевой области.
  2. Поиск в ширину на нижнем слое (детальный поиск): на слое 0 выполняется более тщательное расширение окрестности с очередью кандидатов, максимальная длина которой равна ef_search.

Назначение трёх основных параметров и связанные с ними компромиссы:

ПараметрНазначениеЗначение по умолчаниюЭффект увеличения
max_degreeЧисло двунаправленных рёбер, хранящихся для каждого узла графа32Полнота и потребление памяти увеличиваются, производительность запросов снижается
ef_constructionМаксимальная длина очереди кандидатов на этапе построения индекса40Качество графа улучшается, полнота увеличивается, время построения растёт
ef_searchМаксимальная длина очереди кандидатов на этапе выполнения запроса32Полнота увеличивается, число вычислений расстояния растёт, задержка запросов и затраты CPU повышаются

Практический способ подбора гиперпараметров:

  1. Создайте таблицу table_multi_index без индексов с несколькими векторными столбцами (от 2 до 3 векторных столбцов).
  2. Загрузите данные в эту таблицу с помощью Stream Load или другими способами.
  3. Постройте индексы для всех векторных столбцов с помощью CREATE INDEX и BUILD INDEX, используя разные сочетания параметров для каждого столбца.
  4. После построения индексов вычислите полноту отдельно для каждого столбца и выберите наиболее подходящее сочетание гиперпараметров.

Число строк, охватываемых индексом​

Данные во внутренней таблице Doris организованы иерархически:

УровеньЗначение
ТаблицаПонятие верхнего уровня
TabletОсновная единица миграции и перебалансировки данных. Данные таблицы равномерно распределяются по N tablet на основе ключа бакетирования
RowsetОсновная единица управления версиями. Каждая загрузка или компактация добавляет новый rowset в tablet
СегментФайлы, в которых непосредственно хранятся данные

Как и инвертированный индекс, векторный индекс также работает на уровне сегментов. Размер сегмента определяется параметрами конфигурации BE write_buffer_size и vertical_compaction_max_segment_size. Во время загрузки и компактации, когда memtable достигает определённого размера, его содержимое сбрасывается в файл сегмента, и для этого сегмента строится векторный индекс (по одному индексу на каждый индексируемый столбец).

Согласно механизму поиска и построения HNSW, для заданного набора параметров индекса объём данных, который он может эффективно охватить, ограничен. Когда объём данных превышает порог, полнота перестаёт соответствовать требованиям.

Влияние компактации на полноту​

Компактация иногда создаёт более крупные сегменты, из-за чего исходные гиперпараметры индекса больше не обеспечивают достаточный охват новых сегментов увеличенного размера.

Рекомендуемый подход: запустите FULL COMPACTION перед выполнением BUILD INDEX. Построение индекса на полностью скомпактированных сегментах даёт сразу два преимущества:

  • Стабильная полнота
  • Меньшее усиление записи при построении индекса

Производительность запросов​

Холодная загрузка файлов индекса​

Индекс ANN в Doris реализован на основе библиотеки faiss с открытым исходным кодом от Meta. Индекс HNSW может ускорять запросы только после загрузки всей структуры графа в память.

Прежде чем выполнять большое число параллельных запросов, запустите первый запрос на холодном кеше, чтобы загрузить в память файлы индексов задействованных сегментов. Иначе производительность запросов значительно снизится.

Потребление памяти и производительность​

Индекс HNSW без сжатия квантованием занимает примерно в 1.3 раза больше памяти, чем индексируемые векторы.

Например, для набора данных из 1M векторов размерности 128 индексу HNSW FLAT потребуется около 128 x 4 x 1,000,000 x 1.3 ~= 650 MB.

Оценка потребления памяти при разных объёмах данных:

dimrowsОценка объёма памяти
1281M650 MB
76810M48 GB
768100M110 GB

Для обеспечения производительности запросов узлы BE должны располагать достаточным объёмом памяти. Иначе частые операции ввода-вывода индекса приведут к значительному снижению производительности запросов.
