Apache Doris 4.2 Peer Read: холодные запросы выполняются в 7.5 раза быстрее благодаря общему кешу

Xin Deng3 ноября 2026 г.

В системе Apache Doris с разделением вычислений и хранения несколько вычислительных групп совместно используют данные в объектном хранилище. Без общего доступа к кешу обычно возникают три проблемы:

  • Высокая задержка первого запроса после разделения чтения и записи. Недавно загруженные данные могут уже находиться в кеше группы записи, но первый запрос группы чтения всё равно извлекает их из объектного хранилища. Поиск по первичному ключу может занять несколько секунд.
  • Колебания производительности после масштабирования. После добавления узлов или перераспределения таблетов кеши новых узлов пусты, и для восстановления производительности запросов требуется время.
  • Повторное чтение из объектного хранилища после вытеснения данных из кеша. Из-за ограниченной ёмкости кеша ранее загруженные данные при следующем обращении к ним может потребоваться скачать заново.

Проблему решает общий доступ к кешу. Peer Read, появившийся в Apache Doris 4.2, при промахе локального кеша пытается прочитать данные из кеша другого узла, в том числе из другой вычислительной группы. Если у этого узла нет данных или он отвечает слишком медленно, чтение переключается на объектное хранилище.

В рабочей нагрузке пользователя облачного сервиса Doris включение Peer Read сократило среднюю задержку холодного поиска по первичному ключу с 4.45 до 0.59 секунды, то есть примерно в 7.5 раза. Задержка P99 снизилась с 7.69 до 1.52 секунды, а число обращений к объектному хранилищу сократилось примерно на 98%. В отдельном тесте TPC-H с объёмом данных 1 TB общее время холодного чтения для 22 запросов сократилось примерно на 51%.

1. Общие данные, изолированные кеши​

Кластер Doris с разделением вычислений и хранения может использовать несколько вычислительных групп для разделения чтения и записи, изоляции оперативных и пакетных нагрузок, а также гибкого масштабирования. Группы совместно используют данные и метаданные, поэтому зафиксированные изменения становятся видны другим группам.

При этом каждый BE поддерживает собственный локальный File Cache. Без Peer Read группа чтения не может напрямую использовать блоки, кешированные группой записи или другой группой чтения. Каждой группе приходится заполнять собственный кеш.

Почему холодное чтение выполняется медленно​

Объектное хранилище обеспечивает высокую пропускную способность при чтении больших объёмов данных, но задержка отдельных запросов к нему намного выше, чем при чтении с локальных дисков или по сети внутри одного центра обработки данных. Перед чтением данных таблицы многим запросам нужно прочитать футеры сегментов и индексы. Таких операций много, хотя объём данных в каждой из них невелик.

В описанной ниже нагрузке с поиском по первичному ключу на каждый запрос в среднем приходилось более 200 удалённых операций I/O, главным образом для чтения футеров и индексов. Ожидание этих небольших операций занимало значительную часть времени выполнения запроса.

Прогрев кеша и Peer Read​

В предыдущих версиях Doris уже поддерживался прогрев кеша, в том числе инкрементальный: после загрузки данных он уведомляет группы чтения. Прогрев заранее определяет, какие данные понадобятся, и загружает их из объектного хранилища до поступления запросов. Peer Read обрабатывает промахи кеша, обнаруженные во время выполнения запроса.

Эти подходы дополняют друг друга: прогрев заранее подготавливает данные, которые заведомо часто запрашиваются, а Peer Read помогает при промахах кеша во время выполнения запроса.

2. Как работает Peer Read​

Peer Read использует существующие кеши File Cache на узлах BE без отдельного сервиса кеширования. Он задействуется только при промахе локального кеша; при попадании чтение идёт по прежнему пути.

2.1 Поиск подходящих узлов​

Подходящие узлы определяются двумя способами:

  • Подсказки FE при масштабировании. При переносе таблета между узлами BE в одной вычислительной группе FE сообщает принимающему узлу об исходном BE и назначает ему наивысший приоритет. При первых чтениях блоки можно получить из кеша прежнего BE.
  • Запрос к FE по мере необходимости. Если локально нет подходящих узлов, BE в фоновом режиме запрашивает у FE, каким узлам назначен таблет в разных вычислительных группах. Текущее чтение не ждёт ответа и обращается к объектному хранилищу. При холодном запросе обычно выполняется много параллельных чтений: первое чтение футера может запустить поиск узлов, чтобы последующие чтения в том же запросе использовали их кеши.

BE также запоминает вычислительную группу, из которой в последний раз удалось прочитать данные для каждого таблета, и при следующем обращении отдаёт ей предпочтение.

2.2 Получение только недостающих блоков​

Запрашивающий узел обращается к другим узлам только за блоками, которых нет в его локальном кеше. Полученные данные используются в текущем запросе и сохраняются в локальном File Cache, чтобы при последующих чтениях тех же блоков обращаться к нему.

2.3 Дать другим узлам фору в 20 мс​

По умолчанию Peer Read конкурирует с чтением из объектного хранилища, получая настраиваемую фору в 20 мс. BE сначала отправляет запрос другому узлу. Если ответ приходит за это время, Doris не обращается к объектному хранилищу. В противном случае Doris также запускает чтение из объектного хранилища и использует результат, полученный первым.

Если сразу запускать оба чтения, при каждом промахе кеша будет отправляться запрос к объектному хранилищу. Если ждать ответа другого узла без ограничения по времени, один медленный узел может задержать выполнение запроса. Эта фора помогает сбалансировать оба вида затрат.

2.4 Автоматический переход к объектному хранилищу​

Если другой узел недоступен, не отвечает вовремя, не содержит нужного блока или для него действует ограничение частоты запросов, Doris обращается к объектному хранилищу. Неудачная попытка чтения с другого узла не приводит к сбою запроса.

Список подходящих узлов также меняется. Узел, у которого нет запрошенных данных, перемещается в конец списка. При повторяющихся сбоях RPC узел исключается из списка. Если ни один из подходящих узлов неоднократно не находит данные для таблета, Doris временно прекращает попытки чтения с других узлов для этого таблета, чтобы избежать бесполезных запросов.

2.5 Заполнение кеша через группу записи​

При развёртывании с одной группой записи и несколькими группами чтения группа записи может выступать в роли вычислительной группы, заполняющей кеш. Если её BE получает запрос на чтение, но нужного блока в его кеше тоже нет, он загружает блок из объектного хранилища, сохраняет его в своём File Cache и возвращает запросившей группе чтения.

Пока загруженная копия остаётся в кеше, она может обслуживать другие группы чтения, сокращая число отдельных загрузок одних и тех же данных. Для запросов на заполнение кеша действуют ограничения по числу одновременных операций и времени ожидания; если эти ограничения достигнуты, запрашивающая группа сама обращается к объектному хранилищу.

3. TPC-H 1 ТБ: время холодного чтения сократилось примерно вдвое​

Мы сравнили холодное чтение в группе записи и группе чтения на TPC-H объёмом 1 ТБ. Данные уже находились в кеше группы записи. Перед каждым из 22 запросов, выполнявшихся последовательно, кеш группы чтения очищали.

Конфигурация теста: TPC-H 1 ТБ; один FE с 4 ядрами CPU и 16 ГБ ОЗУ; шесть BE, каждый с 32 ядрами CPU, 128 ГБ ОЗУ и тремя облачными дисками по 500 ГБ. В группе записи и группе чтения было по три BE. Размер блока кеша составлял 1 МБ, а Peer Read работал в режиме гонки запросов с настройками по умолчанию.

С Peer Read общее время выполнения сократилось с 323.3 до 158.6 секунды. Последовательный режим, в котором сначала выполняется попытка чтения с другого узла, а затем — из объектного хранилища, дал близкий результат: 155.5 секунды. В последовательном режиме все 22 запросов выполнялись быстрее, чем при прямом чтении из объектного хранилища; ускорение отдельных запросов составляло от 1.4× до 3.3×.

Когда кеш группы записи тоже пуст​

Мы также проверили случай, когда данных не было в кеше ни одной из групп. Группа записи загружала их из объектного хранилища, сохраняла в кеше и передавала группе чтения. Общее время для 22 запросов составило 332.4 секунды, примерно на 3% больше по сравнению с прямым чтением из объектного хранилища.

В этом тесте использовались то же оборудование и последовательный режим. Дополнительная передача данных между узлами увеличила время примерно на 3%. При этом данные остались в кеше группы записи и могли обслуживать последующие запросы других групп чтения, давая преимущества, измеренные в тесте с прогретым кешем другого узла. Результат относится к этой конфигурации и не означает, что дополнительные затраты всегда будут такими же.

4. Нагрузка облачного сервиса Doris: ускорение холодных точечных запросов — 7.5×​

Пользователь облачного сервиса Doris использует одну группу записи, которая непрерывно загружает данные, и несколько групп чтения, которые обслуживают внешние API преимущественно с помощью запросов по первичному ключу. Первые запросы к новым данным выполнялись с непредсказуемой задержкой. Каждой группе чтения требовался кэш значительного объёма, из-за чего одни и те же данные дублировались между группами.

Для Peer Read администратор базы данных назначил группу записи вычислительной группой для заполнения кэша групп чтения. При отсутствии данных в локальном кэше запрос сначала направляется группе записи. Если и в её кэше данных нет, она получает их от имени запрашивающей группы.

Пользователь протестировал 100 запросов по первичному ключу к таблице бизнес-данных с моделью Unique Key. Сначала группа записи прогрела данные. Затем пользователь очистил кэш группы чтения, перезапустил её и выполнил те же 100 запросов с отключённым и включённым Peer Read. Запросы обращались к 100 разным таблетам и выполнялись последовательно, по одному разу каждый.

В каждой вычислительной группе был один BE; тест состоял из одного последовательного прогона. Эти показатели получены в среде облачного сервиса Doris, используемого этим пользователем.

Во всех 100 запросах данные были получены от других узлов, а при включённом Peer Read запросы выполнялись быстрее. Средняя задержка снизилась примерно на 87%, ускорение составило 7.5× ; задержка P99 снизилась примерно на 80%. Число обращений к объектному хранилищу сократилось примерно до 1.7% от исходного, что уменьшило часть расходов на хранение, зависящую от числа запросов.

Точечные запросы выиграли больше, чем запросы TPC-H с большим объёмом сканирования: их задержка в основном складывалась из множества операций чтения небольших концевых блоков сегментов и индексов. Peer Read сократил ожидание каждой такой операции.

Чтение из локального кэша по-прежнему выполнялось примерно на порядок быстрее. Peer Read сокращает задержку холодного чтения, пока заполняется локальный кэш; чтение из локального кэша остаётся самым быстрым вариантом.

5. Включение Peer Read в Apache Doris​

В Apache Doris 4.2 Peer Read доступен как экспериментальная функция и по умолчанию отключён.

Настройка​

  1. Включите File Cache на каждом BE, задав enable_file_cache = true.
  2. Задайте enable_cache_read_from_peer = true на каждом BE. Этот параметр управляет чтением с других узлов как внутри вычислительной группы, так и между группами.
  3. Чтобы включить заполнение кэша в конфигурации с одной группой записи и несколькими группами чтения, задайте peer_cache_fill_compute_group_id на каждом BE в каждой группе чтения, отправляющей запросы. Для группы записи укажите идентификатор вычислительной группы, а не её имя.

См. документацию Doris 4.x по Peer Cache Read с инструкциями по настройке, описанием параметров и рекомендациями по устранению неполадок.

Проверка пути чтения​

Проверьте следующие счётчики в разделе SegmentIterator в Query Profile:

СчётчикЗначение
NumPeerIOTotalКоличество чтений с других узлов
CrossCGPeerIOTotalКоличество чтений с узлов в других вычислительных группах
PeerRaceWin / S3RaceWinКоличество гонок запросов, в которых победили соответственно другой узел и объектное хранилище

Особенности эксплуатации​

  • При чтении между группами используются сеть и диски группы, к которой принадлежит другой узел. Группа, заполняющая кеш, также расходует пропускную способность объектного хранилища и ёмкость кеша. Отключайте Peer Read там, где требуется строгая изоляция ресурсов.
  • Чтение с узлов в других зонах доступности может повлечь плату за межзональный трафик.
  • Если S3RaceWin значительно превышает PeerRaceWin, значит в этой среде чтение с другого узла не быстрее. Если важно сократить число запросов к объектному хранилищу, попробуйте увеличить peer_race_hedge_delay_ms. Если важнее задержка, а чтение с других узлов даёт мало пользы, рассмотрите возможность отключить Peer Read.
  • Peer Read применяется к внутренним таблицам в режиме разделения вычислений и хранения данных. При чтении внешних таблиц, например Hive и Iceberg, этот механизм не используется.

6. Повторное использование кешированных данных между группами​

Peer Read позволяет вычислительной группе использовать блоки, уже кешированные в других узлах кластера. Это помогает при чтении недавно загруженных данных, первом обращении к узлам после масштабирования и повторном обращении к данным после их вытеснения из кеша — без отдельного сервиса кеширования. Если другой узел не может предоставить данные, Doris обращается к объектному хранилищу.

В тесте TPC-H объёмом 1 TB общее время холодного чтения сократилось примерно вдвое. В нагрузке пользователя облачного сервиса Doris со запросами по первичному ключу средняя задержка холодных запросов снизилась с 4.45 до 0.59 секунды. На момент публикации исходной статьи выпуск Apache Doris 4.2 ещё планировался; оцените экспериментальную реализацию Peer Read на своей нагрузке с учётом требований к изоляции ресурсов.
