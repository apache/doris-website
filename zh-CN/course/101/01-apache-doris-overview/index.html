数据组织

Doris 如何 组织 数据？

先了解逻辑层级，再深入看看表如何在集群中划分和分布。

  1. Catalog数据源

  3. TableSchema + 属性
  4. 分区逻辑范围

学习提示

表是逻辑结构落到存储的地方。

Catalog 标识数据源，Database 划定逻辑边界，Table 定义 schema 和属性。在表内部，分区隔离数据范围，分桶分布数据以便并行处理。

记住这个区别

分区回答“数据属于哪个范围？”，分桶回答“数据分布在哪里、如何分布？”

列式存储

为什么要按 列存储数据?

分析查询通常只访问大量数据行中的少数几列。列式存储让 Doris 只读取和处理查询所需的数据。

I/O减少读取量

只扫描查询引用的列。

ZIP提高压缩率

类型相同且相近的值更容易紧凑编码。

CPU批量处理

连续存放的向量能提高缓存利用率，并支持 SIMD。

学习提示

列式布局减少无用功。

同一列的值具有相同类型，分布也往往相近。这有利于编码、压缩、CPU 缓存利用和批量处理。

可以这样理解

行式存储把完整记录放在一起；列式存储把同一字段的值放在一起。

表模型

当 Key 重复时会怎样?

表模型决定 Doris 是保留每一行、合并值，还是为每个 Key 维护一条逻辑数据行。

DUPDuplicate Key

保留每条输入数据，适合事件明细和日志。

AGGAggregate Key

使用声明的聚合函数合并 Value 列。

UNIUnique Key

为每个 Key 保留一条逻辑数据行，适合更新和 CDC。

学习提示

加载数据前，先确定数据行的处理方式。

Duplicate Key 适合不可变的明细数据；Aggregate Key 按声明的聚合方式存储预聚合结果；Unique Key 支持以 UPSERT 方式更新的记录。

生产环境注意事项

表创建后无法更改表模型。选择前，请确认所需的更新行为。

存算一体架构

认识经典的 FE + BE 集群。

在存算一体架构中，Frontend 节点负责协调系统，Backend 节点负责执行查询，并将 tablet 副本持久化到本地存储。

  1. SQL 客户端MySQL 协议
  2. Frontend解析 + 规划 + 协调
  3. Backend存储 + 执行
学习提示

控制与数据处理各有分工。

FE 负责身份验证、SQL 解析与规划、元数据管理和协调。BE 存储 tablet、运行向量化算子、执行数据压实，并参与副本修复和均衡。

高可用性

生产环境会部署多个 FE 节点，并按需配置 tablet 副本数。FE 使用 BDB JE 复制元数据，无需 ZooKeeper。

存算分离架构

当存储与计算 分离时，会发生什么变化?

无状态计算组可以独立扩缩容，持久数据则保存在共享存储中。

  1. 01
    SQL 与元数据层

    FE 提供 SQL 服务；Meta Service 管理数据层元数据。

  2. 02
    计算组

    无状态 BE 节点执行计算并缓存热数据。

  3. 03
    共享存储

    对象存储或受支持的分布式文件系统负责持久化数据。

学习提示

弹性伸缩也带来了额外的运维工作。

FE 负责请求和 SQL 层元数据，Meta Service 管理数据层元数据；无状态 BE 节点缓存热数据，并基于共享持久存储执行计算。

运维上的权衡

共享存储必须可靠；缓存未命中时读取数据可能增加延迟；平台团队还需要运维额外的服务。

选择架构

从实际约束出发，不要只看哪种架构 更新.

存算一体和存算分离适合不同的运行环境，没有哪种架构在所有场景下都更好。

存算一体

有状态 BE 节点执行计算，并在本地持久化数据。

  • 运维复杂度较低
  • 访问本地存储
  • 计算与存储一起扩缩容
存算分离

无状态计算组共享持久存储。

  • 计算资源独立弹性伸缩
  • 计算组之间隔离工作负载
  • 依赖更多平台组件
学习提示

简单易用与弹性伸缩需要权衡。

存算一体通常更容易作为起点。如果确实需要共享存储、平台团队统一运维、独立扩缩容或隔离的计算组，存算分离就值得考虑。

选择原则

不要仅仅因为存算分离架构更新就选择它。增加的组件必须用于解决具体问题。

如果可以使用本地磁盘，且计算资源可以随存储一起扩容，应从哪种架构开始？

核心引擎模块

两个引擎协同，以 更少的工作、更快的速度.

存储引擎组织数据和访问路径；查询引擎将 SQL 转换为分布式向量化流水线。

COL列式存储

读取所需的列，并压缩分析数据。

IDX索引

Prefix、Min/Max、Bloom 和倒排索引用于裁剪扫描范围。

MPP分布式处理

将查询执行分布到多个 Backend 节点。

OPT优化器

应用基于规则、成本和历史信息的优化策略。

学习提示

优化从执行前就开始。

排序键、分区、索引和表模型减少需要访问的数据量。MPP、向量化、Pipeline 调度和优化器则降低处理剩余数据的成本。

MPP 与 Pipeline

MPP 将工作分布到多个节点；Pipeline 执行在每个节点内跨 CPU 核心调度算子工作。

查询执行

跟随 SQL，从文本走向 分布式流水线.

查询经过校验和优化后，被拆分为片段和实例，在多个 BE 节点上执行，最后汇总为结果。

  1. 解析校验 SQL
  2. 规划重写 + 成本估算
  3. 片段拆分分布式工作
  4. 执行运行向量化流水线
  5. 返回汇总结果
学习提示

片段描述工作，实例执行工作。

片段是分布式计划中的一个逻辑部分；实例是在 BE 上运行的一个物理副本。需要重新分布数据时，Exchange 算子在实例之间传输数据行。

向量化执行

算子按列批量处理数据，而不是逐行处理，从而减少每行的处理开销，提高 CPU 效率。

优化与回顾

最快的工作，是 Doris 可以 省去的工作.

Doris 通过预计算、逻辑重写、基于统计信息的计划生成和运行时过滤，在执行前及执行过程中减少需要处理的数据。

MV物化视图

通过查询重写复用预计算结果。

RBO基于规则

应用确定性的逻辑变换。

CBO基于成本

利用统计信息比较物理计划。

RF运行时过滤器

将过滤条件推向扫描阶段，尽早剔除数据行。

学习提示

优化贯穿多个阶段。

物化视图可以避免重复计算，RBO 简化计划，CBO 比较预估成本，运行时过滤器则在关联查询期间尽早剔除数据行。
