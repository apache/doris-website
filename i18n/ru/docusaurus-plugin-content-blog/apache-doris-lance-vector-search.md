Нагрузки, связанные с автономным вождением и мультимодальным поиском, быстро растут. Запросу часто недостаточно найти ближайшие векторы: результаты нужно отфильтровать по типу транспортного средства, времени, устройству или региону, затем соединить с бизнес-данными и вычислить агрегаты.

Если выделить векторный поиск в отдельный сервис, процесс усложняется. Приложение получает кандидатов, переносит их в базу данных или аналитический движок и формирует итоговый результат. По мере роста наборов данных перенос данных и координация между системами обходятся всё дороже.

Doris и Lance распределяют работу иначе. Lance предоставляет мультимодальное хранилище, а также векторные и полнотекстовые индексы. Doris планирует запросы, выполняет их в кластере и проводит остальные операции SQL. К существующим наборам данных Lance можно обращаться напрямую, объединяя фильтрацию, векторный поиск, соединения, агрегацию и сортировку в одном SQL-запросе.

В тесте на данных автономного вождения **Doris + Lance выполнили векторный поиск с четырьмя фильтрами по одному миллиарду записей за 2.32 секунды, тогда как Ray + pylance потребовалось 25.228 секунды**, то есть время выполнения различалось примерно в 10.87×. В тесте использовались Top-K 20,000, полнота поиска 95%, включённые кеши; одновременных запросов не было. Полные результаты и их ограничения приведены ниже.

## 1. Архитектура {#1-architecture}

Набор данных Lance содержит файлы данных, метаданные версий, фрагменты данных и индексы. Doris читает эти метаданные при планировании запроса. Фронтенд (FE) планирует работу, а бэкенды (BEs) читают данные и выполняют поиск. Результаты поиска напрямую поступают в другие операторы Doris для соединения и агрегации.

![Doris FE планирует доступ к наборам данных Lance, а BEs выполняют поиск и операции SQL, в том числе с таблицами бизнес-данных](/images/blogs/apache-doris-lance-vector-search/architecture.jpg)

Doris поддерживает два варианта каталогов. Filesystem Catalog обнаруживает наборы данных по каталогам файловой системы, а REST Catalog — через сервис Lance Namespace. Сами данные могут находиться в локальной файловой системе, объектном хранилище, совместимом с S3, или OSS. Для разовых запросов к набору данных можно обращаться напрямую через табличную функцию для файлов (TVF) с поддержкой формата Lance.

Doris предоставляет векторный поиск через `vector_search()` а полнотекстовый поиск Lance (FTS) — через `full_text_search()`. Полнотекстовый поиск позволяет искать любое из слов (Match OR), все слова (Match AND) или фразу. Для поиска фразы нужен индекс, хранящий позиции токенов. В режиме строгого покрытия, который используется по умолчанию, индекс должен быть у всех фрагментов выбранной версии набора данных; для фрагментов без индекса автоматический переход к полному сканированию не выполняется. Результаты обеих поисковых функций можно затем анализировать средствами SQL. Для объединения ранжирования по векторам и по тексту необходимо явно задать правила слияния результатов и расчёта оценок.

Запрос выполняется в три основных этапа:

1. **Планирование работы.** FE читает схему, версию набора данных, список фрагментов и сведения об индексном покрытии. На этой основе он определяет типы столбцов, столбцы для чтения и границы задач. Каждый запрос использует фиксированную версию набора данных.
2. **Чтение и поиск.** BEs обращаются к Lance через lance-c, получают данные Arrow и преобразуют их в Doris Blocks для последующих операторов.
3. **Анализ результатов.** Результаты можно использовать в соединениях, агрегации, сортировке и постраничной выдаче, в том числе в запросах к внутренним таблицам Doris или другим каталогам.

Приложение может описать получение и анализ данных в одном запросе, не выполняя отдельные соединения и расчёты после получения результатов из Lance.

## 2. Параллельный поиск {#2-parallel-search}

Распределённый поиск начинается с определения границ задач. Если границы выбраны неудачно, задачи могут многократно считывать одни и те же данные индекса; если задач слишком мало, ресурсы BE используются не полностью.

Doris разбивает задачи поиска в Lance по **физическим сегментам индекса**. Сегмент индекса и фрагмент данных — разные единицы: один сегмент индекса может охватывать несколько фрагментов. Перед назначением задач сканирования Doris считывает информацию об их соответствии.

![FE назначает физические сегменты индекса параллельным задачам ANN, а фрагменты без индекса — задачам поиска полным перебором, после чего объединяет результаты в глобальный Top-K](/images/blogs/apache-doris-lance-vector-search/parallel-search.jpg)

Для векторного поиска FE находит индекс, соответствующий векторному столбцу и метрике расстояния, а затем распределяет его сегменты между BE. Для фрагментов выбранной версии, не охваченных индексом, создаются задачи поиска полным перебором: они сканируют данные напрямую. Их результаты участвуют в том же итоговом объединении.

Doris сортирует найденных кандидатов и выбирает глобальный Top-K. Поиск по данным, охваченным индексом, использует индекс; остальные данные тоже участвуют в запросе. Если индекс использует приближённый поиск ближайших соседей (ANN), полнота результатов по-прежнему зависит от типа индекса и параметров поиска.

Обычное сканирование с фильтрацией тоже может использовать индексы. Некоторые предикаты равенства, диапазона, `IN`, а также предикаты по меткам массивов могут использовать индексы Lance BTree, Bitmap или LabelList. Там, где это поддерживается, Doris организует сканирование по сегментам индекса и также сканирует данные, не охваченные индексом. Возможность использовать индекс зависит от предиката и типа индекса.

Размер сегментов влияет на эффективность параллельной обработки. Достаточное число сегментов позволяет распределить работу между несколькими BE; чрезмерное дробление увеличивает затраты на планирование задач, открытие индексов и объединение результатов. Выбирайте разбиение с учётом распределения данных, числа BE и количества одновременно выполняемых запросов.

## 3. Фильтрация до поиска {#3-filtering-before-search}

Параллельная обработка помогает использовать ресурсы кластера, но сокращение области поиска может сэкономить ещё больше работы. От того, на каком этапе применяется фильтр, зависит и число результатов запроса. Если нужны похожие записи для определённого типа транспортного средства, поиск по всем записям с последующим исключением других типов может дать меньше K результатов.

В `vector_search()` и `full_text_search()`, `filter` задаёт предикат, а `prefilter` определяет, когда он применяется. **По умолчанию используется `prefilter=false`.** Явно установите `"prefilter"="true"` , чтобы выполнить фильтрацию до отбора кандидатов для поиска.

![Предварительная фильтрация сначала сужает область поиска; последующая фильтрация и внешнее условие WHERE могут исключить кандидатов после их получения](/images/blogs/apache-doris-lance-vector-search/prefiltering.jpg)

В этом примере поиск ограничен типом транспортного средства и регионом. Используется демонстрационный четырёхмерный вектор, а запрос возвращает Top-20 результатов; в бенчмарке ниже используется Top-K 20,000. Замените таблицу, столбцы и значения своими, а размерность вектора и параметр `metric` приведите в соответствие с набором данных и индексом.

```sql
SELECT scene_id, scene_text, resource_uri, _distance
FROM vector_search(
    "table" = "lance_demo.autodrive.scene_samples",
    "column" = "embedding",
    "query_vector" = "[0.12, 0.34, 0.56, 0.78]",
    "top_k" = "20",
    "metric" = "cosine",
    "filter" = "vehicle_type = 'sedan' AND region_code = 'zone_a'",
    "prefilter" = "true",
    "use_index" = "true"
)
ORDER BY _distance ASC, scene_id;
```

При `prefilter=true`Lance применяет фильтр функции до отбора кандидатов. Подходящий скалярный индекс может сузить область поиска; в противном случае для проверки предиката всё ещё может потребоваться сканирование. Экономия зависит от наличия индекса и селективности фильтра.

При значении по умолчанию `prefilter=false`Lance сначала отбирает кандидатов, а затем применяет фильтр функции `filter`. Внешнее условие SQL `WHERE` дополнительно фильтрует результаты в Doris. В обоих случаях часть найденных записей может быть исключена, и строк останется меньше K.

При обычном сканировании данных Lance Doris может передавать поддерживаемые предикаты SQL в Lance. Некоторые динамические фильтры соединения также могут преобразовываться в предикаты `IN` или предикаты диапазона — в зависимости от совместимости предикатов и типов. При использовании поисковых функций явно задавайте `prefilter` , чтобы управлять порядком фильтрации.

## 4. Чтение выходных столбцов по мере необходимости {#4-reading-output-columns-on-demand}

Для поиска могут понадобиться только расстояния и несколько столбцов для фильтрации, тогда как итоговый результат включает длинные тексты, метки и пути к ресурсам. Если читать все эти столбцы сразу, на кандидатов, которые не попадут в результат, будут напрасно расходоваться ресурсы ввода-вывода и передачи данных.

Для подходящих запросов векторного и полнотекстового поиска Doris может разделить чтение на два этапа: сначала выбрать результаты, а затем загрузить остальные выходные столбцы.

![На первом этапе столбцы для поиска, идентификаторы строк и оценки проходят через отбор Top-K; на втором загружаются столбцы для отображения выбранных строк](/images/blogs/apache-doris-lance-vector-search/late-materialization.jpg)

При первом чтении возвращаются данные, необходимые для поиска, фильтрации и вычислений, а также идентификаторы строк и расстояния или оценки. После того как Doris выберет глобальные Top-K результатов, при втором чтении он загрузит остальные выходные столбцы по идентификаторам строк.

Это сокращает объём чтения и передачи столбцов, которые нужны только после определения итогового результата. Чтение данных, необходимых для поиска и фильтрации, при этом сохраняется. Оптимизация особенно полезна, когда итоговый результат невелик, а каждая запись содержит объёмный текст или множество атрибутов.

Оба чтения используют одну и ту же версию набора данных, поэтому извлечённая строка и её содержимое, загруженное позже, остаются согласованными. Doris также позволяет выбирать снимки Lance по версии, времени или именованной ссылке для воспроизводимых запросов. В [подробном разборе отложенной материализации](/blog/apache-doris-lance-lazy-materialization) описана реализация.

## 5. Кеширование и диагностика {#5-caching-and-diagnostics}

Повторяющиеся запросы часто обращаются к одним и тем же индексам и файлам. Кеширование сокращает число повторных загрузок индексов, разборов метаданных и чтений из объектного хранилища.

В пределах каждого BE Doris использует общий сеанс Lance. Обычное сканирование, векторный и полнотекстовый поиск, а также загрузка строк по идентификаторам могут повторно использовать соответствующие кеши этого сеанса.

![Сканирование, поиск и загрузка строк по идентификаторам используют общий сеанс Lance в пределах одного BE, включая кеши индексов и метаданных в памяти и локальный кеш данных](/images/blogs/apache-doris-lance-vector-search/caching.jpg)

Каждый BE управляет собственными кешами; у BE нет общего пула кеша Lance. Кроме того, ёмкость кеша отражает лишь часть расхода памяти. Дополнительная память нужна задачам сканирования, предварительной загрузке и сортировке.

Используйте `EXPLAIN`, Query Profile и метрики BE для анализа задержки. План показывает границы задач. Профиль позволяет оценить время открытия набора данных, загрузки индексов, удалённого чтения, преобразования формата и загрузки столбцов на втором этапе. Доля попаданий в кеш индексов и метаданных и заполненность этих кешей измеряются на уровне BE и могут отражать работу нескольких запросов.

Сначала проверьте, использовал ли запрос индекс или полный перебор. Затем выясните, что занимает больше всего времени: фильтрация, чтение данных, поиск или загрузка выходных столбцов. Определения метрик приведены в [справке по Lance Query Profile](https://doris.apache.org/docs/dev/lakehouse/best-practices/lance-query-profile/) .

## 6. Анализ результатов поиска с помощью SQL {#6-sql-analysis-after-retrieval}

Результаты поиска можно использовать в SQL как таблицу. Doris передаёт их операторам соединения, агрегации и сортировки. Например, один запрос может найти похожие образцы в Lance, соединить их с метками из внутренней таблицы Doris и подсчитать образцы по категориям.

![Поиск по эмбеддингам передаёт результаты соединениям с бизнес-данными и анализу с помощью SQL для формирования отобранного набора сцен](/images/blogs/apache-doris-lance-vector-search/search-to-analysis.jpg)

Следующий запрос извлекает Top-20 образцов для выбранного типа транспортного средства и региона, затем соединяет их с `internal.demo.scene_labels` для подсчёта сцен по категориям. Предполагается, что `scene_id` уникален в наборе данных Lance, а таблица меток содержит по одной записи для каждого `scene_id`. Четырёхмерный вектор и метрика приведены для примера: они должны соответствовать вашим данным и индексу.

```sql
WITH candidates AS (
    SELECT scene_id
    FROM vector_search(
        "table" = "lance_demo.autodrive.scene_samples",
        "column" = "embedding",
        "query_vector" = "[0.12, 0.34, 0.56, 0.78]",
        "top_k" = "20",
        "metric" = "cosine",
        "filter" = "vehicle_type = 'sedan' AND region_code = 'zone_a'",
        "prefilter" = "true",
        "use_index" = "true"
    )
    ORDER BY _distance ASC, scene_id
    LIMIT 20
)
SELECT
    COALESCE(l.scene_type, 'Uncategorized') AS scene_type,
    COUNT(*) AS sample_count
FROM candidates c
LEFT JOIN internal.demo.scene_labels l
    ON c.scene_id = l.scene_id
GROUP BY COALESCE(l.scene_type, 'Uncategorized')
ORDER BY sample_count DESC, scene_type;
```

`candidates` задаёт результаты поиска, `LEFT JOIN` добавляет категории, а `GROUP BY` подсчитывает образцы в каждой из них. Отсутствующие метки и категории со значением NULL отображаются как `Uncategorized`. Приложение получает агрегированный результат напрямую.

Эти подсчёты относятся к возвращённым образцам Top-K, а не ко всему набору данных. Чтобы подсчитать образцы во всём наборе, просканируйте таблицу Lance и выполните агрегацию напрямую. Предикаты типа транспортного средства и региона внутри функции поиска ограничивают область поиска при выборе кандидатов.

## 7. Результаты тестирования {#7-benchmark-results}

В тестировании сравниваются Doris + Lance и Ray + pylance на наборах данных автономного вождения с 100 млн, 500 млн и одним миллиардом записей. Рассматриваются шесть типов запросов: векторный поиск без фильтров и векторный поиск с фильтром по устройству, времени, типу транспортного средства, географическому признаку или с четырьмя фильтрами одновременно.

**Во всех тестах использовались Top-K 20,000 и полнота поиска 95%; кеши были включены, параллельных запросов не было. Время указано в секундах.** Ray использовал четыре актора для 100 млн записей и 16 акторов для 500 млн и одного миллиарда записей. Включённые кеши не означают, что каждое чтение происходило из кеша. В доступных данных не указаны аппаратные конфигурации обеих систем, количество BE в Doris и способ агрегирования времени выполнения. Результаты показывают время выполнения в этом тесте; их не следует считать сравнением с нормализацией по аппаратной конфигурации.

| Фильтр по типу транспортного средства | 0.53 | 1.689 | 3.19× |
| Фильтр по географическому признаку | 1.19 | 12.908 | 10.85× |
| Четыре фильтра одновременно | 2.32 | 25.228 | 10.87× |

При поиске по одному миллиарду записей фильтрация по географическому признаку и поиск с четырьмя фильтрами заняли у Doris 1.19 и 2.32 секунды соответственно — примерно на 90.8% меньше времени, чем у Ray + pylance. Поиск с фильтром по времени ускорился с 6.044 до 0.73 секунды; отношение времени выполнения составило около 8.28×.

Планирование с учётом индексов, предварительная фильтрация, параллельный поиск и чтение столбцов по мере необходимости — всё это влияет на выполнение запроса. В тесте эти оптимизации не отключались по отдельности, поэтому определить вклад каждой из них нельзя.

## 8. Доступность и дальнейшие шаги {#8-availability-and-next-steps}

На момент публикации исходной статьи в октябре 2026 года эту интеграцию планировали для Apache Doris 4.2. В [документации по Lance Catalog](https://doris.apache.org/docs/4.x/lakehouse/catalogs/lance-catalog/) описаны её экспериментальный статус и требования к совместимости.

Doris использует Lance на всех этапах выполнения запроса: сегменты индекса распределяют работу между узлами BE, предварительная фильтрация сужает область поиска, поздняя материализация сокращает чтение выходных столбцов, а кеши позволяют повторно использовать индексы, метаданные и содержимое файлов. Благодаря этим механизмам существующие наборы данных Lance можно использовать для поиска и SQL-аналитики без этапа сборки данных в приложении.

Результаты тестирования показывают потенциал векторного поиска по большим наборам данных с бизнес-фильтрами. Оцените выигрыш на собственных данных, индексах и инфраструктуре. Более широкий пример применения приведён в статье [Apache Doris и Lance для аналитики в области физического ИИ](/blog/apache-doris-lance-physical-ai-analytics).
