Запросы для автономного вождения, поиска по базам знаний и мультимодального поиска часто решают сразу несколько задач: находят похожие записи, применяют бизнес-фильтры и возвращают текст и атрибуты. По мере роста наборов данных задержка зависит как от скорости поиска, так и от объёма данных, которые считывает, обрабатывает и передаёт конвейер выполнения.

В [предыдущей статье](/blog/apache-doris-lance-vector-search) описан тест на миллиарде записей: векторный поиск с четырьмя фильтрами занял 2.32 секунды с Doris + Lance и 25.228 секунды с Ray + pylance. Соотношение задержек составило около 10.87×. При том же масштабе Doris + Lance выполнил векторный поиск без фильтров за 0.43 секунды, а с фильтром по времени — за 0.73 секунды.

В этом процессе совместно работают планирование запросов, параллельный поиск, предварительная фильтрация, чтение столбцов по требованию и кеширование. Эта статья посвящена **отложенной материализации**, также называемой **двухэтапным чтением**. Столбцы, нужные только для окончательного вывода, считываются после TopN. Благодаря этому на чтение и передачу содержимого кандидатов, которые затем будут отброшены, не тратятся ресурсы.

## Зачем откладывать чтение некоторых столбцов? {#why-read-some-columns-later}

Предположим, таблица базы знаний в Lance содержит `id`, `title`, `body` и `embedding`. Следующий запрос возвращает 20 наиболее релевантных документов:

```sql
SELECT id, title, body, _distance
FROM vector_search(
    "table" = "lance_catalog.demo.documents",
    "column" = "embedding",
    "query_vector" = "[0.1, 0.2, 0.3, 0.4]",
    "metric" = "l2",
    "top_k" = "20"
)
ORDER BY _distance ASC;
```

Четырёхмерный вектор приведён для примера; используйте вектор и метрику расстояния, совместимые с вашим набором данных и индексом.

Запросу нужны все четыре выходных значения, но на разных этапах. `_distance` нужно получить до ранжирования. В этом примере `title` и `body` нужны только для вывода, поэтому их чтение можно отложить до отбора результатов. Можно ли отложить чтение бизнес-идентификатора `id` зависит от того, используется ли он при фильтрации, сортировке или других вычислениях.

Если считывать полный текст документа при формировании кандидатов, затраты на ввод-вывод, декодирование и передачу данных возникают и для документов, которые не попадут в результат. При распределённом выполнении эти затраты растут: несколько частей поисковой задачи формируют локальных кандидатов, которых Doris объединяет в глобальном TopN. Некоторые кандидаты так и не попадают в окончательный результат, хотя их содержимое уже было загружено и прошло через преобразование Arrow, передачу Block и сортировку.

Отложенная материализация меняет порядок работы: **сначала по необходимым данным отбираются результаты, затем для выбранных строк считывается остальное содержимое**. Наибольшую экономию дают широкие столбцы, например длинные тексты документов и объёмные атрибуты.

![При ранней материализации ранжируются полные строки-кандидаты, а при двухэтапном чтении сначала ранжируются ID и оценки, после чего считываются данные выбранных строк](/images/blogs/apache-doris-lance-lazy-materialization/eager-vs-two-phase.jpg)

## Как работают вместе два этапа {#how-the-two-phases-work-together}

В этой оптимизации совместно работают оптимизатор Doris, система распределённого выполнения и механизм чтения отдельных строк Lance. FE определяет выходные столбцы, чтение которых можно отложить, и добавляет в физический план узел материализации. Узлы BE выполняют поиск, фильтрацию и TopN, а затем по сохранённым локаторам строк пакетно считывают остальные столбцы.

| Этап | Основная работа | Передаваемые данные |
| --- | --- | --- |
| Этап 1: выбор результатов | Формирование кандидатов, необходимая фильтрация и ранжирование | Столбцы, необходимые на раннем этапе, расстояние или оценка релевантности и скрытые локаторы строк |
| Этап 2: формирование полного результата | Чтение столбцов по ID строк и восстановление порядка результатов | Отложенные выходные столбцы выбранных строк |

![FE планирует работу с зафиксированным снимком данных; узлы BE выполняют параллельный поиск, глобальный TopN и материализацию для этой версии набора данных Lance](/images/blogs/apache-doris-lance-lazy-materialization/distributed-architecture.jpg)

Для запроса, к которому применима эта оптимизация, процесс выглядит так:

```text
Lance search splits
  → required early columns + score/distance + hidden row locator
  → Doris filtering / local TopN / exchange / global TopN
  → Materialize: batch row-ID fetch
  → restore result order and assemble output
```

Точное расположение TopN, Exchange, Project и Filter зависит от плана. Главное, что отложенные столбцы не попадают в поток кандидатов, пока оптимизированный TopN не выберет строки.

При такой схеме возникают два вопроса реализации: чтение каких столбцов можно отложить и как Doris затем точно получит их значения?

## Этап 1: чтение только необходимых столбцов {#phase-1-read-only-the-required-columns}

### Отслеживание зависимостей столбцов {#trace-column-dependencies}

Возможность отложить чтение столбца зависит от того, как он используется. Даже большой столбец с текстом документа приходится читать сразу, если его значение нужно для предварительной фильтрации или сортировки.

При постобработке физического плана Nereids `LazyMaterializeTopN` начинает с выходных слотов TopN и отслеживает происхождение каждого столбца. `MaterializeProbeVisitor` обходит план и проверяет, нужен ли столбец заранее для сортировки, фильтрации или другого оператора, а также восходит ли он к исходному столбцу, значения которого можно получить по ID строки.

Значения ключей сортировки нужны до TopN. Значения столбцов, используемых остаточными фильтрами на стороне Doris, нужны до применения этих фильтров. Выражения, которые Project вычисляет на раннем этапе, также определяют, какие входные столбцы необходимо сохранить. Оптимизатор отслеживает псевдонимы и зависимости от исходных столбцов, чтобы при исключении одного выходного столбца не удалить входной столбец, который всё ещё нужен другому.

![Расстояние и столбцы для остаточных фильтров остаются на первом этапе, а столбец с текстом документа, нужный только для вывода, можно получить после глобального TopN](/images/blogs/apache-doris-lance-lazy-materialization/column-eligibility.jpg)

| Использование столбца | Обработка | Причина |
| --- | --- | --- |
| Векторное расстояние `_distance` или оценка полнотекстового поиска `_score` | Сохранять при поиске и ранжировании | Эти значения формируются при поиске; их нельзя получить как значения обычных хранимых столбцов |
| Ключи сортировки на стороне Doris или входные столбцы остаточных фильтров | Читать на раннем этапе | Для выбора кандидатов операторам нужны фактические значения |
| Входные столбцы выражений, вычисляемых на раннем этапе | Сохранять с учётом зависимостей выражений | Для вычисления выражения нужны эти входные значения |
| Столбцы верхнего уровня, используемые только для вывода, такие как `title` и `body` | Откладывать чтение, когда это возможно | После выбора строк их значения можно получить из исходного набора данных |

### Сокращение проекций и сохранение локаторов {#prune-projections-and-retain-locators}

После определения столбцов, которые можно отложить, `LazySlotPruning` корректирует выходные данные сканирования и вышестоящих операторов. Он исключает отложенные столбцы из первого этапа и добавляет скрытый столбец с глобальным локатором строки. Затем оптимизатор создаёт `PhysicalLazyMaterialize`, сохраняя сведения о столбцах, которые нужно извлечь, их исходных отношениях и столбце локаторов для каждого отношения.

На BE `LanceTableReader` создаёт сканер с сокращённой проекцией. Когда требуется последующее извлечение данных, он вызывает `lance_scanner_with_row_id(scanner, true)` для получения нативных идентификаторов строк Lance. Конвертер помещает их во внутренний локатор Doris, который может передаваться между операторами и BE.

Таким образом, тело документа можно не включать в данные кандидата, сохранив информацию, необходимую для его последующего извлечения.

## Этап 2: извлечение содержимого выбранных строк {#phase-2-fetch-the-selected-contents}

После того как TopN выбирает строки, на втором этапе извлекаются остальные выходные столбцы. При этом необходимо сохранить согласованность снимка данных и порядок результатов, организовав эффективное чтение.

### Фиксация снимка данных и поиск строки {#pin-the-snapshot-and-locate-the-row}

Lance возвращает нативные `uint64` идентификаторы строк. Doris помещает каждый из них во внутренний локатор с версией, содержащий исходный BE, идентификатор сопоставления в пределах запроса и идентификатор строки Lance.

Идентификатор сопоставления указывает на сохранённый контекст сканирования, а не на физическое имя файла. Идентификатор строки Lance также нельзя считать просто номером строки в файле Parquet или ORC.

Сохранённый контекст содержит URI набора данных, зафиксированную версию и параметры доступа к хранилищу. На втором этапе эти значения восстанавливаются по идентификатору сопоставления, после чего открывается тот же снимок набора данных. Версия снимка хранится в контексте, поэтому её не нужно повторять в каждом локаторе.

**На обоих этапах идентификаторы строк должны относиться к одному и тому же снимку данных.** Если на первом этапе выбрана строка из версии V, на втором этапе её нужно извлечь из V, а не открывать `latest`. `LanceTableReader::read_by_row_ids` поэтому требует фиксированную версию и открывает набор данных через общий `LanceSessionManager`.

### Распределение запросов и пакетное извлечение данных {#route-requests-and-fetch-in-batches}

Оператор материализации декодирует скрытые локаторы и группирует `multiget_data_v2` запросы по исходным BE. Принимающий BE находит сохранённый контекст сканирования, затем сортирует идентификаторы строк и удаляет повторы в пределах каждого сопоставления, формируя пакетный запрос.

![Выбранные строки содержат идентификаторы BE, идентификаторы сопоставления и идентификаторы строк Lance; сгруппированные запросы позволяют найти зафиксированный снимок данных, извлечь строки и восстановить порядок результатов](/images/blogs/apache-doris-lance-lazy-materialization/row-id-fetch.jpg)

На пути чтения, предназначенном для Lance, `RowIdStorageReader` использует `LanceTableReader::read_by_row_ids` для вызова API уровня набора данных. Он извлекает столбцы по идентификатору строки без повторного создания обычного `FileScanner` для сканирования фрагмента, в котором формировались кандидаты:

```cpp
lance_dataset_take_rows(
    dataset,
    row_ids.data(),
    row_ids.size(),
    projected_columns,
    &arrow_stream
);
```

`projected_columns` содержит только столбцы, необходимые на втором этапе. SDK возвращает `ArrowArrayStream`. Doris импортирует его в `RecordBatchReader`, считывает пакеты и преобразует их в Doris Blocks.

Некоторые операции чтения Lance выполняются только при обработке потока Arrow. Поэтому при измерении времени извлечения данных нужно учитывать как вызов API, так и последующие `ReadNext` вызовы. Общий сеанс может повторно использовать соответствующие кэши метаданных и данных, но второй этап всё равно требует времени на открытие набора данных, запросы по идентификаторам строк, чтение из хранилища, декодирование и преобразование.

### Восстановление порядка и формирование результата {#restore-order-and-assemble-output}

Сортировка и удаление повторяющихся ID строк меняют порядок чтения из хранилища, а ответы от разных BE могут поступать в любом порядке. Doris сопоставляет позиции в результате с позициями при чтении и исходными BE, а затем собирает полученные значения в исходном порядке результатов TopN.

Повторяющийся ID строки в одной группе можно прочитать один раз и сопоставить с несколькими позициями результата. Реализация также сверяет количество запрошенных и полученных строк, длины столбцов и количество строк в ответах разных BE. Эти проверки помогают правильно сопоставить полученные значения со строками, снимком данных и порядком ранжирования.

## Откуда берётся экономия {#where-the-savings-come-from}

Ленивая материализация сокращает чтение широких выходных столбцов на раннем этапе для кандидатов, которые впоследствии будут отброшены.

Потенциальную экономию показывает простая модель. Предположим, что фрагменты поиска выдают C кандидатов, итоговый результат содержит K строк, а в каждой строке есть W байт выходных столбцов, чтение которых можно отложить:

```text
Early payload volume ≈ C × W
Deferred payload volume ≈ K × W
Avoided payload volume ≈ (C − K) × W
```

Это оценка логического объёма данных выходных столбцов. Она не учитывает чтение индекса и повторное ранжирование векторов и не равна объёму данных, загруженных из объектного хранилища. На фактические затраты влияют дополнительное чтение страниц или блоков, сжатие, кеширование, локаторы строк и RPC-запросы на получение данных.

Например, если каждый из 16 фрагментов поиска выдаёт 20 кандидатов, в итоговом результате остаётся 20 строк, а текст каждого документа занимает 4 KiB:

| Способ чтения | Логический объём текстов документов |
| --- | ---: |
| Прочитать тексты документов заранее для всех 320 кандидатов | 320 × 4 KiB = 1.25 MiB |
| Получить тексты документов только для итоговых 20 строк | 20 × 4 KiB = 80 KiB |

Логический объём текстов документов сокращается до **1/16**. Это иллюстративная модель, а не измеренный прирост скорости или снижение объёма передачи данных из объектного хранилища.

Экономия может проявиться на нескольких этапах:

- **Чтение и декодирование:** для отброшенных кандидатов не нужно заранее читать и декодировать отложенные столбцы.
- **Передача данных и перемещение в памяти:** меньший размер промежуточных Blocks снижает сетевой трафик и объём копирования данных в памяти.
- **Сортировка:** широкие столбцы больше не проходят через TopN вместе с каждым кандидатом.

| Когда выгода наиболее вероятна | Когда выигрыш может быть небольшим |
| --- | --- |
| Широкие выходные столбцы и небольшой итоговый Top-K | Возвращаются только расстояния, оценки или несколько узких столбцов |
| Много кандидатов из нескольких фрагментов поиска | Количество кандидатов уже близко к количеству строк в итоговом результате |
| Столбцы нужны только для отображения | Большинство столбцов участвует в ранней фильтрации, сортировке или вычислениях |
| Чтение, декодирование или передача данных обходятся дорого | Преобладают затраты на вычисления ANN, повторное ранжирование, предварительную фильтрацию или ожидание в очереди |

При использовании `OFFSET` каждому фрагменту поиска может потребоваться сформировать `top_k + offset`  кандидатов, хотя возвращаются только `top_k`  строк. Ленивая материализация позволяет не получать выходные столбцы для пропущенных строк, но не устраняет формирование кандидатов, сортировку и пропуск строк.

Итоговый выигрыш зависит от того, насколько сэкономленная работа превышает дополнительные затраты на получение данных, RPC и повторную сборку результата.

## Сравнение производительности: двухэтапное чтение включено и выключено {#benchmark-two-phase-reads-on-and-off}

Во внутреннем тесте сравнили одни и те же запросы с включённым и выключенным двухэтапным чтением. Время выполнения векторного поиска без фильтров, с фильтром по времени, а также с фильтрами по времени и массиву датчиков сократилось с десятков секунд до нескольких секунд.

### Условия тестирования {#test-setup}

В тесте использовали сборку на основе `doris-4.1.5-release-c7f95adaaa` и набор данных из **104,343,874 строк**. Этот идентификатор сборки описывает тестовое окружение; он не подтверждает доступность функции в стандартном выпуске 4.1.5. Кластер состоял из одного FE и двух BE. У каждого BE было 32 ядер CPU, 128 ГБ оперативной памяти и 1 ТБ хранилища. Скалярные и векторные индексы содержали по 15 сегментов.

Все три запроса вызывали `vector_search`, сортировали результаты по расстоянию L2, задавали `nprobes=128`, `use_index=true`и `top_k=20000`, а также возвращали все столбцы, включая вектор. В запросе с фильтром по датчику массив фильтровали по Pandar128.

В тесте переключали параметр `enable_lance_lazy_materialization`. Перед каждой группой запусков кластер перезапускали, а каждый SQL-запрос выполняли три раза подряд. ### Почему эти запросы ускорились {#why-these-queries-benefited}

Эти запросы ранжировали кандидатов и возвращали строки целиком, включая векторы. Несколько задач поиска формировали кандидатов, но лишь часть из них попадала в глобальный Top-K. При раннем чтении столбцов, нужных только для вывода, для отсеянных кандидатов напрасно выполнялись чтение, декодирование и передача данных.

Двухэтапное чтение откладывает эту работу. На первом этапе передаются данные, необходимые для поиска, фильтрации и сортировки, вместе с локаторами строк. На втором этапе выбранные строки дополняются оставшимися столбцами. Поэтому объём обработки полных строк больше зависит от размера итоговой выборки, чем от числа промежуточных кандидатов.

Эксперимент показывает, что даже при Top-K, равном 20,000, можно получить выигрыш, если запрос возвращает все столбцы. Фактическое ускорение зависит от нагрузки и соотношения между сэкономленной работой и накладными расходами второго этапа.

## Доступность {#availability}

На момент публикации исходной статьи эту возможность планировали включить в предстоящий выпуск Apache Doris 4.2. Сведения о поддержке в выпусках и совместимости приведены в [документации по Lance Catalog](https://doris.apache.org/docs/4.x/lakehouse/catalogs/lance-catalog/) .

Ленивая материализация объединяет три механизма: оптимизатор определяет, чтение каких выходных столбцов можно отложить, при распределённом выполнении передаются стабильные указатели на строки, а Lance извлекает данные выбранных строк по нативным row ID из зафиксированного снимка данных. В приложениях поиска, которые возвращают объёмные тексты и атрибуты, это позволяет приблизить объём чтения столбцов к размеру итоговой выборки и не тратить ресурсы на кандидатов, которые будут отброшены.
