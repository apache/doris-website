Apache Doris предоставляет встроенный механизм аутентификации пользователей. Администраторы создают пользователей, задают пароли и управляют источником подключения с помощью SQL-команд. В этом документе описывается состав идентичности пользователя Doris, доступные политики паролей, приоритет сопоставления IP-адресов, а также распространённые эксплуатационные сценарии и методы устранения неполадок.

## Основные понятия {#core-concepts}

<!-- Knowledge type: Concept -->

### Пользователь (user_identity) {#user-user_identity}

В Doris значение `user_identity` однозначно идентифицирует пользователя и состоит из двух частей:

- `user_name`: имя пользователя.
- `host`: адрес хоста, с которого подключается клиент. Поддерживается нечёткое сопоставление с помощью `%`.

Если `host` не указан, по умолчанию используется `'%'`, то есть пользователь может подключаться к Doris с любого хоста.

### Свойства пользователя {#user-properties}

Свойства пользователя непосредственно относятся к `user_name`, а не к `user_identity`. То есть `user@'192.%'` и `user@['domain']` используют один и тот же набор свойств пользователя. Свойства принадлежат пользователю, а не `user@'192.%'` или `user@['domain']`.

Свойства пользователя включают, помимо прочего, максимальное количество подключений пользователя, конфигурацию кластера загрузки и так далее.

### Встроенные пользователи {#built-in-users}

Встроенные пользователи создаются Doris по умолчанию и сразу имеют определённые привилегии, включая root и admin. Их начальные пароли пусты. После запуска FE пароль можно изменить с помощью команды изменения пароля. **Пользователей по умолчанию нельзя удалить.**

| Пользователь | Разрешённый источник входа | Роль по умолчанию |
| --- | --- | --- |
| `root@'%'` | Любой узел | operator |
| `admin@'%'` | Любой узел | admin |

### Пароль {#password}

Пароль — это учётные данные, используемые пользователем для входа. Он задаётся администратором при создании пользователя, а затем пользователь также может изменить его самостоятельно.

## Механизм аутентификации {#authentication-mechanism}

<!-- Knowledge type: Process description -->

Аутентификация Doris состоит из следующих двух этапов:

1. **Клиент отправляет данные аутентификации.** Клиент упаковывает сведения о пользователе (имя пользователя, пароль, базу данных и так далее) и отправляет их серверу Doris, чтобы подтвердить свою личность и запросить доступ к базе данных.
2. **Сервер проверяет личность.** Получив данные аутентификации, Doris проверяет их. Если имя пользователя, пароль и IP-адрес клиента указаны правильно и пользователь имеет доступ к выбранной базе данных, аутентификация завершается успешно, и Doris сопоставляет пользователя с системной идентичностью пользователя. В противном случае аутентификация завершается ошибкой, а клиенту возвращается соответствующее сообщение об ошибке.

## Политики паролей {#password-policies}

<!-- Knowledge type: Configuration parameters -->
<!-- Applicable scenarios: Enterprise security compliance / Password lifecycle management -->

Doris поддерживает следующие политики паролей, помогающие администраторам управлять жизненным циклом и безопасностью паролей.

| Политика | Назначение | Значение по умолчанию |
| --- | --- | --- |
| `PASSWORD_HISTORY` | Запрет повторного использования последних N паролей | 0 (отключено) |
| `PASSWORD_EXPIRE` | Установка срока действия пароля | NEVER (не истекает) |
| `FAILED_LOGIN_ATTEMPTS` + `PASSWORD_LOCK_TIME` | Блокировка учётной записи после последовательных неудачных входов | Отключено |
| `validate_password_policy` | Проверка сложности пароля | NONE/0 (проверка не выполняется) |

### PASSWORD_HISTORY {#password_history}

Определяет, может ли текущий пользователь повторно использовать предыдущие пароли при сбросе пароля. Например, `PASSWORD_HISTORY 10` запрещает использовать любой из последних 10 паролей в качестве нового пароля. Если задано `PASSWORD_HISTORY DEFAULT`, используется значение глобальной переменной `password_history`. Значение 0 отключает эту функцию; значение по умолчанию — 0.

Примеры:

- Установка глобальной переменной: `SET GLOBAL password_history = 10`
- Установка для пользователя: `ALTER USER user1@'ip' PASSWORD_HISTORY 10`

### PASSWORD_EXPIRE {#password_expire}

Задаёт срок действия пароля текущего пользователя. Например, `PASSWORD_EXPIRE INTERVAL 10 DAY` означает, что срок действия пароля истекает через 10 дней. `PASSWORD_EXPIRE NEVER` означает, что срок действия пароля не истекает. Если задано `PASSWORD_EXPIRE DEFAULT`, используется значение глобальной переменной `default_password_lifetime` (в днях). По умолчанию используется NEVER (или 0), то есть пароль не истекает.

Примеры:

- Установка глобальной переменной: `SET GLOBAL default_password_lifetime = 1`
- Установка для пользователя: `ALTER USER user1@'ip' PASSWORD_EXPIRE INTERVAL 10 DAY`

### FAILED_LOGIN_ATTEMPTS и PASSWORD_LOCK_TIME {#failed_login_attempts-and-password_lock_time}

Блокирует учётную запись текущего пользователя после n неудачных попыток входа и задаёт длительность блокировки. Например, `FAILED_LOGIN_ATTEMPTS 3 PASSWORD_LOCK_TIME 1 DAY` означает, что после 3 неудачных попыток входа учётная запись блокируется на один день. Администратор может вручную разблокировать заблокированную учётную запись с помощью оператора ALTER USER.

Пример:

- Установка для пользователя: `ALTER USER user1@'ip' FAILED_LOGIN_ATTEMPTS 3 PASSWORD_LOCK_TIME 1 DAY`

### Сложность пароля {#password-strength}

Эта функция управляется глобальной переменной `validate_password_policy`. По умолчанию используется NONE/0, то есть сложность пароля не проверяется. Если задано STRONG/2, пароль должен содержать как минимум 3 из следующих 4 категорий: прописные буквы, строчные буквы, цифры и специальные символы; его длина должна быть не менее 8 символов.

Пример:

- `SET validate_password_policy = STRONG`

### Просмотр политик паролей {#viewing-password-policies}

После настройки указанных политик их можно просмотреть с помощью следующей команды:

```sql
SHOW PROC "/auth/'<user>'@'<host>'";
```

Обратите внимание: части user и host должны быть заключены каждая в одинарные кавычки. Например:

```sql
SHOW PROC "/auth/'root'@'%'";
SHOW PROC "/auth/'user1'@'127.0.0.1'";
```

## Два пароля {#dual-passwords}

<!-- Knowledge type: Operational procedure + Rules -->
<!-- Applicable scenarios: Application credential rotation -->

**Поддерживается начиная с 4.2.1.** Встроенная аутентификация по паролю может хранить для одной учётной записи один основной пароль и один сохранённый вторичный пароль. Этот период перекрытия позволяет перевести клиентов на новый пароль, не отклоняя подключения клиентов, которые всё ещё используют предыдущий пароль. Вторичный пароль по умолчанию отсутствует и создаётся только с помощью `RETAIN CURRENT PASSWORD`. Эти изменения влияют на последующие аутентификации и не отключают существующие сеансы.

### Предварительные условия {#prerequisites}

- Перед использованием этих предложений обновите каждый FE до версии 4.2.1 или более поздней.
- Выполняйте ротацию как администратор с глобальной привилегией `GRANT_PRIV` или `ADMIN_PRIV`. RETAIN требует этой привилегии даже для собственной учётной записи; обычная самостоятельная команда SET PASSWORD без RETAIN таких прав не требует.
- Используйте учётную запись со встроенным непустым основным паролем. LDAP и интеграции аутентификации управляют собственными учётными данными.

### Ротация пароля {#rotate-a-password}

1. Создайте пример учётной записи, затем задайте новый пароль, сохранив текущий. Для существующей учётной записи выполните только оператор ALTER USER.

    ```sql
    CREATE USER 'app_user'@'%' IDENTIFIED BY 'OldPwd_2026!';
    ALTER USER 'app_user'@'%' IDENTIFIED BY 'NewPwd_2026!' RETAIN CURRENT PASSWORD;
    ```

    Аутентификацию могут пройти и `OldPwd_2026!`, и `NewPwd_2026!`. Эквивалентное изменение с сохранением — `SET PASSWORD FOR 'app_user'@'%' = PASSWORD('NewPwd_2026!') RETAIN CURRENT PASSWORD`; используйте его вместо оператора ALTER, а не после него.

2. Обновите каждый клиент, чтобы он использовал `NewPwd_2026!`. Проверьте состояние сохранённого пароля учётной записи:

    ```sql
    SHOW GRANTS FOR 'app_user'@'%';
    ```

    В столбце `Password` отображается `Yes (dual)`. Команды `SHOW ALL GRANTS` и `SHOW PROC '/auth'` показывают тот же маркер. Метрика `doris_fe_secondary_password_auth_total` каждого FE подсчитывает успешные аутентификации с использованием вторичного пароля для всех учётных записей после проверок политик учётных записей; отслеживайте её приращения, а не ждите, пока этот накопительный счётчик обнулится.

3. После миграции всех клиентов отзовите вторичный пароль:

    ```sql
    ALTER USER 'app_user'@'%' DISCARD OLD PASSWORD;
    ```

    Аутентификацию сможет пройти только `NewPwd_2026!`, а столбец `Password` снова будет иметь значение `Yes`. Повторное выполнение DISCARD при отсутствии вторичного пароля не меняет состояние.

### Срок действия пароля и правила политик {#password-lifetime-and-policy-rules}

| Операция | Результат |
| --- | --- |
| Непустой новый пароль с RETAIN | Предыдущий основной пароль становится единственным вторичным; любой прежний вторичный пароль заменяется. |
| Непустое изменение без RETAIN | Существующий вторичный пароль остаётся действительным. Одна лишь замена основного пароля его не отзывает. |
| Пустой новый пароль | Оба слота очищаются, даже если указан RETAIN. |
| RETAIN при пустом текущем основном пароле | Операция отклоняется. |
| DISCARD OLD PASSWORD | Удаляется только вторичный пароль. История паролей и счётчик срока действия пароля не изменяются. |

Оба пароля подчиняются политикам блокировки и истечения срока действия учётной записи. Изменение с RETAIN также является изменением пароля, поэтому оно должно соответствовать правилам сложности и истории паролей и обновляет счётчик срока действия. Привязка, отвязка или изменение интеграции аутентификации очищает сохранённый вторичный пароль; RETAIN отклоняется при таких переходах. DISCARD является самостоятельной операцией ALTER USER и не может сочетаться с изменением пароля, политики или комментария.

### Доменные учётные записи и изменения версий {#domain-accounts-and-version-changes}

Для доменной учётной записи команда DISCARD сначала очищает постоянную доменную учётную запись. Записи разрешённых IP-адресов перестают принимать её сохранённую копию при следующем обновлении средства разрешения доменных имён. Обычный интервал составляет 10 секунд, но это не является строгим верхним пределом времени отзыва.

Во время поэтапного обновления старый FE выполняет аутентификацию только по основному паролю и не может разобрать новые предложения. Перед началом ротации двух паролей дождитесь обновления всех FE. Понижение версии после использования этой функции приводит к потере сохранённого вторичного пароля: сохраняется только основной, а повторное обновление не восстанавливает старый вторичный пароль.

Полный справочник операторов см. в разделах [ALTER USER](../../../sql-manual/sql-statements/account-management/ALTER-USER) и [SET PASSWORD](../../../sql-manual/sql-statements/account-management/SET-PASSWORD).

## Приоритет сопоставления идентичности пользователя {#user-identity-matching-priority}

<!-- Knowledge type: Rule description -->
<!-- Applicable scenarios: Login rejection troubleshooting / Conflicts between multiple user_identity values -->

`user_identity` состоит из `user_name` и `host`, но при входе пользователь указывает только `user_name`. Doris сопоставляет соответствующий `host` на основе IP-адреса клиента, чтобы определить, какое значение `user_identity` использовать для входа.

Если IP-адресу клиента соответствует только одно значение `user_identity`, Doris использует его. Если соответствуют несколько значений `user_identity`, Doris применяет следующий приоритет:

| Сценарий сравнения | Приоритет |
| --- | --- |
| Конкретный IP и домен | Конкретный IP имеет приоритет над доменом |
| Конкретный IP и диапазон IP | Выигрывает более конкретный диапазон IP (например, `192.%` имеет приоритет над `%`) |

### Пример 1: IP имеет приоритет над доменом {#example-1-ip-takes-priority-over-domain}

```sql
CREATE USER user1@['domain1'] IDENTIFIED BY "12345";
CREATE USER user1@'ip1' IDENTIFIED BY "abcde";
```

Предположим, что `domain1` разрешается в два IP-адреса: `ip1` и `ip2`. Поскольку IP имеет приоритет над доменом, при попытке пользователя `user1` войти в Doris с `ip1` и паролем `'12345'` вход будет отклонён (правильный пароль — `'abcde'`).

### Пример 2: более конкретный диапазон IP имеет приоритет {#example-2-more-specific-ip-range-wins}

```sql
CREATE USER user1@'%' IDENTIFIED BY "12345";
CREATE USER user1@'192.%' IDENTIFIED BY "abcde";
```

Поскольку `'192.%'` имеет приоритет над `'%'`, при попытке пользователя `user1` войти в Doris с `192.168.1.1` и паролем `'12345'` вход будет отклонён (правильный пароль — `'abcde'`).

## Имитация чёрного списка с помощью белого списка {#simulating-a-blacklist-with-a-whitelist}

<!-- Knowledge type: Operational technique -->
<!-- Applicable scenarios: Block specific IPs from logging in -->

Doris изначально не поддерживает чёрные списки, а поддерживает только белые списки. Однако приоритет сопоставления [идентичности пользователя](#user-identity-matching-priority) можно использовать для имитации чёрного списка.

Например, предположим, что создан пользователь `user@'192.%'`, которому разрешён вход с адресов `192.*`. Чтобы запретить вход с `192.168.10.1`, создайте другого пользователя `cmy@'192.168.10.1'` и задайте новый пароль. Поскольку `192.168.10.1` имеет более высокий приоритет, чем `192.%`, пользователи с `192.168.10.1` больше не смогут войти со старым паролем.

## Часто задаваемые вопросы {#faq}

<!-- Knowledge type: Troubleshooting -->
<!-- Applicable scenarios: Login failures / Identity confusion / Forgotten passwords -->

### В: Как сбросить забытый пароль? {#q-how-do-i-reset-a-forgotten-password}

Если вы забыли пароль и не можете войти в Doris, выполните следующие действия для восстановления доступа:

1. Добавьте следующий параметр в файл конфигурации FE:

    ```text
    skip_localhost_auth_check = true
    ```

2. Перезапустите FE.
3. Войдите в Doris на хосте FE как пользователь root без пароля.
4. После входа сбросьте пароль с помощью команды `SET PASSWORD`.

### В: Могут ли другие пользователи сбросить пароль пользователя root? {#q-can-other-users-reset-the-root-users-password}

Нет. **Ни один пользователь, кроме root, не может сбросить пароль пользователя root.**

### В: В чём разница между `current_user()` и `user()`? {#q-what-is-the-difference-between-current_user-and-user}

Для просмотра `current_user` и `user` соответственно выполните `SELECT current_user()` и `SELECT user()`:

- `current_user`: идентичность, под которой текущий пользователь прошёл аутентификацию (`user_identity`, использованная при создании пользователя).
- `user`: фактическая идентичность пользователя, которой он располагает в данный момент, включая реальный IP-адрес клиента.

Например, предположим, что создан пользователь `user1@'192.%'`, а затем пользователь `user1` с адреса `192.168.10.1` входит в систему. В этом случае `current_user` имеет значение `user1@'192.%'`, а `user` — `user1@'192.168.10.1'`.

Все привилегии предоставляются определённому `current_user`, и фактический пользователь обладает всеми привилегиями этого `current_user`.

### В: Вход пользователя отклонён, но пароль подтверждён как правильный. Почему? {#q-a-users-login-is-rejected-but-the-password-is-confirmed-to-be-correct-why}

Обычно это означает, что сработали правила [приоритета сопоставления идентичности пользователя](#user-identity-matching-priority): IP-адрес клиента соответствует более конкретному `user_identity`, и для входа следует использовать пароль, принадлежащий этому `user_identity`. Фактически сопоставленную идентичность можно проверить следующей командой:

```sql
SELECT current_user();
```
