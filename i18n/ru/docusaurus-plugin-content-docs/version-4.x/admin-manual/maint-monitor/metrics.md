# Метрики мониторинга {#monitoring-metrics}

<!-- Knowledge type: Configuration parameters / Parameter reference -->
<!-- Applicable scenarios: Cluster health monitoring / Alert configuration / Performance troubleshooting -->

Процессы FE и BE в Doris имеют встроенные метрики мониторинга, которые по умолчанию предоставляются в формате, совместимом с Prometheus. В этом документе систематизированы все доступные метрики и указан их приоритет, чтобы после интеграции с Prometheus + Grafana вы могли быстро настроить систему мониторинга и оповещений.

## Сценарии использования {#applicable-scenarios}

| Сценарий | Назначение |
| --- | --- |
| Мониторинг состояния кластера | Быстрое выявление аномалий на узлах FE/BE с помощью метрик P0 |
| Настройка оповещений | Настройка оповещений по пороговым значениям таких метрик, как QPS, частота ошибок и Compaction Score |
| Диагностика производительности | Поиск узких мест по метрикам задержки запросов, очередей пулов потоков и использования памяти |
| Планирование ресурсов | Оценка нагрузки на кластер по использованию дисков, количеству tablet и соединений |
| Анализ инцидентов | Выявление первопричин сбоев путем сопоставления метрик сервера (CPU, IO, сеть) с метриками процессов |

## Категории метрик {#metric-categories}

По объекту наблюдения метрики мониторинга Doris делятся на две категории:

1. **Мониторинг процесса**: показатели работы самого процесса Doris, например количество запросов, количество транзакций и состояние Compaction.
2. **Мониторинг узла**: показатели ресурсов сервера, на котором работает процесс Doris, например CPU, память, IO и сеть.

## Получение метрик мониторинга {#retrieving-monitoring-metrics}

### Формат, совместимый с Prometheus (по умолчанию) {#prometheus-compatible-format-default}

Обратитесь непосредственно к HTTP-порту узла FE или BE:

```shell
curl http://fe_host:http_port/metrics
curl http://be_host:webserver_port/metrics
```

Пример ответа:

```text
doris_fe_cache_added{type="partition"} 0
doris_fe_cache_added{type="sql"} 0
doris_fe_cache_hit{type="partition"} 0
doris_fe_cache_hit{type="sql"} 0
doris_fe_connection_total 2
```

### Формат JSON {#json-format}

Для получения метрик в формате JSON используйте параметр `type=json`:

```shell
curl http://fe_host:http_port/metrics?type=json
curl http://be_host:webserver_port/metrics?type=json
```

### Метрики bvar {#bvar-metrics}

Процессы BE и Meta Service / Recycler также экспортируют метрики bvar через свои службы brpc. Используйте `/brpc_metrics` для получения данных в формате, совместимом с Prometheus, и `/vars` для просмотра диагностических показателей по имени:

```shell
curl http://be_host:brpc_port/brpc_metrics
curl http://be_host:brpc_port/vars
curl http://cloud_host:brpc_listen_port/brpc_metrics
```

Эти конечные точки используют `brpc_port` BE (по умолчанию `8060`) или `brpc_listen_port` Meta Service / Recycler (по умолчанию `5000`), которые отличаются от указанных выше HTTP-портов мониторинга FE / BE. Ниже приведены зарегистрированные имена bvar; не все они имеют префикс `doris_be_`.

#### Определение версии {#version-identification}

Начиная с версии 4.1.5, метрики версии BE и Meta Service / Recycler содержат следующие метки в `/brpc_metrics`:

| Метрика | Тип | Метки | Значение |
| --- | --- | --- | --- |
| `doris_be_version` | Gauge | `version`, `major`, `minor`, `patch`, `hotfix`, `short_hash` | Версия сборки BE и идентификатор коммита |
| `doris_cloud_version` | Gauge | Те же, что выше | Версия сборки Meta Service / Recycler и идентификатор коммита |

Каждый процесс экспортирует один образец метрики версии. Значение метрики сохраняет существующее кодирование версии; полная версия указана в метке `version`, а идентификатор коммита — в `short_hash`. Метрика `doris_cloud_version` не различает, выполняет ли процесс функции Meta Service, Recycler или обе функции. Для определения роли добавьте метку цели сбора метрик.

Параметр процесса `bvar_max_dump_multi_dimension_metric_num` ограничивает количество образцов многомерных метрик bvar. Его значение по умолчанию — `5000`; значение `0` отключает такие образцы, в том числе метрики версии. BE поддерживает этот параметр начиная с версии 4.1.5, а для применения изменений требуется перезапуск. См. [Конфигурация BE](../config/be-config.md#bvar_max_dump_multi_dimension_metric_num).

## Приоритет метрик и рекомендации {#monitoring-priority-and-best-practices}

<!-- Knowledge type: Best practices -->

- Последний столбец каждой таблицы метрик содержит приоритет. **P0 — наивысший приоритет**; чем больше значение, тем ниже важность. Подключайте метрики P0 в первую очередь.
- Подавляющее большинство метрик мониторинга имеют тип Counter (накопительное значение). **Для получения полезной информации необходимо снимать показания через определенные интервалы (например, каждые 15 секунд) и вычислять скорость изменения за единицу времени**.

    Например, вычислив скорость изменения `doris_fe_query_err`, можно получить частоту ошибок запросов (количество ошибок в секунду).

> Вы можете дополнить эту таблицу, чтобы сделать набор метрик мониторинга более полным и полезным.

## Диагностические метрики bvar {#bvar-diagnostic-metrics}

Следующие метрики поддерживаются начиная с версии 4.1.5 и доступны через описанные выше порты brpc. Счетчики накапливают значения с момента запуска процесса; метрики Gauge отражают текущие значения.

| Имя или префикс | Процесс | Тип | Значение |

| `sync_tablets_meta_num` | BE в режиме с разделением вычислений и хранения | Counter | Накопительное количество фоновых попыток синхронизации метаданных tablet; учитывается до вызова и не отражает количество успешных вызовов |

## Часто задаваемые вопросы {#faq}

<!-- Knowledge type: Troubleshooting -->
<!-- Applicable scenarios: Monitoring metric integration and interpretation -->

### Вопрос: конечная точка мониторинга возвращает 404. Что делать? {#q-the-monitoring-endpoint-returns-404-what-should-i-do}

Убедитесь, что вы обращаетесь к `http_port` FE или `webserver_port` BE, и проверьте фактические значения портов в `fe.conf` / `be.conf`.

### Вопрос: метрики Counter только увеличиваются и никогда не уменьшаются. Это нормально? {#q-counter-metrics-only-increase-and-never-decrease-is-this-normal}

Да, это нормально. Counter представляет накопительное значение. Для получения текущей скорости необходимо снимать показания через определенные интервалы и вычислять скорость изменения (например, с помощью `rate()` в PromQL).

### Вопрос: разрыв значений `doris_fe_max_journal_id` между узлами FE слишком велик. Что делать? {#q-the-gap-of-doris_fe_max_journal_id-between-multiple-fes-is-too-large-what-should-i-do}

Это указывает на задержку синхронизации метаданных. Проверьте сетевую связность и скорость воспроизведения журналов на Follower / Observer FE относительно Master FE.

### Вопрос: Compaction Score остается слишком высоким. Как найти причину? {#q-compaction-score-remains-too-high-how-do-i-troubleshoot}

Обратите внимание на `doris_be_tablet_base_max_compaction_score` и `doris_be_tablet_cumulative_max_compaction_score` и сопоставьте их с дисковым IO и количеством задач Compaction, чтобы выявить узкое место.

### Вопрос: запросы или задачи загрузки накапливаются. Как найти причину? {#q-queries-or-loads-are-accumulating-how-do-i-troubleshoot}

Проверьте метрики очередей пулов потоков, такие как `fragment_thread_pool_queue_size`, `doris_be_scanner_thread_pool_queue_size` и `doris_be_send_batch_thread_pool_queue_size`.
