# Метрики мониторинга {#monitoring-metrics}

<!-- Knowledge type: Configuration parameters / Parameter reference -->
<!-- Applicable scenarios: Cluster health monitoring / Alert configuration / Performance troubleshooting -->

Процессы FE и BE в Doris имеют встроенные метрики мониторинга, которые по умолчанию предоставляются в формате, совместимом с Prometheus. В этом документе систематически перечислены доступные метрики и указаны их приоритеты (Priority), чтобы после подключения Prometheus + Grafana можно было быстро настроить мониторинг и оповещения.

## Сценарии применения {#applicable-scenarios}

| Сценарий | Назначение |
| --- | --- |
| Мониторинг состояния кластера | Быстрое обнаружение неполадок узлов FE/BE по метрикам P0 |
| Настройка оповещений | Настройка пороговых оповещений по QPS, частоте ошибок, Compaction Score и другим метрикам |
| Диагностика производительности | Поиск узких мест по задержке запросов, очередям пулов потоков и использованию памяти |
| Планирование ресурсов | Оценка нагрузки на кластер по использованию дисков, количеству таблетов и числу соединений |
| Разбор инцидентов | Поиск причин сбоев с помощью метрик узлов (CPU, IO, сеть) и процессов |

## Категории метрик {#metric-categories}

Метрики мониторинга Doris делятся на две категории по объекту наблюдения:

1. **Мониторинг процессов**: показатели работы самих процессов Doris, например количество запросов и транзакций, а также состояние Compaction.
2. **Мониторинг узлов**: показатели ресурсов машин, на которых работают процессы Doris, например CPU, память, IO и сеть.

## Получение метрик мониторинга {#retrieving-monitoring-metrics}

### Формат, совместимый с Prometheus (по умолчанию) {#prometheus-compatible-format-default}

Обратитесь напрямую к HTTP-порту узла FE или BE:

```shell
curl http://fe_host:http_port/metrics
curl http://be_host:webserver_port/metrics
```

Пример ответа:

```text
doris_fe_cache_added{type="partition"} 0
doris_fe_cache_added{type="sql"} 0
doris_fe_cache_hit{type="partition"} 0
doris_fe_cache_hit{type="sql"} 0
doris_fe_connection_total 2
```

### Формат JSON {#json-format}

Для получения метрик в формате JSON используйте параметр `type=json`:

```shell
curl http://fe_host:http_port/metrics?type=json
curl http://be_host:webserver_port/metrics?type=json
```

### Метрики bvar {#bvar-metrics}

Процессы BE и Meta Service / Recycler также предоставляют метрики bvar через службы brpc. Путь `/brpc_metrics` возвращает данные в формате, совместимом с Prometheus, а `/vars` позволяет просматривать диагностические данные по имени:

```shell
curl http://be_host:brpc_port/brpc_metrics
curl http://be_host:brpc_port/vars
curl http://cloud_host:brpc_listen_port/brpc_metrics
```

Эти конечные точки используют `brpc_port` процесса BE (по умолчанию `8060`) или `brpc_listen_port` процесса Meta Service / Recycler (по умолчанию `5000`). Они отличаются от указанных выше HTTP-портов мониторинга FE и BE. Приведённые ниже имена bvar соответствуют зарегистрированным именам; префикс `doris_be_` есть не у всех.

#### Определение версии {#version-identification}

Начиная с версии 4.1.5 метрики версии BE и Meta Service / Recycler в `/brpc_metrics` содержат следующие метки:

| Метрика | Тип | Метки | Значение |
| --- | --- | --- | --- |
| `doris_be_version` | Gauge | `version`, `major`, `minor`, `patch`, `hotfix`, `short_hash` | Версия сборки BE и идентификатор коммита |
| `doris_cloud_version` | Gauge | Те же, что выше | Версия сборки Meta Service / Recycler и идентификатор коммита |

Каждый процесс экспортирует один образец метрики версии. Значение метрики сохраняет существующую кодировку версии; полную версию следует читать из метки `version`, а идентификатор коммита — из `short_hash`. Метрика `doris_cloud_version` не показывает, выполняет процесс роль Meta Service, Recycler или обе роли. Для определения роли добавьте метку целевого объекта сбора метрик.

Параметр процесса `bvar_max_dump_multi_dimension_metric_num` ограничивает число многомерных образцов bvar. Значение по умолчанию — `5000`; значение `0` отключает такие образцы, включая метрики версии. BE поддерживает этот параметр начиная с версии 4.1.5; после его изменения требуется перезапуск. См. [конфигурацию BE](../config/be-config.md#bvar_max_dump_multi_dimension_metric_num).

## Приоритеты мониторинга и рекомендации {#monitoring-priority-and-best-practices}

<!-- Knowledge type: Best practices -->

- Последний столбец каждой таблицы метрик содержит приоритет (Priority). **P0 — наивысший приоритет**; чем больше значение, тем ниже важность метрики. Сначала подключайте метрики P0.
- Подавляющее большинство метрик мониторинга имеют тип Counter (накопительное значение). **Чтобы получить полезную информацию, собирайте значения через заданные интервалы (например, каждые 15 секунд) и вычисляйте скорость изменения за единицу времени**.

    Например, по скорости изменения `doris_fe_query_err` можно определить частоту ошибок запросов (ошибок в секунду).

> Вы можете дополнить эту таблицу, чтобы справочник метрик мониторинга стал полнее и полезнее.

## Диагностические метрики bvar {#bvar-diagnostic-metrics}

Следующие метрики поддерживаются начиная с версии 4.1.5 и доступны через описанные выше порты brpc. Счётчики Counter накапливают значения с момента запуска процесса; показатели Gauge отражают текущие значения.

| Имя или префикс | Процесс | Тип | Значение |
| --- | --- | --- | --- |
| `sync_tablets_meta_num` | BE в режиме разделения вычислений и хранения | Counter | Накопительное число фоновых попыток синхронизации метаданных таблетов. Учитывается до вызова и не равно числу успешных вызовов |
| `sync_tablets_rowsets_num` | BE в режиме разделения вычислений и хранения | Counter | Накопительное число фоновых попыток синхронизации rowset таблетов. Учитывается до вызова и не равно числу успешных вызовов |
| `vertical_compaction_active_segment_contexts` | BE | Gauge | Текущее число активных контекстов Segment, удерживаемых вертикальной Compaction |
| `hdfs_get_path_info` | BE | Статистика задержки, микросекунды | Префикс метрик задержки `hdfsGetPathInfo`, помогающих диагностировать доступ к метаданным файлов HDFS |
| `ms_repair_tablet_index` | Meta Service | Counter | Накопительное число старых записей Tablet Index, исправленных при фиксации транзакции добавлением отсутствующего `db_id`; учитывается только после успешной фиксации |
| `file_cache_ttl_mgr_ttl_info_map_size` (с префиксом пути кэша) | BE | Gauge | Текущее число записей с информацией о TTL таблетов, отслеживаемых в памяти, а не число блоков кэша |

Префиксы путей кэша и метрики вытеснения описаны в разделе [«Мониторинг файлового кэша»](../../compute-storage-decoupled/file-cache/file-cache.md#cache-space-and-hit-rate-metrics). По завершении вертикальной Compaction поле `vertical_compaction_active_segment_contexts_peak` в журнале BE уровня INFO фиксирует пиковое число контекстов для этой задачи. Это поле журнала, а не ещё один показатель Gauge на уровне процесса.

### Вопрос: Конечная точка мониторинга возвращает 404. Что делать? {#q-the-monitoring-endpoint-returns-404-what-should-i-do}

Убедитесь, что обращаетесь к `http_port` процесса FE или `webserver_port` процесса BE, и проверьте фактические значения портов в `fe.conf` / `be.conf`.

### Вопрос: Метрики Counter только растут и никогда не уменьшаются. Это нормально? {#q-counter-metrics-only-increase-and-never-decrease-is-this-normal}

Да. Counter представляет накопительное значение. Чтобы получить текущую скорость изменения, нужно собирать значения через интервалы и вычислять скорость изменения (например, с помощью `rate()` в PromQL).

### Вопрос: Значения `doris_fe_max_journal_id` на разных узлах FE сильно расходятся. Что делать? {#q-the-gap-of-doris_fe_max_journal_id-between-multiple-fes-is-too-large-what-should-i-do}

Это указывает на задержку синхронизации метаданных. Проверьте сетевое соединение и скорость воспроизведения журналов на Follower / Observer FE относительно Master FE.

### Вопрос: Compaction Score остаётся слишком высоким. Как найти причину? {#q-compaction-score-remains-too-high-how-do-i-troubleshoot}

Проверьте `doris_be_tablet_base_max_compaction_score` и `doris_be_tablet_cumulative_max_compaction_score`; сопоставьте их с дисковым IO и числом задач Compaction, чтобы найти узкое место.

### Вопрос: Запросы или задачи загрузки накапливаются. Как найти причину? {#q-queries-or-loads-are-accumulating-how-do-i-troubleshoot}

Проверьте метрики очередей пулов потоков, в том числе `fragment_thread_pool_queue_size`, `doris_be_scanner_thread_pool_queue_size` и `doris_be_send_batch_thread_pool_queue_size`.
