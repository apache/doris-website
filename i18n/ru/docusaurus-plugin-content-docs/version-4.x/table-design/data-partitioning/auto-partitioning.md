Автоматическое партиционирование (AUTO PARTITION) — это возможность Doris автоматически создавать партиции при загрузке данных на основе значений столбца партиционирования. Оно решает следующие проблемы:

- Столбец партиционирования содержит разрозненные данные, значения которых сложно предсказать, поэтому при создании таблицы невозможно точно перечислить все необходимые партиции.
- Партиций слишком много, чтобы создавать их вручную.
- Столбец партиционирования не связан с системным временем, поэтому динамическое партиционирование не подходит для такого сценария.

Doris поддерживает два типа автоматического партиционирования:

| Тип | Способ партиционирования | Функция партиционирования | Поддерживаемые типы столбца партиционирования |
| --- | --- | --- | --- |
| AUTO **RANGE** PARTITION | Автоматическое партиционирование по диапазону | `date_trunc` | `DATE`, `DATETIME` |
| AUTO **LIST** PARTITION | Автоматическое партиционирование по перечисляемым значениям | Вызовы функций не поддерживаются | `BOOLEAN`, `TINYINT`, `SMALLINT`, `INT`, `BIGINT`, `LARGEINT`, `DATE`, `DATETIME`, `CHAR`, `VARCHAR` |

## Сценарии использования {#use-cases}

Рассмотрим столбец партиционирования с временным типом данных:

- При динамическом партиционировании Doris может автоматически создавать новые партиции через фиксированные интервалы времени для хранения данных, поступающих в реальном времени. Для таких сценариев, как журналы действий пользователей в реальном времени, этой возможности обычно достаточно.
- Однако в более сложных сценариях, например при обработке данных, поступающих не в реальном времени, столбец партиционирования не связан с текущим системным временем и содержит множество разрозненных значений. Партиционирование по этому столбцу по-прежнему необходимо, но нужные партиции нельзя определить заранее либо их количество слишком велико.

В таких случаях ни динамическое, ни ручное партиционирование не удовлетворяет требованиям, а автоматическое партиционирование хорошо подходит для решения задачи.

### Пример сценария: таблица истории сделок {#example-scenario-trade-history-table}

Предположим, в компании есть таблица истории сделок, партиционированная по дате сделки. При ручном партиционировании DDL обычно выглядит следующим образом:

```sql
CREATE TABLE `DAILY_TRADE_VALUE`
(
    `TRADE_DATE`              datev2 NOT NULL COMMENT 'Trade date',
    `TRADE_ID`                varchar(40) NOT NULL COMMENT 'Trade ID',
    ......
)
UNIQUE KEY(`TRADE_DATE`, `TRADE_ID`)
PARTITION BY RANGE(`TRADE_DATE`)
(
    PARTITION p_2000 VALUES [('2000-01-01'), ('2001-01-01')),
    PARTITION p_2001 VALUES [('2001-01-01'), ('2002-01-01')),
    PARTITION p_2002 VALUES [('2002-01-01'), ('2003-01-01')),
    PARTITION p_2003 VALUES [('2003-01-01'), ('2004-01-01')),
    PARTITION p_2004 VALUES [('2004-01-01'), ('2005-01-01')),
    PARTITION p_2005 VALUES [('2005-01-01'), ('2006-01-01')),
    PARTITION p_2006 VALUES [('2006-01-01'), ('2007-01-01')),
    PARTITION p_2007 VALUES [('2007-01-01'), ('2008-01-01')),
    PARTITION p_2008 VALUES [('2008-01-01'), ('2009-01-01')),
    PARTITION p_2009 VALUES [('2009-01-01'), ('2010-01-01')),
    PARTITION p_2010 VALUES [('2010-01-01'), ('2011-01-01')),
    PARTITION p_2011 VALUES [('2011-01-01'), ('2012-01-01')),
    PARTITION p_2012 VALUES [('2012-01-01'), ('2013-01-01')),
    PARTITION p_2013 VALUES [('2013-01-01'), ('2014-01-01')),
    PARTITION p_2014 VALUES [('2014-01-01'), ('2015-01-01')),
    PARTITION p_2015 VALUES [('2015-01-01'), ('2016-01-01')),
    PARTITION p_2016 VALUES [('2016-01-01'), ('2017-01-01')),
    PARTITION p_2017 VALUES [('2017-01-01'), ('2018-01-01')),
    PARTITION p_2018 VALUES [('2018-01-01'), ('2019-01-01')),
    PARTITION p_2019 VALUES [('2019-01-01'), ('2020-01-01')),
    PARTITION p_2020 VALUES [('2020-01-01'), ('2021-01-01')),
    PARTITION p_2021 VALUES [('2021-01-01'), ('2022-01-01'))
)
DISTRIBUTED BY HASH(`TRADE_DATE`) BUCKETS 10
PROPERTIES (
  "replication_num" = "1"
);
```

У этого подхода есть следующие недостатки:

1. При создании таблицы необходимо вручную перечислить все партиции.
2. При изменении диапазона значений столбца партиционирования, например при добавлении данных за 2022 год, партиции необходимо изменять с помощью [ALTER-TABLE-PARTITION](../../sql-manual/sql-statements/table-and-view/table/ALTER-TABLE-PARTITION), что неудобно.
3. Изменение партиций или переход к более мелкой детализации требует значительных усилий.

С использованием AUTO PARTITION DDL можно упростить до следующего:

```sql
CREATE TABLE `DAILY_TRADE_VALUE`
(
    `TRADE_DATE`              datev2 NOT NULL,
    `TRADE_ID`                varchar(40) NOT NULL,
    ......
)
UNIQUE KEY(`TRADE_DATE`, `TRADE_ID`)
AUTO PARTITION BY RANGE (date_trunc(`TRADE_DATE`, 'year'))
(
)
DISTRIBUTED BY HASH(`TRADE_DATE`) BUCKETS 10
PROPERTIES (
  "replication_num" = "1"
);
```

Во вновь созданной таблице по умолчанию нет партиций:

```sql
show partitions from `DAILY_TRADE_VALUE`;
Empty set (0.12 sec)
```

После вставки данных соответствующие партиции создаются автоматически:

```sql
insert into `DAILY_TRADE_VALUE` values ('2012-12-13', 1), ('2008-02-03', 2), ('2014-11-11', 3);

show partitions from `DAILY_TRADE_VALUE`;
```

## Синтаксис {#syntax}

Используйте следующий синтаксис в части `partitions_definition` оператора [CREATE-TABLE](../../sql-manual/sql-statements/table-and-view/table/CREATE-TABLE).

### AUTO RANGE PARTITION {#auto-range-partition}

```sql
[AUTO] PARTITION BY RANGE(<partition_expr>)
<origin_partitions_definition>
```

Где:

```sql
partition_expr ::= date_trunc(<partition_column>, '<interval>')
```

:::tip
В AUTO RANGE PARTITION ключевое слово `AUTO` можно опустить; автоматическое партиционирование при этом сохраняется.
:::

Пример:

```sql
CREATE TABLE `date_table` (
    `TIME_STAMP` datev2 NOT NULL
) ENGINE=OLAP
DUPLICATE KEY(`TIME_STAMP`)
AUTO PARTITION BY RANGE (date_trunc(`TIME_STAMP`, 'month'))
(
)
DISTRIBUTED BY HASH(`TIME_STAMP`) BUCKETS 10
PROPERTIES (
    "replication_allocation" = "tag.location.default: 1"
);
```

### AUTO LIST PARTITION {#auto-list-partition}

```sql
AUTO PARTITION BY LIST(`partition_col1` [, `partition_col2`, ...])
<origin_partitions_definition>
```

Автоматическое партиционирование LIST поддерживает партиционирование по нескольким столбцам с тем же синтаксисом, что и обычное партиционирование LIST: `AUTO PARTITION BY LIST(`col1`, `col2`, ...)`. Для каждого значения столбца партиционирования, у которого ещё нет соответствующей партиции, создаётся отдельная новая партиция.

Пример:

```sql
CREATE TABLE `str_table` (
    `str` varchar not null
) ENGINE=OLAP
DUPLICATE KEY(`str`)
AUTO PARTITION BY LIST (`str`)
()
DISTRIBUTED BY HASH(`str`) BUCKETS 10
PROPERTIES (
    "replication_allocation" = "tag.location.default: 1"
);
```

### Сравнение ограничений {#constraint-comparison}

| Ограничение | AUTO RANGE PARTITION | AUTO LIST PARTITION |
| --- | --- | --- |
| Поддерживаемые функции партиционирования | Только `date_trunc` | Вызовы функций не поддерживаются |
| Поддерживаемые типы столбца партиционирования | `DATE`, `DATETIME` | `BOOLEAN`, `TINYINT`, `SMALLINT`, `INT`, `BIGINT`, `LARGEINT`, `DATE`, `DATETIME`, `CHAR`, `VARCHAR` |
| Поддержка партиционирования по нескольким столбцам | Нет | Да |
| Ограничение длины имени партиции | - | Не должно превышать 50 символов (имя формируется путём объединения и экранирования содержимого столбцов партиционирования; фактическая допустимая длина может быть меньше) |
| Правило определения значений партиций | Разбиение по временным диапазонам, определяемым усечением с помощью `date_trunc` | Для каждого нового перечисляемого значения, для которого ещё нет партиции, создаётся отдельная новая партиция |

## Партиционирование значений NULL {#null-value-partitioning}

После включения переменной сеанса `allow_partition_column_nullable` два типа автоматического партиционирования различаются поддержкой столбцов NULLABLE:

| Тип автоматического партиционирования | Поддержка столбца партиционирования NULLABLE |
| --- | --- |
| AUTO LIST PARTITION | Поддерживается. При записи NULL создаётся обычная партиция для NULL. |
| AUTO RANGE PARTITION | Не поддерживается |

### AUTO LIST PARTITION: столбец NULLABLE поддерживается {#auto-list-partition-nullable-column-supported}

```sql
create table auto_null_list(
    k0 varchar null
)
auto partition by list (k0)
(
)
DISTRIBUTED BY HASH(`k0`) BUCKETS 1
properties("replication_num" = "1");

insert into auto_null_list values (null);

select * from auto_null_list;
+------+
| k0   |
+------+
| NULL |
+------+

select * from auto_null_list partition(pX);
+------+
| k0   |
+------+
| NULL |
+------+
```

### AUTO RANGE PARTITION: столбец NULLABLE не поддерживается {#auto-range-partition-nullable-column-not-supported}

```sql
CREATE TABLE `range_table_nullable` (
    `k1` INT,
    `k2` DATETIMEV2(3),
    `k3` DATETIMEV2(6)
) ENGINE=OLAP
DUPLICATE KEY(`k1`)
AUTO PARTITION BY RANGE (date_trunc(`k2`, 'day'))
()
DISTRIBUTED BY HASH(`k1`) BUCKETS 16
PROPERTIES (
    "replication_allocation" = "tag.location.default: 1"
);

ERROR 1105 (HY000): errCode = 2, detailMessage = AUTO RANGE PARTITION doesn't support NULL column
```

## Управление жизненным циклом {#lifecycle-management}

:::info
Doris поддерживает совместное использование автоматического и динамического партиционирования для управления жизненным циклом, но такое сочетание больше не рекомендуется.
:::

Таблицы AUTO RANGE PARTITION поддерживают управление жизненным циклом исторических партиций с помощью свойства `partition.retention_count`. Это свойство принимает положительное целое число `N`, которое означает, что **сохраняются только `N` исторических партиций с наибольшими значениями партиций**; все текущие и будущие партиции сохраняются.

Ограничения использования:

- Это свойство можно задавать только для таблиц AUTO RANGE PARTITION. В противном случае оператор завершается ошибкой `Only AUTO RANGE PARTITION table could set partition.retention_count`.
- Его **нельзя использовать вместе с уже включённым динамическим партиционированием** (`dynamic_partition.enable = true`). В противном случае оператор завершается ошибкой `Can not use partition.retention_count and dynamic_partition properties at the same time`. Создание партиций с помощью динамического партиционирования и удаление партиций по заданному количеству сохраняемых партиций являются взаимоисключающими режимами планирования. Это ограничение действует начиная с версии 4.1.4 как в режиме с совмещёнными вычислениями и хранением, так и в режиме с разделёнными вычислениями и хранением.
- Начиная с версии 4.1.4, режим с разделёнными вычислениями и хранением также поддерживает изменение этого свойства с помощью `ALTER TABLE ... SET ("partition.retention_count" = "N")`. До версии 4.1.4 такой оператор `ALTER` в режиме с разделёнными вычислениями и хранением отклонялся или не имел эффекта.

### Определения понятий {#concept-definitions}

- **Историческая партиция**: партиция, верхняя граница которой меньше или равна текущему времени.
- **Текущая или будущая партиция**: партиция, нижняя граница которой больше или равна текущему времени.
- **Сравнение значений партиций**: поскольку партиции RANGE никогда не пересекаются, утверждение «значение партиции A больше значения партиции B» эквивалентно утверждению «нижняя граница партиции A больше верхней границы партиции B», а также утверждению «верхняя граница партиции A больше верхней границы партиции B».

### Пример {#example}

```sql
create table auto_recycle(
    k0 datetime(6) not null
)
AUTO PARTITION BY RANGE (date_trunc(k0, 'day')) ()
DISTRIBUTED BY HASH(`k0`) BUCKETS 1
properties(
    "partition.retention_count" = "3"
);
```

Эта конфигурация означает, что сохраняются только 3 исторические партиции с наибольшими значениями дат. Предположим, текущая дата — `2025-10-21`, а данные вставлены за каждый день с `2025-10-16` по `2025-10-23`. После одного цикла удаления устаревших партиций остаётся 6 партиций, как показано ниже:

![Удаление устаревших партиций](/images/blogs/auto-partition-lifetime1.png)

Список оставшихся партиций:

- p20251018000000
- p20251019000000
- p20251020000000 (эта и перечисленные выше партиции: сохраняются только три исторические партиции)
- p20251021000000 (эта и перечисленные ниже партиции: текущие и будущие партиции не затрагиваются)
- p20251022000000
- p20251023000000

## Совместное использование с автоматическим бакетированием {#used-together-with-auto-bucketing}

Только AUTO RANGE PARTITION можно использовать совместно с функцией [автоматического бакетирования](./data-bucketing.md#2-automatically-set-the-number-of-buckets).

При таком сочетании Doris предполагает, что данные загружаются в таблицу инкрементально, в хронологическом порядке, и каждая загрузка затрагивает только одну партицию. Поэтому **это сочетание рекомендуется только для таблиц, в которые данные загружаются инкрементально пакетами**.

:::warning Примечание
Если схема загрузки данных не соответствует описанному выше подходу, а автоматическое партиционирование и автоматическое бакетирование используются вместе, количество бакетов в новых партициях может оказаться крайне неоптимальным, что способно существенно повлиять на производительность запросов.
:::

## Управление партициями {#partition-management}

После включения автоматического партиционирования можно точно находить нужные партиции с помощью следующих двух инструментов:

- Функция `auto_partition_name`: сопоставляет значение столбца партиционирования с именем партиции.
- Табличная функция `partitions`: возвращает подробную информацию о партиции по её имени.

Продолжим пример с таблицей `DAILY_TRADE_VALUE`: после вставки данных запросим партицию, к которой относится конкретная запись:

```sql
select * from partitions("catalog"="internal","database"="optest","table"="DAILY_TRADE_VALUE") where PartitionName = auto_partition_name('range', 'year', '2008-02-03');
+-------------+-----------------+----------------+---------------------+--------+--------------+--------------------------------------------------------------------------------+-----------------+---------+----------------+---------------+---------------------+---------------------+--------------------------+-----------+------------+-------------------------+-----------+--------------------+--------------+
| PartitionId | PartitionName   | VisibleVersion | VisibleVersionTime  | State  | PartitionKey | Range                                                                          | DistributionKey | Buckets | ReplicationNum | StorageMedium | CooldownTime        | RemoteStoragePolicy | LastConsistencyCheckTime | DataSize  | IsInMemory | ReplicaAllocation       | IsMutable | SyncWithBaseTables | UnsyncTables |
+-------------+-----------------+----------------+---------------------+--------+--------------+--------------------------------------------------------------------------------+-----------------+---------+----------------+---------------+---------------------+---------------------+--------------------------+-----------+------------+-------------------------+-----------+--------------------+--------------+
|      127095 | p20080101000000 |              2 | 2024-11-14 17:29:02 | NORMAL | TRADE_DATE   | [types: [DATEV2]; keys: [2008-01-01]; ..types: [DATEV2]; keys: [2009-01-01]; ) | TRADE_DATE      |      10 |              1 | HDD           | 9999-12-31 23:59:59 |                     | \N                       | 985.000 B |          0 | tag.location.default: 1 |         1 |                  1 | \N           |
+-------------+-----------------+----------------+---------------------+--------+--------------+--------------------------------------------------------------------------------+-----------------+---------+----------------+---------------+---------------------+---------------------+--------------------------+-----------+------------+-------------------------+-----------+--------------------+--------------+
```

Так можно точно определить идентификатор и значение каждой партиции для последующих операций с конкретными партициями, например `insert overwrite partition`.

## Примечания {#notes}

| Примечание | Описание |
| --- | --- |
| Поддержка партиционирования по нескольким столбцам | AUTO LIST PARTITION поддерживает партиционирование по нескольким столбцам с тем же синтаксисом, что и обычное партиционирование LIST. |
| Партиции, созданные при неудачных загрузках, не удаляются автоматически | Если во время вставки или загрузки данных были созданы партиции, но загрузка не завершилась полностью из-за ошибки или отмены, созданные партиции не удаляются автоматически. |
| Использование аналогично обычным партициям | Для таблицы с AUTO PARTITION меняется только способ создания партиций: они создаются автоматически вместо ручного создания. Во всём остальном таблица и её партиции используются так же, как таблицы без AUTO PARTITION. |
| Ограничение максимального количества партиций | Максимальное количество партиций в таблице задаётся параметром `max_auto_partition_num` в [конфигурации FE](../../admin-manual/config/fe-config). Настройте его при необходимости, чтобы случайно не создать слишком много партиций. |
| Интервал опроса при отправке данных | При загрузке данных в таблицу AUTO PARTITION интервал опроса, с которым Coordinator отправляет данные, отличается от интервала для обычных таблиц. Он задаётся параметром `olap_table_sink_send_interval_auto_partition_factor` в [конфигурации BE](../../admin-manual/config/be-config). После включения sink-node memtable (`enable_memtable_on_sink_node = true`) эта переменная не действует. |
| Поведение INSERT OVERWRITE | Особенности поведения таблицы AUTO PARTITION при вставке данных с помощью [insert-overwrite](../../sql-manual/sql-statements/data-modification/DML/INSERT-OVERWRITE) описаны в документации INSERT OVERWRITE. |
| Конфликты метаданных могут приводить к сбоям загрузки | Если при создании партиций во время загрузки над таблицей выполняются другие операции с метаданными, например Schema Change или Rebalance, загрузка может завершиться ошибкой. |
