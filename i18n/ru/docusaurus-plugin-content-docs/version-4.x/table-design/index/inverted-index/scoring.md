При выполнении полнотекстовых запросов (например, с `MATCH_ANY`, `MATCH_ALL` или `MATCH_PHRASE`) часто требуется отсортировать результаты по степени совпадения, чтобы сначала получить наиболее релевантные записи. Doris предоставляет **оценку релевантности**: каждой строке присваивается числовая оценка на основе условий запроса. Чем выше оценка, тем выше релевантность.

Сейчас Doris по умолчанию использует для оценки релевантности алгоритм **BM25 (Best Matching 25)**.

**Типичные сценарии использования:**

- Поисковые приложения: возврат списка документов, наиболее релевантных ключевым словам
- Анализ журналов: сортировка по релевантности для быстрого поиска записей, лучше всего соответствующих ключевым словам
- Рекомендация контента: отбор приоритетного контента по сходству текстов
- Поиск в базе знаний: возврат возможных ответов с сортировкой по релевантности вопросу

## Быстрый старт {#quick-start}

Следующий пример показывает, как включить оценку релевантности в запросе и отсортировать результаты по оценке:

```sql
SELECT *,
       score() AS relevance
FROM search_demo
WHERE content MATCH_ANY 'text search test'
ORDER BY relevance DESC
LIMIT 10;
```

После выполнения Doris вычисляет оценку для каждой строки с помощью алгоритма BM25 и возвращает 10 наиболее релевантных записей:

```text
+------+-----------------------------------+---------+--------------+-----------+
| id   | content                           | author  | publish_date | relevance |
+------+-----------------------------------+---------+--------------+-----------+
|    1 | Full text search engine test demo | Alice   | 2024-01-01   |  2.915228 |
|    7 | Text processing techniques        | Grace   | 2024-01-07   |  1.341931 |
|    5 | Performance test framework        | Eve     | 2024-01-05   |  1.341931 |
|    3 | Advanced search algorithms        | Charlie | 2024-01-03   |  1.341931 |
+------+-----------------------------------+---------+--------------+-----------+
```

## Условия использования {#activation-conditions}

Чтобы использовать показанную выше форму оценки Top-N, оператор `SELECT`, вычисляющий `score()`, должен соответствовать всем трём условиям:

1. В части `SELECT` явно вызывается функция `score()`.
2. Его часть `WHERE` содержит хотя бы одно условие `MATCH_*` или `SEARCH`.
3. В нём есть один ключ `ORDER BY`, ссылающийся на псевдоним оценки, а также `LIMIT`.

В Doris 4.0.x и с 4.1.0 по 4.1.5 требуется эта форма Top-N.

### Фильтрация по оценке релевантности {#filter-by-relevance-score}

Сначала подготовьте отдельную примерную таблицу с токенизированным инвертированным индексом. Для выполнения следующих инструкций нужны права на создание базы данных и таблицы, загрузку данных и выполнение запросов:

```sql
CREATE DATABASE IF NOT EXISTS score_filter_example;
USE score_filter_example;

CREATE TABLE score_filter_demo (
    id BIGINT,
    content TEXT,
    INDEX idx_content (content) USING INVERTED
        PROPERTIES("parser" = "english", "support_phrase" = "true")
)
DUPLICATE KEY(id)
DISTRIBUTED BY HASH(id) BUCKETS 1
PROPERTIES ("replication_num" = "1");

INSERT INTO score_filter_demo VALUES
(1, 'Full text search engine test demo'),
(2, 'Database performance analysis'),
(3, 'Search engine examples');
```

Начиная с Doris 4.0.4, фильтр по минимальной оценке можно задавать непосредственно в `WHERE`. Следующая форма Top-N совместима с Doris 4.0.4 и более поздними версиями:

```sql
SELECT *, score() AS relevance
FROM score_filter_demo
WHERE content MATCH_ANY 'text search test'
  AND score() > 5
ORDER BY relevance DESC
LIMIT 10;
```

Запрос возвращает до 10 совпадающих строк с оценкой выше 5, отсортированных по убыванию оценки. Если ни одна совпадающая строка не проходит порог, результат будет пустым. Оценки зависят от запроса и набора данных, поэтому 5 здесь служит лишь примером порога.

В `WHERE` используйте непосредственно `score()`, а в `ORDER BY` — псевдоним из списка выбираемых выражений. Прямая фильтрация поддерживает одно условие минимальной оценки: `score() > <threshold>` или `score() >= <threshold>`, где порог задан числовым литералом. Объединяйте его с условием поиска с помощью `AND`. Верхние границы (`<`, `<=`), равенство (`=`), несколько условий для оценки и условия для оценки, вложенные в `OR`, не поддерживаются.

#### Совместимость с Doris 4.0.0–4.0.3 {#compatibility-with-doris-400-to-403}

В Doris 4.0.0–4.0.3 использовать `score()` в `WHERE` нельзя. В этих версиях сначала выберите ограниченный набор кандидатов с оценками в подзапросе: условие `MATCH_*`, сортировка `ORDER BY` по псевдониму оценки и `LIMIT` должны находиться внутри этого подзапроса. Затем отфильтруйте результаты по псевдониму во внешнем запросе:

```sql
SELECT a.*
FROM (
    SELECT *, score() AS relevance
    FROM score_filter_demo
    WHERE content MATCH_ANY 'text search test'
    ORDER BY relevance DESC
    LIMIT 1000
) AS a
WHERE a.relevance > 5
ORDER BY a.relevance DESC
LIMIT 10;
```

Запрос возвращает до 10 строк с оценкой выше 5 из 1000 кандидатов с наивысшими оценками. Если ни один из этих кандидатов не проходит порог, результат будет пустым. Выбирайте ограничение числа кандидатов с учётом потребностей приложения: эта схема фильтрует набор кандидатов, а не возвращает все совпадающие строки с оценкой выше порога.

В Doris 4.0.0–4.0.3 сохраняйте внутренний `LIMIT`: без него внутренний запрос перестаёт соответствовать обязательной форме Top-N, и оптимизатор может перенести внешнее условие по оценке в запрос, вычисляющий оценку. Одних `ORDER BY` и `LIMIT` во внешнем запросе недостаточно для выполнения необходимой внутренней операции Top-N.

## Алгоритм BM25 {#bm25-algorithm}

BM25 — алгоритм оценки релевантности текста, основанный на вероятностной модели. Он взвешивает совпадения с учётом трёх факторов: **частоты термина (TF)**, **обратной частоты документа (IDF)** и **длины записи**. По сравнению с традиционной моделью TF-IDF, BM25 устойчивее, лучше поддаётся настройке и эффективнее уравновешивает оценки длинных и коротких текстов.

### Основная формула {#core-formula}

```text
score = IDF × (tf × (k1 + 1)) / (tf + k1 × (1 - b + b × |d| / avgdl))
```

Переменные в формуле означают следующее:

| Переменная | Значение |
| ---------- | -------- |
| `tf` | Число вхождений термина запроса в текущую строку |
| `IDF` | Обратная частота документа, отражающая редкость термина |
| `\|d\|` | Длина текущей строки (число токенов после токенизации) |
| `avgdl` | Средняя длина всех строк таблицы |
| `k1`, `b` | Параметры настройки алгоритма |

### Параметры {#parameters}

| Параметр | Значение по умолчанию | Описание |
| -------- | --------------------- | -------- |
| `k1` | 1.2 | Определяет степень влияния частоты термина на оценку |
| `b` | 0.75 | Определяет степень нормализации по длине записи |
| `boost` | 1.0 | Весовой коэффициент на уровне запроса |

### Вспомогательные статистические показатели {#auxiliary-statistics}

```text
IDF   = log(1 + (N - n + 0.5) / (n + 0.5))
avgdl = total_terms / total_rows
```

Где:

- `N`: общее число строк в таблице
- `n`: число строк, содержащих термин запроса

Если запрос содержит несколько терминов, **итоговая оценка равна сумме оценок каждого термина**.

### Длина записи и свойство `norms` {#record-length-and-the-norms-property}

Свойство индекса `norms` и параметр конфигурации BE `inverted_index_skip_norms_for_variant` поддерживаются начиная с Doris 4.1.5.

Значение `|d|` берётся из norms, которые занимают один байт на строку для каждого индексируемого поля, включая строки, в которых у этого поля нет значения. Токенизированные индексы записывают norms по умолчанию (`"norms" = "true"`); нетокенизированные индексы их не записывают. Для индексов, используемых только для фильтрации, установите `"norms" = "false"`, чтобы сэкономить место:

```sql
INDEX idx_content(content) USING INVERTED PROPERTIES("parser" = "english", "norms" = "false")
```

Подпути VARIANT наследуют свойство индекса `norms`, что требует `rows × paths` байт. Если установить для параметра конфигурации BE `inverted_index_skip_norms_for_variant` (по умолчанию `false`, можно изменять во время работы) значение `true`, norms будут отключены для всех индексов путей VARIANT независимо от свойства индекса.

Отключение norms не влияет на фильтрацию `MATCH_*`, но `score()` возвращает ошибку, если считывает хотя бы один сегмент без norms. Эти настройки влияют на вновь записанные сегменты; существующие сегменты не изменятся, пока compaction не перезапишет их. Перед изменением настроек обновите все BE до версии, которая их поддерживает.

## Интерпретация результатов {#interpreting-the-results}

Понимание результатов оценки помогает точнее использовать ранжирование по релевантности:

| Характеристика | Описание |
| -------------- | -------- |
| Диапазон оценок | Положительное число без фиксированной верхней границы; обычно важна относительная величина, а не абсолютное значение |
| Запрос с несколькими терминами | Если в запросе несколько терминов, общая оценка равна сумме оценок отдельных терминов |
| Влияние длины | При одинаковых совпадающих терминах более короткая запись получает немного более высокую оценку |
| Отсутствие совпадающего термина | Если термин запроса не встречается в таблице, соответствующая оценка равна 0 |

## Часто задаваемые вопросы {#faq}

**Вопрос 1: Почему мой запрос не возвращает оценки?**

Проверьте по порядку:

1. Вызывается ли функция `score()` в `SELECT`.
2. Содержит ли тот же `SELECT` условие `MATCH_*` или `SEARCH` в `WHERE`.
3. Если используется форма Top-N, ссылается ли `ORDER BY` на псевдоним оценки и есть ли в запросе `LIMIT`.
4. Является ли индекс токенизированным инвертированным индексом.

**Вопрос 2: Чем BM25 отличается от TF-IDF?**

BM25 развивает TF-IDF за счёт двух улучшений: **насыщения частоты термина** и **нормализации по длине**. Благодаря им оценки длинных и коротких текстов становятся более сбалансированными, а алгоритм — более устойчивым.

**Вопрос 3: Можно ли сравнивать оценки разных запросов?**

Не рекомендуется. Оценки BM25 зависят от конкретных терминов запроса и распределения данных в таблице. Абсолютные значения для разных запросов несопоставимы. **Сравнивайте относительные величины только в пределах результатов одного и того же запроса.**
