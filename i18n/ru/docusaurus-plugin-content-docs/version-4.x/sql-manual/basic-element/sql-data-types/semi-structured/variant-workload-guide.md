## Обзор {#overview}

`VARIANT` хранит полуструктурированные данные JSON и применяет Subcolumnization к часто используемым путям.

Используйте это руководство при выборе модели данных для новой рабочей нагрузки с `VARIANT`. Оно поможет ответить на следующие вопросы:

- Что лучше использовать для этой нагрузки: `VARIANT` или статические столбцы?
- Если JSON очень широкий, с чего начать: с поведения по умолчанию, разреженных столбцов или режима DOC?
- Для каких настроек оставить значения по умолчанию, а какие изменить в первую очередь?

Если вы уже решили использовать `VARIANT` и вам нужны только синтаксис или правила типов, перейдите к разделу [VARIANT](./VARIANT). Минимальный пример импорта, который можно сразу выполнить, приведён в разделе [Импорт данных Variant](../../../../data-operate/import/complex-types/variant).

:::tip Зачем выбирать VARIANT
`VARIANT` сохраняет гибкость JSON, а Doris при этом может применять Subcolumnization к часто используемым путям. Благодаря этому распространённые фильтры, агрегации и индексы на уровне путей работают эффективно, а заранее фиксировать схему всего документа не требуется. Для очень широкого JSON оптимизации на уровне хранения позволяют эффективно использовать Subcolumnization при значительно большем числе путей.
:::

## Когда подходит VARIANT {#when-variant-fits}

`VARIANT` обычно хорошо подходит, если выполняется большинство следующих условий:

- Входные данные представлены в JSON или другом полуструктурированном формате, поля которого меняются со временем.
- Запросы обычно обращаются к подмножеству горячих путей, а не к каждому полю в каждой строке.
- Вам нужна гибкая схема без потери производительности колоночной аналитики.
- Для некоторых путей нужны индексы, тогда как многие другие пути могут оставаться динамическими.

Отдавайте предпочтение статическим столбцам, если преобладают следующие условия:

- Схема стабильна и известна заранее.
- Основные поля регулярно используются как ключи соединения, ключи сортировки или столбцы со строго контролируемыми типами.
- Главная задача — архивировать исходный JSON, а не анализировать данные по путям.

## Сначала ответьте на четыре вопроса {#four-questions-first}

Прежде чем менять настройки, ответьте на эти четыре вопроса.

### 1. Есть ли явно выраженные горячие пути? {#1-are-there-clear-hot-paths}

Если запросы постоянно обращаются к одним и тем же путям JSON, Doris может продолжать применять к ним Subcolumnization. Именно в этом случае `VARIANT` приносит наибольшую пользу.

### 2. Нужны ли некоторым путям фиксированные типы или стабильные индексы? {#2-do-a-few-paths-need-fixed-types-or-stable-indexes}

Если да, используйте Schema Template только для этих путей. Он предназначен для небольшого набора критически важных для бизнеса полей, а не для описания всего документа.

### 3. Действительно ли JSON становится широким? {#3-is-this-really-becoming-wide-json}

Проблема широкого JSON возникает, когда число путей продолжает расти и начинает создавать нагрузку на метаданные, компактацию или заметно увеличивать накладные расходы запросов.

### 4. Что важнее для широкого JSON: аналитика по горячим путям или возврат документа целиком? {#4-for-wide-json-what-matters-more-hot-path-analytics-or-whole-document-return}

- Если основная ценность по-прежнему заключается в фильтрации, агрегации и индексировании горячих полей по путям, выбирайте разреженные столбцы.
- Если важнее эффективность загрузки или возврат документа целиком, выбирайте режим DOC.

## Основные понятия {#key-concepts}

Прежде чем переходить к режимам хранения ниже, ознакомьтесь с этими терминами. Каждый из них объяснён в 2-3 строках; подробности реализации см. в разделе [VARIANT](./VARIANT).

**Subcolumnization.** При записи данных в столбец `VARIANT` Doris автоматически обнаруживает пути JSON и извлекает горячие пути в отдельные подстолбцы с колоночным хранением для эффективной аналитики.

<img src="/images/variant/variant-default-storage.png" alt="VARIANT по умолчанию: автоматическое извлечение подстолбцов" width="720" />

**Schema Template.** Объявление для столбца `VARIANT`, которое закрепляет стабильные типы за выбранными путями. Используйте его для ключевых бизнес-полей, которые должны сохранять заданный тип, поддерживать индексирование и вести себя предсказуемо. Не пытайтесь перечислить все возможные пути.

**Широкий JSON.** Проблема широкого JSON возникает, когда число уникальных путей продолжает расти и начинает увеличивать размер метаданных, затраты на запись, компактацию или выполнение запросов.

**Разреженные столбцы.** Если в широком JSON есть явное разделение на горячие и холодные пути, разреженные столбцы сохраняют Subcolumnization для горячих путей, а холодные, редко используемые пути перемещают в общее разреженное хранилище. Разреженное хранилище поддерживает шардирование по нескольким физическим столбцам для большего параллелизма чтения.

<img src="/images/variant/variant-sparse-storage.png" alt="Разреженные столбцы: разделение горячих и холодных путей" width="720" />

Как показано выше, горячие пути, такие как `user_id`, `page`, остаются отдельными подстолбцами с колоночным хранением и полной скоростью аналитической обработки, а тысячи редко используемых путей объединяются в общем разреженном хранилище. Порог задаётся параметром `variant_max_subcolumns_count`.

**Шардирование разреженного хранилища.** Когда редко используемых путей очень много, один разреженный столбец может стать узким местом при чтении. Шардирование разреженного хранилища распределяет такие пути по хешу между несколькими физическими столбцами (`variant_sparse_hash_shard_count`), что позволяет сканировать их параллельно.

<img src="/images/variant/variant-sparse-sharding.png" alt="Шардирование разреженного хранилища: параллельное чтение редко используемых путей" width="720" />

**Режим DOC.** Откладывает Subcolumnization при записи и дополнительно сохраняет исходный JSON как хранимое поле в формате map (**doc map**). Это обеспечивает быструю загрузку и эффективный возврат документа целиком ценой дополнительного места для хранения. Subcolumnization по-прежнему выполняется, но позже, во время компактации.

<img src="/images/variant/variant-doc-mode.png" alt="Режим DOC: отложенное извлечение и быстрый возврат документа" width="700" />

Как показано выше, при записи JSON сохраняется в Doc Store в исходном виде для быстрой загрузки. Подстолбцы извлекаются позже, во время компактации. При чтении запросы по путям, например `SELECT v['user_id']`, читают материализованные подстолбцы с полной скоростью колоночной обработки, а запросы к документу целиком (`SELECT v`) читают его непосредственно из Doc Store, без восстановления из подстолбцов.

В режиме DOC есть три варианта чтения в зависимости от того, материализован ли запрашиваемый путь:

<img src="/images/variant/variant-doc-mode-readpaths.png" alt="Режим DOC: подробности вариантов чтения" width="720" />

- **DOC Materialized**: запрашиваемый путь уже извлечён в подстолбец после компактации или при достижении порога `variant_doc_materialization_min_rows`. Чтение выполняется с полной скоростью колоночной обработки, как и в режиме VARIANT по умолчанию.
- **DOC Map**: запрашиваемый путь ещё не материализован. Для поиска значения запросу приходится сканировать всю doc map, что значительно медленнее на широком JSON.
- **DOC Map (с шардированием)**: используется тот же резервный способ чтения, но благодаря `variant_doc_hash_shard_count` doc map распределяется между несколькими физическими столбцами, что позволяет сканировать их параллельно и значительно быстрее получать значение.

**Storage Format V3.** Отделяет метаданные столбцов от завершающего блока сегмента. Рекомендуется для любой таблицы с `VARIANT`, особенно для широкого JSON, поскольку устраняет узкое место в работе с метаданными при наличии тысяч подстолбцов.

## Режимы хранения {#storage-modes}

Выберите начальную конфигурацию по таблице ниже, затем прочитайте соответствующий раздел.

| | Типичный сценарий | Рекомендуемый режим | Основные настройки |
|---|---|---|---|
| **A** | Журналы событий, журналы аудита | VARIANT по умолчанию + V3 | Оставьте значения по умолчанию |
| **B** | Реклама / телеметрия / профили пользователей (широкий JSON, мало горячих путей) | Разреженные столбцы + V3 | `variant_max_subcolumns_count`, `variant_sparse_hash_shard_count` |
| **C** | Вывод моделей / трассировки / архивы (приоритет загрузки или возврат документа целиком) | Режим DOC + V3 | `variant_enable_doc_mode`, `variant_doc_materialization_min_rows` |
| **D** | Заказы / платежи / устройства (ключевым путям нужны стабильные типы) | Schema Template + A или B | Определяйте только ключевые пути |

### Режим по умолчанию {#default-mode}

Это наиболее надёжная отправная точка для большинства новых рабочих нагрузок с `VARIANT`.

Типичный пример: журналы событий или данные аудита, в которых запросы постоянно обращаются к нескольким известным путям.

```sql
CREATE TABLE IF NOT EXISTS event_log (
    ts DATETIME NOT NULL,
    event_id BIGINT NOT NULL,
    event_type VARCHAR(64),
    payload VARIANT
)
DUPLICATE KEY(`ts`, `event_id`)
DISTRIBUTED BY HASH(`event_id`) BUCKETS 16
PROPERTIES (
    "replication_num" = "1",
    "storage_format" = "V3"
);
```

Используйте этот режим, если пока не уверены, достаточно ли широка нагрузка, чтобы оправдать разреженные столбцы или режим DOC, а основная польза по-прежнему связана с фильтрацией, агрегацией и группировкой по нескольким распространённым путям.

На что обратить внимание:
- Не увеличивайте `variant_max_subcolumns_count` заранее, если рост числа путей ещё не создаёт нагрузки.
- Если JSON не широкий, включение разреженных столбцов или режима DOC добавит сложности без пользы.

### Режим разреженного хранения {#sparse-mode}

Выбирайте разреженные столбцы, если данные широкие, но большинство запросов по-прежнему обращается к небольшому набору горячих путей.

Типичный пример: JSON с рекламными данными, телеметрией или профилями, содержащий тысячи необязательных атрибутов, из которых регулярно запрашиваются лишь десятки.

```sql
CREATE TABLE IF NOT EXISTS telemetry_wide (
    ts DATETIME NOT NULL,
    device_id BIGINT NOT NULL,
    attributes VARIANT<
        'device_type' : STRING,
        'region' : STRING,
        properties(
            'variant_max_subcolumns_count' = '2048',
            'variant_sparse_hash_shard_count' = '64'
        )
    >
)
DUPLICATE KEY(`ts`, `device_id`)
DISTRIBUTED BY HASH(`device_id`) BUCKETS 32
PROPERTIES (
    "replication_num" = "1",
    "storage_format" = "V3"
);
```

Используйте этот режим, если общее число ключей очень велико, но основная нагрузка по-прежнему связана с фильтрацией, агрегацией и индексированием по путям.

На что обратить внимание:
- Если узкое место — аналитика по горячим путям, не переходите сразу к режиму DOC.
- Значение `variant_max_subcolumns_count` по умолчанию — `2048`, и для большинства нагрузок это уже подходящая отправная точка для автоматической Subcolumnization. Не задавайте настолько большое значение, что фактически все пути будут проходить через Subcolumnization. Если нагрузке действительно требуется очень большое число извлечённых подстолбцов, отдавайте предпочтение [режиму DOC](#doc-mode-template).

### Режим DOC {#doc-mode-template}

Выбирайте режим DOC, если возврат всего документа JSON или минимизация накладных расходов загрузки важнее оптимизации аналитики по путям.

Типичный пример: ответы моделей, снимки трассировок или архивные документы JSON, которые часто возвращаются целиком.

Режим DOC полезен в следующих случаях:

- Когда масштаб Subcolumnization становится очень большим и приближается к 10,000 путей, требования к оборудованию быстро растут. В таком масштабе режим DOC — более стабильный выбор.
- Потребление памяти при компактации может снизиться примерно на две трети по сравнению с немедленной Subcolumnization по умолчанию.
- При загрузке широких данных с разреженными столбцами пропускная способность может вырасти примерно в 5–10×.
- Когда запросы читают значение `VARIANT` целиком (`SELECT variant_col`), режим DOC позволяет избежать восстановления документа из тысяч подстолбцов и ускоряет чтение на порядки.

**Начало работы:**

```sql
CREATE TABLE IF NOT EXISTS trace_archive (
    ts DATETIME NOT NULL,
    trace_id VARCHAR(64) NOT NULL,
    span VARIANT<
        'service_name' : STRING,
        properties(
            'variant_enable_doc_mode' = 'true',
            'variant_doc_materialization_min_rows' = '10000',
            'variant_doc_hash_shard_count' = '64'
        )
    >
)
DUPLICATE KEY(`ts`, `trace_id`)
DISTRIBUTED BY HASH(`trace_id`) BUCKETS 32
PROPERTIES (
    "replication_num" = "1",
    "storage_format" = "V3"
);
```

Используйте этот режим, если на первом месте стоит пропускная способность загрузки, нагрузке часто требуется получать документ JSON целиком или очень широкие столбцы часто читаются с помощью `SELECT variant_col`.

На что обратить внимание:
- Режим DOC не является универсальным выбором для любой нагрузки с широким JSON. Если преобладает аналитика по горячим путям, обычно лучше подходят разреженные столбцы.
- Режим DOC и разреженные столбцы взаимоисключающие. Их нельзя включить одновременно.

### Schema Template {#schema-template}

Выбирайте Schema Template, если небольшому числу путей нужны стабильные типы, стабильное поведение или отдельные индексы.

Типичный пример: данные заказов, платежей или устройств, в которых несколько критически важных для бизнеса путей должны сохранять заданный тип и поддерживать поиск.

```sql
CREATE TABLE IF NOT EXISTS order_events (
    ts DATETIME NOT NULL,
    order_id BIGINT NOT NULL,
    detail VARIANT<
        'status' : STRING,
        'amount' : DECIMAL(18, 2),
        'currency' : STRING
    >,
    INDEX idx_status(detail) USING INVERTED PROPERTIES("field_pattern" = "status")
)
DUPLICATE KEY(`ts`, `order_id`)
DISTRIBUTED BY HASH(`order_id`) BUCKETS 16
PROPERTIES (
    "replication_num" = "1",
    "storage_format" = "V3"
);
```

Используйте его, если лишь несколько полей критически важны для бизнеса и соответствующим путям нужна более строгая типизация или стратегия индексирования на уровне путей. При необходимости сочетайте Schema Template с разреженными столбцами или с `VARIANT` в режиме по умолчанию.

На что обратить внимание:
- Не превращайте всю схему JSON в статический шаблон. Это лишает `VARIANT` смысла.
- Schema Template должен охватывать только ключевые пути; остальные остаются динамическими.

## Производительность {#performance}

На диаграмме ниже сравнивается время извлечения значения по одному пути из широкого набора данных с 10K путей (200K строк, извлечение одного ключа, 16 CPU, медиана по 3 запускам).

<img src="/images/variant/variant-bench-query-time.svg" alt="Извлечение по одному пути из широких данных: время запроса" width="720" />

| Режим | Время запроса | Пиковое потребление памяти |
|---|---:|---:|
| DOC Materialized | 76 мс | 1 MiB |
| VARIANT по умолчанию | 76 мс | 1 MiB |
| DOC Map (с шардированием) | 148 мс | 1 MiB |
| JSONB | 887 мс | 32 GiB |
| DOC Map | 2,533 мс | 1 MiB |
| MAP\<STRING,STRING\> | 2,800 мс | 1 MiB |
| STRING (исходный JSON) | 6,104 мс | 48 GiB |

Основные выводы:

- **Материализованные подстолбцы дают лучший результат.** И режим по умолчанию, и DOC Materialized показывают ~76 мс — в 80× быстрее исходного JSON в STRING и в 12× быстрее JSONB.
- **Шардирование DOC Map помогает.** Шардирование doc map сокращает время запроса по нематериализованным путям с 2.5 с до 148 мс.
- **JSONB и STRING требуют много памяти.** Их пиковое потребление памяти составляет 32–48 GiB против 1 MiB у режимов VARIANT.

## Рекомендации {#best-practices}

### Этап загрузки {#import-phase}

- **Для новых таблиц с `VARIANT` сразу используйте Storage Format V3.** V3 отделяет метаданные столбцов от завершающего блока сегмента. Без него нагрузки с широким JSON страдают от медленного открытия файлов и высоких накладных расходов памяти.
- **Заранее закрепляйте ключевые пути через Schema Template.** Без Schema Template система определяет типы автоматически. Если тип одного и того же пути меняется между пакетами данных, например сначала целое число, затем строка, он преобразуется в JSONB, а индексы на этом пути теряются.
- **Начинайте с настроек по умолчанию, затем корректируйте их по наблюдаемым проблемам.** Для большинства нагрузок значений по умолчанию достаточно. Настраивайте параметры под конкретный сценарий только тогда, когда таким нагрузкам, как обучение ИИ, подключённые автомобили или системы пользовательских тегов, требуется необычно большой масштаб Subcolumnization и множество индексов на уровне путей. Избыточная настройка с первого дня, например очень большое значение `variant_max_subcolumns_count` или включение режима DOC без необходимости, добавляет сложности без подтверждённой пользы.

### Этап выполнения запросов {#query-phase}

- **Не используйте `SELECT *` как основной шаблон запроса для очень широких столбцов `VARIANT`.** Без режима DOC запросы `SELECT *` или `SELECT variant_col` должны восстанавливать большой JSON из всех подстолбцов, что значительно медленнее явного указания путей, например `SELECT v['path']`.
- **Всегда применяйте CAST к вложенным путям, если запрос зависит от типа.** Автоматическое определение типа может не соответствовать ожиданиям. Если `v['id']` на самом деле хранится как STRING, а вы сравниваете его с целочисленным литералом, индексы не будут использоваться и результат может оказаться неверным.

### Этап эксплуатации {#operations-phase}

- **Следите за нагрузкой на компактацию.** Рост числа подстолбцов увеличивает затраты на слияние. Если Compaction Score продолжает расти, проверьте, не слишком ли велико значение `variant_max_subcolumns_count` и не слишком ли высока скорость загрузки.
- **Следите за изменениями схемы.** Если структура JSON часто меняется, горячие пути могут попасть в разреженное хранилище, что приведёт к внезапному замедлению запросов. Закрепляйте критически важные пути с помощью Schema Template.
- **Следите за конфликтами типов.** Частые конфликты типов на одном и том же пути указывают на то, что этот путь следует закрепить через Schema Template, чтобы избежать преобразования в JSONB и потери индексов.

## Быстрая проверка {#quick-verify}

После создания таблицы выполните эту минимальную последовательность действий, чтобы убедиться, что всё работает:

```sql
-- Insert sample data
INSERT INTO event_log VALUES
    ('2025-01-01 10:00:00', 1001, 'click', '{"page": "home", "user_id": 42, "duration_ms": 320}'),
    ('2025-01-01 10:00:01', 1002, 'purchase', '{"item": "widget", "price": 9.99, "user_id": 42}'),
    ('2025-01-01 10:00:02', 1003, 'click', '{"page": "search", "user_id": 99, "query": "doris variant"}');

-- Verify data
SELECT payload['user_id'], payload['page'] FROM event_log;

-- Check Subcolumnization results
SET describe_extend_variant_column = true;
DESC event_log;

-- Check per-row types
SELECT variant_type(payload) FROM event_log;
```
