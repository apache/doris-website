> **Кратко** Apache Doris Table Stream — готовящийся к выпуску публичный API для чтения изменений на уровне строк (вставок, обновлений, удалений) из таблицы Doris, аналогично чтению binlog MySQL. Базовые механизмы уже есть в кодовой базе: журнал изменений для каждой таблицы, объект `STREAM`, фиксирующий смещения по разделам, и метаданные чтения. Функция пока не достигла стадии GA, а значение `changelog.ttl_seconds` по умолчанию составляет 86,400 секунд (одни сутки). Для CDC из Doris используйте [Flink Doris Connector](../connection-integration/data-integration/flink-doris-connector). **Статус: Скоро (предварительная версия).**

## Зачем использовать журнал изменений и Table Stream в Apache Doris? {#why}

Журнал изменений и Table Stream в Apache Doris предоставляют потребителям поток изменений на уровне строк, благодаря которому задание Flink, журнал аудита или поисковый индекс могут реагировать на каждую вставку, обновление и удаление без повторного чтения таблицы. Apache Doris хорошо справляется с [загрузкой данных об изменениях](./kafka-cdc-integration). Получить данные об изменениях из Doris сложнее. Если внешней системе (заданию Flink, журналу аудита, другому кластеру Doris, поисковому индексу) нужно реагировать на каждую вставку, [обновление и удаление](./data-update-delete), доступные сейчас варианты неудобны:

- Периодически перечитывать таблицу и вычислять различия. Просто реализовать, дорого выполнять, работа в реальном времени невозможна.
- Настроить двойную запись из источников в Kafka и Doris. Два приёмника данных, два возможных источника сбоев.

Журнал изменений и Table Stream устраняют этот пробел. Журнал изменений записывает каждое зафиксированное изменение на уровне строк. Table Stream представляет собой именованный курсор по этому журналу: потребитель подключается к потоку, читает изменения с момента своего последнего смещения и подтверждает их обработку. Это тот же принцип, что у binlog MySQL, Snowflake Streams или слота логической репликации Postgres, реализованный как полноценный объект Doris.

## Что такое журнал изменений и Table Stream в Apache Doris? {#what}

Журнал изменений Apache Doris — это журнал изменений на уровне строк, который Doris ведёт для каждой таблицы, а Table Stream в Apache Doris — объект для потребителей, предоставляющий доступ к этому журналу в виде CDC на уровне строк. Журнал изменений записывает каждое зафиксированное изменение строки с временем его фиксации и, при необходимости, значениями до изменения. Он отделён от binlog, который используется для межкластерной репликации (CCR): у журнала изменений есть собственные свойства `changelog.*`, и в одной таблице нельзя включить оба механизма одновременно.

Table Stream — это объект для потребителей, построенный поверх журнала изменений. Поток создаётся командой `CREATE STREAM <name> ON TABLE <base_table>`, хранит собственные смещения по разделам и предоставляет SQL-интерфейс: `SHOW CREATE STREAM` и представление `information_schema` для отслеживания прогресса чтения.

**Основные термины**

- **`changelog.enable`**: свойство отдельной таблицы. Значение `true` включает журнал изменений для этой таблицы. Его можно задать только при создании таблицы.
- **`changelog.need_historical_value`**: свойство отдельной таблицы. При значении `true` также записываются значения до каждого обновления и удаления; поддерживается только для таблиц Unique Key Merge-on-Write.
- **`changelog.ttl_seconds`**: параметр срока хранения. По умолчанию TTL составляет одни сутки; его можно изменить после создания таблицы.
- **`STREAM`**: объект Catalog в Doris, связанный с базовой таблицей и отслеживающий смещения по разделам для одного потребителя.
- **Тип чтения потока**: `detail`, `append_only` или `min_delta` (по умолчанию). Определяет, выдаёт ли поток каждое изменение строки, только вставки или минимальный набор изменений.
- **Отставание потока**: видимая версия раздела минус смещение, сохранённое потоком. Отображается в столбце `LAG`.

## Как работают журнал изменений и Table Stream в Apache Doris? {#how}

Журнал изменений Apache Doris записывает изменения на уровне строк в BE, а Table Stream дополняет этот журнал смещениями по разделам, чтобы внешний потребитель мог читать изменения постепенно и подтверждать их обработку.

1. **Включите журнал изменений при создании таблицы.** `CREATE TABLE t (...) PROPERTIES ("changelog.enable" = "true")`. Для существующей таблицы включить журнал изменений нельзя. BE хранит изменения на уровне строк вместе с данными tablet; срок хранения определяется параметром `changelog.ttl_seconds`.
2. **Создайте поток для таблицы.** `CREATE STREAM s ON TABLE t PROPERTIES ("type" = "min_delta")`. FE создаёт объект `STREAM`, сохраняет текущую видимую версию каждого раздела как начальное смещение и регистрирует объект в базе данных. При `show_initial_rows = true` поведение меняется: первое чтение возвращает историческое состояние.
3. **Читайте изменения.** Внешний потребитель (сейчас это внешний CDC-коннектор, в дальнейшем появятся встроенные интерфейсы чтения) читает данные из потока. Каждый пакет продвигает смещения по разделам и сохраняет время чтения.
4. **Очищайте журнал.** Изменения старше `changelog.ttl_seconds` становятся недоступны независимо от того, прочитали ли их все потоки, после чего фоновая компакция освобождает занимаемое ими место. Поток, смещение которого вышло за пределы этого окна, необходимо сбросить и заново инициализировать по свежему снимку.
5. **Наблюдайте за состоянием.** `information_schema.table_streams` перечисляет все потоки и их базовые таблицы. `table_stream_consumption` показывает для каждого раздела `UNIT` (раздел), `CONSUMPTION_STATUS`, `LAG` и `LAST_CONSUMPTION_TIME`. Эти данные позволяют отслеживать отставание.

## Быстрый старт {#quick-start}

```sql
-- 1. Enable the changelog when the source table is created
CREATE TABLE orders (
  order_id   BIGINT,
  order_date DATE,
  status     VARCHAR(16),
  amount     DECIMAL(10, 2)
)
UNIQUE KEY(order_id, order_date)
PARTITION BY RANGE(order_date) (
  PARTITION p_2026_05 VALUES [('2026-05-01'), ('2026-06-01'))
)
DISTRIBUTED BY HASH(order_id) BUCKETS 8
PROPERTIES (
  "enable_unique_key_merge_on_write" = "true",
  "changelog.enable" = "true",
  "changelog.need_historical_value" = "true",
  "changelog.ttl_seconds" = "86400"
);

-- 2. Create a Table Stream over it (planned syntax, subject to change)
CREATE STREAM orders_cdc ON TABLE orders
PROPERTIES ("type" = "min_delta", "show_initial_rows" = "false");

-- 3. Inspect the stream and its lag
SHOW CREATE STREAM orders_cdc;
SELECT * FROM information_schema.table_stream_consumption
WHERE STREAM_NAME = 'orders_cdc';
```

**Ожидаемый результат**

```
+---------+------------+-----------+--------------------+-----+----------------------+
| DB_NAME | STREAM_NAME| STREAM_ID | UNIT (partition)   | LAG | LAST_CONSUMPTION_TIME|
+---------+------------+-----------+--------------------+-----+----------------------+
| sales   | orders_cdc | 10042     | p_2026_05          | 0   | 2026-05-09 10:14:33  |
+---------+------------+-----------+--------------------+-----+----------------------+
```

`LAG = 0` означает, что потребитель достиг видимой версии раздела. По мере фиксации записей в исходной таблице `LAG` растёт, а по мере чтения потребителем уменьшается. Если отставание потребителя превышает `changelog.ttl_seconds`, ему требуется повторное создание снимка; `STALE_REASON` не сообщает об этом случае, поэтому сравнивайте задержку чтения со сроком хранения.

## Когда стоит использовать журнал изменений и Table Stream в Apache Doris? {#when}

После выхода GA используйте журнал изменений и Table Stream в Apache Doris, если внешней системе нужны события изменений на уровне строк из таблицы Doris без повторного чтения всей таблицы.

**Подходящие сценарии (после GA)**

- Запуск обработки в задании Flink или Spark на основе событий изменений в Doris без повторного чтения таблицы.
- Поддержание внешнего поискового индекса, кеша или журнала аудита, которым нужны все вставки и удаления.
- Репликация между кластерами Doris, требующая явного отслеживания смещений потребителей.
- Запуск пересчёта внешнего материализованного представления при изменении `LAG` раздела.

**Неподходящие сценарии (особенно сейчас)**

- Производственные конвейеры CDC на текущий момент. Объект `STREAM` есть в исходном коде, но ещё не объявлен общедоступным в статусе GA. Используйте [интеграцию с Kafka и CDC](./kafka-cdc-integration).
- Длительные паузы в работе потребителей при коротком сроке хранения журнала изменений. Если отставание потребителя превышает `changelog.ttl_seconds`, необходимые ему изменения становятся недоступны, и потребителя приходится инициализировать заново.
- Кластеры с разделёнными хранением и вычислениями. Поддержка Table Stream в таком режиме пока прорабатывается.
- Чтение таблиц из внешних Catalog (Hive, Iceberg). Table Stream поддерживает только внутренние OLAP-таблицы.
