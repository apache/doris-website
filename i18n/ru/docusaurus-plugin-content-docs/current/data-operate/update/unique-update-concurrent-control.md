<!-- Applicable scenarios: High-concurrency data ingestion / Out-of-order updates on the Unique Key model / UPDATE transaction control -->

В модели Unique Key Doris предоставляет средства управления параллельными обновлениями. Они решают три типичные задачи:

| Сценарий | Проблема | Решение Doris |
| --- | --- | --- |
| Многократная загрузка записей с одним первичным ключом | Нужно определить, какая запись в итоге вступит в силу при параллельной загрузке | MVCC (Multi-Version Concurrency Control): порядок перезаписи определяется номером версии |
| Поступление данных не по порядку при многопоточной синхронизации | Старые данные поступают позже и ошибочно перезаписывают новые | Столбец Sequence: пользователь задаёт порядок замещения, и строка с большим значением Sequence имеет приоритет |
| Параллельные UPDATE в одной таблице | Обновления строк могут привести к появлению некорректных данных, поэтому по умолчанию выполняются последовательно | Блокировка на уровне таблицы обеспечивает уровень изоляции Serializable; ограничение параллельного выполнения можно снять |

Ниже описаны принципы работы и способы применения этих механизмов.

## Управление параллелизмом с помощью MVCC {#mvcc-multi-version-concurrency-control}

<!-- Knowledge type: Concept description -->

Doris использует управление параллелизмом с помощью нескольких версий данных (MVCC, Multi-Version Concurrency Control):

- Каждой операции записи данных назначается транзакция записи, которая гарантирует атомарность: запись либо полностью выполняется, либо полностью завершается с ошибкой.
- При фиксации транзакции записи система присваивает ей номер версии.
- Если при многократной загрузке данных в таблицу Unique Key встречаются одинаковые первичные ключи, Doris определяет порядок перезаписи по номеру версии: **данные с более высоким номером версии перезаписывают данные с более низким номером версии**.

## Управление параллельным выполнением UPDATE {#update-concurrency-control}

<!-- Knowledge type: Configuration parameter -->
<!-- Applicable scenarios: Concurrent execution of multiple UPDATE statements -->

### Поведение по умолчанию {#default-behavior}

По умолчанию Doris **не разрешает** параллельно выполнять несколько операций `UPDATE` в одной таблице.

Причина в том, что сейчас Doris поддерживает обновление строк целиком: даже если указать только `SET v2 = 1`, все остальные столбцы Value также перезаписываются, хотя их значения не меняются. Если две операции `UPDATE` одновременно обновляют одну строку, их поведение не определено и возникает риск появления некорректных данных.

Поэтому по умолчанию оператор `UPDATE` обеспечивает уровень изоляции Serializable с помощью блокировки на уровне таблицы: несколько операций `UPDATE` могут выполняться только последовательно.

### Снятие ограничения на параллельное выполнение {#lifting-the-concurrency-limit}

Если вы можете гарантировать, что параллельные обновления не затронут одновременно одну и ту же строку, ограничение можно снять, изменив конфигурацию FE:

| Параметр конфигурации | Значение по умолчанию | Описание |
| --- | --- | --- |
| `enable_concurrent_update` | `false` | При значении `true` разрешает параллельное выполнение `UPDATE`, но гарантии транзакций больше не предоставляются |

## Столбец Sequence {#sequence-column}

<!-- Knowledge type: Feature description -->
<!-- Applicable scenarios: Multi-threaded concurrent synchronization / Out-of-order data ingestion -->

### Зачем нужен столбец Sequence {#why-you-need-a-sequence-column}

Модель Unique предназначена главным образом для сценариев, в которых требуется уникальность первичных ключей, и гарантирует эту уникальность. Однако в следующих случаях одного номера версии загрузки недостаточно:

- При синхронизации данных с Doris через несколько параллельных потоков данные из разных потоков могут поступать не по порядку.
- Старые данные могут поступить позже и ошибочно перезаписать новые.
- Когда данные с одинаковым первичным ключом загружаются в одном пакете или в разных пакетах, порядок замещения не гарантирован, поэтому конечный результат может быть непредсказуемым.

Для решения этой проблемы Doris позволяет при загрузке задать **столбец Sequence**. Строки с одинаковыми столбцами Key замещаются в зависимости от значения столбца Sequence: **большее значение замещает меньшее**, а обратное замещение не происходит. Таким образом, порядок задаёт пользователь.

Для этого Doris добавляет скрытый столбец `__DORIS_SEQUENCE_COL__`. Его тип пользователь указывает при создании таблицы, а значение определяется при загрузке. По этому значению Doris выбирает строку, которая вступит в силу среди строк с одинаковыми столбцами Key.

:::caution Примечание
Столбец Sequence в настоящее время поддерживается только моделью Unique.
:::

### Включение столбца Sequence {#enabling-the-sequence-column}

Включить его можно следующими способами:

| Сценарий | Действие |
| --- | --- |
| Включить при создании таблицы | Задать `function_column.sequence_col` или `function_column.sequence_type` в `PROPERTIES` оператора `CREATE TABLE` |
| Включить в существующей таблице | Выполнить `ALTER TABLE example_db.my_table ENABLE FEATURE "SEQUENCE_LOAD" WITH PROPERTIES ("function_column.sequence_type" = "Date")` |
| Проверить, включён ли столбец | Выполнить `SET show_hidden_columns=true`, затем `desc tablename`. Если вывод содержит `__DORIS_SEQUENCE_COL__`, столбец включён |

Эти два свойства различаются следующим образом:

| Свойство | Значение | Требуется ли соответствующий столбец в схеме |
| --- | --- | --- |
| `function_column.sequence_col` | Сопоставляет столбец Sequence с существующим столбцом таблицы | Да |
| `function_column.sequence_type` | Задаёт только тип столбца Sequence, который хранится как скрытый столбец | Нет |

Поддерживаемые типы столбца: целочисленные типы, `DATE`, `DATETIME` и `TIMESTAMP_NS`. **После создания таблицы тип столбца изменить нельзя.**

### Пример использования {#usage-example}

Ниже полный процесс показан на примере Stream Load.

#### 1. Создание таблицы с поддержкой столбца Sequence {#1-create-a-table-that-supports-the-sequence-column}

Создайте таблицу `test_table` модели Unique и сопоставьте столбец Sequence со столбцом `modify_date`:

```sql
CREATE TABLE test.test_table
(
    user_id bigint,
    date date,
    group_id bigint,
    modify_date date,
    keyword VARCHAR(128)
)
UNIQUE KEY(user_id, date, group_id)
DISTRIBUTED BY HASH (user_id) BUCKETS 32
PROPERTIES(
    "function_column.sequence_col" = 'modify_date',
    "replication_num" = "1",
    "in_memory" = "false"
);
```

Полученная схема таблицы выглядит так:

```sql
MySQL>  desc test_table;
+-------------+--------------+------+-------+---------+---------+
| Field       | Type         | Null | Key   | Default | Extra   |
+-------------+--------------+------+-------+---------+---------+
| user_id     | BIGINT       | No   | true  | NULL    |         |
| date        | DATE         | No   | true  | NULL    |         |
| group_id    | BIGINT       | No   | true  | NULL    |         |
| modify_date | DATE         | No   | false | NULL    | REPLACE |
| keyword     | VARCHAR(128) | No   | false | NULL    | REPLACE |
+-------------+--------------+------+-------+---------+---------+
```

Если вы не хотите, чтобы этот столбец отображался в схеме таблицы, вместо этого укажите его тип с помощью `function_column.sequence_type`:

```sql
PROPERTIES (
    "function_column.sequence_type" = 'Date'
);
```

#### 2. Загрузка данных и проверка работы Sequence {#2-import-data-and-verify-the-sequence-behavior}

При использовании сопоставления столбцов (`function_column.sequence_col`) дополнительные параметры в команде загрузки не нужны. Загрузите следующие данные с помощью Stream Load:

```Plain
1	2020-02-22	1	2020-02-21	a
1	2020-02-22	1	2020-02-22	b
1	2020-02-22	1	2020-03-05	c
1	2020-02-22	1	2020-02-26	d
1	2020-02-22	1	2020-02-23	e
1	2020-02-22	1	2020-02-24	b
```

Команда Stream Load:

```shell
curl --location-trusted -u root: -T testData http://host:port/api/test/test_table/_stream_load
```

Результат запроса:

```sql
MySQL> select * from test_table;
+---------+------------+----------+-------------+---------+
| user_id | date       | group_id | modify_date | keyword |
+---------+------------+----------+-------------+---------+
|       1 | 2020-02-22 |        1 | 2020-03-05  | c       |
+---------+------------+----------+-------------+---------+
```

Поскольку `2020-03-05` — наибольшее значение столбца Sequence (`modify_date`), в столбце `keyword` сохраняется `c`.

#### 3. Указание столбца Sequence при разных способах загрузки {#3-specifying-the-sequence-column-in-different-import-methods}

Если таблица использует `function_column.sequence_type`, столбец Sequence скрыт, и при загрузке ему необходимо сопоставить входное поле. В следующих примерах используется **отдельная таблица**, а не описанная выше `test_table`, в которой столбец Sequence сопоставлен с `modify_date`.

```sql
CREATE DATABASE IF NOT EXISTS test;
CREATE TABLE test.test_sequence_hidden
(
    k1 BIGINT NOT NULL,
    k2 DATE NOT NULL,
    v1 BIGINT,
    v2 VARCHAR(128)
)
UNIQUE KEY(k1, k2)
DISTRIBUTED BY HASH(k1) BUCKETS 1
PROPERTIES (
    "function_column.sequence_type" = "DATE",
    "replication_num" = "1"
);
```

Подготовьте файл `sequence_data.tsv` со следующими строками, разделёнными знаками табуляции. Четвёртое входное поле, `source_sequence`, задаёт значение скрытого столбца Sequence; оно не является видимым столбцом таблицы.

```text
1	2020-02-22	1	2020-02-22	a
1	2020-02-22	1	2020-03-23	w
```

**Stream Load**

Сопоставьте входные поля в порядке их следования в файле и укажите поле Sequence в заголовке запроса:

```shell
curl --location-trusted -u root: \
    -H "columns: k1,k2,v1,source_sequence,v2" \
    -H "function_column.sequence_col: source_sequence" \
    -T sequence_data.tsv http://host:port/api/test/test_sequence_hidden/_stream_load
```

**Broker Load**

Загрузите тот же файл в HDFS и замените путь и учётные данные Broker ниже. Используйте разделитель табуляции и тот же порядок полей, затем выберите четвёртое входное поле с помощью `ORDER BY source_sequence`:

```sql
LOAD LABEL test.sequence_hidden_broker
(
    DATA INFILE("hdfs://host:port/user/data/sequence_data.tsv")
    INTO TABLE `test_sequence_hidden`
    COLUMNS TERMINATED BY "\t"
    (k1,k2,v1,source_sequence,v2)
    ORDER BY source_sequence
)
WITH BROKER 'broker'
(
    "username" = "user",
    "password" = "pass"
)
PROPERTIES ("timeout" = "3600");
```

**Routine Load**

Создайте задачу, указав свой брокер Kafka и тему, а затем отправьте каждую приведённую выше строку как отдельное сообщение Kafka с полями, разделёнными знаками табуляции:

```sql
CREATE ROUTINE LOAD test.sequence_hidden_routine ON test_sequence_hidden
    COLUMNS TERMINATED BY "\t",
    COLUMNS(k1,k2,v1,source_sequence,v2),
    ORDER BY source_sequence
    PROPERTIES
    (
        "desired_concurrent_number" = "1",
        "format" = "csv"
    )
    FROM KAFKA
    (
        "kafka_broker_list" = "broker1:9092",
        "kafka_topic" = "my_topic"
    );
```

После успешной загрузки, когда данные станут видимыми, строка с большим значением Sequence (`2020-03-23`) и значением `w` в столбце `v2` сохранится. В следующих примерах с `modify_date` снова используется исходная таблица `test_table` и заданное в ней сопоставление столбцов.

#### 4. Проверка гарантированного порядка замещения {#4-verify-the-replacement-order-guarantee}

Продолжая предыдущий пример, загрузите следующие данные, в которых все значения Sequence меньше существующего максимума `2020-03-05`:

```Plain
1	2020-02-22	1	2020-02-22	a
1	2020-02-22	1	2020-02-23	b
```

Результат запроса:

```sql
MySQL [test]> select * from test_table;
+---------+------------+----------+-------------+---------+
| user_id | date       | group_id | modify_date | keyword |
+---------+------------+----------+-------------+---------+
|       1 | 2020-02-22 |        1 | 2020-03-05  | c       |
+---------+------------+----------+-------------+---------+
```

Поскольку все значения Sequence в этой загрузке меньше существующего максимума `2020-03-05`, результат не меняется.

Теперь загрузите данные с большим значением Sequence:

```Plain
1	2020-02-22	1	2020-02-22	a
1	2020-02-22	1	2020-03-23	w
```

Результат запроса:

```sql
MySQL [test]> select * from test_table;
+---------+------------+----------+-------------+---------+
| user_id | date       | group_id | modify_date | keyword |
+---------+------------+----------+-------------+---------+
|       1 | 2020-02-22 |        1 | 2020-03-23  | w       |
+---------+------------+----------+-------------+---------+
```

Поскольку значение Sequence `2020-03-23` у новых данных больше существующего максимума `2020-03-05`, исходные данные замещаются.

**Вывод**: при загрузке Doris сравнивает значения столбца Sequence во всех пакетах и **записывает в таблицу запись с наибольшим значением**.

### Особенности использования {#usage-notes}

<!-- Knowledge type: Caveats -->

1. **Требования к Sequence зависят от определения таблицы**: при использовании `function_column.sequence_col` загружайте сопоставленный обычный столбец по стандартным правилам для столбцов; дополнительный параметр сопоставления Sequence при загрузке не нужен. При использовании `function_column.sequence_type` настройте сопоставление входного столбца для Stream Load или Broker Load, как показано выше. Если полнострочный `INSERT` содержит явный список целевых столбцов, включите в него сопоставленный обычный столбец (если его значение по умолчанию не равно `CURRENT_TIMESTAMP`) либо скрытый столбец `__DORIS_SEQUENCE_COL__`, если сопоставленного столбца нет. В `INSERT` без списка целевых столбцов сопоставленный обычный столбец уже включён. Частичные обновления столбцов описаны ниже, в пункте 3. Если обязательное значение Sequence отсутствует, возникает следующая ошибка:

    ```Plain
    Table test_tbl has sequence column, need to specify the sequence column
    ```

2. **Отключение проверки обязательного наличия столбца Sequence**: в таких сценариях, как репликация таблицы или внутренняя миграция данных, обязательную проверку столбца Sequence в операторах `INSERT` можно отключить с помощью переменной сеанса:

    ```sql
    set require_sequence_in_insert = false;
    ```

3. **Совместимость с частичными обновлениями столбцов**: начиная с версии 2.0 реализация Merge-on-Write для таблиц Doris Unique Key поддерживает частичные обновления столбцов. При такой загрузке каждый раз можно обновлять только часть столбцов, поэтому **столбец Sequence не обязателен**:

    - Если задание загрузки содержит столбец Sequence, поведение не меняется.
    - Если задание загрузки не содержит столбец Sequence, Doris берёт значение этого столбца из соответствующей строки существующих данных для обновлённой строки.
    - Если в существующих данных нет записи с таким же Key, Doris автоматически подставляет `null` или значение по умолчанию.

4. **Гарантия корректности при параллельной загрузке**: при параллельной загрузке Doris использует MVCC для обеспечения корректности данных. Если два пакета обновляют разные столбцы строки с одним Key, то после успешного выполнения задания загрузки с более низким номером версии задание с более высоким номером версии использует записанную первым заданием строку с тем же Key, чтобы заполнить отсутствующие значения.
