В этом документе представлены результаты практического тестирования производительности загрузки и запросов с индексом ANN в Doris на наборах данных среднего и большого объёма, включая сотни миллионов записей. Документ поможет оценить производительность запросов при разных объёмах данных и понять, как плавно перейти от одноузлового к распределённому развёртыванию.

## Быстрая навигация {#quick-navigation}

Прочитав этот документ, вы сможете ответить на следующие вопросы:

- Может ли один узел BE обеспечивать поиск в реальном времени по десяткам миллионов векторов? Каких значений QPS и задержки можно ожидать?
- Как продолжить обслуживать векторные запросы к сотням миллионов векторов с помощью нескольких узлов BE, если памяти одного узла уже недостаточно?
- Как различается производительность при разной размерности векторов (768/1536) и разных метриках расстояния (`inner_product`/`l2_distance`)?
- Как воспроизвести результаты этих тестов?

## Тестовая среда и наборы данных {#test-environment-and-datasets}

### Топология развёртывания {#deployment-topology}

| Режим развёртывания | Узлы BE | Конфигурация узла | Подходящий объём данных |
|-----------------|----------|---------------|---------------------|
| Один узел       | 1        | 16C64GB       | Десятки миллионов   |
| Распределённый  | 3        | 16C64GB       | Сотни миллионов     |

FE и BE развёрнуты отдельно. Во всех тестах используется инструмент [VectorDBBench](https://github.com/zilliztech/VectorDBBench).

#### Мониторинг CPU {#cpu-monitoring}

На этапе холодных запросов индекс необходимо загрузить в память, поэтому использование CPU относительно низкое, а система в основном ожидает завершения операций IO. После перехода к горячим запросам использование CPU значительно возрастает и приближается к 100%.

## Тест производительности распределённого развёртывания (3 x 16C64GB) {#distributed-benchmark-3-x-16c64gb}

Когда объём данных превышает объём, который можно обоснованно разместить в памяти одного узла с конфигурацией 16C64GB, можно масштабировать систему горизонтально, развернув несколько узлов BE. В этом разделе на примере набора данных `Performance768D100M` (100M строк, 768 измерений) показано, что Doris сохраняет возможность выполнять векторные запросы в реальном времени и при объёме 100M.

:::tip Совет
Результаты этого теста не предназначены для прямого сравнения абсолютных значений с результатами одноузловых тестов на меньших объёмах данных. Они лучше подходят для оценки того, как меняется производительность с ростом объёма данных.
:::

### Загрузка и построение индекса {#load-and-index-build}

Поскольку объём памяти каждого узла ограничен 64GB, в этом тесте для уменьшения потребления памяти используется сжатие с помощью векторного квантования.

| Показатель        | Значение |
|-------------------|-------|
| Набор данных      | Performance768D100M |
| Объём данных      | 100M строк |
| Размерность вектора | 768 |
| Параметры пакета  | `NUM_PER_BATCH=500000`<br/>`--stream-load-rows-per-batch 500000` |
| Параметры индекса | `"dim"="768", "index_type"="hnsw", "metric_type"="l2_distance", "pq_m"="384", "pq_nbits"="8", "quantizer"="pq"` |
| Время построения индекса | 4h5min |
| `show data all`   | 198.809 GB (137.259 GB + 61.550 GB) |

**Распределение данных после построения индекса:**

- Всего 3 бакета
- Каждый бакет содержит 34 rowset размером около 1.99 GB каждый
- Каждый rowset содержит 6 сегментов

**Использование CPU:** Во время построения индекса использование CPU в целом оставалось стабильным на уровне около 50%. Длительных периодов максимальной загрузки CPU не наблюдалось, поэтому сохранялся некоторый запас ресурсов.

## Основные выводы {#key-conclusions}

- **Десятки миллионов на одном узле:** При объёме векторных данных в десятки миллионов одноузловое развёртывание Doris обеспечивает сотни QPS для ANN-запросов при высокой полноте поиска (>=0.92).
- **Сотни миллионов в распределённом развёртывании:** На наборе данных из 100M векторов развёртывание с несколькими узлами BE в сочетании со сжатием с помощью векторного квантования позволяет продолжать выполнять векторные запросы в реальном времени (BestQPS около 77, Recall@100 около 0.93).
- **Горизонтальная масштабируемость:** Когда объём данных превышает ёмкость памяти одного узла, распределённое развёртывание позволяет сохранить возможность поиска в реальном времени.

## Примечания к тестам {#test-notes}

При интерпретации результатов учитывайте следующее:

- **Разные метрики расстояния:** В одноузловых тестах используется `inner_product`, а в распределённом тесте используется `l2_distance`. **Прямое сравнение абсолютных значений не рекомендуется.**
- **Разные объёмы данных и параметры индекса:** Объёмы данных и параметры индекса, например использование квантования, различаются между группами тестов. Результаты лучше подходят для оценки того, как меняется производительность с ростом объёма данных.
- **Корректировка с учётом холодных запросов:** В одноузловом тесте `Performance768D10M` результат для 10 одновременных запросов был скорректирован после исключения влияния холодных запросов.

## Как воспроизвести результаты {#how-to-reproduce}

Тесты выполняются с помощью инструмента [VectorDBBench](https://github.com/zilliztech/VectorDBBench).

### Воспроизведение одноузловых тестов {#single-node-reproduction}

```bash
# Performance768D10M
export NUM_PER_BATCH=500000
vectordbbench doris ... --case-type Performance768D10M --stream-load-rows-per-batch 500000

# Performance1536D5M
export NUM_PER_BATCH=250000
vectordbbench doris ... --case-type Performance1536D5M --stream-load-rows-per-batch 250000
```

### Воспроизведение распределённого теста с 3BE {#distributed-3be-reproduction}

```bash
export NUM_PER_BATCH=500000
vectordbbench doris ... --case-type Performance768D100M --stream-load-rows-per-batch 500000
```

## Часто задаваемые вопросы {#faq}

**Вопрос 1: Какое максимальное количество векторов может вместить один узел с конфигурацией 16C64GB?**

Это зависит от размерности векторов, использования квантования и параметров индекса. В приведённом тесте 10M строк с 768-мерными векторами (около 56 GB) стабильно обрабатываются на одном узле с конфигурацией 16C64GB. При дальнейшем росте объёма данных или увеличении размерности включите векторное квантование либо используйте распределённое развёртывание с несколькими узлами BE.

**Вопрос 2: Почему QPS в распределённом тесте ниже, чем в одноузловых тестах?**

Эти группы тестов различаются метрикой расстояния, объёмом данных и параметрами индекса (в распределённом тесте включено квантование PQ), поэтому напрямую сравнивать абсолютные значения нельзя. Цель распределённого теста состоит в проверке масштабируемости на больших объёмах данных, а не в достижении максимального QPS.

**Вопрос 3: Почему для набора данных объёмом 100M требуется квантование?**

Объём памяти каждого узла ограничен 64GB, а исходный размер 100M векторов размерности 768 уже превышает эту ёмкость. Квантование PQ (`pq_m=384`, `pq_nbits=8`) значительно снижает потребление памяти и позволяет выполнять поиск в реальном времени на больших объёмах данных.

**Вопрос 4: Включает ли время загрузки время построения индекса?**

В одноузловых тестах «время загрузки» означает общее время записи. Индекс строится либо во время записи, либо на этапе фоновой компактации. В распределённом тесте `build index time` указан отдельно, чтобы можно было оценить затраты на построение индекса при больших объёмах данных.
