При выполнении полнотекстовых запросов (например, с `MATCH_ANY`, `MATCH_ALL` или `MATCH_PHRASE`) часто требуется сортировать результаты по «степени совпадения», чтобы первыми возвращались наиболее релевантные записи. Doris поддерживает **оценку релевантности**: каждой строке присваивается числовая оценка на основе условий запроса. Чем выше оценка, тем выше релевантность.

В настоящее время Doris по умолчанию использует для оценки релевантности алгоритм **BM25 (Best Matching 25)**.

**Типичные сценарии использования:**

- Поисковые приложения: возврат списка наиболее релевантных документов по ключевым словам
- Анализ журналов: сортировка по релевантности для быстрого поиска записей, лучше всего соответствующих ключевым словам
- Рекомендация контента: отбор приоритетного контента на основе сходства текстов
- Поиск по базе знаний: возврат возможных ответов, упорядоченных по релевантности вопросу

## Быстрый старт {#quick-start}

Следующий пример показывает, как получить оценку релевантности в запросе и отсортировать результаты по ней:

```sql
SELECT *,
       score() AS relevance
FROM search_demo
WHERE content MATCH_ANY 'text search test'
ORDER BY relevance DESC
LIMIT 10;
```

После выполнения Doris вычисляет оценку каждой строки с помощью алгоритма BM25 и возвращает 10 наиболее релевантных записей:

```text
+------+-----------------------------------+---------+--------------+-----------+
| id   | content                           | author  | publish_date | relevance |
+------+-----------------------------------+---------+--------------+-----------+
|    1 | Full text search engine test demo | Alice   | 2024-01-01   |  2.915228 |
|    7 | Text processing techniques        | Grace   | 2024-01-07   |  1.341931 |
|    5 | Performance test framework        | Eve     | 2024-01-05   |  1.341931 |
|    3 | Advanced search algorithms        | Charlie | 2024-01-03   |  1.341931 |
+------+-----------------------------------+---------+--------------+-----------+
```

## Условия использования {#activation-conditions}

В текущей версии для разработки оператор `SELECT`, вычисляющий `score()`, должен обращаться к одной внутренней таблице Doris и содержать хотя бы одно условие `MATCH_*` или `SEARCH` в собственном предложении `WHERE`. Соединения, подзапросы внутри этого `SELECT` и латеральные представления не поддерживаются.

Во внешнем операторе `SELECT` без агрегирования `score()` можно использовать в списке выбираемых выражений, оконных функциях и `ORDER BY`; `ORDER BY` и `LIMIT` необязательны. В запросе с `GROUP BY`, агрегатными функциями или `DISTINCT` функцию `score()` можно использовать только в `WHERE` для фильтрации по минимальной оценке.

Оператор `SELECT`, вычисляющий оценку внутри подзапроса, представления, CTE или операции над множествами, по-прежнему должен сортировать результаты по своей оценке и содержать `LIMIT`. Коррелированные подзапросы не могут вызывать `score()`. Форма Top-N из примера быстрого старта также поддерживается.

### Фильтрация по оценке релевантности {#filter-by-relevance-score}

Сначала подготовьте отдельную таблицу для примера с инвертированным индексом, использующим токенизацию. Для выполнения следующих инструкций нужны права на создание базы данных и таблицы, загрузку данных и выполнение запросов:

```sql
CREATE DATABASE IF NOT EXISTS score_filter_example;
USE score_filter_example;

CREATE TABLE score_filter_demo (
    id BIGINT,
    content TEXT,
    INDEX idx_content (content) USING INVERTED
        PROPERTIES("parser" = "english", "support_phrase" = "true")
)
DUPLICATE KEY(id)
DISTRIBUTED BY HASH(id) BUCKETS 1
PROPERTIES ("replication_num" = "1");

INSERT INTO score_filter_demo VALUES
(1, 'Full text search engine test demo'),
(2, 'Database performance analysis'),
(3, 'Search engine examples');
```

Doris 4.0.4 и более поздние версии поддерживают прямую фильтрацию по минимальной оценке в `WHERE`. Следующая форма Top-N совместима с Doris 4.0.4 и более поздними версиями:

```sql
SELECT *, score() AS relevance
FROM score_filter_demo
WHERE content MATCH_ANY 'text search test'
  AND score() > 5
ORDER BY relevance DESC
LIMIT 10;
```

Запрос возвращает до 10 совпадающих строк с оценкой выше 5, отсортированных по убыванию оценки. Если ни одна совпадающая строка не проходит порог, результат пуст. Оценки зависят от запроса и набора данных, поэтому значение 5 приведено только в качестве примера порога.

Используйте саму функцию `score()` в `WHERE`, а её псевдоним из списка выбираемых выражений — в `ORDER BY`. Прямая фильтрация поддерживает одно условие минимальной оценки: `score() > <threshold>` или `score() >= <threshold>`, где порог — числовая константа. Для совместимости с выпущенными версиями 4.x используйте числовой литерал. Объединяйте условия оценки и поиска с помощью `AND`. Верхние границы (`<`, `<=`), равенство (`=`), несколько условий оценки и условия оценки внутри `OR` не поддерживаются.

#### Фильтрация без Top-N в версии для разработки {#filtering-without-top-n-in-the-development-version}

В текущей версии для разработки внешний оператор `SELECT`, обращающийся к одной таблице, может фильтровать по оценке без `ORDER BY` и `LIMIT`:

```sql
SELECT id, content, score() AS relevance
FROM score_filter_demo
WHERE content MATCH_ANY 'text search test'
  AND score() > 5;
```

Запрос возвращает все совпадающие строки с оценкой выше 5, не задавая порядок и ограничение числа строк. Оператор `SELECT`, вычисляющий оценку внутри подзапроса, представления, CTE или операции над множествами, по-прежнему должен содержать собственную сортировку по оценке и `LIMIT`.

#### Совместимость с Doris 4.0.0–4.0.3 {#compatibility-with-doris-400-to-403}

Doris версий с 4.0.0 по 4.0.3 не допускает использование `score()` в `WHERE`. В этих версиях сначала выберите в подзапросе ограниченное число кандидатов с вычисленной оценкой: условие `MATCH_*`, сортировка `ORDER BY` по псевдониму оценки и `LIMIT` должны находиться внутри подзапроса. Затем отфильтруйте результаты по псевдониму во внешнем запросе:

```sql
SELECT a.*
FROM (
    SELECT *, score() AS relevance
    FROM score_filter_demo
    WHERE content MATCH_ANY 'text search test'
    ORDER BY relevance DESC
    LIMIT 1000
) AS a
WHERE a.relevance > 5
ORDER BY a.relevance DESC
LIMIT 10;
```

Запрос возвращает до 10 строк с оценкой выше 5 из 1000 кандидатов с наивысшими оценками. Если ни один из этих кандидатов не проходит порог, результат пуст. Выбирайте ограничение числа кандидатов с учётом потребностей приложения: эта схема фильтрует выбранных кандидатов, а не возвращает все совпадающие строки с оценкой выше порога.

В Doris версий с 4.0.0 по 4.0.3 сохраняйте внутренний `LIMIT`: без него подзапрос теряет необходимую форму Top-N, и оптимизатор может перенести внешнее условие по оценке внутрь запроса, вычисляющего оценку. Одних лишь внешних `ORDER BY` и `LIMIT` недостаточно для необходимой внутренней операции Top-N.

### Поддерживаемые типы индексов {#supported-index-types}

| Тип индекса | Поддержка оценки | Описание |
| ---------- | ---------------- | -------- |
| Инвертированный индекс с токенизацией | Да | Позволяет вычислять оценки релевантности BM25 |
| Инвертированный индекс без токенизации | Нет | Поддерживает только точное совпадение; оценки не вычисляются |

### Поддерживаемые типы запросов {#supported-query-types}

- `MATCH_ANY`
- `MATCH_ALL`
- `MATCH_PHRASE`
- `MATCH_PHRASE_PREFIX`
- `SEARCH`

## Алгоритм BM25 {#bm25-algorithm}

BM25 — алгоритм оценки релевантности текста, основанный на вероятностной модели. Он рассчитывает взвешенную оценку совпадений с учётом трёх факторов: **частоты термина (TF)**, **обратной частоты документа (IDF)** и **длины записи**. По сравнению с традиционной моделью TF-IDF алгоритм BM25 более устойчив и гибок в настройке, а также эффективно уравновешивает оценки длинных и коротких текстов.

### Основная формула {#core-formula}

```text
score = IDF × (tf × (k1 + 1)) / (tf + k1 × (1 - b + b × |d| / avgdl))
```

Переменные в формуле имеют следующие значения:

| Переменная | Значение |
| ---------- | -------- |
| `tf` | Число вхождений термина запроса в текущую строку |
| `IDF` | Обратная частота документа, характеризующая редкость термина |
| `\|d\|` | Длина текущей строки (число токенов после токенизации) |
| `avgdl` | Средняя длина всех строк таблицы |
| `k1`, `b` | Параметры настройки алгоритма |

### Параметры {#parameters}

| Параметр | Значение по умолчанию | Описание |
| -------- | --------------------- | -------- |
| `k1` | 1.2 | Определяет степень влияния частоты термина на оценку |
| `b` | 0.75 | Определяет степень нормализации по длине записи |
| `boost` | 1.0 | Весовой коэффициент на уровне запроса |

### Дополнительные статистические показатели {#auxiliary-statistics}

```text
IDF   = log(1 + (N - n + 0.5) / (n + 0.5))
avgdl = total_terms / total_rows
```

Где:

- `N`: общее число строк в таблице
- `n`: число строк, содержащих термин запроса

Если запрос содержит несколько терминов, **итоговая оценка равна сумме оценок каждого термина**.

### Длина записи и свойство `norms` {#record-length-and-the-norms-property}

Свойство индекса `norms` и параметр конфигурации BE `inverted_index_skip_norms_for_variant` поддерживаются начиная с Doris 4.1.5.

Значение `|d|` берётся из norms, которые занимают один байт на каждую строку для каждого индексируемого поля, включая строки, где у поля нет значения. Индексы с токенизацией по умолчанию записывают norms (`"norms" = "true"`), а индексы без токенизации — нет. Для индексов, используемых только для фильтрации, установите `"norms" = "false"`, чтобы сэкономить место:

```sql
INDEX idx_content(content) USING INVERTED PROPERTIES("parser" = "english", "norms" = "false")
```

Подпути VARIANT наследуют свойство индекса `norms`; затраты на хранение составляют `rows × paths` байт. Если установить параметр конфигурации BE `inverted_index_skip_norms_for_variant` (по умолчанию `false`, можно изменить во время работы) в `true`, запись norms отключается для всех индексов путей VARIANT независимо от свойства индекса.

Отключение norms не влияет на фильтрацию `MATCH_*`, но `score()` возвращает ошибку, если считывает хотя бы один сегмент без norms. Эти настройки влияют на вновь записываемые сегменты; существующие сегменты остаются без изменений, пока compaction не перезапишет их. Перед изменением настроек обновите все BE до версии, которая их поддерживает.

## Интерпретация результатов {#interpreting-the-results}

Понимание оценок помогает точнее использовать ранжирование по релевантности:

| Характеристика | Описание |
| -------------- | -------- |
| Диапазон оценок | Положительные числа без фиксированной верхней границы; обычно важно относительное значение, а не абсолютное |
| Запрос с несколькими терминами | Если запрос содержит несколько терминов, общая оценка равна сумме оценок отдельных терминов |
| Влияние длины | При одинаковых совпадающих терминах более короткая запись получает немного более высокую оценку |
| Отсутствие совпадающего термина | Если термин запроса не встречается в таблице, соответствующая оценка равна 0 |

## Частые вопросы {#faq}

**Вопрос 1: Почему мой запрос не возвращает оценки?**

Последовательно проверьте:

1. Добавлена ли функция `score()` в список выбираемых выражений `SELECT`, если нужно вывести оценку.
2. Обращается ли тот же оператор `SELECT` к одной внутренней таблице и содержит ли он условие `MATCH_*` или `SEARCH` в `WHERE`.
3. Если оператор `SELECT`, вычисляющий оценку, находится внутри подзапроса, представления, CTE или операции над множествами, сортирует ли он результаты по собственной оценке и содержит ли собственный `LIMIT`.
4. Является ли индекс инвертированным индексом с токенизацией.

**Вопрос 2: Чем BM25 отличается от TF-IDF?**

BM25 развивает TF-IDF за счёт двух улучшений: **насыщения частоты термина** и **нормализации по длине**. Благодаря им оценки длинных и коротких текстов становятся более сбалансированными, а алгоритм — более устойчивым.

**Вопрос 3: Можно ли сравнивать оценки разных запросов?**

Это не рекомендуется. Оценки BM25 зависят от конкретных терминов запроса и распределения данных в таблице. Абсолютные значения для разных запросов несопоставимы. **Сравнивайте относительные значения только в пределах набора результатов одного запроса.**
