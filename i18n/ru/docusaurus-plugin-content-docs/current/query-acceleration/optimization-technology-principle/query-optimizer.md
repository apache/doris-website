## Определение одним предложением {#one-sentence-definition}

Оптимизатор запросов Doris (Nereids) — это современный оптимизатор запросов, построенный на основе фреймворка Cascades. Он сочетает RBO (оптимизацию на основе правил) и CBO (оптимизацию на основе стоимости), чтобы формировать эффективные планы выполнения сложных запросов.

## Предпосылки разработки {#development-background}

<!-- Knowledge type: Background explanation -->

Существующий оптимизатор запросов сталкивается с тремя категориями проблем:

| Проблема | Конкретное проявление |
| :--- | :--- |
| Высокая сложность запросов | Пользовательские запросы становятся всё сложнее, а сценарии их использования — всё разнообразнее |
| Строгие требования к работе в реальном времени | Пользователи ожидают немедленного получения результатов запросов |
| Быстрый темп развития | Оптимизатор должен быстро адаптироваться к постоянно возникающим новым требованиям |

В этих условиях в Doris началась разработка совершенно нового оптимизатора запросов. Построенный на современной архитектуре, он призван эффективнее обрабатывать запросы в сценариях использования Doris и заложить прочную основу для поддержки более сложных требований в будущем.

## Преимущества оптимизатора запросов Doris {#advantages-of-the-doris-query-optimizer}

<!-- Knowledge type: Feature introduction -->
<!-- Applicable scenario: Evaluate whether to enable Nereids, compare differences between the new and old optimizers -->

Оптимизатор запросов Doris обладает существенными преимуществами перед прежним оптимизатором по трём направлениям: он более интеллектуальный, стабильный и гибкий.

### Более интеллектуальный {#smarter}

- Оптимизатор явно представляет каждое отдельное преобразование RBO и CBO в виде «правила».
- Каждое правило содержит набор шаблонов, описывающих структуру плана запроса. Это позволяет оптимизатору точно определять планы, к которым можно применить оптимизацию.
- Благодаря этому оптимизатор лучше поддерживает сложные запросы, например с многоуровневыми вложенными подзапросами.

Часть, отвечающая за CBO, построена на передовом фреймворке Cascades и в полной мере использует следующие три категории информации:

1. Подробная статистика данных
2. Информация о характеристиках данных
3. Тщательно настроенная модель стоимости

Благодаря этой информации оптимизатор легко справляется со сложными запросами, например с соединениями множества таблиц.

### Более стабильный {#more-stable}

- Все правила оптимизации применяются к дереву логического плана выполнения.
- После синтаксического и семантического анализа запрос преобразуется в древовидную структуру.
- По сравнению с прежним оптимизатором внутренние структуры данных нового оптимизатора более продуманны и унифицированны.

Рассмотрим обработку подзапросов: новый оптимизатор использует новую структуру данных и устраняет характерную для прежнего оптимизатора ситуацию, когда множество правил обрабатывают подзапросы по отдельности. Это снижает вероятность логических ошибок в правилах оптимизации.

### Более гибкий {#more-flexible}

Продуманная современная архитектура оптимизатора позволяет легко расширять правила оптимизации и этапы обработки. Новые возможности можно быстро добавлять в соответствии с постоянно меняющимися требованиями.

## Принцип работы оптимизатора {#working-principle-of-the-optimizer}

<!-- Knowledge type: Process explanation -->

### Общая схема работы {#overall-workflow}

![Принцип работы оптимизатора](/images/cost-based-optimizer.jpg)

Процесс работы оптимизатора можно условно разделить на следующие четыре шага:

| Шаг | Этап | Описание |
| :--- | :--- | :--- |
| 1 | Синтаксический анализ | Преобразование текста SQL в абстрактное синтаксическое дерево (AST). Если SQL корректен, обработка продолжается; в противном случае выдаётся ошибка и обработка прекращается |
| 2 | Семантический анализ | Проверка существования таблиц, столбцов и функций в AST, а также соответствия их использования синтаксическим и семантическим правилам. Если проверка пройдена, обработка продолжается; в противном случае выдаётся ошибка и обработка прекращается |
| 3 | Переписывание плана запроса (RBO) | Переписывание плана запроса с помощью заранее определённых правил. Распространённые приёмы включают отсечение ненужных столбцов, проталкивание предикатов и отсечение партиций |
| 4 | Оптимизация плана запроса (CBO) | Перебор множества эквивалентных планов в пределах пространства поиска, оценка стоимости выполнения каждого плана и выбор плана с наименьшей стоимостью в качестве итогового плана выполнения |

Цели каждого шага:

- **Синтаксический анализ**: убедиться, что текст SQL можно разобрать и преобразовать в корректное AST.
- **Семантический анализ**: убедиться, что объекты, на которые ссылается AST, существуют и используются корректно.
- **Переписывание RBO**: повысить скорость выполнения с помощью детерминированных правил.
- **Оптимизация CBO**: выбрать оптимальный план выполнения на основе модели стоимости, чтобы обеспечить наиболее эффективное выполнение запроса.

## Часто используемые сеансовые переменные {#common-session-variables}

### nereids_timeout_second {#nereids_timeout_second}

| Параметр | Описание |
| :--- | :--- |
| Назначение | Задаёт максимально допустимое время планирования запроса. При превышении этого значения планирование прекращается и возвращается сообщение об ошибке |
| Значение по умолчанию | 30s |
| Сценарий использования | Если запрос обращается к большому количеству внешних таблиц или сам запрос особенно сложен, увеличьте это значение до подходящего уровня, чтобы обеспечить нормальную обработку запроса |

**Цель механизма**: во время планирования запроса система устанавливает блокировки на чтение для всех таблиц, задействованных в SQL. Основные цели ограничения времени планирования:

- Поддерживать стабильность кластера
- Предотвращать чрезмерное потребление ресурсов из-за слишком долгого планирования
- Избегать конфликтов блокировок

**Рекомендации по настройке**:

- При возникновении ошибки превышения времени планирования сначала проверьте, не слишком ли сложен SQL и не задействовано ли в нём слишком много таблиц.
- Если вы убедились, что такая сложность запроса оправданна, увеличьте это значение с помощью `SET nereids_timeout_second = <seconds>;`.
