## Обзор {#overview}

Тип VARIANT хранит полуструктурированные данные JSON: объекты, массивы, строки, числа, логические значения и `null`. При записи Doris определяет тип каждого пути JSON и выполняет Subcolumnization для часто встречающихся путей, сохраняя их как отдельные столбцовые подстолбцы. Запрос к такому пути считывает только нужный подстолбец.

:::tip Зачем использовать VARIANT
`VARIANT` подходит для документов, структура которых меняется со временем, если запросы по-прежнему обращаются к небольшому набору часто используемых путей.

- Часто используемые пути участвуют в Subcolumnization и получают преимущества столбцового хранения, отсечения файлов и векторизованного выполнения.
- Для важных путей доступны индексы на уровне пути и полнотекстовый поиск; при этом сохраняются преимущества отсечения с помощью разреженных индексов Doris.
- Оптимизации для широких столбцов позволяют применять автоматическую Subcolumnization при масштабе порядка 10k подстолбцов. Когда число путей, участвующих в Subcolumnization, приближается к 10,000, требования к оборудованию быстро растут, поэтому обычно безопаснее начинать с режима DOC.

Если нужно выбрать между поведением по умолчанию, разреженными столбцами, режимом DOC и Schema Template, начните с [руководства по нагрузкам VARIANT](./variant-workload-guide.md). Эта страница служит справочником по записи и разбору данных, правилам типов, CAST, семантике NULL и сравнений, ALTER, индексам, ограничениям и настройкам.
:::

:::info Версия
На этой странице описан VARIANT в Doris 5.0.0 и более поздних версиях. Следующие отличия от Doris 4.x наиболее вероятно повлияют на существующий SQL:

- `INSERT` сохраняет строку как строку VARIANT, а не разбирает её как JSON. Это относится и к `INSERT INTO ... SELECT` из табличных функций, таких как `s3()` и `hdfs()`. Для записи текста JSON через `INSERT` используйте `PARSE_TO_VARIANT`. Задания загрузки, такие как Stream Load, по-прежнему разбирают JSON.
- Целые значения VARIANT поддерживают `GROUP BY`, `DISTINCT` и операции над множествами. Два значения VARIANT можно сравнивать с помощью `=`, `!=` и `<=>`, а также использовать как ключи соединения, `ORDER BY` и оконных функций.
- `VARIANT_TYPE` возвращает одно имя типа, например `object`, вместо отображения путей в типы.
- К элементам массивов VARIANT можно обращаться по целочисленным индексам, начиная с 1.

Сведения о Doris 4.x см. в версии этой страницы для 4.x.
:::

## Быстрый старт {#quick-start}

```sql
CREATE TABLE events (
    id BIGINT,
    v  VARIANT
)
DUPLICATE KEY(id)
DISTRIBUTED BY HASH(id) BUCKETS 1
PROPERTIES ("replication_num" = "1");

-- INSERT keeps a string literal as a VARIANT string, so parse JSON text explicitly.
INSERT INTO events VALUES
    (1, PARSE_TO_VARIANT('{"user": {"id": 42, "name": "alice"}, "tags": ["doris", "sql"], "score": 9.5}')),
    (2, PARSE_TO_VARIANT('{"user": {"id": 7, "name": "bob"}, "score": 3}'));

SELECT id,
       CAST(v['user']['name'] AS STRING) AS name,
       v['tags'][1] AS first_tag
FROM events
WHERE CAST(v['score'] AS DOUBLE) > 5;
```

```text
+------+-------+-----------+
| id   | name  | first_tag |
+------+-------+-----------+
|    1 | alice | doris     |
+------+-------+-----------+
```

- `v['user']['name']` и `v['tags'][1]` возвращают значения `VARIANT`. Индексы массива начинаются с 1.
- Перед сравнением или вычислением приведите значение пути к конкретному типу с помощью CAST.
- Задания загрузки, такие как Stream Load, автоматически разбирают текст JSON. См. [Запись данных](#write-data).

## Определение столбца VARIANT {#define-a-variant-column}

```sql
column_name VARIANT
column_name VARIANT< field_definition [, field_definition ...] >
column_name VARIANT< properties('key' = 'value' [, ...]) >
column_name VARIANT< field_definition [, ...], properties('key' = 'value' [, ...]) >

field_definition:
    [MATCH_NAME | MATCH_NAME_GLOB] 'path_or_pattern' : data_type [COMMENT 'comment']
```

- Список `field_definition` представляет собой [Schema Template](#schema-template). Он закрепляет тип хранения выбранных путей.
- `properties(...)` задаёт свойства хранения на уровне столбца. См. [Свойства столбца](#column-properties).
- Столбец VARIANT может иметь ограничение `NULL` или `NOT NULL`. Единственное допустимое значение по умолчанию — `NULL`.
- Имя столбца VARIANT верхнего уровня не может содержать точку (`.`), даже если оно заключено в обратные кавычки: например, определение `` `v.x` VARIANT `` недопустимо. Это ограничение действует для `CREATE TABLE` и `ALTER TABLE`, но не распространяется на имена полей JSON внутри значения VARIANT.

```sql
CREATE TABLE IF NOT EXISTS example_tbl (
    k BIGINT,
    v VARIANT<
        'id' : INT,             -- path id is stored as INT
        'message*' : STRING,    -- paths matching message* are stored as STRING
        'tags*' : ARRAY<TEXT>,  -- paths matching tags* are stored as ARRAY<TEXT>
        properties('variant_max_subcolumns_count' = '2048')
    > NULL
)
DUPLICATE KEY(k)
DISTRIBUTED BY HASH(k) BUCKETS 1
PROPERTIES ("replication_num" = "1");
```

Где в таблице можно использовать столбец VARIANT:

| Применение | Поддерживается | Примечания |
| --- | --- | --- |
| Столбец значений в таблицах Duplicate Key, Unique Key и Aggregate Key | Да | В таблице Aggregate Key тип агрегации должен быть `REPLACE` или `REPLACE_IF_NOT_NULL`. |
| Ключевой столбец, столбец секционирования или распределения по корзинам | Нет | |
| Вложение в другой тип в схеме таблицы (`ARRAY<VARIANT>`, `MAP`, `STRUCT`) | Нет | Результат запроса всё же может иметь тип `ARRAY<VARIANT>`, например результат `COLLECT_LIST(v)`. |
| Значение по умолчанию | Только `NULL` | `DEFAULT '{}'` и другие значения по умолчанию, отличные от NULL, отклоняются. |

## Запись данных {#write-data}

`INSERT` и `CAST` сохраняют строку как строку VARIANT. `PARSE_TO_VARIANT`, `TRY_PARSE_TO_VARIANT` и задания загрузки, такие как Stream Load, разбирают текст JSON. Примеры см. в разделе [Загрузка данных VARIANT](../../../../data-operate/import/complex-types/variant.md).

### Ошибки разбора {#parse-errors}

[PARSE_TO_VARIANT](../../../sql-functions/scalar-functions/variant-functions/parse-to-variant.md), [TRY_PARSE_TO_VARIANT](../../../sql-functions/scalar-functions/variant-functions/try-parse-to-variant.md) и задания загрузки используют один и тот же парсер JSON. Задания загрузки обрабатывают ошибки так же, как `TRY_PARSE_TO_VARIANT`:

| Входные данные | `PARSE_TO_VARIANT` | `TRY_PARSE_TO_VARIANT` и задания загрузки |
| --- | --- | --- |
| Корректный JSON | Разобранное значение | Разобранное значение |
| Текст, не являющийся корректным JSON, например `hello` или `{"id":` | Сохраняется как строка VARIANT | Сохраняется как строка VARIANT |
| JSON с целым числом вне диапазона [-2^63, 2^64 - 1] или числом вне диапазона `DOUBLE`, например `{"a": 1, "n": 100000000000000000000}` | Весь текст сохраняется как строка VARIANT, поэтому `v['a']` возвращает `NULL` | Весь текст сохраняется как строка VARIANT |
| Пустая строка | Пустой объект `{}` | Пустой объект `{}` |
| Вложенность глубже 128 уровней | Ошибка | SQL `NULL` |
| Ключ объекта длиннее `variant_max_json_key_length` байт (настройка BE, по умолчанию 255) | Ошибка | SQL `NULL` |
| Повторяющиеся ключи в одном объекте | Ошибка | SQL `NULL` |
| Строка, не являющаяся корректной UTF-8 | Ошибка | SQL `NULL` |

Документ с настолько глубокой вложенностью, что сам парсер JSON его отклоняет (около 1,000 уровней), считается некорректным JSON и поэтому сохраняется как строка.

Эти правила изменяют две настройки BE:

- `variant_throw_exeception_on_invalid_json` (по умолчанию `false`): при значении `true` текст, отклонённый парсером, включая JSON с числами вне диапазона, вызывает ошибку в `PARSE_TO_VARIANT` и даёт SQL `NULL` в `TRY_PARSE_TO_VARIANT` и заданиях загрузки вместо строки VARIANT.
- `variant_enable_duplicate_json_path_check` (по умолчанию `false`): при значении `true` повторяющийся ключ объекта сохраняет первое значение вместо вызова ошибки. Запись также не завершается ошибкой, если ключ с точкой повторяет вложенный путь; сохраняется только одно из значений.

Чтобы сохранить структуру документа с целыми числами вне диапазона, преобразуйте его через JSON: `CAST(CAST(text AS JSON) AS VARIANT)`. Целые числа длиной до 38 цифр остаются точными числами, более длинные целые числа в диапазоне `LARGEINT` становятся строками, а ещё более длинные — значениями `DOUBLE`. `PARSE_TO_VARIANT(CAST(text AS JSON))` не помогает, поскольку повторно разбирает текст JSON.

```sql
SELECT VARIANT_TYPE(PARSE_TO_VARIANT('{"id": 1}')) AS valid_json,    -- object
       VARIANT_TYPE(PARSE_TO_VARIANT('{"id":'))    AS invalid_json,  -- string
       VARIANT_TYPE(CAST('{"id": 1}' AS VARIANT))  AS string_cast;   -- string
```

### Что сохраняется при записи {#what-storage-keeps}

При записи в таблицу значение нормализуется. Прочитанное значение может отличаться от вычисленного до записи:

| До записи | После чтения из таблицы |
| --- | --- |
| Элемент объекта со значением JSON `null`, например `{"a": null, "b": 1}` | Элемент удаляется: `{"b":1}`. `v['a']` возвращает SQL `NULL`. |
| Элемент объекта со значением в виде пустого объекта или массива либо объекта, который становится пустым по этим правилам, например `{"a": {}, "b": [], "c": {"d": null}}` | Удаляется: `{}` |
| Элемент объекта со значением в виде массива, содержащего только `null`, например `{"p": [null, null], "q": 1}` | Может быть удалён: `{"q":1}` |
| Значения внутри массивов, например `{"arr": [{"a": null}, {}, [], null]}` | Сохраняются без изменений. `v['arr'][1]['a']` — это VARIANT `null`. |
| Корневое значение JSON `null`, например `PARSE_TO_VARIANT('null')` | Пустой объект `{}` |
| Корневой пустой массив `[]` или пустой объект `{}` | Сохраняется |
| Значения `DATE` и `DATETIME` в корневом значении, например `CAST(date_col AS VARIANT)`, или на пути, который также содержит значения других типов | Сохраняются как текст и при чтении становятся строками. На пути объекта, содержащем только даты, они сохраняют свой тип. |
| Логические значения и числа на одном пути | Логические значения могут читаться как `1` или `0` в зависимости от порядка значений при одной записи и от уплотнения |
| Ключ с точкой, например `{"a.b": 1}` | Сохраняется как вложенный путь: `{"a":{"b":1}}`. И `v['a.b']`, и `v['a']['b']` возвращают `1`. Если документ содержит и ключ `a.b`, и ключ `b` внутри `a`, вся операция INSERT или задание загрузки завершается ошибкой, если только `variant_enable_duplicate_json_path_check` не имеет значение `true`. |
| Ключи объекта | Возвращаются в порядке байтов |

Эти правила зависят от других строк, записываемых вместе, и от режима DOC, поэтому не рассчитывайте на сохранение значений `null` или пустых контейнеров после записи. Пути, объявленные в Schema Template, вместо этого преобразуются к объявленному типу; см. [Schema Template](#schema-template).

## Определение типов и конфликты типов {#type-inference-and-type-conflicts}

Без Schema Template Doris определяет тип каждого значения при разборе JSON. `VARIANT_TYPE` возвращает этот тип:

| Значение JSON | Тип |
| --- | --- |
| Целое число в диапазоне `BIGINT` | `tinyint`, `smallint`, `int` или `bigint` — наименьший подходящий тип |
| Целое число больше диапазона `BIGINT`, до 18446744073709551615 | `decimal` |
| Число с дробной частью или показателем степени | `double` |
| Целое число вне диапазона [-2^63, 2^64 - 1] или число вне диапазона `DOUBLE` | Не считается числом: весь текст является некорректным JSON (см. [Ошибки разбора](#parse-errors)) |
| Строка | `string` |
| `true`, `false` | `bool` |
| `null` | `null` |
| Массив, объект | `array`, `object` |

При хранении каждому пути назначается один тип:

- Целые числа сохраняются как `BIGINT` или, при необходимости, как `LARGEINT`. Числа с плавающей точкой сохраняются как `DOUBLE`, десятичные числа — как `DECIMAL`, строки — как `STRING`, логические значения — как `BOOLEAN`, а массивы скалярных значений — как `ARRAY<T>`.
- Массивы объектов, вложенные массивы и пути со значениями разных типов, например целыми числами и числами с плавающей точкой, числами и строками либо скалярными значениями и массивами, сохраняются как `JSONB` (в `DESC` отображается как `json`). Массивы с конфликтующими типами элементов становятся `ARRAY<JSONB>`.

```sql
{"a" : 12345678}
{"a" : "HelloWorld"}
-- a is stored as JSONB
```

Путь `JSONB` сохраняет все значения, но теряет типизированное хранение: индексы и отсечение по типам больше не применяются к этому пути. Логические значения — особый случай: если первое значение пути является логическим, а последующие — числами, путь может сохраняться как числовой, и логические значения при чтении станут `1` или `0`. Если для пути нужен стабильный тип, объявите его в Schema Template.

`VARIANT_TYPE` сообщает тип каждого значения, поэтому целое число, прочитанное из пути `BIGINT`, всё ещё может иметь тип `tinyint`. Чтобы увидеть тип хранения каждого пути, выполните `SET describe_extend_variant_column = true;`, а затем `DESC table_name;`. См. [Просмотр подстолбцов и типов](#inspect-subcolumns-and-types).

## Доступ к путям и вывод {#access-paths-and-output}

- `v['key']` и `v['a']['b']` читают элементы объекта. `v['arr'][1]` читает элемент массива: индексы начинаются с 1, а `-1` обозначает последний элемент. [ELEMENT_AT](../../../sql-functions/scalar-functions/variant-functions/element-at.md) работает аналогично.
- Результат имеет тип `VARIANT`. Отсутствующий ключ, индекс `0`, индекс вне диапазона, строковый ключ для массива, целочисленный индекс для объекта и ключ для скалярного значения возвращают SQL `NULL`.
- В вычисленном значении ключ с точкой считается единым ключом: `v['a.b']` читает ключ `a.b`, а `v['a']['b']` — ключ `b` внутри `a`. При хранении это различие теряется; см. [Что сохраняется при записи](#what-storage-keeps).
- Путь не применяется автоматически к элементам массива. Для `{"a": [{"b": 1}]}` выражение `v['a']['b']` возвращает `NULL`; используйте `v['a'][1]['b']`.

```sql
SELECT v['user']['id']      AS id,       -- 42
       v['tags'][-1]        AS last_tag, -- sql
       v['user']['missing'] AS missing   -- NULL
FROM events
WHERE id = 1;
```

Обычно значение пути приводят с помощью CAST к типу, необходимому запросу:

```sql
SELECT * FROM tbl WHERE ARRAY_CONTAINS(CAST(v['tags'] AS ARRAY<TEXT>), 'Doris');
SELECT * FROM tbl WHERE CAST(v['date'] AS DATE) = '2021-01-02';
SELECT * FROM tbl WHERE v['bool'];                -- implicit CAST to BOOLEAN
SELECT * FROM tbl WHERE v['str'] MATCH 'Doris';   -- uses an inverted index on the path
```

Чтение целого значения VARIANT возвращает текст JSON. Ключи объекта выводятся в порядке байтов и без пробелов, поэтому текст не совпадает с исходным побайтно. Корневая строка возвращается без кавычек.

```sql
CREATE TABLE variant_tbl (k INT, v VARIANT)
DUPLICATE KEY(k)
DISTRIBUTED BY HASH(k) BUCKETS 1
PROPERTIES ("replication_num" = "1");

INSERT INTO variant_tbl VALUES (1, PARSE_TO_VARIANT('{ "b": 2, "a": 1, "c": { "y": 20, "x": 10 } }'));

SELECT v FROM variant_tbl WHERE k = 1;
-- {"a":1,"b":2,"c":{"x":10,"y":20}}
```

## CAST {#cast}

### Приведение к VARIANT {#cast-to-variant}

| Исходный тип | Результат |
| --- | --- |
| `CHAR`, `VARCHAR`, `STRING` | Строка VARIANT. Текст JSON не разбирается. Строка должна быть корректной UTF-8, иначе CAST завершается ошибкой. |
| `BOOLEAN` | Логическое значение. |
| `TINYINT`, `SMALLINT`, `INT`, `BIGINT` | Целое число. |
| `LARGEINT` | Десятичное число. Значение, модуль которого превышает 10^38 - 1, становится строкой. |
| `FLOAT`, `DOUBLE` | Число с плавающей точкой. |
| `DECIMALV2`, `DECIMAL(p, s)` при `p <= 38` | Десятичное число. |
| `DATE`, `DATETIME(p)`, `TIMESTAMP_NS` | Дата или временная метка без часового пояса. |
| `IPV4`, `IPV6` | Строка с текстовым представлением значения. |
| `JSON` / `JSONB` | Та же структура. CAST завершается ошибкой, если значение невозможно представить в VARIANT, например число `DECIMAL256`, или если объект содержит повторяющиеся ключи. |
| `ARRAY<T>` | Массив с преобразованием каждого элемента. `T` должен быть `VARIANT` или одним из типов в этой таблице. |
| `MAP`, `STRUCT`, `TIME`, `TIMESTAMPTZ`, `VARBINARY` и другие типы | Не поддерживаются. Оператор завершается ошибкой. |

Исходное значение также должно быть допустимым для своего типа; недопустимое значение отклоняется, а не исправляется. CAST никогда не разбирает строку: `CAST('{"id": 1}' AS VARIANT)` даёт строку `{"id": 1}`. Для разбора текста JSON используйте `PARSE_TO_VARIANT`.

### Приведение из VARIANT {#cast-from-variant}

| Целевой тип | Результат |
| --- | --- |
| `BOOLEAN` | Логические значения сохраняются. Ненулевые числа становятся `true`. Строки преобразуются по правилам `CAST(string AS BOOLEAN)`. |
| `TINYINT`, `SMALLINT`, `INT`, `BIGINT`, `LARGEINT` | Целые числа. Дробная часть десятичного числа или числа с плавающей точкой отбрасывается (`1.5` становится `1`). Логические значения становятся `1` или `0`. Числовые строки, такие как `"123"`, преобразуются. |
| `FLOAT`, `DOUBLE`, `DECIMAL(p, s)` | Числа и числовые строки. `DECIMAL` округляет до масштаба `s`. Значение, слишком большое для `FLOAT`, становится `Infinity`. |
| `DATE`, `DATETIME(p)`, `TIMESTAMP_NS` | Значения даты и времени, строки в формате даты или времени и числа, такие как `20240102`. |
| `TIMESTAMPTZ(p)` | Значения даты и времени и строки в формате даты или времени. |
| `IPV4`, `IPV6` | Строки в формате IP-адреса. |
| `CHAR`, `VARCHAR`, `STRING` | Корневая строка возвращается без изменений и без кавычек. Объекты и массивы возвращаются как текст JSON. Другие скалярные значения форматируются как значения соответствующего типа SQL: корневое логическое значение становится `1` или `0`, значение `DATETIME` имеет шесть знаков после запятой, а значение `TIMESTAMP_NS` — девять. VARIANT `null` становится строкой `null`. |
| `JSON` / `JSONB` | Та же структура. Значения без аналога в JSON, например даты и временные метки, становятся строками JSON; временная метка с часовым поясом форматируется в часовом поясе сеанса. |
| `ARRAY<T>` | Массив с поэлементным преобразованием; элемент, который нельзя преобразовать, становится `NULL`. Строка, содержащая массив JSON, например `"[1, 2]"`, также преобразуется. Другие значения возвращают `NULL`. |
| `MAP`, `STRUCT`, `TIME` и другие типы | Не поддерживаются. Оператор завершается ошибкой. |

Значение, которое нельзя преобразовать к целевому типу, возвращает SQL `NULL`, даже если включён `enable_strict_cast`. Исключение составляют случаи, когда преобразования между типом значения и целевым типом вообще нет, например для числа и `TIMESTAMPTZ`, `IPV4` или `IPV6`, либо для даты или временной метки и `BOOLEAN`: тогда оператор завершается ошибкой.

```sql
SELECT CAST(PARSE_TO_VARIANT('"123"') AS INT)      AS from_string,   -- 123
       CAST(PARSE_TO_VARIANT('"abc"') AS INT)      AS not_a_number,  -- NULL
       CAST(PARSE_TO_VARIANT('1.5') AS INT)        AS truncated,     -- 1
       CAST(PARSE_TO_VARIANT('300') AS TINYINT)    AS overflow,      -- NULL
       CAST(PARSE_TO_VARIANT('{"a": 1}') AS INT)   AS from_object,   -- NULL
       CAST(PARSE_TO_VARIANT('[1, "2", null, "x"]') AS ARRAY<INT>) AS arr;  -- [1, 2, null, null]

SELECT CAST(PARSE_TO_VARIANT('true') AS STRING)        AS bool_root,     -- 1
       CAST(PARSE_TO_VARIANT('{"b": true}') AS STRING) AS object_text,   -- {"b":true}
       CAST(PARSE_TO_VARIANT('"abc"') AS STRING)       AS string_root,   -- abc
       CAST(PARSE_TO_VARIANT('null') AS STRING)        AS variant_null;  -- null
```

### Десятичные значения, даты и время {#decimal-and-datetime-values}

При преобразовании этих типов в VARIANT:

| Тип Doris | Поведение |
| --- | --- |
| Устаревший `DECIMALV2` | Точно сохраняются значения с точностью до 27 и масштабом до 9. |
| `DECIMAL(p, s)` | Точно сохраняются значения при `1 <= p <= 38` и `0 <= s <= p`. Десятичные числа с точностью выше 38 не поддерживаются. |
| `DATE` | Календарная дата без времени и часового пояса. |
| `DATETIME(p)` | `0 <= p <= 6`, без корректировки часового пояса. |
| `TIMESTAMP_NS` | Наносекундная точность без корректировки часового пояса; значения должны находиться в диапазоне TIMESTAMP_NS. |
| `TIMESTAMPTZ(p)` | Не поддерживается ни в CAST, ни для пути Schema Template. |
| `TIME` | Не поддерживается. |

## Семантика NULL {#null-semantics}

В VARIANT есть два вида null:

- **SQL `NULL`** означает отсутствие значения. Он возникает при значении столбца `NULL`, отсутствии пути, например `v['no_such_key']`, или неудачном CAST.
- **VARIANT `null`** — это значение: литерал JSON `null`, например `PARSE_TO_VARIANT('null')` или элемент массива `null`. Для него `VARIANT_TYPE` возвращает `null`.

| Операция | SQL `NULL` | VARIANT `null` |
| --- | --- | --- |
| `v IS NULL` | `true` | `false` |
| `COALESCE(v, x)`, `IFNULL(v, x)`, где `x` имеет тип VARIANT | Возвращает `x` | Возвращает VARIANT `null` |
| `COUNT(v)` | Не учитывается | Учитывается |
| `GROUP BY v`, `DISTINCT` | Все значения SQL `NULL` образуют одну группу | Все значения VARIANT `null` образуют другую группу |
| `v = x`, соединение по равенству | Совпадений нет | Совпадает с другим VARIANT `null` |
| `ORDER BY v` | Позиция определяется `NULLS FIRST` или `NULLS LAST` | При сортировке по возрастанию стоит перед всеми остальными значениями, отличными от NULL |
| `CAST(v AS STRING)` | SQL `NULL` | Строка `null` |

После записи значения элемент объекта со значением `null` вне массивов удаляется, поэтому его чтение возвращает SQL `NULL`, а корневой `null` читается как `{}` (см. [Что сохраняется при записи](#what-storage-keeps)). Следовательно, в сохранённых данных `v['a'] IS NULL` не позволяет отличить отсутствующий элемент от элемента со значением `null`.

## Сравнение, группировка и сортировка {#comparison-grouping-and-ordering}

Значения VARIANT сравниваются по логическому значению, а не по тексту или физическому представлению. Проверка равенства, хеширование (`GROUP BY`, `DISTINCT`, соединения) и сортировка (`ORDER BY`, ключи оконных функций) используют одни правила, поэтому равные значения всегда попадают в одну группу и занимают одинаковую позицию при сортировке.

### Поддерживаемые операции {#supported-operations}

| Операция над значениями VARIANT | Поддержка | Примечания |
| --- | --- | --- |
| `=`, `!=`, `<=>` между двумя значениями VARIANT или со значением литерала `NULL` | Поддерживается | Включая подпути, например `v['a'] = w['a']`. |
| Соединение по равенству, полусоединение и антисоединение, подзапросы `IN` и `NOT IN` | Поддерживается | Для ключей соединения VARIANT фильтры времени выполнения не создаются. |
| `GROUP BY`, `DISTINCT`, `COUNT(DISTINCT ...)`, `UNION`, `INTERSECT`, `EXCEPT` | Поддерживается | |
| `ORDER BY`, `ORDER BY ... LIMIT` | Поддерживается | |
| Оконные `PARTITION BY` и `ORDER BY` | Поддерживается | |
| `COUNT(v)`, `COLLECT_LIST(v)`, `ARRAY_AGG(v)` | Поддерживается | |
| `IF`, `CASE`, `IFNULL`, `COALESCE` | Поддерживается | При сочетании VARIANT с другим типом значения VARIANT преобразуются к этому типу (`DECIMAL(38, 9)`, если другой тип — целочисленный); значения, которые нельзя преобразовать, становятся `NULL`. |
| `CAST(v AS ARRAY<VARIANT>)`, `EXPLODE_VARIANT_ARRAY`, `EXPLODE` и `EXPLODE_OUTER` для `ARRAY<VARIANT>` | Поддерживается | |
| `<`, `<=`, `>`, `>=`, `BETWEEN` между значениями VARIANT | Не поддерживается | Сначала приведите к конкретному типу с помощью CAST. |
| Сравнение целого значения VARIANT со значением другого типа, например `v = 1` | Не поддерживается | Подпуть преобразуется неявно: `v['a'] = 1` работает. |
| Список `IN`, содержащий значения VARIANT, например `v IN (PARSE_TO_VARIANT('1'))` | Не поддерживается | `v IN ('a', 'b')` со значениями других типов работает за счёт неявного преобразования. |
| `MIN`, `MAX` | Не поддерживается | Сначала примените CAST к подпути. |
| `ARRAY(...)`, `MAP(...)`, `NAMED_STRUCT(...)` с аргументами VARIANT | Не поддерживается | |

### Равенство {#equality}

- **Числа.** Целое число, десятичное число с нулевой дробной частью и число с плавающей точкой, имеющее целочисленное значение, равны: `1`, `1.0` и `1.00` — одно значение. Конечные нули десятичного числа не имеют значения, а `-0.0` равно `0`. Десятичное число и число с плавающей точкой, имеющие ненулевую дробную часть, никогда не равны: `DECIMAL 1.5` не равно `DOUBLE 1.5`. Числа JSON с дробной частью разбираются как `DOUBLE`; десятичные числа поступают из CAST, путей Schema Template и целых чисел, превышающих диапазон `BIGINT`.
- **Значения разных видов никогда не равны.** Число `1`, строка `"1"` и `true` — три разных значения. `DATE` не равно строке `"2024-01-01"`, а временная метка без часового пояса не равна временной метке с часовым поясом.
- **Строки** равны только при совпадении байтов. Сравнение учитывает регистр.
- **Объекты** равны, если у них одинаковые ключи с равными значениями. Порядок ключей не важен.
- **Массивы** равны, если у них одинаковая длина и равные элементы в одинаковом порядке.
- VARIANT `null` равно другому VARIANT `null`. SQL `NULL` подчиняется правилам SQL.

```sql
SELECT PARSE_TO_VARIANT('1') = PARSE_TO_VARIANT('1.0')                             AS int_double,  -- 1
       PARSE_TO_VARIANT('1.5') = CAST(CAST(1.5 AS DECIMAL(10, 2)) AS VARIANT)       AS dbl_dec,     -- 0
       PARSE_TO_VARIANT('1') = PARSE_TO_VARIANT('"1"')                             AS num_str,     -- 0
       PARSE_TO_VARIANT('{"a": 1, "b": 2}') = PARSE_TO_VARIANT('{"b": 2, "a": 1}') AS obj,         -- 1
       PARSE_TO_VARIANT('[1, 2]') = PARSE_TO_VARIANT('[2, 1]')                     AS arr;         -- 0
```

### Порядок сортировки {#ordering}

`ORDER BY` для значений VARIANT использует единый полный порядок. Значения разных видов сначала упорядочиваются по виду:

```text
null < boolean < number < string < binary < date < timestamp with time zone
     < timestamp without time zone < time < UUID < object < array
```

Значения binary, time и UUID нельзя получить в Doris путём разбора JSON или CAST; они могут поступать только из данных VARIANT, записанных другими системами, например из файлов Parquet со столбцами VARIANT.

В пределах одного вида:

- **Логические значения:** `false` перед `true`.
- **Числа:** целые (`INT`, `BIGINT` и т. д.), десятичные (`DECIMAL`) и числа с плавающей точкой (`FLOAT`, `DOUBLE`) сортируются по числовому значению. `INT 1`, `FLOAT/DOUBLE 1.0` и `DECIMAL 1.00` равны и занимают одну позицию при сортировке; конечные нули десятичного числа не влияют на порядок. При одинаковом значении с ненулевой дробной частью десятичное число идёт первым: `DECIMAL 1.5` предшествует `FLOAT/DOUBLE 1.5`, и как значения VARIANT они не равны. Точность чисел с плавающей точкой может влиять на порядок: `DOUBLE 0.1` немного больше `DECIMAL 0.1`. Отрицательная бесконечность идёт первой; положительная бесконечность и затем NaN — последними.
- **Строки:** по байтам UTF-8. Заглавные буквы идут перед строчными, а `"10"` — перед `"9"`.
- **Даты и временные метки:** в хронологическом порядке. Любая дата идёт перед любой временной меткой.
- **Объекты:** по элементам в порядке ключей: сначала сравниваются наименьшие ключи, затем их значения, затем следующие ключи. Объект, элементы которого образуют префикс другого, идёт первым, поэтому `{"a":1}` < `{"a":1,"b":2}` < `{"b":0}`.
- **Массивы:** по элементам; префикс идёт первым, поэтому `[]` < `[null]` < `[1]` < `[1,2]`.

Позиция SQL `NULL` задаётся через `NULLS FIRST` или `NULLS LAST`.

```sql
SELECT v, VARIANT_TYPE(v) AS type
FROM (
    SELECT PARSE_TO_VARIANT('[1, 2]') AS v UNION ALL
    SELECT PARSE_TO_VARIANT('{"a": 1}')    UNION ALL
    SELECT PARSE_TO_VARIANT('"9"')         UNION ALL
    SELECT PARSE_TO_VARIANT('"10"')        UNION ALL
    SELECT PARSE_TO_VARIANT('10')          UNION ALL
    SELECT PARSE_TO_VARIANT('9.5')         UNION ALL
    SELECT PARSE_TO_VARIANT('true')        UNION ALL
    SELECT PARSE_TO_VARIANT('null')        UNION ALL
    SELECT NULL
) t
ORDER BY v;
```

```text
+---------+---------+
| v       | type    |
+---------+---------+
| NULL    | NULL    |
| null    | null    |
| true    | bool    |
| 9.5     | double  |
| 10      | tinyint |
| 10      | string  |
| 9       | string  |
| {"a":1} | object  |
| [1,2]   | array   |
+---------+---------+
```

### Сравнение по конкретному типу и по правилам VARIANT {#typed-comparison-and-variant-comparison}

Операнды определяют, какие правила применяются: VARIANT или конкретного типа. Пусть путь `a` содержит значения `1`, `1.0` и `"1"`:

| Выражение | Тип сравнения | Результат |
| --- | --- | --- |
| `v['a'] = 1` | `DECIMAL(38, 9)` после неявного CAST для `v['a']` | Совпадают все три значения |
| `v['a'] = CAST(1 AS VARIANT)`, `v['a'] = w['a']` | VARIANT | Совпадают `1` и `1.0`, но не `"1"` |
| `GROUP BY v['a']` | VARIANT | `1` и `1.0` образуют одну группу, `"1"` — другую |
| `GROUP BY CAST(v['a'] AS STRING)` | `STRING` | Одна группа, `1` |
| `ORDER BY v['a']` | VARIANT | Сначала числа, затем строки |
| `ORDER BY CAST(v['a'] AS INT)` | `INT` | Числовой порядок; значения, которые нельзя преобразовать, становятся `NULL` |

### Примечания {#notes}

- **Стоимость.** Ключи VARIANT хешируются и сравниваются по логическому значению. В тесте на 44 миллионах строк `GROUP BY`, сортировка и соединения по ключу VARIANT занимали в 1.2–3.7 раза больше времени, чем те же операции над `CAST(v['path'] AS <type>)`. Если путь имеет один известный тип, применяйте CAST.
- **Результаты зависят от сохранённых значений.** Нормализация, описанная в разделе [Что сохраняется при записи](#what-storage-keeps), происходит до сравнения: элемент со значением `null` уже отсутствует, корневое значение `DATE` сравнивается как строка, а логические значения на одном пути с числами могут читаться как `1` или `0`. Пути, для которых важен тип, объявляйте в Schema Template.
- **Смешанные типы сортируются по виду, а не по значению.** Если путь содержит числа и числовые строки, `ORDER BY v['a']` помещает все числа перед всеми строками и упорядочивает строки по байтам. Для числового или лексикографического порядка приведите значения к одному типу.
- **Одинаково выглядящие значения могут различаться.** В результате `GROUP BY` число `1` и строка `"1"` отображаются одинаково, но образуют две группы. Используйте `VARIANT_TYPE`, чтобы увидеть разницу.
- Порядок между видами значений определён Doris для получения детерминированных результатов. Он не является частью стандарта JSON и может отличаться в других системах.
- Внутренний хеш значения VARIANT — деталь реализации, а не стабильная контрольная сумма для пользователей.

## Schema Template {#schema-template}

Schema Template объявляет тип хранения выбранных путей. Объявляйте только ключевые пути, которым нужен стабильный тип или индекс для конкретного пути; остальная часть документа остаётся динамической.

```sql
CREATE TABLE test_var_schema (
    id BIGINT NOT NULL,
    v1 VARIANT<
        'large_int_val': LARGEINT,
        'string_val': STRING,
        'decimal_val': DECIMAL(38, 9),
        'datetime_val': DATETIME,
        'ip_val': IPV4
    > NULL
)
PROPERTIES ("replication_num" = "1");
```

Для поля шаблона доступны следующие типы:

- Числа: `TINYINT`, `SMALLINT`, `INT`, `BIGINT`, `LARGEINT`, `FLOAT`, `DOUBLE` и `DECIMAL(p, s)` при `p <= 38`
- `STRING` (или `TEXT`)
- `BOOLEAN`
- `DATE`, `DATETIME(p)`, `TIMESTAMP_NS`
- `IPV4`, `IPV6`
- `ARRAY<T>`, где `T` — один из перечисленных выше типов (только одно измерение)

### Запись в пути шаблона {#writing-to-template-paths}

Для объявленного пути каждое значение преобразуется к указанному типу по правилам нестрогого CAST. Значение, которое нельзя преобразовать, сохраняется как `NULL`, поэтому при чтении путь отсутствует; остальная часть строки всё равно записывается. Преобразование может изменить значение:

```sql
CREATE TABLE tpl_demo (
    k INT,
    v VARIANT<'id': INT, 'price': DECIMAL(10, 2), 'ts': DATETIME(3)>
)
DUPLICATE KEY(k)
DISTRIBUTED BY HASH(k) BUCKETS 1
PROPERTIES ("replication_num" = "1");

INSERT INTO tpl_demo VALUES
    (1, PARSE_TO_VARIANT('{"id": "123", "price": 9.999, "ts": "2024-01-01 10:00:00.123456"}')),
    (2, PARSE_TO_VARIANT('{"id": "abc", "price": "x", "ts": "not a time"}')),
    (3, PARSE_TO_VARIANT('{"id": 1.7}'));

SELECT k, v FROM tpl_demo ORDER BY k;
```

```text
+------+------------------------------------------------------------+
| k    | v                                                          |
+------+------------------------------------------------------------+
|    1 | {"id":123,"price":10.00,"ts":"2024-01-01 10:00:00.123000"} |
|    2 | {}                                                         |
|    3 | {"id":1}                                                   |
+------+------------------------------------------------------------+
```

- `"123"` становится `123`, у `1.7` отбрасывается дробная часть и получается `1`, `9.999` округляется до `10.00`, а временная метка сохраняет объявленную точность (миллисекунды); её текстовое представление всегда содержит шесть знаков после запятой.
- `"abc"`, `"x"` и `"not a time"` нельзя преобразовать, поэтому они удаляются.
- Число JSON с дробной частью до преобразования разбирается как `DOUBLE`, поэтому путь `DECIMAL` может потерять точность. Чтобы сохранить все цифры, записывайте такие значения как строки JSON (см. [Частые вопросы](#faq)).
- Даты и IP-адреса должны быть строками JSON: `{"date": 2020-01-01}` и `{"ip": 127.0.0.1}` не являются корректным JSON; записывайте `{"date": "2020-01-01"}` и `{"ip": "127.0.0.1"}`.

:::caution
Значение преобразуется только тогда, когда для его типа JSON существует преобразование к объявленному типу. Число JSON на пути `IPV4` или `IPV6` приводит к ошибке всей операции записи. Если одна операция записи смешивает строки JSON и числа на пути `DATE`, `DATETIME`, `IPV4` или `IPV6`, даже корректные значения этого пути могут быть отброшены. Записывайте значения таких путей как строки JSON.
:::

### Чтение путей шаблона {#reading-template-paths}

`v['path']` сохраняет тип `VARIANT` даже для объявленного пути; Doris не приводит его к объявленному типу автоматически. Явно применяйте CAST, когда нужен объявленный тип, и приводите значение к нему в фильтрах, чтобы запрос мог использовать карты зон и индексы этого пути:

```sql
SELECT CAST(v['ts'] AS DATETIME(3)) AS ts,       -- 2024-01-01 10:00:00.123
       CAST(v['ts'] AS STRING)      AS ts_text,  -- 2024-01-01 10:00:00.123000
       VARIANT_TYPE(v['price'])     AS type      -- decimal
FROM tpl_demo
WHERE CAST(v['id'] AS INT) = 123;
```

Schema Template определяет только способ хранения значений. Тот же JSON, вычисленный в запросе, сохраняет тип, полученный при разборе:

```sql
SELECT VARIANT_TYPE(PARSE_TO_VARIANT('{"price": 9.999}')['price']);  -- double
```

### Сопоставление с шаблоном {#pattern-matching}

По умолчанию имя поля является glob-шаблоном (`MATCH_NAME_GLOB`): `*` соответствует любой последовательности символов, включая `.` между вложенными ключами, а `?` — одному символу. Например, `'m*'` соответствует и `m1`, и `m2.x`. Если путь соответствует нескольким полям, используется первое по порядку определения:

```sql
CREATE TABLE test_var_pattern (
    id BIGINT NOT NULL,
    v1 VARIANT<
        'enumString*' : STRING,
        'enum*' : ARRAY<TEXT>,
        'ip*' : IPV6
    > NULL
)
PROPERTIES ("replication_num" = "1");

-- enumString1 matches both enumString* and enum*; the first one (STRING) is used.
```

Чтобы сопоставить имя, содержащее буквальный символ `*`, используйте `MATCH_NAME`:

```sql
v1 VARIANT<
    MATCH_NAME 'enumString*' : STRING
> NULL
```

Пути, соответствующие шаблону, всегда проходят Subcolumnization и не учитываются в `variant_max_subcolumns_count`, поэтому избегайте шаблонов, которым соответствует большое число путей.

После создания столбца изменить Schema Template нельзя. См. [ALTER TABLE](#alter-table).

## ALTER TABLE {#alter-table}

Для `ADD COLUMN` (включая пакетное добавление), `MODIFY COLUMN` и `RENAME COLUMN` имя столбца VARIANT верхнего уровня также должно быть без точек. Например, следующий оператор отклоняется:

```sql
ALTER TABLE example_tbl ADD COLUMN `v.x` VARIANT;
-- ERROR: Cannot use `VARIANT` type column named with a `.` character: v.x
```

`ALTER TABLE` поддерживает:

- `ADD COLUMN` для допускающего NULL столбца VARIANT, со Schema Template и свойствами или без них.
- `DROP COLUMN`, `RENAME COLUMN` и `MODIFY COLUMN ... COMMENT '...'`.
- `ADD INDEX` и `DROP INDEX`. Индекс с `field_pattern` можно определить только в `CREATE TABLE`.
- Для столбца без Schema Template: изменение `NOT NULL` на `NULL` и изменение `variant_doc_materialization_min_rows` (у столбца, созданного до версии 4.2 без режима DOC и с `variant_max_subcolumns_count = 0`, значение может оставаться только `0`). Для `MODIFY COLUMN` требуется полное определение столбца; пропущенное свойство получает значение по умолчанию (см. [Свойства столбца](#column-properties)), поэтому повторно указывайте каждое свойство, значение которого отличается от значения по умолчанию.

Не поддерживаются:

- `ADD COLUMN ... VARIANT NOT NULL`: столбцу `NOT NULL`, добавляемому через `ALTER`, требуется значение по умолчанию, а VARIANT допускает только `DEFAULT NULL`. Определяйте столбцы VARIANT с `NOT NULL` в `CREATE TABLE`.
- Добавление Schema Template к существующему столбцу. Для столбца со Schema Template через `MODIFY COLUMN` можно изменить только комментарий; любое другое изменение завершается ошибкой, даже если повторно указан тот же шаблон.
- Изменение свойств, кроме `variant_doc_materialization_min_rows`, изменение `NULL` на `NOT NULL` и преобразование между VARIANT и другими типами.
- `BUILD INDEX` для столбца VARIANT.

Для таких изменений создайте таблицу с новым определением и скопируйте данные через `INSERT INTO ... SELECT`; если исходный столбец имеет тип `STRING`, оберните его в `PARSE_TO_VARIANT`.

```sql
ALTER TABLE t ADD COLUMN v2 VARIANT NOT NULL;
-- ERROR: Field 'v2' doesn't have a default value

-- v is a VARIANT column without a Schema Template.
ALTER TABLE t MODIFY COLUMN v VARIANT<'id': INT>;
-- ERROR: Can not change variant schema templates
```

## Свойства столбца {#column-properties}

Свойства столбца задаются в `properties(...)` внутри типа VARIANT:

```sql
CREATE TABLE example_table (
  id INT,
  data_variant VARIANT<
      'path_1' : INT,
      'path_2' : STRING,
      properties(
          'variant_max_subcolumns_count' = '2048',
          'variant_doc_hash_shard_count' = '64'
      )
  >
);
```

| Свойство | По умолчанию | ALTER | Описание |
| --- | --- | --- | --- |
| `variant_max_subcolumns_count` | `2048` | Нет | Максимальное число динамических путей, проходящих Subcolumnization в одном файле данных; сначала выбираются пути с большим числом ненулевых значений, остальные сохраняются в разреженных столбцах. `0` означает, что ни один динамический путь не проходит Subcolumnization и все они сохраняются в разреженных столбцах; для столбца, созданного до версии 4.2, `0` по-прежнему означает отсутствие ограничения, см. [Разреженные столбцы](#sparse-columns). Диапазон от 0 до 100000; рекомендуется не превышать 10000. Значения по умолчанию достаточно для большинства нагрузок; если нагрузке действительно нужно гораздо больше подстолбцов, предпочтите [режим DOC](./variant-workload-guide.md#doc-mode-template). |
| `variant_enable_typed_paths_to_sparse` | `false` | Нет | Начиная с версии 4.2 задать нельзя: определение столбца с этим свойством завершается ошибкой даже при значении `false`. Пути Schema Template всегда проходят Subcolumnization и не учитываются в `variant_max_subcolumns_count`. Столбец, для которого до версии 4.2 было задано `true`, сохраняет это поведение: такие пути учитываются в ограничении и могут храниться в разреженных столбцах. До версии 4.2 `SHOW CREATE TABLE` выводит это свойство для каждого столбца VARIANT без режима DOC; перед выполнением такого вывода удалите свойство и замените в нём `variant_sparse_hash_shard_count` на `variant_doc_hash_shard_count`, чтобы сохранить число шардов. |
| `variant_doc_hash_shard_count` | `1` | Нет | Число физических разреженных столбцов, между которыми пути распределяются по хешу; в режиме DOC — число столбцов, на которые делится хранимый документ. Диапазон от 0 до 1024; `0` трактуется как `1`. До версии 4.2 действовало только в режиме DOC. |
| `variant_max_sparse_column_statistics_size` | `10000` | Нет | Максимальное число разреженных путей в одном файле данных, для которых записывается статистика. Если предел превышен, запрос к пути без статистики не может пропустить разреженные столбцы. Диапазон от 1 до 50000. |
| `variant_enable_doc_mode` | `false` | Нет | Включает режим DOC, при котором также сохраняется полный документ. Можно задавать вместе с `variant_max_subcolumns_count`, `variant_doc_materialization_min_rows` и `variant_doc_hash_shard_count`, но не с `variant_max_sparse_column_statistics_size`. |
| `variant_doc_materialization_min_rows` | `0` | Только без Schema Template | Файл данных с меньшим числом строк пропускает Subcolumnization и сохраняет динамические пути в разреженных столбцах (в режиме DOC — только документ); Subcolumnization выполняется, когда при уплотнении создаётся файл данных, достигший порога. `0` означает выполнение Subcolumnization при записи. Диапазон от 0 до 1000000000. До версии 4.2 действовало только в режиме DOC. |

Столбец **ALTER** показывает, можно ли изменить свойство через `ALTER TABLE ... MODIFY COLUMN`; см. [ALTER TABLE](#alter-table). Использование свойств разреженных столбцов и режима DOC описано в разделе [Широкие столбцы](#wide-columns).

### Настройки BE {#be-configuration}

| Настройка | По умолчанию | Описание |
| --- | --- | --- |
| `variant_max_json_key_length` | `255` | Максимальная длина ключа объекта JSON в байтах. Более длинный ключ вызывает ошибку разбора. Диапазон от 1 до 65535. |
| `variant_throw_exeception_on_invalid_json` | `false` | При `false` текст, отклонённый парсером JSON, сохраняется как строка VARIANT. При `true` возникает ошибка разбора. |
| `variant_enable_duplicate_json_path_check` | `false` | При `false` повторяющийся ключ объекта вызывает ошибку разбора. При `true` сохраняется первое значение, а повторения игнорируются. |

Все три настройки можно изменять во время работы. Как сообщается об ошибке разбора, описано в разделе [Ошибки разбора](#parse-errors).

## Индексы Variant {#variant-indexes}

### Выбор индексов {#choosing-indexes}

VARIANT поддерживает BloomFilter и Inverted Index для подпутей.
- Для фильтров по равенству и IN с высокой кардинальностью предпочтителен BloomFilter (более компактный индекс и лучшая производительность записи).
- Для поиска по токенам, фразам и диапазонам используйте Inverted Index с подходящими свойствами `parser`/`analyzer`.
- Для поиска ключевых слов по всему столбцу используйте [индекс значений VARIANT](../../../../table-design/index/inverted-index/variant-values-index.md) в Doris 4.2 или более поздней версии.

Фильтр может использовать индекс или BloomFilter, только если сравнивает значение пути с учётом его типа хранения. Для числовых путей явно применяйте CAST; для сравнения строкового пути со строковым литералом CAST не нужен.

```sql
...
PROPERTIES("replication_num" = "1", "bloom_filter_columns" = "v");

-- Use BloomFilter for equality/IN filters
SELECT * FROM tbl WHERE CAST(v['id'] AS BIGINT) = 12345678;
SELECT * FROM tbl WHERE CAST(v['id'] AS BIGINT) IN (1, 2, 3);
```

При создании обычного инвертированного индекса для столбца VARIANT все подпути наследуют одинаковые свойства индекса (например, парсер):

```sql
CREATE TABLE IF NOT EXISTS tbl (
    k BIGINT,
    v VARIANT,
    INDEX idx_v(v) USING INVERTED PROPERTIES("parser" = "english")
);

-- All subpaths inherit the english parser
SELECT * FROM tbl WHERE v['id_1'] MATCH 'Doris';
SELECT * FROM tbl WHERE v['id_2'] MATCH 'Apache';
```

### Индекс по подпути {#index-by-subpath}

Для отдельных подпутей VARIANT можно задать собственные свойства индекса и даже настроить для одного пути инвертированные индексы с токенизацией и без неё. Для индекса конкретного пути его тип должен быть объявлен через Schema Template.

```sql
-- Common properties: field_pattern (target path), analyzer, parser, support_phrase, norms, etc.
CREATE TABLE IF NOT EXISTS tbl (
    k BIGINT,
    v VARIANT<'content' : STRING>,
    INDEX idx_tokenized(v) USING INVERTED PROPERTIES("parser" = "english", "field_pattern" = "content"),
    INDEX idx_v(v) USING INVERTED PROPERTIES("field_pattern" = "content")
);

-- v.content has both tokenized and non-tokenized inverted indexes
SELECT * FROM tbl WHERE v['content'] MATCH 'Doris';
SELECT * FROM tbl WHERE v['content'] = 'Doris';
```

Индексация путей с подстановочными символами:

```sql
CREATE TABLE IF NOT EXISTS tbl (
    k BIGINT,
    v VARIANT<'pattern_*' : STRING>,
    INDEX idx_tokenized(v) USING INVERTED PROPERTIES("parser" = "english", "field_pattern" = "pattern_*"),
    INDEX idx_v(v) USING INVERTED -- global non-tokenized inverted index
);

SELECT * FROM tbl WHERE v['pattern_1'] MATCH 'Doris';
SELECT * FROM tbl WHERE v['pattern_1'] = 'Doris';
```

Начиная с Doris 4.1.5, нормы можно отключить свойством индекса или настройкой BE, приведёнными ниже.

Токенизированные индексы путей VARIANT по умолчанию записывают нормы BM25: один байт на строку для каждого пути, включая строки, где для этого пути нет значения. Для путей, используемых только в фильтрах, отключите нормы с помощью `"norms" = "false"`. Без `field_pattern` это свойство применяется ко всем подпутям, охваченным индексом:

```sql
CREATE TABLE IF NOT EXISTS tbl (
    k BIGINT,
    v VARIANT<'body_*' : STRING>,
    INDEX idx_body(v) USING INVERTED PROPERTIES("parser" = "english", "field_pattern" = "body_*", "norms" = "false")
);
```

Отключение норм не влияет на фильтрацию `MATCH`, но `score()` возвращает ошибку при чтении сегмента без норм. Настройка BE `inverted_index_skip_norms_for_variant` отключает нормы для всех путей VARIANT. Подробности см. в разделе [Длина записи и свойство norms](../../../../table-design/index/inverted-index/scoring.md#record-length-and-the-norms-property).

### Когда индексы не работают {#when-indexes-dont-work}

1. Изменение типа приводит к потере индекса: если тип подпути меняется на несовместимый (например, INT → JSONB), индекс теряется. Закрепите типы и индексы через Schema Template.
2. Фильтр не сравнивает путь в соответствии с его типом хранения:
   ```sql
   -- An implicit numeric comparison is evaluated row by row and uses no index
   SELECT * FROM tbl WHERE v['id'] = 123456;

   -- CAST to the stored type instead
   SELECT * FROM tbl WHERE CAST(v['id'] AS BIGINT) = 123456;
   ```
   Если `v['id']` хранится как строка, сравнивайте его со строкой: `v['id'] = '123456'`.
3. Неверно настроен индекс: индексы применяются к подпутям, а не ко всему столбцу VARIANT.
   ```sql
   -- VARIANT itself cannot be indexed as a whole
   SELECT * FROM tbl WHERE v MATCH 'Doris';

   -- If whole-JSON search is needed, store a duplicate STRING column and index it
   CREATE TABLE IF NOT EXISTS tbl (
       k BIGINT,
       v VARIANT,
       v_str STRING,
       INDEX idx_v_str(v_str) USING INVERTED PROPERTIES("parser" = "english")
   );
   SELECT * FROM tbl WHERE v_str MATCH 'Doris';
   ```
4. Путь хранится в разреженных столбцах: для индекса подпути нужен подстолбец. У пути сверх `variant_max_subcolumns_count` его нет; при `variant_max_subcolumns_count = 0` его нет ни у одного динамического пути; файл данных с числом строк ниже `variant_doc_materialization_min_rows` также не имеет динамического подстолбца, пока уплотнение не создаст файл данных, достигший порога. Без подстолбца `SEARCH()` завершается ошибкой "SEARCH index unavailable for Variant field", а `MATCH` переходит к построчному сопоставлению значений, если только `enable_match_without_inverted_index = false` не заставляет его завершиться ошибкой. Закрепите путь через Schema Template или см. [Разреженные столбцы](#sparse-columns).

## Широкие столбцы {#wide-columns}

Когда загружаемые данные содержат много различных ключей JSON, число подстолбцов, создаваемых Subcolumnization, может быстро расти; в большом масштабе это приводит к разрастанию метаданных, повышению стоимости записи и слияния и замедлению запросов. Для работы с «широкими столбцами» (избыточным числом подстолбцов) VARIANT предоставляет два механизма: **разреженные столбцы** и **кодирование DOC**.

Рекомендации по выбору для нагрузки см. в [руководстве по нагрузкам VARIANT](./variant-workload-guide.md). Здесь описаны только механизмы и связанные с ними свойства.

При кодировании DOC также действуют `variant_max_subcolumns_count`, `variant_doc_materialization_min_rows` и `variant_doc_hash_shard_count`: извлекается не более `variant_max_subcolumns_count` путей, а остальные читаются из документа; `variant_max_sparse_column_statistics_size` нельзя задавать вместе с кодированием DOC. Рекомендации по значениям для разных сценариев см. в разделе [Хранение и настройка VARIANT](./variant-storage-tuning.md).

### Разреженные столбцы {#sparse-columns}

**Как это работает**

- Система ранжирует пути по доле ненулевых значений и разреженности: часто встречающиеся (менее разреженные) пути проходят Subcolumnization и сохраняются как отдельные подстолбцы; оставшиеся редко встречающиеся (разреженные) пути объединяются и сохраняются в разреженных столбцах. Максимальное число извлекаемых подстолбцов задаёт `variant_max_subcolumns_count`.
- Путь, объявленный в Schema Template, не переносится в разреженные столбцы (кроме столбца, для которого до версии 4.2 было задано `variant_enable_typed_paths_to_sparse = true`).
- `variant_max_subcolumns_count = 0` сохраняет каждый динамический путь в разреженных столбцах, а пути Schema Template по-прежнему проходят Subcolumnization. Используйте этот режим, когда значения преимущественно читаются целиком. Чтобы вместо этого пропустить все динамические пути через Subcolumnization, например ради индексов подпутей, задайте число больше количества различных путей:
  ```sql
  -- every dynamic path in sparse columns
  v VARIANT<properties('variant_max_subcolumns_count' = '0')>

  -- every dynamic path as a subcolumn, as long as the paths fit in the count
  v VARIANT<properties('variant_max_subcolumns_count' = '2048')>
  ```

  Начиная с версии 4.2, это значение применяется ко всем операторам создания таблицы, включая `CREATE TABLE`, `CREATE TABLE LIKE` и `CREATE TABLE AS SELECT`. Столбец, созданный до версии 4.2, сохраняет прежнее поведение: `0` направляет каждый динамический путь в Subcolumnization без ограничения. `SHOW CREATE TABLE` помечает столбец VARIANT комментарием после его типа: `/* variant_serialize_type = v1 */` для столбца, созданного до версии 4.2, и `/* variant_serialize_type = v2 */` для созданного начиная с версии 4.2. Комментарий лишь показывает поведение: при выполнении выведенного определения он игнорируется и создаётся новый столбец.

  ```sql
  -- Version 4.1
  CREATE TABLE old_t (
      k INT,
      v VARIANT<properties('variant_max_subcolumns_count' = '0')>
  )
  DUPLICATE KEY(k) DISTRIBUTED BY HASH(k) BUCKETS 1;
  INSERT INTO old_t VALUES (1, PARSE_TO_VARIANT('{"a": 1, "b": "x"}'));

  -- After upgrading to version 4.2: new_t has the same definition as old_t, with a count of 0
  CREATE TABLE new_t LIKE old_t;
  INSERT INTO new_t SELECT * FROM old_t;

  SET describe_extend_variant_column = true;
  DESC old_t;  -- lists the subcolumns v.a and v.b, because old_t keeps the old meaning
  DESC new_t;  -- lists no subcolumn, because new_t stores a and b in sparse columns
  SHOW CREATE TABLE old_t;  -- the type of v is followed by /* variant_serialize_type = v1 */
  SHOW CREATE TABLE new_t;  -- the type of v is followed by /* variant_serialize_type = v2 */
  ```

  Когда `CREATE TABLE AS SELECT` сохраняет VARIANT, вычисленный запросом, например `PARSE_TO_VARIANT(...)`, `TRY_PARSE_TO_VARIANT(...)` или подпуть `v['a']`, в новом столбце, столбец получает `variant_max_subcolumns_count` из типа выражения: `0` для `PARSE_TO_VARIANT` и `TRY_PARSE_TO_VARIANT`, поэтому все динамические пути сохраняются в разреженных столбцах; для подпути берётся значение исходного столбца. Чтобы получить ограничение по умолчанию, приведите выражение к VARIANT: `CAST(PARSE_TO_VARIANT(s) AS VARIANT)` имеет ограничение `2048`.
- Разреженные столбцы поддерживают распределение по шардам: разнесение разреженных подпутей по нескольким разреженным столбцам уменьшает нагрузку на чтение отдельного столбца и повышает эффективность чтения. Число физически сохраняемых разреженных столбцов задаётся через `variant_doc_hash_shard_count`. В версиях 4.0 и 4.1 число шардов задавалось через `variant_sparse_hash_shard_count`; начиная с версии 4.2 это свойство по-прежнему принимается, но его значение игнорируется.

:::caution Откат версии
После обновления до версии 4.2, если создан новый столбец VARIANT, не откатывайтесь к версии старше 4.2. Новые столбцы сохраняются по правилам версии 4.2, описанным на этой странице: например, более старая версия понимает `0` в новом столбце с `variant_max_subcolumns_count = 0` как отсутствие ограничения, и при её уплотнении пути, сохранённые только в разреженных столбцах, теряются. Следующие операции создают новые столбцы VARIANT:

- `CREATE TABLE` со столбцом VARIANT.
- `CREATE TABLE LIKE` или повторное выполнение вывода `SHOW CREATE TABLE` для таблицы со столбцом VARIANT, в том числе созданным до версии 4.2.
- `CREATE TABLE AS SELECT`, результат которого содержит столбец VARIANT.
- `ALTER TABLE ... ADD COLUMN` для столбца VARIANT, в том числе в таблице, созданной до версии 4.2.
- Асинхронное материализованное представление со столбцом VARIANT.

В выводе `SHOW CREATE TABLE` новый столбец помечен `/* variant_serialize_type = v2 */`.
:::

**Справочные примечания**

- Если доли ненулевых значений у большинства ключей близки (разница в разреженности невелика), трудно выделить действительно разреженные пути и польза разреженных столбцов снижается.
- Значение `variant_max_subcolumns_count` по умолчанию — `2048`, и его уже достаточно для большинства нагрузок. Не увеличивайте его резко лишь ради предварительного выделения большего числа извлекаемых подстолбцов; если нагрузке действительно требуется масштабная Subcolumnization, предпочтите [режим DOC](./variant-workload-guide.md#doc-mode-template). Рекомендуемый практический верхний предел по-прежнему составляет ≤ `10000`.
- `variant_doc_hash_shard_count` можно приблизительно оценить как «число разреженных путей / 128». Например, если всего ключей JSON ≈ 10,000, а `variant_max_subcolumns_count = 2000`, то разреженных путей ≈ 8000, и начальным значением `variant_doc_hash_shard_count` может быть около `8000/128`.

### Кодирование DOC (режим DOC) {#doc-encoding-doc-mode}

**Как это работает**

- Пути по-прежнему могут проходить Subcolumnization для запросов по пути, максимум до `variant_max_subcolumns_count` путей; исходный JSON дополнительно сохраняется как хранимое поле, чтобы эффективно возвращать полный документ JSON.
- Кодирование DOC поддерживает распределение по шардам: исходный JSON делится для хранения между несколькими столбцами и собирается обратно при запросе полного JSON. Число шардов DOC задаётся через `variant_doc_hash_shard_count`.
- При записи небольшими пакетами Subcolumnization можно пропустить и отложить до последующих слияний. Это регулируется свойством `variant_doc_materialization_min_rows`. Например, при `variant_doc_materialization_min_rows = 10000` запись менее 10,000 строк сохранит только исходный JSON и не запустит Subcolumnization для этого пакета.
- Для сверхшироких нагрузок режим DOC также является более стабильным выбором, когда масштаб Subcolumnization приближается к десяти тысячам подстолбцов. По сравнению с немедленной Subcolumnization по умолчанию потребление памяти при уплотнении может сократиться примерно на две трети, а пропускная способность загрузки разреженных широких столбцов может вырасти примерно в 5-10 раз.
- Когда столбец `VARIANT` очень широкий и запросы часто читают документ целиком, режим DOC может ускорить `SELECT variant_col` на порядки по сравнению с восстановлением документа из множества подстолбцов.

```sql
CREATE TABLE example_table (
  id INT,
  data_variant VARIANT<
      'path_1' : INT,
      'path_2' : STRING,
      properties(
          'variant_enable_doc_mode' = 'true',
          'variant_doc_materialization_min_rows' = '10000',
          'variant_doc_hash_shard_count' = '64'
      )
  >
);
```

**Справочные примечания**

- Для режима DOC необходимо `variant_enable_doc_mode = true`.
- В режиме DOC поля Schema Template ограничены строками, целыми числами, `FLOAT`, `DOUBLE`, `BOOLEAN` и массивами этих типов.
- В режиме DOC `variant_doc_hash_shard_count` можно приблизительно оценить как «общее число ключей JSON / 128».
- Новый столбец в режиме DOC по умолчанию имеет `1` шард (64 до версии 4.2).
- Начиная с версии 4.2, `variant_doc_hash_shard_count` задаёт число шардов как с режимом DOC, так и без него. Вывод `SHOW CREATE TABLE` для таблицы в режиме DOC, созданной до версии 4.2, можно выполнить с сохранением числа шардов; `variant_max_subcolumns_count` в нём не указан, поэтому новый столбец извлечёт не более `2048` путей, если не задать другое значение явно.
- Столбец в режиме DOC, созданный до версии 4.2, сохраняет прежнее поведение: как только файл данных достигает порога строк, извлекаются все пути, а число шардов остаётся тем, с которым столбец был создан.

### Поведение при достижении пределов и рекомендации по настройке {#behavior-at-limits-and-tuning-suggestions}

1. После превышения порога новые пути записываются в разреженные столбцы; слияния Rowset также могут перенести туда некоторые пути.
2. Система стремится оставлять в Subcolumnization пути с большей долей ненулевых значений и более высокой частотой обращений.
3. При приближении числа путей в Subcolumnization к 10,000 требуется мощное оборудование (рекомендуется ≥128G RAM и ≥32C на узел). Если нагрузка уже близка к этому масштабу, сначала оцените режим DOC.
4. Настройка загрузки: разумно увеличьте клиентский `batch_size` или используйте Group Commit (при необходимости увеличьте `group_commit_interval_ms`/`group_commit_data_bytes`).
5. Если отсечение корзин не требуется, рассмотрите распределение RANDOM и включение загрузки в один таблет для снижения усиления записи при уплотнении.
6. Параметры настройки BE: `max_cumu_compaction_threads` (≥8), `vertical_compaction_num_columns_per_group=500` (ускоряет вертикальное уплотнение, но увеличивает расход памяти), `segment_cache_memory_percentage=20` (повышает эффективность кэша метаданных).
7. Следите за Compaction Score; если он постоянно растёт, уплотнение отстаёт — снизьте интенсивность загрузки.
8. Избегайте больших `SELECT *` для VARIANT; предпочитайте выборку конкретных путей, например `SELECT v['path']`.

## Просмотр подстолбцов и типов {#inspect-subcolumns-and-types}

Способ 1: используйте [VARIANT_TYPE](../../../sql-functions/scalar-functions/variant-functions/variant-type.md), чтобы построчно получать тип значения или отдельного пути. Функция считывает каждую проверяемую строку:

```sql
SELECT VARIANT_TYPE(v), VARIANT_TYPE(v['a']) FROM variant_tbl LIMIT 10;
```

Способ 2: расширенный `DESC` показывает подпути, извлечённые через Subcolumnization, и их типы хранения:

```sql
SET describe_extend_variant_column = true;
DESC variant_tbl;
```

```sql
DESCRIBE ${table_name} PARTITION ($partition_name);
```

Способ 1 показывает тип каждого значения; способ 2 — как хранится каждый путь.

## Ограничения {#limitations}

- **Оптимизация широких таблиц**: для широких таблиц с большим числом динамических подстолбцов (например, более 2000 столбцов), создаваемых типом `VARIANT`, настоятельно рекомендуется включить **Storage Format V3**, указав `"storage_format" = "V3"` в `PROPERTIES` таблицы. Это отделяет метаданные столбцов от Segment Footer, ускоряет открытие файлов и снижает расход памяти.
- Ключ JSON по умолчанию может иметь длину не более 255 байт (`variant_max_json_key_length`).
- Столбец VARIANT не может быть ключевым столбцом, столбцом секционирования или распределения по корзинам и не может быть вложен в другой тип в схеме таблицы (см. [Определение столбца VARIANT](#define-a-variant-column)).
- Вне режима DOC чтение целого столбца VARIANT сканирует все подпути. Для очень широких столбцов прямой `SELECT variant_col` обычно не рекомендуется, если режим DOC не включён. Если столбец содержит много подпутей, рассмотрите хранение исходной строки JSON в дополнительном столбце STRING/JSONB для поиска по всему объекту, например через `LIKE`:

```sql
CREATE TABLE example_table (
  id INT,
  data_variant VARIANT
);
SELECT * FROM example_table WHERE data_variant LIKE '%doris%';

-- Better: keep the original JSON string for whole-object matching
CREATE TABLE example_table (
  id INT,
  data_string STRING,
  data_variant VARIANT
);
SELECT * FROM example_table WHERE data_string LIKE '%doris%';
```

## Сравнение с типом JSON {#compared-with-json-type}

- Хранение: JSON сохраняется как JSONB (построчно). VARIANT применяет Subcolumnization при записи (лучшее сжатие и меньший объём).
- Запросы: JSON требует разбора. VARIANT сканирует столбцы напрямую и обычно работает значительно быстрее.

Модифицированный тест ClickBench (43 запроса):
- Хранение: VARIANT экономит ~65% по сравнению с JSON.
- Запросы: VARIANT быстрее JSON в 8x+ раз и близок по скорости к заранее определённым статическим столбцам.

**Объём хранения**

| Тип | Размер |
| --- | --- |
| Заранее определённые столбцы | 12.618 GB |
| VARIANT | 12.718 GB |
| JSON | 35.711 GB |

**Экономия места ~65%**

| Запуск | Заранее определённые столбцы | VARIANT | JSON |
| --- | --- | --- | --- |
| Первый (холодный) | 233.79s | 248.66s | Большинство запросов превысило время ожидания |
| Второй (прогретый) | 86.02s | 94.82s | 789.24s |
| Третий (прогретый) | 83.03s | 92.29s | 743.69s |

## Частые вопросы {#faq}

1. Одинаковы ли `null` в VARIANT и SQL `NULL`?
   - Нет. JSON `null`, вычисленный в запросе, — это значение VARIANT `null`, а отсутствующий путь даёт SQL `NULL`. После записи значения элементы объектов со значением `null` вне массивов удаляются и при чтении дают SQL `NULL`. См. [Семантика NULL](#null-semantics).
2. Почему `v['a']` возвращает `NULL` после `INSERT INTO t VALUES (1, '{"a": 1}')`?
   - `INSERT` сохраняет строку как строку VARIANT без разбора; так же работает `INSERT INTO ... SELECT` из `s3()`, `hdfs()` или другого строкового столбца. Используйте `PARSE_TO_VARIANT('{"a": 1}')` или загрузите данные заданием, таким как Stream Load. См. [Запись данных](#write-data).
3. Почему целый документ JSON сохраняется как строка, хотя это корректный JSON?
   - Вероятно, документ содержит целое число вне диапазона [-2^63, 2^64 - 1] или число вне диапазона `DOUBLE`. Парсер отклоняет такой документ, и по умолчанию он сохраняется как строка. См. [Ошибки разбора](#parse-errors).
4. Почему мой запрос или индекс не работает?
   - Проверьте, приводите ли вы пути с помощью CAST к их типам хранения (неявные числовые сравнения не могут использовать индексы), не перешёл ли тип в JSONB из-за конфликтов и не ожидаете ли вы ошибочно, что индекс целого VARIANT действует для подпутей.
5. Почему `ORDER BY v['a']` помещает `"10"` после `9`, а `GROUP BY v['a']` разделяет `1` и `"1"`?
   - При сортировке и проверке равенства VARIANT сначала учитывает вид значения: числа идут перед строками, а число никогда не равно строке. Если нужна числовая или лексикографическая семантика, приведите путь к одному типу с помощью CAST. См. [Сравнение, группировка и сортировка](#comparison-grouping-and-ordering).
6. Почему `COALESCE(v['a'], 0)` возвращает `0.000000000`, когда `v['a']` — строка, а `IF(..., v['a'], 1)` возвращает `NULL`?
   - При сочетании VARIANT с другим типом значения VARIANT преобразуются к этому типу; для целочисленного типа это `DECIMAL(38, 9)`. Строку, например `"abc"`, преобразовать нельзя, и она становится `NULL`, поэтому `COALESCE` возвращает `0` в виде `0.000000000`. Используйте `COALESCE(v['a'], CAST(0 AS VARIANT))`, чтобы сохранить результат типа VARIANT, или приведите `v['a']` к нужному типу.
7. Почему DECIMAL теряет точность при записи в столбец VARIANT?
   - Числа JSON с дробной частью определяются как `DOUBLE`, а не `DECIMAL`, поэтому последние цифры могут теряться. Объявление пути как `DECIMAL` в Schema Template, например `v VARIANT<'num': DECIMAL(9, 3)>`, не решает проблему полностью, поскольку значение сначала разбирается как `DOUBLE`. Записывайте значение внутри документа как строку JSON, например `PARSE_TO_VARIANT('{"num": "12.345"}')`; тогда оно напрямую преобразуется в `DECIMAL(9, 3)` без потери точности.
