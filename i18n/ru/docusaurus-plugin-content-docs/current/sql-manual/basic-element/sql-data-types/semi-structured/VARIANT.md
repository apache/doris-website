## Обзор {#overview}

Тип VARIANT хранит полуструктурированные данные JSON: объекты, массивы, строки, числа, логические значения и `null`. При записи Doris выводит тип каждого JSON-пути и выполняет Subcolumnization для часто используемых путей, сохраняя их как независимые столбцовые подстолбцы. Запрос к такому пути читает только нужный подстолбец.

:::tip Зачем нужен VARIANT
`VARIANT` подходит, когда структура документов со временем меняется, но запросы по-прежнему сосредоточены на небольшом наборе часто используемых путей.

- Часто используемые пути участвуют в Subcolumnization и получают преимущества столбцовой производительности, отсечения файлов и векторизованного выполнения.
- Для ключевых путей можно использовать индексы уровня пути и полнотекстовый поиск, сохраняя преимущества отсечения по разреженным индексам Doris.
- Оптимизации широких столбцов делают автоматический Subcolumnization практичным при масштабе в 10k подстолбцов. Когда число путей, участвующих в Subcolumnization, приближается к 10,000, требования к оборудованию быстро растут, поэтому режим DOC обычно является более безопасной отправной точкой.

Если нужно выбрать между поведением по умолчанию, разреженными столбцами, режимом DOC и Schema Template, начните с [Руководства по рабочим нагрузкам Variant](./variant-workload-guide.md). Эта страница является справочником по записи и разбору, правилам типов, CAST, семантике NULL и сравнения, ALTER, индексам, ограничениям и конфигурации.
:::

:::info Версия
На этой странице описан VARIANT в Doris 5.0.0 и более поздних версиях. Отличия от Doris 4.x, которые с наибольшей вероятностью повлияют на существующий SQL:

- `INSERT` сохраняет строку как строку VARIANT вместо разбора как JSON. Это также относится к `INSERT INTO ... SELECT` из табличных функций, таких как `s3()` и `hdfs()`. Используйте `PARSE_TO_VARIANT`, чтобы записывать текст JSON через `INSERT`. Задания загрузки, такие как Stream Load, по-прежнему разбирают JSON.
- Целые значения VARIANT поддерживают `GROUP BY`, `DISTINCT` и операции над множествами. Два значения VARIANT можно сравнивать с помощью `=`, `!=` и `<=>`, а также использовать как ключи соединения, ключи `ORDER BY` и оконные ключи.
- `VARIANT_TYPE` возвращает одно имя типа, например `object`, вместо карты путей и типов.
- К массивам VARIANT можно обращаться по целочисленным индексам, начиная с 1.

Для Doris 4.x см. версию этой страницы для 4.x.
:::

## Быстрый старт {#quick-start}

```sql
CREATE TABLE events (
    id BIGINT,
    v  VARIANT
)
DUPLICATE KEY(id)
DISTRIBUTED BY HASH(id) BUCKETS 1
PROPERTIES ("replication_num" = "1");

-- INSERT keeps a string literal as a VARIANT string, so parse JSON text explicitly.
INSERT INTO events VALUES
    (1, PARSE_TO_VARIANT('{"user": {"id": 42, "name": "alice"}, "tags": ["doris", "sql"], "score": 9.5}')),
    (2, PARSE_TO_VARIANT('{"user": {"id": 7, "name": "bob"}, "score": 3}'));

SELECT id,
       CAST(v['user']['name'] AS STRING) AS name,
       v['tags'][1] AS first_tag
FROM events
WHERE CAST(v['score'] AS DOUBLE) > 5;
```

```text
+------+-------+-----------+
| id   | name  | first_tag |
+------+-------+-----------+
|    1 | alice | doris     |
+------+-------+-----------+
```

- `v['user']['name']` и `v['tags'][1]` возвращают значения `VARIANT`. Индексы массивов начинаются с 1.
- Перед сравнением или вычислением приведите путь к конкретному типу с помощью CAST.
- Задания загрузки, такие как Stream Load, автоматически разбирают текст JSON. См. [Запись данных](#write-data).

## Определение столбца VARIANT {#define-a-variant-column}

```sql
column_name VARIANT
column_name VARIANT< field_definition [, field_definition ...] >
column_name VARIANT< properties('key' = 'value' [, ...]) >
column_name VARIANT< field_definition [, ...], properties('key' = 'value' [, ...]) >

field_definition:
    [MATCH_NAME | MATCH_NAME_GLOB] 'path_or_pattern' : data_type [COMMENT 'comment']
```

- Список `field_definition` — это [Schema Template](#schema-template). Он фиксирует тип хранения выбранных путей.
- `properties(...)` задаёт свойства хранения на уровне столбца. См. [Свойства столбца](#column-properties).
- Столбец VARIANT может быть `NULL` или `NOT NULL`. Единственное допустимое значение по умолчанию — `NULL`.
- Имя столбца VARIANT верхнего уровня не может содержать точку (`.`), даже если заключено в обратные кавычки: например, `` `v.x` VARIANT `` недопустимо. Это ограничение относится к `CREATE TABLE` и `ALTER TABLE`; оно не ограничивает имена полей JSON внутри значения VARIANT.

```sql
CREATE TABLE IF NOT EXISTS example_tbl (
    k BIGINT,
    v VARIANT<
        'id' : INT,             -- path id is stored as INT
        'message*' : STRING,    -- paths matching message* are stored as STRING
        'tags*' : ARRAY<TEXT>,  -- paths matching tags* are stored as ARRAY<TEXT>
        properties('variant_max_subcolumns_count' = '2048')
    > NULL
)
DUPLICATE KEY(k)
DISTRIBUTED BY HASH(k) BUCKETS 1
PROPERTIES ("replication_num" = "1");
```

Где столбец VARIANT можно использовать в таблице:

| Использование | Поддерживается | Примечания |
| --- | --- | --- |
| Столбец значений в таблицах Duplicate Key, Unique Key и Aggregate Key | Да | В таблице Aggregate Key тип агрегации должен быть `REPLACE` или `REPLACE_IF_NOT_NULL`. |
| Столбец ключа, столбец секционирования, столбец бакетирования | Нет | |
| Вложение в другой тип в схеме таблицы (`ARRAY<VARIANT>`, `MAP`, `STRUCT`) | Нет | Результат запроса всё же может быть `ARRAY<VARIANT>`, например результатом `COLLECT_LIST(v)`. |
| Значение по умолчанию | Только `NULL` | `DEFAULT '{}'` и другие значения по умолчанию, отличные от NULL, отклоняются. |

## Запись данных {#write-data}

`INSERT` и `CAST` сохраняют строку как строку VARIANT. `PARSE_TO_VARIANT`, `TRY_PARSE_TO_VARIANT` и задания загрузки, такие как Stream Load, разбирают текст JSON. Примеры загрузки см. в разделе [Загрузка данных VARIANT](../../../../data-operate/import/complex-types/variant.md).

### Ошибки разбора {#parse-errors}

[PARSE_TO_VARIANT](../../../sql-functions/scalar-functions/variant-functions/parse-to-variant.md), [TRY_PARSE_TO_VARIANT](../../../sql-functions/scalar-functions/variant-functions/try-parse-to-variant.md) и задания загрузки используют один и тот же парсер JSON. Задания загрузки обрабатывают ошибки так же, как `TRY_PARSE_TO_VARIANT`:

| Входные данные | `PARSE_TO_VARIANT` | `TRY_PARSE_TO_VARIANT` и задания загрузки |
| --- | --- | --- |
| Допустимый JSON | Разобранное значение | Разобранное значение |
| Текст, не являющийся допустимым JSON, например `hello` или `{"id":` | Сохраняется как строка VARIANT | Сохраняется как строка VARIANT |
| JSON, содержащий целое вне диапазона [-2^63, 2^64 - 1] или число вне диапазона `DOUBLE`, например `{"a": 1, "n": 100000000000000000000}` | Весь текст сохраняется как строка VARIANT, поэтому `v['a']` возвращает `NULL` | Весь текст сохраняется как строка VARIANT |
| Пустая строка | Пустой объект `{}` | Пустой объект `{}` |
| Вложенность глубже 128 уровней | Ошибка | SQL `NULL` |
| Ключ объекта длиннее `variant_max_json_key_length` байт (конфигурация BE, по умолчанию 255) | Ошибка | SQL `NULL` |
| Повторяющиеся ключи в одном объекте | Ошибка | SQL `NULL` |
| Строка, не являющаяся допустимым UTF-8 | Ошибка | SQL `NULL` |

Документ, вложенный настолько глубоко, что сам парсер JSON отклоняет его (около 1,000 уровней), является недопустимым JSON и поэтому сохраняется как строка.

Две конфигурации BE изменяют эти правила:

- `variant_throw_exeception_on_invalid_json` (по умолчанию `false`): если установить `true`, текст, отклонённый парсером, включая JSON с числами вне диапазона, вызывает ошибку для `PARSE_TO_VARIANT` и SQL `NULL` для `TRY_PARSE_TO_VARIANT` и заданий загрузки вместо сохранения как строки VARIANT.
- `variant_enable_duplicate_json_path_check` (по умолчанию `false`): если установить `true`, повторяющийся ключ в объекте сохраняет своё первое значение вместо ошибки. Это также предотвращает сбой записи, когда ключ с точкой повторяет вложенный путь; сохраняется только одно из значений.

Чтобы сохранить документ со целыми числами вне диапазона в структурированном виде, преобразуйте его через JSON: `CAST(CAST(text AS JSON) AS VARIANT)`. Целые числа длиной до 38 цифр остаются точными числами, более крупные числа в диапазоне `LARGEINT` становятся строками, а ещё более крупные — `DOUBLE`. `PARSE_TO_VARIANT(CAST(text AS JSON))` не помогает, поскольку снова разбирает текст JSON.

```sql
SELECT VARIANT_TYPE(PARSE_TO_VARIANT('{"id": 1}')) AS valid_json,    -- object
       VARIANT_TYPE(PARSE_TO_VARIANT('{"id":'))    AS invalid_json,  -- string
       VARIANT_TYPE(CAST('{"id": 1}' AS VARIANT))  AS string_cast;   -- string
```

### Что сохраняется при хранении {#what-storage-keeps}

Запись значения в таблицу нормализует его. Значение, прочитанное обратно, может отличаться от значения, вычисленного до записи:

| До записи | Прочитано из таблицы |
| --- | --- |
| Член объекта со значением JSON `null`, например `{"a": null, "b": 1}` | Член удаляется: `{"b":1}`. `v['a']` возвращает SQL `NULL`. |
| Член объекта со значением пустого объекта или массива либо объект, ставший пустым по этим правилам, например `{"a": {}, "b": [], "c": {"d": null}}` | Удаляется: `{}` |
| Член объекта, массив которого содержит только `null`, например `{"p": [null, null], "q": 1}` | Может быть удалён: `{"q":1}` |
| Значения внутри массивов, например `{"arr": [{"a": null}, {}, [], null]}` | Сохраняются как есть. `v['arr'][1]['a']` — это VARIANT `null`. |
| Корневой JSON `null`, например `PARSE_TO_VARIANT('null')` | Пустой объект `{}` |
| Корневой пустой массив `[]` или пустой объект `{}` | Сохраняется |
| Значения `DATE` и `DATETIME` в корневом значении, например `CAST(date_col AS VARIANT)`, или на пути, который также содержит значения других типов | Сохраняются как текст и читаются обратно как строки. На пути объекта, содержащем только даты, они сохраняют свой тип. |
| Логические значения и числа, смешанные на одном пути | Логические значения могут читаться как `1` или `0` в зависимости от порядка значений внутри одной записи и от compaction |
| Ключ с точкой, например `{"a.b": 1}` | Сохраняется как вложенный путь: `{"a":{"b":1}}`. И `v['a.b']`, и `v['a']['b']` возвращают `1`. Если документ содержит и ключ `a.b`, и ключ `b` внутри `a`, весь `INSERT` или весь job загрузки завершается ошибкой, если `variant_enable_duplicate_json_path_check` не равно `true`. |
| Ключи объекта | Возвращаются в порядке байтов |

Эти правила зависят от других строк, записанных вместе, и от режима DOC, поэтому не полагайтесь на сохранение значений `null` или пустых контейнеров. Пути, объявленные в Schema Template, преобразуются в объявленный тип; см. [Schema Template](#schema-template).

## Вывод типов и конфликты типов {#type-inference-and-type-conflicts}

Без Schema Template Doris выводит тип каждого значения при разборе JSON. `VARIANT_TYPE` возвращает этот тип:

| Значение JSON | Тип |
| --- | --- |
| Целое в диапазоне `BIGINT` | `tinyint`, `smallint`, `int` или `bigint` — наименьший подходящий тип |
| Целое выше диапазона `BIGINT`, до 18446744073709551615 | `decimal` |
| Число с дробной частью или экспонентой | `double` |
| Целое вне [-2^63, 2^64 - 1] или число вне диапазона `DOUBLE` | Не число: весь текст является недопустимым JSON (см. [Ошибки разбора](#parse-errors)) |
| Строка | `string` |
| `true`, `false` | `bool` |
| `null` | `null` |
| Массив, объект | `array`, `object` |

При хранении данных каждый путь получает один тип хранения:

- Целые числа хранятся как `BIGINT` или как `LARGEINT`, если это необходимо. Числа с плавающей точкой хранятся как `DOUBLE`, десятичные числа — как `DECIMAL`, строки — как `STRING`, логические значения — как `BOOLEAN`, а массивы скаляров — как `ARRAY<T>`.
- Массивы объектов, вложенные массивы и пути, значения которых имеют разные типы, например целые и числа с плавающей точкой, числа и строки или скаляры и массивы, хранятся как `JSONB` (в `DESC` отображаются как `json`). Массивы с конфликтующими типами элементов становятся `ARRAY<JSONB>`.

```sql
{"a" : 12345678}
{"a" : "HelloWorld"}
-- a is stored as JSONB
```

Путь `JSONB` сохраняет каждое значение, но теряет типизированное хранение: индексы и отсечение по типу больше не применяются к этому пути. Логические значения являются особым случаем: если первое значение на пути — логическое, а последующие значения — числа, путь может храниться как число, и логические значения будут читаться как `1` или `0`. Если путь должен иметь стабильный тип, объявите его в Schema Template.

`VARIANT_TYPE` сообщает тип каждого значения, поэтому целое, прочитанное из пути `BIGINT`, всё ещё может иметь тип `tinyint`. Чтобы увидеть тип хранения каждого пути, выполните `SET describe_extend_variant_column = true;`, а затем `DESC table_name;`. См. [Просмотр подстолбцов и типов](#inspect-subcolumns-and-types).

## Доступ к путям и вывод {#access-paths-and-output}

- `v['key']` и `v['a']['b']` читают члены объекта. `v['arr'][1]` читает элемент массива: индексы начинаются с 1, а `-1` обозначает последний элемент. [ELEMENT_AT](../../../sql-functions/scalar-functions/variant-functions/element-at.md) эквивалентен этой записи.
- Результат имеет тип `VARIANT`. Отсутствующий ключ, индекс `0`, индекс за пределами диапазона, строковый ключ для массива, целочисленный индекс для объекта и ключ у скалярного значения возвращают SQL `NULL`.
- В вычисляемом значении ключ с точкой является единым ключом: `v['a.b']` читает ключ `a.b`, а `v['a']['b']` читает `b` внутри `a`. Хранилище не сохраняет это различие; см. [Что сохраняется при хранении](#what-storage-keeps).
- Путь не выполняет отображение по массивам. Для `{"a": [{"b": 1}]}` выражение `v['a']['b']` возвращает `NULL`; используйте `v['a'][1]['b']`.

```sql
SELECT v['user']['id']      AS id,       -- 42
       v['tags'][-1]        AS last_tag, -- sql
       v['user']['missing'] AS missing   -- NULL
FROM events
WHERE id = 1;
```

Обычно путь приводят к типу, который нужен запросу:

```sql
SELECT * FROM tbl WHERE ARRAY_CONTAINS(CAST(v['tags'] AS ARRAY<TEXT>), 'Doris');
SELECT * FROM tbl WHERE CAST(v['date'] AS DATE) = '2021-01-02';
SELECT * FROM tbl WHERE v['bool'];                -- implicit CAST to BOOLEAN
SELECT * FROM tbl WHERE v['str'] MATCH 'Doris';   -- uses an inverted index on the path
```

Чтение всего значения VARIANT возвращает текст JSON. Ключи объекта возвращаются в порядке байтов и без пробелов, поэтому текст не совпадает с входными данными побайтно. Корневая строка возвращается без кавычек.

```sql
CREATE TABLE variant_tbl (k INT, v VARIANT)
DUPLICATE KEY(k)
DISTRIBUTED BY HASH(k) BUCKETS 1
PROPERTIES ("replication_num" = "1");

INSERT INTO variant_tbl VALUES (1, PARSE_TO_VARIANT('{ "b": 2, "a": 1, "c": { "y": 20, "x": 10 } }'));

SELECT v FROM variant_tbl WHERE k = 1;
-- {"a":1,"b":2,"c":{"x":10,"y":20}}
```

## CAST {#cast}

### CAST в VARIANT {#cast-to-variant}

| Исходный тип | Результат |
| --- | --- |
| `CHAR`, `VARCHAR`, `STRING` | Строка VARIANT. Текст JSON не разбирается. Строка должна быть допустимым UTF-8, иначе CAST завершается ошибкой. |
| `BOOLEAN` | Логическое значение. |
| `TINYINT`, `SMALLINT`, `INT`, `BIGINT` | Целое число. |
| `LARGEINT` | Десятичное число. Значение, абсолютная величина которого превышает 10^38 - 1, становится строкой. |
| `FLOAT`, `DOUBLE` | Число с плавающей точкой. |
| `DECIMALV2`, `DECIMAL(p, s)` с `p <= 38` | Десятичное число. |
| `DATE`, `DATETIME(p)`, `TIMESTAMP_NS` | Дата или метка времени без часового пояса. |
| `IPV4`, `IPV6` | Строка с текстовым представлением значения. |
| `JSON` / `JSONB` | Та же структура. Значение, которое VARIANT не может хранить, например число `DECIMAL256`, или повторяющиеся ключи в объекте приводят к ошибке CAST. |
| `ARRAY<T>` | Массив; каждый элемент преобразуется. `T` должен быть `VARIANT` или типом из этой таблицы. |
| `MAP`, `STRUCT`, `TIME`, `TIMESTAMPTZ`, `VARBINARY` и другие типы | Не поддерживаются. Оператор завершается ошибкой. |

Исходное значение также должно быть допустимым для собственного типа; недопустимое значение отклоняется, а не исправляется. CAST никогда не разбирает строки: `CAST('{"id": 1}' AS VARIANT)` — это строка `{"id": 1}`. Используйте `PARSE_TO_VARIANT`, чтобы разобрать текст JSON.

### CAST из VARIANT {#cast-from-variant}

| Целевой тип | Результат |
| --- | --- |
| `BOOLEAN` | Логические значения сохраняются. Числа становятся `true`, если не равны нулю. Строки преобразуются по правилам `CAST(string AS BOOLEAN)`. |
| `TINYINT`, `SMALLINT`, `INT`, `BIGINT`, `LARGEINT` | Целые числа. Дробная часть десятичного или числа с плавающей точкой отбрасывается (`1.5` становится `1`). Логические значения становятся `1` или `0`. Числовые строки, например `"123"`, преобразуются. |
| `FLOAT`, `DOUBLE`, `DECIMAL(p, s)` | Числа и числовые строки. `DECIMAL` округляется до масштаба `s`. Значение, слишком большое для `FLOAT`, становится `Infinity`. |
| `DATE`, `DATETIME(p)`, `TIMESTAMP_NS` | Значения даты и времени, строки в формате даты или времени и числа, такие как `20240102`. |
| `TIMESTAMPTZ(p)` | Значения даты и времени и строки в формате даты или времени. |
| `IPV4`, `IPV6` | Строки в формате IP-адреса. |
| `CHAR`, `VARCHAR`, `STRING` | Корневая строка возвращается как есть, без кавычек. Объекты и массивы возвращаются как текст JSON. Остальные скаляры форматируются как соответствующий SQL-тип: корневое логическое значение становится `1` или `0`, значение `DATETIME` содержит шесть дробных цифр, а `TIMESTAMP_NS` — девять. VARIANT `null` становится строкой `null`. |
| `JSON` / `JSONB` | Та же структура. Значения без аналога в JSON, например даты и метки времени, становятся строками JSON; метка времени с часовым поясом форматируется в часовом поясе сеанса. |
| `ARRAY<T>` | Массив, преобразованный поэлементно; элемент, который нельзя преобразовать, становится `NULL`. Также преобразуется строка, содержащая массив JSON, например `"[1, 2]"`. Для других значений возвращается `NULL`. |
| `MAP`, `STRUCT`, `TIME` и другие типы | Не поддерживаются. Оператор завершается ошибкой. |

Если значение нельзя преобразовать в целевой тип, возвращается SQL `NULL`, в том числе при включённом `enable_strict_cast`. Исключение — тип значения вообще не имеет преобразования в целевой тип, например число в `TIMESTAMPTZ`, `IPV4` или `IPV6`, либо дата или метка времени в `BOOLEAN`: тогда оператор завершается ошибкой.

```sql
SELECT CAST(PARSE_TO_VARIANT('"123"') AS INT)      AS from_string,   -- 123
       CAST(PARSE_TO_VARIANT('"abc"') AS INT)      AS not_a_number,  -- NULL
       CAST(PARSE_TO_VARIANT('1.5') AS INT)        AS truncated,     -- 1
       CAST(PARSE_TO_VARIANT('300') AS TINYINT)    AS overflow,      -- NULL
       CAST(PARSE_TO_VARIANT('{"a": 1}') AS INT)   AS from_object,   -- NULL
       CAST(PARSE_TO_VARIANT('[1, "2", null, "x"]') AS ARRAY<INT>) AS arr;  -- [1, 2, null, null]

SELECT CAST(PARSE_TO_VARIANT('true') AS STRING)        AS bool_root,     -- 1
       CAST(PARSE_TO_VARIANT('{"b": true}') AS STRING) AS object_text,   -- {"b":true}
       CAST(PARSE_TO_VARIANT('"abc"') AS STRING)       AS string_root,   -- abc
       CAST(PARSE_TO_VARIANT('null') AS STRING)        AS variant_null;  -- null
```

### Десятичные значения и значения даты/времени {#decimal-and-datetime-values}

При преобразовании этих типов в VARIANT:

| Тип Doris | Поведение |
| --- | --- |
| Устаревший `DECIMALV2` | Точно сохраняются значения с precision до 27 и scale до 9. |
| `DECIMAL(p, s)` | Точно сохраняются `1 <= p <= 38` и `0 <= s <= p`. Десятичные числа с precision больше 38 не поддерживаются. |
| `DATE` | Календарная дата без времени и часового пояса. |
| `DATETIME(p)` | `0 <= p <= 6`, без корректировки часового пояса. |
| `TIMESTAMP_NS` | Наносекундная точность без корректировки часового пояса; значения должны находиться в диапазоне TIMESTAMP_NS. |
| `TIMESTAMPTZ(p)` | Не поддерживается ни CAST, ни как путь Schema Template. |
| `TIME` | Не поддерживается. |

## Семантика NULL {#null-semantics}

В VARIANT есть два вида null:

- **SQL `NULL`** означает отсутствие значения. Он возникает из значения столбца `NULL`, отсутствующего пути, например `v['no_such_key']`, или неудачного CAST.
- **VARIANT `null`** является значением: литералом JSON `null`, например `PARSE_TO_VARIANT('null')` или элементом массива `null`. Для него `VARIANT_TYPE` возвращает `null`.

| Операция | SQL `NULL` | VARIANT `null` |
| --- | --- | --- |
| `v IS NULL` | `true` | `false` |
| `COALESCE(v, x)`, `IFNULL(v, x)` с VARIANT `x` | Возвращает `x` | Возвращает VARIANT `null` |
| `COUNT(v)` | Не учитывается | Учитывается |
| `GROUP BY v`, `DISTINCT` | Все значения SQL `NULL` образуют одну группу | Все значения VARIANT `null` образуют другую группу |
| `v = x`, равенство при соединении | Никогда не совпадает | Совпадает с другим VARIANT `null` |
| `ORDER BY v` | Размещается согласно `NULLS FIRST` или `NULLS LAST` | При сортировке по возрастанию находится перед любым другим значением, отличным от NULL |
| `CAST(v AS STRING)` | SQL `NULL` | Строка `null` |

После сохранения значения член объекта со значением `null`, находящийся вне массивов, удаляется, поэтому при чтении возвращается SQL `NULL`, а корневой `null` читается как `{}` (см. [Что сохраняется при хранении](#what-storage-keeps)). Для сохранённых данных `v['a'] IS NULL` поэтому не позволяет отличить отсутствующий член от члена со значением `null`.

## Сравнение, группировка и сортировка {#comparison-grouping-and-ordering}

Значения VARIANT сравниваются по логическому значению, а не по тексту или физическому кодированию. Равенство, хеширование (`GROUP BY`, `DISTINCT`, соединения) и сортировка (`ORDER BY`, оконные ключи) используют одни и те же правила, поэтому равные значения всегда попадают в одну группу и являются равными при сортировке.

### Поддерживаемые операции {#supported-operations}

| Операция над значениями VARIANT | Поддержка | Примечания |
| --- | --- | --- |
| `=`, `!=`, `<=>` между двумя значениями VARIANT или со значением `NULL` | Поддерживается | Включает подпути, например `v['a'] = w['a']`. |
| Равенство при соединении, полусоединение и антисоединение, подзапросы `IN` и `NOT IN` | Поддерживается | Фильтры выполнения не создаются для ключей соединения VARIANT. |
| `GROUP BY`, `DISTINCT`, `COUNT(DISTINCT ...)`, `UNION`, `INTERSECT`, `EXCEPT` | Поддерживается | |
| `ORDER BY`, `ORDER BY ... LIMIT` | Поддерживается | |
| `PARTITION BY` и `ORDER BY` окна | Поддерживается | |
| `COUNT(v)`, `COLLECT_LIST(v)`, `ARRAY_AGG(v)` | Поддерживается | |
| `IF`, `CASE`, `IFNULL`, `COALESCE` | Поддерживается | При смешивании VARIANT с другим типом значения VARIANT преобразуются в другой тип (`DECIMAL(38, 9)`, если другая сторона является целым числом); значения, которые нельзя преобразовать, становятся `NULL`. |
| `CAST(v AS ARRAY<VARIANT>)`, `EXPLODE_VARIANT_ARRAY`, `EXPLODE` и `EXPLODE_OUTER` над `ARRAY<VARIANT>` | Поддерживается | |
| `<`, `<=`, `>`, `>=`, `BETWEEN` между значениями VARIANT | Не поддерживается | Сначала выполните CAST в конкретный тип. |
| Сравнение целого значения VARIANT со значением не VARIANT, например `v = 1` | Не поддерживается | Подпуть преобразуется неявно: `v['a'] = 1` работает. |
| Список `IN`, содержащий значения VARIANT, например `v IN (PARSE_TO_VARIANT('1'))` | Не поддерживается | `v IN ('a', 'b')` с не- VARIANT значениями работает через неявное преобразование. |
| `MIN`, `MAX` | Не поддерживается | Сначала выполните CAST подпути. |
| `ARRAY(...)`, `MAP(...)`, `NAMED_STRUCT(...)` с аргументами VARIANT | Не поддерживается | |

### Равенство {#equality}

- **Числа.** Целое число, десятичное число с нулевой дробной частью и число с плавающей точкой, имеющее целое значение, равны: `1`, `1.0` и `1.00` — одно значение. Концевые нули десятичного числа не имеют значения, а `-0.0` равно `0`. Десятичное число и число с плавающей точкой с дробной частью никогда не равны: `DECIMAL 1.5` не равно `DOUBLE 1.5`. JSON-числа с дробной частью разбираются как `DOUBLE`; десятичные числа появляются из CAST, путей Schema Template и целых чисел, слишком больших для `BIGINT`.
- **Значения разных видов никогда не равны.** Число `1`, строка `"1"` и `true` — три разных значения. `DATE` не равно строке `"2024-01-01"`, а метка времени без часового пояса не равна метке времени с часовым поясом.
- **Строки** равны только при побайтовом совпадении. Сравнение чувствительно к регистру.
- **Объекты** равны, если у них одинаковые ключи с равными значениями. Порядок ключей не имеет значения.
- **Массивы** равны, если у них одинаковая длина и равные элементы в одинаковом порядке.
- VARIANT `null` равен другому VARIANT `null`. SQL `NULL` подчиняется правилам SQL.

```sql
SELECT PARSE_TO_VARIANT('1') = PARSE_TO_VARIANT('1.0')                             AS int_double,  -- 1
       PARSE_TO_VARIANT('1.5') = CAST(CAST(1.5 AS DECIMAL(10, 2)) AS VARIANT)       AS dbl_dec,     -- 0
       PARSE_TO_VARIANT('1') = PARSE_TO_VARIANT('"1"')                             AS num_str,     -- 0
       PARSE_TO_VARIANT('{"a": 1, "b": 2}') = PARSE_TO_VARIANT('{"b": 2, "a": 1}') AS obj,         -- 1
       PARSE_TO_VARIANT('[1, 2]') = PARSE_TO_VARIANT('[2, 1]')                     AS arr;         -- 0
```

### Сортировка {#ordering}

`ORDER BY` для значений VARIANT использует один полный порядок. Значения разных видов сначала упорядочиваются по виду:

```text
null < boolean < number < string < binary < date < timestamp with time zone
     < timestamp without time zone < time < UUID < object < array
```

Значения binary, time и UUID нельзя получить разбором JSON или CAST в Doris; они могут поступать только из данных VARIANT, записанных другими системами, например из файлов Parquet со столбцами VARIANT.

Внутри одного вида:

- **Логические значения:** `false` перед `true`.
- **Числа:** целые числа (`INT`, `BIGINT` и т. д.), десятичные числа (`DECIMAL`) и числа с плавающей точкой (`FLOAT`, `DOUBLE`) сортируются по числовому значению. `INT 1`, `FLOAT/DOUBLE 1.0` и `DECIMAL 1.00` равны и имеют одинаковую позицию; концевые нули десятичного числа не имеют значения. Для равных ненцелых значений десятичное число сортируется первым: `DECIMAL 1.5` предшествует `FLOAT/DOUBLE 1.5`, и как значения VARIANT они не равны. Точность чисел с плавающей точкой может влиять на порядок: `DOUBLE 0.1` немного больше `DECIMAL 0.1`. Отрицательная бесконечность сортируется первой; положительная бесконечность, а затем NaN — последними.
- **Строки:** по байтам UTF-8. Заглавные буквы сортируются перед строчными, а `"10"` — перед `"9"`.
- **Даты и метки времени:** в хронологическом порядке. Любая дата сортируется перед любой меткой времени.
- **Объекты:** поэлементно в порядке ключей: сначала сравниваются наименьшие ключи, затем их значения, затем следующие ключи. Объект, записи которого являются префиксом записей другого объекта, сортируется первым, поэтому `{"a":1}` < `{"a":1,"b":2}` < `{"b":0}`.
- **Массивы:** поэлементно; префикс сортируется первым, поэтому `[]` < `[null]` < `[1]` < `[1,2]`.

Положение SQL `NULL` определяется `NULLS FIRST` или `NULLS LAST`.

```sql
SELECT v, VARIANT_TYPE(v) AS type
FROM (
    SELECT PARSE_TO_VARIANT('[1, 2]') AS v UNION ALL
    SELECT PARSE_TO_VARIANT('{"a": 1}')    UNION ALL
    SELECT PARSE_TO_VARIANT('"9"')         UNION ALL
    SELECT PARSE_TO_VARIANT('"10"')        UNION ALL
    SELECT PARSE_TO_VARIANT('10')          UNION ALL
    SELECT PARSE_TO_VARIANT('9.5')         UNION ALL
    SELECT PARSE_TO_VARIANT('true')        UNION ALL
    SELECT PARSE_TO_VARIANT('null')        UNION ALL
    SELECT NULL
) t
ORDER BY v;
```

```text
+---------+---------+
| v       | type    |
+---------+---------+
| NULL    | NULL    |
| null    | null    |
| true    | bool    |
| 9.5     | double  |
| 10      | tinyint |
| 10      | string  |
| 9       | string  |
| {"a":1} | object  |
| [1,2]   | array   |
+---------+---------+
```

### Сравнение по типу и сравнение VARIANT {#typed-comparison-and-variant-comparison}

Выбор правил VARIANT или правил конкретного типа определяется операндами. Рассмотрим путь `a`, значения которого равны `1`, `1.0` и `"1"`:

| Выражение | Способ сравнения | Результат |
| --- | --- | --- |
| `v['a'] = 1` | `DECIMAL(38, 9)` через неявный CAST `v['a']` | Совпадают все три значения |
| `v['a'] = CAST(1 AS VARIANT)`, `v['a'] = w['a']` | VARIANT | Совпадают `1` и `1.0`, но не `"1"` |
| `GROUP BY v['a']` | VARIANT | `1` и `1.0` образуют одну группу, `"1"` — другую |
| `GROUP BY CAST(v['a'] AS STRING)` | `STRING` | Одна группа, `1` |
| `ORDER BY v['a']` | VARIANT | Сначала числа, затем строки |
| `ORDER BY CAST(v['a'] AS INT)` | `INT` | Числовой порядок; значения, которые нельзя преобразовать, становятся `NULL` |

### Примечания {#notes}

- **Стоимость.** Ключи VARIANT хешируются и сравниваются по логическому значению. В тесте на 44 миллионах строк `GROUP BY`, сортировка и соединения по ключу VARIANT выполнялись в 1.2–3.7 раза дольше тех же операций с `CAST(v['path'] AS <type>)`. Если путь имеет один известный тип, выполните CAST.
- **Результаты соответствуют сохранённым значениям.** Нормализация из раздела [Что сохраняется при хранении](#what-storage-keeps) выполняется до сравнения: член со значением `null` удаляется, `DATE` в корневом значении сравнивается как строка, а логические значения, смешанные с числами на одном пути, могут читаться как `1` или `0`. Пути, тип которых важен, объявляйте в Schema Template.
- **Смешанные типы сортируются по виду, а не по значению.** Если путь содержит и числа, и числовые строки, `ORDER BY v['a']` помещает все числа перед всеми строками, а строки сортирует по байтам. Для числового или лексикографического порядка приведите всё к одному типу с помощью CAST.
- **Похожиe значения могут отличаться.** В результате `GROUP BY` число `1` и строка `"1"` отображаются одинаково, но образуют две группы. Для различения используйте `VARIANT_TYPE`.
- Порядок между видами определён Doris для детерминированности результатов. Он не является частью стандарта JSON и может отличаться в других системах.
- Внутренний хеш значения VARIANT является деталью реализации и не представляет собой стабильную контрольную сумму для пользователя.

## Schema Template {#schema-template}

Schema Template объявляет тип хранения выбранных путей. Объявляйте только ключевые пути, которым нужен стабильный тип или индекс уровня пути; остальная часть документа остаётся динамической.

```sql
CREATE TABLE test_var_schema (
    id BIGINT NOT NULL,
    v1 VARIANT<
        'large_int_val': LARGEINT,
        'string_val': STRING,
        'decimal_val': DECIMAL(38, 9),
        'datetime_val': DATETIME,
        'ip_val': IPV4
    > NULL
)
PROPERTIES ("replication_num" = "1");
```

Поле шаблона может использовать следующие типы:

- Числа: `TINYINT`, `SMALLINT`, `INT`, `BIGINT`, `LARGEINT`, `FLOAT`, `DOUBLE` и `DECIMAL(p, s)` с `p <= 38`
- `STRING` (или `TEXT`)
- `BOOLEAN`
- `DATE`, `DATETIME(p)`, `TIMESTAMP_NS`
- `IPV4`, `IPV6`
- `ARRAY<T>`, где `T` — один из перечисленных типов (только одно измерение)

### Запись в пути шаблона {#writing-to-template-paths}

В объявленном пути каждое значение преобразуется в объявленный тип по правилам нестрогого CAST. Значение, которое нельзя преобразовать, сохраняется как `NULL`, поэтому при чтении путь отсутствует; остальная часть строки всё равно записывается. Преобразование может изменить значение:

```sql
CREATE TABLE tpl_demo (
    k INT,
    v VARIANT<'id': INT, 'price': DECIMAL(10, 2), 'ts': DATETIME(3)>
)
DUPLICATE KEY(k)
DISTRIBUTED BY HASH(k) BUCKETS 1
PROPERTIES ("replication_num" = "1");

INSERT INTO tpl_demo VALUES
    (1, PARSE_TO_VARIANT('{"id": "123", "price": 9.999, "ts": "2024-01-01 10:00:00.123456"}')),
    (2, PARSE_TO_VARIANT('{"id": "abc", "price": "x", "ts": "not a time"}')),
    (3, PARSE_TO_VARIANT('{"id": 1.7}'));

SELECT k, v FROM tpl_demo ORDER BY k;
```

```text
+------+------------------------------------------------------------+
| k    | v                                                          |
+------+------------------------------------------------------------+
|    1 | {"id":123,"price":10.00,"ts":"2024-01-01 10:00:00.123000"} |
|    2 | {}                                                         |
|    3 | {"id":1}                                                   |
+------+------------------------------------------------------------+
```

- `"123"` становится `123`, `1.7` усекается до `1`, `9.999` округляется до `10.00`, а метка времени сохраняет объявленную точность (миллисекунды); в текстовом представлении всегда отображаются шесть дробных цифр.
- `"abc"`, `"x"` и `"not a time"` нельзя преобразовать, поэтому они отбрасываются.
- JSON-число с дробной частью перед преобразованием разбирается как `DOUBLE`, поэтому путь `DECIMAL` может потерять точность. Чтобы сохранить все цифры, записывайте такие значения как строки JSON (см. [FAQ](#faq)).
- Значения даты и IP должны быть строками JSON: `{"date": 2020-01-01}` и `{"ip": 127.0.0.1}` не являются допустимым JSON; записывайте `{"date": "2020-01-01"}` и `{"ip": "127.0.0.1"}`.

:::caution
Значение преобразуется только тогда, когда его тип JSON можно преобразовать в объявленный тип. Число JSON на пути `IPV4` или `IPV6` приводит к сбою всей записи. Если одна запись содержит на пути `DATE`, `DATETIME`, `IPV4` или `IPV6` и строки JSON, и числа, допустимые значения этого пути также могут быть отброшены. Значения таких путей записывайте как строки JSON.
:::

### Чтение путей шаблона {#reading-template-paths}

`v['path']` сохраняет тип `VARIANT` даже для объявленного пути; Doris не приводит его автоматически к объявленному типу. Когда нужен объявленный тип, выполните явный CAST; в фильтрах также приводите к объявленному типу, чтобы запрос мог использовать zone maps и индексы этого пути:

```sql
SELECT CAST(v['ts'] AS DATETIME(3)) AS ts,       -- 2024-01-01 10:00:00.123
       CAST(v['ts'] AS STRING)      AS ts_text,  -- 2024-01-01 10:00:00.123000
       VARIANT_TYPE(v['price'])     AS type      -- decimal
FROM tpl_demo
WHERE CAST(v['id'] AS INT) = 123;
```

Schema Template определяет только способ хранения значений. Тот же JSON, вычисленный в запросе, сохраняет разобранный тип:

```sql
SELECT VARIANT_TYPE(PARSE_TO_VARIANT('{"price": 9.999}')['price']);  -- double
```

### Сопоставление шаблонов {#pattern-matching}

По умолчанию имя поля является шаблоном glob (`MATCH_NAME_GLOB`): `*` соответствует любой последовательности символов, включая `.` между вложенными ключами, а `?` соответствует одному символу. Например, `'m*'` соответствует и `m1`, и `m2.x`. Если путь соответствует нескольким полям, используется первое поле в порядке определения:

```sql
CREATE TABLE test_var_pattern (
    id BIGINT NOT NULL,
    v1 VARIANT<
        'enumString*' : STRING,
        'enum*' : ARRAY<TEXT>,
        'ip*' : IPV6
    > NULL
)
PROPERTIES ("replication_num" = "1");

-- enumString1 matches both enumString* and enum*; the first one (STRING) is used.
```

Чтобы сопоставить имя, буквально содержащее `*`, используйте `MATCH_NAME`:

```sql
v1 VARIANT<
    MATCH_NAME 'enumString*' : STRING
> NULL
```

Сопоставленные пути всегда проходят через Subcolumnization и не учитываются в `variant_max_subcolumns_count`, поэтому избегайте шаблонов, соответствующих большому числу путей.

После создания столбца Schema Template изменить нельзя. См. [ALTER TABLE](#alter-table).

## ALTER TABLE {#alter-table}

`ADD COLUMN` (включая пакетное добавление), `MODIFY COLUMN` и `RENAME COLUMN` также требуют, чтобы имя столбца VARIANT верхнего уровня не содержало точек. Например, следующий оператор отклоняется:

```sql
ALTER TABLE example_tbl ADD COLUMN `v.x` VARIANT;
-- ERROR: Cannot use `VARIANT` type column named with a `.` character: v.x
```

`ALTER TABLE` поддерживает:

- `ADD COLUMN` для nullable-столбца VARIANT с Schema Template и свойствами или без них.
- `DROP COLUMN`, `RENAME COLUMN` и `MODIFY COLUMN ... COMMENT '...'`.
- `ADD INDEX` и `DROP INDEX`. Индекс с `field_pattern` можно определить только в `CREATE TABLE`.
- Для столбца без Schema Template: изменение `NOT NULL` на `NULL` и изменение `variant_doc_materialization_min_rows` (для столбца, созданного до версии 4.2 без режима DOC и с `variant_max_subcolumns_count = 0`, можно сохранить только `0`). `MODIFY COLUMN` принимает полное определение столбца; свойство, которое не указано, получает значение по умолчанию (см. [Свойства столбца](#column-properties)), поэтому указывайте каждое свойство, значение которого отличается от значения по умолчанию.

Не поддерживается:

- `ADD COLUMN ... VARIANT NOT NULL`: столбцу `NOT NULL`, добавляемому через `ALTER`, требуется значение по умолчанию, а VARIANT допускает только `DEFAULT NULL`. Столбцы VARIANT с `NOT NULL` определяйте в `CREATE TABLE`.
- Добавление Schema Template к существующему столбцу. Для столбца, у которого уже есть Schema Template, `MODIFY COLUMN` может изменить только комментарий; любое другое изменение завершается ошибкой, даже если указать тот же шаблон.
- Изменение любого свойства, кроме `variant_doc_materialization_min_rows`, изменение `NULL` на `NOT NULL` и преобразование между VARIANT и другими типами.
- `BUILD INDEX` для столбца VARIANT.

Для таких изменений создайте таблицу с новым определением и скопируйте данные с помощью `INSERT INTO ... SELECT`; исходный столбец `STRING` оберните в `PARSE_TO_VARIANT`.

```sql
ALTER TABLE t ADD COLUMN v2 VARIANT NOT NULL;
-- ERROR: Field 'v2' doesn't have a default value

-- v is a VARIANT column without a Schema Template.
ALTER TABLE t MODIFY COLUMN v VARIANT<'id': INT>;
-- ERROR: Can not change variant schema templates
```

## Свойства столбца {#column-properties}

Свойства столбца задаются в `properties(...)` внутри типа VARIANT:

```sql
CREATE TABLE example_table (
  id INT,
  data_variant VARIANT<
      'path_1' : INT,
      'path_2' : STRING,
      properties(
          'variant_max_subcolumns_count' = '2048',
          'variant_doc_hash_shard_count' = '64'
      )
  >
);
```

| Свойство | По умолчанию | ALTER | Описание |
| --- | --- | --- | --- |
| `variant_max_subcolumns_count` | `2048` | Нет | Максимальное число динамических путей, проходящих через Subcolumnization в одном файле данных; сначала выбираются пути с большим числом ненулевых значений, остальные пути сохраняются в разреженных столбцах. `0` означает, что ни один динамический путь не проходит через Subcolumnization и все они хранятся в разреженных столбцах; в столбце, созданном до версии 4.2, `0` по-прежнему означает отсутствие ограничения, см. [Разреженные столбцы](#sparse-columns). Диапазон от 0 до 100000; сохраняйте значение не выше 10000. Значения по умолчанию достаточно для большинства рабочих нагрузок; если действительно требуется гораздо больше подстолбцов, предпочитайте [режим DOC](./variant-workload-guide.md#doc-mode-template). |
| `variant_enable_typed_paths_to_sparse` | `false` | Нет | Начиная с версии 4.2 установить нельзя: определение столбца с этим свойством завершается ошибкой, даже если указано `false`. Пути Schema Template всегда проходят через Subcolumnization и не учитываются в `variant_max_subcolumns_count`. Столбец, для которого до версии 4.2 было установлено `true`, сохраняет это поведение: такие пути учитываются в ограничении и могут храниться в разреженных столбцах. `SHOW CREATE TABLE` до версии 4.2 выводит это свойство для каждого столбца VARIANT без режима DOC; перед выполнением такого вывода удалите его, а `variant_sparse_hash_shard_count` замените на `variant_doc_hash_shard_count`, чтобы сохранить число сегментов. |
| `variant_doc_hash_shard_count` | `1` | Нет | Число физических разреженных столбцов, на которые разреженные пути распределяются по хешу; в режиме DOC — число столбцов, на которые разбивается сохранённый документ. Диапазон от 0 до 1024; `0` трактуется как `1`. До версии 4.2 применялось только в режиме DOC. |
| `variant_max_sparse_column_statistics_size` | `10000` | Нет | Максимальное число разреженных путей в одном файле данных, для которых записывается статистика. После превышения этого значения запрос к пути без статистики не может пропускать разреженные столбцы. Диапазон от 1 до 50000. |
| `variant_enable_doc_mode` | `false` | Нет | Включает режим DOC, который также хранит полный документ. Может задаваться вместе с `variant_max_subcolumns_count`, `variant_doc_materialization_min_rows` и `variant_doc_hash_shard_count`, но не вместе с `variant_max_sparse_column_statistics_size`. |
| `variant_doc_materialization_min_rows` | `0` | Только без Schema Template | Файл данных с меньшим числом строк пропускает Subcolumnization и сохраняет динамические пути в разреженных столбцах (в режиме DOC — только документ); Subcolumnization выполняется после того, как compaction запишет файл данных, достигший порога. `0` выполняет Subcolumnization во время записи. Диапазон от 0 до 1000000000. До версии 4.2 применялось только в режиме DOC. |

Столбец **ALTER** показывает, может ли `ALTER TABLE ... MODIFY COLUMN` изменить свойство; см. [ALTER TABLE](#alter-table). О применении свойств разреженных столбцов и режима DOC см. [Широкие столбцы](#wide-columns).

### Конфигурация BE {#be-configuration}

| Конфигурация | По умолчанию | Описание |
| --- | --- | --- |
| `variant_max_json_key_length` | `255` | Максимальная длина ключа объекта JSON в байтах. Более длинный ключ является ошибкой разбора. Диапазон от 1 до 65535. |
| `variant_throw_exeception_on_invalid_json` | `false` | При `false` текст, отклонённый парсером JSON, сохраняется как строка VARIANT. При `true` это ошибка разбора. |
| `variant_enable_duplicate_json_path_check` | `false` | При `false` повторяющийся ключ в объекте является ошибкой разбора. При `true` сохраняется первое значение, а повторы игнорируются. |

Все три параметра можно изменять во время выполнения. О сообщении об ошибке разбора см. [Ошибки разбора](#parse-errors).

## Индексы Variant {#variant-indexes}

### Выбор индексов {#choosing-indexes}

VARIANT поддерживает BloomFilter и Inverted Index для под-путей.
- Фильтры равенства/IN с высокой кардинальностью: предпочитайте BloomFilter (более разреженный индекс и лучшая производительность записи).
- Поиск с токенизацией, фразами и диапазонами: используйте Inverted Index и задавайте подходящие свойства `parser`/`analyzer`.

Фильтр может использовать индекс или BloomFilter только тогда, когда он сравнивает путь с его сохранённым типом. Числовые пути приводите явно; для сравнения строкового пути со строковым литералом CAST не нужен.

```sql
...
PROPERTIES("replication_num" = "1", "bloom_filter_columns" = "v");

-- Use BloomFilter for equality/IN filters
SELECT * FROM tbl WHERE CAST(v['id'] AS BIGINT) = 12345678;
SELECT * FROM tbl WHERE CAST(v['id'] AS BIGINT) IN (1, 2, 3);
```

После создания Inverted Index на столбце VARIANT все под-пути наследуют одинаковые свойства индекса (например, parser):

```sql
CREATE TABLE IF NOT EXISTS tbl (
    k BIGINT,
    v VARIANT,
    INDEX idx_v(v) USING INVERTED PROPERTIES("parser" = "english")
);

-- All subpaths inherit the english parser
SELECT * FROM tbl WHERE v['id_1'] MATCH 'Doris';
SELECT * FROM tbl WHERE v['id_2'] MATCH 'Apache';
```

### Индексирование по под-пути {#index-by-subpath}

Можно задать свойства индекса для определённых под-путей VARIANT и даже настроить для одного пути токенизированный и нетокенизированный Inverted Index. Для индексов, специфичных для пути, тип пути должен быть объявлен через Schema Template.

```sql
-- Common properties: field_pattern (target path), analyzer, parser, support_phrase, norms, etc.
CREATE TABLE IF NOT EXISTS tbl (
    k BIGINT,
    v VARIANT<'content' : STRING>,
    INDEX idx_tokenized(v) USING INVERTED PROPERTIES("parser" = "english", "field_pattern" = "content"),
    INDEX idx_v(v) USING INVERTED PROPERTIES("field_pattern" = "content")
);

-- v.content has both tokenized and non-tokenized inverted indexes
SELECT * FROM tbl WHERE v['content'] MATCH 'Doris';
SELECT * FROM tbl WHERE v['content'] = 'Doris';
```

Индексирование путей с подстановочными символами:

```sql
CREATE TABLE IF NOT EXISTS tbl (
    k BIGINT,
    v VARIANT<'pattern_*' : STRING>,
    INDEX idx_tokenized(v) USING INVERTED PROPERTIES("parser" = "english", "field_pattern" = "pattern_*"),
    INDEX idx_v(v) USING INVERTED -- global non-tokenized inverted index
);

SELECT * FROM tbl WHERE v['pattern_1'] MATCH 'Doris';
SELECT * FROM tbl WHERE v['pattern_1'] = 'Doris';
```

Начиная с Doris 4.1.5 norms можно отключить с помощью свойства индекса или приведённой ниже конфигурации BE.

Токенизированные индексы на путях VARIANT по умолчанию записывают norms BM25, расходуя один байт на строку и путь, включая строки без значения этого пути. Для путей, используемых только для фильтрации, отключите norms с помощью `"norms" = "false"`. Без `field_pattern` это свойство применяется ко всем под-путям, охватываемым индексом:

```sql
CREATE TABLE IF NOT EXISTS tbl (
    k BIGINT,
    v VARIANT<'body_*' : STRING>,
    INDEX idx_body(v) USING INVERTED PROPERTIES("parser" = "english", "field_pattern" = "body_*", "norms" = "false")
);
```

Отключение norms не влияет на фильтрацию `MATCH`, но `score()` возвращает ошибку при чтении сегмента без norms. Конфигурация BE `inverted_index_skip_norms_for_variant` отключает norms для всех путей VARIANT. Подробнее см. [Длина записи и свойство norms](../../../../table-design/index/inverted-index/scoring.md#record-length-and-the-norms-property).

### Когда индексы не работают {#when-indexes-dont-work}

1. Изменение типа приводит к потере индекса: если тип под-пути меняется на несовместимый (например, INT → JSONB), индекс теряется. Закрепите типы и индексы с помощью Schema Template.
2. Фильтр не сравнивает путь с его сохранённым типом:
   ```sql
   -- An implicit numeric comparison is evaluated row by row and uses no index
   SELECT * FROM tbl WHERE v['id'] = 123456;

   -- CAST to the stored type instead
   SELECT * FROM tbl WHERE CAST(v['id'] AS BIGINT) = 123456;
   ```
   Если `v['id']` хранится как строка, сравнивайте его со строкой: `v['id'] = '123456'`.
3. Неправильно настроенный индекс: индексы применяются к под-путям, а не ко всему столбцу VARIANT.
   ```sql
   -- VARIANT itself cannot be indexed as a whole
   SELECT * FROM tbl WHERE v MATCH 'Doris';

   -- If whole-JSON search is needed, store a duplicate STRING column and index it
   CREATE TABLE IF NOT EXISTS tbl (
       k BIGINT,
       v VARIANT,
       v_str STRING,
       INDEX idx_v_str(v_str) USING INVERTED PROPERTIES("parser" = "english")
   );
   SELECT * FROM tbl WHERE v_str MATCH 'Doris';
   ```
4. Путь хранится в разреженных столбцах: индексу под-пути требуется подстолбец. У пути за пределами `variant_max_subcolumns_count` подстолбца нет, при `variant_max_subcolumns_count = 0` его нет ни у одного динамического пути, а в файле данных с меньшим числом строк, чем `variant_doc_materialization_min_rows`, динамический подстолбец отсутствует, пока compaction не запишет файл, достигший порога. Без подстолбца `SEARCH()` завершается ошибкой "SEARCH index unavailable for Variant field", а `MATCH` переходит к сопоставлению значений построчно, если только `enable_match_without_inverted_index = false`, при котором он завершается ошибкой. Закрепите путь с помощью Schema Template или см. [Разреженные столбцы](#sparse-columns).

## Широкие столбцы {#wide-columns}

Когда загружаемые данные содержат много различных ключей JSON, число подстолбцов, создаваемых Subcolumnization, может быстро расти; в большом масштабе это может привести к разрастанию метаданных, увеличению стоимости записи и слияния и замедлению запросов. Для работы с «широкими столбцами» (слишком большим числом подстолбцов) VARIANT предоставляет два механизма: **разреженные столбцы** и **кодирование DOC**.

Рекомендации по выбору рабочей нагрузки см. в [Руководстве по рабочим нагрузкам Variant](./variant-workload-guide.md). В этом разделе описаны только механизмы и связанные с ними свойства.

При кодировании DOC также применяются `variant_max_subcolumns_count`, `variant_doc_materialization_min_rows` и `variant_doc_hash_shard_count`: извлекается не более `variant_max_subcolumns_count` путей, а остальные пути читаются из документа; `variant_max_sparse_column_statistics_size` нельзя задавать вместе с кодированием DOC. Значения для разных сценариев см. в [Хранение и настройка VARIANT](./variant-storage-tuning.md).

### Разреженные столбцы {#sparse-columns}

**Принцип работы**

- Система ранжирует пути по доле ненулевых значений / разреженности: часто встречающиеся (менее разреженные) пути проходят через Subcolumnization и сохраняются как независимые подстолбцы; остальные редкие (разреженные) пути объединяются и сохраняются в разреженных столбцах. Максимальное число извлекаемых подстолбцов задаётся `variant_max_subcolumns_count`.
- Путь, объявленный в Schema Template, не перемещается в разреженные столбцы (кроме столбца, для которого до версии 4.2 было установлено `variant_enable_typed_paths_to_sparse = true`).
- `variant_max_subcolumns_count = 0` сохраняет каждый динамический путь в разреженных столбцах, а пути Schema Template по-прежнему проходят через Subcolumnization. Используйте это, когда значения в основном читаются целиком. Чтобы каждый динамический путь проходил через Subcolumnization, например для сохранения индексов под-путей, задайте значение выше числа различных путей:
  ```sql
  -- every dynamic path in sparse columns
  v VARIANT<properties('variant_max_subcolumns_count' = '0')>

  -- every dynamic path as a subcolumn, as long as the paths fit in the count
  v VARIANT<properties('variant_max_subcolumns_count' = '2048')>
  ```

  Начиная с версии 4.2 это значение имеет такой смысл во всех операторах создания таблиц, включая `CREATE TABLE`, `CREATE TABLE LIKE` и `CREATE TABLE AS SELECT`. Столбец, созданный до версии 4.2, сохраняет старое поведение: `0` отправляет каждый динамический путь через Subcolumnization без ограничения. `SHOW CREATE TABLE` помечает столбец VARIANT комментарием после его типа: `/* variant_serialize_type = v1 */` для столбца, созданного до версии 4.2, и `/* variant_serialize_type = v2 */` для столбца, созданного начиная с версии 4.2. Комментарий показывает поведение; при выполнении вывода он пропускается, и создаётся новый столбец.

  ```sql
  -- Version 4.1
  CREATE TABLE old_t (
      k INT,
      v VARIANT<properties('variant_max_subcolumns_count' = '0')>
  )
  DUPLICATE KEY(k) DISTRIBUTED BY HASH(k) BUCKETS 1;
  INSERT INTO old_t VALUES (1, PARSE_TO_VARIANT('{"a": 1, "b": "x"}'));

  -- After upgrading to version 4.2: new_t has the same definition as old_t, with a count of 0
  CREATE TABLE new_t LIKE old_t;
  INSERT INTO new_t SELECT * FROM old_t;

  SET describe_extend_variant_column = true;
  DESC old_t;  -- lists the subcolumns v.a and v.b, because old_t keeps the old meaning
  DESC new_t;  -- lists no subcolumn, because new_t stores a and b in sparse columns
  SHOW CREATE TABLE old_t;  -- the type of v is followed by /* variant_serialize_type = v1 */
  SHOW CREATE TABLE new_t;  -- the type of v is followed by /* variant_serialize_type = v2 */
  ```

  Когда `CREATE TABLE AS SELECT` сохраняет вычисленный запросом VARIANT, например `PARSE_TO_VARIANT(...)`, `TRY_PARSE_TO_VARIANT(...)` или под-путь `v['a']`, в новом столбце, столбец получает `variant_max_subcolumns_count` из типа выражения: `0` для `PARSE_TO_VARIANT` и `TRY_PARSE_TO_VARIANT`, поэтому каждый динамический путь сохраняется в разреженных столбцах, а для под-пути берётся значение исходного столбца. Чтобы получить ограничение по умолчанию, приведите выражение к VARIANT; `CAST(PARSE_TO_VARIANT(s) AS VARIANT)` имеет ограничение `2048`.
- Разреженные столбцы поддерживают шардирование: распределение разреженных под-путей по нескольким разреженным столбцам уменьшает накладные расходы на чтение одного столбца и повышает эффективность чтения. Используйте `variant_doc_hash_shard_count`, чтобы указать число физических разреженных столбцов. Версии 4.0 и 4.1 задавали это число с помощью `variant_sparse_hash_shard_count`; начиная с версии 4.2 параметр всё ещё принимается, но его значение игнорируется.

:::caution Откат
После обновления до версии 4.2, как только создан новый столбец VARIANT, откатываться к версии до 4.2 нельзя. Новые столбцы хранятся с поведением 4.2, описанным на этой странице: например, версия до 4.2 читает `0` нового столбца с `variant_max_subcolumns_count = 0` как отсутствие ограничения, а её compaction удаляет пути, хранящиеся только в разреженных столбцах. Следующие операторы создают новые столбцы VARIANT:

- `CREATE TABLE` со столбцом VARIANT.
- `CREATE TABLE LIKE` или повторный запуск вывода `SHOW CREATE TABLE` для таблицы со столбцом VARIANT, в том числе созданной до версии 4.2.
- `CREATE TABLE AS SELECT`, результат которого содержит столбец VARIANT.
- `ALTER TABLE ... ADD COLUMN` для столбца VARIANT, в том числе в таблице, созданной до версии 4.2.
- Асинхронное материализованное представление со столбцом VARIANT.

В `SHOW CREATE TABLE` новый столбец помечается как `/* variant_serialize_type = v2 */`.
:::

**Справочные примечания**

- Если большинство ключей имеют похожие доли ненулевых значений (контраст разреженности мал), трудно определить действительно разреженные пути, поэтому преимущество разреженных столбцов снижается.
- Значение `variant_max_subcolumns_count` по умолчанию равно `2048`, чего уже достаточно для большинства рабочих нагрузок. Не увеличивайте его агрессивно только для предварительного выделения большего числа извлекаемых подстолбцов; если рабочей нагрузке действительно нужен масштабный Subcolumnization, предпочитайте [режим DOC](./variant-workload-guide.md#doc-mode-template). Практическую верхнюю границу по-прежнему рекомендуется держать ≤ `10000`.
- `variant_doc_hash_shard_count` можно приблизительно оценить как «число разреженных путей / 128». Пример: всего ключей JSON ≈ 10,000, `variant_max_subcolumns_count = 2000`, тогда разреженных путей ≈ 8000, поэтому начальным значением `variant_doc_hash_shard_count` может быть примерно `8000/128`.

### Кодирование DOC (режим DOC) {#doc-encoding-doc-mode}

**Принцип работы**

- Пути по-прежнему могут проходить через Subcolumnization для запросов по пути, максимум для `variant_max_subcolumns_count` путей, а исходный JSON дополнительно сохраняется как поле хранения для эффективного возврата полного документа JSON.
- Кодирование DOC поддерживает шардирование: исходный JSON разбивается на несколько столбцов для хранения и собирается обратно при запросе полного JSON. Используйте `variant_doc_hash_shard_count`, чтобы задать число шардов DOC.
- При небольших пакетных записях Subcolumnization можно пропустить и отложить до последующих слияний. Это управляется `variant_doc_materialization_min_rows`. Например, если `variant_doc_materialization_min_rows = 10000`, записи менее чем на 10,000 строк сохраняют только исходный JSON и не запускают Subcolumnization для этого пакета.
- Для сверхшироких рабочих нагрузок режим DOC также является более стабильным выбором, когда масштаб Subcolumnization приближается к десяти тысячам подстолбцов. По сравнению с нетерпеливым Subcolumnization по умолчанию память compaction может уменьшиться примерно на две трети, а пропускная способность загрузки разреженных широких столбцов может вырасти примерно в 5-10 раз.
- Когда столбец `VARIANT` очень широк и запросы часто читают весь документ, режим DOC может повысить производительность `SELECT variant_col` на порядки по сравнению с восстановлением документа из множества подстолбцов.

```sql
CREATE TABLE example_table (
  id INT,
  data_variant VARIANT<
      'path_1' : INT,
      'path_2' : STRING,
      properties(
          'variant_enable_doc_mode' = 'true',
          'variant_doc_materialization_min_rows' = '10000',
          'variant_doc_hash_shard_count' = '64'
      )
  >
);
```

**Справочные примечания**

- Для режима DOC требуется `variant_enable_doc_mode = true`.
- В режиме DOC поля Schema Template ограничены строками, целыми числами, `FLOAT`, `DOUBLE`, `BOOLEAN` и массивами этих типов.
- В режиме DOC `variant_doc_hash_shard_count` можно приблизительно оценить как «общее число ключей JSON / 128».
- Новый столбец режима DOC по умолчанию имеет `1` шард (64 до версии 4.2).
- Начиная с версии 4.2 `variant_doc_hash_shard_count` задаёт число шардов и в режиме DOC, и без него. Вывод `SHOW CREATE TABLE` для таблицы в режиме DOC, созданной до версии 4.2, можно выполнить как есть, и число шардов сохранится; в нём не указывается `variant_max_subcolumns_count`, поэтому новый столбец извлекает не более `2048` путей, если явно не указать это свойство.
- Столбец режима DOC, созданный до версии 4.2, сохраняет старое поведение: как только файл данных достигает порога строк, извлекаются все пути, а число шардов остаётся тем, с которым столбец был создан.

### Поведение при достижении ограничений и рекомендации по настройке {#behavior-at-limits-and-tuning-suggestions}

1. После превышения порога новые пути записываются в разреженные столбцы; слияния Rowset также могут переместить некоторые пути в разреженные столбцы.
2. Система предпочитает сохранять в Subcolumnization пути с более высокой долей ненулевых значений и более высокой частотой доступа.
3. При приближении к 10,000 путей в Subcolumnization требуется мощное оборудование (рекомендуется ≥128G RAM и ≥32C на узел). Если рабочая нагрузка уже близка к этому диапазону, сначала оцените режим DOC.
4. Настройка загрузки: корректно увеличьте клиентский `batch_size` или используйте Group Commit (при необходимости увеличьте `group_commit_interval_ms`/`group_commit_data_bytes`).
5. Если отсечение бакетов не требуется, рассмотрите RANDOM-бакетирование и включение загрузки в один планшет, чтобы уменьшить усиление записи при compaction.
6. Параметры настройки BE: `max_cumu_compaction_threads` (≥8), `vertical_compaction_num_columns_per_group=500` (улучшает вертикальное слияние, но увеличивает потребление памяти), `segment_cache_memory_percentage=20` (повышает эффективность кэша метаданных).
7. Следите за Compaction Score; если он продолжает расти, compaction не успевает — снизьте нагрузку записи.
8. Избегайте больших `SELECT *` для VARIANT; предпочитайте конкретные проекции, например `SELECT v['path']`.

## Просмотр подстолбцов и типов {#inspect-subcolumns-and-types}

Способ 1: используйте [VARIANT_TYPE](../../../sql-functions/scalar-functions/variant-functions/variant-type.md), чтобы построчно получить тип значения или одного пути. Он читает каждую проверяемую строку:

```sql
SELECT VARIANT_TYPE(v), VARIANT_TYPE(v['a']) FROM variant_tbl LIMIT 10;
```

Способ 2: расширенный `DESC` показывает под-пути, извлечённые через Subcolumnization, и их типы хранения:

```sql
SET describe_extend_variant_column = true;
DESC variant_tbl;
```

```sql
DESCRIBE ${table_name} PARTITION ($partition_name);
```

Способ 1 показывает тип каждого значения; способ 2 — способ хранения каждого пути.

## Ограничения {#limitations}

- **Оптимизация широких таблиц**: для широких таблиц с большим числом динамических подстолбцов (например, более 2000 столбцов), созданных типом `VARIANT`, настоятельно рекомендуется включить **формат хранения V3**, указав `"storage_format" = "V3"` в `PROPERTIES` таблицы. Это отделяет метаданные столбцов от Segment Footer, ускоряет открытие файлов и уменьшает накладные расходы на память.
- Ключ JSON по умолчанию может иметь длину не более 255 байт (`variant_max_json_key_length`).
- Столбец VARIANT не может быть ключевым, секционирующим или бакетирующим столбцом и не может быть вложен в другой тип в схеме таблицы (см. [Определение столбца VARIANT](#define-a-variant-column)).
- Вне режима DOC чтение всего столбца VARIANT сканирует все под-пути. Для очень широких столбцов прямой `SELECT variant_col` обычно не рекомендуется, если режим DOC не включён. Если у столбца много под-путей, рассмотрите хранение исходной строки JSON в дополнительном столбце STRING/JSONB для поиска всего объекта с помощью `LIKE`:

```sql
CREATE TABLE example_table (
  id INT,
  data_variant VARIANT
);
SELECT * FROM example_table WHERE data_variant LIKE '%doris%';

-- Better: keep the original JSON string for whole-object matching
CREATE TABLE example_table (
  id INT,
  data_string STRING,
  data_variant VARIANT
);
SELECT * FROM example_table WHERE data_string LIKE '%doris%';
```

## Сравнение с типом JSON {#compared-with-json-type}

- Хранение: JSON хранится как JSONB (ориентированное на строки). VARIANT выполняет Subcolumnization при записи (более высокая степень сжатия и меньший размер).
- Запросы: JSON требует разбора. VARIANT напрямую сканирует столбцы и обычно работает намного быстрее.

Модифицированный ClickBench (43 запроса):
- Хранение: VARIANT экономит около 65% по сравнению с JSON.
- Запросы: VARIANT работает более чем в 8 раз быстрее JSON и близок к заранее определённым статическим столбцам.

## FAQ {#faq}

1. Одинаковы ли `null` в VARIANT и SQL `NULL`?
   - Нет. Вычисленный в запросе JSON `null` является значением VARIANT `null`, а отсутствующий путь — SQL `NULL`. После сохранения значения члены объектов вне массивов со значением `null` удаляются и читаются как SQL `NULL`. См. [Семантика NULL](#null-semantics).
2. Почему `v['a']` возвращает `NULL` после `INSERT INTO t VALUES (1, '{"a": 1}')`?
   - `INSERT` сохраняет строку как строку VARIANT без разбора; то же происходит с `INSERT INTO ... SELECT` из `s3()`, `hdfs()` или другого строкового столбца. Используйте `PARSE_TO_VARIANT('{"a": 1}')` или загрузите данные заданием загрузки, например Stream Load. См. [Запись данных](#write-data).
3. Почему целый документ JSON хранится как строка, хотя он является допустимым JSON?
   - Документ, вероятно, содержит целое вне [-2^63, 2^64 - 1] или число вне диапазона `DOUBLE`. Парсер отклоняет такой документ, и по умолчанию он сохраняется как строка. См. [Ошибки разбора](#parse-errors).
4. Почему мой запрос или индекс не работает?
   - Проверьте, приводите ли вы пути к их сохранённым типам (неявные числовые сравнения не используют индексы), не был ли тип повышен до JSONB из-за конфликтов и не ожидаете ли вы ошибочно, что индекс целого VARIANT работает вместо индекса под-путей.
5. Почему `ORDER BY v['a']` помещает `"10"` после `9`, а `GROUP BY v['a']` разделяет `1` и `"1"`?
   - Сортировка и равенство VARIANT сначала учитывают вид значения: числа сортируются перед строками, и число никогда не равно строке. Когда нужна числовая или лексикографическая семантика, приведите путь к одному типу. См. [Сравнение, группировка и сортировка](#comparison-grouping-and-ordering).
6. Почему `COALESCE(v['a'], 0)` возвращает `0.000000000`, когда `v['a']` — строка, а `IF(..., v['a'], 1)` возвращает `NULL`?
   - При смешивании VARIANT с другим типом значения VARIANT преобразуются в другой тип, то есть в `DECIMAL(38, 9)`, если другая сторона — целое число. Строка вроде `"abc"` не преобразуется и становится `NULL`, поэтому `COALESCE` возвращает `0` как `0.000000000`. Чтобы сохранить результат VARIANT, используйте `COALESCE(v['a'], CAST(0 AS VARIANT))` или приведите `v['a']` к нужному типу.
7. Почему DECIMAL теряет точность при записи в столбец VARIANT?
   - JSON-числа с дробной частью выводятся как `DOUBLE`, а не как `DECIMAL`, поэтому конечные цифры могут теряться. Объявление пути как `DECIMAL` в Schema Template, например `v VARIANT<'num': DECIMAL(9, 3)>`, не полностью помогает, поскольку значение сначала разбирается как `DOUBLE`. Записывайте значение как строку JSON внутри документа, например `PARSE_TO_VARIANT('{"num": "12.345"}')`; тогда оно напрямую преобразуется в `DECIMAL(9, 3)` без потери точности.
