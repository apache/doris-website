## Обзор {#overview}

Тип VARIANT хранит полуструктурированные данные JSON: объекты, массивы, строки, числа, логические значения и `null`. При записи Doris определяет тип каждого пути JSON и выполняет Subcolumnization для часто встречающихся путей, сохраняя их как отдельные подстолбцы в колоночном формате. Запрос к такому пути читает только нужный подстолбец.

:::tip Зачем нужен VARIANT
`VARIANT` хорошо подходит для случаев, когда структура документов со временем меняется, но запросы по-прежнему обращаются к небольшому набору часто используемых путей.

- Для часто используемых путей выполняется Subcolumnization, что позволяет использовать преимущества колоночного хранения, пропуска файлов и векторизованного выполнения.
- Для ключевых путей доступны индексы на уровне пути, полнотекстовый поиск и пропуск данных с помощью разреженного индекса Doris.
- Оптимизации для широких столбцов позволяют эффективно применять автоматическую Subcolumnization при количестве подстолбцов порядка 10k. Когда число путей, участвующих в Subcolumnization, приближается к 10,000, требования к оборудованию быстро растут, поэтому обычно разумнее начинать с режима DOC.

Если вы ещё выбираете между поведением по умолчанию, разреженными столбцами, режимом DOC и Schema Template, начните с [руководства по выбору режима Variant для рабочей нагрузки](./variant-workload-guide.md). Эта страница служит справочником по записи и разбору данных, правилам типов, CAST, семантике NULL и сравнений, ALTER, индексам, ограничениям и настройке.
:::

:::info Версия
Эта страница описывает VARIANT в Doris 5.0.0 и более поздних версиях. Отличия от Doris 4.x, которые с наибольшей вероятностью повлияют на существующий SQL:

- `INSERT` сохраняет строку как строковое значение VARIANT, а не разбирает её как JSON. Это относится и к `INSERT INTO ... SELECT` из табличных функций, таких как `s3()` и `hdfs()`. Для записи JSON-текста используйте `PARSE_TO_VARIANT` в `INSERT`. Задания загрузки, например Stream Load, по-прежнему разбирают JSON.
- Для значений VARIANT целиком поддерживаются `GROUP BY`, `DISTINCT` и операции над множествами. Два значения VARIANT можно сравнивать с помощью `=`, `!=` и `<=>`, а также использовать как ключи соединения, ключи `ORDER BY` и ключи оконных операций.
- `VARIANT_TYPE` возвращает одно имя типа, например `object`, вместо отображения путей в типы.
- К элементам массивов VARIANT можно обращаться по целочисленным индексам, начиная с 1.

Для Doris 4.x см. версию этой страницы для 4.x.
:::

## Быстрый старт {#quick-start}

```sql
CREATE TABLE events (
    id BIGINT,
    v  VARIANT
)
DUPLICATE KEY(id)
DISTRIBUTED BY HASH(id) BUCKETS 1
PROPERTIES ("replication_num" = "1");

-- INSERT keeps a string literal as a VARIANT string, so parse JSON text explicitly.
INSERT INTO events VALUES
    (1, PARSE_TO_VARIANT('{"user": {"id": 42, "name": "alice"}, "tags": ["doris", "sql"], "score": 9.5}')),
    (2, PARSE_TO_VARIANT('{"user": {"id": 7, "name": "bob"}, "score": 3}'));

SELECT id,
       CAST(v['user']['name'] AS STRING) AS name,
       v['tags'][1] AS first_tag
FROM events
WHERE CAST(v['score'] AS DOUBLE) > 5;
```

```text
+------+-------+-----------+
| id   | name  | first_tag |
+------+-------+-----------+
|    1 | alice | doris     |
+------+-------+-----------+
```

- `v['user']['name']` и `v['tags'][1]` возвращают значения `VARIANT`. Индексы массивов начинаются с 1.
- Прежде чем сравнивать значение пути или использовать его в вычислениях, приведите его к конкретному типу с помощью CAST.
- Задания загрузки, например Stream Load, автоматически разбирают JSON-текст. См. [Запись данных](#write-data).

## Определение столбца VARIANT {#define-a-variant-column}

```sql
column_name VARIANT
column_name VARIANT< field_definition [, field_definition ...] >
column_name VARIANT< properties('key' = 'value' [, ...]) >
column_name VARIANT< field_definition [, ...], properties('key' = 'value' [, ...]) >

field_definition:
    [MATCH_NAME | MATCH_NAME_GLOB] 'path_or_pattern' : data_type [COMMENT 'comment']
```

- Список `field_definition` — это [Schema Template](#schema-template). Он фиксирует тип хранения выбранных путей.
- `properties(...)` задаёт свойства хранения на уровне столбца. См. [Свойства столбца](#column-properties).
- Столбец VARIANT может быть `NULL` или `NOT NULL`. Единственное допустимое значение по умолчанию — `NULL`.
- Имя столбца VARIANT верхнего уровня не может содержать точку (`.`), даже если оно заключено в обратные кавычки: например, `` `v.x` VARIANT `` недопустимо. Это ограничение применяется к `CREATE TABLE` и `ALTER TABLE`; оно не ограничивает имена полей JSON внутри значения VARIANT.

```sql
CREATE TABLE IF NOT EXISTS example_tbl (
    k BIGINT,
    v VARIANT<
        'id' : INT,             -- path id is stored as INT
        'message*' : STRING,    -- paths matching message* are stored as STRING
        'tags*' : ARRAY<TEXT>,  -- paths matching tags* are stored as ARRAY<TEXT>
        properties('variant_max_subcolumns_count' = '2048')
    > NULL
)
DUPLICATE KEY(k)
DISTRIBUTED BY HASH(k) BUCKETS 1
PROPERTIES ("replication_num" = "1");
```

Где можно использовать столбец VARIANT в таблице:

| Использование | Поддерживается | Примечания |
| --- | --- | --- |
| Столбец значений в таблицах Duplicate Key, Unique Key и Aggregate Key | Да | В таблице Aggregate Key тип агрегации должен быть `REPLACE` или `REPLACE_IF_NOT_NULL`. |
| Ключевой столбец, столбец партиционирования, столбец распределения по бакетам | Нет | |
| Вложение в другой тип в схеме таблицы (`ARRAY<VARIANT>`, `MAP`, `STRUCT`) | Нет | Результат запроса при этом может иметь тип `ARRAY<VARIANT>`, например при использовании `COLLECT_LIST(v)`. |
| Значение по умолчанию | Только `NULL` | `DEFAULT '{}'` и другие значения по умолчанию, отличные от NULL, отклоняются. |

## Запись данных {#write-data}

`INSERT` и `CAST` сохраняют строку как строковое значение VARIANT. `PARSE_TO_VARIANT`, `TRY_PARSE_TO_VARIANT` и задания загрузки, например Stream Load, разбирают JSON-текст. Примеры загрузки см. в разделе [Загрузка данных VARIANT](../../../../data-operate/import/complex-types/variant.md).

### Ошибки разбора {#parse-errors}

[PARSE_TO_VARIANT](../../../sql-functions/scalar-functions/variant-functions/parse-to-variant.md), [TRY_PARSE_TO_VARIANT](../../../sql-functions/scalar-functions/variant-functions/try-parse-to-variant.md) и задания загрузки используют один и тот же парсер JSON. Задания загрузки обрабатывают ошибки так же, как `TRY_PARSE_TO_VARIANT`:

| Входные данные | `PARSE_TO_VARIANT` | `TRY_PARSE_TO_VARIANT` и задания загрузки |
| --- | --- | --- |
| Корректный JSON | Результат разбора | Результат разбора |
| Текст, который не является корректным JSON, например `hello` или `{"id":` | Сохраняется как строковое значение VARIANT | Сохраняется как строковое значение VARIANT |
| JSON, содержащий целое число вне диапазона [-2^63, 2^64 - 1] или число вне диапазона `DOUBLE`, например `{"a": 1, "n": 100000000000000000000}` | Весь текст сохраняется как строковое значение VARIANT, поэтому `v['a']` возвращает `NULL` | Весь текст сохраняется как строковое значение VARIANT |
| Пустая строка | Пустой объект `{}` | Пустой объект `{}` |
| Вложенность глубже 128 уровней | Ошибка | SQL `NULL` |
| Ключ объекта длиннее `variant_max_json_key_length` байт (настройка BE, по умолчанию 255) | Ошибка | SQL `NULL` |
| Повторяющиеся ключи в одном объекте | Ошибка | SQL `NULL` |
| Строка с некорректной кодировкой UTF-8 | Ошибка | SQL `NULL` |

Документ с настолько глубокой вложенностью, что его отклоняет сам парсер JSON (около 1,000 уровней), считается некорректным JSON и поэтому сохраняется как строка.

Эти правила изменяются двумя настройками BE:

- `variant_throw_exeception_on_invalid_json` (по умолчанию `false`): при значении `true` текст, отклонённый парсером, в том числе JSON с числами вне допустимого диапазона, вызывает ошибку в `PARSE_TO_VARIANT` и возвращает SQL `NULL` в `TRY_PARSE_TO_VARIANT` и заданиях загрузки, а не сохраняется как строковое значение VARIANT.
- `variant_enable_duplicate_json_path_check` (по умолчанию `false`): при значении `true` для повторяющегося ключа объекта сохраняется первое значение вместо возникновения ошибки. Эта настройка также предотвращает сбой записи, когда ключ с точкой повторяет вложенный путь; сохраняется только одно из значений.

Чтобы сохранить структуру документа с целыми числами вне допустимого диапазона, преобразуйте его через JSON: `CAST(CAST(text AS JSON) AS VARIANT)`. Целые числа длиной до 38 цифр остаются точными числами, более длинные целые числа в пределах диапазона `LARGEINT` становятся строками, а ещё большие — `DOUBLE`. Использование `PARSE_TO_VARIANT(CAST(text AS JSON))` не помогает, поскольку JSON-текст разбирается повторно.

```sql
SELECT VARIANT_TYPE(PARSE_TO_VARIANT('{"id": 1}')) AS valid_json,    -- object
       VARIANT_TYPE(PARSE_TO_VARIANT('{"id":'))    AS invalid_json,  -- string
       VARIANT_TYPE(CAST('{"id": 1}' AS VARIANT))  AS string_cast;   -- string
```

### Что сохраняется при записи {#what-storage-keeps}

При записи значения в таблицу оно нормализуется. Прочитанное значение может отличаться от значения, вычисленного до записи:

| До записи | При чтении из таблицы |
| --- | --- |
| Поле объекта со значением JSON `null`, например `{"a": null, "b": 1}` | Поле удаляется: `{"b":1}`. `v['a']` возвращает SQL `NULL`. |
| Поле объекта, значение которого — пустой объект или массив либо объект, ставший пустым после применения этих правил, например `{"a": {}, "b": [], "c": {"d": null}}` | Удаляется: `{}` |
| Поле объекта, массив которого содержит только `null`, например `{"p": [null, null], "q": 1}` | Может быть удалено: `{"q":1}` |
| Значения внутри массивов, например `{"arr": [{"a": null}, {}, [], null]}` | Сохраняются без изменений. `v['arr'][1]['a']` — это значение VARIANT `null`. |
| Корневое значение JSON `null`, например `PARSE_TO_VARIANT('null')` | Пустой объект `{}` |
| Корневой пустой массив `[]` или пустой объект `{}` | Сохраняется |
| Значения `DATE` и `DATETIME` в корне, например `CAST(date_col AS VARIANT)`, или в пути, который также содержит значения других типов | Сохраняются в текстовом виде, поэтому при чтении возвращаются как строки. В пути объекта, который содержит только даты, они сохраняют свой тип. |
| Логические значения и числа в одном пути | Логические значения могут возвращаться как `1` или `0` в зависимости от порядка значений в рамках одной записи и от compaction |
| Ключ, содержащий точку, например `{"a.b": 1}` | Сохраняется как вложенный путь: `{"a":{"b":1}}`. И `v['a.b']`, и `v['a']['b']` возвращают `1`. Документ, содержащий одновременно ключ `a.b` и ключ `b` внутри `a`, приводит к сбою всего INSERT или задания загрузки, если `variant_enable_duplicate_json_path_check` не имеет значения `true`. |
| Ключи объектов | Возвращаются в порядке байтов |

Эти правила зависят от других строк, записываемых вместе, и от режима DOC, поэтому не следует рассчитывать на то, что значения `null` или пустые контейнеры сохранятся при записи. Пути, объявленные в Schema Template, вместо этого преобразуются к объявленному типу; см. [Schema Template](#schema-template).

## Определение типов и конфликты типов {#type-inference-and-type-conflicts}

Без Schema Template Doris определяет тип каждого значения при разборе JSON. `VARIANT_TYPE` возвращает этот тип:

| Значение JSON | Тип |
| --- | --- |
| Целое число в пределах диапазона `BIGINT` | `tinyint`, `smallint`, `int` или `bigint` — наименьший подходящий тип |
| Целое число выше диапазона `BIGINT`, но не больше 18446744073709551615 | `decimal` |
| Число с дробной частью или экспонентой | `double` |
| Целое число вне диапазона [-2^63, 2^64 - 1] или число вне диапазона `DOUBLE` | Не считается числом: весь текст считается некорректным JSON (см. [Ошибки разбора](#parse-errors)) |
| Строка | `string` |
| `true`, `false` | `bool` |
| `null` | `null` |
| Массив, объект | `array`, `object` |

При хранении данных каждому пути назначается один тип хранения:

- Целые числа хранятся как `BIGINT` или как `LARGEINT`, если этого требует значение. Числа с плавающей точкой хранятся как `DOUBLE`, десятичные числа — как `DECIMAL`, строки — как `STRING`, логические значения — как `BOOLEAN`, а массивы скалярных значений — как `ARRAY<T>`.
- Массивы объектов, вложенные массивы и пути со значениями разных типов, например целыми числами и числами с плавающей точкой, числами и строками или скалярными значениями и массивами, хранятся как `JSONB` (отображается как `json` в выводе `DESC`). Массивы с конфликтующими типами элементов становятся `ARRAY<JSONB>`.

```sql
{"a" : 12345678}
{"a" : "HelloWorld"}
-- a is stored as JSONB
```

Путь с типом `JSONB` сохраняет все значения, но теряет типизированное хранение: индексы и пропуск данных с учётом типа больше не применяются к этому пути. Логические значения — особый случай: если первое значение пути логическое, а последующие значения — числа, путь может храниться как число, а логические значения будут возвращаться как `1` или `0`. Если пути нужен стабильный тип, объявите его в Schema Template.

`VARIANT_TYPE` сообщает тип каждого значения, поэтому целое число, прочитанное из пути с типом `BIGINT`, всё ещё может иметь тип `tinyint`. Чтобы увидеть тип хранения каждого пути, выполните `SET describe_extend_variant_column = true;`, а затем `DESC table_name;`. См. [Просмотр подстолбцов и типов](#inspect-subcolumns-and-types).

## Доступ к путям и вывод {#access-paths-and-output}

- `v['key']` и `v['a']['b']` читают поля объекта. `v['arr'][1]` читает элемент массива: индексы начинаются с 1, а `-1` обозначает последний элемент. [ELEMENT_AT](../../../sql-functions/scalar-functions/variant-functions/element-at.md) работает аналогично.
- Результат имеет тип `VARIANT`. Отсутствующий ключ, индекс `0`, индекс вне допустимого диапазона, строковый ключ для массива, целочисленный индекс для объекта и ключ для скалярного значения возвращают SQL `NULL`.
- В вычисленном значении ключ, содержащий точку, считается единым ключом: `v['a.b']` читает ключ `a.b`, а `v['a']['b']` — ключ `b` внутри `a`. При хранении это различие не сохраняется; см. [Что сохраняется при записи](#what-storage-keeps).
- Путь не применяется автоматически к элементам массива. Для `{"a": [{"b": 1}]}` выражение `v['a']['b']` возвращает `NULL`; используйте `v['a'][1]['b']`.

```sql
SELECT v['user']['id']      AS id,       -- 42
       v['tags'][-1]        AS last_tag, -- sql
       v['user']['missing'] AS missing   -- NULL
FROM events
WHERE id = 1;
```

В типичных сценариях путь приводят с помощью CAST к типу, необходимому запросу:

```sql
SELECT * FROM tbl WHERE ARRAY_CONTAINS(CAST(v['tags'] AS ARRAY<TEXT>), 'Doris');
SELECT * FROM tbl WHERE CAST(v['date'] AS DATE) = '2021-01-02';
SELECT * FROM tbl WHERE v['bool'];                -- implicit CAST to BOOLEAN
SELECT * FROM tbl WHERE v['str'] MATCH 'Doris';   -- uses an inverted index on the path
```

Чтение значения VARIANT целиком возвращает JSON-текст. Ключи объектов возвращаются в порядке байтов, без пробельных символов, поэтому текст не совпадает с исходным побайтово. Корневое строковое значение возвращается без кавычек.

```sql
CREATE TABLE variant_tbl (k INT, v VARIANT)
DUPLICATE KEY(k)
DISTRIBUTED BY HASH(k) BUCKETS 1
PROPERTIES ("replication_num" = "1");

INSERT INTO variant_tbl VALUES (1, PARSE_TO_VARIANT('{ "b": 2, "a": 1, "c": { "y": 20, "x": 10 } }'));

SELECT v FROM variant_tbl WHERE k = 1;
-- {"a":1,"b":2,"c":{"x":10,"y":20}}
```

## CAST {#cast}

### CAST в VARIANT {#cast-to-variant}

| Исходный тип | Результат |
| --- | --- |
| `CHAR`, `VARCHAR`, `STRING` | Строковое значение VARIANT. JSON-текст не разбирается. Строка должна иметь корректную кодировку UTF-8, иначе CAST завершается ошибкой. |
| `BOOLEAN` | Логическое значение. |
| `TINYINT`, `SMALLINT`, `INT`, `BIGINT` | Целое число. |
| `LARGEINT` | Десятичное число. Значение, модуль которого превышает 10^38 - 1, становится строкой. |
| `FLOAT`, `DOUBLE` | Число с плавающей точкой. |
| `DECIMALV2`, `DECIMAL(p, s)` с `p <= 38` | Десятичное число. |
| `DATE`, `DATETIME(p)`, `TIMESTAMP_NS` | Дата или временная метка без часового пояса. |
| `IPV4`, `IPV6` | Строка с текстовым представлением значения. |
| `JSON` / `JSONB` | Та же структура. Значение, которое VARIANT не может хранить, например число `DECIMAL256`, или повторяющиеся ключи в объекте приводят к ошибке CAST. |
| `ARRAY<T>` | Массив; каждый элемент преобразуется. `T` должен быть `VARIANT` или одним из типов в этой таблице. |
| `MAP`, `STRUCT`, `TIME`, `TIMESTAMPTZ`, `VARBINARY` и другие типы | Не поддерживаются. Инструкция завершается ошибкой. |

Исходное значение также должно быть корректным для собственного типа; некорректное значение отклоняется, а не исправляется. CAST никогда не разбирает строку: `CAST('{"id": 1}' AS VARIANT)` — это строка `{"id": 1}`. Для разбора JSON-текста используйте `PARSE_TO_VARIANT`.

### CAST из VARIANT {#cast-from-variant}

| Целевой тип | Результат |
| --- | --- |
| `BOOLEAN` | Логические значения без изменений. Числа становятся `true`, если они не равны нулю. Строки преобразуются так же, как при `CAST(string AS BOOLEAN)`. |
| `TINYINT`, `SMALLINT`, `INT`, `BIGINT`, `LARGEINT` | Целые числа. Дробная часть десятичного числа или числа с плавающей точкой отбрасывается (`1.5` становится `1`). Логические значения становятся `1` или `0`. Числовые строки, например `"123"`, преобразуются. |
| `FLOAT`, `DOUBLE`, `DECIMAL(p, s)` | Числа и числовые строки. `DECIMAL` округляет до масштаба `s`. Значение, слишком большое для `FLOAT`, становится `Infinity`. |
| `DATE`, `DATETIME(p)`, `TIMESTAMP_NS` | Значения даты и времени, строки в формате даты или времени и числа, например `20240102`. |
| `TIMESTAMPTZ(p)` | Значения даты и времени и строки в формате даты или времени. |
| `IPV4`, `IPV6` | Строки в формате IP-адреса. |
| `CHAR`, `VARCHAR`, `STRING` | Корневое строковое значение возвращается как есть, без кавычек. Объекты и массивы возвращаются как JSON-текст. Другие скалярные значения форматируются так же, как соответствующий тип SQL: корневое логическое значение становится `1` или `0`, значение `DATETIME` имеет шесть знаков дробной части секунд, а значение `TIMESTAMP_NS` — девять. Значение VARIANT `null` становится строкой `null`. |
| `JSON` / `JSONB` | Та же структура. Значения без аналога в JSON, например даты и временные метки, становятся строками JSON; временная метка с часовым поясом форматируется в часовом поясе сеанса. |
| `ARRAY<T>` | Массив, преобразуемый поэлементно; элемент, который невозможно преобразовать, становится `NULL`. Строка, содержащая массив JSON, например `"[1, 2]"`, также преобразуется. Другие значения возвращают `NULL`. |
| `MAP`, `STRUCT`, `TIME` и другие типы | Не поддерживаются. Инструкция завершается ошибкой. |

Значение, которое невозможно преобразовать к целевому типу, возвращает SQL `NULL`, в том числе при включённой настройке `enable_strict_cast`. Исключение — значение, для типа которого вообще не предусмотрено преобразование к целевому типу, например число в `TIMESTAMPTZ`, `IPV4` или `IPV6`, либо дата или временная метка в `BOOLEAN`: в таком случае инструкция завершается ошибкой.

```sql
SELECT CAST(PARSE_TO_VARIANT('"123"') AS INT)      AS from_string,   -- 123
       CAST(PARSE_TO_VARIANT('"abc"') AS INT)      AS not_a_number,  -- NULL
       CAST(PARSE_TO_VARIANT('1.5') AS INT)        AS truncated,     -- 1
       CAST(PARSE_TO_VARIANT('300') AS TINYINT)    AS overflow,      -- NULL
       CAST(PARSE_TO_VARIANT('{"a": 1}') AS INT)   AS from_object,   -- NULL
       CAST(PARSE_TO_VARIANT('[1, "2", null, "x"]') AS ARRAY<INT>) AS arr;  -- [1, 2, null, null]

SELECT CAST(PARSE_TO_VARIANT('true') AS STRING)        AS bool_root,     -- 1
       CAST(PARSE_TO_VARIANT('{"b": true}') AS STRING) AS object_text,   -- {"b":true}
       CAST(PARSE_TO_VARIANT('"abc"') AS STRING)       AS string_root,   -- abc
       CAST(PARSE_TO_VARIANT('null') AS STRING)        AS variant_null;  -- null
```

### Десятичные значения и значения даты и времени {#decimal-and-datetime-values}

При преобразовании этих типов в VARIANT:

| Тип Doris | Поведение |
| --- | --- |
| Устаревший `DECIMALV2` | Точность до 27 и масштаб до 9 сохраняются без потерь. |
| `DECIMAL(p, s)` | При `1 <= p <= 38` и `0 <= s <= p` значения сохраняются без потерь. Десятичные числа с точностью больше 38 не поддерживаются. |
| `DATE` | Календарная дата без времени и часового пояса. |
| `DATETIME(p)` | `0 <= p <= 6`, без поправки на часовой пояс. |
| `TIMESTAMP_NS` | Наносекундная точность без поправки на часовой пояс; значения должны находиться в диапазоне TIMESTAMP_NS. |
| `TIMESTAMPTZ(p)` | Не поддерживается ни при CAST, ни в качестве типа пути Schema Template. |
| `TIME` | Не поддерживается. |

## Семантика NULL {#null-semantics}

У VARIANT есть два вида null:

- **SQL `NULL`** означает отсутствие значения. Он возникает из значения столбца `NULL`, отсутствующего пути, например `v['no_such_key']`, или неудачного CAST.
- **VARIANT `null`** — это значение: литерал JSON `null`, например `PARSE_TO_VARIANT('null')` или элемент массива `null`. Для него `VARIANT_TYPE` возвращает `null`.

| Операция | SQL `NULL` | VARIANT `null` |
| --- | --- | --- |
| `v IS NULL` | `true` | `false` |
| `COALESCE(v, x)`, `IFNULL(v, x)`, где `x` имеет тип VARIANT | Возвращает `x` | Возвращает значение VARIANT `null` |
| `COUNT(v)` | Не учитывается | Учитывается |
| `GROUP BY v`, `DISTINCT` | Все значения SQL `NULL` образуют одну группу | Все значения VARIANT `null` образуют другую группу |
| `v = x`, соединение по равенству | Никогда не совпадает | Совпадает с другим значением VARIANT `null` |
| `ORDER BY v` | Размещается согласно `NULLS FIRST` или `NULLS LAST` | При сортировке по возрастанию располагается перед всеми остальными значениями, отличными от NULL |
| `CAST(v AS STRING)` | SQL `NULL` | Строка `null` |

После сохранения значения поле объекта со значением `null` вне массивов удаляется, поэтому его чтение возвращает SQL `NULL`, а корневое значение `null` возвращается как `{}` (см. [Что сохраняется при записи](#what-storage-keeps)). Поэтому для сохранённых данных выражение `v['a'] IS NULL` не позволяет отличить отсутствующее поле от поля со значением `null`.

## Сравнение, группировка и упорядочивание {#comparison-grouping-and-ordering}

Значения VARIANT сравниваются по логическому значению, а не по тексту или физическому представлению. Равенство, хеширование (`GROUP BY`, `DISTINCT`, соединения) и упорядочивание (`ORDER BY`, ключи оконных операций) используют одинаковые правила, поэтому равные значения всегда попадают в одну группу и имеют одинаковую позицию при сортировке.

### Поддерживаемые операции {#supported-operations}

| Операция над значениями VARIANT | Поддержка | Примечания |
| --- | --- | --- |
| `=`, `!=`, `<=>` между двумя значениями VARIANT или с литералом `NULL` | Поддерживается | Включая вложенные пути, например `v['a'] = w['a']`. |
| Соединение по равенству, semi join и anti join, подзапросы `IN` и `NOT IN` | Поддерживается | Для ключей соединения VARIANT не создаются runtime filters. |
| `GROUP BY`, `DISTINCT`, `COUNT(DISTINCT ...)`, `UNION`, `INTERSECT`, `EXCEPT` | Поддерживается | |
| `ORDER BY`, `ORDER BY ... LIMIT` | Поддерживается | |
| `PARTITION BY` и `ORDER BY` в оконных операциях | Поддерживается | |
| `COUNT(v)`, `COLLECT_LIST(v)`, `ARRAY_AGG(v)` | Поддерживается | |
| `IF`, `CASE`, `IFNULL`, `COALESCE` | Поддерживается | При смешивании VARIANT с другим типом значения VARIANT преобразуются к этому типу (`DECIMAL(38, 9)`, если это целочисленный тип); значения, которые невозможно преобразовать, становятся `NULL`. |
| `CAST(v AS ARRAY<VARIANT>)`, `EXPLODE_VARIANT_ARRAY`, `EXPLODE` и `EXPLODE_OUTER` для `ARRAY<VARIANT>` | Поддерживается | |
| `<`, `<=`, `>`, `>=`, `BETWEEN` между значениями VARIANT | Не поддерживается | Сначала приведите к конкретному типу с помощью CAST. |
| Сравнение значения VARIANT целиком со значением другого типа, например `v = 1` | Не поддерживается | Вложенный путь преобразуется неявно: `v['a'] = 1` работает. |
| Список `IN`, содержащий значения VARIANT, например `v IN (PARSE_TO_VARIANT('1'))` | Не поддерживается | `v IN ('a', 'b')` со значениями других типов работает благодаря неявному преобразованию. |
| `MIN`, `MAX` | Не поддерживается | Сначала приведите вложенный путь с помощью CAST. |
| `ARRAY(...)`, `MAP(...)`, `NAMED_STRUCT(...)` с аргументами VARIANT | Не поддерживается | |

### Равенство {#equality}

- **Числа.** Целое число, десятичное число с нулевой дробной частью и число с плавающей точкой, имеющее целое значение, равны: `1`, `1.0` и `1.00` — одно значение. Конечные нули десятичного числа не имеют значения, а `-0.0` равно `0`. Десятичное число и число с плавающей точкой, имеющие дробную часть, никогда не равны: `DECIMAL 1.5` не равно `DOUBLE 1.5`. Числа JSON с дробной частью разбираются как `DOUBLE`; десятичные числа появляются при CAST, в путях Schema Template и при разборе целых чисел, слишком больших для `BIGINT`.
- **Значения разных видов никогда не равны.** Число `1`, строка `"1"` и `true` — три разных значения. Значение `DATE` не равно строке `"2024-01-01"`, а временная метка без часового пояса не равна временной метке с часовым поясом.
- **Строки** равны только при совпадении их байтов. Сравнение учитывает регистр.
- **Объекты** равны, если у них одинаковые ключи с равными значениями. Порядок ключей не имеет значения.
- **Массивы** равны, если у них одинаковая длина и равные элементы в одинаковом порядке.
- Значение VARIANT `null` равно другому значению VARIANT `null`. Для SQL `NULL` действуют правила SQL.

```sql
SELECT PARSE_TO_VARIANT('1') = PARSE_TO_VARIANT('1.0')                             AS int_double,  -- 1
       PARSE_TO_VARIANT('1.5') = CAST(CAST(1.5 AS DECIMAL(10, 2)) AS VARIANT)       AS dbl_dec,     -- 0
       PARSE_TO_VARIANT('1') = PARSE_TO_VARIANT('"1"')                             AS num_str,     -- 0
       PARSE_TO_VARIANT('{"a": 1, "b": 2}') = PARSE_TO_VARIANT('{"b": 2, "a": 1}') AS obj,         -- 1
       PARSE_TO_VARIANT('[1, 2]') = PARSE_TO_VARIANT('[2, 1]')                     AS arr;         -- 0
```

### Упорядочивание {#ordering}

`ORDER BY` для значений VARIANT использует единый полный порядок. Значения разных видов сначала упорядочиваются по виду:

```text
null < boolean < number < string < binary < date < timestamp with time zone
     < timestamp without time zone < time < UUID < object < array
```

Двоичные значения, значения времени и UUID нельзя получить разбором JSON или с помощью CAST в Doris; они могут появиться только в данных VARIANT, записанных другими системами, например в файлах Parquet со столбцами VARIANT.

Внутри одного вида:

- **Логические значения:** `false` перед `true`.
- **Числа:** целые числа (`INT`, `BIGINT` и т. д.), десятичные числа (`DECIMAL`) и числа с плавающей точкой (`FLOAT`, `DOUBLE`) сортируются по числовому значению. `INT 1`, `FLOAT/DOUBLE 1.0` и `DECIMAL 1.00` равны и занимают одинаковую позицию при сортировке; конечные нули десятичного числа не имеют значения. Для равных нецелых значений десятичное число идёт первым: `DECIMAL 1.5` предшествует `FLOAT/DOUBLE 1.5`, и как значения VARIANT они не равны. Точность чисел с плавающей точкой может влиять на порядок: `DOUBLE 0.1` немного больше `DECIMAL 0.1`. Отрицательная бесконечность располагается первой; положительная бесконечность, а затем NaN — последними.
- **Строки:** по байтам UTF-8. Прописные буквы идут перед строчными, а `"10"` — перед `"9"`.
- **Даты и временные метки:** в хронологическом порядке. Любая дата идёт перед любой временной меткой.
- **Объекты:** поэлементно в порядке ключей: сначала сравниваются наименьшие ключи, затем их значения, затем следующие ключи. Объект, элементы которого являются префиксом другого объекта, идёт первым, поэтому `{"a":1}` < `{"a":1,"b":2}` < `{"b":0}`.
- **Массивы:** поэлементно; префикс идёт первым, поэтому `[]` < `[null]` < `[1]` < `[1,2]`.

SQL `NULL` размещается согласно `NULLS FIRST` или `NULLS LAST`.

```sql
SELECT v, VARIANT_TYPE(v) AS type
FROM (
    SELECT PARSE_TO_VARIANT('[1, 2]') AS v UNION ALL
    SELECT PARSE_TO_VARIANT('{"a": 1}')    UNION ALL
    SELECT PARSE_TO_VARIANT('"9"')         UNION ALL
    SELECT PARSE_TO_VARIANT('"10"')        UNION ALL
    SELECT PARSE_TO_VARIANT('10')          UNION ALL
    SELECT PARSE_TO_VARIANT('9.5')         UNION ALL
    SELECT PARSE_TO_VARIANT('true')        UNION ALL
    SELECT PARSE_TO_VARIANT('null')        UNION ALL
    SELECT NULL
) t
ORDER BY v;
```

```text
+---------+---------+
| v       | type    |
+---------+---------+
| NULL    | NULL    |
| null    | null    |
| true    | bool    |
| 9.5     | double  |
| 10      | tinyint |
| 10      | string  |
| 9       | string  |
| {"a":1} | object  |
| [1,2]   | array   |
+---------+---------+
```

### Сравнение в конкретном типе и сравнение VARIANT {#typed-comparison-and-variant-comparison}

Операнды определяют, используются ли при сравнении правила VARIANT или правила конкретного типа. Рассмотрим путь `a` со значениями `1`, `1.0` и `"1"`:

| Выражение | Тип при сравнении | Результат |
| --- | --- | --- |
| `v['a'] = 1` | `DECIMAL(38, 9)` благодаря неявному CAST для `v['a']` | Совпадают все три значения |
| `v['a'] = CAST(1 AS VARIANT)`, `v['a'] = w['a']` | VARIANT | Совпадают `1` и `1.0`, но не `"1"` |
| `GROUP BY v['a']` | VARIANT | `1` и `1.0` образуют одну группу, `"1"` — другую |
| `GROUP BY CAST(v['a'] AS STRING)` | `STRING` | Одна группа, `1` |
| `ORDER BY v['a']` | VARIANT | Сначала числа, затем строки |
| `ORDER BY CAST(v['a'] AS INT)` | `INT` | Числовой порядок; значения, которые невозможно преобразовать, становятся `NULL` |

### Примечания {#notes}

- **Затраты.** Ключи VARIANT хешируются и сравниваются по логическому значению. В тесте на 44 миллионах строк `GROUP BY`, сортировка и соединения по ключу VARIANT занимали в 1.2–3.7 раза больше времени, чем те же операции над `CAST(v['path'] AS <type>)`. Если у пути один известный тип, используйте CAST.
- **Результаты определяются сохранёнными значениями.** Нормализации из раздела [Что сохраняется при записи](#what-storage-keeps) выполняются до сравнения: поле, имевшее значение `null`, отсутствует, корневое значение `DATE` сравнивается как строка, а логические значения, смешанные с числами в одном пути, могут возвращаться как `1` или `0`. Объявляйте пути, для которых важен тип, в Schema Template.
- **Смешанные типы сортируются по виду, а не по значению.** Если путь содержит и числа, и числовые строки, `ORDER BY v['a']` размещает все числа перед всеми строками, а строки упорядочивает по байтам. Для числового или лексикографического порядка приведите значения к одному типу с помощью CAST.
- **Одинаково отображаемые значения могут различаться.** В результате `GROUP BY` число `1` и строка `"1"` отображаются одинаково, но образуют две группы. Чтобы увидеть разницу, используйте `VARIANT_TYPE`.
- Порядок между видами определяется Doris, чтобы результаты были детерминированными. Он не является частью стандарта JSON и может отличаться от порядка в других системах.
- Внутренний хеш значения VARIANT — деталь реализации, а не стабильная контрольная сумма для пользователя.

## Schema Template {#schema-template}

Schema Template объявляет тип хранения выбранных путей. Объявляйте только ключевые пути, которым нужен стабильный тип или отдельный индекс; остальная часть документа остаётся динамической.

```sql
CREATE TABLE test_var_schema (
    id BIGINT NOT NULL,
    v1 VARIANT<
        'large_int_val': LARGEINT,
        'string_val': STRING,
        'decimal_val': DECIMAL(38, 9),
        'datetime_val': DATETIME,
        'ip_val': IPV4
    > NULL
)
PROPERTIES ("replication_num" = "1");
```

Поле шаблона может использовать следующие типы:

- Числа: `TINYINT`, `SMALLINT`, `INT`, `BIGINT`, `LARGEINT`, `FLOAT`, `DOUBLE` и `DECIMAL(p, s)` с `p <= 38`
- `STRING` (или `TEXT`)
- `BOOLEAN`
- `DATE`, `DATETIME(p)`, `TIMESTAMP_NS`
- `IPV4`, `IPV6`
- `ARRAY<T>`, где `T` — один из перечисленных выше типов (только одно измерение)

### Запись в пути шаблона {#writing-to-template-paths}

В объявленном пути каждое значение преобразуется к объявленному типу по нестрогим правилам CAST. Значение, которое невозможно преобразовать, сохраняется как `NULL`, поэтому при чтении путь отсутствует; остальная часть строки при этом записывается. Преобразование может изменить значение:

```sql
CREATE TABLE tpl_demo (
    k INT,
    v VARIANT<'id': INT, 'price': DECIMAL(10, 2), 'ts': DATETIME(3)>
)
DUPLICATE KEY(k)
DISTRIBUTED BY HASH(k) BUCKETS 1
PROPERTIES ("replication_num" = "1");

INSERT INTO tpl_demo VALUES
    (1, PARSE_TO_VARIANT('{"id": "123", "price": 9.999, "ts": "2024-01-01 10:00:00.123456"}')),
    (2, PARSE_TO_VARIANT('{"id": "abc", "price": "x", "ts": "not a time"}')),
    (3, PARSE_TO_VARIANT('{"id": 1.7}'));

SELECT k, v FROM tpl_demo ORDER BY k;
```

```text
+------+------------------------------------------------------------+
| k    | v                                                          |
+------+------------------------------------------------------------+
|    1 | {"id":123,"price":10.00,"ts":"2024-01-01 10:00:00.123000"} |
|    2 | {}                                                         |
|    3 | {"id":1}                                                   |
+------+------------------------------------------------------------+
```

- `"123"` становится `123`, `1.7` усекается до `1`, `9.999` округляется до `10.00`, а временная метка сохраняет объявленную точность (миллисекунды); её текстовое представление всегда содержит шесть знаков дробной части секунд.
- `"abc"`, `"x"` и `"not a time"` невозможно преобразовать, поэтому они удаляются.
- Число JSON с дробной частью перед преобразованием разбирается как `DOUBLE`, поэтому путь `DECIMAL` может потерять точность. Записывайте такие значения как строки JSON, чтобы сохранить каждую цифру (см. [Частые вопросы](#faq)).
- Значения дат и IP-адресов должны быть строками JSON: `{"date": 2020-01-01}` и `{"ip": 127.0.0.1}` не являются корректным JSON; записывайте `{"date": "2020-01-01"}` и `{"ip": "127.0.0.1"}`.

:::caution
Значение преобразуется только в том случае, если для его типа JSON предусмотрено преобразование к объявленному типу. Число JSON в пути `IPV4` или `IPV6` приводит к сбою всей записи. Если в рамках одной записи в пути `DATE`, `DATETIME`, `IPV4` или `IPV6` смешаны строки и числа JSON, даже корректные значения этого пути могут быть удалены. Записывайте значения таких путей как строки JSON.
:::

### Чтение путей шаблона {#reading-template-paths}

`v['path']` сохраняет тип `VARIANT` даже для объявленного пути; Doris не приводит его к объявленному типу автоматически. Явно применяйте CAST, когда нужен объявленный тип, и приводите к нему значения в фильтрах, чтобы запрос мог использовать zone maps и индексы этого пути:

```sql
SELECT CAST(v['ts'] AS DATETIME(3)) AS ts,       -- 2024-01-01 10:00:00.123
       CAST(v['ts'] AS STRING)      AS ts_text,  -- 2024-01-01 10:00:00.123000
       VARIANT_TYPE(v['price'])     AS type      -- decimal
FROM tpl_demo
WHERE CAST(v['id'] AS INT) = 123;
```

Schema Template определяет только способ хранения значений. Тот же JSON, вычисленный в запросе, сохраняет тип, полученный при разборе:

```sql
SELECT VARIANT_TYPE(PARSE_TO_VARIANT('{"price": 9.999}')['price']);  -- double
```

### Сопоставление с шаблонами {#pattern-matching}

По умолчанию имя поля является glob-шаблоном (`MATCH_NAME_GLOB`): `*` соответствует любой последовательности символов, включая `.` между вложенными ключами, а `?` — одному символу. Например, `'m*'` соответствует и `m1`, и `m2.x`. Если путь соответствует нескольким полям, используется первое поле в порядке определения:

```sql
CREATE TABLE test_var_pattern (
    id BIGINT NOT NULL,
    v1 VARIANT<
        'enumString*' : STRING,
        'enum*' : ARRAY<TEXT>,
        'ip*' : IPV6
    > NULL
)
PROPERTIES ("replication_num" = "1");

-- enumString1 matches both enumString* and enum*; the first one (STRING) is used.
```

Для точного сопоставления с именем, содержащим символ `*`, используйте `MATCH_NAME`:

```sql
v1 VARIANT<
    MATCH_NAME 'enumString*' : STRING
> NULL
```

По умолчанию для совпавших путей выполняется Subcolumnization. Если совпадает слишком много путей и создаётся слишком много подстолбцов, рассмотрите настройку `variant_enable_typed_paths_to_sparse` (см. [Свойства столбца](#column-properties)).

Schema Template нельзя изменить после создания столбца. См. [ALTER TABLE](#alter-table).

## ALTER TABLE {#alter-table}

`ADD COLUMN` (включая пакетное добавление), `MODIFY COLUMN` и `RENAME COLUMN` также должны использовать имя столбца VARIANT верхнего уровня без точек. Например, следующая инструкция отклоняется:

```sql
ALTER TABLE example_tbl ADD COLUMN `v.x` VARIANT;
-- ERROR: Cannot use `VARIANT` type column named with a `.` character: v.x
```

`ALTER TABLE` поддерживает:

- `ADD COLUMN` для столбца VARIANT, допускающего NULL, с Schema Template и свойствами или без них.
- `DROP COLUMN`, `RENAME COLUMN` и `MODIFY COLUMN ... COMMENT '...'`.
- `ADD INDEX` и `DROP INDEX`. Индекс с `field_pattern` можно определить только в `CREATE TABLE`.
- Для столбца без Schema Template: изменение `NOT NULL` на `NULL` и изменение `variant_doc_materialization_min_rows`. `MODIFY COLUMN` принимает полное определение столбца; пропущенное свойство получает значение соответствующей переменной сеанса `default_variant_*`, поэтому повторно указывайте каждое свойство, значение которого отличается.

Не поддерживается:

- `ADD COLUMN ... VARIANT NOT NULL`: столбцу `NOT NULL`, добавленному через `ALTER`, нужно значение по умолчанию, а VARIANT допускает только `DEFAULT NULL`. Определяйте столбцы VARIANT с `NOT NULL` в `CREATE TABLE`.
- Добавление Schema Template к существующему столбцу. Для столбца со Schema Template через `MODIFY COLUMN` можно изменить только комментарий; любое другое изменение завершается ошибкой, даже если оно повторяет тот же шаблон.
- Изменение любого свойства, кроме `variant_doc_materialization_min_rows`, изменение `NULL` на `NOT NULL` и преобразование между VARIANT и другими типами.
- `BUILD INDEX` для столбца VARIANT.

Для таких изменений создайте таблицу с новым определением и скопируйте данные через `INSERT INTO ... SELECT`; исходный столбец `STRING` оберните в `PARSE_TO_VARIANT`.

```sql
ALTER TABLE t ADD COLUMN v2 VARIANT NOT NULL;
-- ERROR: Field 'v2' doesn't have a default value

-- v is a VARIANT column without a Schema Template.
ALTER TABLE t MODIFY COLUMN v VARIANT<'id': INT>;
-- ERROR: Can not change variant schema templates
```

## Свойства столбца {#column-properties}

Свойства столбца задаются в `properties(...)` внутри типа VARIANT:

```sql
CREATE TABLE example_table (
  id INT,
  data_variant VARIANT<
      'path_1' : INT,
      'path_2' : STRING,
      properties(
          'variant_max_subcolumns_count' = '2048',
          'variant_enable_typed_paths_to_sparse' = 'true',
          'variant_sparse_hash_shard_count' = '64'
      )
  >
);
```

| Свойство | По умолчанию | ALTER | Описание |
| --- | --- | --- | --- |
| `variant_max_subcolumns_count` | `2048` | Нет | Максимальное число динамических путей, для которых выполняется Subcolumnization в одном файле данных; первыми выбираются пути с большим числом значений, отличных от null, а остальные пути сохраняются в разреженных столбцах. `0` означает отсутствие ограничения. Диапазон от 0 до 100000; рекомендуется не превышать 10000. Значения по умолчанию достаточно для большинства рабочих нагрузок; если нагрузке действительно требуется намного больше подстолбцов, предпочтителен [режим DOC](./variant-workload-guide.md#doc-mode-template). |
| `variant_enable_typed_paths_to_sparse` | `false` | Нет | По умолчанию для путей Schema Template всегда выполняется Subcolumnization, и они не учитываются в ограничении `variant_max_subcolumns_count`. При значении `true` они учитываются в ограничении и могут храниться в разреженных столбцах. |
| `variant_sparse_hash_shard_count` | `1` | Нет | Число физических разреженных столбцов, между которыми разреженные пути распределяются по хешу. Диапазон от 0 до 1024; `0` трактуется как `1`. |
| `variant_max_sparse_column_statistics_size` | `10000` | Нет | Максимальное число разреженных путей в одном файле данных, для которых записывается статистика. При превышении этого значения запрос к пути без статистики не может пропустить разреженные столбцы. Диапазон от 1 до 50000. |
| `variant_enable_doc_mode` | `false` | Нет | Включает режим DOC. Нельзя задать одновременно с `variant_max_subcolumns_count`, `variant_enable_typed_paths_to_sparse`, `variant_max_sparse_column_statistics_size` или `variant_sparse_hash_shard_count`. |
| `variant_doc_materialization_min_rows` | `0` | Только без Schema Template | Только для режима DOC. При записи меньшего числа строк сохраняется только документ; Subcolumnization выполняется, когда compaction объединит файлы до достижения порога. `0` означает выполнение Subcolumnization при записи. Диапазон от 0 до 1000000000. |
| `variant_doc_hash_shard_count` | `64` | Нет | Только для режима DOC. Число столбцов, на которые разбивается хранимый документ. Диапазон от 0 до 1024; `0` трактуется как `1`. |

Столбец **ALTER** показывает, можно ли изменить свойство через `ALTER TABLE ... MODIFY COLUMN`; см. [ALTER TABLE](#alter-table). О применении свойств разреженных столбцов и режима DOC см. в разделе [Широкие столбцы](#wide-columns).

Переменные `default_variant_*` применяются при определении столбца через `CREATE TABLE` или `ALTER TABLE`. Их изменение не влияет на существующие столбцы, но влияет на последующий `MODIFY COLUMN`, в котором свойство не указано.

### Настройки BE {#be-configuration}

| Настройка | По умолчанию | Описание |
| --- | --- | --- |
| `variant_max_json_key_length` | `255` | Максимальная длина ключа объекта JSON в байтах. Более длинный ключ вызывает ошибку разбора. Диапазон от 1 до 65535. |
| `variant_throw_exeception_on_invalid_json` | `false` | При значении `false` текст, отклонённый парсером JSON, сохраняется как строковое значение VARIANT. При значении `true` возникает ошибка разбора. |
| `variant_enable_duplicate_json_path_check` | `false` | При значении `false` повторяющийся ключ объекта вызывает ошибку разбора. При значении `true` сохраняется первое значение, а повторы игнорируются. |

Все три настройки можно изменять во время работы. О том, как сообщается ошибка разбора, см. в разделе [Ошибки разбора](#parse-errors).

## Индексы Variant {#variant-indexes}

### Выбор индексов {#choosing-indexes}

VARIANT поддерживает BloomFilter и Inverted Index для вложенных путей.
- Для фильтров по равенству/IN с высокой кардинальностью предпочтителен BloomFilter (более разреженный индекс, более высокая производительность записи).
- Для поиска с токенизацией, по фразам или диапазонам используйте Inverted Index и задавайте подходящие свойства `parser`/`analyzer`.

Фильтр может использовать индекс или BloomFilter только при сравнении пути в его типе хранения. Явно приводите числовые пути с помощью CAST; строковый путь при сравнении со строковым литералом не требует CAST.

```sql
...  
PROPERTIES("replication_num" = "1", "bloom_filter_columns" = "v");

-- Use BloomFilter for equality/IN filters
SELECT * FROM tbl WHERE CAST(v['id'] AS BIGINT) = 12345678;
SELECT * FROM tbl WHERE CAST(v['id'] AS BIGINT) IN (1, 2, 3);
```

После создания инвертированного индекса для столбца VARIANT все вложенные пути наследуют одинаковые свойства индекса (например, парсер):

```sql
CREATE TABLE IF NOT EXISTS tbl (
    k BIGINT,
    v VARIANT,
    INDEX idx_v(v) USING INVERTED PROPERTIES("parser" = "english")
);

-- All subpaths inherit the english parser
SELECT * FROM tbl WHERE v['id_1'] MATCH 'Doris';
SELECT * FROM tbl WHERE v['id_2'] MATCH 'Apache';
```

### Индекс для вложенного пути {#index-by-subpath}

Можно задать свойства индекса для определённых вложенных путей VARIANT и даже настроить для одного пути инвертированные индексы как с токенизацией, так и без неё. Для индексов отдельных путей тип пути должен быть объявлен через Schema Template.

```sql
-- Common properties: field_pattern (target path), analyzer, parser, support_phrase, norms, etc.
CREATE TABLE IF NOT EXISTS tbl (
    k BIGINT,
    v VARIANT<'content' : STRING>,
    INDEX idx_tokenized(v) USING INVERTED PROPERTIES("parser" = "english", "field_pattern" = "content"),
    INDEX idx_v(v) USING INVERTED PROPERTIES("field_pattern" = "content")
);

-- v.content has both tokenized and non-tokenized inverted indexes
SELECT * FROM tbl WHERE v['content'] MATCH 'Doris';
SELECT * FROM tbl WHERE v['content'] = 'Doris';
```

Индексирование путей по шаблону:

```sql
CREATE TABLE IF NOT EXISTS tbl (
    k BIGINT,
    v VARIANT<'pattern_*' : STRING>,
    INDEX idx_tokenized(v) USING INVERTED PROPERTIES("parser" = "english", "field_pattern" = "pattern_*"),
    INDEX idx_v(v) USING INVERTED -- global non-tokenized inverted index
);

SELECT * FROM tbl WHERE v['pattern_1'] MATCH 'Doris';
SELECT * FROM tbl WHERE v['pattern_1'] = 'Doris';
```

Начиная с Doris 4.1.5, norms можно отключить с помощью свойства индекса или настройки BE, приведённых ниже.

Индексы с токенизацией для путей VARIANT по умолчанию записывают norms для BM25, что требует одного байта на строку для каждого пути, включая строки без значения этого пути. Для путей, используемых только при фильтрации, отключите norms с помощью `"norms" = "false"`. Без `field_pattern` это свойство применяется ко всем вложенным путям, охваченным индексом:

```sql
CREATE TABLE IF NOT EXISTS tbl (
    k BIGINT,
    v VARIANT<'body_*' : STRING>,
    INDEX idx_body(v) USING INVERTED PROPERTIES("parser" = "english", "field_pattern" = "body_*", "norms" = "false")
);
```

Отключение norms не влияет на фильтрацию `MATCH`, но `score()` возвращает ошибку при чтении сегмента без norms. Настройка BE `inverted_index_skip_norms_for_variant` отключает norms для всех путей VARIANT. Подробности см. в разделе [Длина записи и свойство norms](../../../../table-design/index/inverted-index/scoring.md#record-length-and-the-norms-property).

### Когда индексы не работают {#when-indexes-dont-work}

1. Изменение типа приводит к потере индекса: если тип вложенного пути меняется на несовместимый (например, INT → JSONB), индекс теряется. Чтобы это исправить, зафиксируйте типы и индексы через Schema Template.
2. Фильтр сравнивает путь не в его типе хранения:
   ```sql
   -- An implicit numeric comparison is evaluated row by row and uses no index
   SELECT * FROM tbl WHERE v['id'] = 123456;

   -- CAST to the stored type instead
   SELECT * FROM tbl WHERE CAST(v['id'] AS BIGINT) = 123456;
   ```
   Если `v['id']` хранится как строка, сравнивайте его со строкой: `v['id'] = '123456'`.
3. Неправильно настроенный индекс: индексы применяются к вложенным путям, а не ко всему столбцу VARIANT.
   ```sql
   -- VARIANT itself cannot be indexed as a whole
   SELECT * FROM tbl WHERE v MATCH 'Doris';

   -- If whole-JSON search is needed, store a duplicate STRING column and index it
   CREATE TABLE IF NOT EXISTS tbl (
       k BIGINT,
       v VARIANT,
       v_str STRING,
       INDEX idx_v_str(v_str) USING INVERTED PROPERTIES("parser" = "english")
   );
   SELECT * FROM tbl WHERE v_str MATCH 'Doris';
   ```

## Широкие столбцы {#wide-columns}

Если загружаемые данные содержат много различных ключей JSON, число подстолбцов, создаваемых при Subcolumnization, может быстро расти; при больших объёмах это приводит к разрастанию метаданных, увеличению затрат на запись и слияние, а также замедлению запросов. Для работы с «широкими столбцами» (слишком большим числом подстолбцов) VARIANT предоставляет два механизма: **разреженные столбцы** и **кодирование DOC**.

Рекомендации по выбору режима для рабочей нагрузки см. в [руководстве по выбору режима Variant для рабочей нагрузки](./variant-workload-guide.md). Этот раздел описывает только сами механизмы и связанные с ними свойства.

Примечание: эти два механизма взаимоисключающие — включение кодирования DOC отключает разреженные столбцы, и наоборот.

### Разреженные столбцы {#sparse-columns}

**Как это работает**

- Система ранжирует пути по доле значений, отличных от null, и степени разреженности: для часто встречающихся (менее разреженных) путей выполняется Subcolumnization, и они хранятся как отдельные подстолбцы; остальные редкие (разреженные) пути объединяются и хранятся в разреженных столбцах. Максимальное число выделенных подстолбцов регулируется свойством `variant_max_subcolumns_count`.
- Если путь объявлен в Schema Template, по умолчанию он не переносится в разреженные столбцы; задайте `variant_enable_typed_paths_to_sparse`, чтобы разрешить перенос типизированных путей в разреженные столбцы.
- Разреженные столбцы поддерживают шардирование: разреженные вложенные пути распределяются между несколькими разреженными столбцами, чтобы снизить затраты на чтение каждого столбца и повысить эффективность чтения. Число физически хранимых разреженных столбцов задаётся через `variant_sparse_hash_shard_count`.

**Справочные замечания**

- Если у большинства ключей примерно одинаковая доля значений, отличных от null (небольшие различия в разреженности), выявить действительно разреженные пути трудно, и польза от разреженных столбцов снижается.
- Значение `variant_max_subcolumns_count` по умолчанию — `2048`, чего уже достаточно для большинства рабочих нагрузок. Не стоит резко увеличивать его только ради предварительного выделения большего числа подстолбцов; если нагрузке действительно требуется масштабная Subcolumnization, предпочтителен [режим DOC](./variant-workload-guide.md#doc-mode-template). Рекомендуется по-прежнему удерживать практический верхний предел на уровне ≤ `10000`.
- `variant_sparse_hash_shard_count` можно приблизительно оценить как «число разреженных путей / 128». Например: всего ключей JSON ≈ 10,000, `variant_max_subcolumns_count = 2000`, тогда разреженных путей ≈ 8000, поэтому для `variant_sparse_hash_shard_count` можно начать со значения около `8000/128`.

### Кодирование DOC (режим DOC) {#doc-encoding-doc-mode}

**Как это работает**

- Для путей по-прежнему может выполняться Subcolumnization, чтобы обслуживать запросы к отдельным путям, а исходный JSON дополнительно сохраняется как stored field для эффективного возврата полного документа JSON.
- Кодирование DOC поддерживает шардирование: исходный JSON разбивается на несколько столбцов для хранения и собирается заново при запросе полного JSON. Число шардов DOC задаётся через `variant_doc_hash_shard_count`.
- При записи небольшими пакетами Subcolumnization можно пропустить и отложить до последующих слияний. Это регулируется свойством `variant_doc_materialization_min_rows`. Например, если `variant_doc_materialization_min_rows = 10000`, при записи менее 10,000 строк сохраняется только исходный JSON, а Subcolumnization для этого пакета не запускается.
- Для нагрузок с очень широкими столбцами режим DOC также более стабилен, когда масштаб Subcolumnization приближается к десяти тысячам подстолбцов. По сравнению с немедленной Subcolumnization по умолчанию потребление памяти при compaction может снизиться примерно на две трети, а пропускная способность загрузки разреженных широких столбцов — вырасти примерно в 5-10 раз.
- Когда столбец `VARIANT` очень широкий, а запросы часто читают документ целиком, режим DOC может повысить производительность `SELECT variant_col` на порядки по сравнению с восстановлением документа из множества подстолбцов.

```sql
CREATE TABLE example_table (
  id INT,
  data_variant VARIANT<
      'path_1' : INT,
      'path_2' : STRING,
      properties(
          'variant_enable_doc_mode' = 'true',
          'variant_doc_materialization_min_rows' = '10000',
          'variant_doc_hash_shard_count' = '64'
      )
  >
);
```

**Справочные замечания**

- Для режима DOC требуется `variant_enable_doc_mode = true`.
- В режиме DOC поля Schema Template ограничены строками, целыми числами, `FLOAT`, `DOUBLE`, `BOOLEAN` и массивами этих типов.
- `variant_doc_hash_shard_count` можно приблизительно оценить как «общее число ключей JSON / 128».

### Поведение при достижении пределов и рекомендации по настройке {#behavior-at-limits-and-tuning-suggestions}

1. После превышения порога новые пути записываются в разреженные столбцы; слияния Rowset также могут переносить некоторые пути в разреженные столбцы.
2. Система предпочитает сохранять в Subcolumnization пути с большей долей значений, отличных от null, и более высокой частотой обращений.
3. При количестве путей в Subcolumnization около 10,000 требуется мощное оборудование (рекомендуется ≥128G RAM и ≥32C на узел). Если нагрузка уже близка к этому диапазону, сначала оцените режим DOC.
4. Настройка загрузки: увеличьте клиентский `batch_size` до подходящего значения или используйте Group Commit (при необходимости увеличьте `group_commit_interval_ms`/`group_commit_data_bytes`).
5. Если пропуск бакетов не нужен, рассмотрите распределение по бакетам RANDOM и включение загрузки в один tablet, чтобы уменьшить усиление записи при compaction.
6. Параметры настройки BE: `max_cumu_compaction_threads` (≥8), `vertical_compaction_num_columns_per_group=500` (улучшает vertical compaction, но увеличивает потребление памяти), `segment_cache_memory_percentage=20` (повышает эффективность кеша метаданных).
7. Следите за Compaction Score; если показатель постоянно растёт, compaction не успевает за загрузкой — снизьте интенсивность загрузки.
8. Избегайте объёмных `SELECT *` для VARIANT; выбирайте конкретные проекции, например `SELECT v['path']`.

## Просмотр подстолбцов и типов {#inspect-subcolumns-and-types}

Способ 1: используйте [VARIANT_TYPE](../../../sql-functions/scalar-functions/variant-functions/variant-type.md), чтобы получить тип значения или отдельного пути для каждой строки. Функция читает каждую проверяемую строку:

```sql
SELECT VARIANT_TYPE(v), VARIANT_TYPE(v['a']) FROM variant_tbl LIMIT 10;
```

Способ 2: расширенный вывод `DESC` показывает вложенные пути, выделенные при Subcolumnization, и их типы хранения:

```sql
SET describe_extend_variant_column = true;
DESC variant_tbl;
```

```sql
DESCRIBE ${table_name} PARTITION ($partition_name);
```

Способ 1 показывает тип каждого значения; способ 2 — то, как хранится каждый путь.

## Ограничения {#limitations}

- **Оптимизация широких таблиц**: для широких таблиц с большим числом динамических подстолбцов (например, более 2000 столбцов), создаваемых типом `VARIANT`, настоятельно рекомендуется включить **Storage Format V3**, указав `"storage_format" = "V3"` в `PROPERTIES` таблицы. Это отделяет метаданные столбцов от Segment Footer, ускоряя открытие файлов и снижая затраты памяти.
- По умолчанию длина ключа JSON не может превышать 255 байт (`variant_max_json_key_length`).
- Столбец VARIANT не может быть ключевым столбцом, столбцом партиционирования или распределения по бакетам, а также не может быть вложен в другой тип в схеме таблицы (см. [Определение столбца VARIANT](#define-a-variant-column)).
- Вне режима DOC чтение всего столбца VARIANT сканирует все вложенные пути. Для очень широких столбцов прямой `SELECT variant_col` обычно не рекомендуется, если режим DOC не включён. Если у столбца много вложенных путей, рассмотрите хранение исходной строки JSON в дополнительном столбце STRING/JSONB для поиска по объекту целиком, например через `LIKE`:

```sql
CREATE TABLE example_table (
  id INT,
  data_variant VARIANT
);
SELECT * FROM example_table WHERE data_variant LIKE '%doris%';

-- Better: keep the original JSON string for whole-object matching
CREATE TABLE example_table (
  id INT,
  data_string STRING,
  data_variant VARIANT
);
SELECT * FROM example_table WHERE data_string LIKE '%doris%';
```

## Сравнение с типом JSON {#compared-with-json-type}

- Хранение: JSON хранится как JSONB (в строковом формате). VARIANT использует Subcolumnization при записи (более высокая степень сжатия, меньший объём).
- Запросы: JSON требует разбора. VARIANT сканирует столбцы напрямую и обычно работает намного быстрее.

Модифицированный ClickBench (43 запроса):
- Хранение: VARIANT экономит ~65% по сравнению с JSON.
- Запросы: VARIANT быстрее JSON в 8 раз и более, приближаясь по скорости к заранее определённым статическим столбцам.

**Объём хранения**

| Тип                 | Размер     |
| ------------------- | ---------- |
| Заранее определённые столбцы | 12.618 GB  |
| VARIANT             | 12.718 GB  |
| JSON                | 35.711 GB  |

**Экономия места ~65%**

| Запуск          | Заранее определённые столбцы | VARIANT | JSON            |
| ----------------| ---------- | ------- | --------------- |
| Первый (холодный) | 233.79s    | 248.66s | Большинство запросов превысили время ожидания |
| Второй (прогретый) | 86.02s     | 94.82s  | 789.24s         |
| Третий (прогретый) | 83.03s     | 92.29s  | 743.69s         |

## Частые вопросы {#faq}

1. Одинаковы ли `null` в VARIANT и SQL `NULL`?
   - Нет. Значение JSON `null`, вычисленное в запросе, является значением VARIANT `null`, тогда как отсутствующий путь — это SQL `NULL`. После сохранения значения поля объектов со значением `null` вне массивов удаляются и при чтении возвращаются как SQL `NULL`. См. [Семантика NULL](#null-semantics).
2. Почему `v['a']` возвращает `NULL` после `INSERT INTO t VALUES (1, '{"a": 1}')`?
   - `INSERT` сохраняет строку как строковое значение VARIANT без разбора; так же работает `INSERT INTO ... SELECT` из `s3()`, `hdfs()` или другого строкового столбца. Используйте `PARSE_TO_VARIANT('{"a": 1}')` или загрузите данные заданием загрузки, например Stream Load. См. [Запись данных](#write-data).
3. Почему весь документ JSON сохраняется как строка, хотя это корректный JSON?
   - Вероятно, документ содержит целое число вне диапазона [-2^63, 2^64 - 1] или число вне диапазона `DOUBLE`. Парсер отклоняет такой документ, и по умолчанию он сохраняется как строка. См. [Ошибки разбора](#parse-errors).
4. Почему мой запрос или индекс не работает?
   - Проверьте, приводите ли вы пути с помощью CAST к их типам хранения (неявные числовые сравнения не могут использовать индексы), не был ли тип изменён на JSONB из-за конфликтов и не ожидаете ли вы ошибочно индексирования всего VARIANT вместо вложенных путей.
5. Почему `ORDER BY v['a']` размещает `"10"` после `9`, а `GROUP BY v['a']` разделяет `1` и `"1"`?
   - При упорядочивании и проверке равенства VARIANT сначала учитывается вид значения: числа идут перед строками, а число никогда не равно строке. Приведите путь к одному типу с помощью CAST, если нужна числовая или лексикографическая семантика. См. [Сравнение, группировка и упорядочивание](#comparison-grouping-and-ordering).
6. Почему `COALESCE(v['a'], 0)` возвращает `0.000000000`, когда `v['a']` — строка, а `IF(..., v['a'], 1)` возвращает `NULL`?
   - При смешивании VARIANT с другим типом значения VARIANT преобразуются к этому типу; для целого числа это `DECIMAL(38, 9)`. Строку вроде `"abc"` невозможно преобразовать, и она становится `NULL`, поэтому `COALESCE` возвращает `0` как `0.000000000`. Напишите `COALESCE(v['a'], CAST(0 AS VARIANT))`, чтобы сохранить результат VARIANT, либо приведите `v['a']` к нужному типу с помощью CAST.
7. Почему DECIMAL теряет точность при записи в столбец VARIANT?
   - Тип чисел JSON с дробной частью определяется как `DOUBLE`, а не `DECIMAL`, поэтому последние цифры могут теряться. Объявление пути как `DECIMAL` в Schema Template, например `v VARIANT<'num': DECIMAL(9, 3)>`, не решает проблему полностью, поскольку сначала значение разбирается как `DOUBLE`. Запишите значение внутри документа как строку JSON, например `PARSE_TO_VARIANT('{"num": "12.345"}')`; тогда оно будет преобразовано напрямую в `DECIMAL(9, 3)` без потерь.
