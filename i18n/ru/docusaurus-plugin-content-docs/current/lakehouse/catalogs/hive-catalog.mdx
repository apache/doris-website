Подключившись к Hive Metastore или совместимой с ним службе метаданных, Doris может автоматически получать сведения о базах данных и таблицах Hive для выполнения запросов.

Hive Metastore используют для хранения метаданных и другие системы. Поэтому через Hive Catalog можно обращаться не только к таблицам Hive, но и к таблицам других форматов, использующих Hive Metastore, например Iceberg и Hudi.

## Сценарии применения {#applicable-scenarios}

| Сценарий | Описание |
|--------------|--------------------------------------------------------------|
| Ускорение запросов | Использование распределённого вычислительного движка Doris для прямого доступа к данным Hive и ускорения запросов. |
| Интеграция данных | Чтение данных Hive и запись во внутренние таблицы Doris либо выполнение операций ZeroETL с помощью вычислительного движка Doris. |
| Обратная запись данных | Обработка данных из любого источника, поддерживаемого Doris, и их запись в таблицы Hive. |

## Настройка Catalog {#configuring-catalog}

### Синтаксис {#syntax}

```sql
CREATE CATALOG [IF NOT EXISTS] catalog_name PROPERTIES (
    'type'='hms', -- required
    'hive.metastore.type' = '<hive_metastore_type>', -- optional
    'hive.version' = '<hive_version>', -- optional
    'fs.defaultFS' = '<fs_defaultfs>', -- required for write, optional for read-only
    {MetaStoreProperties},
    {StorageProperties},
    {HiveProperties},
    {CommonProperties}
);
```

* `<hive_metastore_type>`

  Тип Hive Metastore.

  * `hms`: стандартная служба Hive Metastore.
  * `glue`: доступ к службе метаданных AWS Glue через совместимый с Hive Metastore интерфейс.
  * `dlf`: доступ к службе метаданных Alibaba Cloud DLF через совместимый с Hive Metastore интерфейс.

* `<fs_defaultfs>`

  Этот параметр обязателен при записи данных из Doris в таблицы данного Hive Catalog. Пример:

  `'fs.defaultFS' = 'hdfs://namenode:port'`

* `{MetaStoreProperties}`

  В разделе MetaStoreProperties указывают параметры подключения и аутентификации для службы метаданных Metastore. Подробнее см. раздел «Поддерживаемые службы метаданных».

* `{StorageProperties}`

  В разделе StorageProperties указывают параметры подключения и аутентификации для системы хранения. Подробнее см. раздел «Поддерживаемые системы хранения».

* `{HiveProperties}`

  В разделе HiveProperties указывают свойства Hive Catalog.

  * `get_schema_from_table`: значение по умолчанию — false. Обычно Doris получает схему таблицы из Hive Metastore. Однако иногда возникают проблемы совместимости, например ошибка `Storage schema reading not supported`. В таком случае можно установить значение true, чтобы получать схему непосредственно из объекта Table. Учтите, что при этом сведения о значениях столбцов по умолчанию игнорируются. Свойство поддерживается начиная с версий 2.1.10 и 3.0.6.

  * `hive.recursive_directories`: определяет, нужно ли рекурсивно обходить вложенные каталоги при перечислении каталогов разделов. Параметр поддерживается начиная с версии 3.0.2. До версии 4.0 его значением по умолчанию было `false`, в более поздних версиях — `true`. Пути разделов некоторых таблиц Hive могут не соответствовать сведениям о разделах в схеме таблицы. Чтобы получить файлы данных во вложенных каталогах, необходимо установить значение true.

  * `hive.ignore_absent_partitions`: определяет, следует ли игнорировать несуществующие разделы. Значение по умолчанию — `true`. Если установить `false`, при обнаружении несуществующего раздела запрос завершится ошибкой. Параметр поддерживается начиная с версии 3.0.2.

  * `hive.staging_dir`: задаёт корневой каталог для временного размещения данных при записи в Hive. Сначала данные записываются в этот каталог, а после завершения записи перемещаются в конечный каталог таблицы Hive. Можно указать абсолютный путь или путь относительно корневого каталога таблицы Hive. Значение по умолчанию — `/tmp/.doris_staging`. Иногда запись в таблицу Hive завершается ошибкой, поскольку каталог `/tmp` и каталог таблицы находятся в разных пространствах имён. В таком случае проблему можно решить, указав относительный путь. Параметр поддерживается начиная с версии 4.0.3.

  * `hive.parquet.time-zone`: часовой пояс совместимости, используемый для восстановления временных меток Parquet `INT96`, созданных прежними версиями средств записи, когда FileScannerV2 читает таблицы Hive. По умолчанию значение пустое: поля даты и времени, записанные в `INT96`, сохраняются без преобразования часового пояса. Устанавливайте это свойство только в том случае, если файлы `INT96` в Catalog были нормализованы средством записи с известным часовым поясом. Таблицы Hudi намеренно игнорируют это свойство и сохраняют прежнюю зависимость от часового пояса сеанса SQL. Подробнее см. [Совместимость временных меток Parquet INT96](#timestamp-compatibility).

* `{CommonProperties}`

  В разделе CommonProperties указывают общие свойства. См. раздел «Общие свойства» в [обзоре Catalog](../catalog-overview.md).

## Кеш метаданных {#meta-cache}

Для ускорения доступа к внешним источникам данных Apache Doris кеширует метаданные Hive: объекты таблиц, имена и объекты разделов, статистику столбцов, списки файлов и производные структуры для отсечения разделов.

:::tip
В версиях до Doris 4.1.x кеширование метаданных в основном управляется глобальными параметрами FE. Подробнее см. [Кеш метаданных](../meta-cache.md).
Начиная с Doris 4.1.x кеш внешних метаданных Hive Catalog настраивается едиными ключами `meta.cache.*`. Ниже описаны параметры текущей версии; в Doris 4.1.x и 4.2.x используется другой набор параметров, описанный в версии 4.x этой страницы.
:::

### Настройка свойств кеша {#meta-cache-unified-model}

Для каждой записи кеша используется единый формат ключа: `meta.cache.<engine>.<entry>.{enable,ttl-second,capacity,max-weight}`. Для Hive значение `<engine>` — `hive`. Hive Metastore Catalog с таблицами Iceberg также использует записи `iceberg`, описанные в разделе [Iceberg Catalog](./iceberg-catalog.mdx#meta-cache).

| Свойство | Пример | Значение |
|---|---|---|
| `enable` | `true/false` | Включает или отключает запись кеша. |
| `ttl-second` | `600`, `0`, `-1` | `0` отключает запись (действует немедленно и позволяет видеть последние изменения данных); `-1` означает отсутствие срока действия; другие положительные целые числа задают TTL в секундах с момента обращения. |
| `capacity` | `10000` | Максимальное число элементов кеша. `0` отключает запись. |
| `max-weight` | `1GB` | Поддерживается начиная с Doris 4.1.4. Необязательный предел оценочного объёма памяти, занимаемого записью кеша. Значение должно быть положительным; `0` отклоняется. Принимается только для записей, указанных ниже. |

**Условия действия:** запись действует при `enable=true`, `ttl-second != 0` и `capacity > 0`. Кроме того, при допуске элементов учитываются пределы оценочного объёма памяти для FE, Catalog или отдельной записи. См. [Управление памятью кеша внешних метаданных](../external-meta-cache-memory-management).

### Записи кеша {#meta-cache-unified-modules}

Hive Catalog содержит следующие записи кеша. Все они принимают `max-weight`.

| Запись (`<entry>`) | Префикс ключа свойства | `ENTRY_NAME` | Кешируемые данные и влияние | Значения по умолчанию: enable / TTL / capacity |
|---|---|---|---|---|
| `table` | `meta.cache.hive.table.` | `hive-table` | Объекты таблиц из Hive Metastore. Уменьшает число обращений к Metastore при планировании. | `true` / 86400 с / 10000 |
| `partition_names` | `meta.cache.hive.partition_names.` | `hive-partition-names` | Списки имён разделов. Влияет на перечисление разделов; при отключении новые разделы становятся видны сразу. | `true` / 86400 с / 10000 |
| `partition` | `meta.cache.hive.partition.` | `hive-partition` | Объекты разделов, например расположение и формат входных данных. | `true` / 86400 с / 100000 |
| `column_stats` | `meta.cache.hive.column_stats.` | `hive-column-stats` | Статистика столбцов из Hive Metastore. | `true` / 86400 с / 10000 |
| `file` | `meta.cache.hive.file.` | `hive-file` | Списки файлов. Уменьшает число удалённых операций LIST; при отключении изменения файлов становятся видны сразу. | `true` / 86400 с / 10000 |
| `partition_view` | `meta.cache.hive.partition_view.` | `hive-partition-view` | Структуры для отсечения разделов, полученные из имён разделов. | `true` / 86400 с / 1000 |

Схема столбцов таблиц Hive кешируется общим движком `default` (`meta.cache.default.schema.*`), который используется всеми внешними Catalog.

### Сопоставление и преобразование прежних параметров {#meta-cache-mapping}

Рекомендуется использовать единые ключи. Следующие прежние свойства Catalog по-прежнему принимаются и сопоставляются с новыми ключами:

| Прежний ключ свойства | Единый ключ | Описание |
|---|---|---|
| `schema.cache.ttl-second` | `meta.cache.default.schema.ttl-second` и `meta.cache.hive.table.ttl-second` | Срок действия кешей схем таблиц и объектов таблиц |
| `partition.cache.ttl-second` | `meta.cache.hive.partition_names.ttl-second` | Срок действия списков имён разделов |
| `file.meta.cache.ttl-second` | `meta.cache.hive.file.ttl-second` | Срок действия списков файлов |

### Рекомендации {#meta-cache-best-practices}

* **Доступ к последним изменениям данных в реальном времени**: чтобы каждый запрос видел последние изменения разделов или файлов во внешнем источнике, установите соответствующий `ttl-second` равным `0`.
  ```sql
  -- Disable the file listing cache to see file changes in real time
  ALTER CATALOG hive_ctl SET PROPERTIES ("meta.cache.hive.file.ttl-second" = "0");
  -- Disable the partition name cache to see new partitions in real time
  ALTER CATALOG hive_ctl SET PROPERTIES ("meta.cache.hive.partition_names.ttl-second" = "0");
  ```
* **Оптимизация производительности**: если метаданные меняются редко, увеличьте `capacity` и `ttl-second`, чтобы снизить нагрузку на Hive Metastore и файловые системы. Для очень больших таблиц используйте `max-weight`, чтобы ограничить объём памяти кешей списков файлов и структур отсечения разделов.

:::caution
После успешного изменения свойства Catalog затронутые кеши метаданных удаляются и при следующем обращении создаются заново с новой конфигурацией. Изменение `meta.cache.max-weight` или `schema.cache.ttl-second` удаляет все кеши Catalog; изменение `meta.cache.<engine>.<entry>.*` удаляет кеши соответствующего движка. Выполняющиеся запросы не затрагиваются.
:::

### Наблюдение за кешем {#meta-cache-unified-observability}

Метрики кеша доступны в системной таблице `information_schema.catalog_meta_cache_statistics`. В `ENTRY_NAME` отображаются имена из таблицы выше, а строка движка `default` относится к общему кешу схем таблиц:

```sql
SELECT engine_name, entry_name,
       effective_enabled, ttl_second, capacity,
       estimated_size, hit_rate, max_weight, estimated_weight
FROM information_schema.catalog_meta_cache_statistics
WHERE catalog_name = 'hive_ctl'
ORDER BY engine_name, entry_name;
```

Описание системной таблицы см. в разделе [catalog_meta_cache_statistics](../../admin-manual/system-tables/information_schema/catalog_meta_cache_statistics.md).

## Совместимость временных меток Parquet INT96 {#timestamp-compatibility}

Таблицы Hive могут содержать файлы с временными метками, созданные разными движками. Необходимость преобразования часового пояса зависит от физического кодирования и поведения средства записи. Doris не определяет часовой пояс средства записи по значению Parquet `INT96`, поскольку `INT96` не содержит аннотации часового пояса.

Начиная с версии 4.1.5 свойство `hive.parquet.time-zone` принимает часовой пояс IANA или смещение относительно UTC от `-12:00` до `+14:00`. Значения `UTC` и `GMT` принимаются, а краткие обозначения, такие как `CST` и `PRC`, отклоняются. См. [Parquet](../file-formats/parquet.md#timestamp-and-date-compatibility).

### Временные метки Parquet INT96 {#parquet-int96-timestamps}

FileScannerV2 обрабатывает временные метки Parquet следующим образом:

| Физическое кодирование | Поведение по умолчанию | Влияние `hive.parquet.time-zone` |
|---|---|---|
| `INT96`, сопоставленный с `DATETIMEV2` | Сохраняются поля даты и времени, записанные в файле. Часовой пояс сеанса SQL не смещает значение. | Исходное значение `INT96` рассматривается как момент времени в UTC и преобразуется в настроенный часовой пояс совместимости. Это восстанавливает временные метки, нормализованные прежним средством записи. |
| `INT64` с логическим типом временной метки | Применяется семантика логического типа Parquet. | Не влияет. |

Например, предположим, что требуемая локальная временная метка — `2021-01-01 10:11:00` в часовом поясе `Asia/Shanghai`:

* Если файл непосредственно хранит поля локального времени как `10:11:00`, не устанавливайте `hive.parquet.time-zone`. Doris вернёт `10:11:00`, даже если сеанс SQL использует `Asia/Shanghai`.
* Если прежнее средство записи нормализовало значение в UTC перед сохранением в `INT96`, файл может содержать `02:11:00`. Установите `hive.parquet.time-zone` равным `Asia/Shanghai`, чтобы Doris восстановил `10:11:00`.

Настройте часовой пояс совместимости при создании Catalog:

```sql
CREATE CATALOG hive_legacy_int96 PROPERTIES (
    'type' = 'hms',
    'hive.metastore.uris' = 'thrift://127.0.0.1:9083',
    'hive.parquet.time-zone' = 'Asia/Shanghai'
);
```

Значением может быть имя часового пояса IANA, например `Asia/Shanghai`, либо смещение относительно UTC от `-12:00` до `+14:00`. Недопустимое значение приводит к ошибке создания Catalog.

:::caution
`hive.parquet.time-zone` применяется ко всем столбцам временных меток `INT96`, сопоставленным с `DATETIMEV2`, в таблицах Hive данного Catalog. Свойство не влияет на таблицы Iceberg в том же Hive Metastore, поскольку Iceberg определяет собственную семантику временных меток. Hudi также намеренно игнорирует это свойство: как непосредственное сканирование базовых файлов, так и сканирование merge-on-read через JNI сохраняют прежнее поведение и интерпретируют временные метки с учётом часового пояса сеанса SQL. По метаданным Parquet Doris не может надёжно определить, какое соглашение использовало средство записи `INT96`. Не устанавливайте это свойство только для совпадения с часовым поясом сеанса SQL. Если в одном Hive Metastore есть таблицы Hive с файлами `INT96`, записанными по разным соглашениям, по возможности предоставляйте доступ к ним через отдельные Catalog.
:::

Это же свойство принимают табличные функции для чтения файлов Parquet. Преобразование совместимости применяется только при декодировании Parquet `INT96` в FileScannerV2. Поведение FileScannerV1 намеренно не изменено, и он может возвращать другие результаты; переключение на FileScannerV1 не служит способом обеспечить совместимость с этим изменением. Логические временные метки Parquet `INT64` не затрагиваются. Если столбец `INT96` сопоставлен с `TIMESTAMPTZ`, Doris игнорирует свойство и сохраняет момент времени в UTC; отображение значения по-прежнему подчиняется семантике `TIMESTAMPTZ` и часового пояса сеанса.

### Рекомендации по переходу {#migration-recommendations}

* По умолчанию Doris записывает логические временные метки Parquet `INT64`. Устанавливайте `enable_int96_timestamps = true` только тогда, когда прежнему средству чтения, например Hive 2 или Hive 3, требуется `INT96`.
* Перед переходом на версию с таким поведением FileScannerV2 проверьте существующие таблицы Hive. После обновления Catalog с файлами `INT96`, нормализованными прежним средством записи, может возвращать другое локальное время. Сравните характерные значения и при необходимости преобразования установите `hive.parquet.time-zone` равным часовому поясу средства записи. Для Hudi переход в связи с этим изменением не требуется: он сохраняет прежнюю зависимость от часового пояса сеанса.
* Перед установкой `hive.parquet.time-zone` изучите характерные файлы и сравните известные значения временных меток. Ненужная настройка создаёт такое же смещение, которое она призвана устранить.
* Храните файлы, записанные с разными соглашениями для `INT96`, в отдельных Catalog либо перезапишите их с единым кодированием `INT64`.
* Когда Doris явно экспортирует `INT96` с `enable_int96_timestamps = true`, он нормализует временные метки с использованием часового пояса сеанса экспорта. Чтобы прочитать файл обратно через FileScannerV2, установите `hive.parquet.time-zone` равным часовому поясу этого сеанса экспорта. См. [Обзор экспорта](../../data-operate/export/export-overview.md).

## Операции чтения {#query-operations}

### Базовые запросы {#basic-query}

После настройки Catalog данные его таблиц можно запрашивать следующими способами:

```sql
-- 1. switch to catalog, use database and query
SWITCH hive_ctl;
USE hive_db;
SELECT * FROM hive_tbl LIMIT 10;

-- 2. use hive database directly
USE hive_ctl.hive_db;
SELECT * FROM hive_tbl LIMIT 10;

-- 3. use full qualified name to query
SELECT * FROM hive_ctl.hive_db.hive_tbl LIMIT 10;
```

### Запрос сведений о разделах Hive {#querying-hive-partitions}

Сведения о разделах Hive можно получить двумя способами:

* `SHOW PARTITIONS FROM [catalog.][db.]hive_table`

  Эта команда выводит все разделы указанной таблицы Hive и их значения.

  ```sql
  SHOW PARTITIONS FROM hive_table;

  +--------------------------------+
  | Partition                      |
  +--------------------------------+
  | pt1=2024-10-10/pt2=beijing     |
  | pt1=2024-10-10/pt2=shanghai    |
  | pt1=2024-10-11/pt2=beijing     |
  | pt1=2024-10-11/pt2=shanghai    |
  | pt1=2024-10-12/pt2=nanjing     |
  +--------------------------------+
  ```

* Через таблицу метаданных `table$partitions`

  Начиная с версий 2.1.7 и 3.0.3 сведения о разделах Hive можно запрашивать через таблицу метаданных `table$partitions`. По сути это реляционная таблица, в которой каждому столбцу разделения соответствует отдельный столбец; её можно использовать в любом запросе SELECT.

  ```sql
  SELECT * FROM hive_table$partitions;

  +------------+-------------+
  | pt1        | pt2         |
  +------------+-------------+
  | 2024-10-10 | beijing     |
  | 2024-10-10 | shanghai    |
  | 2024-10-12 | nanjing     |
  | 2024-10-11 | beijing     |
  | 2024-10-11 | shanghai    |
  +------------+-------------+
  ```

:::caution Изменение поведения (4.1.4)

Начиная с версии 4.1.4 маркер раздела по умолчанию `__HIVE_DEFAULT_PARTITION__`, используемый при разделении Hive по каталогам, преобразуется в настоящее значение **NULL**, а не кодируется строкой `\N`. При этом литеральная строка `\N`, действительно записанная в пути раздела, сохраняется как данные.

До версии 4.1.4 эти случаи были неразличимы и оба отображались в результатах запроса как `\N`. После обновления условие `WHERE <partition_col> IS NULL` правильно находит раздел Hive по умолчанию.

:::

### Запросы к транзакционным таблицам Hive {#querying-hive-transactional-tables}

Транзакционные таблицы Hive поддерживают семантику ACID. Подробнее см. [Hive Transactions](https://cwiki.apache.org/confluence/display/Hive/Hive+Transactions).

* Поддержка транзакционных таблиц Hive

  | Тип таблицы | Поддерживаемые операции в Hive | Свойства таблицы Hive | Поддерживаемые версии Hive |
  | ------------------------------- | ----------------------------------- | ------------------------------------------------------------------- | ---------------------------------------------------------------- |
  | Транзакционная таблица Full-ACID | Поддерживает Insert, Update, Delete | `'transactional'='true'` | 4.x, 3.x, 2.x (для чтения в 2.x требуется Major Compaction в Hive) |
  | Транзакционная таблица Insert-Only | Поддерживает только Insert | `'transactional'='true'`, `'transactional_properties'='insert_only'` | 4.x, 3.x, 2.x (при создании Catalog укажите `hive.version`) |

* Текущие ограничения

  Сценарии с Original Files не поддерживаются. После преобразования таблицы в транзакционную новые файлы данных используют схему транзакционной таблицы Hive, а существующие файлы данных не преобразуются. Такие файлы называют Original Files.

### Запросы к представлениям Hive {#querying-hive-views}

Представления Hive можно запрашивать, но с некоторыми ограничениями:

* Определение представления Hive на HiveQL должно быть совместимо с инструкциями SQL, поддерживаемыми Doris. Иначе возникнет ошибка разбора.

* Некоторые функции HiveQL могут называться так же, как функции Doris, но работать иначе. Из-за этого результаты запросов Hive и Doris могут различаться. Если вы столкнулись с такой проблемой, сообщите о ней сообществу.

### Связанные параметры {#related-parameters}

* Переменные сеанса

| Имя параметра | Значение по умолчанию | Описание | Начиная с версии |
| ----------| ---- | ---- | --- |
| `hive_parquet_use_column_names` | `true` | По умолчанию при чтении данных Parquet таблицы Hive Doris находит в файле Parquet столбец с тем же именем, что и в таблице Hive, и читает данные по имени. Если переменная равна `false`, Doris читает данные из файла Parquet по порядку столбцов в таблице Hive независимо от их имён. Аналогично переменной `parquet.column.index.access` в Hive. Параметр применяется только к именам столбцов верхнего уровня и не действует внутри Struct. | 2.1.6+, 3.0.3+ |
| `hive_orc_use_column_names` | `true` | Аналогичен `hive_parquet_use_column_names`, но относится к данным ORC таблиц Hive. Аналогичен переменной `orc.force.positional.evolution` в Hive. | 2.1.6+, 3.0.3+ |

## Операции записи {#write-operations}

Данные можно записывать в таблицы Hive с помощью инструкции INSERT. Поддерживается запись как в таблицы Hive, созданные Doris, так и в существующие таблицы Hive совместимых форматов.

Для секционированных таблиц данные автоматически записываются в соответствующий раздел либо на их основе создаётся новый раздел. Начиная с версии 4.1.5 конструкция `PARTITION (column = literal)` поддерживает статические разделы и сочетание статических и динамических столбцов разделения. Не включайте статические столбцы разделения в список целевых столбцов INSERT и в результаты SELECT или VALUES; оставшиеся динамические столбцы разделения передавайте во входных данных.

### INSERT INTO {#insert-into}

Операция INSERT добавляет данные в целевую таблицу.

```sql
INSERT INTO hive_tbl VALUES (val1, val2, val3, val4);
INSERT INTO hive_ctl.hive_db.hive_tbl SELECT col1, col2 FROM internal.db1.tbl1;

INSERT INTO hive_tbl(col1, col2) VALUES (val1, val2);
INSERT INTO hive_tbl(col1, col2, partition_col1, partition_col2) VALUES (1, 2, "beijing", "2023-12-12");
```

Начиная с версии 4.1.5 запись поддерживает статические разделы и сочетание статических и динамических разделов:

```sql
-- Full Static Partition
INSERT INTO hive_tbl PARTITION (partition_col1='2026-07-30', partition_col2='beijing')
VALUES (val1, val2);
INSERT INTO hive_tbl PARTITION (partition_col1='2026-07-30', partition_col2='beijing')
SELECT col1, col2 FROM source_table;

-- Hybrid Partition Mode: "partition_col1" is static, "partition_col2" comes from SELECT dynamically
INSERT INTO hive_tbl PARTITION (partition_col1='2026-07-30')
VALUES (val1, val2, partition_val2);
INSERT INTO hive_tbl PARTITION (partition_col1='2026-07-30')
SELECT col1, col2, partition_col2 FROM source_table;
```

### INSERT OVERWRITE {#insert-overwrite}

INSERT OVERWRITE полностью заменяет существующие данные таблицы новыми.

```sql
INSERT OVERWRITE TABLE hive_tbl VALUES (val1, val2, val3, val4);
INSERT OVERWRITE TABLE hive_ctl.hive_db.hive_tbl(col1, col2) SELECT col1, col2 FROM internal.db1.tbl1;
```

Начиная с версии 4.1.5 запись поддерживает статические разделы и сочетание статических и динамических разделов:

```sql
-- Full Static Partition
INSERT OVERWRITE TABLE hive_tbl PARTITION (partition_col1='2026-07-30', partition_col2='beijing')
VALUES (val1, val2);
INSERT OVERWRITE TABLE hive_tbl PARTITION (partition_col1='2026-07-30', partition_col2='beijing')
SELECT col1, col2 FROM source_table;

-- Hybrid Partition Mode: "partition_col1" is static, "partition_col2" comes from SELECT dynamically
INSERT OVERWRITE TABLE hive_tbl PARTITION (partition_col1='2026-07-30')
VALUES (val1, val2, partition_val2);
INSERT OVERWRITE TABLE hive_tbl PARTITION (partition_col1='2026-07-30')
SELECT col1, col2, partition_col2 FROM source_table;
```

Семантика INSERT OVERWRITE соответствует Hive и имеет следующие особенности:

* Если целевая таблица секционирована, а исходная таблица пуста, операция не оказывает действия. Целевая таблица остаётся без изменений.

* Если целевая таблица не секционирована, а исходная таблица пуста, целевая таблица очищается.

* Начиная с версии 4.1.5 поддерживаются запись с указанием статических разделов и смешанный режим со статическими и динамическими разделами. Однако даже при указании статических разделов они не очищаются, если исходный запрос возвращает пустой результат.

**Полный пример со статическими разделами (начиная с 4.1.5)**

Настройте описанный на этой странице Hive Catalog, подготовьте существующую базу данных `hive_ctl.hive_db` и предоставьте права на создание таблиц, запись и запросы. Для Catalog, используемого при записи, необходимо настроить `fs.defaultFS`. В примере статическая дата сочетается с динамическими регионами, после чего перезаписывается один полностью заданный статический раздел:

```sql
CREATE TABLE hive_ctl.hive_db.static_write_demo (
    id INT,
    dt STRING,
    region STRING
)
ENGINE=HIVE
PARTITION BY LIST (dt, region) ()
PROPERTIES ("file_format" = "parquet");

INSERT INTO hive_ctl.hive_db.static_write_demo PARTITION (dt='2026-10-01')
VALUES (1, 'beijing'), (2, 'shanghai');

INSERT OVERWRITE TABLE hive_ctl.hive_db.static_write_demo
PARTITION (dt='2026-10-01', region='beijing') VALUES (3);

SELECT id, dt, region FROM hive_ctl.hive_db.static_write_demo ORDER BY id;
```

```text
+----+------------+----------+
| id | dt         | region   |
+----+------------+----------+
|  2 | 2026-10-01 | shanghai |
|  3 | 2026-10-01 | beijing  |
+----+------------+----------+
```

Значения статических разделов должны быть литералами. Нельзя указывать ключ разделения более одного раза или повторять статический столбец разделения в явном списке столбцов INSERT. Имена статических ключей сопоставляются без учёта регистра; несуществующий столбец разделения вызывает ошибку.

### CTAS {#ctas}

Создать таблицу Hive и вставить в неё данные можно с помощью инструкции `CTAS (CREATE TABLE AS SELECT)`:

```sql
CREATE TABLE hive_ctas ENGINE=hive AS SELECT * FROM other_table;
```

CTAS позволяет указать форматы файлов, способы разделения и другие параметры, как показано ниже:

```sql
CREATE TABLE hive_ctas ENGINE=hive
PARTITION BY LIST (pt1, pt2) ()
AS SELECT col1, pt1, pt2 FROM part_ctas_src WHERE col1 > 0;

CREATE TABLE hive_ctl.hive_db.hive_ctas (col1, col2, pt1) ENGINE=hive
PARTITION BY LIST (pt1) ()
PROPERTIES (
    "file_format"="parquet",
    "compression"="zstd"
)
AS SELECT col1, pt1 AS col2, pt2 AS pt1 FROM test_ctas.part_ctas_src WHERE col1 > 0;
```

### Связанные параметры {#related-parameters-1}

* Конфигурация BE

  | Имя параметра | Значение по умолчанию | Описание |
  | ----------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------- | ----------- |
  | `hive_sink_max_file_size` | 1GB | Максимальный размер файла данных. Когда объём данных превышает этот предел, текущий файл закрывается и для продолжения записи создаётся новый. |
  | `table_sink_partition_write_max_partition_nums_per_writer` | 128 | Максимальное число разделов, в которые может записывать каждый экземпляр на узле BE. |
  | `table_sink_non_partition_write_scaling_data_processed_threshold` | 25MB | Порог объёма данных для запуска масштабируемой записи в несекционированные таблицы. Для каждого следующего объёма данных размером `table_sink_non_partition_write_scaling_data_processed_threshold` используется новый экземпляр записи. Механизм изменяет число экземпляров записи в зависимости от объёма данных, повышая пропускную способность параллельной записи; при небольших объёмах он экономит ресурсы и сокращает число файлов. |
  | `table_sink_partition_write_min_data_processed_rebalance_threshold` | 25MB | Минимальный порог объёма данных для запуска перераспределения при записи в секционированные таблицы. Перераспределение запускается, если `current accumulated data volume` - `data volume since last rebalancing or initial accumulation` >= `table_sink_partition_write_min_data_processed_rebalance_threshold`. Если размеры итоговых файлов существенно различаются, уменьшите порог для улучшения баланса. Более низкий порог может увеличить затраты на перераспределение и повлиять на производительность. |
  | `table_sink_partition_write_min_partition_data_processed_rebalance_threshold` | 15MB | Минимальный порог объёма данных раздела для запуска перераспределения. Перераспределение выполняется, если `current partition data volume` >= `threshold` \* `number of tasks already allocated to the partition`. Если размеры итоговых файлов существенно различаются, уменьшите порог для улучшения баланса. Более низкий порог может увеличить затраты на перераспределение и повлиять на производительность. |


## Управление базами данных и таблицами {#database-and-table-management}

Пользователи могут создавать и удалять базы данных и таблицы в Hive Metastore через Doris. Для этих операций Doris только вызывает API Hive Metastore и сам не хранит метаданные Hive на постоянной основе.

### Создание и удаление баз данных {#creating-and-dropping-databases}

Переключитесь на нужный Catalog с помощью инструкции `SWITCH` и выполните `CREATE DATABASE`:

```sql
SWITCH hive_ctl;
CREATE DATABASE [IF NOT EXISTS] hive_db;
```

Базу данных также можно создать по полному имени или указать её расположение, например:

```sql
CREATE DATABASE [IF NOT EXISTS] hive_ctl.hive_db;

CREATE DATABASE [IF NOT EXISTS] hive_ctl.hive_db
PROPERTIES ('location'='hdfs://172.21.16.47:4007/path/to/db/');
```

Расположение базы данных можно посмотреть командой `SHOW CREATE DATABASE`:

```sql
mysql> SHOW CREATE DATABASE hive_db;
+----------+---------------------------------------------------------------------------------------------+
| Database | Create Database                                                                             |
+----------+---------------------------------------------------------------------------------------------+
| hive_db  | CREATE DATABASE hive_db LOCATION 'hdfs://172.21.16.47:4007/usr/hive/warehouse/hive_db.db'   |
+----------+---------------------------------------------------------------------------------------------+
```

Чтобы удалить базу данных:

```sql
DROP DATABASE [IF EXISTS] hive_ctl.hive_db;
```

:::caution
Перед удалением базы данных Hive необходимо удалить все её таблицы, иначе возникнет ошибка. Эта операция также удалит соответствующую базу данных в Hive.
:::

### Создание и удаление таблиц {#creating-and-dropping-tables}

- **Создание таблиц**

  Doris поддерживает создание в Hive как секционированных, так и несекционированных таблиц.

  ```sql
  -- Create unpartitioned hive table
  CREATE TABLE unpartitioned_table (
    `col1` BOOLEAN COMMENT 'col1',
    `col2` INT COMMENT 'col2',
    `col3` BIGINT COMMENT 'col3',
    `col4` CHAR(10) COMMENT 'col4',
    `col5` FLOAT COMMENT 'col5',
    `col6` DOUBLE COMMENT 'col6',
    `col7` DECIMAL(9,4) COMMENT 'col7',
    `col8` VARCHAR(11) COMMENT 'col8',
    `col9` STRING COMMENT 'col9'
  )  ENGINE=hive
  PROPERTIES (
    'file_format'='parquet'
  );

  -- Create partitioned hive table
  -- The partition columns must be in table's column definition list
  CREATE TABLE partition_table (
    `col1` BOOLEAN COMMENT 'col1',
    `col2` INT COMMENT 'col2',
    `col3` BIGINT COMMENT 'col3',
    `col4` DECIMAL(2,1) COMMENT 'col4',
    `pt1` VARCHAR COMMENT 'pt1',
    `pt2` VARCHAR COMMENT 'pt2'
  )  ENGINE=hive
  PARTITION BY LIST (pt1, pt2) ()
  PROPERTIES (
    'file_format'='orc',
    'compression'='zlib'
  );

  -- Create text format table(Since 2.1.7 & 3.0.3)
  CREATE TABLE text_table (
      `id` INT,
      `name` STRING
  ) PROPERTIES (
      'file_format'='text',
      'compression'='gzip',
      'field.delim'='\t',
      'line.delim'='\n',
      'collection.delim'=';',
      'mapkey.delim'=':',
      'serialization.null.format'='\\N',
      'escape.delim'='\\'
  );
  ```

  После создания таблицы её инструкцию создания в Hive можно посмотреть командой `SHOW CREATE TABLE`.

  В отличие от синтаксиса создания таблиц Hive, при создании секционированной таблицы в Doris столбцы разделения необходимо включить в схему таблицы. Они должны стоять в конце схемы и сохранять тот же порядок.

  :::tip
  В кластерах Hive, где транзакционные возможности ACID включены по умолчанию, у таблиц, созданных Doris, свойство `transactional` будет равно `true`. Поскольку Doris поддерживает лишь часть возможностей транзакционных таблиц Hive, он может не суметь прочитать созданные им таблицы Hive. Чтобы избежать этого, при создании нетранзакционной таблицы Hive явно укажите `"transactional" = "false"` в её свойствах:

  ```sql
  CREATE TABLE non_acid_table(
    `col1` BOOLEAN COMMENT 'col1',
    `col2` INT COMMENT 'col2',
    `col3` BIGINT COMMENT 'col3'
  ) ENGINE=hive
  PROPERTIES (
    'transactional'='false'
  );
  ```
  :::

- **Удаление таблиц**

  Таблицу Hive можно удалить инструкцией `DROP TABLE`. При удалении таблицы удаляются все её данные, включая данные разделов.

- **Сопоставление типов столбцов**

  Подробнее см. раздел [Сопоставление типов столбцов]. Учитывайте следующие ограничения:

  - Столбцы должны допускать значения NULL по умолчанию; `NOT NULL` не поддерживается.
  - Hive 3.0 поддерживает значения по умолчанию. Чтобы их задать, явно добавьте `"hive.version" = "3.0.0"` в свойства Catalog.
  - Если типы вставляемых данных несовместимы (например, строка `'abc'` вставляется в числовой столбец), значение преобразуется в `null`.

- **Разделение на разделы**

  Типы разделов Hive соответствуют разделам List в Doris. Поэтому при создании секционированной таблицы Hive в Doris используйте синтаксис разделения List, но явно перечислять каждый раздел не нужно. При вставке данных Doris автоматически создаёт соответствующий раздел Hive на основе значений данных. Поддерживаются таблицы с разделением по одному или нескольким столбцам.

- **Форматы файлов**

  - ORC (по умолчанию)
  - Parquet

    При записи типа DATETIME в файл Parquet используется физический тип INT96, а не INT64. Это обеспечивает совместимость с логикой версий Hive до 4.0.

  - Text (поддерживается начиная с версий 2.1.7 и 3.0.3)

      Формат Text поддерживает следующие свойства таблицы:

		  - `field.delim`: разделитель столбцов. По умолчанию — `\1`.
		  - `line.delim`: разделитель строк. По умолчанию — `\n`.
		  - `collection.delim`: разделитель элементов сложных типов. По умолчанию — `\2`.
		  - `mapkey.delim`: разделитель пар ключ–значение в map. По умолчанию — `\3`.
		  - `serialization.null.format`: формат хранения значений `NULL`. По умолчанию — `\N`.
		  - `escape.delim`: символ экранирования. По умолчанию — `\`.

- **Форматы сжатия**

  Следующие кодеки применяются при выборе сжатия для создания таблиц и записи данных через Doris. `plain` означает отсутствие сжатия.

  | Версия Doris | Parquet | ORC |
  | --- | --- | --- |
  | 4.0.x, 4.1.0–4.1.2 | `snappy` (по умолчанию), `zstd`, `plain` | `snappy`, `zlib` (по умолчанию), `zstd`, `plain` |
  | 4.1.3 и последующие выпуски 4.1 | `snappy` (по умолчанию), `zstd`, `plain`, `lz4` | `snappy`, `zlib` (по умолчанию), `zstd`, `plain`, `lz4` |

  Для таблиц, создаваемых через Doris, кодек выбирается свойством `compression`. При записи в существующие таблицы Hive Doris читает свойства таблицы `parquet.compression`, `orc.compress` и `text.compression` для соответствующих форматов файлов.

## Подписка на события Hive Metastore {#subscribing-to-hive-metastore-events}

Узлы FE могут периодически читать события Notification Events из HMS. Это позволяет Doris обнаруживать изменения метаданных таблиц Hive в реальном времени и поддерживать их актуальность. Сейчас поддерживаются следующие события:

| Событие | Действие и соответствующее поведение |
| ---------------- | ------------------------------------------------------------------------- |
| CREATE DATABASE | Создаёт базу данных в соответствующем каталоге данных. |
| DROP DATABASE | Удаляет базу данных в соответствующем каталоге данных. |
| ALTER DATABASE | В основном отражает изменение свойств базы данных, комментариев и расположения хранилища по умолчанию. Эти изменения не влияют на возможность Doris запрашивать внешние каталоги данных, поэтому событие пока игнорируется. |
| CREATE TABLE | Создаёт таблицу в соответствующей базе данных. |
| DROP TABLE | Удаляет таблицу из соответствующей базы данных и сбрасывает кеш таблицы. |
| ALTER TABLE | При переименовании удаляет таблицу со старым именем и создаёт таблицу с новым; в остальных случаях сбрасывает кеш таблицы. |
| ADD PARTITION | Добавляет раздел в кешированный список разделов соответствующей таблицы. |
| DROP PARTITION | Удаляет раздел из кешированного списка разделов и сбрасывает кеш раздела. |
| ALTER PARTITION | При переименовании удаляет раздел со старым именем и создаёт раздел с новым; в остальных случаях сбрасывает кеш раздела. |

:::tip
1. Если импорт данных изменяет файлы, секционированные таблицы вызывают событие `ALTER PARTITION`, а несекционированные — событие `ALTER TABLE`.

2. Если изменять файловую систему напрямую, обходя HMS, HMS не создаст соответствующие события и Doris не обнаружит изменения метаданных.
:::

С этой возможностью связаны следующие параметры в `fe.conf`:

1. `enable_hms_events_incremental_sync`: включает автоматическую инкрементальную синхронизацию метаданных. По умолчанию отключена.

2. `hms_events_polling_interval_ms`: интервал чтения событий; по умолчанию — 10000 миллисекунд.

3. `hms_events_batch_size_per_rpc`: максимальное число событий, считываемых за один вызов RPC; по умолчанию — 500.

Для использования этой возможности (кроме Huawei Cloud MRS) необходимо изменить файл `hive-site.xml` службы HMS и перезапустить HMS и HiveServer2.

```xml
<property>
    <name>hive.metastore.event.db.notification.api.auth</name>
    <value>false</value>
</property>
<property>
    <name>hive.metastore.dml.events</name>
    <value>true</value>
</property>
<property>
    <name>hive.metastore.transactional.event.listeners</name>
    <value>org.apache.hive.hcatalog.listener.DbNotificationListener</value>
</property>
```

Для Huawei Cloud MRS необходимо изменить файл `hivemetastore-site.xml` и перезапустить HMS и HiveServer2.

```xml
<property>
    <name>metastore.transactional.event.listeners</name>
    <value>org.apache.hive.hcatalog.listener.DbNotificationListener</value>
</property>
```

## Приложение {#appendix}

### Механизм транзакций {#transaction-mechanism}

Операции записи в Hive выполняются в отдельной транзакции. До её фиксации данные не видны извне. Операции с соответствующими таблицами становятся видны другим пользователям только после фиксации.

Транзакции обеспечивают атомарность операций: все операции внутри транзакции либо завершаются успешно, либо завершаются неудачей.

Транзакции не могут полностью гарантировать изоляцию операций, но разделение операций файловой системы и операций с метаданными Hive Metastore помогает свести несогласованность к минимуму.

Например, транзакция изменяет несколько разделов таблицы Hive, а задача выполняется двумя пакетами. Первый пакет может стать виден извне до завершения второго: разделы первого пакета уже доступны для чтения, а разделы второго — ещё нет.

Если при фиксации транзакции возникает исключение, она полностью откатывается, включая изменения файлов HDFS и метаданных Hive Metastore. Дополнительных действий от пользователя не требуется.

### Механизм параллельной записи {#concurrent-writing-mechanism}

Сейчас Apache Doris поддерживает параллельную запись с помощью нескольких инструкций вставки. Однако пользователи должны следить за тем, чтобы параллельная запись не приводила к конфликтам.

Обычные нетранзакционные таблицы Hive не имеют полноценного механизма транзакций. Механизм транзакций Apache Doris стремится сократить периоды несогласованности, но не гарантирует полноценные свойства ACID. Поэтому параллельная запись в таблицы Hive через Apache Doris может привести к проблемам согласованности данных.

1. **Параллельные операции `INSERT`**

2. Операции `INSERT` добавляют данные и при параллельном выполнении не конфликтуют, давая ожидаемый результат.

3. **Параллельные операции `INSERT OVERWRITE`**

4. Параллельные операции `INSERT OVERWRITE` с одной таблицей или разделом могут привести к потере или повреждению данных и непредсказуемым результатам.

5. Обычные способы решения:

   * Для секционированных таблиц записывайте данные в разные разделы. Параллельные операции с разными разделами не конфликтуют.

   * Для несекционированных таблиц используйте `INSERT` вместо `INSERT OVERWRITE`, чтобы избежать конфликтов.

   * Для операций, которые могут конфликтовать, на стороне приложения обеспечьте выполнение только одной операции записи в каждый момент времени.

### Операции с файлами HDFS {#hdfs-file-operations}

Данные таблицы Hive в HDFS обычно сначала записываются во временный каталог, а затем окончательно размещаются с помощью операций файловой системы, таких как `rename`. Ниже подробно описаны операции с файлами HDFS для разных видов работы с данными.

Формат временного каталога данных: `/tmp/.doris_staging/<username>/<uuid>`

Формат имени записываемого файла данных: `<query-id>_<uuid>-<index>.<compress-type>.<file-type>`

Примеры файловых операций для различных сценариев:

1. **Несекционированная таблица**

   * **Добавление данных**

     * Каталог целевой таблицы: `hdfs://ns/usr/hive/warehouse/example.db/table1`

     * Временный файл: `hdfs://ns/tmp/.doris_staging/root/f02247cb662846038baae272af5eeb05/b35fdbcea3a4e39-86d1f36987ef1492_7e3985bf-9de9-4fc7-b84e-adf11aa08756-0.orc`

     * На этапе фиксации все временные файлы перемещаются в каталог целевой таблицы.

   * **Перезапись данных**

     * Каталог целевой таблицы: `hdfs://ns/usr/hive/warehouse/example.db/table1`

     * Временный файл: `hdfs://ns/tmp/.doris_staging/root/f02247cb662846038baae272af5eeb05/b35fdbcea3a4e39-86d1f36987ef1492_7e3985bf-9de9-4fc7-b84e-adf11aa08756-0.orc`

     * Действия на этапе фиксации:

       1. Переименовать каталог целевой таблицы во временный каталог: `hdfs://ns/usr/hive/warehouse/example.db/_temp_b35fdbcea3a4e39-86d1f36987ef1492_table1`

       2. Переименовать временный каталог в каталог целевой таблицы.

       3. Удалить временный каталог бывшей целевой таблицы.

2. **Секционированная таблица**

   * **Добавление в новый раздел**

     * Каталог целевой таблицы: `hdfs://ns/usr/hive/warehouse/example.db/table2/part_col=2024-01-01`

     * Временный файл: `hdfs://ns/tmp/.doris_staging/root/a7eac7505d7a42fdb06cb9ef1ea3e912/par1=a/d678a74d232345e0-b659e2fb58e86ffd_549ad677-ee75-4fa1-b8a6-3e821e1dae61-0.orc`

     * На этапе фиксации временный каталог переименовывается в каталог целевой таблицы.

   * **Добавление данных в существующий раздел**

     * Каталог целевой таблицы: `hdfs://ns/usr/hive/warehouse/example.db/table2/part_col=2024-01-01`

     * Временный файл: `hdfs://ns/tmp/.doris_staging/root/a7eac7505d7a42fdb06cb9ef1ea3e912/par1=a/d678a74d232345e0-b659e2fb58e86ffd_549ad677-ee75-4fa1-b8a6-3e821e1dae61-0.orc`

     * На этапе фиксации файлы из временного каталога перемещаются в каталог целевой таблицы.

   * **Перезапись существующего раздела**

     * Каталог целевой таблицы: `hdfs://ns/usr/hive/warehouse/example.db/table2/part_col=2024-01-01`

     * Временный файл: `hdfs://ns/tmp/.doris_staging/root/a7eac7505d7a42fdb06cb9ef1ea3e912/par1=a/d678a74d232345e0-b659e2fb58e86ffd_549ad677-ee75-4fa1-b8a6-3e821e1dae61-0.orc`

     * Действия на этапе фиксации:

       1. Переименовать каталог целевого раздела во временный каталог раздела: `hdfs://ns/usr/hive/warehouse/example.db/table2/_temp_d678a74d232345e0-b659e2fb58e86ffd_part_col=2024-01-01`

       2. Переименовать временный каталог раздела в каталог целевого раздела.

       3. Удалить временный каталог бывшего целевого раздела.
