Doris поддерживает доступ к данным таблиц Iceberg через различные службы метаданных. Помимо чтения данных, Doris также поддерживает запись в таблицы Iceberg, включая INSERT, INSERT OVERWRITE, UPDATE, DELETE и MERGE INTO.

[Быстрый старт с Apache Doris и Apache Iceberg](../best-practices/doris-iceberg.md).

:::tip
Пользователи могут обращаться к таблицам Iceberg, использующим Hive Metastore для хранения метаданных, через Hive Catalog. Однако рекомендуется использовать непосредственно Iceberg Catalog, чтобы избежать некоторых проблем совместимости.
:::

## Сценарии использования {#applicable-scenarios}

| Сценарий    | Описание                                                                 |
| ----------- | --------------------------------------------------------------------------- |
| Ускорение запросов | Используйте распределённый вычислительный движок Doris для прямого доступа к данным Iceberg и ускорения запросов.      |
| Интеграция данных  | Читайте данные Iceberg и записывайте их во внутренние таблицы Doris или выполняйте операции ZeroETL с помощью вычислительного движка Doris. |
| Обратная запись данных   | Обрабатывайте данные из любого источника, поддерживаемого Doris, и записывайте их обратно в хранилище таблиц Iceberg.       |

## Настройка Catalog {#configuring-catalog}

### Синтаксис {#syntax}

```sql
CREATE CATALOG [IF NOT EXISTS] catalog_name PROPERTIES (
    'type' = 'iceberg',
    'iceberg.catalog.type' = '<iceberg_catalog_type>',
    'warehouse' = '<warehouse>', --optional
    {MetaStoreProperties},
    {StorageProperties},
    {IcebergProperties},
    {CommonProperties}
);
```

* `<iceberg_catalog_type>`

  Тип Iceberg Catalog. Поддерживаются следующие варианты:

  * `hms`: использует Hive Metastore в качестве службы метаданных.

  * `rest`: служба метаданных, совместимая с интерфейсом Iceberg Rest Catalog.

  * `hadoop`: обеспечивает прямой доступ к метаданным, хранящимся в файловой системе.

  * `glue`: использует AWS Glue в качестве службы метаданных.

  * `dlf`: использует Alibaba Cloud DLF в качестве службы метаданных.

  * `jdbc`: использует Iceberg JDBC Catalog в качестве службы метаданных.

  * `s3tables`: использует AWS S3 Tables Catalog для доступа к [S3 Table Bucket](https://aws.amazon.com/s3/features/tables/).

* `<warehouse>`

  Путь к хранилищу Iceberg. Этот параметр обязателен, если `<iceberg_catalog_type>` имеет значение `hadoop`.

  Путь `warehouse` должен указывать на уровень выше пути `Database`. Например, если путь к таблице — `s3://bucket/path/to/db1/table1`, то `warehouse` должен иметь значение `s3://bucket/path/to/`.

* `{MetaStoreProperties}`

  Раздел MetaStoreProperties предназначен для указания параметров подключения и аутентификации службы метаданных Metastore. См. раздел [Поддерживаемые службы метаданных].

* `{StorageProperties}`

  Раздел StorageProperties предназначен для указания параметров подключения и аутентификации системы хранения. См. раздел [Поддерживаемые системы хранения].

* `{IcebergProperties}`

  Раздел IcebergProperties предназначен для параметров, специфичных для Iceberg Catalog.

    - `list-all-tables`

        Применяется к Iceberg Catalog, использующему Hive Metastore в качестве службы метаданных. Значение по умолчанию — `true`. По умолчанию операция `SHOW TABLES` выводит таблицы всех типов в текущей базе данных (Hive Metastore может хранить таблицы, не относящиеся к Iceberg). Этот подход обеспечивает наилучшую производительность.

        Если задано значение `false`, Doris поочерёдно проверяет тип каждой таблицы и возвращает только таблицы Iceberg. При большом количестве таблиц этот режим работает медленно.

    - `iceberg.rest.view-enabled`

        Поддерживается начиная с версии 4.0.6.

        Действует только для Iceberg REST Catalog. Определяет, включены ли операции с представлениями (включая `listViews`, `loadView`, `viewExists`, `dropView` и т. д.). Значение по умолчанию — `true`.

        Некоторые реализации Iceberg REST Catalog предоставляют API таблиц, но API представлений в них недоступны или возвращают ошибки. При выполнении `SHOW TABLES` Doris вызывает `ViewCatalog.listViews()`, чтобы исключить представления из списка таблиц, поэтому такие службы REST могут приводить к сбоям `SHOW TABLES` и загрузки метаданных таблиц.

        В этом случае установите параметр в `false`, и Doris будет пропускать все операции с представлениями, что позволит операциям с метаданными, таким как `SHOW TABLES`, работать корректно.

* `{CommonProperties}`

  Раздел CommonProperties предназначен для общих свойств. Подробнее об общих свойствах см. в разделе [Обзор Catalog](../catalog-overview.md).

## Кэш метаданных {#meta-cache}

Для ускорения доступа к внешним источникам данных Apache Doris кэширует метаданные Iceberg. К ним относятся загруженные метаданные таблиц, данные разделов, манифесты, производные проекции разделов, идентификатор последнего снимка и определённый формат файлов.

:::tip
В версиях до Doris 4.1.x кэширование метаданных в основном управляется глобально с помощью параметров конфигурации FE. Подробнее см. в разделе [Кэш метаданных](../meta-cache.md).
Начиная с Doris 4.1.x, кэш внешних метаданных Iceberg Catalog настраивается с помощью унифицированных ключей `meta.cache.*`. Приведённые ниже элементы относятся к текущей версии; Doris 4.1.x и 4.2.x используют другой набор элементов, описанный в версии 4.x этой страницы.
:::

### Настройка свойств кэша {#meta-cache-unified-model}

Для каждого элемента кэша используется унифицированный формат ключей конфигурации: `meta.cache.<engine>.<entry>.{enable,ttl-second,capacity,max-weight}`. Для Iceberg значение `<engine>` — `iceberg`. Параметр `meta.cache.iceberg.table.ttl-second` задаёт общий TTL: это TTL по умолчанию для элементов `table` и `partition`, а также TTL кэшей без собственного токена `<entry>`. Значение `0` отключает их все, поэтому каждый запрос напрямую считывает последний снимок.

| Свойство | Пример | Значение |
|---|---|---|
| `enable` | `true/false` | Включает или отключает этот элемент кэша. |
| `ttl-second` | `600`, `0`, `-1` | `0` отключает элемент (действует немедленно, можно использовать для просмотра последних данных); `-1` означает отсутствие срока действия; другие положительные целые числа задают TTL в секундах с момента доступа. |
| `capacity` | `10000` | Максимальное количество записей кэша. `0` отключает элемент. |
| `max-weight` | `1GB` | Поддерживается начиная с Doris 4.1.4. Необязательное ограничение оценочного объёма памяти, удерживаемой элементом. Должно быть положительным; `0` не допускается. Принимается только элементами, отмеченными ниже. |

**Условия действия:** элемент действует, если `enable=true`, `ttl-second != 0` и `capacity > 0`. Ограничение памяти на уровне FE, Catalog или элемента дополнительно регулирует добавление записей на основе оценки памяти; см. [Управление памятью кэша внешних метаданных](../external-meta-cache-memory-management).

### Модули кэша {#meta-cache-unified-modules}

Следующие элементы имеют собственные ключи конфигурации и принимают `max-weight`:

| Элемент (`<entry>`) | Префикс ключа свойства | `ENTRY_NAME` | Кэшируемое содержимое и влияние | Значения по умолчанию: включение / TTL / ёмкость |
|---|---|---|---|---|
| `table` | `meta.cache.iceberg.table.` | `iceberg-table` | Загруженные метаданные таблиц Iceberg. Влияние: сокращает число обращений к Catalog и чтений файлов метаданных. | `true` / 86400 с / 1000 |
| `partition` | `meta.cache.iceberg.partition.` | `iceberg-partition` | Необработанные данные разделов снимка таблицы. | `true` / как у `table` / 1000 |
| `manifest` | `meta.cache.iceberg.manifest.` | `iceberg-manifest` | Разобранное содержимое манифестов. При планировании сканирования используется только при значении `enable`, равном `true`; значение по умолчанию — `false`. | `true` для самого кэша, `false` для его использования / без срока действия / 100000 |
| `partition_view` | `meta.cache.iceberg.partition_view.` | `iceberg.mvcc-partition-view`, `iceberg.list-partitions-view` | Две производные проекции разделов с общим ограничением количества записей. | `true` / 86400 с / 1000 |

Следующие кэши не имеют токена `<entry>`. Они подчиняются ограничениям памяти Catalog и FE, а их TTL определяется параметром `meta.cache.iceberg.table.ttl-second`: `iceberg-latest-snapshot` (идентификатор последнего снимка), `iceberg-format` (определённый формат файлов), `iceberg-comment` (комментарии таблиц; создаётся только для REST Catalog с выдаваемыми учётными данными) и `iceberg-equality-delete-field-ids`.

Схема столбцов таблиц Iceberg кэшируется общим движком `default` (`meta.cache.default.schema.*`).

:::note
Если `iceberg.rest.session` имеет значение `user`, кэши `table`, `partition`, `partition_view`, latest-snapshot и format не создаются, поскольку общий кэш обходил бы индивидуальную авторизацию пользователей. REST Catalog с выдаваемыми учётными данными также не создаёт кэш `table`.
:::

### Сопоставление и преобразование устаревших параметров {#meta-cache-mapping}

| Устаревший ключ свойства | Унифицированный ключ | Описание |
|---|---|---|
| `schema.cache.ttl-second` | `meta.cache.default.schema.ttl-second` | Срок действия кэша схемы таблицы |

### Рекомендации {#meta-cache-best-practices}

* **Доступ к последним данным в реальном времени**: если каждый запрос должен видеть последний снимок таблиц Iceberg, задайте для `meta.cache.iceberg.table.ttl-second` значение `0`.
  ```sql
  -- Disable the table, partition, latest-snapshot, and format caches to read the latest snapshot live
  ALTER CATALOG iceberg_ctl SET PROPERTIES ("meta.cache.iceberg.table.ttl-second" = "0");
  ```
* **Оптимизация производительности**:
    * Включение кэша манифестов может существенно ускорить планирование запросов для больших таблиц. Если манифесты велики, ограничьте память кэша с помощью `max-weight`:
      ```sql
      ALTER CATALOG iceberg_ctl SET PROPERTIES (
        "meta.cache.iceberg.manifest.enable" = "true",
        "meta.cache.iceberg.manifest.max-weight" = "1GB"
      );
      ```
    * Успешное изменение свойства Catalog удаляет затронутые кэши метаданных и пересоздаёт их с новой конфигурацией при следующем обращении. Изменение `meta.cache.max-weight` или `schema.cache.ttl-second` удаляет все кэши Catalog; изменение `meta.cache.<engine>.<entry>.*` удаляет кэши соответствующего движка. Уже выполняющиеся запросы не затрагиваются.

### Наблюдаемость {#meta-cache-unified-observability}

Метрики кэша доступны в системной таблице `information_schema.catalog_meta_cache_statistics`. Столбец `ENTRY_NAME` содержит имена, перечисленные в таблице выше, а строка движка `default` соответствует общему кэшу схем таблиц:

```sql
SELECT engine_name, entry_name,
       effective_enabled, ttl_second, capacity,
       estimated_size, hit_rate, max_weight, estimated_weight
FROM information_schema.catalog_meta_cache_statistics
WHERE catalog_name = 'iceberg_ctl'
ORDER BY engine_name, entry_name;
```

См. документацию этой системной таблицы: [catalog_meta_cache_statistics](../../admin-manual/system-tables/information_schema/catalog_meta_cache_statistics.md).

### Ошибки метаданных и чтения (начиная с 4.1.5) {#metadata-and-read-errors-since-415}

- `DESCRIBE`, `SHOW COLUMNS` и `SHOW CREATE TABLE` сохраняют объявления обязательных и необязательных полей текущей схемы Iceberg. При сканировании по-прежнему обрабатываются поля, отсутствующие из-за эволюции схемы; отображаемое объявление NOT NULL не гарантирует, что поле существует в каждом историческом файле.
- Версия dev передаёт метаданные разделов для записи на уровне строк в виде сериализованных данных разделов. Ошибка версии 4.1.5 `Cannot produce Iceberg row IDs with unsupported partition types in spec ...` относится к прежнему представлению Row ID и не применима к текущему представлению.
- Отсутствие файла данных или файла удалений, на который ссылается зафиксированный снимок, приводит к сбою запроса, даже если задано `ignore_not_found_file_in_external_table=true`. Восстановите отсутствующий объект или выберите допустимый снимок с полным набором файлов.
- `schema.name-mapping.default` должен содержать допустимый массив JSON Iceberg Name Mapping. Недопустимое значение приводит к сбою сканирования данных вместо перехода к текущим именам столбцов и возврата NULL. Исправьте или удалите это свойство с помощью системы записи, например Spark, затем обновите таблицу в Doris. Запросы к системным таблицам метаданных не выполняют эту проверку сканирования данных.

Начиная с версии 4.1.4, формат определяется для каждого файла данных (split), поэтому **запросы к одной таблице Iceberg, содержащей одновременно файлы данных Parquet и ORC, выполняются корректно**.

Начиная с версии 4.1.4, метаданные разделов Iceberg с преобразованием identity передаются с каждым split, а ключи разделов в пути охватывают столбцы identity всех спецификаций партиционирования таблицы. Благодаря этому значения столбцов разделов также корректно возвращаются для таблиц, прошедших **эволюцию партиционирования**.

### Регистр имён столбцов {#column-name-case}

Doris сохраняет исходный регистр имён столбцов таблицы Iceberg и сопоставляет столбцы при чтении без учёта регистра. Запросы к столбцам, имена которых содержат прописные буквы или смешанный регистр (например, `UserId` или `ORDER_ID`), выполняются корректно.

:::info Примечание о версиях

В версиях ветки 4.0 до 4.0.8 столбцы при чтении определялись по точному совпадению имён, поэтому в таблицах Iceberg и Paimon с именами столбцов в смешанном регистре мог считываться неверный столбец или возникать ошибка запроса. Это исправлено в 4.0.8.

:::

## Сопоставление пространств имён {#namespace-mapping}

Иерархия метаданных Iceberg: Catalog -> Namespace -> Table. Пространство имён может иметь несколько уровней (Nested Namespace).

```
      ┌─────────┐             
      │ Catalog │             
      └────┬────┘             
           │                  
     ┌─────┴─────┐            
  ┌──▼──┐     ┌──▼──┐         
  │ NS1 │     │ NS2 │         
  └──┬──┘     └──┬──┘         
     │           │            
┌────▼───┐    ┌──▼──┐         
│ Table1 │    │ NS3 │         
└────────┘    └──┬──┘         
                 │            
          ┌──────┴───────┐    
     ┌────▼───┐     ┌────▼───┐
     │ Table2 │     │ Table3 │
     └────────┘     └────────┘
```


Начиная с версии 3.1.2, Doris поддерживает сопоставление вложенных пространств имён для Iceberg Rest Catalog.

В приведённом выше примере таблицы сопоставляются с метаданными Doris следующим образом:

| Catalog | База данных | Таблица |
| --- | --- | --- |
| Catalog | NS1 | Table1 |
| Catalog | NS2.NS3 | Table2 |
| Catalog | NS2.NS3 | Table3 |

Поддержку вложенных пространств имён необходимо включить явно. Подробнее см. в разделе [Iceberg Rest Catalog](../metastores/iceberg-rest.md)

### Iceberg Rest Catalog {#iceberg-rest-catalog}

:::caution Изменение поведения (4.1.4)

Начиная с версии 4.1.4, если для `iceberg.rest.signing-name` задана управляемая служба подписи, например `glue`, `s3tables` или `osstables`, **обязательно** нужно также задать `'iceberg.rest.sigv4-enabled' = 'true'`. В противном случае создание Catalog завершается ошибкой:

```text
Rest Catalog requires sigv4-enabled set to true when signing-name is <name>
```

Если в существующем Catalog задан только `signing-name`, а `sigv4-enabled` не включён, после обновления проверка завершается ошибкой и это свойство необходимо добавить.

При использовании `osstables` обязательны и `iceberg.rest.signing-region`, и `iceberg.rest.sigv4-enabled = 'true'`. В противном случае возвращается следующая ошибка:

```text

```

## Операции запросов {#query-operations}

### Базовый запрос {#basic-query}

```sql
-- 1. switch to catalog, use database and query
SWITCH iceberg;
USE iceberg_db;
SELECT * FROM iceberg_tbl LIMIT 10;

-- 2. use iceberg database directly
USE iceberg.iceberg_db;
SELECT * FROM iceberg_tbl LIMIT 10;

-- 3. use full qualified name to query
SELECT * FROM iceberg.iceberg_db.iceberg_tbl LIMIT 10;
```

### Столбцы метаданных файлов {#file-metadata-columns}

> Поддерживается начиная с версии 4.2.0.

Doris предоставляет два скрытых столбца метаданных для таблиц данных Iceberg. С их помощью можно определить физический файл данных и строку, из которых получен каждый результат запроса.

| Столбец | Тип | Описание |
| --- | --- | --- |
| `_file` | `STRING NOT NULL` | Исходный путь, записанный для файла данных Iceberg. |
| `_pos` | `BIGINT NOT NULL` | Физическая позиция строки во всём файле данных, отсчитываемая с нуля. |

Предварительные условия: настройте Iceberg Catalog, как описано в предыдущих примерах, и создайте таблицу данных Iceberg, содержащую столбец `id` и использующую файлы Parquet или ORC. В следующем запросе предполагается, что `iceberg_tbl` уже содержит строки со значениями `id`, равными `1` и `2`:

```sql
SELECT id, `_file`, `_pos`
FROM iceberg.iceberg_db.iceberg_tbl
ORDER BY `_file`, `_pos`;
```

Пример результата (путь к файлу зависит от расположения таблицы):

```text
+----+---------------------------------------+------+
| id | _file                                 | _pos |
+----+---------------------------------------+------+
|  1 | s3://bucket/warehouse/db/table/a.orc |    0 |
|  2 | s3://bucket/warehouse/db/table/a.orc |    1 |
+----+---------------------------------------+------+
```

По умолчанию эти столбцы не отображаются в `SELECT *` или `DESC`.

Чтобы включить скрытые столбцы в `SELECT *` и `DESC`, включите `show_hidden_columns` для сеанса:

```sql
SET show_hidden_columns = true;
```

Связанные переменные сеанса:

| Переменная | Тип | По умолчанию | Обязательна | Действие |
| --- | --- | --- | --- | --- |
| `show_hidden_columns` | `BOOLEAN` | `false` | Нет | Включает скрытые столбцы в `SELECT *` и `DESC`. Не требуется, если столбцы указаны явно. |
| `enable_file_scanner_v2` | `BOOLEAN` | `true` | Нет | Должна оставаться включённой, если запрос обращается к этим столбцам метаданных. |
| `force_jni_scanner` | `BOOLEAN` | `false` | Нет | Должна оставаться отключённой, поскольку модуль чтения JNI не может формировать эти столбцы метаданных. |

Позиция строки определяется относительно всего физического файла. Фильтрация по предикатам, обработка удалений и разбиение сканирования не изменяют нумерацию оставшихся строк. Поэтому сочетание `_file` и `_pos` позволяет найти физическую запись в текущем снимке таблицы. Перезапись или компактация файлов данных может изменить оба значения, поэтому их нельзя использовать как стабильный логический идентификатор строки.

:::caution
Эти столбцы доступны только при чтении таблицы данных Iceberg через нативный модуль чтения Parquet или ORC в FileScannerV2. Запрос, обращающийся к ним, завершается ошибкой, если `enable_file_scanner_v2` отключена, `force_jni_scanner` включена или выбранные файлы данных нельзя прочитать нативным модулем Parquet/ORC.

`_file` и `_pos` — зарезервированные имена, сравниваемые без учёта регистра. Не используйте их как имена физических столбцов таблицы Iceberg.
:::

### Чтение исторических данных {#time-travel}

Можно прочитать определённый снимок таблицы Iceberg.

По умолчанию запросы на чтение обращаются к последней версии снимка.

Получить сведения о снимках таблицы Iceberg можно с помощью системной таблицы `$snapshots`:

:::caution Изменение поведения (4.1.4)

Начиная с версии 4.1.4, табличная функция `iceberg_meta()` удалена. Для запросов метаданных используйте системные таблицы Iceberg (например, `iceberg_tbl$snapshots`). См. раздел [Системные таблицы](#system-tables) ниже.

:::

```sql
SELECT * FROM iceberg_ctl.iceberg_db.iceberg_tbl$snapshots\G

      summary: {"added-data-files":"2","added-records":"3","added-files-size":"2742","changed-partition-count":"2","total-records":"3","total-files-size":"2742","total-data-files":"2","total-delete-files":"0","total-position-deletes":"0","total-equality-deletes":"0"}
*************************** 2. row ***************************
 committed_at: 2024-11-28 11:10:11
  snapshot_id: 6099853805930794326
    parent_id: 8903826400153112036
    operation: append

```

Предложения `FOR TIME AS OF` и `FOR VERSION AS OF` позволяют читать исторические данные по идентификатору снимка или времени его создания. Примеры:

```sql
-- Read data as of a specific timestamp
SELECT * FROM iceberg_table FOR TIME AS OF '2023-01-01 00:00:00';

-- Read data as of a specific snapshot ID
SELECT * FROM iceberg_table FOR VERSION AS OF 123456789;
```

Начиная с 4.1.5, `FOR TIME AS OF` принимает от 1 до 9 цифр дробной части секунды после `yyyy-MM-dd HH:mm:ss`, интерпретирует значение в часовом поясе сеанса и преобразует его в миллисекунды для выбора снимка. Например, используйте `FOR TIME AS OF '2024-01-01 12:00:00.123456'`. Снимок выбирается с точностью до миллисекунды; поддержка этого синтаксиса не означает сохранения времени снимков с точностью до наносекунды.

Doris 4.1.5 также исправляет чтение исторических снимков после переименования и удаления столбцов, расширения типов и эволюции партиционирования. Каждый файл интерпретируется с использованием спецификации партиционирования, действовавшей при его записи, а не только текущей спецификации. Исторические запросы не должны переписываться для чтения текущих материализованных представлений.

### Ветви и теги {#branch-and-tag}

> Начиная с 3.1.0.
>
> О создании, удалении и управлении ветвями и тегами см. раздел [Управление ветвями и тегами].

Поддерживается чтение определённых ветвей и тегов таблиц Iceberg.

Для совместимости с такими системами, как Spark/Trino, поддерживается несколько вариантов синтаксиса.

```sql
-- BRANCH
SELECT * FROM iceberg_tbl@branch(branch1);
SELECT * FROM iceberg_tbl@branch("name" = "branch1");
SELECT * FROM iceberg_tbl FOR VERSION AS OF 'branch1';

-- TAG
SELECT * FROM iceberg_tbl@tag(tag1);
SELECT * FROM iceberg_tbl@tag("name" = "tag1");
SELECT * FROM iceberg_tbl FOR VERSION AS OF 'tag1';
```

При использовании синтаксиса `FOR VERSION AS OF` Doris автоматически определяет, является ли параметр временной меткой или именем ветви/тега.

### Представления {#view}

> Начиная с 3.1.0

Поддерживаются запросы к представлениям Iceberg. Запросы к представлениям выполняются так же, как запросы к обычным таблицам. Учитывайте следующее:

- Поддерживается только Iceberg Catalog типа `hms`.
- SQL определения представления должен быть совместим с диалектом SQL Doris, иначе возникнут ошибки разбора. (Преобразование диалектов будет доступно в будущих версиях).

### Скрытые столбцы Iceberg V3 (Row Lineage) {#iceberg-v3-hidden-columns-row-lineage}

:::tip
Это экспериментальная возможность, поддерживаемая начиная с версии 4.1.0.
:::

Doris поддерживает запросы к скрытым столбцам Row Lineage таблиц Iceberg V3. Iceberg V3 вводит системные скрытые столбцы с данными о происхождении строк, которые используются для отслеживания изменений данных. Это особенно удобно для инкрементальной синхронизации и аудита данных:

- `_row_id`: числовое значение, однозначно идентифицирующее строку данных (формируется на основе файла и позиции, в которые записаны данные).
- `_last_updated_sequence_number`: Sequence Number последнего изменения этой строки. Когда операция `UPDATE` или `MERGE INTO` обновляет данные, это числовое значение автоматически увеличивается вместе с номером версии.

**Как запрашивать скрытые столбцы:**

По умолчанию скрытые столбцы не видны при использовании `DESC` или `SELECT *`. Их можно запросить явно, указав имена столбцов напрямую:

```sql
SELECT id, _row_id, _last_updated_sequence_number FROM iceberg_tbl;
```

Скрытые столбцы также можно сделать видимыми в стандартном выводе (например, `DESC` и `SELECT *`), включив переменную сеанса `show_hidden_columns`:

```sql
SET show_hidden_columns = true;
DESC iceberg_tbl;
```

**Примечания:**

1. Версия формата таблицы Iceberg (`format-version`) должна иметь значение `3`, чтобы эти параметры уровня строк формировались. Запросы к столбцам происхождения строк в таблицах форматов V1 и V2 могут приводить к ошибкам.
2. Скрытые столбцы поддерживаются системой. Пользователям запрещено явно указывать столбцы `_row_id` или `_last_updated_sequence_number` либо записывать в них данные с помощью операторов записи, таких как `INSERT`. Начиная с версии 4.1.4, указание столбца происхождения строк в списке столбцов оператора `INSERT` для таблицы с `format-version >= 3` сразу приводит к ошибке: `Cannot specify invisible column '<name>' in INSERT statement`.

### Значения по умолчанию в Iceberg V3 {#iceberg-v3-default-values}

> Поддерживается начиная с версии 4.1.4.

Iceberg V3 определяет два вида значений столбцов по умолчанию, и Doris поддерживает оба:

- `initial-default`: значение по умолчанию, назначаемое **существующим историческим данным** при добавлении столбца. При чтении старого файла данных, записанного до появления столбца, Doris возвращает это значение вместо NULL. Поддерживается для Parquet и ORC и распространяется на столбцы верхнего уровня, вложенные поля внутри `STRUCT` и сложные родительские столбцы, отсутствующие целиком. Оно также применяется при вычислении предикатов.
- `write-default`: значение по умолчанию, подставляемое для **столбцов, не указанных** при записи. При использовании `INSERT INTO t (subset of columns) VALUES (...)` неуказанные столбцы записываются с текущим значением `write-default` (в более ранних версиях записывался NULL).

**Указание значения по умолчанию через DDL:**

```sql
ALTER TABLE iceberg_tbl ADD COLUMN c1 INT DEFAULT 10;
```

Этот оператор задаёт и `write-default`, и `initial-default` в Iceberg. Он **требует, чтобы `format-version` таблицы имел значение `3`**; таблицы V1 и V2 не поддерживают столбцы со значением по умолчанию, отличным от NULL.

**Выражение `DEFAULT()`:**

Начиная с версии 4.1.4, выражение `DEFAULT(<column>)` позволяет явно обращаться к значению столбца по умолчанию в DML. Его можно использовать в `INSERT`, `UPDATE ... SET` и в каждой ветви `MERGE INTO`:

```sql
INSERT INTO iceberg_tbl VALUES (1, DEFAULT(c1));

UPDATE iceberg_tbl SET c1 = DEFAULT(c1) WHERE id = 1;

MERGE INTO iceberg_tbl t USING src s ON t.id = s.id
WHEN NOT MATCHED THEN INSERT VALUES (s.id, DEFAULT(c1));
```

Семантика:

- Для целевой таблицы Iceberg выражение `DEFAULT()` разрешается по схеме Iceberg, зафиксированной для этой записи. Обращение к столбцу, не входящему в целевую таблицу записи, приводит к ошибке `DEFAULT requires a target column reference` или `Cannot find column information for DEFAULT(<col>)`.
- Для столбца, не относящегося к Iceberg, используется его значение по умолчанию. Если у столбца нет значения по умолчанию и он имеет атрибут NOT NULL или является автоинкрементным, возвращается ошибка `Column '<name>' has no default value and does not allow NULL or column is auto-increment`. Если столбец допускает NULL и не имеет значения по умолчанию, используется NULL.
- Другие ошибки: `DEFAULT requires a column reference, but got: <expr>` и `DEFAULT cannot be used on generated column '<name>'`.

:::info Примечание

Свойство Iceberg `write-default` относится к стороне записи коннектора. Оно **не** отображается через `DESCRIBE`, `SHOW CREATE TABLE` или `information_schema.columns.COLUMN_DEFAULT`.

:::

## Системные таблицы {#system-tables}

> Начиная с 3.1.0

Doris поддерживает запросы к системным таблицам Iceberg для получения метаданных таблиц. Системные таблицы позволяют просматривать историю снимков, файлы манифестов, файлы данных, разделы и другие метаданные.

Для доступа к метаданным таблицы Iceberg добавьте к имени таблицы символ `$`, а затем имя системной таблицы:

```sql
SELECT * FROM iceberg_table$system_table_name;
```

Например, для просмотра истории таблицы выполните:

```sql
SELECT * FROM iceberg_table$history;
```

> Системная таблица `all_manifests` поддерживается начиная с версии 4.0.4.
>
> Системная таблица `position_deletes` поддерживается начиная с версии 4.1.4.

:::caution Изменение поведения (4.1.4)

Начиная с версии 4.1.4, запросы к системным таблицам Iceberg выполняются по нативному пути выполнения, а табличная функция `iceberg_meta()` **удалена**. Вместо неё используйте синтаксис системных таблиц `<table>$<system_table_name>`. См. [ICEBERG_META](../../sql-manual/sql-functions/table-valued-functions/iceberg-meta.md).

Синтаксис доступа к самим системным таблицам и возвращаемые ими результаты не изменились. Кроме того, системные таблицы теперь поддерживают `SHOW CREATE TABLE`.

:::

### entries {#entries}

Показывает все записи манифестов для текущего снимка таблицы:

`all_entries` и `entries` похожи, но `all_entries` содержит записи из всех снимков, а `entries` — только из текущего снимка.

```sql
SELECT * FROM iceberg_table$entries;
```

Результат:

## Операции записи {#write-operations}

### INSERT INTO {#insert-into}

Операция INSERT добавляет данные в целевую таблицу.

Например:

```sql
INSERT INTO iceberg_tbl VALUES (val1, val2, val3, val4);
INSERT INTO iceberg.iceberg_db.iceberg_tbl SELECT col1, col2 FROM internal.db1.tbl1;

INSERT INTO iceberg_tbl(col1, col2) VALUES (val1, val2);
INSERT INTO iceberg_tbl(col1, col2, partition_col1, partition_col2) VALUES (1, 2, 'beijing', '2023-12-12');
```

Начиная с версии 3.1.0, поддерживается запись данных в указанные ветви:

```sql
INSERT INTO iceberg_tbl@branch(b1) values (val1, val2, val3, val4);
INSERT INTO iceberg_tbl@branch(b1) (col3, col4) values (val3, val4);
```

### INSERT OVERWRITE {#insert-overwrite}

Операция INSERT OVERWRITE полностью заменяет существующие данные таблицы новыми.

```sql
INSERT OVERWRITE TABLE iceberg_tbl VALUES (val1, val2, val3, val4);
INSERT OVERWRITE TABLE iceberg.iceberg_db.iceberg_tbl(col1, col2) SELECT col1, col2 FROM internal.db1.tbl1;
```

Начиная с версии 3.1.0, поддерживается запись данных в указанные ветви:

```sql
INSERT OVERWRITE TABLE iceberg_tbl@branch(b1) values (val1, val2, val3, val4);
INSERT OVERWRITE TABLE iceberg_tbl@branch(b1) (col3, col4) values (val3, val4);
```

Начиная с версии 4.1.0, поддерживается запись данных в статические разделы (или в гибридном режиме):

```sql
-- Full Static Partition
INSERT OVERWRITE TABLE iceberg_tbl PARTITION (dt='2025-01-25', region='bj')
SELECT id, name FROM source_table;

-- Hybrid Partition Mode: "dt" is static, "region" comes from SELECT dynamically
INSERT OVERWRITE TABLE iceberg_tbl PARTITION (dt='2025-01-25')
SELECT id, name, region FROM source_table;
```

### CTAS {#ctas}

Создать таблицу Iceberg и записать в неё данные можно с помощью оператора `CTAS` (Create Table As Select):

```sql
CREATE TABLE iceberg_ctas AS SELECT * FROM other_table;
```

CTAS поддерживает указание форматов файлов, партиционирования и других свойств:

```sql
CREATE TABLE iceberg_ctas
PARTITION BY LIST (pt1, pt2) ()
AS SELECT col1, pt1, pt2 FROM part_ctas_src WHERE col1 > 0;

CREATE TABLE iceberg.iceberg_db.iceberg_ctas (col1, col2, pt1)
PARTITION BY LIST (pt1) ()
PROPERTIES (
    'write-format'='parquet',
    'compression-codec'='zstd'
)
AS SELECT col1, pt1 AS col2, pt2 AS pt1 FROM test_ctas.part_ctas_src WHERE col1 > 0;
```

> Начиная с 3.1.0

```sql
INSERT INTO iceberg_table@branch(b1) SELECT * FROM other_table;
INSERT OVERWRITE TABLE iceberg_table@branch(b1) SELECT * FROM other_table;
```

### DELETE {#delete}

:::tip
Это экспериментальная возможность, поддерживаемая начиная с версии 4.1.0.
:::

Операция `DELETE` удаляет из таблицы Iceberg строки данных, соответствующие заданным условиям. В её основе лежат следующие механизмы: для таблиц формата V2 система записывает файлы Position Delete; для таблиц формата V3 система записывает файлы Deletion Vectors в формате Puffin.

**Предварительные условия:**

- Версия формата таблицы Iceberg (`format-version`) должна быть 2 или выше. Таблицы формата V1 не поддерживают операцию `DELETE`.

**Синтаксис:**

```sql
DELETE FROM iceberg_tbl WHERE <condition>;
```

**Примеры:**

```sql
-- Delete a single row
DELETE FROM iceberg_tbl WHERE id = 1;

-- Delete using multiple conditions
DELETE FROM iceberg_tbl WHERE age > 30 AND name = 'Bob';

-- Delete using a subquery
DELETE FROM iceberg_tbl WHERE id IN (SELECT id FROM other_table WHERE status = 'inactive');
```

Для партиционированных таблиц используется тот же синтаксис:

```sql
DELETE FROM iceberg_partition_tbl WHERE id = 10;
```

### UPDATE {#update}

:::tip
Это экспериментальная возможность, поддерживаемая начиная с версии 4.1.0.
:::

Операция `UPDATE` изменяет строки данных таблицы Iceberg, соответствующие заданным условиям. Сначала система записывает сведения для отслеживания удалений (с помощью файлов Position Delete для V2 и Deletion Vectors в формате Puffin для V3), чтобы пометить старые строки данных как недействительные, а затем добавляет новые файлы с обновлёнными данными (если включён формат V3, значение отслеживания `_last_updated_sequence_number` вновь вставленной строки автоматически увеличивается).

**Предварительные условия:**

- Версия формата таблицы Iceberg (`format-version`) должна быть 2 или выше. Таблицы формата V1 не поддерживают операцию `UPDATE`.

**Синтаксис:**

```sql
UPDATE iceberg_tbl SET <column1> = <value1> [, <column2> = <value2>, ...] WHERE <condition>;
```

**Примеры:**

```sql
-- Update a single column
UPDATE iceberg_tbl SET name = 'Alice_new' WHERE id = 1;

-- Update multiple columns
UPDATE iceberg_tbl SET name = 'Updated', age = 28 WHERE id = 2;

-- Update using expressions
UPDATE iceberg_tbl SET age = age * 2 + 1, name = concat(name, '-modified') WHERE id = 3;

-- Update using a subquery as condition
UPDATE iceberg_tbl SET name = 'UpdatedViaSubquery' WHERE id IN (SELECT id FROM other_table);
```

Для партиционированных таблиц используется тот же синтаксис:

```sql
UPDATE iceberg_partition_tbl SET name = 'Updated' WHERE id = 10;
```

### MERGE INTO {#merge-into}

:::tip
Это экспериментальная возможность, поддерживаемая начиная с версии 4.1.0.
:::

Операция `MERGE INTO` сопоставляет исходные данные с целевой таблицей Iceberg и выполняет вставку, обновление или удаление в зависимости от результатов сопоставления. Она подходит для таких сценариев, как синхронизация данных и инкрементальные обновления.

**Предварительные условия:**

- Версия формата таблицы Iceberg (`format-version`) должна быть 2 или выше. Таблицы формата V1 не поддерживают операцию `MERGE INTO`.

**Синтаксис:**

```sql
MERGE INTO target_table t
USING <source> s
ON <merge_condition>
[WHEN MATCHED [AND <condition>] THEN DELETE]
[WHEN MATCHED [AND <condition>] THEN UPDATE SET <column1> = <value1> [, ...]]
[WHEN NOT MATCHED [AND <condition>] THEN INSERT (<columns>) VALUES (<values>)]
```

Здесь `<source>` может быть подзапросом или другой таблицей.

**Примеры:**

- Полная операция сопоставления (включает обновление, удаление и вставку):

    ```sql
    MERGE INTO iceberg_tbl t
    USING (
        SELECT 1 AS id, 'Alice_new' AS name, 26 AS age, 'U' AS flag
        UNION ALL
        SELECT 2, 'Bob', 30, 'D'
        UNION ALL
        SELECT 4, 'Dora', 28, 'I'
    ) s
    ON t.id = s.id
    WHEN MATCHED AND s.flag = 'D' THEN DELETE
    WHEN MATCHED THEN UPDATE SET
        name = s.name,
        age = s.age
    WHEN NOT MATCHED THEN INSERT (id, name, age)
    VALUES (s.id, s.name, s.age);
    ```

    В приведённом выше примере:
    * Строка с `id = 2` удаляется, поскольку `flag = 'D'`.
    * Строка с `id = 1` обновляется новыми значениями `name` и `age`.
    * Строка с `id = 4` вставляется, поскольку её нет в целевой таблице.

- Только обновление совпавших строк:

    ```sql
    MERGE INTO iceberg_tbl t
    USING (SELECT 1 AS id, 'Alice_matched' AS name, 26 AS age) s
    ON t.id = s.id
    WHEN MATCHED THEN UPDATE SET name = s.name, age = s.age;
    ```

- Только вставка строк без совпадений:

    ```sql
    MERGE INTO iceberg_tbl t
    USING (SELECT 4 AS id, 'Dora' AS name, 40 AS age) s
    ON t.id = s.id
    WHEN NOT MATCHED THEN INSERT (id, name, age) VALUES (s.id, s.name, s.age);
    ```

- Использование подзапроса в качестве источника данных:

    ```sql
    MERGE INTO iceberg_tbl t
    USING (SELECT id FROM other_table WHERE id = 2) s
    ON t.id = s.id
    WHEN MATCHED THEN UPDATE SET name = 'UpdatedViaSubquery';
    ```

- Операция `MERGE INTO` для партиционированных таблиц:

    ```sql
    MERGE INTO iceberg_partition_tbl t
    USING (
        SELECT 1 AS id, 'Alice_new' AS name, 26 AS age, DATE '2024-01-01' AS dt, 'U' AS flag
        UNION ALL
        SELECT 2, 'Bob', 30, DATE '2024-01-02', 'D'
        UNION ALL
        SELECT 4, 'Dora', 28, DATE '2024-01-04', 'I'
    ) s
    ON t.id = s.id
    WHEN MATCHED AND s.flag = 'D' THEN DELETE
    WHEN MATCHED THEN UPDATE SET
        name = s.name,
        age = s.age
    WHEN NOT MATCHED THEN INSERT (id, name, age, dt)
    VALUES (s.id, s.name, s.age, s.dt);
    ```

**Примечания:**

1. Все три описанные выше операции (`DELETE`, `UPDATE`, `MERGE INTO`) требуют, чтобы версия формата таблицы Iceberg (`format-version`) была 2 или выше. Попытка выполнить их для таблицы формата V1 приводит к ошибке: `must have format version 2 or higher for position deletes`. Для таблицы формата V3 система не только использует Deletion Vectors в формате Puffin вместо исходных данных Position Delete, но и автоматически корректирует атрибуты жизненного цикла происхождения (`_last_updated_sequence_number`) записываемых записей, если изменяется их содержимое.
2. Эти операции поддерживают форматы файлов Parquet и ORC.
3. При конкурентной записи Iceberg использует механизм оптимистического управления конкурентным доступом. При конфликтах записи операция может выбросить исключение конфликта транзакций.
4. Операция `UPDATE`, как самостоятельная, так и в составе `MERGE INTO`, поддерживает выражения и функции, например `age = age * 2 + 1` или `name = concat(name, '-modified')`.
5. Эти операции применимы как к партиционированным, так и к непартиционированным таблицам.
6. **Начиная с версии 4.1.4**, `MERGE INTO` проверяет соответствие между источником и целевой таблицей: если одной целевой строке соответствуют несколько исходных строк, оператор завершается ошибкой `multiple source rows matched the same target row` вместо получения недетерминированного результата. Если ожидается соответствие «один ко многим», сначала устраните дубликаты на стороне источника.

### Связанные параметры {#related-parameters}

* BE (Backend)

  | Имя параметра                                                               | Значение по умолчанию | Описание |
  | ----------------------------------------------------------------------------- | ------------- | ----------- |
  | `iceberg_sink_max_file_size`                                                  | 1GB           | Максимальный размер файла данных. Когда объём записанных данных превышает этот размер, текущий файл закрывается и создаётся новый для продолжения записи. |
  | `table_sink_partition_write_max_partition_nums_per_writer`                    | 128           | Максимальное количество разделов, в которые каждый экземпляр может записывать данные на узле BE. |
  | `table_sink_non_partition_write_scaling_data_processed_threshold`             | 25MB          | Порог объёма данных для запуска масштабирования записи в непартиционированных таблицах. Этот механизм регулирует число модулей записи в зависимости от объёма данных, повышая пропускную способность, экономя ресурсы и сводя к минимуму число файлов при небольших объёмах данных. |

Перебалансировка начинается, если `current accumulated data volume` - `data volume since last rebalancing` >= `table_sink_partition_write_min_data_processed_rebalance_threshold`. Снижение этого порога может улучшить баланс при значительных различиях размеров файлов, но может увеличить затраты на перебалансировку и повлиять на производительность. |
  | `table_sink_partition_write_min_partition_data_processed_rebalance_threshold` |               | Минимальный порог объёма данных раздела для запуска перебалансировки. Перебалансировка начинается, если `current partition data volume` >= `threshold` \* `number of tasks already allocated to the partition`. Снижение этого порога может улучшить баланс при значительных различиях размеров файлов, но может увеличить затраты на перебалансировку и повлиять на производительность. |
  
## Управление базами данных и таблицами {#database-and-table-management}

### Создание и удаление баз данных {#creating-and-dropping-databases}

Можно переключиться на нужный Catalog с помощью оператора `SWITCH` и выполнить команду `CREATE DATABASE`:

```sql
SWITCH iceberg;
CREATE DATABASE [IF NOT EXISTS] iceberg_db;
```

Также можно создать базу данных с помощью полного имени или указать расположение (сейчас указание расположения поддерживают только Catalog типа HMS), например:

```sql
CREATE DATABASE [IF NOT EXISTS] iceberg.iceberg_db;

CREATE DATABASE [IF NOT EXISTS] iceberg.iceberg_db
PROPERTIES ('location'='hdfs://172.21.16.47:4007/path/to/db/');
```

Просмотреть сведения о расположении базы данных можно с помощью команды `SHOW CREATE DATABASE`:

```sql
mysql> SHOW CREATE DATABASE iceberg_db;
+-------------+-------------------------------------------------------------------------------------------------+
| Database    | Create Database                                                                                 |
+-------------+-------------------------------------------------------------------------------------------------+
| iceberg_db  | CREATE DATABASE iceberg_db LOCATION 'hdfs://172.21.16.47:4007/usr/hive/warehouse/iceberg_db.db' |
+-------------+-------------------------------------------------------------------------------------------------+
```

Чтобы удалить базу данных:

```sql
DROP DATABASE [IF EXISTS] iceberg.iceberg_db;
```

:::caution
Перед удалением базы данных Iceberg необходимо удалить все её таблицы; в противном случае возникнет ошибка.
:::

### Создание и удаление таблиц {#creating-and-dropping-tables}

* **Создание таблиц**

  Doris поддерживает создание как партиционированных, так и непартиционированных таблиц Iceberg.

  Например:
  
  ```sql
  -- Create unpartitioned iceberg table
  CREATE TABLE unpartitioned_table (
    `col1` BOOLEAN COMMENT 'col1',
    `col2` INT COMMENT 'col2',
    `col3` BIGINT COMMENT 'col3',
    `col4` FLOAT COMMENT 'col4',
    `col5` DOUBLE COMMENT 'col5',
    `col6` DECIMAL(9,4) COMMENT 'col6',
    `col7` STRING COMMENT 'col7',
    `col8` DATE COMMENT 'col8',
    `col9` DATETIME COMMENT 'col9'
  )
  PROPERTIES (
    'write-format'='parquet'
  );

  -- Create partitioned iceberg table
  -- The partition columns must be in table's column definition list
  CREATE TABLE partition_table (
    `ts` DATETIME COMMENT 'ts',
    `col1` BOOLEAN COMMENT 'col1',
    `col2` INT COMMENT 'col2',
    `col3` BIGINT COMMENT 'col3',
    `col4` FLOAT COMMENT 'col4',
    `col5` DOUBLE COMMENT 'col5',
    `col6` DECIMAL(9,4) COMMENT 'col6',
    `col7` STRING COMMENT 'col7',
    `col8` DATE COMMENT 'col8',
    `col9` DATETIME COMMENT 'col9',
    `pt1` STRING COMMENT 'pt1',
    `pt2` STRING COMMENT 'pt2'
  )
  PARTITION BY LIST (day(ts), pt1, pt2) ()
  PROPERTIES (
    'write-format'='orc',
    'compression-codec'='zlib'
  );
  ```

  Начиная с версии 4.1.0, Doris поддерживает указание столбцов сортировки при создании таблицы Iceberg. При записи данные сортируются по указанным столбцам, что повышает производительность запросов.

  ```sql
  CREATE TABLE ordered_table (
    `id` int NULL,
    `name` text NULL,
    `score` double NULL,
    `create_time` datetimev2(6) NULL
  )
  ORDER BY  (`id` ASC NULLS FIRST, `score` DESC NULLS LAST)
  PROPERTIES (
    "write-format" = "parquet",
    "write.parquet.compression-codec" = "zstd"
  );
  ```

  - Если столбцы сортировки не указаны, сортировка при записи не выполняется.
  - Порядок сортировки по умолчанию — ASC NULLS FIRST.

  После создания можно использовать команду `SHOW CREATE TABLE` для просмотра оператора создания таблицы Iceberg. Подробнее о функциях партиционирования см. в разделе [Партиционирование](#).

* **Удаление таблиц**

  Удалить таблицу Iceberg можно с помощью оператора `DROP TABLE`. При удалении таблицы также удаляются её данные, включая данные разделов.

  Например:

  ```sql
  DROP TABLE [IF EXISTS] iceberg_tbl;
  ```

* **Сопоставление типов столбцов**

  См. раздел [Сопоставление типов столбцов](#).

* **Партиционирование**

    Типы разделов Iceberg соответствуют разделам List в Doris. Поэтому при создании партиционированной таблицы Iceberg в Doris следует использовать синтаксис партиционирования List, но явно перечислять каждый раздел не требуется. При вставке данных Doris автоматически создаёт соответствующие разделы Iceberg на основе значений данных.

    * Поддерживается создание таблиц, партиционированных по одному или нескольким столбцам.

    * Поддерживаются функции преобразования разделов для неявного партиционирования и эволюции партиционирования Iceberg. Конкретные функции преобразования разделов Iceberg см. в разделе [Преобразования разделов Iceberg](https://iceberg.apache.org/spec/#partition-transforms):

        * `year(ts)` или `years(ts)`

        * `month(ts)` или `months(ts)`

        * `day(ts)` или `days(ts)` или `date(ts)`

        * `hour(ts)` или `hours(ts)` или `date_hour(ts)`

        * `bucket(N, col)`

        * `truncate(L, col)`

* **Форматы файлов**

    * Parquet (по умолчанию)

        В таблицах Iceberg, созданных Doris, тип Datetime соответствует типу `timestamp_ntz`.

        В версиях после 3.1.0 при записи типа Datetime в файл Parquet используется физический тип INT64 вместо INT96.

        Если таблица Iceberg создана другой системой, типы `timestamp` и `timestamp_ntz` оба сопоставляются с типом Datetime в Doris. Однако при записи необходимость обработки часового пояса определяется фактическим типом.

    * ORC

* **Форматы сжатия**

    * Parquet: snappy, zstd (по умолчанию), plain (без сжатия).

    * ORC: snappy, zlib (по умолчанию), zstd, plain (без сжатия).

* **Среда хранения**

    * HDFS

    * Объектное хранилище

### Изменение схемы {#schema-change}

Начиная с 3.1.0, Doris поддерживает изменение схемы таблиц Iceberg с помощью оператора `ALTER TABLE`.

Поддерживаются следующие операции изменения схемы:

* **Переименование столбца**

    Используйте предложение `RENAME COLUMN` для переименования столбцов. Начиная с версии 4.1.4, поддерживается переименование столбцов внутри вложенных типов, а ключевое слово `TO` необязательно.

    ```sql
    ALTER TABLE iceberg_table RENAME COLUMN old_col_name TO new_col_name;

    -- Supported since 4.1.4: TO can be omitted
    ALTER TABLE iceberg_table RENAME COLUMN old_col_name new_col_name;

    -- Supported since 4.1.4: rename a nested field
    ALTER TABLE iceberg_table RENAME COLUMN s.old_field TO new_field;
    ```

* **Добавление столбца**

    Используйте `ADD COLUMN` для добавления нового столбца. Начиная с версии 4.1.4, поддерживается добавление нового столбца во вложенный тип (STRUCT) через путь с точками (например, `s.new_field`); новое вложенное поле должно допускать NULL.

    При добавлении нового столбца можно указать допустимость NULL, значение по умолчанию, комментарий и позицию столбца.

    ```sql
    ALTER TABLE iceberg_table ADD COLUMN col_name col_type [NULL|NOT NULL, [DEFAULT default_value, [COMMENT 'comment', [FIRST|AFTER col_name]]]];
    ```

    Пример:

    ```sql
    ALTER TABLE iceberg_table ADD COLUMN new_col STRING NOT NULL DEFAULT 'default_value' COMMENT 'This is a new col' AFTER old_col;
    ```

* **Добавление нескольких столбцов**

    С помощью `ADD COLUMN` также можно добавить несколько столбцов. Новые столбцы добавляются в конец таблицы. Указание позиции для нескольких столбцов не поддерживается. Добавление новых столбцов во вложенные типы не поддерживается.

    Синтаксис для каждого столбца такой же, как при добавлении одного столбца.

    ```sql
    ALTER TABLE iceberg_table ADD COLUMN (col_name1 col_type1 [NULL|NOT NULL, [DEFAULT default_value, [COMMENT 'comment']]], col_name2 col_type2 [NULL|NOT NULL, [DEFAULT default_value, [COMMENT 'comment']]] ...);
    ```

* **Удаление столбца**

    Используйте `DROP COLUMN` для удаления столбцов. Начиная с версии 4.1.4, поддерживается удаление столбца внутри вложенного типа через путь с точками.

    ```sql
    ALTER TABLE iceberg_table DROP COLUMN col_name;

    -- Supported since 4.1.4: drop a nested field
    ALTER TABLE iceberg_table DROP COLUMN s.field_name;
    ```

* **Изменение столбца**

    Используйте оператор `MODIFY COLUMN` для изменения атрибутов столбца, включая тип, допустимость NULL, значение по умолчанию, комментарий и позицию столбца.

    Начиная с версии 4.0.4, Doris поддерживает изменение сложных типов (STRUCT, ARRAY, MAP), включая безопасное расширение типов и добавление полей структуры в конец.
    
    Безопасные расширения типов, поддерживаемые во вложенных типах:
    - INT -> BIGINT, LARGEINT
    - TINYINT -> SMALLINT, INT, BIGINT, LARGEINT
    - SMALLINT -> INT, BIGINT, LARGEINT
    - BIGINT -> LARGEINT
    - FLOAT -> DOUBLE
    - VARCHAR(n) -> VARCHAR(m), где m > n
    
    Ограничения для сложных типов:
    - Все новые вложенные поля должны допускать NULL.
    - Нельзя сделать необязательное поле обязательным.
    - В качестве значения по умолчанию для сложных типов поддерживается только NULL.

    Примечание: при изменении атрибутов столбца все неизменяемые атрибуты также следует явно указать с их исходными значениями.

    ```sql
    ALTER TABLE iceberg_table MODIFY COLUMN col_name col_type [NULL|NOT NULL, [DEFAULT default_value, [COMMENT 'comment', [FIRST|AFTER col_name]]]];
    ```

  Пример:

  ```sql
  CREATE TABLE iceberg_table (
      id INT,
      name STRING
  );
  -- Modify the id column type to BIGINT, set as NOT NULL, default value to 0, and add comment
  ALTER TABLE iceberg_table MODIFY COLUMN id BIGINT NOT NULL DEFAULT 0 COMMENT 'This is a modified id column';
  ```

  Пример изменения сложных типов:

  ```sql
  -- Create Iceberg table with complex types
  CREATE TABLE iceberg_tbl (
      id BIGINT,
      user_info STRUCT<name:STRING, scores:ARRAY<INT>, age:INT>,
      dt STRING
  );

  -- Append a new field (email) to the STRUCT column
  ALTER TABLE iceberg_tbl MODIFY COLUMN user_info STRUCT<name:STRING, scores:ARRAY<INT>, age:INT, email:STRING>;

  -- Promote the nested ARRAY element type from INT to BIGINT
  ALTER TABLE iceberg_tbl MODIFY COLUMN user_info STRUCT<name:STRING, scores:ARRAY<BIGINT>, age:INT, email:STRING>;
  ```

* **Изменение порядка столбцов**

    Используйте `ORDER BY`, чтобы изменить порядок столбцов, указав новую последовательность.

    ```sql
    ALTER TABLE iceberg_table ORDER BY (col_name1, col_name2, ...);
    ```

#### Изменение схемы вложенных столбцов (4.1.4+) {#nested-column-schema-change-414}

Начиная с версии 4.1.4, `ADD COLUMN`, `DROP COLUMN`, `MODIFY COLUMN` и `RENAME COLUMN` принимают путь с точками (например, `a.b.c`) для непосредственной работы с вложенным полем. Эта возможность применима **только к таблицам Iceberg**; её использование с таблицей любого другого типа приводит к ошибке: `Nested column path is only supported for Iceberg tables: ...`.

Основные ограничения и ошибки:

| Сообщение об ошибке | Описание |
| --- | --- |
| `New nested field '<path>' must be nullable` | Новое вложенное поле должно допускать NULL |
| `Rollup is not supported for Iceberg column operations` | Предложение Rollup не поддерживается |
| `PROPERTIES are not supported for Iceberg column operations` | Предложение PROPERTIES не поддерживается |
| `KEY is not supported for Iceberg ADD/MODIFY COLUMN` | Ключевое слово KEY не поддерживается |
| `Generated columns are not supported for Iceberg ADD/MODIFY COLUMN` | Генерируемые столбцы не поддерживаются |
| `Modifying default values is not supported for Iceberg columns` | Изменение значения по умолчанию существующего столбца не поддерживается |
| `ON UPDATE is not supported for Iceberg ADD COLUMN` | Предложение ON UPDATE не поддерживается |
| `Modify column type from complex to primitive is not supported` | Изменение сложного типа на примитивный не поддерживается |
| `Cannot change MAP key type from ...` / `Cannot <op> MAP key nested column` | Изменение типа ключа MAP или выполнение операции с вложенным столбцом ключа MAP не поддерживается |
| `Iceberg does not support comments on collection element or value fields` | Комментарии для полей элементов коллекции или значений MAP не поддерживаются |
| `Multiple Iceberg ALTER clauses are not supported when a statement ...` | При работе с вложенными столбцами оператор может содержать только одно предложение ALTER |

### Эволюция партиционирования {#partition-evolution}

Начиная с версии 4.0.2, Doris поддерживает эволюцию партиционирования таблиц Iceberg с помощью операторов `ALTER`.

Поддерживаются следующие преобразования разделов:

| Преобразование | Синтаксис | Пример |
|-----------|--------|---------|
| bucket | `bucket(N, column)` | `bucket(16, id)` |
| truncate | `truncate(N, column)` | `truncate(10, name)` |
| year | `year(column)` | `year(ts)` |
| month | `month(column)` | `month(ts)` |
| day | `day(column)` | `day(ts)` |
| hour | `hour(column)` | `hour(ts)` |
| identity | `column` | `category` |

Поддерживаются следующие операции:

- **Добавление ключа партиционирования**

    ```sql
    -- use optional AS keyword to specify a custom name for the partition field
    ALTER TABLE table_name ADD PARTITION KEY partition_transform [AS key_name];

    -- example
    ALTER TABLE prod.db.sample ADD PARTITION KEY bucket(16, id);
    ALTER TABLE prod.db.sample ADD PARTITION KEY truncate(4, data);
    ALTER TABLE prod.db.sample ADD PARTITION KEY year(ts);
    -- use optional AS keyword to specify a custom name for the partition field 
    ALTER TABLE prod.db.sample ADD PARTITION KEY bucket(16, id) AS shard;
    ```

- **Удаление ключа партиционирования**

    ```sql
    ALTER TABLE table_name DROP PARTITION KEY partition_transform｜key_name;

    -- example
    ALTER TABLE prod.db.sample DROP PARTITION KEY catalog;
    ALTER TABLE prod.db.sample DROP PARTITION KEY bucket(16, id);
    ALTER TABLE prod.db.sample DROP PARTITION KEY truncate(4, data);
    ALTER TABLE prod.db.sample DROP PARTITION KEY year(ts);
    ALTER TABLE prod.db.sample DROP PARTITION KEY shard;
    ```

- **Замена ключа партиционирования**

    ```sql
    -- use optional AS keyword to specify a custom name for the partition field
    ALTER TABLE table_name REPLACE PARTITION KEY key_name WITH partition_transform [AS key_name];

    -- example
    ALTER TABLE prod.db.sample REPLACE PARTITION KEY ts_day WITH day(ts);
    -- use optional AS keyword to specify a custom name for the new partition field 
    ALTER TABLE prod.db.sample REPLACE PARTITION KEY ts_day WITH day(ts) AS day_of_ts;
    ```

### Управление ветвями и тегами {#managing-branch--tag}

> Начиная с 3.1.0

* **Создание ветви**

  Синтаксис:

  ```sql
  ALTER TABLE [catalog.][database.]table_name
  CREATE [OR REPLACE] BRANCH [IF NOT EXISTS] <branch_name>
  [AS OF VERSION <snapshot_id>]
  [RETAIN <num> { DAYS | HOURS | MINUTES }]
  [WITH SNAPSHOT RETENTION { snapshotKeep | timeKeep }]

  snapshotKeep:
    <num> SNAPSHOTS [<num> { DAYS | HOURS | MINUTES }]

  timeKeep:
    <num> { DAYS | HOURS | MINUTES }
  ```

  Примеры:

  ```sql
  -- Create branch "b1".
  ALTER TABLE tbl CREATE BRANCH b1;
  ALTER TABLE tb1 CREATE BRANCH IF NOT EXISTS b1;
  -- Create or replace branch "b1".
  ALTER TABLE tb1 CREATE OR REPLACE BRANCH b1;
  -- Create or replace branch "b1" based on snapshot "123456".
  ALTER TABLE tb1 CREATE OR REPLACE BRANCH b1 AS OF VERSION 123456;
  -- Create or replace branch "b1" based on snapshot "123456", branch retained for 1 day.
  ALTER TABLE tb1 CREATE OR REPLACE BRANCH b1 AS OF VERSION 123456 RETAIN 1 DAYS;
  -- Create branch "b1" based on snapshot "123456", branch retained for 30 days. Keep the latest 3 snapshots in the branch.
  ALTER TABLE tb1 CREATE BRANCH b1 AS OF VERSION 123456 RETAIN 30 DAYS WITH SNAPSHOT RETENTION 3 SNAPSHOTS;
  -- Create branch "b1" based on snapshot "123456", branch retained for 30 days. Snapshots in the branch are retained for at most 2 days.
  ALTER TABLE tb1 CREATE BRANCH b1 AS OF VERSION 123456 RETAIN 30 DAYS WITH SNAPSHOT RETENTION 2 DAYS;
  -- Create branch "b1" based on snapshot "123456", branch retained for 30 days. Keep the latest 3 snapshots in the branch, and snapshots in the branch are retained for at most 2 days.
  ALTER TABLE tb1 CREATE BRANCH b1 AS OF VERSION 123456 RETAIN 30 DAYS WITH SNAPSHOT RETENTION 3 SNAPSHOTS 2 DAYS;
  ```

* **Удаление ветви**

  Синтаксис:

  ```sql
  ALTER TABLE [catalog.][database.]table_name
  DROP BRANCH [IF EXISTS] <branch_name>;
  ```

  Пример:

  ```sql
  ALTER TABLE tbl DROP BRANCH b1;
  ```

* **Создание тега**

  Синтаксис:

  ```sql
  ALTER TABLE [catalog.][database.]table_name
  CREATE [OR REPLACE] TAG [IF NOT EXISTS] <tag_name>
  [AS OF VERSION <snapshot_id>]
  [RETAIN <num> { DAYS | HOURS | MINUTES }]
  ```

  Примеры:

  ```sql
  -- Create tag "t1".
  ALTER TABLE tbl CREATE TAG t1;
  ALTER TABLE tb1 CREATE TAG IF NOT EXISTS t1;
  -- Create or replace tag "t1".
  ALTER TABLE tb1 CREATE OR REPLACE TAG t1;
  -- Create or replace tag "t1" based on snapshot "123456".
  ALTER TABLE tb1 CREATE OR REPLACE TAG b1 AS OF VERSION 123456;
  -- Create or replace tag "b1" based on snapshot "123456", tag retained for 1 day.
  ALTER TABLE tb1 CREATE OR REPLACE TAG b1 AS OF VERSION 123456 RETAIN 1 DAYS;
  ```

* **Удаление тега**

  Синтаксис:

  ```sql
  ALTER TABLE [catalog.][database.]table_name
  DROP TAG [IF EXISTS] <tag_name>;
  ```

  Пример:

  ```sql
  ALTER TABLE tbl DROP TAG t1;
  ```

## Действия с таблицами Iceberg {#iceberg-table-actions}

> Эта возможность поддерживается начиная с версии 4.0.2. Требования к версии для каждой операции приведены в её описании.
>
> Это экспериментальная возможность.

Doris поддерживает выполнение специальных действий с таблицами Iceberg с помощью синтаксиса `ALTER TABLE EXECUTE`. Этот синтаксис предоставляет единый интерфейс для различных операций, таких как оптимизация таблиц и управление снимками.

```sql
ALTER TABLE [catalog.][database.]table_name
EXECUTE <action_name> ("key1" = "value1", "key2" = "value2", ...)
[WHERE <condition>]
```

* `action_name`: имя выполняемой операции
* `("key1" = "value1", ...)`: параметры операции в виде пар «ключ — значение». Имена параметров должны быть заключены в двойные кавычки
* `[WHERE <condition>]`: необязательное условие WHERE для указания раздела или диапазона данных для операции (поддерживается только некоторыми операциями)

### cherrypick_snapshot {#cherrypick_snapshot}

Операция `cherrypick_snapshot` объединяет изменения из указанного снимка с текущим состоянием таблицы, создавая новый снимок без изменения или удаления исходного.

> Поддерживаемая версия: 4.0.2+

**Синтаксис:**

```sql
ALTER TABLE [catalog.][database.]table_name
EXECUTE cherrypick_snapshot ("snapshot_id" = "<snapshot_id>")
```

**Параметры:**

| Параметр | Тип | Обязателен | Описание |
| -------- | ---- | ---- | ---- |
| `snapshot_id` | Long | Да | Идентификатор снимка, изменения которого нужно объединить |

**Возвращаемое значение:**

Выполнение операции `cherrypick_snapshot` возвращает набор результатов со следующими 2 столбцами:

| Имя столбца | Тип | Описание |
| ---- | ---- | ---- |
| `source_snapshot_id` | BIGINT | Идентификатор объединённого снимка |
| `current_snapshot_id` | BIGINT | Идентификатор снимка, созданного и установленного как текущий после объединения |

**Пример:**

```sql
-- Merge changes from snapshot 123456789 into the current table state
ALTER TABLE iceberg_db.iceberg_table 
EXECUTE cherrypick_snapshot ("snapshot_id" = "123456789");
```

**Примечания:**

1. Эта операция не поддерживает условия WHERE
2. Если указанный снимок не существует, операция завершается ошибкой
3. Объединение создаёт новый снимок и не удаляет исходный

### expire_snapshots {#expire_snapshots}

Операция `expire_snapshots` удаляет старые снимки из таблиц Iceberg, освобождая место в хранилище и ускоряя работу с метаданными. Эта операция соответствует спецификации процедуры Apache Iceberg Spark.

> Поддерживаемая версия: 4.1.0+

**Синтаксис:**

```sql
ALTER TABLE [catalog.][database.]table_name
EXECUTE expire_snapshots ("key1" = "value1", "key2" = "value2", ...)
```

**Параметры:**

| Параметр | Тип | Обязателен | Описание |
| -------- | ---- | ---- | ---- |
| `older_than` | String | Нет | Временной порог удаления снимков. Снимки старше него будут удалены. Поддерживается формат даты и времени ISO (например, `2024-01-01T00:00:00`) или временная метка в миллисекундах |
| `retain_last` | Integer | Нет | Количество сохраняемых снимков-предков. Если указан отдельно, автоматически задаёт для `older_than` текущее время |
| `snapshot_ids` | String | Нет | Список конкретных идентификаторов снимков для удаления, разделённых запятыми |
| `max_concurrent_deletes` | Integer | Нет | Размер пула потоков для операций удаления |
| `clean_expired_metadata` | Boolean | Нет | Если задано значение `true`, удаляет неиспользуемые спецификации партиционирования и схемы |

**Возвращаемое значение:**

Выполнение операции `expire_snapshots` возвращает набор результатов со следующими 6 столбцами:

| Имя столбца | Тип | Описание |
| ---- | ---- | ---- |
| `deleted_data_files_count` | BIGINT | Количество удалённых файлов данных |
| `deleted_position_delete_files_count` | BIGINT | Количество удалённых файлов Position Delete |
| `deleted_equality_delete_files_count` | BIGINT | Количество удалённых файлов Equality Delete |
| `deleted_manifest_files_count` | BIGINT | Количество удалённых файлов манифестов |
| `deleted_manifest_lists_count` | BIGINT | Количество удалённых файлов списков манифестов |
| `deleted_statistics_files_count` | BIGINT | Количество удалённых файлов статистики |

**Пример:**

```sql
-- Expire snapshots, keeping only the last 2
ALTER TABLE iceberg_db.iceberg_table 
EXECUTE expire_snapshots ("retain_last" = "2");

-- Expire snapshots older than a specific timestamp
ALTER TABLE iceberg_db.iceberg_table 
EXECUTE expire_snapshots ("older_than" = "2024-01-01T00:00:00");

-- Expire specific snapshots by ID
ALTER TABLE iceberg_db.iceberg_table 
EXECUTE expire_snapshots ("snapshot_ids" = "123456789,987654321");

-- Combine parameters: expire snapshots older than 2024-06-01 but keep at least the last 5
ALTER TABLE iceberg_db.iceberg_table 
EXECUTE expire_snapshots ("older_than" = "2024-06-01T00:00:00", "retain_last" = "5");
```

**Примечания:**

1. Эта операция не поддерживает условия WHERE.
2. Если указаны и `older_than`, и `retain_last`, применяются оба условия: удаляются только снимки старше `older_than`, которые при этом НЕ входят в число последних `retain_last` снимков.
3. `snapshot_ids` можно использовать отдельно для удаления конкретных снимков.
4. Эта операция безвозвратно удаляет снимки и связанные с ними файлы данных. Используйте её с осторожностью.
5. Перед выполнением рекомендуется запросить системную таблицу `$snapshots`, чтобы изучить сведения о снимках таблицы.

### fast_forward {#fast_forward}

Операция `fast_forward` быстро перемещает текущий снимок одной ветви к последнему снимку другой ветви.

```sql

```

**Параметры:**

| Параметр | Тип | Обязателен | Описание |
| -------- | ---- | ---- | ---- |
| `branch` | String | Да | Имя перемещаемой ветви |
| `to` | String | Да | Имя целевой ветви; `branch` будет перемещена к последнему снимку этой ветви |

**Возвращаемое значение:**

Выполнение операции `fast_forward` возвращает набор результатов со следующими 3 столбцами:

| Имя столбца | Тип | Описание |
| ---- | ---- | ---- |
| `branch_updated` | STRING | Имя перемещённой ветви |

**Примечания:**

2. Если указанная ветвь не существует, операция завершается ошибкой
3. Перемещать можно только ветви, теги не поддерживаются

| `wap_id` | String | Да | Значение `wap.id` публикуемого снимка |

**Возвращаемое значение:**

Выполнение операции `publish_changes` возвращает набор результатов со следующими 2 столбцами:

| Имя столбца | Тип | Описание |

### rewrite_data_files {#rewrite_data_files}

Операция `rewrite_data_files` перезаписывает файлы данных таблицы Iceberg для компактации мелких файлов, повышая производительность запросов и эффективность хранения. Это синхронная операция.

> Поддерживаемая версия: 4.0.2+

**Синтаксис:**

```sql
ALTER TABLE [catalog.][database.]table_name
EXECUTE rewrite_data_files ("key1" = "value1", "key2" = "value2", ...) [WHERE <condition>]
```

**Параметры:**

| Параметр | Тип | Значение по умолчанию | Описание |
| -------- | ---- | ------ | ---- |
| `target-file-size-bytes` | Long | 536870912 (512MB) | Целевой размер файла в байтах. Желаемый размер выходных файлов |
| `min-file-size-bytes` | Long | target-file-size-bytes * 0.75 | Минимальный размер файла в байтах. Файлы меньшего размера будут перезаписаны. Если не указан, по умолчанию равен 75% целевого размера файла |
| `max-file-size-bytes` | Long | target-file-size-bytes * 1.8 | Максимальный размер файла в байтах. Файлы большего размера будут разделены. Если не указан, по умолчанию равен 180% целевого размера файла |
| `min-input-files` | Integer | 5 | Минимальное количество входных файлов для запуска перезаписи. Перезапись выполняется, только когда количество файлов для перезаписи достигает этого порога |
| `rewrite-all` | Boolean | false | Определяет, нужно ли перезаписывать все файлы независимо от их размера |
| `max-file-group-size-bytes` | Long | 107374182400 (100GB) | Максимальный размер одной группы файлов в байтах. Ограничивает объём данных, обрабатываемых одной задачей перезаписи |
| `delete-file-threshold` | Integer | Integer.MAX_VALUE | Минимальное количество файлов удалений для запуска перезаписи |
| `delete-ratio-threshold` | Double | 0.3 | Минимальная доля удалённых записей для запуска перезаписи (удалённые записи / общее количество записей). Диапазон: 0.0 - 1.0 |
| `output-spec-id` | Long | 2 | Идентификатор спецификации партиционирования для выходных файлов |

**Возвращаемое значение:**

Выполнение операции `rewrite_data_files` возвращает набор результатов со следующими 4 столбцами:

| Имя столбца | Тип | Описание |
| ---- | ---- | ---- |
| `rewritten_data_files_count` | INT | Количество перезаписанных файлов данных |
| `added_data_files_count` | INT | Количество добавленных новых файлов данных |
| `rewritten_bytes_count` | INT | Количество перезаписанных байтов |
| `removed_delete_files_count` | BIGINT | Количество удалённых файлов удалений |

**Примеры:**

```sql
-- Rewrite data files with default parameters
ALTER TABLE iceberg_db.iceberg_table EXECUTE rewrite_data_files();

-- Specify target file size and minimum input files
ALTER TABLE iceberg_db.iceberg_table 
EXECUTE rewrite_data_files (
  "target-file-size-bytes" = "134217728",
  "min-input-files" = "10"
);

-- Rewrite data in specific partitions using WHERE condition
ALTER TABLE iceberg_db.iceberg_table 
EXECUTE rewrite_data_files (
  "target-file-size-bytes" = "268435456"
)
WHERE date_col = '2024-01-01';

-- Rewrite all files
ALTER TABLE iceberg_db.iceberg_table 
EXECUTE rewrite_data_files (
  "rewrite-all" = "true",
  "target-file-size-bytes" = "536870912"
);
```

**Примечания:**

1. Операция `rewrite_data_files` читает и перезаписывает файлы данных, что создаёт дополнительную нагрузку на ввод-вывод и вычислительные ресурсы. Распределяйте ресурсы кластера соответствующим образом.
2. Перед выполнением можно использовать SQL из раздела [Просмотр распределения файлов данных](#view-data-file-distribution), чтобы оценить необходимость перезаписи
3. Условия WHERE позволяют ограничить разделы или диапазон данных для перезаписи. Такое условие исключает файлы, не содержащие данных, соответствующих WHERE, сокращая количество файлов и объём данных для перезаписи
4. Перед выполнением можно использовать SQL из раздела [Логика выбора файлов для перезаписи](#rewrite_data_files-file-selection-strategy), чтобы определить, какие файлы будут перезаписаны

| Параметр | Тип | Обязателен | Описание |
| -------- | ---- | ---- | ---- |
| `timestamp` | String | Да | Момент времени, к которому нужно откатиться. Поддерживаются два формата:<br />1. Формат даты и времени ISO: `yyyy-MM-dd HH:mm:ss.SSS` (например, `2024-01-01 10:30:00.000`)<br/>2. Временная метка в миллисекундах (например, `1704067200000`) |

**Возвращаемое значение:**

Выполнение операции `rollback_to_timestamp` возвращает набор результатов со следующими 2 столбцами:

| Имя столбца | Тип | Описание |
| ---- | ---- | ---- |
| `previous_snapshot_id` | BIGINT | Идентификатор текущего снимка до отката |
| `current_snapshot_id` | BIGINT | Идентификатор снимка на указанный момент времени, установленного как текущий |

**Примеры:**

```sql
-- Roll back to specified point in time (ISO format)
ALTER TABLE iceberg_db.iceberg_table 
EXECUTE rollback_to_timestamp ("timestamp" = "2024-01-01 10:30:00.000");

-- Roll back to specified point in time (timestamp format)
ALTER TABLE iceberg_db.iceberg_table 
EXECUTE rollback_to_timestamp ("timestamp" = "1704067200000");
```

**Примечания:**

1. Эта операция не поддерживает условия WHERE
2. Параметр `timestamp` поддерживает формат даты и времени ISO (`yyyy-MM-dd HH:mm:ss.SSS`) или формат временной метки в миллисекундах
3. Если на указанный момент времени нет соответствующего снимка, операция завершается ошибкой

### set_current_snapshot {#set_current_snapshot}

Операция `set_current_snapshot` устанавливает текущий снимок таблицы Iceberg по указанному идентификатору снимка или ссылке (ветви либо тегу).

> Поддерживаемая версия: 4.0.2+

**Синтаксис:**

```sql
ALTER TABLE [catalog.][database.]table_name
EXECUTE set_current_snapshot ("snapshot_id" = "<snapshot_id>" | "ref" = "<ref_name>")
```

**Параметры:**

| Параметр | Тип | Обязателен | Описание |
| -------- | ---- | ---- | ---- |
| `snapshot_id` | Long | Один из двух | Идентификатор снимка, который нужно установить как текущий |
| `ref` | String | Один из двух | Имя ссылки (ветви или тега), снимок которой нужно установить как текущий |

**Возвращаемое значение:**

Выполнение операции `set_current_snapshot` возвращает набор результатов со следующими 2 столбцами:

| Имя столбца | Тип | Описание |
| ---- | ---- | ---- |
| `previous_snapshot_id` | BIGINT | Идентификатор текущего снимка до операции |
| `current_snapshot_id` | BIGINT | Идентификатор снимка после операции (из параметра `snapshot_id` или определённый по параметру `ref`) |

**Примеры:**

```sql
-- Set current snapshot by snapshot ID
ALTER TABLE iceberg_db.iceberg_table 
EXECUTE set_current_snapshot ("snapshot_id" = "123456789");

-- Set current snapshot by branch name
ALTER TABLE iceberg_db.iceberg_table 
EXECUTE set_current_snapshot ("ref" = "feature_branch");

-- Set current snapshot by tag name
ALTER TABLE iceberg_db.iceberg_table 
EXECUTE set_current_snapshot ("ref" = "v1.0");
```

**Примечания:**

1. Эта операция не поддерживает условия WHERE
2. Параметры `snapshot_id` и `ref` взаимоисключающие; можно указать только один из них
3. Если указанный идентификатор снимка или ссылка не существует, операция завершается ошибкой
4. Если текущий снимок уже является целевым, операция сразу завершается без создания нового снимка

### publish_changes {#publish_changes-1}

Операция `publish_changes` используется в режиме WAP (Write-Audit-Publish) для публикации снимка с указанным `wap.id` в качестве текущего состояния таблицы.  
Она находит снимок, у которого `wap.id` совпадает с заданным `wap_id`, и применяет его изменения к текущей таблице, делая подготовленные данные видимыми для всех операций чтения. 

**Синтаксис:**

```sql
ALTER TABLE [catalog.][database.]table_name
EXECUTE publish_changes("wap_id" = "<wap_id>")
```

**Параметры:**

**Параметры:**

| Имя параметра | Тип | Обязателен | Описание |
| -------------- | ---- | -------- | ----------- |
| `wap_id` | STRING | Да | Идентификатор WAP публикуемого снимка |

**Возвращаемое значение:**

Выполнение `publish_changes` возвращает набор результатов со следующими 2 столбцами:

| Имя столбца | Тип | Описание |
| ----------- | ---- | ----------- |
| `previous_snapshot_id` | STRING | Идентификатор текущего снимка до публикации (NULL, если его нет) |
| `current_snapshot_id` | STRING | Идентификатор нового снимка, созданного и установленного как текущий после публикации |

**Примеры:**

```sql
-- Publish the snapshot whose WAP ID is test_wap_001
ALTER TABLE iceberg_db.iceberg_table 
EXECUTE publish_changes("wap_id" = "test_wap_001");
```

**Примечания:**

1. Эта операция не поддерживает предложение WHERE, а также предложения PARTITION/PARTITIONS
2. Она имеет смысл только для таблиц Iceberg с write.wap.enabled = true и снимками WAP, созданными через wap.id
3. Если снимок с указанным wap_id не найден, операция завершается ошибкой
4. После публикации новый снимок становится текущим
5. Если до публикации снимка не было, previous_snapshot_id может иметь значение NULL

### Просмотр распределения файлов данных {#view-data-file-distribution}

Следующий SQL позволяет проанализировать распределение данных и количество файлов удалений в таблицах Iceberg, чтобы определить необходимость оптимизации, например `rewrite_data_files`.

- Вывод распределения файлов данных по размеру. Позволяет определить, не слишком ли много мелких файлов:

    ```sql
    SELECT
        CASE
            WHEN file_size_in_bytes BETWEEN 0 AND 8 * 1024 * 1024 THEN '0-8M'
            WHEN file_size_in_bytes BETWEEN 8 * 1024 * 1024 + 1 AND 32 * 1024 * 1024 THEN '8-32M'
            WHEN file_size_in_bytes BETWEEN 32 * 1024 * 1024 + 1 AND 128 * 1024 * 1024 THEN '32-128M'
            WHEN file_size_in_bytes BETWEEN 128 * 1024 * 1024 + 1 AND 512 * 1024 * 1024 THEN '128-512M'
            WHEN file_size_in_bytes > 512 * 1024 * 1024 THEN '> 512M'
            ELSE 'Unknown'
        END AS SizeRange,
        COUNT(*) AS FileNum
    FROM store_sales$data_files
    GROUP BY
        SizeRange;

    +-----------+---------+
    | SizeRange | FileNum |
    +-----------+---------+
    | 0-8M      |       8 |
    | 8-32M     |       6 |
    +-----------+---------+
    ```

- Вывод количества файлов данных и файлов удалений:

    ```sql
    SELECT
        CASE
            WHEN content = 0 THEN 'DataFile'
            WHEN content = 1 THEN 'PositionDeleteFile'
            WHEN content = 2 THEN 'EqualityDeleteFile'
            ELSE 'Unknown'
        END AS ContentType,
        COUNT(*) AS FileNum,
        SUM(file_size_in_bytes) AS SizeInBytes,
        SUM(record_count) AS Records
    FROM
        iceberg_table$files
    GROUP BY
        ContentType;

    +--------------------+---------+-------------+---------+
    | ContentType        | FileNum | SizeInBytes | Records |
    +--------------------+---------+-------------+---------+

    | PositionDeleteFile |      11 |       36608 |   10890 |
    +--------------------+---------+-------------+---------+
    ```

### Оставшиеся ссылки на удаления (Dangling Delete) {#dangling-delete}

В некоторых случаях после выполнения действия `rewrite_data_files` ссылки на определённые Position Delete могут остаться в метаданных снимка (Dangling Delete). Если в такой ситуации напрямую использовать сведения о количестве строк из метаданных, результат может быть неверным.

Поэтому по умолчанию для запросов `COUNT(*)` при обнаружении файла Position Delete оптимизация проталкивания COUNT не включается; вместо этого файл читается напрямую для получения фактического результата `COUNT(*)`. Однако этот способ требует времени.

Если пользователь может гарантировать отсутствие проблемы Dangling Delete, эту проверку можно пропустить с помощью переменной сеанса Doris `ignore_iceberg_dangling_delete`. Её значение по умолчанию — `false`. При значении `true` система возвращает результат `COUNT(*)` напрямую на основе сведений о количестве строк из метаданных, повышая эффективность запросов.

Эта возможность поддерживается начиная с версий 3.1.4 и 4.0.3.

## Приложение {#appendix}

### Стратегия выбора файлов для `rewrite_data_files` {#rewrite_data_files-file-selection-strategy}

В этом разделе описана логика выбора файлов для перезаписи. Следующие SQL-запросы также позволяют проанализировать по сведениям системных таблиц, какие файлы будут перезаписаны. Это помогает отладить и понять поведение перезаписи до выполнения реальных операций.

Операция перезаписи использует двухэтапную стратегию фильтрации и группировки:

1. Этап 1: фильтрация на уровне файлов

    Сначала файлы фильтруются по условиям уровня файлов. Для перезаписи рассматриваются только файлы, удовлетворяющие хотя бы одному из следующих условий:

    1. **Размер файла вне диапазона**: файл меньше `min-file-size-bytes` или больше `max-file-size-bytes`
    2. **Слишком много файлов удалений**: количество связанных файлов удалений >= `delete-file-threshold`
    3. **Высокая доля удалений**: доля удалённых записей >= `delete-ratio-threshold`

    **Примечание об условиях для файлов удалений:** условия, связанные с файлами удалений (`delete-file-threshold` и `delete-ratio-threshold`), влияют на выбор файлов для перезаписи, но не могут быть точно рассчитаны с помощью SQL-запросов к системным таблицам. Текущих сведений системных таблиц недостаточно, чтобы точно определить, какие файлы данных затрагиваются файлами удалений. Файлы удалений могут затрагивать только определённые файлы данных (особенно файлы Position Delete), а для установления связи между файлами удалений и файлами данных нужны более подробные метаданные, недоступные в текущих системных таблицах. Реальные операции перезаписи оценивают эти условия на основе более подробных метаданных, не представленных в системных таблицах.

2. Этап 2: группировка BinPack и фильтрация на уровне групп

    После фильтрации на уровне файлов файлы группируются по разделам, а затем внутри каждого раздела — с помощью **алгоритма BinPack** на основе размера файлов и `max-file-group-size-bytes`. Алгоритм BinPack подбирает распределение файлов по группам для оптимизации операций перезаписи.

    После группировки группы файлов фильтруются по условиям уровня групп. Группы перезаписываются, если удовлетворяют хотя бы одному из следующих условий:

    1. **Достаточно входных файлов**: количество файлов в группе > 1 и количество файлов >= `min-input-files`
    2. **Достаточный объём содержимого**: количество файлов в группе > 1 и общий размер > `target-file-size-bytes`
    3. **Слишком большой объём содержимого**: общий размер группы > `max-file-group-size-bytes`
    4. **Есть файлы с проблемами удалений**: хотя бы у одного файла в группе слишком много файлов удалений или высокая доля удалений.

    **Примечание о группировке BinPack:** алгоритм BinPack, используемый для группировки файлов внутри каждого раздела, — сложный алгоритм оптимизации, который невозможно точно воспроизвести с помощью SQL-запросов к системным таблицам. Он учитывает размер файлов и `max-file-group-size-bytes`, подбирая распределение файлов по группам, поэтому результат может отличаться от простой группировки по разделам. Приведённые ниже SQL-запросы позволяют выявить только файлы, соответствующие условиям уровня файлов, но не позволяют точно рассчитать итоговые группы файлов для перезаписи.

Примеры стратегий запросов:

- Запрос 1: определение файлов, соответствующих условиям уровня файлов

    Этот запрос определяет файлы, соответствующие условиям уровня файлов (по размеру), которые будут рассматриваться для перезаписи:

    ```sql
    -- Set parameters (adjust according to your rewrite parameters)
    SET @min_file_size_bytes = 16 * 1024 * 1024;   -- 16 MB (default: target-file-size-bytes * 0.75)
    SET @max_file_size_bytes = 768 * 1024 * 1024;  -- 768 MB (default: target-file-size-bytes * 1.8)

    SELECT 
        file_path,
        `partition`,
        file_size_in_bytes / 1024.0 / 1024.0 AS file_size_mb,
        record_count,
        CASE 
            WHEN file_size_in_bytes < @min_file_size_bytes THEN 'Too small'
            WHEN file_size_in_bytes > @max_file_size_bytes THEN 'Too large'
        END AS size_issue
    FROM iceberg_table$data_files
    WHERE file_size_in_bytes < @min_file_size_bytes 
    OR file_size_in_bytes > @max_file_size_bytes
    ORDER BY `partition`, file_size_in_bytes DESC;
    ```

    **Пример вывода:**

    ```text
    +----------------------------------------------------------------------------------------+---------------------------+-------------+--------------+------------+
    | file_path                                                                             | partition                 | file_size_mb | record_count | size_issue |
    +----------------------------------------------------------------------------------------+---------------------------+-------------+--------------+------------+
    | s3a://bucket/path/to/table/data/date_col=2024-01-01/00000-0-00000-00000-0.parquet   | {"date_col":"2024-01-01"} |     0.00215  |            5 | Too small  |
    | s3a://bucket/path/to/table/data/date_col=2024-01-01/00001-0-00001-00001-0.parquet     | {"date_col":"2024-01-01"} |     0.00198  |            5 | Too small  |
    | s3a://bucket/path/to/table/data/date_col=2024-01-02/00002-0-00002-00002-0.parquet     | {"date_col":"2024-01-02"} |     0.00231  |            5 | Too small  |
    | s3a://bucket/path/to/table/data/date_col=2024-01-02/00003-0-00003-00003-0.parquet     | {"date_col":"2024-01-02"} |   850.23456  |      1250000 | Too large  |
    | s3a://bucket/path/to/table/data/date_col=2024-01-03/00004-0-00004-00004-0.parquet     | {"date_col":"2024-01-03"} |     0.00245  |            5 | Too small  |
    ```

    **Примечание:** этот запрос позволяет определить только файлы, соответствующие условиям уровня файлов (по размеру). Фактические группы файлов для перезаписи зависят от алгоритма группировки BinPack, который нельзя точно воспроизвести с помощью SQL-запросов. Файлы, найденные этим запросом, могут быть сгруппированы алгоритмом BinPack иначе, а некоторые группы могут быть исключены по условиям уровня групп.

- Запрос 2: общая сводная статистика

    Этот запрос предоставляет общую статистику по файлам, соответствующим условиям уровня файлов:

    ```sql
    -- Set parameters (adjust according to your rewrite parameters)
    SET @min_file_size_bytes = 16 * 1024 * 1024;
    SET @max_file_size_bytes = 768 * 1024 * 1024;

    WITH file_analysis AS (
        SELECT 
            `partition`,
            file_path,
            file_size_in_bytes,
            record_count,
            (file_size_in_bytes < @min_file_size_bytes OR file_size_in_bytes > @max_file_size_bytes) AS meets_file_level_conditions
        FROM iceberg_table$data_files
    )
    SELECT 
        'Total files' AS metric, 
        COUNT(*) AS value
    FROM file_analysis
    UNION ALL
    SELECT 
        'Files meeting file-level conditions', 
        SUM(CASE WHEN meets_file_level_conditions THEN 1 ELSE 0 END)
    FROM file_analysis
    UNION ALL
    SELECT 
        'Total size (GB)', 
        ROUND(SUM(file_size_in_bytes) / 1024.0 / 1024.0 / 1024.0, 2)
    FROM file_analysis
    UNION ALL
    SELECT 
        'Size meeting file-level conditions (GB)', 
        ROUND(SUM(CASE WHEN meets_file_level_conditions THEN file_size_in_bytes ELSE 0 END) / 1024.0 / 1024.0 / 1024.0, 2)
    FROM file_analysis
    UNION ALL
    SELECT 
        'Percentage meeting file-level conditions (%)', 
        ROUND(SUM(CASE WHEN meets_file_level_conditions THEN 1 ELSE 0 END) * 100.0 / COUNT(*), 2)
    FROM file_analysis;
    ```

    **Пример вывода:**

    ```text
    +----------------------------------------------+--------+
    | metric                                       | value  |
    +----------------------------------------------+--------+
    | Total files                                  |  15.00 |
    | Total size (GB)                              |   2.45 |
    | Files meeting file-level conditions          |  12.00 |
    | Size meeting file-level conditions (GB)      |   1.85 |
    | Percentage meeting file-level conditions (%) |  80.00 |
    +----------------------------------------------+--------+
    5 rows in set
    ```

    **Примечания:**

    - Замените `iceberg_table` в примере фактическим именем таблицы
    - Скорректируйте значения параметров (`@min_file_size_bytes`, `@max_file_size_bytes`) в соответствии с фактическими параметрами перезаписи
    - Приведённые выше значения по умолчанию соответствуют стандартным параметрам перезаписи (min-file-size-bytes = target-file-size-bytes * 0.75, max-file-size-bytes = target-file-size-bytes * 1.8)

- Просмотр связей между снимками и ветвями:

    ```sql
    SELECT
        refs_data.snapshot_id,
        snapshots.committed_at,
        snapshots.operation,
        ARRAY_SORT(refs_data.refs)
    FROM (
        SELECT
            snapshot_id,
            ARRAY_AGG(CONCAT(type, ':', name)) AS refs
        FROM
            iceberg_table$refs
        GROUP BY
            snapshot_id
    ) AS refs_data
    JOIN (
        SELECT
            snapshot_id,
            committed_at,
            operation
        FROM
            iceberg_table$snapshots
    ) AS snapshots
    ON refs_data.snapshot_id = snapshots.snapshot_id
    ORDER BY
        snapshots.committed_at;

    +---------------------+----------------------------+-----------+-------------------------------------+
    | snapshot_id         | committed_at               | operation | ARRAY_SORT(refs_data.refs)          |
    +---------------------+----------------------------+-----------+-------------------------------------+
    | 8272911997874079853 | 2025-07-10 15:27:07.177000 | append    | ["BRANCH:b1", "TAG:t1"]             |
    | 1325777059626757917 | 2025-07-10 15:27:07.530000 | append    | ["BRANCH:b2", "TAG:t2"]             |
    |   76492482642020578 | 2025-07-10 15:27:07.865000 | append    | ["BRANCH:b3", "TAG:t3"]             |
    | 1788715857849070138 | 2025-07-12 04:15:19.626000 | append    | ["BRANCH:main", "TAG:t4", "TAG:t5"] |
    +---------------------+----------------------------+-----------+-------------------------------------+
    ```
