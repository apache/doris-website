# Parquet {#parquet}

В этом документе описана поддержка чтения и записи файлов формата Parquet в Doris. Она распространяется на следующие возможности:

* Чтение и запись данных в Catalog.
* Чтение данных с помощью Table Valued Functions.
* Чтение данных с помощью Broker Load.
* Запись данных при Export.
* Запись данных с помощью Outfile.

## Декодирование временных меток INT96 {#int96-timestamp-decoding}

Parquet `INT96` хранит поля даты и времени без указания часового пояса. Поэтому FileScannerV2 по умолчанию сохраняет исходное локальное время без смещения на часовой пояс сеанса SQL. Например, исходное значение `2021-01-01 10:11:00` остаётся `10:11:00` при сопоставлении с `DATETIMEV2`, в том числе при сканировании через Catalog, использовании табличных функций и Broker Load.

Это поведение относится только к `INT96`. Значения Parquet `INT64` с логическим типом временной метки по-прежнему обрабатываются в соответствии с семантикой этого типа. Если старые средства записи Hive приводили значения `INT96` к известному часовому поясу, задайте `hive.parquet.time-zone` в [Hive Catalog](../catalogs/hive-catalog.mdx#timestamp-compatibility). Табличные функции для внешних файлов также принимают это свойство. Другие точки входа FileScannerV2 сохраняют исходное локальное время `INT96`. Исключение составляет Hudi: при нативном сканировании и сканировании через JNI он намеренно сохраняет прежнее поведение с часовым поясом сеанса SQL и игнорирует `hive.parquet.time-zone`.

Когда столбец `INT96` сопоставляется с `TIMESTAMPTZ`, Doris сохраняет момент времени в UTC, а не применяет часовой пояс, заданный для совместимости.

## Сопоставление типа UUID {#uuid-type-mapping}

При чтении поддерживается `FIXED_LEN_BYTE_ARRAY(16)` с аннотацией UUID, с обычным кодированием или кодированием по словарю, в каноническом порядке байтов от старшего к младшему. В dev-версии обычные Parquet TVF и Iceberg Catalog напрямую сопоставляют столбцы с аннотацией UUID с нативным типом `UUID` независимо от старых параметров сопоставления двоичных типов. В Doris 4.1.5 Parquet TVF по-прежнему возвращают канонические строки UUID или VARBINARY в зависимости от `enable_mapping_varbinary`; в этом выпуске UUID в Iceberg сопоставляется с `VARBINARY(16)`.

При записи столбца Doris типа `UUID`, включая элементы UUID, вложенные в ARRAY, MAP или STRUCT, создаётся `FIXED_LEN_BYTE_ARRAY(16)` с логической аннотацией UUID. Благодаря этому другие системы, понимающие аннотацию, восстанавливают значение как UUID. Dev-версия при чтении таких файлов восстанавливает нативный UUID, в том числе для вложенных элементов UUID.

Полное описание сопоставления UUID при выводе через OUTFILE и EXPORT см. в разделе [Сопоставление типов столбцов в экспортируемых файлах](../../data-operate/export/export-overview.md#column-type-mapping-for-exported-files).

## Поддерживаемые форматы сжатия {#supported-compression-formats}

### Чтение {#reading}

При чтении существующих файлов поддерживаются следующие кодеки.

* uncompressed
* snappy
* lz4
* zstd
* gzip
* lzo
* brotli

### Запись {#writing}

| Способ записи | Поддерживаемые кодеки |
| --- | --- |
| Hive / Iceberg Catalog | `plain`, `snappy`, `zstd`, `lz4` (начиная с 4.1.3), `gzip` (начиная с 4.2.0) |
| OUTFILE / EXPORT | `plain`, `snappy`, `gzip`, `brotli`, `zstd`, `lz4` |

`plain` означает отсутствие сжатия. Параметры записи через Catalog и их значения по умолчанию описаны в разделах [Hive Catalog](../catalogs/hive-catalog.mdx) и [Iceberg Catalog](../catalogs/iceberg-catalog.mdx). Для OUTFILE / EXPORT кодек выбирается свойством `compress_type`.

## Запись индексов страниц (dev-версия) {#writing-page-indexes-dev-version}

Doris может дополнительно записывать метаданные Parquet `ColumnIndex` и `OffsetIndex` при экспорте через OUTFILE или EXPORT, а также при вставке данных в таблицы Hive и Iceberg, хранящиеся в формате Parquet. Средство чтения, поддерживающее эти индексы, может находить подходящие страницы по значению и сохранять соответствие строк между столбцами. Существующие файлы не изменяются.

Перед командой записи задайте следующие переменные сеанса. Они влияют только на вывод в Parquet и не включают фильтрацию по индексам страниц при чтении.

| Переменная | Тип | Значение по умолчанию | Поведение |
| --- | --- | --- | --- |
| `enable_parquet_write_page_index` | Boolean | `true` | Записывает индексы страниц в новые файлы Parquet. Для `ColumnIndex` требуется доступная статистика по столбцу; `OffsetIndex` фиксирует расположение страниц данных и позиции строк. |
| `parquet_write_data_page_size` | Integer, байты | `1048576` (1 MiB) | Целевой размер несжатой страницы данных в диапазоне от `1` до `2147483647`. Действует независимо от того, включена ли запись индексов. Не задаёт размер группы строк или страницы словаря. |

Размер страницы — целевое значение: отдельное значение или пакет записи могут его превысить. Для LZ4 в формате фреймов Hadoop, используемого при выводе `lz4` через Hive/Iceberg, Doris ограничивает это значение `131072` байтами (128 KiB), чтобы сохранить совместимость со средствами чтения Hadoop. На вывод в формате raw LZ4 это ограничение кодека не распространяется.

Например, подготовьте доступный для записи бакет S3 и учётные данные, как описано в разделе [OUTFILE](../../data-operate/export/outfile.md), затем экспортируйте результат запроса с индексами и целевым размером страницы 256 KiB. Замените заполнители параметров хранилища своими значениями:

```sql
SET enable_parquet_write_page_index = true;
SET parquet_write_data_page_size = 262144;

SELECT 1 AS id, 'example' AS label
INTO OUTFILE 's3://example-bucket/export/result_'
FORMAT AS PARQUET
PROPERTIES (
    "s3.endpoint" = "https://s3.example.com",
    "s3.region" = "us-east-1",
    "s3.access_key" = "<access_key>",
    "s3.secret_key" = "<secret_key>"
);
```

Полученные файлы будут содержать метаданные индексов страниц для подходящих столбцов. Для Hive или Iceberg задайте те же переменные сеанса перед `INSERT INTO` или `INSERT OVERWRITE`; целевая таблица уже должна быть настроена на запись Parquet. Для EXPORT задайте их до отправки задания.

По умолчанию запись индексов включена (`true`), что сохраняет существующее поведение средства записи в dev-версии. Чтобы не включать индексы страниц в последующие файлы, измените параметр перед записью:

```sql
SET enable_parquet_write_page_index = false;
```

Чтобы восстановить значения по умолчанию в текущем сеансе:

```sql
SET enable_parquet_write_page_index = true;
SET parquet_write_data_page_size = 1048576;
```

Индексы увеличивают объём метаданных и затраты при записи. Страницы меньшего размера могут ускорить выборочное чтение, особенно если значения сгруппированы, но при этом создаётся больше записей индекса и заголовков страниц. Эффект зависит от средства чтения и распределения данных; включение индексов не гарантирует ускорения запросов. Средства чтения могут читать файлы и без использования этих необязательных индексов. Эти параметры не меняют версию формата Parquet или версию страниц данных.

## Запись фильтров Блума (dev-версия) {#writing-bloom-filters-dev-version}

Включайте запись фильтров Блума, если последующие средства чтения могут использовать предикаты равенства или `IN` для пропуска групп строк. Задайте следующую переменную сеанса перед командой OUTFILE, вставкой в доступную для записи файловую табличную функцию или вставкой в таблицу Hive либо Iceberg, хранящуюся в формате Parquet. Она влияет только на новые файлы.

| Переменная | Тип | Значение по умолчанию | Поведение |
| --- | --- | --- | --- |
| `enable_parquet_write_bloom_filter` | Boolean | `false` | Записывает стандартные фильтры Блума Parquet для подходящих физических столбцов-листьев в каждой группе строк, включая элементы, вложенные в ARRAY, MAP и STRUCT. Для столбцов BOOLEAN и столбцов с устаревшим типом INT96 фильтры не создаются. |

Например, подготовьте доступный для записи бакет S3 и учётные данные, как описано в разделе [OUTFILE](../../data-operate/export/outfile.md), затем замените заполнители параметров хранилища и выполните экспорт с включёнными фильтрами Блума:

```sql
SET enable_parquet_write_bloom_filter = true;

SELECT 1 AS id, 'example' AS label
INTO OUTFILE 's3://example-bucket/export/bloom_result_'
FORMAT AS PARQUET
PROPERTIES (
    "s3.endpoint" = "https://s3.example.com",
    "s3.region" = "us-east-1",
    "s3.access_key" = "<access_key>",
    "s3.secret_key" = "<secret_key>"
);

SET enable_parquet_write_bloom_filter = false;
```

Новые файлы содержат фильтр Блума для каждого подходящего столбца в каждой группе строк. Последняя команда `SET` восстанавливает значение по умолчанию для последующих операций записи в этом сеансе; она не удаляет фильтры из уже записанных файлов. Тот же параметр можно задать перед `INSERT INTO` или `INSERT OVERWRITE`, если целевая таблица настроена на запись Parquet.

Фильтры Блума доступны, когда кодирование по словарю сохраняется, при переполнении переключается на обычное кодирование или отключено. Для них не требуется отключать словари; настройка фильтров не зависит от приведённых выше параметров записи индексов страниц. Значения NULL в фильтры Блума не добавляются. Переключатель чтения Doris `enable_parquet_filter_by_bloom_filter` отдельно управляет использованием фильтров; включение их записи не заставляет средство чтения их использовать. Средства чтения, игнорирующие необязательные метаданные фильтров Блума, всё равно могут читать файлы.

Включайте этот параметр выборочно, например для предикатов равенства по столбцам с большим числом уникальных значений после переполнения словаря. Средство записи использует ожидаемое число различных значений по умолчанию 1,048,576 и целевую вероятность ложноположительного результата 0.05, выделяя примерно 1 MiB на каждый подходящий столбец-лист в каждой группе строк, включая столбцы, целиком состоящие из NULL. Буферы фильтров Блума накапливаются по всем группам строк до закрытия файла и учитываются в лимите памяти запроса. Поэтому широкие схемы или большое число групп строк могут существенно увеличить потребление памяти. Фильтры также увеличивают затраты на хеширование и размер файла и не гарантируют ускорения чтения. В этой версии нет настроек выбора столбцов, размера фильтров Блума или отдельного лимита памяти для них на уровне файла.

## Параметры {#parameters}

### Совместимость временных меток и дат (начиная с 4.1.5) {#timestamp-and-date-compatibility}

Начиная с 4.1.5, при чтении и записи Parquet сохраняется различие между локальным временем и моментом времени. Логическая временная метка без часового пояса сопоставляется с `DATETIME`, а логическая временная метка с `isAdjustedToUTC=true` — с `TIMESTAMPTZ`. Ни свойство совместимости Catalog, ни `enable_mapping_timestamp_tz=false` в файловой TVF не могут восстановить сопоставление последней с `DATETIME`.

Parquet INT96 не содержит аннотации часового пояса и определяется как `DATETIME(6)`. Hive Catalog и файловые TVF принимают необязательное свойство `hive.parquet.time-zone` для указания часового пояса, который использовался при записи INT96. По умолчанию это пустая строка, при которой сохраняется локальное время. Укажите часовой пояс IANA или смещение относительно UTC от `-12:00` до `+14:00`. Значения `UTC` и `GMT` принимаются; короткие обозначения, такие как `CST` и `PRC`, отклоняются. Задавайте это свойство, только если часовой пояс записи известен, например `"hive.parquet.time-zone" = "Asia/Shanghai"`.

Начиная с 4.1.5, значение `enable_int96_timestamps` для Outfile и Export по умолчанию равно `false`, поэтому записываются логические временные метки INT64. Устанавливайте его в `true` только для потребителей, которым требуется INT96. Для записи в таблицы Hive предусмотрен другой вариант настройки совместимости; см. [Hive Catalog](../catalogs/hive-catalog.mdx).

Файлы DATE, записанные со старым кодированием Doris и содержащие даты от `0000-01-01` до `0000-02-28`, требуют миграции с учётом средства, которым они были записаны. Одного обновления средства чтения недостаточно для их исправления. См. [Миграция файлов DATE с нулевым годом](../../admin-manual/cluster-management/upgrade.md#year-zero-date-file-migration).

### Переменные сеанса {#session-variables}

* `enable_parquet_lazy_mat` (2.1+, 3.0+)

    Определяет, включает ли средство чтения Parquet отложенную материализацию. По умолчанию — true.

* `hive_parquet_use_column_names` (2.1.6+, 3.0.3+)

    При чтении данных Parquet из таблиц Hive Doris по умолчанию использует столбцы файла Parquet, имена которых совпадают с именами столбцов таблицы Hive. Если эта переменная имеет значение `false`, Doris читает данные из файла Parquet в соответствии с порядком столбцов в таблице Hive независимо от их имён. Это похоже на переменную Hive `parquet.column.index.access`. Параметр применяется только к именам столбцов верхнего уровня и не действует для столбцов внутри Struct.

### Конфигурация BE {#be-configuration}

* `parquet_metadata_size_limit` (начиная с 4.1.5)

    Максимальный размер сериализованных метаданных в конце файла для нативного средства чтения Parquet V2. По умолчанию — `268435456` байт (256 MiB); значение должно быть больше `0` и может изменяться динамически. Этот лимит не связан с лимитом заголовка страницы. При его превышении возвращается сообщение `Parquet v2 footer size ... exceeds metadata limit ...`. См. [Конфигурация BE](../../admin-manual/config/be-config.md#parquet_metadata_size_limit).

* `enable_parquet_page_index` (2.1.5+, 3.0+)

    Определяет, использует ли средство чтения Parquet индекс страниц для фильтрации данных. Предназначен только для отладки на случай, если индекс страниц иногда ошибочно отфильтровывает данные. Значение по умолчанию — false.

* `parquet_header_max_size_mb` (2.1+, 3.0+)

    Максимальный размер буфера, выделяемого при чтении заголовка страницы Parquet. По умолчанию — 1M.

* `parquet_rowgroup_max_buffer_mb` (2.1+, 3.0+)

    Максимальный размер буфера, выделяемого при чтении группы строк Parquet. По умолчанию — 128M.

* `parquet_column_max_buffer_mb` (2.1+, 3.0+)

    Максимальный размер буфера, выделяемого при чтении столбца внутри группы строк Parquet. По умолчанию — 8M.
