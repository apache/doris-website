Каталог данных описывает свойства источника данных.

В Doris можно создать несколько каталогов данных, указывающих на разные источники, например Hive, Iceberg, Paimon и PostgreSQL. Через каталоги данных Doris автоматически получает сведения о базах данных, таблицах, схемах, разделах и расположении данных из соответствующих источников. Пользователи могут обращаться к этим каталогам данных с помощью стандартных SQL-запросов для анализа данных, а также выполнять запросы с соединением данных из нескольких каталогов.

В Doris есть два типа каталогов данных:

| Тип | Описание |
| ---------------- | -------------------------------------------------------- |
| Internal Catalog | Встроенный каталог данных с фиксированным именем `internal`, в котором хранятся данные внутренних таблиц Doris. Его нельзя создать, изменить или удалить. |
| External Catalog | Внешние каталоги данных — все каталоги, кроме Internal Catalog. Пользователи могут создавать, изменять и удалять внешние каталоги данных. |

Каталоги данных в основном применяются в следующих трёх сценариях. Возможности конкретного каталога зависят от его типа; подробности приведены в документации соответствующего каталога данных.

| Сценарий | Описание |
| ---- | ------------------------------------------- |
| Ускорение запросов | Непосредственное ускорение запросов к данным озера, например в Hive, Iceberg и Paimon. |
| Интеграция данных | Прямой доступ к разным источникам по подходу ZeroETL для получения результирующих данных или удобного перемещения данных между источниками. |
| Обратная запись данных | Обработка и преобразование данных в Doris с последующей записью во внешние источники. |

В этой статье основные операции с каталогами данных показаны на примере [Iceberg Catalog](./catalogs/iceberg-catalog). Подробности о разных каталогах данных приведены в соответствующей документации.

## Маскирование конфиденциальных свойств {#sensitive-property-masking}

Единая политика маскирования свойств Catalog запланирована для Doris 4.2.0, а также для версий 5.0 и выше. В поддерживаемых путях отображения, аудита и отслеживания происхождения данных маскируются пароли, ключи доступа, токены, строки JDBC и учётные данные в URL; значения, используемые при подключении, остаются неизменными. Правила, различия между версиями, настройки и ограничения описаны в разделе [«Маскирование свойств Catalog»](./catalog-property-masking.md).

## Создание каталога данных {#creating-a-data-catalog}

Создайте Iceberg Catalog с помощью инструкции `CREATE CATALOG`.

```sql
CREATE CATALOG iceberg_catalog PROPERTIES (
    'type' = 'iceberg',
    'iceberg.catalog.type' = 'hadoop',
    'warehouse' = 's3://bucket/dir/key',
    's3.endpoint' = 'https://s3.us-east-1.amazonaws.com',
    's3.access_key' = 'ak',
    's3.secret_key' = 'sk'
);
```

По сути, созданный в Doris каталог данных служит «прокси» для доступа к службе метаданных соответствующего источника, например Hive Metastore, и его хранилищу, например HDFS/S3. Doris хранит только свойства подключения и другие сведения о каталоге данных, но не сами метаданные или данные соответствующего источника.

### Общие свойства {#common-properties}

Помимо свойств, характерных для каждого каталога данных, существуют общие для всех каталогов свойства `{CommonProperties}`.

| Свойство | Описание | Пример |
| ----------------------- | ------------------------------------------------------------------------- | ------------------------------------- |
| `include_database_list` | Задаёт несколько баз данных для синхронизации, разделённых символом `,`. По умолчанию синхронизируются все базы данных. Имена баз данных чувствительны к регистру. Если во внешнем источнике много баз данных, а обращаться нужно лишь к нескольким, это свойство позволяет избежать синхронизации большого объёма метаданных. | `'include_database_list' = 'db1,db2'` |
| `exclude_database_list` | Задаёт несколько баз данных, исключаемых из синхронизации, разделённых символом `,`. По умолчанию фильтрация не применяется и синхронизируются все базы данных. Имена баз данных чувствительны к регистру. Свойство подходит для того же сценария, что и предыдущее, но исключает базы данных, к которым не нужен доступ. При конфликте `exclude` имеет приоритет над `include`. | `'exclude_database_list' = 'db1,db2'` |
| `include_table_list` | Задаёт несколько таблиц для синхронизации в формате `db.tbl`, разделённых символом `,`. Если свойство задано, при получении списка таблиц базы данных возвращаются только указанные таблицы: полный список не запрашивается у удалённой службы метаданных. Это полезно, когда во внешнем источнике много таблиц и получение полного списка может завершиться по тайм-ауту. | `'include_table_list' = 'db1.tbl1,db1.tbl2,db2.tbl3'` |
| `lower_case_table_names` | Управляет учётом регистра в именах таблиц на уровне Catalog. Значения и их смысл приведены ниже, в разделе [«Учёт регистра в именах таблиц»](#table-name-case-sensitivity-lower_case_table_names). По умолчанию значение наследуется от глобальной переменной `lower_case_table_names`. | `'lower_case_table_names' = '1'` |
| `lower_case_database_names` | Управляет учётом регистра в именах баз данных на уровне Catalog. Значения и их смысл приведены ниже, в разделе [«Учёт регистра в именах баз данных»](#database-name-case-sensitivity-lower_case_database_names). Значение по умолчанию — `0` (регистр учитывается). | `'lower_case_database_names' = '2'` |

### Указание списка таблиц {#specifying-table-list}

Эта возможность поддерживается начиная с версии 4.1.0.

Если внешний источник данных, например Hive Metastore, содержит много таблиц, получение их полного списка от удалённой службы метаданных может занять много времени или завершиться по тайм-ауту. Свойство `include_table_list` позволяет указать таблицы для синхронизации и не запрашивать полный список у удалённой службы.

В `include_table_list` таблицы задаются в формате `db.tbl` и разделяются запятыми `,`.

```sql
CREATE CATALOG hive_catalog PROPERTIES (
    'type' = 'hms',
    'hive.metastore.uris' = 'thrift://hms-host:9083',
    'include_table_list' = 'db1.table1,db1.table2,db2.table3'
);
```

После установки свойства:

- При получении списка таблиц в `db1` возвращаются только `table1` и `table2`, без вызова API удалённой службы метаданных для получения полного списка.
- При получении списка таблиц в `db2` возвращается только `table3`.
- Для баз данных, не указанных в `include_table_list`, например `db3`, полный список таблиц по-прежнему запрашивается у удалённой службы метаданных.
- Записи `include_table_list` с неверным форматом, отличным от `db.tbl`, игнорируются.

:::tip
Это свойство можно использовать вместе с `include_database_list`. Например, сначала отберите нужные базы данных с помощью `include_database_list`, а затем укажите нужные таблицы с помощью `include_table_list`.
:::

### Учёт регистра в именах таблиц {#table-name-case-sensitivity-lower_case_table_names}

Эта возможность поддерживается начиная с версии 4.1.0.

Свойство `lower_case_table_names` управляет обработкой регистра имён таблиц на уровне Catalog. Оно поддерживает три режима:

| Значение | Режим | Описание |
| -- | ---- | ---- |
| `0` | С учётом регистра (по умолчанию) | Имена таблиц сохраняются и сравниваются в исходном регистре. При обращении к таблице регистр её имени должен точно совпадать с регистром в удалённых метаданных. |
| `1` | Хранение в нижнем регистре | Имена таблиц в Doris хранятся в нижнем регистре. Подходит, если при обращении к внешним источникам нужно единообразно использовать имена таблиц в нижнем регистре. |
| `2` | Сравнение без учёта регистра | Имена таблиц сравниваются без учёта регистра, но при отображении сохраняется исходный регистр из удалённых метаданных. Подходит, если регистр имён таблиц во внешнем источнике не согласован и к таблицам нужно обращаться без учёта регистра. |

Если свойство не задано, по умолчанию наследуется значение глобальной переменной `lower_case_table_names`.

```sql
CREATE CATALOG hive_catalog PROPERTIES (
    'type' = 'hms',
    'hive.metastore.uris' = 'thrift://hms-host:9083',
    'lower_case_table_names' = '2'
);
```

:::caution
Если `lower_case_table_names` имеет значение `1` или `2`, а в удалённых метаданных есть таблицы, имена которых отличаются только регистром, например `MyTable` и `mytable`, возможен конфликт. Doris обнаружит его и сообщит об ошибке.
:::

### Учёт регистра в именах баз данных {#database-name-case-sensitivity-lower_case_database_names}

Эта возможность поддерживается начиная с версии 4.1.0.

Свойство `lower_case_database_names` управляет обработкой регистра имён баз данных на уровне Catalog. Оно поддерживает три режима:

| Значение | Режим | Описание |
| -- | ---- | ---- |
| `0` | С учётом регистра (по умолчанию) | Имена баз данных сохраняются и сравниваются в исходном регистре. При обращении к базе данных регистр её имени должен точно совпадать с регистром в удалённых метаданных. |
| `1` | Хранение в нижнем регистре | Имена баз данных в Doris хранятся в нижнем регистре. Подходит, если при обращении к внешним источникам нужно единообразно использовать имена баз данных в нижнем регистре. |
| `2` | Сравнение без учёта регистра | Имена баз данных сравниваются без учёта регистра, но при отображении сохраняется исходный регистр из удалённых метаданных. Подходит, если регистр имён баз данных во внешнем источнике не согласован и к базам данных нужно обращаться без учёта регистра. |

Значение по умолчанию — `0` (регистр учитывается).

```sql
CREATE CATALOG hive_catalog PROPERTIES (
    'type' = 'hms',
    'hive.metastore.uris' = 'thrift://hms-host:9083',
    'lower_case_database_names' = '2',
    'lower_case_table_names' = '2'
);
```

:::caution
Если `lower_case_database_names` имеет значение `1` или `2`, а в удалённых метаданных есть базы данных, имена которых отличаются только регистром, например `MyDB` и `mydb`, возможен конфликт. Doris обнаружит его и сообщит об ошибке.
:::

:::info
`lower_case_database_names` и `lower_case_table_names` можно задавать независимо друг от друга. Например, для имён баз данных можно включить учёт регистра (`0`), а для имён таблиц — сравнение без учёта регистра (`2`).
:::

### Сопоставление типов столбцов {#column-type-mapping}

После создания каталога данных Doris автоматически синхронизирует сведения о его базах данных, таблицах и схемах. Правила сопоставления типов столбцов для разных каталогов данных приведены в соответствующей документации.

Если внешний тип данных, например `UNION` или `INTERVAL`, пока нельзя сопоставить с типом столбца Doris, Doris назначает столбцу тип `UNSUPPORTED`. Поведение запросов с типом `UNSUPPORTED` показано в следующих примерах.

Предположим, схема синхронизированной таблицы выглядит так:

```text
k1 INT,
k2 INT,
k3 UNSUPPORTED,
k4 INT
```

Поведение запросов будет следующим:

```sql
SELECT * FROM table;                -- Error: Unsupported type 'UNSUPPORTED_TYPE' in 'k3'
SELECT * EXCEPT(k3) FROM table;     -- Query OK.
SELECT k1, k3 FROM table;           -- Error: Unsupported type 'UNSUPPORTED_TYPE' in 'k3'
SELECT k1, k4 FROM table;           -- Query OK.
```

### Свойство Nullable {#nullable-property}

В настоящее время поддержка свойства Nullable для столбцов внешних таблиц в Doris имеет особые ограничения. Поведение описано ниже:

| Тип в источнике | Поведение Doris при чтении | Поведение Doris при записи |
| --- | --- | --- |
| Nullable | Nullable | Разрешает записывать значения Null |
| Not Null | Nullable, то есть столбец всё равно читается как допускающий NULL | Разрешает записывать значения Null, то есть не выполняет строгую проверку таких значений. Пользователи должны самостоятельно обеспечивать целостность и согласованность данных. |

## Использование каталогов данных {#using-data-catalogs}

### Просмотр каталогов данных {#viewing-data-catalogs}

После создания каталоги можно просмотреть с помощью команды `SHOW CATALOGS`:

```text
mysql> SHOW CATALOGS;
+-----------+-----------------+----------+-----------+-------------------------+---------------------+------------------------+
| CatalogId | CatalogName     | Type     | IsCurrent | CreateTime              | LastUpdateTime      | Comment                |
+-----------+-----------------+----------+-----------+-------------------------+---------------------+------------------------+
|     10024 | iceberg_catalog | iceberg  | yes       | 2023-12-25 16:11:41.687 | 2023-12-25 20:43:18 | NULL                   |
|         0 | internal        | internal |           | NULL                    | NULL                | Doris internal catalog |
+-----------+-----------------+----------+-----------+-------------------------+---------------------+------------------------+
```

Инструкцию создания каталога можно просмотреть с помощью [SHOW CREATE CATALOG](../sql-manual/sql-statements/catalog/SHOW-CREATE-CATALOG).

### Переключение каталогов данных {#switching-data-catalogs}

Инструкция `SWITCH` в Doris переключает контекст сеанса подключения на соответствующий каталог данных, подобно тому как инструкция `USE` переключает базы данных.

После переключения на каталог данных можно с помощью инструкции `USE` перейти к определённой базе данных, а с помощью `SHOW DATABASES` — просмотреть базы данных в текущем каталоге.

```sql
SWITCH iceberg_catalog;

SHOW DATABASES;
+--------------------+
| Database           |
+--------------------+
| information_schema |
| mysql              |
| test               |
| iceberg_db         |
+--------------------+

USE iceberg_db;
```

Чтобы сразу перейти к определённой базе данных в определённом каталоге, можно передать инструкции `USE` полное имя `catalog_name.database_name`:

```sql
USE iceberg_catalog.iceberg_db;
```

Полное имя также можно использовать в командной строке MySQL или строке подключения JDBC для совместимости с протоколом подключения MySQL.

```sql
# Command line tool
mysql -h host -P9030 -uroot -Diceberg_catalog.iceberg_db

# JDBC url
jdbc:mysql://host:9030/iceberg_catalog.iceberg_db
```

Встроенный каталог данных имеет фиксированное имя `internal`. Переключение на него выполняется так же, как на внешний каталог данных.

### Каталог данных по умолчанию {#default-data-catalog}

С помощью пользовательского свойства `default_init_catalog` можно задать каталог данных по умолчанию для определённого пользователя. После этого при подключении такого пользователя к Doris сеанс автоматически переключается на заданный каталог.

```sql
SET PROPERTY default_init_catalog=hive_catalog;
```

Примечание 1. Если каталог данных явно указан в командной строке MySQL или строке подключения JDBC, используется он, а пользовательское свойство `default_init_catalog` не действует.

Примечание 2. Если каталог данных, заданный пользовательским свойством `default_init_catalog`, больше не существует, сеанс автоматически переключается на каталог `internal` по умолчанию.

Примечание 3. Эта возможность поддерживается начиная с версии 3.1.x.

### Простые запросы {#simple-queries}

К таблицам во внешних каталогах данных можно выполнять любые SQL-запросы, поддерживаемые Doris.

```sql
SELECT id, SUM(cost) FROM iceberg_db.table1
GROUP BY id ORDER BY id;
```

### Запросы к нескольким каталогам данных {#cross-catalog-queries}

Doris поддерживает запросы с соединением данных из разных каталогов.

Создадим ещё один каталог — [MySQL Catalog](./catalogs/jdbc-mysql-catalog.md):

```sql
CREATE CATALOG mysql_catalog properties(
    'type' = 'jdbc',
    'user' = 'root',
    'password' = '123456',
    'jdbc_url' = 'jdbc:mysql://host:3306/mysql_db',
    'driver_url' = 'mysql-connector-java-8.0.25.jar',
    'driver_class' = 'com.mysql.cj.jdbc.Driver'
);
```

Затем выполним SQL-запрос с соединением таблиц Iceberg и MySQL:

```sql
SELECT * FROM
iceberg_catalog.iceberg_db.table1 tbl1 JOIN mysql_catalog.mysql_db.dim_table tbl2
ON tbl1.id = tbl2.id;
```

### Загрузка данных {#data-ingestion}

Данные из источников можно загрузить в Doris с помощью команды `INSERT`.

```sql
INSERT INTO internal.doris_db.tbl1
SELECT * FROM iceberg_catalog.iceberg_db.table1;
```

Также с помощью инструкции `CTAS (Create Table As Select)` можно создать внутреннюю таблицу Doris на основе внешнего источника и загрузить в неё данные:

```sql
CREATE TABLE internal.doris_db.tbl1
PROPERTIES('replication_num' = '1')
AS
SELECT * FROM iceberg_catalog.iceberg_db.table1;
```

### Обратная запись данных {#data-write-back}

Doris поддерживает прямую обратную запись данных во внешние источники с помощью инструкции `INSERT`. Подробности см. в документации:

* [Hive Catalog](./catalogs/hive-catalog.mdx)

* [Iceberg Catalog](./catalogs/iceberg-catalog.mdx)

* [JDBC Catalog](./catalogs/jdbc-catalog-overview.md)

## Обновление каталогов данных {#refreshing-data-catalogs}

Созданные в Doris каталоги данных служат «прокси» для доступа к службам метаданных соответствующих источников. Doris кэширует часть метаданных. Кэширование ускоряет доступ к ним и позволяет избежать частых сетевых запросов. Однако данные в кэше могут устаревать: без обновления кэша новые метаданные будут недоступны. Поэтому Doris предоставляет несколько способов обновления каталогов данных.

```sql
-- Refresh catalog
REFRESH CATALOG catalog_name;

-- Refresh specified database
REFRESH DATABASE catalog_name.db_name;

-- Refresh specified table
REFRESH TABLE catalog_name.db_name.table_name;
```

В Doris также можно отключить кэширование метаданных, чтобы получать актуальные метаданные в реальном времени.

- До Doris 4.1.x: см. раздел [«Кэш метаданных»](./meta-cache.md).
- Начиная с Doris 4.1.x: см. раздел «Кэш метаданных» в документации каждого Catalog.
    - [Hive Catalog](./catalogs/hive-catalog.mdx#meta-cache)
    - [Iceberg Catalog](./catalogs/iceberg-catalog.mdx#meta-cache)
    - [Hudi Catalog](./catalogs/hudi-catalog.md#meta-cache)
    - [Paimon Catalog](./catalogs/paimon-catalog.mdx#meta-cache)
    - [MaxCompute Catalog](./catalogs/maxcompute-catalog.md#meta-cache)

## Изменение каталогов данных {#modifying-data-catalogs}

Свойства или имя каталога данных можно изменить с помощью `ALTER CATALOG`:

```sql
-- Rename a catalog
ALTER CATALOG iceberg_catalog RENAME iceberg_catalog2;

-- Modify properties of a catalog
ALTER CATALOG iceberg_catalog SET PROPERTIES ('key1' = 'value1' [, 'key' = 'value2']);

-- Modify the comment of a catalog
ALTER CATALOG iceberg_catalog MODIFY COMMENT 'my iceberg catalog';
```

## Удаление каталогов данных {#dropping-data-catalogs}

Указанный внешний каталог данных можно удалить с помощью `DROP CATALOG`.

```sql
DROP CATALOG [IF EXISTS] iceberg_catalog;
```

Удаление внешнего каталога данных из Doris не удаляет сами данные. Удаляется только сопоставление каталога данных, хранящееся в Doris.

## Управление правами доступа {#permission-management}

Управление правами доступа к базам данных и таблицам во внешних каталогах данных устроено так же, как для внутренних таблиц. Подробности см. в документации [«Аутентификация и авторизация»](../admin-manual/auth/authentication-and-authorization.md).

## Проверка определения разделов внешних таблиц (начиная с 4.1.5) {#external-table-partition-validation-since-415}

Начиная с версии 4.1.5, при создании внешней таблицы Doris проверяет модель разделов Catalog до преобразования определения разделов:

| Catalog | Поддерживаемое определение | Неподдерживаемое определение |
| --- | --- | --- |
| Hive | `PARTITION BY LIST` с именами существующих столбцов | RANGE, выражения разделения и явные значения разделов |
| Paimon / MaxCompute | Ключи разделения, заданные именами столбцов | Выражения с функциями разделения и явные значения разделов |
| Iceberg | Поддерживаемые определения разделов по столбцам или преобразованиям | Явные значения разделов в синтаксисе внутренних таблиц Doris |

Не используйте для внешних таблиц определения внутренних таблиц с перечислением значений разделов. Например, в Hive разделы создаются на основе записанных данных, поэтому заранее указывать `VALUES IN (...)` не требуется.
