Новая открытая архитектура управления данными Data Lakehouse объединяет высокую производительность и возможности работы в реальном времени, свойственные хранилищам данных, с низкой стоимостью и гибкостью озёр данных. Это позволяет пользователям удобнее решать разнообразные задачи обработки и анализа данных. Такая архитектура всё шире применяется в корпоративных системах больших данных.

В последних версиях Apache Doris расширил интеграцию с озёрами данных и стал зрелым решением для построения Data Lakehouse.

- Начиная с версии 0.15, в Apache Doris появились внешние таблицы Hive и Iceberg, что позволило исследовать возможности совместного использования с Apache Iceberg для работы с озёрами данных.
- Начиная с версии 1.2, Apache Doris официально представил функцию Multi-Catalog, обеспечивающую автоматическое сопоставление метаданных и доступ к данным из различных источников, а также многочисленные оптимизации производительности чтения внешних данных и выполнения запросов. Теперь Doris обладает всеми возможностями для построения быстрой и удобной архитектуры Lakehouse.
- В версии 2.1 архитектура Data Lakehouse в Apache Doris была значительно улучшена: расширены возможности чтения и записи основных форматов озёр данных (Hudi, Iceberg, Paimon и др.), добавлены совместимость с несколькими диалектами SQL и возможность беспрепятственной миграции из существующих систем в Apache Doris. Для задач науки о данных и чтения больших объёмов данных в Doris интегрирован высокоскоростной интерфейс чтения Arrow Flight, благодаря чему эффективность передачи данных выросла в 100 раз.

## Apache Doris и Hudi {#apache-doris--hudi}

[Apache Hudi](https://hudi.apache.org/) сегодня является одним из самых популярных открытых форматов озёр данных и платформой управления транзакционными озёрами данных. Он поддерживает различные распространённые движки запросов, включая Apache Doris.

Apache Doris также расширил возможности чтения таблиц данных Apache Hudi:

- Поддержка таблиц Copy on Write: Snapshot Query
- Поддержка таблиц Merge on Read: Snapshot Queries, Read Optimized Queries
- Поддержка Time Travel
- Поддержка Incremental Read

Высокая производительность выполнения запросов в Apache Doris в сочетании с возможностями Apache Hudi по управлению данными в реальном времени позволяет эффективно, гибко и с низкими затратами выполнять запросы и анализировать данные. Это сочетание также обеспечивает надёжные возможности отслеживания происхождения данных, аудита и инкрементальной обработки. Совместное использование Apache Doris и Apache Hudi уже проверено и внедрено несколькими пользователями сообщества в реальных бизнес-сценариях:

- Анализ и обработка данных в реальном времени: типичные сценарии, такие как обновление данных и выполнение аналитических запросов в реальном времени в финансовой сфере, рекламе и электронной коммерции, требуют обработки данных в реальном времени. Hudi обеспечивает обновление данных и управление ими в реальном времени, сохраняя их согласованность и надёжность. Doris эффективно обрабатывает запросы к большим объёмам данных в реальном времени. Вместе они позволяют успешно решать задачи анализа и обработки данных в реальном времени.
- Отслеживание происхождения данных и аудит: в отраслях с высокими требованиями к безопасности и точности данных, таких как финансы и здравоохранение, отслеживание происхождения данных и аудит имеют решающее значение. Hudi предоставляет функцию Time Travel для просмотра исторических состояний данных. В сочетании с эффективным выполнением запросов в Apache Doris это позволяет быстро анализировать данные на любой момент времени для точного отслеживания их происхождения и аудита.
- Инкрементальное чтение и анализ данных: при масштабном анализе данных часто возникают трудности из-за больших объёмов данных и частых обновлений. Hudi поддерживает инкрементальное чтение, позволяя пользователям обрабатывать только изменённые данные без полного обновления всего набора. Функция Incremental Read в Apache Doris дополнительно улучшает этот процесс, значительно повышая эффективность обработки и анализа данных.
- Федеративные запросы к разным источникам данных: во многих компаниях данные поступают из множества источников и хранятся в разных базах данных. Функция Multi-Catalog в Doris поддерживает автоматическое сопоставление и синхронизацию различных источников данных, позволяя выполнять федеративные запросы к ним. Это существенно сокращает путь передачи данных и повышает эффективность работы компаний, которым необходимо извлекать и объединять данные из нескольких источников для анализа.

В этой статье мы покажем, как быстро развернуть тестовую и демонстрационную среду Apache Doris + Apache Hudi в Docker, и рассмотрим различные операции, которые помогут быстро приступить к работе.

Дополнительные сведения см. в разделе [Hudi Catalog](../catalogs/hudi-catalog.md)

### 02 Развёртывание среды {#02-environment-deployment}

1. Создайте сеть Docker

	`sudo docker network create -d bridge hudi-net`

2. Запустите все компоненты

	`sudo ./start-hudi-compose.sh`
	
	> Примечание: перед запуском можно изменить значения `DORIS_PACKAGE` и `DORIS_DOWNLOAD_URL` в `start-hudi-compose.sh`, чтобы выбрать нужную версию Doris. Рекомендуется использовать версию 2.1.4 или выше.

3. После запуска можно использовать следующий скрипт для входа в командную строку Spark или Doris:

	```
	-- Spark
	sudo ./login-spark.sh
	
	-- Doris
	sudo ./login-doris.sh
	```

### 03 Подготовка данных {#03-data-preparation}

Теперь создадим данные Hudi с помощью Spark. Как показано в коде ниже, в кластере уже есть таблица Hive с именем `customer`. На её основе можно создать таблицу Hudi:

```
-- ./login-spark.sh
spark-sql> use default;

-- create a COW table
spark-sql> CREATE TABLE customer_cow
USING hudi
TBLPROPERTIES (
  type = 'cow',
  primaryKey = 'c_custkey',
  preCombineField = 'c_name'
)
PARTITIONED BY (c_nationkey)
AS SELECT * FROM customer;

-- create a MOR table
spark-sql> CREATE TABLE customer_mor
USING hudi
TBLPROPERTIES (
  type = 'mor',
  primaryKey = 'c_custkey',
  preCombineField = 'c_name'
)
PARTITIONED BY (c_nationkey)
AS SELECT * FROM customer;
```

## Оптимизация запросов {#query-optimization}

Данные в Apache Hudi можно условно разделить на две категории: базовые и инкрементальные. Базовые данные обычно представляют собой объединённые файлы Parquet, а инкрементальные данные содержат изменения, созданные операциями INSERT, UPDATE или DELETE. Базовые данные можно читать напрямую, а инкрементальные необходимо читать через Merge on Read.

При запросах к таблицам Hudi COW или выполнении запросов Read Optimized к таблицам MOR используются базовые данные. Их можно читать напрямую с помощью встроенного в Doris Parquet Reader, что обеспечивает быстрое выполнение запросов. Для чтения инкрементальных данных Doris необходимо обращаться к Java SDK Hudi через вызовы JNI. Чтобы обеспечить оптимальную производительность запросов, Apache Doris разделяет данные запроса на базовую и инкрементальную части и читает их описанными выше способами.

Чтобы проверить этот подход к оптимизации, воспользуемся оператором EXPLAIN и посмотрим, сколько базовых и инкрементальных данных содержится в приведённом ниже примере запроса. Для таблицы COW все 101 фрагмент данных относятся к базовым данным (`hudiNativeReadSplits=101/101`), поэтому всю таблицу COW можно прочитать напрямую с помощью Parquet Reader в Doris, обеспечив наилучшую производительность запроса. Для таблицы ROW большинство фрагментов содержат базовые данные (`hudiNativeReadSplits=100/101`), а один фрагмент содержит инкрементальные данные, что также обеспечивает хорошую производительность запроса.

```
-- COW table is read natively
doris> explain select * from customer_cow where c_custkey = 32;
|   0:VHUDI_SCAN_NODE(68)                                        |
|      table: customer_cow                                       |
|      predicates: (c_custkey[#5] = 32)                          |
|      inputSplitNum=101, totalFileSize=45338886, scanRanges=101 |
|      partition=26/26                                           |
|      cardinality=1, numNodes=1                                 |
|      pushdown agg=NONE                                         |
|      hudiNativeReadSplits=101/101                              |

-- MOR table: because only the base file contains `c_custkey = 32` that is updated, 100 splits are read natively, while the split with log file is read by JNI.
doris> explain select * from customer_mor where c_custkey = 32;
|   0:VHUDI_SCAN_NODE(68)                                        |
|      table: customer_mor                                       |
|      predicates: (c_custkey[#5] = 32)                          |
|      inputSplitNum=101, totalFileSize=45340731, scanRanges=101 |
|      partition=26/26                                           |
|      cardinality=1, numNodes=1                                 |
|      pushdown agg=NONE                                         |
|      hudiNativeReadSplits=100/101                              |
```

Чтобы подробнее проследить изменения базовых и инкрементальных данных Hudi, можно выполнить несколько операций удаления с помощью Spark:

```
-- Use delete statement to see more differences
spark-sql> delete from customer_cow where c_custkey = 64;
doris> explain select * from customer_cow where c_custkey = 64;

spark-sql> delete from customer_mor where c_custkey = 64;
doris> explain select * from customer_mor where c_custkey = 64;
```

Кроме того, можно дополнительно сократить объём читаемых данных, используя условия по разделам для их отсечения, и тем самым ускорить запрос. В примере ниже отсечение разделов выполняется по условию `c_nationkey=15`, благодаря чему запрос обращается к данным только одного раздела (`partition=1/26`).

```
-- customer_xxx is partitioned by c_nationkey, we can use the partition column to prune data
doris> explain select * from customer_mor where c_custkey = 64 and c_nationkey = 15;
|   0:VHUDI_SCAN_NODE(68)                                        |
|      table: customer_mor                                       |
|      predicates: (c_custkey[#5] = 64), (c_nationkey[#12] = 15) |
|      inputSplitNum=4, totalFileSize=1798186, scanRanges=4      |
|      partition=1/26                                            |
|      cardinality=1, numNodes=1                                 |
|      pushdown agg=NONE                                         |
|      hudiNativeReadSplits=3/4                                  |
```
