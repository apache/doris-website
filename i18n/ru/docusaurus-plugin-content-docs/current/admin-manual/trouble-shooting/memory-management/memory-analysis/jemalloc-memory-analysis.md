По умолчанию Doris использует Jemalloc в качестве универсального аллокатора памяти. Память, занимаемая самим Jemalloc, включает Cache и Metadata. В Cache входят Thread Cache и Dirty Page. Исходный профиль аллокатора памяти можно просмотреть в реальном времени в разделе **Профили Jemalloc**, расположенном в разделе **Информация о памяти** на веб-странице профиля процесса Doris BE по адресу http://{be_host}:{be_web_server_port}/profile.

## Анализ памяти Jemalloc Cache {#jemalloc-cache-memory-analysis}

Если у трекера памяти `Label=tc/jemalloc_cache, Type=overview` большое значение, это означает, что Cache в Jemalloc или TCMalloc занимает много памяти. Doris использует Jemalloc в качестве аллокатора по умолчанию, поэтому здесь рассматривается только ситуация, когда много памяти занимает Jemalloc Cache.

```
MemTrackerLimiter Label=tc/jemalloc_cache, Type=overview, Limit=-1.00 B(-1 B), Used=410.44 MB(430376896 B), Peak=-1.00 B(-1 B)
```

> До Doris 2.1.6 в `Label=tc/jemalloc_cache` также учитывается Jemalloc Metadata, и причиной слишком большого значения `Label=tc/jemalloc_cache` вполне может быть большой объём памяти, занимаемой Jemalloc Metadata. См. анализ трекера памяти `Label=tc/jemalloc_metadata`.

Во время работы процесса BE Jemalloc Cache состоит из двух частей.

- Thread Cache: кеширует заданное количество страниц. См. [Jemalloc opt.tcache](https://jemalloc.net/jemalloc.3.html#opt.tcache).

- Dirty Page: все страницы памяти в Arena, которые можно использовать повторно.

### Как просмотреть Jemalloc Cache {#jemalloc-cache-view-method}

Чтобы получить профиль Jemalloc, откройте раздел **Профили Jemalloc** в разделе **Информация о памяти** на веб-странице профиля процесса Doris BE по адресу `http://{be_host}:{be_web_server_port}/profile` (значение webserver_port по умолчанию: 8040). Использование Jemalloc Cache можно оценить по нескольким ключевым показателям.

- `tcache_bytes` в профиле Jemalloc показывает общий объём Jemalloc Thread Cache в байтах. Большое значение `tcache_bytes` означает, что Jemalloc Thread Cache занимает слишком много памяти.

- Большая сумма значений столбца `dirty` в таблице `extents` профиля Jemalloc указывает на то, что Jemalloc Dirty Page занимает слишком много памяти.

### Thread Cache занимает слишком много памяти {#thread-cache-memory-is-too-large}

Возможно, в Thread Cache кешируется много больших страниц, поскольку его верхний предел задаётся количеством страниц, а не их суммарным размером в байтах.

Попробуйте уменьшить значение `lg_tcache_max` в `JEMALLOC_CONF` в файле `be.conf`. Параметр `lg_tcache_max` задаёт верхний предел размера страницы в байтах, допускаемого к кешированию. Значение по умолчанию составляет 15, то есть 32 KB (2^15). Страницы большего размера не кешируются в Thread Cache. Параметр `lg_tcache_max` соответствует показателю `Maximum thread-cached size class` в профиле Jemalloc.

> До Doris 2.1 значение `lg_tcache_max` по умолчанию в `JEMALLOC_CONF` в файле `be.conf` составляет 20, что в некоторых сценариях приводит к чрезмерному размеру Jemalloc Cache. После Doris 2.1 его вернули к стандартному для Jemalloc значению 15.

Обычно это происходит потому, что запрос или загрузка в процессе BE запрашивает много страниц памяти крупных классов размеров, либо потому, что после выполнения запроса или загрузки с большим потреблением памяти в Thread Cache остаётся много таких страниц. Очистка Thread Cache выполняется в двух случаях. Первый: когда число операций выделения и освобождения памяти достигает определённого значения, освобождаются блоки памяти, которые давно не использовались. Второй: при завершении потока освобождаются все страницы. Здесь возможен неблагоприятный сценарий. Если поток больше не выполняет новых запросов или загрузок, он перестаёт выделять память и переходит в так называемое состояние `idle`. Пользователи ожидают, что после завершения запроса память будет освобождена, но в этом сценарии Thread Cache не очищается, пока поток не завершится.

Однако обычно следить за Thread Cache не требуется. Когда процессу не хватает доступной памяти, а размер Thread Cache превышает 1G, Doris принудительно очищает Thread Cache.

Уменьшите значение `dirty_decay_ms` в `JEMALLOC_CONF` в файле `be.conf` до 2000 мс или меньше. Значение `dirty_decay_ms` по умолчанию в `be.conf` составляет 5000 мс. Jemalloc освобождает грязные страницы по плавной кривой в течение времени, заданного параметром `dirty_decay_ms`. Подробнее см. [Jemalloc opt.dirty_decay_ms](https://jemalloc.net/jemalloc.3.html#opt.dirty_decay_ms). Когда процессу BE не хватает доступной памяти и запускается Minor GC или Full GC, он активно освобождает все грязные страницы в соответствии с определённой стратегией.

> До Doris 2.1 значение `dirty_decay_ms` по умолчанию в `JEMALLOC_CONF` в файле `be.conf` составляет 15000, что в некоторых сценариях приводит к чрезмерному размеру Jemalloc Cache. После Doris 2.1 значение по умолчанию составляет 5000.

Раздел `extents` профиля Jemalloc содержит статистику по группам страниц разного размера во всех `arena` Jemalloc, где `ndirty` обозначает количество грязных страниц, а `dirty` обозначает их общий объём памяти. См. описание `stats.arenas.<i>.extents.<j>.{extent_type}_bytes` в документации [Jemalloc](https://jemalloc.net/jemalloc.3.html). Чтобы получить объём памяти Dirty Page в Jemalloc в байтах, сложите значения `dirty` для всех размеров страниц.

## Анализ памяти Jemalloc Metadata {#jemalloc-metadata-memory-analysis}

Если у трекера памяти `Label=tc/jemalloc_metadata, Type=overview` большое значение, это означает, что Metadata в Jemalloc или TCMalloc занимает много памяти. Doris использует Jemalloc в качестве аллокатора по умолчанию, поэтому здесь рассматривается только ситуация, когда много памяти занимает Jemalloc Metadata.

```
MemTrackerLimiter Label=tc/jemalloc_metadata, Type=overview, Limit=-1.00 B(-1 B), Used=144 MB(151759440 B), Peak=-1.00 B(-1 B)
```

> Трекер памяти `Label=tc/jemalloc_metadata` был добавлен после Doris 2.1.6. Ранее Jemalloc Metadata учитывалась в трекере памяти `Label=tc/jemalloc_cache`.

### Как просмотреть Jemalloc Metadata {#how-to-view-jemalloc-metadata}

Профиль Jemalloc можно получить в разделе **Профили Jemalloc**, расположенном в разделе **Информация о памяти** на веб-странице профиля процесса Doris BE по адресу `http://{be_host}:{be_web_server_port}/profile` (значение webserver_port по умолчанию: 8040). Найдите в профиле Jemalloc общую статистику использования памяти, показанную ниже. В ней `metadata` обозначает объём памяти Jemalloc Metadata.

`Allocated: 2401232080, active: 2526302208, metadata: 535979296 (n_thp 221), resident: 2995621888, mapped: 3221979136, retained: 131542581248`

- `Allocated`: общий объём памяти в байтах, выделенной Jemalloc для процесса BE.

- `active`: общий объём всех страниц в байтах, выделенных Jemalloc для процесса BE. Он кратен размеру страницы и обычно больше или равен `Allocated`.

- `metadata`: общий объём метаданных Jemalloc в байтах. Он зависит от количества выделенных и кешированных страниц, фрагментации памяти и других факторов. См. документацию [Jemalloc stats.metadata](https://jemalloc.net/jemalloc.3.html#stats.metadata)

- `retained`: размер отображений виртуальной памяти, удерживаемых Jemalloc. Эта память не возвращается операционной системе через munmap или аналогичные механизмы и не имеет тесной связи с физической памятью. См. документацию [Jemalloc stats.retained](https://jemalloc.net/jemalloc.3.html#stats.retained)

### Jemalloc Metadata занимает слишком много памяти {#jemalloc-metadata-memory-is-too-large}

Объём Jemalloc Metadata растёт с увеличением объёма виртуальной памяти процесса. Обычно большой объём виртуальной памяти процесса Doris BE объясняется тем, что Jemalloc удерживает множество отображений виртуальной памяти, то есть упомянутый выше `retained`. Виртуальная память, возвращённая Jemalloc, по умолчанию кешируется в Retained в ожидании повторного использования и не освобождается ни автоматически, ни вручную.

Основная причина большого объёма Jemalloc Retained заключается в недостаточном повторном использовании памяти на уровне кода Doris. Из-за этого приходится запрашивать большой объём виртуальной памяти, которая после освобождения попадает в Jemalloc Retained. Обычно отношение объёма виртуальной памяти к объёму Jemalloc Metadata находится в пределах 300-500. То есть при объёме виртуальной памяти 10T Jemalloc Metadata может занимать 20G.

Если Jemalloc Metadata и Retained продолжают расти, а объём виртуальной памяти процесса становится слишком большим, рекомендуется рассмотреть регулярный перезапуск процесса Doris BE. Обычно это происходит только после длительной работы Doris BE и встречается лишь в небольшом числе кластеров Doris. В настоящее время уменьшить объём отображений виртуальной памяти, удерживаемых Jemalloc Retained, без потери производительности невозможно. В Doris постоянно ведётся работа по оптимизации использования памяти.

Если описанные выше проблемы возникают часто, воспользуйтесь следующими способами.

1. Радикальное решение: отключить кеширование отображений виртуальной памяти в Jemalloc Retained. Для этого добавьте `retain:false` после `JEMALLOC_CONF` в файле `be.conf` и перезапустите BE. Однако производительность запросов может значительно снизиться: производительность в тесте TPC-H Benchmark уменьшится примерно в 3 раза.

2. В Doris 2.1 можно отключить Pipelinex и Pipeline, выполнив `set global experimental_enable_pipeline_engine=false; set global experimental_enable_pipeline_x_engine=false;`, поскольку pipelinex и pipeline запрашивают больше виртуальной памяти. Это также приведёт к снижению производительности запросов.
