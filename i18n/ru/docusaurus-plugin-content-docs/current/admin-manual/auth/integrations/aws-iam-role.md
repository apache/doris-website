# Как работает IAM Assume Role в Apache Doris {#how-apache-doris-iam-assume-role-works}

<!-- Knowledge type: Architecture principle / Authentication mechanism description -->
<!-- Applicable scenarios: Security compliance refactor / Replacing long-term AK/SK credentials / Cross-account S3 access -->

В этом документе описано, как Apache Doris обращается к ресурсам S3 с помощью механизма AWS IAM Assume Role: его преимущества перед традиционным подходом с AK/SK, процесс аутентификации с временными учётными данными STS и интеграция Doris с этим механизмом при развёртывании на EC2.

## Сценарии применения {#applicable-scenarios}

| Сценарий | Описание |
|------|------|
| Замена долгосрочных учётных данных AK/SK | Использование динамических временных учётных данных STS для устранения риска утечки ключей, явно заданных в конфигурации |
| Доступ к S3 из другого аккаунта | Сущность из исходного аккаунта принимает роль в целевом аккаунте, а External ID обеспечивает безопасную изоляцию |
| Аудит соблюдения принципа минимальных привилегий | Авторизация на основе ролей; AWS предоставляет журналы аудита с указанием конкретных исполнителей и действий |
| Кластеры Doris, развёрнутые на EC2 | Узлы FE/BE автоматически выполняют Assume Role через EC2 Instance Profile |

## Предварительные требования {#prerequisites}

- Apache Doris версии **3.0.6 или новее** (S3 Load, TVF, Export, Resource, Repository, Storage Vault и другие функции поддерживают Assume Role)
- Процессы FE и BE развёрнуты на экземплярах AWS EC2 с привязанной IAM Role
- Для исходного и целевого аккаунтов заранее определены роли IAM и отношения доверия
- Доступен сервис STS

## 1. Проблемы традиционного подхода с AK/SK при доступе к ресурсам AWS {#1-problems-with-the-traditional-aksk-approach-for-accessing-aws-resources}

<!-- Knowledge type: Background analysis -->

Схема доступа со статическими AK/SK имеет существенные недостатки в управлении ключами, отслеживании действий для аудита и контроле прав:

| Категория риска | Конкретное проявление |
|----------|----------|
| **Риск длительного несанкционированного доступа** | Статические AK/SK необходимо явно указывать в файлах конфигурации. При утечке из-за раскрытия кода, случайного коммита или кражи злоумышленники на постоянной основе получают все права владельца ключей. Это создаёт постоянный риск утечки данных, несанкционированного изменения ресурсов и финансовых потерь |
| **Пробелы в аудите** | Если несколько пользователей или сервисов используют один набор ключей, журналы облачных операций фиксируют только идентификатор ключа и не позволяют связать действия с конкретным пользователем. В результате невозможно установить, кто на самом деле выполнил действие или какой бизнес-модуль за него отвечает |
| **Высокие затраты на сопровождение** | Ротация ключей крайне трудоёмка: ключи бизнес-модулей приходится менять вручную, что чревато ошибками и легко приводит к перебоям в работе сервисов |
| **Недостаточный контроль прав** | Укрупнённая авторизация на уровне аккаунта не позволяет соблюдать принцип минимальных привилегий на уровне сервисов или экземпляров |

## 2. Обзор механизма AWS IAM Assume Role {#2-introduction-to-the-aws-iam-assume-role-mechanism}

<!-- Knowledge type: Concept definition -->

### 2.1 Что такое AWS IAM Assume Role {#21-what-is-aws-iam-assume-role}

AWS Assume Role представляет собой безопасный механизм смены идентичности, который позволяет доверенной сущности (например, пользователю IAM, экземпляру EC2 или внешнему аккаунту) временно получать права целевой роли через STS (Security Token Service). Схема работы показана ниже:

![Схема работы AWS IAM Assume Role](/images/integrations/aws_iam_role_flow.png)

### 2.2 Преимущества AWS IAM Assume Role {#22-advantages-of-using-aws-iam-assume-role}

- **Механизм динамических токенов**: замена постоянных учётных данных временными, действующими от 15 минут до 12 часов
- **Безопасная изоляция между аккаунтами**: использование External ID для безопасной изоляции между аккаунтами с возможностью аудита через консоль AWS
- **Принцип минимальных привилегий**: доступ на основе ролей с соблюдением принципа минимальных привилегий

### 2.3 Процесс аутентификации для доступа к бакету S3 через AWS IAM Assume Role {#23-authentication-flow-for-accessing-an-s3-bucket-via-aws-iam-assume-role}

<!-- Knowledge type: Operation flow / Authentication flow -->

Полный процесс аутентификации состоит из трёх этапов: проверки идентичности исходного пользователя, активации прав целевой роли и выполнения операций с ресурсами.

![Процесс аутентификации для доступа IAM Role к бакету S3](/images/integrations/iam_role_access_bucket.png)

#### Этап 1: Проверка идентичности исходного пользователя {#stage-1-source-user-identity-verification}

1. **Проверка политики разрешений**
    - Когда исходный пользователь инициирует запрос AssumeRole, механизм политик IAM исходного аккаунта сначала проверяет, разрешено ли пользователю вызывать действие `sts:AssumeRole`.
    - Основание проверки: IAM Permissions Policies, привязанные к идентичности исходного пользователя

2. **Проверка отношений доверия**
    - Через STS в целевой аккаунт отправляется запрос для проверки того, включён ли исходный пользователь в список разрешённых сущностей политики доверия целевой роли.
    - Основание проверки: IAM Trust Relationships Policies, привязанные к целевой роли (они явно указывают, каким аккаунтам или пользователям разрешено принимать эту роль)

#### Этап 2: Активация прав целевой роли {#stage-2-target-role-permission-activation}

3. **Генерация временных учётных данных**

    Если проверка отношений доверия пройдена, STS генерирует набор временных учётных данных из трёх компонентов:

    ```json
    {
        "AccessKeyId": "***",
        "SecretAccessKey": "***",
        "SessionToken": "***"
    }
    ```

    Учётные данные действуют от 15 минут до 12 часов.

4. **Проверка прав целевой роли**
    - Прежде чем целевая роль использует временные учётные данные для доступа к S3, механизм политик IAM целевого аккаунта проверяет, разрешено ли роли выполнять запрошенное действие S3 (например, `s3:GetObject` или `s3:PutObject`).
    - Основание проверки: IAM Permissions Policies, привязанные к целевой роли (они определяют, какие действия разрешены роли)

#### Этап 3: Выполнение операций с ресурсами {#stage-3-resource-operation-execution}

5. **Доступ к бакету**: после успешного прохождения всех проверок целевая роль может выполнять операции S3 API.

## 3. Как Doris использует механизм AWS IAM Assume Role {#3-how-doris-applies-the-aws-iam-assume-role-mechanism}

<!-- Knowledge type: Integration solution -->
<!-- Applicable scenarios: Configuring STS authentication for Doris on EC2 clusters -->

### 3.1 Принцип интеграции {#31-integration-principle}

Doris использует механизм AWS IAM Assume Role, привязывая экземпляры AWS EC2, на которых развёрнуты процессы FE и BE, к исходному аккаунту. Основная схема работы показана ниже:

![Схема интеграции Doris с IAM Role](/images/integrations/doris_iam_role.png)

После настройки процессы Doris FE и BE автоматически получают профиль экземпляра EC2 и выполняют Assume Role для доступа к бакету. При расширении кластера узлы BE автоматически проверяют, привязана ли IAM Role к каждому новому экземпляру EC2, чтобы не допустить пропусков в конфигурации.

### 3.2 Поддерживаемые функции {#32-supported-feature-scope}

S3 Load, TVF, Export, Resource, Repository, Storage Vault и другие функции Doris поддерживают подход AWS Assume Role в версии **3.0.6 и новее**. Проверка подключения выполняется при выполнении SQL-инструкций для этих функций.

### 3.3 Пример настройки через SQL {#33-sql-configuration-example}

В следующем примере создаётся S3 Repository:

```sql
CREATE REPOSITORY `s3_repo`
WITH S3 ON LOCATION "s3://bucket/path/"
PROPERTIES (
  "s3.role_arn" = "arn:aws:iam::1234567890:role/doris-s3-role",
  "s3.external_id" = "doris-external-id",
  "timeout" = "3600"
);
```

Основные параметры:

| Параметр | Обязательный | Описание |
|------|------|------|
| `s3.role_arn` | Да | ARN роли IAM Role2 в аккаунте AWS IAM Account2 |
| `s3.external_id` | Нет | Значение externalId, заданное в Trust Relationships Policies |
| `timeout` | Нет | Тайм-аут операции в секундах |

Подробные сведения об использовании SQL-инструкций для других функций см. в разделе [Аутентификация и авторизация AWS](../../../admin-manual/auth/integrations/aws-authentication-and-authorization#assumed-role-authentication-and-authorization).
