Apache Doris предоставляет встроенный механизм аутентификации пользователей. Администраторы создают пользователей, задают пароли и управляют источниками подключений с помощью команд SQL. В этом документе описаны состав идентификатора пользователя Doris, доступные политики паролей, приоритет сопоставления IP-адресов, а также распространённые рабочие сценарии и способы устранения неполадок.

## Основные понятия {#core-concepts}

<!-- Knowledge type: Concept -->

### Пользователь (user_identity) {#user-user_identity}

В Doris значение `user_identity` однозначно определяет пользователя и состоит из двух частей:

- `user_name`: имя пользователя.
- `host`: адрес хоста, с которого подключается клиент. Для нечёткого сопоставления поддерживается `%`.

Если `host` не указан, по умолчанию используется `'%'`: пользователь может подключаться к Doris с любого хоста.

### Свойства пользователя {#user-properties}

Свойства пользователя привязаны непосредственно к `user_name`, а не к `user_identity`. Поэтому `user@'192.%'` и `user@['domain']` имеют один и тот же набор свойств пользователя. Эти свойства принадлежат пользователю, а не отдельным идентификаторам `user@'192.%'` или `user@['domain']`.

К свойствам пользователя относятся, в частности, максимальное число подключений и конфигурация кластера загрузки.

### Встроенные пользователи {#built-in-users}

Встроенные пользователи создаются Doris по умолчанию и изначально обладают определёнными привилегиями. К ним относятся root и admin. Их начальные пароли пусты. После запуска FE пароль можно изменить соответствующей командой. **Пользователей по умолчанию нельзя удалить.**

| Пользователь | Разрешённый источник входа | Роль по умолчанию |
| --- | --- | --- |
| `root@'%'` | Любой узел | operator |
| `admin@'%'` | Любой узел | admin |

### Пароль {#password}

Пароль служит учётными данными для входа пользователя. Администратор задаёт его при создании пользователя; впоследствии пользователь также может изменить его самостоятельно.

## Механизм аутентификации {#authentication-mechanism}

<!-- Knowledge type: Process description -->

Аутентификация в Doris состоит из двух этапов:

1. **Клиент отправляет данные для аутентификации.** Клиент собирает сведения о пользователе (имя пользователя, пароль, базу данных и другие данные) и отправляет их серверу Doris, чтобы подтвердить свою личность и запросить доступ к базе данных.
2. **Сервер проверяет личность.** Получив данные для аутентификации, Doris проверяет их. Если имя пользователя, пароль и IP-адрес клиента верны, а пользователь имеет доступ к выбранной базе данных, аутентификация проходит успешно и Doris сопоставляет пользователя с системным идентификатором пользователя. Иначе аутентификация завершается ошибкой, а клиенту возвращается соответствующее сообщение.

## Политики паролей {#password-policies}

<!-- Knowledge type: Configuration parameters -->
<!-- Applicable scenarios: Enterprise security compliance / Password lifecycle management -->

Doris поддерживает следующие политики паролей, помогающие администраторам управлять сроком действия и безопасностью паролей.

| Политика | Назначение | Значение по умолчанию |
| --- | --- | --- |
| `PASSWORD_HISTORY` | Запрещает повторное использование последних N паролей | 0 (отключена) |
| `PASSWORD_EXPIRE` | Задаёт срок действия пароля | NEVER (срок не ограничен) |
| `FAILED_LOGIN_ATTEMPTS` + `PASSWORD_LOCK_TIME` | Блокирует учётную запись после последовательных неудачных попыток входа | Отключена |
| `validate_password_policy` | Проверяет надёжность пароля | NONE/0 (проверка отключена) |

### PASSWORD_HISTORY {#password_history}

Определяет, может ли текущий пользователь при сбросе пароля повторно использовать прежние пароли. Например, `PASSWORD_HISTORY 10` запрещает выбирать в качестве нового любой из последних 10 паролей. При значении `PASSWORD_HISTORY DEFAULT` используется значение глобальной переменной `password_history`. Значение 0 отключает эту функцию; по умолчанию установлено 0.

Примеры:

- Задать глобальную переменную: `SET GLOBAL password_history = 10`
- Задать для пользователя: `ALTER USER user1@'ip' PASSWORD_HISTORY 10`

### PASSWORD_EXPIRE {#password_expire}

Задаёт срок действия пароля текущего пользователя. Например, `PASSWORD_EXPIRE INTERVAL 10 DAY` означает, что срок действия пароля истечёт через 10 дней. `PASSWORD_EXPIRE NEVER` означает, что срок действия пароля не ограничен. При значении `PASSWORD_EXPIRE DEFAULT` используется значение глобальной переменной `default_password_lifetime` (в днях). По умолчанию установлено NEVER (или 0), то есть срок действия пароля не ограничен.

Примеры:

- Задать глобальную переменную: `SET GLOBAL default_password_lifetime = 1`
- Задать для пользователя: `ALTER USER user1@'ip' PASSWORD_EXPIRE INTERVAL 10 DAY`

### FAILED_LOGIN_ATTEMPTS и PASSWORD_LOCK_TIME {#failed_login_attempts-and-password_lock_time}

Блокирует учётную запись текущего пользователя после n неудачных попыток входа и задаёт длительность блокировки. Например, `FAILED_LOGIN_ATTEMPTS 3 PASSWORD_LOCK_TIME 1 DAY` означает, что после 3 неудачных попыток входа учётная запись блокируется на один день. Администратор может вручную разблокировать учётную запись с помощью инструкции ALTER USER.

Пример:

- Задать для пользователя: `ALTER USER user1@'ip' FAILED_LOGIN_ATTEMPTS 3 PASSWORD_LOCK_TIME 1 DAY`

### Надёжность пароля {#password-strength}

Этой функцией управляет глобальная переменная `validate_password_policy`. Значение по умолчанию — NONE/0: надёжность пароля не проверяется. При значении STRONG/2 пароль должен содержать символы как минимум 3 из следующих 4 категорий: прописные буквы, строчные буквы, цифры и специальные символы. Длина пароля должна составлять не менее 8 символов.

Пример:

- `SET validate_password_policy = STRONG`

### Просмотр политик паролей {#viewing-password-policies}

После настройки указанных политик их можно просмотреть следующей командой:

```sql
SHOW PROC "/auth/'<user>'@'<host>'";
```

Обратите внимание: части с пользователем и хостом нужно по отдельности заключить в одинарные кавычки. Например:

```sql
SHOW PROC "/auth/'root'@'%'";
SHOW PROC "/auth/'user1'@'127.0.0.1'";
```

## Два пароля {#dual-passwords}

<!-- Knowledge type: Operational procedure + Rules -->
<!-- Applicable scenarios: Application credential rotation -->

**Поддерживается начиная с версии 4.2.1.** При встроенной аутентификации по паролю одна учётная запись может одновременно иметь основной пароль и сохранённый дополнительный пароль. В течение периода их совместного действия можно переводить клиентов на новый пароль, не отклоняя подключения клиентов, которые ещё используют прежний. По умолчанию дополнительного пароля нет; он создаётся только с помощью `RETAIN CURRENT PASSWORD`. Эти изменения влияют на последующие попытки аутентификации и не разрывают существующие сеансы.

### Предварительные условия {#prerequisites}

- Прежде чем использовать эти конструкции, обновите все FE до версии 4.2.1 или более поздней.
- Смену пароля должен выполнять администратор с глобальной привилегией `GRANT_PRIV` или `ADMIN_PRIV`. Для RETAIN эта привилегия нужна даже при работе со своей учётной записью; для обычной самостоятельной смены пароля через SET PASSWORD без RETAIN она не требуется.
- Используйте учётную запись со встроенной аутентификацией и непустым основным паролем. LDAP и интеграции аутентификации управляют своими учётными данными самостоятельно.

### Смена пароля {#rotate-a-password}

1. Создайте учётную запись для примера, затем задайте новый пароль, сохранив текущий. Для существующей учётной записи выполните только инструкцию ALTER USER.

    ```sql
    CREATE USER 'app_user'@'%' IDENTIFIED BY 'OldPwd_2026!';
    ALTER USER 'app_user'@'%' IDENTIFIED BY 'NewPwd_2026!' RETAIN CURRENT PASSWORD;
    ```

    Для аутентификации подойдут оба пароля: `OldPwd_2026!` и `NewPwd_2026!`. Равнозначный способ сохранить текущий пароль — выполнить `SET PASSWORD FOR 'app_user'@'%' = PASSWORD('NewPwd_2026!') RETAIN CURRENT PASSWORD` вместо инструкции ALTER, а не после неё.

2. Переведите всех клиентов на `NewPwd_2026!`. Проверьте, сохранён ли дополнительный пароль учётной записи:

    ```sql
    SHOW GRANTS FOR 'app_user'@'%';
    ```

    В столбце `Password` отображается `Yes (dual)`. Такой же маркер показывают `SHOW ALL GRANTS` и `SHOW PROC '/auth'`. Метрика `doris_fe_secondary_password_auth_total` каждого FE подсчитывает успешные аутентификации с дополнительным паролем по всем учётным записям после проверки политик учётных записей. Следите за приростом этого накопительного счётчика, а не ждите, пока его значение вернётся к нулю.

3. Когда все клиенты перейдут на новый пароль, отзовите дополнительный пароль:

    ```sql
    ALTER USER 'app_user'@'%' DISCARD OLD PASSWORD;
    ```

    После этого для аутентификации подойдёт только `NewPwd_2026!`, а в столбце `Password` снова появится `Yes`. Если дополнительного пароля нет, повторное выполнение DISCARD ни на что не повлияет.

### Срок действия паролей и правила политик {#password-lifetime-and-policy-rules}

| Операция | Результат |
| --- | --- |
| Новый непустой пароль с RETAIN | Прежний основной пароль становится единственным дополнительным; любой более ранний дополнительный пароль заменяется. |
| Смена на непустой пароль без RETAIN | Существующий дополнительный пароль остаётся действительным. Одна лишь замена основного пароля не отзывает его. |
| Новый пароль пуст | Оба пароля удаляются, даже если указан RETAIN. |
| RETAIN при пустом текущем основном пароле | Операция отклоняется. |
| DISCARD OLD PASSWORD | Удаляется только дополнительный пароль. История паролей и отсчёт срока действия пароля не меняются. |

На оба пароля распространяются политики блокировки учётной записи и срока действия пароля. Смена пароля с сохранением прежнего остаётся сменой пароля: на неё распространяются правила надёжности и истории паролей, а также обновляется отсчёт срока действия. Привязка, отвязка или изменение интеграции аутентификации удаляет сохранённый дополнительный пароль; использовать RETAIN при таких переходах нельзя. DISCARD выполняется как отдельная операция ALTER USER и не может сочетаться со сменой пароля, изменением политики или комментарием.

### Доменные учётные записи и изменения версий {#domain-accounts-and-version-changes}

Для доменной учётной записи DISCARD сначала удаляет дополнительный пароль из постоянной записи доменной учётной записи. Записи с разрешёнными IP-адресами перестают принимать сохранённую копию после следующего обновления результатов разрешения домена. Обычный интервал обновления составляет 10 секунд, но это не строгая верхняя граница времени отзыва.

Во время последовательного обновления FE со старой версией принимает только основной пароль и не может разобрать новые конструкции. Прежде чем начинать ротацию с двумя паролями, дождитесь обновления всех FE. Если после использования этой функции понизить версию, сохранённый дополнительный пароль будет утрачен: останется только основной пароль, а последующее обновление не восстановит прежний дополнительный пароль.

Полное описание инструкций см. в разделах [ALTER USER](../../../sql-manual/sql-statements/account-management/ALTER-USER) и [SET PASSWORD](../../../sql-manual/sql-statements/account-management/SET-PASSWORD).

## Приоритет сопоставления идентификаторов пользователя {#user-identity-matching-priority}

<!-- Knowledge type: Rule description -->
<!-- Applicable scenarios: Login rejection troubleshooting / Conflicts between multiple user_identity values -->

Значение `user_identity` состоит из `user_name` и `host`, но при входе пользователь указывает только `user_name`. Doris сопоставляет IP-адрес клиента с соответствующим `host`, чтобы определить, какой `user_identity` использовать для входа.

Если IP-адресу клиента соответствует только один `user_identity`, Doris использует его. Если подходят несколько значений `user_identity`, действует следующий приоритет:

| Сравниваемые варианты | Приоритет |
| --- | --- |
| Конкретный IP-адрес и домен | Конкретный IP-адрес имеет приоритет перед доменом |
| Конкретный IP-адрес и диапазон IP-адресов | Более конкретный диапазон IP-адресов имеет приоритет (например, `192.%` перед `%`) |

### Пример 1: IP-адрес имеет приоритет перед доменом {#example-1-ip-takes-priority-over-domain}

```sql
CREATE USER user1@['domain1'] IDENTIFIED BY "12345";
CREATE USER user1@'ip1' IDENTIFIED BY "abcde";
```

Предположим, `domain1` разрешается в два IP-адреса: `ip1` и `ip2`. Поскольку IP-адрес имеет приоритет перед доменом, попытка пользователя `user1` войти в Doris с адреса `ip1` с паролем `'12345'` будет отклонена (правильный пароль — `'abcde'`).

### Пример 2: Более конкретный диапазон IP-адресов имеет приоритет {#example-2-more-specific-ip-range-wins}

```sql
CREATE USER user1@'%' IDENTIFIED BY "12345";
CREATE USER user1@'192.%' IDENTIFIED BY "abcde";
```

Поскольку `'192.%'` имеет приоритет перед `'%'`, попытка пользователя `user1` войти в Doris с адреса `192.168.1.1` с паролем `'12345'` будет отклонена (правильный пароль — `'abcde'`).

## Имитация чёрного списка с помощью белого списка {#simulating-a-blacklist-with-a-whitelist}

<!-- Knowledge type: Operational technique -->
<!-- Applicable scenarios: Block specific IPs from logging in -->

Doris не поддерживает чёрные списки напрямую, но поддерживает белые списки. Чтобы имитировать чёрный список, можно использовать [приоритет сопоставления идентификаторов пользователя](#user-identity-matching-priority).

Например, предположим, что создан пользователь `user@'192.%'`, которому разрешён вход с адресов `192.*`. Чтобы запретить вход с `192.168.10.1`, создайте ещё одного пользователя `cmy@'192.168.10.1'` и задайте новый пароль. Поскольку `192.168.10.1` имеет более высокий приоритет, чем `192.%`, пользователи с адреса `192.168.10.1` больше не смогут войти со старым паролем.

## Часто задаваемые вопросы {#faq}

<!-- Knowledge type: Troubleshooting -->
<!-- Applicable scenarios: Login failures / Identity confusion / Forgotten passwords -->

### В: Как сбросить забытый пароль? {#q-how-do-i-reset-a-forgotten-password}

Если вы забыли пароль и не можете войти в Doris, выполните следующие действия:

1. Добавьте следующий параметр в конфигурационный файл FE:

    ```text
    skip_localhost_auth_check = true
    ```

2. Перезапустите FE.
3. На хосте FE войдите в Doris от имени root без пароля.
4. После входа сбросьте пароль командой `SET PASSWORD`.

### В: Могут ли другие пользователи сбросить пароль пользователя root? {#q-can-other-users-reset-the-root-users-password}

Нет. **Никто, кроме самого root, не может сбросить пароль пользователя root.**

### В: Чем отличаются `current_user()` и `user()`? {#q-what-is-the-difference-between-current_user-and-user}

Выполните `SELECT current_user()` и `SELECT user()`, чтобы просмотреть значения `current_user` и `user` соответственно:

- `current_user`: идентификатор, под которым текущий пользователь прошёл аутентификацию (значение `user_identity`, использованное при создании пользователя).
- `user`: фактический идентификатор текущего пользователя, включая реальный IP-адрес клиента.

Например, предположим, что создан пользователь `user1@'192.%'`, после чего пользователь `user1` входит в систему с адреса `192.168.10.1`. Тогда `current_user` равен `user1@'192.%'`, а `user` — `user1@'192.168.10.1'`.

Все привилегии предоставляются конкретному `current_user`, а фактический пользователь обладает всеми привилегиями соответствующего `current_user`.

### В: Почему вход пользователя отклоняется, хотя пароль точно правильный? {#q-a-users-login-is-rejected-but-the-password-is-confirmed-to-be-correct-why}

Обычно причина в [правилах приоритета сопоставления идентификаторов пользователя](#user-identity-matching-priority): IP-адрес клиента соответствует более конкретному `user_identity`, поэтому для входа нужен пароль, принадлежащий этому `user_identity`.
