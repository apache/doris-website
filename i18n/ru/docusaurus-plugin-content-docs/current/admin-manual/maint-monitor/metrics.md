# Метрики мониторинга {#monitoring-metrics}

<!-- Knowledge type: Configuration parameters / Parameter reference -->
<!-- Applicable scenarios: Cluster health monitoring / Alert configuration / Performance troubleshooting -->

Процессы FE и BE Doris имеют встроенные метрики мониторинга, которые по умолчанию доступны в формате, совместимом с Prometheus. В этом документе систематически перечислены все доступные метрики и указан их приоритет (Priority). После подключения Prometheus + Grafana это поможет быстро настроить мониторинг и оповещения.

## Сценарии применения {#applicable-scenarios}

| Сценарий | Назначение |
| --- | --- |
| Мониторинг состояния кластера | Быстро обнаруживать проблемы узлов FE/BE по метрикам P0 |
| Настройка оповещений | Настраивать оповещения по пороговым значениям QPS, частоты ошибок, Compaction Score и других метрик |
| Диагностика производительности | Находить узкие места по задержке запросов, очередям пулов потоков и использованию памяти |
| Планирование ресурсов | Оценивать нагрузку кластера по использованию дисков, числу таблетов и соединений |
| Разбор инцидентов | Анализировать причины сбоев, сопоставляя метрики узлов (CPU, IO, сеть) и процессов |

## Категории метрик {#metric-categories}

Метрики мониторинга Doris делятся на две категории по объекту наблюдения:

1. **Мониторинг процессов**: показатели работы самих процессов Doris, например число запросов и транзакций, состояние Compaction.
2. **Мониторинг узлов**: показатели ресурсов машин, на которых работают процессы Doris, например CPU, память, IO и сеть.

## Получение метрик мониторинга {#retrieving-monitoring-metrics}

### Формат, совместимый с Prometheus (по умолчанию) {#prometheus-compatible-format-default}

Обратитесь непосредственно к HTTP-порту узла FE или BE:

```shell
curl http://fe_host:http_port/metrics
curl http://be_host:webserver_port/metrics
```

Пример ответа:

```text
doris_fe_cache_added{type="partition"} 0
doris_fe_cache_added{type="sql"} 0
doris_fe_cache_hit{type="partition"} 0
doris_fe_cache_hit{type="sql"} 0
doris_fe_connection_total 2
```

### Формат JSON {#json-format}

Чтобы получить метрики в формате JSON, используйте параметр `type=json`:

```shell
curl http://fe_host:http_port/metrics?type=json
curl http://be_host:webserver_port/metrics?type=json
```

### Метрики bvar {#bvar-metrics}

Процессы BE и Meta Service / Recycler также экспортируют метрики bvar через службы brpc. Для вывода в формате, совместимом с Prometheus, используйте `/brpc_metrics`, а для просмотра диагностических данных по имени — `/vars`:

```shell
curl http://be_host:brpc_port/brpc_metrics
curl http://be_host:brpc_port/vars
curl http://cloud_host:brpc_listen_port/brpc_metrics
```

Эти конечные точки используют порт BE `brpc_port` (по умолчанию `8060`) или порт Meta Service / Recycler `brpc_listen_port` (по умолчанию `5000`). Они отличаются от указанных выше HTTP-портов мониторинга FE / BE. Ниже приведены зарегистрированные имена bvar; префикс `doris_be_` есть не у всех.

#### Определение версии {#version-identification}

Начиная с версии 4.1.5, метрики версии BE и Meta Service / Recycler в `/brpc_metrics` содержат следующие метки:

| Метрика | Тип | Метки | Значение |
| --- | --- | --- | --- |
| `doris_be_version` | Gauge | `version`, `major`, `minor`, `patch`, `hotfix`, `short_hash` | Версия сборки BE и идентификатор коммита |
| `doris_cloud_version` | Gauge | Те же, что выше | Версия сборки Meta Service / Recycler и идентификатор коммита |

Каждый процесс экспортирует один образец метрики версии. Значение метрики сохраняет прежний способ кодирования версии; полную версию читайте в метке `version`, а идентификатор коммита — в `short_hash`. Метрика `doris_cloud_version` не различает, работает ли процесс как Meta Service, Recycler или выполняет обе роли. Чтобы определить роль, добавьте метку цели сбора метрик.

Параметр процесса `bvar_max_dump_multi_dimension_metric_num` ограничивает число многомерных образцов bvar. По умолчанию он равен `5000`; значение `0` отключает такие образцы, в том числе метрики версии. BE поддерживает этот параметр начиная с версии 4.1.5; после изменения требуется перезапуск. См. [Конфигурация BE](../config/be-config.md#bvar_max_dump_multi_dimension_metric_num).

## Приоритет мониторинга и рекомендации {#monitoring-priority-and-best-practices}

<!-- Knowledge type: Best practices -->

- Последний столбец каждой таблицы метрик показывает приоритет (Priority). **P0 — самый высокий приоритет**; чем больше число, тем ниже важность. Сначала подключайте метрики P0.
- Подавляющее большинство метрик мониторинга имеют тип Counter (накопительное значение). **Чтобы получить полезную информацию, необходимо собирать значения через равные интервалы (например, каждые 15 секунд) и рассчитывать изменение за единицу времени**.

    Например, по скорости изменения `doris_fe_query_err` можно определить частоту ошибок запросов (ошибок в секунду).

> Вы можете дополнить эту таблицу, чтобы сделать перечень метрик мониторинга полнее и полезнее.

## Диагностические метрики bvar {#bvar-diagnostic-metrics}

Следующие метрики поддерживаются начиная с версии 4.1.5 и доступны через описанные выше порты brpc. Метрики Counter накапливают значения с момента запуска процесса; Gauge показывают текущие значения.

| Имя или префикс | Процесс | Тип | Значение |
| --- | --- | --- | --- |
| `sync_tablets_meta_num` | BE в режиме разделения вычислений и хранения | Counter | Накопительное число фоновых попыток синхронизации метаданных таблетов; учитывается до вызова и не равно числу успешных вызовов |
| `sync_tablets_rowsets_num` | BE в режиме разделения вычислений и хранения | Counter | Накопительное число фоновых попыток синхронизации rowset таблетов; учитывается до вызова и не равно числу успешных вызовов |
| `vertical_compaction_active_segment_contexts` | BE | Gauge | Текущее число активных контекстов Segment, удерживаемых вертикальной Compaction |
| `hdfs_get_path_info` | BE | Статистика задержки, мкс | Префикс метрик задержки `hdfsGetPathInfo` для диагностики доступа к метаданным файлов HDFS |

Префиксы путей кеша и метрики вытеснения описаны в разделе [Мониторинг файлового кеша](../../compute-storage-decoupled/file-cache/file-cache.md#cache-space-and-hit-rate-metrics). ## Часто задаваемые вопросы {#faq}

<!-- Knowledge type: Troubleshooting -->
<!-- Applicable scenarios: Monitoring metric integration and interpretation -->

### В: Конечная точка мониторинга возвращает 404. Что делать? {#q-the-monitoring-endpoint-returns-404-what-should-i-do}

Убедитесь, что обращаетесь к `http_port` узла FE или `webserver_port` узла BE, и проверьте фактические значения портов в `fe.conf` / `be.conf`.

### В: Метрики Counter только растут и никогда не уменьшаются. Это нормально? {#q-counter-metrics-only-increase-and-never-decrease-is-this-normal}

Да. Counter представляет накопительное значение. Чтобы получить текущую скорость изменения, собирайте данные через интервалы и рассчитывайте скорость изменения (например, с помощью `rate()` в PromQL).

### В: Значения `doris_fe_max_journal_id` на разных узлах FE сильно различаются. Что делать? {#q-the-gap-of-doris_fe_max_journal_id-between-multiple-fes-is-too-large-what-should-i-do}

Это указывает на задержку синхронизации метаданных. Проверьте сетевое соединение и скорость воспроизведения журналов на Follower / Observer FE относительно Master FE.

### В: Compaction Score остаётся слишком высоким. Как найти причину? {#q-compaction-score-remains-too-high-how-do-i-troubleshoot}

Проверьте `doris_be_tablet_base_max_compaction_score` и `doris_be_tablet_cumulative_max_compaction_score`, сопоставьте их с дисковым IO и числом задач Compaction, чтобы найти узкое место.

### В: Запросы или задачи загрузки накапливаются. Как найти причину? {#q-queries-or-loads-are-accumulating-how-do-i-troubleshoot}

Проверьте метрики очередей пулов потоков, например `fragment_thread_pool_queue_size`, `doris_be_scanner_thread_pool_queue_size` и `doris_be_send_batch_thread_pool_queue_size`.
