# Управление репликами данных {#data-replica-management}

Этот документ предназначен для администраторов кластера. В нём описаны механизмы балансировки и восстановления реплик Apache Doris, приоритеты планирования, способы просмотра состояния реплик и основные приёмы работы при сбоях реплик или неравномерной нагрузке на кластер.

Начиная с версии 0.9.0, в Doris появилась оптимизированная стратегия управления репликами и расширенные средства просмотра их состояния. Этот документ поможет понять принципы планирования задач для реплик и быстро восстановить кластер при повреждении реплик, простое узлов или неравномерном использовании дисков.

> О восстановлении и балансировке реплик таблиц с атрибутом Colocation см. [Colocate Join](../../query-data/join#colocate-join).

## Терминология {#terminology}

| Термин | Значение |
| --- | --- |
| Tablet | Логический шард таблицы Doris. Таблица состоит из нескольких шардов. |
| Реплика | Копия шарда. По умолчанию у шарда 3 реплики. |
| Исправная реплика | Реплика, у которой Backend работает, а набор версий полон. |
| TabletChecker (TC) | Постоянно работающий фоновый поток, который периодически сканирует все Tablet, проверяет их состояние и по результату решает, нужно ли передать Tablet в TabletScheduler. |
| TabletScheduler (TS) | Постоянно работающий фоновый поток, который обрабатывает Tablet, переданные TabletChecker для восстановления, а также выполняет балансировку реплик кластера. |
| TabletSchedCtx (TSC) | Объект, инкапсулирующий Tablet. Выбрав Tablet, TC оборачивает его в TSC и передаёт в TS. |
| Носитель данных | Носитель для хранения данных. Doris позволяет задавать разные типы носителей (SSD и HDD) на уровне партиций. Планирование задач для реплик выполняется отдельно для каждого типа носителя. |

Общий процесс выглядит следующим образом:

```text

              +--------+              +-----------+
              |  Meta  |              |  Backends |
              +---^----+              +------^----+
                  | |                        | 3. Send clone tasks
 1. Check tablets | |                        |
           +--------v------+        +-----------------+
           | TabletChecker +--------> TabletScheduler |
           +---------------+        +-----------------+
                   2. Waiting to be scheduled


```

На схеме выше показан упрощённый процесс: TabletChecker проверяет состояние Tablet и передаёт нуждающиеся в восстановлении Tablet в TabletScheduler, который отправляет задачи клонирования на BE.

## Состояние реплик {#replica-status}

По разным причинам состояние реплик одного Tablet может различаться. Doris пытается автоматически восстановить такие реплики, чтобы как можно быстрее вернуть кластер в рабочее состояние.

### Состояние исправности реплики {#replica-health-status}

| Состояние | Значение |
| --- | --- |
| BAD | Реплика повреждена. Сюда относятся, в частности, невосстановимые повреждения из-за отказов диска, ошибок программного обеспечения и других причин. |
| VERSION\_MISSING | Отсутствуют версии. Каждой партии загружаемых в Doris данных соответствует версия данных, а данные реплики состоят из нескольких последовательных версий. Из-за ошибок загрузки, задержек или других причин набор версий данных некоторых реплик может быть неполным. |
| HEALTHY | Исправная реплика. Данные в норме, а узел BE, на котором находится реплика, работает штатно: heartbeat поступает нормально, и узел не находится в процессе вывода из эксплуатации. |

### Состояние исправности Tablet {#tablet-health-status}

Состояние исправности Tablet определяется состоянием всех его реплик. Возможны следующие состояния:

| Состояние | Значение |
| --- | --- |
| REPLICA\_MISSING | Отсутствуют реплики. Число работающих реплик меньше ожидаемого числа реплик. |
| VERSION\_INCOMPLETE | Число работающих реплик больше или равно ожидаемому числу реплик, но число исправных реплик меньше ожидаемого. |
| REPLICA\_RELOCATING | Число работающих реплик с полным набором версий равно заданному числу реплик, но некоторые узлы BE, на которых находятся эти реплики, недоступны, например выводятся из эксплуатации. |
| REPLICA\_MISSING\_IN\_CLUSTER | В сценариях с несколькими кластерами число исправных реплик больше или равно ожидаемому, но число реплик в соответствующем кластере меньше ожидаемого. |
| REDUNDANT | Избыточные реплики. Все исправные реплики находятся в соответствующем кластере, но их число превышает ожидаемое; либо присутствуют лишние недоступные реплики. |
| FORCE\_REDUNDANT | Особое состояние. Возникает только при условии «число существующих реплик >= число доступных узлов >= ожидаемое число реплик, а число работающих реплик < ожидаемого числа реплик». В этом случае сначала необходимо удалить реплику, чтобы освободить доступный узел для создания новой реплики. |
| COLOCATE\_MISMATCH | Состояние шарда, характерное для таблиц Colocation: распределение реплик шарда не соответствует распределению, заданному Colocation Group. |
| COLOCATE\_REDUNDANT | Состояние шарда, характерное для таблиц Colocation: у шарда таблицы Colocation есть избыточные реплики. |
| HEALTHY | Исправный шард: ни одно из приведённых выше условий с 1 по 8 не выполняется. |

## Восстановление реплик {#replica-repair}

TabletChecker постоянно работает в фоновом режиме и периодически проверяет состояние всех шардов. Неисправные шарды передаются в TabletScheduler для планирования и восстановления. Само восстановление выполняется задачами клонирования на BE; FE отвечает только за создание этих задач.

> Примечание 1: Основной принцип восстановления реплик — сначала довести число реплик до ожидаемого значения, создав новые или дополнив существующие, а затем удалить избыточные реплики.
>
> Примечание 2: Задача клонирования — это процесс копирования указанных данных с заданного удалённого BE на заданный целевой BE.

### Восстановление в зависимости от состояния {#repair-by-status}

Для разных состояний Doris использует разные способы восстановления:

1. REPLICA\_MISSING / REPLICA\_RELOCATING

    В качестве целевого выбирается доступный узел BE с низкой нагрузкой, а в качестве источника — исправная реплика. Задача клонирования копирует полную реплику с источника на целевой узел. При добавлении недостающих реплик доступный узел BE выбирается напрямую, без учёта типа носителя.

2. VERSION\_INCOMPLETE

    В качестве целевой выбирается реплика с относительно полным набором версий, а в качестве источника — исправная реплика. Задача клонирования пытается скопировать недостающие версии с источника в реплику на целевом узле.

3. REPLICA\_MISSING\_IN\_CLUSTER

    Обрабатывается так же, как REPLICA\_MISSING.

4. REDUNDANT

    После восстановления у шарда обычно остаются избыточные реплики. Для удаления выбирается одна из них. Выбор выполняется в следующем порядке приоритета:

    1. BE, на котором находится реплика, выведен из эксплуатации
    2. Реплика повреждена
    3. BE, на котором находится реплика, недоступен или выводится из эксплуатации
    4. Реплика находится в состоянии CLONE — промежуточном состоянии при выполнении задачи клонирования
    5. У реплики отсутствуют версии
    6. Реплика находится не в том кластере
    7. BE, на котором находится реплика, сильно нагружен

5. FORCE\_REDUNDANT

    В отличие от REDUNDANT, в этом случае число работающих реплик меньше ожидаемого, но дополнительных доступных узлов для создания новой реплики нет. Поэтому сначала необходимо удалить реплику, чтобы освободить доступный узел для создания новой реплики. Порядок удаления реплик такой же, как для REDUNDANT.

6. COLOCATE\_MISMATCH

    В качестве целевого узла для добавления недостающей реплики выбирается один из узлов BE, указанных в распределении реплик Colocation Group.

7. COLOCATE\_REDUNDANT

    Удаляется реплика на узле BE, который не указан в распределении реплик Colocation Group.

При выборе узлов для реплик Doris не размещает реплики одного Tablet на разных BE одного хоста. Благодаря этому даже отказ всех BE на одном хосте не приводит к потере всех реплик.

### Приоритет планирования {#scheduling-priority}

Шардам, ожидающим планирования в TabletScheduler, назначаются разные приоритеты в зависимости от их состояния. Шарды с более высоким приоритетом планируются первыми. Сейчас предусмотрены следующие приоритеты:

| Приоритет | Условие назначения |
| --- | --- |
| VERY\_HIGH | REDUNDANT: шарды с избыточными репликами. Хотя срочность минимальна, обработка выполняется быстрее всего и позволяет быстро освободить дисковое пространство и другие ресурсы, поэтому она выполняется первой.<br/>FORCE\_REDUNDANT: аналогично предыдущему случаю. |
| HIGH | REPLICA\_MISSING, когда отсутствует большинство реплик, например потеряны 2 из 3 реплик.<br/>VERSION\_INCOMPLETE, когда у большинства реплик отсутствуют версии.<br/>COLOCATE\_MISMATCH: шарды таблиц Colocation необходимо восстанавливать как можно скорее.<br/>COLOCATE\_REDUNDANT. |
| NORMAL | REPLICA\_MISSING, когда большинство реплик работает, например потеряна 1 из 3 реплик.<br/>VERSION\_INCOMPLETE, когда у большинства реплик полный набор версий.<br/>REPLICA\_RELOCATING, когда большинство реплик нужно переместить, например 2 из 3 реплик. |
| LOW | REPLICA\_MISSING\_IN\_CLUSTER.<br/>REPLICA\_RELOCATING, когда большинство реплик находится в стабильном состоянии. |

### Назначение приоритета вручную {#manual-priority}

Система определяет приоритет планирования автоматически. Однако если нужно быстрее восстановить определённые таблицы или партиции, следующая команда позволяет назначить таблице или партиции приоритетное восстановление:

```sql
ADMIN REPAIR TABLE tbl [PARTITION (p1, p2, ...)];
```

Эта команда указывает TabletChecker, что при сканировании Tablet проблемным Tablet в таблицах или партициях, помеченных для приоритетного восстановления, следует назначать приоритет `VERY_HIGH`.

> Примечание: Эта команда служит лишь подсказкой и не гарантирует успешного восстановления. Приоритет может меняться в процессе планирования TabletScheduler. После смены или перезапуска Master FE эта информация теряется.

Чтобы отменить приоритет, используйте следующую команду:

```sql
ADMIN CANCEL REPAIR TABLE tbl [PARTITION (p1, p2, ...)];
```

### Динамическое изменение приоритета {#dynamic-priority-adjustment}

Приоритет обеспечивает первоочередное восстановление сильно повреждённых шардов и повышает доступность системы. Однако если задачи восстановления с высоким приоритетом постоянно завершаются неудачей, задачи с низким приоритетом могут так и не попасть в планирование. Поэтому Doris динамически меняет приоритеты задач в зависимости от хода их выполнения, чтобы каждая задача получила возможность быть запланированной:

- После 5 последовательных неудачных попыток планирования, например из-за невозможности получить ресурсы или найти подходящий источник либо целевой узел, приоритет понижается.
- Если задача не была запланирована в течение 30 минут, её приоритет повышается.
- Приоритет задачи для одного и того же Tablet меняется не чаще одного раза в 5 минут.

Чтобы сохранить значимость исходного приоритета, действуют следующие правила: исходный приоритет `VERY_HIGH` понижается не ниже `NORMAL`; исходный приоритет `LOW` повышается не выше `HIGH`. Такое динамическое изменение применяется и к приоритетам, заданным пользователями вручную.

## Балансировка реплик {#replica-balancing}

Doris автоматически выполняет балансировку реплик в кластере. Сейчас поддерживаются две стратегии: **балансировка нагрузки** и **балансировка партиций**.

| Стратегия | Основная цель | Сценарии применения | Примечания |
| --- | --- | --- | --- |
| Балансировка нагрузки | Выровнять использование дисков и число реплик на узлах | Нужно учитывать как дисковую ёмкость, так и равномерность распределения реплик | Оценка рассчитывается по двум показателям |
| Балансировка партиций | Равномерно распределить реплики каждой партиции между узлами | Высокие требования к чтению и записи партиций, необходимость избегать горячих точек | Использование дисков не учитывается; нужно следить за их ёмкостью |

Стратегию можно настроить только через [tablet_rebalancer_type](../config/fe-config) до запуска FE; переключение во время работы не поддерживается.

Независимо от стратегии балансировка реплик всегда гарантирует, что реплики одного Tablet не размещаются на BE одного хоста.

### Балансировка нагрузки {#load-balancing}

Основной принцип балансировки нагрузки: для выбранных шардов сначала создать реплику на слабо нагруженном узле, а затем удалить реплики этих шардов на сильно нагруженных узлах. При этом из-за наличия разных типов носителей узлы BE в одном кластере могут использовать один или два типа носителей. Шард с типом носителя A после балансировки должен по возможности оставаться на носителе типа A. Поэтому узлы BE кластера группируются по типу носителя, а планирование балансировки нагрузки выполняется отдельно для каждой такой группы.

#### Нагрузка на узел BE {#be-node-load}

`ClusterLoadStatistics` (CLS) отражает распределение нагрузки между Backend в кластере. TabletScheduler использует эту статистику для запуска балансировки кластера. Сейчас для каждого BE рассчитывается оценка нагрузки loadScore по двум метрикам: **использование дисков** и **число реплик**. Чем выше оценка, тем сильнее нагружен BE.

У использования дисков и числа реплик есть весовые коэффициенты **capacityCoefficient** и **replicaNumCoefficient**, **сумма которых всегда равна 1**.

- Если параметр `backend_load_capacity_coeficient` имеет допустимое значение в диапазоне `0.0`~`1.0`, то `capacityCoefficient = backend_load_capacity_coeficient`.
- В противном случае `capacityCoefficient` динамически меняется в зависимости от фактического использования дисков:
    - Если общая заполненность дисков BE ниже 50%, `capacityCoefficient` равен 0.5.
    - Если заполненность превышает 75% (порог настраивается параметром FE `capacity_used_percent_high_water`), значение равно 1.
    - При заполненности от 50% до 75% весовой коэффициент плавно растёт по формуле:

```text
capacityCoefficient = 2 * disk usage - 0.5
```

Благодаря этому весовому коэффициенту при слишком высокой заполненности дисков оценка нагрузки Backend становится выше, чтобы как можно быстрее снизить нагрузку на BE.

TabletScheduler обновляет CLS каждые 20 секунд.

### Балансировка партиций {#partition-balancing}

Основной принцип балансировки партиций — свести к минимуму разницу в числе реплик каждой партиции на разных Backend, то есть перекос партиции. Поэтому учитывается только число реплик, а использование дисков не учитывается.

Чтобы минимизировать число перемещений, балансировка партиций использует двумерную жадную стратегию и сначала балансирует партицию с наибольшим перекосом. При балансировке партиции она старается выбрать направление, которое уменьшит разницу в числе реплик между Backend по всему кластеру, то есть перекос кластера / общий перекос.

#### Статистика перекоса {#skew-statistics}

Статистика перекоса представлена в `ClusterBalanceInfo`:

- `partitionInfoBySkew`: отсортировано по ключу перекоса партиции, что позволяет легко найти максимальный перекос партиции.
- `beByTotalReplicaCount`: отсортировано по ключу общего числа реплик на каждом Backend.

`ClusterBalanceInfo` также хранится в CLS и обновляется каждые 20 секунд. Партиций с максимальным перекосом может быть несколько; для расчёта случайным образом выбирается одна из них.

### Планирование балансировки {#balancing-strategy-scheduling}

В каждом цикле планирования TabletScheduler с помощью LoadBalancer выбирает определённое число исправных шардов в качестве кандидатов для балансировки. В следующем цикле он пытается запланировать балансировку этих шардов.

| Ресурс | Описание |
| --- | --- |
| Единица управления ресурсами | Минимальная единица — диск, то есть путь к данным, указанный в `be.conf`. |
| Слот восстановления реплик | По умолчанию на каждом диске есть 2 слота. Задача клонирования занимает по одному слоту на источнике и на целевом узле. Если число свободных слотов равно 0, новые задачи не назначаются. Число слотов можно настроить параметрами FE `schedule_slot_num_per_hdd_path` или `schedule_slot_num_per_ssd_path`. |
| Слот задач балансировки | По умолчанию каждый диск предоставляет 2 независимых слота для задач балансировки. Это позволяет сильно нагруженным узлам освобождать место за счёт балансировки, даже если слоты восстановления заняты. |

## Просмотр состояния реплик {#viewing-replica-status}

Просмотр состояния реплик позволяет оценить состояние самих реплик, а также ход выполнения задач восстановления и балансировки. Большая часть этой информации **доступна только на** узле Master FE, поэтому следующие команды необходимо выполнять при прямом подключении к Master FE.

### Задачи планирования реплик {#replica-scheduling-tasks}

Следующие команды позволяют отдельно просмотреть **ожидающие**, **выполняющиеся** и **завершённые** задачи планирования:

| Состояние | Команда |
| --- | --- |
| Ожидает | `SHOW PROC '/cluster_balance/pending_tablets';` |
| Выполняется | `SHOW PROC '/cluster_balance/running_tablets';` |
| Завершена | `SHOW PROC '/cluster_balance/history_tablets';` |

Пример вывода (`pending_tablets`):


Значения столбцов:

| Столбец | Значение |
| --- | --- |
| TabletId | ID Tablet, ожидающего планирования. Одна задача планирования относится только к одному Tablet. |
| Type | Тип задачи: REPAIR или BALANCE. |
| Status | Текущее состояние Tablet, например REPLICA\_MISSING. |
| State | Состояние задачи планирования: PENDING / RUNNING / FINISHED / CANCELLED / TIMEOUT / UNEXPECTED. |
| OrigPrio | Исходный приоритет. |
| DynmPrio | Текущий приоритет после динамического изменения. |
| SrcBe | ID исходного узла BE. |
| SrcPath | Хеш пути на исходном узле BE. |
| DestBe | ID целевого узла BE. |
| DestPath | Хеш пути на целевом узле BE. |

Значения столбцов в `running_tablets` такие же, как в `pending_tablets`.

- Значение `State`, равное `FINISHED`, означает, что задача завершилась штатно.
- Другие значения можно диагностировать по сообщению об ошибке в столбце `ErrMsg`.

## Известные проблемы {#related-issues}

- В некоторых случаях стратегия восстановления и балансировки реплик по умолчанию может полностью загрузить сеть. Это часто происходит при использовании гигабитных сетевых карт и большого числа дисков на каждом BE. В таком случае нужно изменить некоторые параметры, чтобы сократить число одновременно выполняемых задач балансировки и восстановления.
- Текущая стратегия балансировки реплик таблиц Colocate не гарантирует, что реплики одного Tablet не окажутся на BE одного хоста. Однако стратегия восстановления реплик таблиц Colocate обнаруживает и исправляет такое распределение. После исправления стратегия балансировки может снова посчитать распределение реплик несбалансированным и перераспределить их. В результате эти два состояния постоянно сменяют друг друга, и Colocate Group не может стабилизироваться. Чтобы снизить вероятность размещения реплик на одном хосте, при использовании атрибута Colocate старайтесь поддерживать однородную конфигурацию кластера.

### Контроль и управление ходом восстановления и балансировки реплик кластера {#controlling-and-managing-cluster-replica-repair-and-balancing-progress}

В большинстве случаев с настройками по умолчанию Doris автоматически выполняет восстановление реплик и балансировку кластера. Однако иногда для достижения конкретных целей параметры нужно изменить вручную. Например, чтобы приоритетно восстановить определённую таблицу или партицию, отключить балансировку для снижения нагрузки на кластер или сначала восстановить данные обычных таблиц без Colocation. В этом разделе описано, как управлять ходом восстановления и балансировки реплик кластера с помощью параметров.

#### 1. Удаление повреждённых реплик {#1-delete-corrupted-replicas}

В некоторых случаях Doris не может автоматически обнаружить повреждённые реплики, из-за чего запросы или загрузки часто завершаются ошибками на этих репликах. Тогда повреждённые реплики нужно удалить вручную. Этот способ подходит, например, для удаления реплик со слишком большим числом версий, вызывающих ошибки -235, или реплик с повреждёнными файлами.

Порядок действий:

1. Найдите ID Tablet, которому принадлежит реплика. Предположим, это 10001.
2. Выполните `show tablet 10001;`, а затем возвращённую команду `show proc`, чтобы просмотреть подробную информацию о каждой реплике Tablet.
3. Предположим, ID Backend, на котором находится удаляемая реплика, — 20001. Выполните следующую команду, чтобы пометить реплику как `bad`:

    ```sql
    ADMIN SET REPLICA STATUS PROPERTIES("tablet_id" = "10001", "backend_id" = "20001", "status" = "bad");
    ```

4. Снова выполните команду `show proc` и убедитесь, что столбец `IsBad` соответствующей реплики имеет значение `true`.

Реплика, помеченная как `bad`, больше не участвует в загрузках и запросах. При этом механизм восстановления реплик автоматически создаёт новую реплику взамен неё.

#### 2. Приоритетное восстановление таблицы или партиции {#2-prioritize-repairing-a-table-or-partition}

Выполните `help admin repair table;`, чтобы просмотреть справку. Эта команда пытается приоритетно восстановить Tablet указанной таблицы или партиции.

#### 3. Остановка задач балансировки {#3-stop-balancing-tasks}

Задачи балансировки потребляют часть пропускной способности сети и ресурсов IO. Чтобы прекратить создание новых задач балансировки, выполните:

```sql
ADMIN SET FRONTEND CONFIG ("disable_balance" = "true");
```

#### 4. Остановка всех задач планирования реплик {#4-stop-all-replica-scheduling-tasks}

Задачи планирования реплик включают задачи балансировки и восстановления. Они потребляют часть пропускной способности сети и ресурсов IO. Следующая команда останавливает все задачи планирования реплик, кроме уже выполняющихся, как для таблиц Colocation, так и для обычных таблиц:

```sql
ADMIN SET FRONTEND CONFIG ("disable_tablet_scheduler" = "true");
```

#### 5. Остановка всех задач планирования реплик для таблиц Colocation {#5-stop-all-replica-scheduling-tasks-for-colocation-tables}

Планирование задач для реплик таблиц Colocation и обычных таблиц выполняется независимо. В некоторых случаях имеет смысл сначала остановить балансировку и восстановление таблиц Colocation, чтобы направить ресурсы кластера на восстановление обычных таблиц:

```sql
ADMIN SET FRONTEND CONFIG ("disable_colocate_balance" = "true");
```

#### 6. Более консервативная стратегия восстановления реплик {#6-use-a-more-conservative-strategy-to-repair-replicas}

Doris автоматически восстанавливает реплики при обнаружении недостающих реплик, простоя BE и других подобных ситуаций. Чтобы уменьшить число ошибок, вызванных кратковременными сбоями, например непродолжительным простоем BE, Doris запускает эти задачи с задержкой.

- Параметр `tablet_repair_delay_factor_second`: по умолчанию равен 60 секундам. В зависимости от приоритета задача восстановления запускается с задержкой 60 секунд, 120 секунд или 180 секунд. Следующая команда увеличивает это время, чтобы допускать более длительные сбои и не запускать ненужные задачи восстановления:

    ```sql
    ADMIN SET FRONTEND CONFIG ("tablet_repair_delay_factor_second" = "120");
    ```

#### 7. Более консервативная стратегия запуска перераспределения Colocation Group {#7-use-a-more-conservative-strategy-to-trigger-colocation-group-redistribution}

Перераспределение групп Colocation может сопровождаться большим числом перемещений Tablet. Параметр `colocate_group_relocate_delay_second` задаёт задержку запуска перераспределения; по умолчанию она составляет 1800 секунд. Если узел BE может быть недоступен долгое время, попробуйте увеличить этот параметр, чтобы избежать ненужного перераспределения:

```sql
ADMIN SET FRONTEND CONFIG ("colocate_group_relocate_delay_second" = "3600");
```

#### 8. Ускорение балансировки реплик {#8-faster-replica-balancing}

При балансировке Doris сначала добавляет исправную реплику, а затем удаляет старую, тем самым перемещая реплику. Перед удалением старой реплики Doris ждёт завершения уже запущенных на ней задач загрузки, чтобы балансировка не повлияла на них. Однако это замедляет балансировку. Следующий параметр позволяет Doris пропустить ожидание и сразу удалить старую реплику:

```sql
ADMIN SET FRONTEND CONFIG ("enable_force_drop_redundant_replica" = "true");
```

Это может привести к ошибкам некоторых задач загрузки во время балансировки и потребовать их повторного выполнения, но значительно ускоряет балансировку.

### Рекомендуемый порядок быстрого восстановления кластера {#recommended-procedure-for-fast-cluster-recovery}

Чтобы быстро вернуть кластер в нормальное состояние, рассмотрите следующий порядок действий:

1. Найдите Tablet, из-за которого задачи с высоким приоритетом сообщают об ошибках, и пометьте проблемную реплику как `bad`.
2. Используйте команду `ADMIN REPAIR`, чтобы назначить приоритетное восстановление определённых таблиц.
3. Остановите балансировку реплик, чтобы она не расходовала ресурсы кластера, и снова включите её после восстановления кластера.
4. Используйте более консервативную стратегию запуска задач восстановления, чтобы справиться с лавинообразным ростом числа задач из-за частых простоев BE.
5. При необходимости отключите задачи планирования для таблиц Colocation, чтобы сосредоточить ресурсы кластера на восстановлении других данных с высоким приоритетом.

## Часто задаваемые вопросы {#faq}

### Вопрос: Команда `SHOW PROC '/cluster_health/tablet_health'` возвращает ошибку или неполные данные. Что делать? {#q-the-show-proc-cluster_healthtablet_health-command-reports-an-error-or-shows-incomplete-data-what-should-i-do}

Для этой команды необходимо прямое подключение к Master FE. Проверьте, является ли FE, к которому вы сейчас подключены, узлом Master.

### Вопрос: Реплика долго находится в состоянии `REPLICA_MISSING` и не восстанавливается. Как найти причину? {#q-a-replica-has-been-in-replica_missing-for-a-long-time-without-being-repaired-how-do-i-troubleshoot}

Проверьте `ErrMsg` в выводе `SHOW PROC '/cluster_balance/pending_tablets'`. Частые причины: не удаётся найти подходящий источник или целевой узел, недостаточно места на диске, узел выводится из эксплуатации.

### Вопрос: Слишком много неудачных попыток планирования задач восстановления. Что делать? {#q-there-are-too-many-scheduling-failures-for-repair-tasks-what-should-i-do}

Используйте `SHOW PROC '/cluster_balance/sched_stat'` для просмотра статистики сбоев. Попробуйте увеличить `schedule_slot_num_per_hdd_path` или `schedule_slot_num_per_ssd_path` либо проверьте, нет ли таких проблем, как нехватка места на диске или недоступность узлов.

### Вопрос: Балансировка реплик полностью загружает сеть. Что делать? {#q-replica-balancing-is-saturating-the-network-what-should-i-do}

Уменьшите число одновременно выполняемых задач балансировки и восстановления или временно выполните `ADMIN SET FRONTEND CONFIG ("disable_balance" = "true");`.

### Вопрос: Colocate Group долго не может стабилизироваться. Что делать? {#q-a-colocate-group-cannot-stabilize-for-a-long-time-what-should-i-do}

Старайтесь поддерживать однородную конфигурацию кластера и увеличьте `colocate_group_relocate_delay_second`, чтобы сократить число ненужных перераспределений.

### Вопрос: После отказа BE сразу начинается восстановление большого числа реплик, вызывая колебания нагрузки. Что делать? {#q-after-a-be-goes-down-a-large-number-of-replicas-are-repaired-immediately-causing-load-jitter-what-should-i-do}

Увеличьте `tablet_repair_delay_factor_second`, чтобы система дольше допускала временную недоступность узла.

### Вопрос: После удаления реплики `bad` ошибки продолжаются. Что делать? {#q-after-deleting-a-bad-replica-errors-still-occur-what-should-i-do}

С помощью `SHOW PROC '/dbs/.../<tablet_id>'` убедитесь, что все недостающие реплики восстановлены, и дождитесь завершения задачи клонирования.
