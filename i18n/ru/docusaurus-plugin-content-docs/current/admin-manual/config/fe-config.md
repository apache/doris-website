# Конфигурация FE {#fe-configuration}

В этом документе описаны параметры конфигурации FE.

Файл конфигурации FE `fe.conf` обычно находится в каталоге `conf/` в директории развёртывания FE. В версии 0.14 появится дополнительный файл конфигурации `fe_custom.conf`. Он предназначен для хранения параметров, которые пользователь динамически изменяет и сохраняет во время работы.

После запуска процесс FE сначала считывает параметры из `fe.conf`, а затем — из `fe_custom.conf`. Параметры из `fe_custom.conf` переопределяют одноимённые параметры из `fe.conf`.

Расположение файла `fe_custom.conf` можно задать в `fe.conf` с помощью параметра `custom_config_dir`.

## Просмотр параметров конфигурации {#view-configuration-items}

Просмотреть параметры конфигурации FE можно двумя способами:

1. Веб-страница FE

    Откройте в браузере веб-страницу FE `http://fe_host:fe_http_port/variable`. Текущие действующие параметры конфигурации FE отображаются в разделе `Configure Info`.

2. Просмотр с помощью команды

    После запуска FE параметры его конфигурации можно просмотреть в клиенте MySQL с помощью следующей команды. Подробное описание синтаксиса приведено в разделе [SHOW-CONFIG](../../sql-manual/sql-statements/cluster-management/instance-management/SHOW-FRONTEND-CONFIG):

    `SHOW FRONTEND CONFIG;`

    Столбцы результата имеют следующие значения:

    * Key: имя параметра конфигурации.
    * Value: текущее значение параметра конфигурации.
    * Type: тип значения параметра, например целое число или строка.
    * IsMutable: возможность динамического изменения. Если значение равно true, параметр можно динамически изменять во время работы. Если false, параметр можно задать только в `fe.conf`, и он вступит в силу после перезапуска FE.
    * MasterOnly: применяется ли параметр только к узлу Master FE. Если значение равно true, параметр имеет смысл только для Master FE и не влияет на другие типы узлов FE. Если false, параметр применяется ко всем типам узлов FE.
    * Comment: описание параметра конфигурации.

## Настройка параметров конфигурации {#set-configuration-items}

Начиная с версии 4.1.5, `SHOW FRONTEND CONFIG` и конечные точки экспорта конфигурации маскируют непустые конфиденциальные значения строкой `********`. Это касается, в частности, `initial_root_password`, паролей закрытых ключей TLS, паролей HTTPS Key Store и паролей сертификатов MySQL SSL. Пустые значения остаются пустыми, показывая, что параметр не задан. Маскирование не изменяет действующую конфигурацию.

Параметры конфигурации FE можно настроить следующими способами:

1. Статическая настройка

    Добавьте параметры и задайте их значения в файле `conf/fe.conf`. Параметры из `fe.conf` считываются при запуске процесса FE. Для параметров, отсутствующих в `fe.conf`, используются значения по умолчанию.

2. Динамическая настройка по протоколу MySQL

    После запуска FE параметры можно динамически изменять с помощью следующей команды. Для её выполнения требуются права администратора.

    `ADMIN SET FRONTEND CONFIG (" fe_config_name "=" fe_config_value ");`

    Не все параметры поддерживают динамическое изменение. Проверить его поддержку можно по столбцу `IsMutable` в результате команды ` SHOW FRONTEND CONFIG; `.

    При изменении параметра с признаком `MasterOnly` команда направляется непосредственно на Master FE, и соответствующий параметр изменяется только на Master FE.

    **Изменения, внесённые таким способом, сбрасываются после перезапуска процесса FE.**

    Дополнительную справку об этой команде можно получить с помощью команды `HELP ADMIN SET CONFIG;`.

3. Динамическая настройка по протоколу HTTP

    Подробности приведены в разделе [Действие Set Config](../open-api/fe-http/set-config-action).

    Этот способ также позволяет сохранять изменённые параметры. Они записываются в файл `fe_custom.conf` и продолжают действовать после перезапуска FE.

## Примеры {#examples}

1. Изменение `async_pending_load_task_pool_size`

    С помощью `SHOW FRONTEND CONFIG;` можно убедиться, что этот параметр нельзя изменять динамически (`IsMutable` имеет значение false). Добавьте в `fe.conf`:

    `async_pending_load_task_pool_size = 20`

    Затем перезапустите процесс FE, чтобы настройка вступила в силу.

2. Изменение `dynamic_partition_enable`

    С помощью `SHOW FRONTEND CONFIG;` можно убедиться, что этот параметр допускает динамическое изменение (`IsMutable` имеет значение true). Кроме того, он применяется только к Master FE. Подключитесь к любому FE и выполните следующую команду для изменения конфигурации:

    ```
    ADMIN SET FRONTEND CONFIG ("dynamic_partition_enable" = "true"); `
    ```

    Затем изменённое значение можно просмотреть с помощью следующих команд:

    ```
    set forward_to_master = true;
    SHOW FRONTEND CONFIG;
    ```

    При таком способе изменения настройка сбросится после перезапуска Master FE или выборов нового Master. Чтобы сделать настройку постоянной, добавьте параметр непосредственно в `fe.conf` и перезапустите FE.

3. Изменение `max_distribution_pruner_recursion_depth`

    С помощью `SHOW FRONTEND CONFIG;` можно убедиться, что этот параметр допускает динамическое изменение (`IsMutable` имеет значение true). Он применяется не только к Master FE.

    Аналогичным образом конфигурацию можно изменить командой динамической настройки. Поскольку параметр применяется не только к Master FE, необходимо отдельно подключиться к каждому FE и изменить его значение, чтобы все узлы FE использовали новую настройку.

## Параметры конфигурации {#configurations}

### Метаданные и кластер {#metadata-and-cluster}

#### `meta_dir` {#meta_dir}

По умолчанию: DORIS_HOME_DIR + "/doris-meta"

Тип: string. Описание: каталог для хранения метаданных Doris. Для его размещения настоятельно рекомендуется хранилище со следующими характеристиками:

* Высокая производительность записи (SSD)
* Надёжность (RAID)

#### `catalog_try_lock_timeout_ms` {#catalog_try_lock_timeout_ms}

По умолчанию: 5000 (мс)

IsMutable: true

Тайм-аут tryLock для блокировки Catalog. Обычно изменять его не требуется, кроме случаев тестирования.

#### `enable_bdbje_debug_mode` {#enable_bdbje_debug_mode}

По умолчанию: false

Если задано true, FE запускается в режиме отладки BDBJE.

#### `max_bdbje_clock_delta_ms` {#max_bdbje_clock_delta_ms}

По умолчанию: 5000 (5s)

Максимально допустимое расхождение часов между узлом FE, не являющимся Master, и хостом Master FE. Значение проверяется при каждом установлении соединения такого узла с Master FE через BDBJE. Если расхождение превышает это значение, соединение отклоняется.

#### `metadata_failure_recovery` {#metadata_failure_recovery}

По умолчанию: false

Если задано true, FE сбрасывает группу репликации bdbje, то есть удаляет информацию обо всех узлах, участвующих в выборах, и должен запуститься в роли Master. Если ни один из узлов, участвующих в выборах, не запускается, можно скопировать метаданные на другой узел, установить этот параметр в true и попытаться перезапустить FE.

#### `txn_rollback_limit` {#txn_rollback_limit}

По умолчанию: 100

Максимальное количество транзакций, которые bdbje может откатить при попытке повторного присоединения к группе.

#### `grpc_threadmgr_threads_nums` {#grpc_threadmgr_threads_nums}

По умолчанию: 4096

Количество потоков для обработки событий grpc в grpc_threadmgr.

#### `bdbje_replica_ack_timeout_second` {#bdbje_replica_ack_timeout_second}

По умолчанию: 10 (с)

Тайм-аут ожидания подтверждения от реплики при записи в bdbje. При записи относительно больших записей журнала время ожидания подтверждения может истечь, что приводит к ошибке записи. В таком случае можно увеличить это значение.

#### `bdbje_lock_timeout_second` {#bdbje_lock_timeout_second}

По умолчанию: 5

Тайм-аут блокировки для операций bdbje. Если в журнале FE уровня WARN часто встречается LockTimeoutException, попробуйте увеличить это значение.

#### `bdbje_heartbeat_timeout_second` {#bdbje_heartbeat_timeout_second}

По умолчанию: 30

Тайм-аут heartbeat bdbje между Master и Follower. По умолчанию составляет 30 секунд и совпадает со значением по умолчанию в bdbje. При кратковременных сетевых сбоях или неожиданно длительных паузах Java GC можно увеличить это значение, чтобы снизить вероятность ложного срабатывания тайм-аута.

#### `replica_ack_policy` {#replica_ack_policy}

По умолчанию: SIMPLE_MAJORITY

Варианты: ALL, NONE, SIMPLE_MAJORITY

Политика подтверждения реплик bdbje. Подробнее: <http://docs.oracle.com/cd/E17277_02/html/java/com/sleepycat/je/Durability.ReplicaAckPolicy.html>

#### `replica_sync_policy` {#replica_sync_policy}

По умолчанию: SYNC

Варианты: SYNC, NO_SYNC, WRITE_NO_SYNC

Политика синхронизации bdbje для Follower FE.

#### `master_sync_policy` {#master_sync_policy}

По умолчанию: SYNC

Варианты: SYNC, NO_SYNC, WRITE_NO_SYNC

Политика синхронизации bdbje для Master FE. Если развёрнут только один Follower FE, установите значение 'SYNC'. Если развёрнуто более 3 узлов Follower FE, для этого параметра и параметра 'replica_sync_policy' можно задать WRITE_NO_SYNC. Подробнее: <http://docs.oracle.com/cd/E17277_02/html/java/com/sleepycat/je/Durability.SyncPolicy.html>

#### `bdbje_reserved_disk_bytes` {#bdbje_reserved_disk_bytes}

Желаемый верхний предел объёма зарезервированного пространства в байтах, сохраняемого в реплицируемой среде JE Environment.

По умолчанию: 1073741824

Возможность динамической настройки: false

Применяется только к узлу Master FE: false

#### `ignore_meta_check` {#ignore_meta_check}

По умолчанию: false

IsMutable: true

Если задано true, FE, не являющийся Master, игнорирует отставание своих метаданных от Master FE, даже если оно превышает *meta_delay_toleration_second*. Такой FE продолжает обслуживать запросы на чтение.
Это полезно, если по какой-либо причине необходимо надолго остановить Master FE, сохранив возможность чтения через остальные FE.

#### `meta_delay_toleration_second` {#meta_delay_toleration_second}

По умолчанию: 300 (5 мин)

FE, не являющийся Master, прекращает обслуживание, если отставание метаданных превышает *meta_delay_toleration_second*.

#### `edit_log_port` {#edit_log_port}

По умолчанию: 9010

Порт bdbje.

#### `edit_log_type` {#edit_log_type}

По умолчанию: BDB

Тип журнала изменений.
BDB: запись журнала в bdbje.
LOCAL: устаревший вариант.

#### `edit_log_roll_num` {#edit_log_roll_num}

По умолчанию: 50000

IsMutable: true

MasterOnly: true

Master FE сохраняет образ после каждых *edit_log_roll_num* записей журнала метаданных.

#### `force_do_metadata_checkpoint` {#force_do_metadata_checkpoint}

По умолчанию: false

IsMutable: true

MasterOnly: true

Если задано true, поток создания контрольных точек создаёт контрольную точку независимо от процента использования памяти JVM.

#### `metadata_checkpoint_memory_threshold` {#metadata_checkpoint_memory_threshold}

По умолчанию: 60 (60%)

IsMutable: true

MasterOnly: true

Если процент использования памяти JVM (кучи или пула старого поколения) превышает этот порог, поток создания контрольных точек приостанавливает работу, чтобы избежать OOM.

#### `max_same_name_catalog_trash_num` {#max_same_name_catalog_trash_num}

Максимальное количество одноимённых объектов метаданных в корзине Catalog. При превышении этого значения объект, удалённый раньше остальных, окончательно удаляется без возможности восстановления. 0 означает, что одноимённые объекты не сохраняются. < 0 означает отсутствие ограничения.

Примечание: одноимённость метаданных проверяется в определённой области. Например, базы данных сравниваются в пределах одного кластера; таблицы — в пределах одной базы данных (с одинаковым идентификатором базы данных); разделы — в пределах одной базы данных (с одинаковым идентификатором базы данных) и одной таблицы (с одинаковым идентификатором таблицы).

По умолчанию: 3

Возможность динамической настройки: true

Применяется только к узлу Master FE: true

#### `cluster_id` {#cluster_id}

По умолчанию: -1

Узлы FE или BE считаются принадлежащими одному кластеру Doris, если у них одинаковый идентификатор кластера. Обычно это случайное целое число, которое генерируется при первом запуске Master FE. Его также можно задать вручную.

#### `heartbeat_mgr_blocking_queue_size` {#heartbeat_mgr_blocking_queue_size}

По умолчанию: 1024

MasterOnly: true

Размер блокирующей очереди для хранения задач heartbeat в heartbeat_mgr.

#### `heartbeat_mgr_threads_num` {#heartbeat_mgr_threads_num}

По умолчанию: 8

MasterOnly: true

Количество потоков для обработки событий heartbeat в heartbeat_mgr.

#### `disable_cluster_feature` {#disable_cluster_feature}

По умолчанию: true

IsMutable: true

Поддержка нескольких кластеров будет объявлена устаревшей в версии 0.12. Если установить этот параметр в true, будут отключены все связанные с ней операции, включая:

1. Создание и удаление кластера.
2. Добавление свободного Backend, добавление Backend в кластер и балансировку при выводе кластера из эксплуатации.
3. Изменение количества Backend в кластере.
4. Связывание и миграцию баз данных.

#### `enable_fqdn_mode` {#enable_fqdn_mode}

Этот параметр в основном используется в кластерной среде k8s. Если enable_fqdn_mode имеет значение true, имя Pod, в котором находится BE, остаётся неизменным после его повторного создания, хотя IP-адрес может измениться.

По умолчанию: false

Возможность динамической настройки: false

Применяется только к узлу Master FE: true

#### `enable_token_check` {#enable_token_check}

По умолчанию: true

Параметр для прямой совместимости, который будет удалён в дальнейшем. Включает проверку токена при скачивании файла образа.

#### `fe_meta_auth_token` {#fe_meta_auth_token}

По умолчанию: "" (пустая строка)

IsMutable: false

Токен кластера для аутентификации обращений между узлами FE к HTTP-конечным точкам службы метаданных FE (`image`, `role`, `check`, `put`, `journal_id` и другим). Добавлен в версии 4.0.8 линейки Doris 4.0 и в версии 4.1.4 линейки 4.1.

Если задано непустое значение, эти конечные точки, помимо существующей проверки хоста узла, требуют от вызывающей стороны заголовок с соответствующим токеном. Это предотвращает доступ к конечным точкам метаданных FE из-за пределов кластера. Пустое значение сохраняет прежнее поведение с проверкой только хоста узла, поэтому существующие кластеры и последовательное обновление узлов не затрагиваются.

:::caution Примечание

Перед включением этого параметра его необходимо записать в `fe.conf` с одинаковым значением на **всех FE**. Иначе узлы FE будут отклонять запросы метаданных друг друга, и синхронизация метаданных перестанет работать.

:::

#### `enable_multi_tags` {#enable_multi_tags}

По умолчанию: false

Возможность динамической настройки: false

Применяется только к узлу Master FE: true

Включает поддержку нескольких тегов для одного BE.

#### `initial_root_password` {#initial_root_password}

Начальный пароль пользователя root, зашифрованный SHA-1 в 2 этапа. Значение по умолчанию — '', что означает отсутствие пароля root. Последующие операции `set password` для пользователя root переопределяют начальный пароль.

Пример: чтобы задать пароль в открытом виде `root@123`, выполните SQL-команду Doris `select password('root@123')` для получения зашифрованного пароля `*A00C34073A26B40AB4307650BFB9309D6BFA6999`.

По умолчанию: пустая строка

Возможность динамической настройки: false

Применяется только к узлу Master FE: true

#### `enable_cooldown_replica_affinity` {#enable_cooldown_replica_affinity}

Позволяет выбрать, следует ли в первую очередь использовать для сканирования реплику с выгруженными в холодное хранилище данными. По умолчанию включено.

По умолчанию: true

Возможность динамической настройки: true

Применяется только к узлу Master FE: false

#### `drop_backend_after_decommission` {#drop_backend_after_decommission}

По умолчанию: false

IsMutable: true

MasterOnly: true

1. Определяет, удаляет ли система BE после его успешного вывода из эксплуатации. Если задано true, узел BE удаляется после завершения вывода из эксплуатации. Если false, после успешного вывода узел BE остаётся в состоянии DECOMMISSION, но не удаляется.

   Этот параметр полезен в некоторых сценариях. Предположим, изначально каждый узел BE в кластере Doris имел один диск. Через некоторое время было выполнено вертикальное масштабирование: на каждый узел BE добавили 2 новых диска. Поскольку Doris в настоящее время не поддерживает балансировку данных между дисками внутри BE, объём данных на исходном диске может постоянно значительно превышать объём данных на новых дисках. В таком случае можно вручную выполнить балансировку между дисками следующим образом:

   1. Установите параметр в false.
   2. Выполните вывод из эксплуатации определённого узла BE. Эта операция перенесёт все данные с BE на другие узлы.
   3. После завершения операции BE не будет удалён. Отмените состояние вывода из эксплуатации для этого BE. Данные начнут перераспределяться с других узлов BE обратно на этот узел и будут равномерно распределены по всем его дискам.
   4. Последовательно выполните шаги 2 и 3 для всех узлов BE, чтобы добиться балансировки дисков на всех узлах.

#### `jetty_server_acceptors` {#jetty_server_acceptors}

По умолчанию: 2

#### `jetty_server_selectors` {#jetty_server_selectors}

По умолчанию: 4

#### `jetty_server_workers` {#jetty_server_workers}

По умолчанию: 0

Эти три параметра описывают простую потоковую архитектуру Jetty с тремя пулами: acceptors, selectors и workers. Acceptors принимают новые соединения и передают их selectors, которые разбирают протокол HTTP-сообщений. Затем workers обрабатывают запрос. Первые два пула используют неблокирующую модель: один поток может читать и записывать данные множества сокетов, поэтому количество потоков в этих пулах невелико.

Для большинства проектов достаточно 1-2 потоков acceptors и от 2 до 4 потоков selectors. Workers выполняют блокирующую бизнес-логику, часто связанную с обращениями к базе данных, поэтому им требуется много потоков. Конкретное количество зависит от QPS и доли операций ввода-вывода в приложении. Чем выше QPS, тем больше требуется потоков; чем выше доля ввода-вывода, тем больше потоков находится в ожидании и тем большее общее количество потоков необходимо.

Размер пула workers по умолчанию не задан; настройте его в соответствии с потребностями.

#### `be_exec_version` {#be_exec_version}

Определяет формат сериализации блоков при передаче между фрагментами.

Некоторые изменения кода приводят к изменению формата данных блока. Чтобы узлы BE оставались совместимыми во время последовательного обновления, FE передаёт версию данных, определяющую формат их отправки.

Например, в кластере есть 2 узла BE: один после обновления поддерживает новую версию $v_1$, а другой — только $v_0$. Поскольку FE ещё не обновлён, он везде задаёт $v_0$, и узлы BE обмениваются данными в старом формате. После обновления всех BE обновляется FE. Новый FE задаёт $v_1$, и весь кластер переключается на новый формат данных.

Значение по умолчанию — `max_be_exec_version`. При необходимости версию формата можно вручную понизить, но она не должна быть ниже `min_be_exec_version`.

Значение этой переменной всегда должно находиться в диапазоне между `BeExecVersionManager::min_be_exec_version` и `BeExecVersionManager::max_be_exec_version` для всех BE. То есть при возврате обновлённого кластера к предыдущей версии сначала нужно понизить версию FE, а затем BE, либо вручную уменьшить значение переменной перед понижением версии BE.

#### `max_be_exec_version` {#max_be_exec_version}

Самая новая поддерживаемая версия данных. Не допускает изменения и должна совпадать с `BeExecVersionManager::max_be_exec_version` в BE соответствующей версии.

#### `min_be_exec_version` {#min_be_exec_version}

Самая старая поддерживаемая версия данных. Не допускает изменения и должна совпадать с `BeExecVersionManager::min_be_exec_version` в BE соответствующей версии.

#### `resource_group_load_success_quorum` {#resource_group_load_success_quorum}

По умолчанию: пустое значение

Возможность динамической настройки: true

Применяется только к узлу Master FE: true

Добавлен в версии 4.1.4. Задаёт для каждой группы ресурсов, то есть Location Tag узлов BE, **минимальное количество реплик, в которые данные должны быть успешно записаны** в этой группе при фиксации транзакции загрузки.

Значение представляет собой список через запятую, каждый элемент которого имеет формат `<resource_group>:<min_success_replicas>`, где `<min_success_replicas>` — неотрицательное целое число. Например:

```properties
resource_group_load_success_quorum=group_a:2,group_b:1
```

Если при фиксации транзакции количество успешно записанных реплик в настроенной группе ресурсов меньше заданного значения, транзакция не фиксируется. Группы ресурсов, отсутствующие в конфигурации, не проверяются. Некорректные элементы игнорируются, а в `fe.log` выводится предупреждение.

Используйте этот параметр при развёртывании в нескольких центрах обработки данных или зонах доступности, чтобы загрузка считалась успешной только после записи заданного количества реплик в указанном центре обработки данных.

#### `enable_adaptive_random_bucket_load` {#enable_adaptive_random_bucket_load}

По умолчанию: true

Возможность динамической настройки: true

Применяется только к узлу Master FE: true

Добавлен в версии 4.1.4. Включает адаптивную загрузку в случайные бакеты.

Если параметр включён, FE отправляет узлам BE информацию о расположении tablet, по которой каждый BE определяет набор локальных бакетов, для которых он хранит основную реплику. Как только объём данных, записанных в один tablet, превышает порог (по умолчанию 200 MB), запись переключается между локальными бакетами. Это снижает потребление памяти при загрузке и повышает пропускную способность загрузки в таблицы со случайным распределением по бакетам (`DISTRIBUTED BY RANDOM`). Механизм одинаково применяется ко всем способам загрузки.

Работа этой функции также ограничивается параметрами BE `enable_table_memtable_flush_backpressure` и `table_memtable_flush_pending_count_limit`. См. [Конфигурация BE](./be-config).

#### `enable_forward_group_commit_stream_load_to_follower` {#enable_forward_group_commit_stream_load_to_follower}

По умолчанию: false

Возможность динамической настройки: true

Применяется только к узлу Master FE: true

Добавлен в версии 4.1.4. Включает перенаправление запросов Stream Load, использующих Group Commit, на Follower FE.

Если параметр включён, запросы Stream Load в режиме Group Commit перенаправляются на узлы Follower FE по кругу, распределяя нагрузку по формированию пакетов между несколькими FE.

Учтите, что перенаправление не поддерживается, если свойство `light_schema_change` целевой таблицы имеет значение `false`; такие запросы завершаются с ошибкой.

Конечные точки службы метаданных задаются в формате 'host1:port,host2:port'. Этот параметр необходим для режима разделения хранения и вычислений.

#### `enable_group_commit_streamload_be_forward` {#enable_group_commit_streamload_be_forward}

По умолчанию: false

IsMutable: true

Включает перенаправление Stream Load через BE для Group Commit в режиме разделения вычислений и хранения. Действует только в этом режиме и только для запросов, использующих Group Commit.

Если параметр включён, FE перенаправляет запрос Stream Load на конечную точку `_stream_load_forward`, а получивший его BE пересылает запрос целевому BE для этой таблицы. Это предотвращает распределение запросов Group Commit одной таблицы балансировщиком нагрузки между разными узлами, что мешало бы формированию пакетов.

Одноимённый параметр необходимо включить и на FE, и на BE. **Начиная с версии 4.0.8 линейки Doris 4.0 и версии 4.1.4 линейки 4.1, доступ к конечной точке `_stream_load_forward` на стороне BE регулируется параметром BE: при отключении возвращается `403 Forbidden`, а после включения запросы должны проходить аутентификацию и иметь глобальную привилегию `LOAD`.** См. [Group Commit](../../data-operate/import/load-best-practices/group-commit-manual) и [Конфигурация BE](./be-config).

#### `default_get_version_from_ms_timeout_second` {#default_get_version_from_ms_timeout_second}

По умолчанию: 30 (с)

Возможность динамической настройки: false

Тайм-аут получения FE версии из Meta Service.

:::caution Изменение поведения (4.1.4)

В версии 4.1.4 значение по умолчанию изменено с `3` секунд на `30` секунд. Ранее при нестабильной работе или высокой нагрузке Meta Service тайм-аут в 3 секунды часто приводил к немедленному сбою запросов; увеличенное значение значительно снижает количество таких случайных сбоев.

:::

#### `enable_cloud_replica_stale_route_clean` {#enable_cloud_replica_stale_route_clean}

По умолчанию: true

Возможность динамической настройки: true

Добавлен в версии 4.1.4. Включает очистку записей основных и резервных маршрутов CloudReplica, указывающих на уже несуществующие Backend, при загрузке образа метаданных и во время циклов балансировки tablet.

При выполнении запросов такие устаревшие записи уже игнорируются: Backend для реплики повторно определяется хешированием. Они лишь расходуют память FE и увеличивают размер образа метаданных. Установите `false`, чтобы сохранить прежнее поведение без их очистки.

#### `enable_cloud_colocate_consistent_hash` {#enable_cloud_colocate_consistent_hash}

По умолчанию: true

Возможность динамической настройки: false

Применяется только к узлу Master FE: true

Добавлен в версии 4.1.4. Определяет, используется ли согласованное хеширование rendezvous для размещения бакетов таблиц Colocate в режиме разделения вычислений и хранения. При значении `false` используется прежнее размещение на основе остатка от деления. Этот параметр можно задать только в `fe.conf`, и он вступает в силу после перезапуска.

#### `meta_service_rpc_rate_limit_enabled` {#meta_service_rpc_rate_limit_enabled}

По умолчанию: true (false до 4.1.5)

Возможность динамической настройки: true

Добавлен в версии 4.1.4. Включает оценку ограничения QPS для RPC от FE к Meta Service. Начиная с версии 4.1.5, включён по умолчанию вместе с `meta_service_rpc_rate_limit_dry_run`, поэтому по умолчанию только регистрируются предполагаемые ожидания и отклонения, без фактической задержки или отклонения запросов. Чтобы применять ограничение, оставьте этот параметр равным `true` и установите dry-run в `false`.

#### `meta_service_rpc_rate_limit_dry_run` {#meta_service_rpc_rate_limit_dry_run}

По умолчанию: true

Возможность динамической настройки: true

Применяется только к узлу Master FE: false

Поддерживается с версии 4.1.5. Действует только при `meta_service_rpc_rate_limit_enabled=true`. При значении `true` оценивает ограничение частоты запросов и записывает метрики без ожидания или отклонения запросов. При значении `false` применяет настроенные QPS, окно кратковременных всплесков и тайм-аут ожидания. Метрики ожидания в режиме dry-run отражают расчётное время ожидания.

#### `meta_service_rpc_rate_limit_default_qps_per_core` {#meta_service_rpc_rate_limit_default_qps_per_core}

По умолчанию: 50

Возможность динамической настройки: true

Добавлен в версии 4.1.4. Допустимый QPS на ядро CPU по умолчанию для методов RPC Meta Service, для которых не заданы отдельные настройки в `meta_service_rpc_rate_limit_qps_per_core_config`. Значение меньше или равно `0` означает отсутствие ограничения частоты запросов.

#### `meta_service_rpc_rate_limit_qps_per_core_config` {#meta_service_rpc_rate_limit_qps_per_core_config}

По умолчанию: `getPartitionVersion:500;getTableVersion:500;getTabletStats:50;beginTxn:50`

Возможность динамической настройки: true

Добавлен в версии 4.1.4. Отдельные ограничения QPS на ядро для методов RPC Meta Service в формате `method1:qps1;method2:qps2`. Значение меньше или равно `0` означает, что частота вызова метода не ограничивается.

#### `meta_service_rpc_rate_limit_burst_seconds` {#meta_service_rpc_rate_limit_burst_seconds}

По умолчанию: 2 (с)

Возможность динамической настройки: true

Добавлен в версии 4.1.4. Продолжительность окна кратковременных всплесков при ограничении частоты RPC к Meta Service, в секундах. Долгосрочный средний QPS остаётся прежним, но внутри этого окна допускаются всплески.

#### `meta_service_rpc_rate_limit_wait_timeout_ms` {#meta_service_rpc_rate_limit_wait_timeout_ms}

По умолчанию: 1000 (мс)

Возможность динамической настройки: true

Добавлен в версии 4.1.4. Максимальное время ожидания при ограничении частоты RPC, в миллисекундах. Значение `0` отключает ожидание, поэтому запрос сразу завершается с ошибкой.
