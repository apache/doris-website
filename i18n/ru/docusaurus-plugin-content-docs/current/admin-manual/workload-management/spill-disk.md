## Зачем нужен сброс на диск {#why-spilling-is-needed}

Вычислительный слой Doris основан на архитектуре MPP. Все вычислительные задачи выполняются в памяти BE, а обмен данными между узлами также использует память, поэтому управление памятью напрямую влияет на стабильность запросов. По мере того как все больше пользователей переносят в Doris **обработку данных ETL, обработку материализованных представлений по нескольким таблицам и сложные запросы ad-hoc**, памяти одного узла зачастую не хватает для хранения всего промежуточного состояния.

**Сброс на диск** (spill to disk) записывает на диск промежуточное состояние, например состояние агрегации и временные данные сортировки, позволяя продолжать выполнение запросов при нехватке памяти. Он дает три преимущества:

| Преимущество | Описание |
|------|------|
| Масштабируемость | Позволяет обрабатывать наборы данных, превышающие лимит памяти одного узла |
| Стабильность | Снижает число ошибок запросов и аварийных завершений процессов из-за нехватки памяти |
| Гибкость | Позволяет выполнять более сложные запросы без добавления оборудования |

Сброс на диск сейчас поддерживают следующие операторы: Hash Join, Aggregation, Sort и CTE.

:::caution Примечание
Сброс на диск создает дополнительную нагрузку на дисковый ввод-вывод, поэтому время выполнения запросов может существенно увеличиться. Соответственно увеличьте значение переменной сеанса `query_timeout` и подключите отдельный диск или используйте SSD для каталога сброса, чтобы снизить влияние на обычную загрузку данных и выполнение запросов.

**По умолчанию сброс промежуточных результатов запросов на диск отключен.**
:::

## Как запускается сброс на диск {#how-spilling-is-triggered}

Doris использует механизм **резервирования памяти (reserve memory)**, чтобы управлять запуском сброса на диск. Он работает следующим образом:

1. Во время выполнения Doris оценивает объем памяти, необходимый для обработки каждого Block, и запрашивает его у единого диспетчера памяти.
2. Глобальный аллокатор памяти проверяет, не приведет ли выделение запрошенной памяти к превышению лимита памяти запроса, Workload Group или процесса.
3. При превышении лимита память не выделяется. Doris приостанавливает текущий запрос и запускает сброс на диск для оператора, потребляющего больше всего памяти.
4. После завершения сброса на диск выполнение запроса продолжается.

## Иерархия управления памятью {#memory-management-hierarchy}

Управление памятью в Doris имеет три уровня: **уровень процесса -> уровень Workload Group -> уровень запроса**. Все три уровня ограничивают работу механизма сброса на диск.

### Память на уровне процесса (BE) {#process-level-memory-be}

Параметр `mem_limit` в `be.conf` задает верхний предел использования памяти всем процессом BE. Когда потребление памяти превышает этот порог, Doris отменяет запрос, который в данный момент запрашивает память, а асинхронная фоновая задача завершает некоторые запросы или освобождает кеши.

**Две распространенные проблемные ситуации:**

- **Совместное развертывание**: если BE размещается на одном хосте с FE, Kafka, HDFS или другими процессами, фактически доступный объем памяти может быть значительно меньше `mem_limit`. В этом случае механизм освобождения памяти не справляется и срабатывает OOM Killer операционной системы.
- **Развертывание в контейнерах**: в средах K8s или Cgroup Doris автоматически определяет настройки памяти контейнера, поэтому ручная корректировка не требуется.

### Память Workload Group {#workload-group-memory}

<!-- Knowledge type: parameter reference -->

| Параметр | Описание |
|------|------|
| `max_memory_percent` | Максимальная доля памяти процесса, которую может использовать эта Workload Group. При ее превышении запускается сброс на диск или завершаются запросы. |
| `min_memory_percent` | Минимальная доля памяти, гарантированная этой Workload Group. При нехватке памяти система распределяет ее с учетом этого значения, чтобы другим группам хватало памяти. |
| `memory_low_watermark` | Нижний порог использования памяти. По умолчанию 50%. |
| `memory_high_watermark` | Верхний порог использования памяти. По умолчанию 80%. При превышении этого значения запросы на резервирование памяти отклоняются и запускается сброс на диск. |

Ограничения: сумма значений `min_memory_percent` всех Workload Group не должна превышать 100%, а значение `min_memory_percent` отдельной группы не должно быть больше ее `max_memory_percent`.

### Память на уровне запроса {#query-level-memory}

#### Статическое выделение памяти {#static-memory-allocation}

Значение `exec_mem_limit` задается с помощью переменной сеанса до запуска запроса и не может динамически изменяться во время его выполнения.

:::warning Примечание об обновлении
Значение `exec_mem_limit` по умолчанию составляло 2 GB до **версии 3.1**, а начиная с версии 3.1 было изменено на 100 GB; в этих версиях ограничение фактически применяется на стороне BE. Перед обновлением до версии 3.1 или более поздней явно задайте для этого параметра значение `100g`, чтобы существующие запросы не отменялись из-за превышения лимита и не запускали неожиданный сброс на диск.
:::

#### Динамическое выделение памяти на основе слотов {#slot-based-dynamic-memory-allocation}

При статическом выделении пользователям часто сложно точно оценить объем памяти, необходимый одному запросу, поэтому они задают слишком высокий лимит (например, половину памяти процесса). Это мешает точно управлять распределением памяти. Механизм слотов Workload Group решает эту проблему.

**Принцип работы:**

- Если для Workload Group заданы `max_memory_percent` и `max_concurrency`, память BE логически делится на `max_concurrency` слотов, а объем памяти каждого слота = `max_memory_percent x mem_limit / max_concurrency`.
- По умолчанию каждый запрос занимает 1 слот. Чтобы использовать больше памяти, измените переменную сеанса `query_slot_count`.
- Когда запрос занимает больше слотов, число запросов, которые Workload Group может выполнять одновременно, автоматически уменьшается, а новые запросы попадают в очередь.

**Возможные значения `slot_memory_policy`:**

| Значение | Описание |
|----|------|
| `none` | Значение по умолчанию. Механизм не включен. Запрос использует максимально возможный объем памяти, а сброс на диск запускается при достижении лимита Workload Group. |
| `fixed` | Объем памяти на запрос = `workload group mem_limit x query_slot_count / max_concurrency`. Фиксированное выделение памяти в зависимости от допустимого числа одновременных запросов. |
| `dynamic` | Объем памяти на запрос = `workload group mem_limit x query_slot_count / sum(running query slots)`. Память свободных слотов динамически перераспределяется в пользу выполняющихся крупных запросов. |

Оба варианта, `fixed` и `dynamic`, задают жесткие лимиты. При их превышении запускается сброс на диск или завершается запрос. Они также переопределяют статически заданный лимит `exec_mem_limit`. При настройке `slot_memory_policy` внимательно подбирайте значение `max_concurrency`, иначе возможна нехватка памяти.

## Включение сброса промежуточных результатов запросов на диск {#enable-query-spilling}

<!-- Knowledge type: procedure -->

### Шаг 1: Настройте пути сброса на диск для BE {#step-1-configure-be-spill-paths}

Добавьте следующую конфигурацию в `be.conf`. **Чтобы изменение вступило в силу, BE необходимо перезапустить**:

```properties
spill_storage_root_path=/mnt/disk1/spilltest/doris/be/storage;/mnt/disk2/doris-spill;/mnt/disk3/doris-spill
spill_storage_limit=100%
```

| Параметр | Описание |
|------|------|
| `spill_storage_root_path` | Путь хранения файлов сброса на диск. По умолчанию совпадает со значением `storage_root_path`. Рекомендуется использовать путь на отдельном диске. |
| `spill_storage_limit` | Максимальный объем дискового пространства для файлов сброса. Поддерживается абсолютное значение (например, `100G` или `1T`) либо процент (по умолчанию `20%`). При использовании отдельного диска можно задать `100%`. |

### Шаг 2: Настройте переменные сеанса FE {#step-2-configure-fe-session-variables}

```sql
SET enable_spill = true;
SET exec_mem_limit = 10g;
SET query_timeout = 3600;
```

| Переменная | Описание |
|------|------|
| `enable_spill` | Включает или отключает сброс на диск. По умолчанию `false`. Если включен, сброс на диск запускается автоматически при нехватке памяти. |
| `exec_mem_limit` | Максимальный объем памяти, доступный одному запросу. |
| `query_timeout` | Сброс на диск увеличивает время выполнения запроса, поэтому соответственно увеличьте время ожидания (в секундах). |

### Шаг 3: Настройте Workload Group (необязательно) {#step-3-configure-workload-group-optional}

Скорректируйте `max_memory_percent`, чтобы отдельная Workload Group не исчерпывала всю память процесса:

```sql
ALTER WORKLOAD GROUP normal PROPERTIES ('max_memory_percent'='90%');
```

Включите динамическое выделение памяти на основе слотов, чтобы сброс на диск запускался в первую очередь для крупных запросов:

```sql
ALTER WORKLOAD GROUP normal PROPERTIES ('slot_memory_policy'='dynamic');
```
