В версии 1.1 мы полностью векторизовали вычислительный слой и слой хранения данных и официально включили векторизованный движок выполнения запросов как стабильную функцию. Теперь все запросы по умолчанию выполняются этим движком, а производительность по сравнению с предыдущей версией выросла в 3–5 раз. Появилась возможность обращаться к внешним таблицам Apache Iceberg и выполнять совместные запросы к данным в Doris и Iceberg, что расширяет возможности анализа данных озера данных в Apache Doris. В дополнение к LZ4 добавлен алгоритм сжатия ZSTD, который повышает степень сжатия данных. Также исправлено множество проблем с производительностью и стабильностью предыдущих версий, благодаря чему система стала значительно стабильнее. Рекомендуем скачать и использовать эту версию.

## Примечания по обновлению {#upgrade-notes}

### Векторизованный движок выполнения запросов включён по умолчанию {#the-vectorized-execution-engine-is-enabled-by-default}

В версии 1.0 мы представили векторизованный движок выполнения запросов как экспериментальную функцию. Чтобы использовать его, пользователям требовалось вручную настроить переменные сеанса перед выполнением запросов: `set batch_size = 4096` и `set enable_vectorized_engine = true`.

В версии 1.1 векторизованный движок выполнения запросов официально стал стабильной функцией. Переменная сеанса `enable_vectorized_engine` по умолчанию имеет значение true, поэтому все запросы выполняются этим движком.

### Переименование исполняемого файла BE {#be-binary-file-renaming}

Исполняемый файл BE переименован из palo_be в doris_be. Если ваши сценарии управления кластером или других операций зависят от имени процесса, обновите их.

### Обновление формата хранения Segment {#segment-storage-format-upgrade}

В ранних версиях Apache Doris использовался формат хранения Segment V1. В версии 0.12 мы реализовали новый формат Segment V2 с индексами Bitmap, таблицами в памяти, кэшем страниц, словарным сжатием, отложенной материализацией и другими возможностями. Начиная с версии 0.13, для новых таблиц по умолчанию используется Segment V2 при сохранении совместимости с Segment V1.

Чтобы упростить сопровождение кода и сократить затраты на изучение и развитие устаревших компонентов, мы решили прекратить поддержку формата хранения Segment v1 в следующей версии. Ожидается, что соответствующий код будет удалён в Apache Doris 1.2.

### Обычное обновление {#normal-upgrade}

При обычном обновлении можно последовательно обновлять узлы кластера в соответствии с документацией по обновлению кластера на официальном сайте.

[https://doris.apache.org//docs/admin-manual/cluster-management/upgrade](https://doris.apache.org//docs/admin-manual/cluster-management/upgrade)

## Новые возможности {#features}

### Поддержка случайного распределения данных [экспериментальная функция] {#support-random-distribution-of-data-experimental}

В некоторых сценариях, например при анализе журналов, бывает трудно подобрать ключ бакетирования, который позволит избежать перекоса распределения данных. Для таких случаев системе нужен дополнительный способ распределения.

Теперь при создании таблицы можно указать `DISTRIBUTED BY random BUCKETS number`, чтобы использовать случайное распределение. При загрузке данные будут случайным образом записываться в один планшет, что уменьшит число направлений записи, снизит расход ресурсов и повысит стабильность системы.

### Поддержка создания внешних таблиц Iceberg [экспериментальная функция] {#support-for-creating-iceberg-external-tablesexperimental}

Внешние таблицы Iceberg дают Apache Doris прямой доступ к данным, хранящимся в Iceberg. Они позволяют выполнять совместные запросы к локальным данным и данным Iceberg, избавляют от трудоёмкой загрузки данных, упрощают архитектуру системы анализа и дают возможность проводить более сложный анализ.

В версии 1.1 Apache Doris поддерживает создание внешних таблиц Iceberg и запросы к их данным. Кроме того, команда REFRESH позволяет автоматически синхронизировать схемы всех таблиц в базе данных Iceberg.

### Добавлен алгоритм сжатия ZSTD {#added-zstd-compression-algorithm}

Сейчас способ сжатия данных в Apache Doris задаётся системой; по умолчанию используется LZ4. В сценариях, где особенно важна стоимость хранения данных, прежней степени сжатия может быть недостаточно.

В версии 1.1 при создании таблицы можно указать свойство "compression"="zstd", чтобы выбрать алгоритм ZSTD. В испытании на текстовых журналах объёмом 25GB и 110 миллионами строк максимальная степень сжатия составила почти 10 раз, превысив прежний показатель на 53%. Скорость чтения данных с диска и их распаковки выросла на 30%.

## Улучшения {#improvements}

### Более полная поддержка векторизации {#more-comprehensive-vectorization-support}

В версии 1.1 мы полностью векторизовали вычислительный слой и слой хранения данных, в том числе:

Реализовали векторизацию всех встроенных функций.

Векторизовали слой хранения данных и добавили оптимизацию с использованием словарей для строковых столбцов с низкой кардинальностью.

Оптимизировали векторизованный движок и устранили многочисленные проблемы с его производительностью и стабильностью.

Мы сравнили производительность Apache Doris версий 1.1 и 0.15 на стандартных наборах тестовых данных SSB и TPC-H:

Во всех 13 SQL-запросах набора SSB версия 1.1 показала лучшие результаты, чем версия 0.15. Общая производительность выросла примерно в 3 раза; проблема снижения производительности в отдельных сценариях, наблюдавшаяся в версии 1.0, устранена.

Во всех 22 SQL-запросах набора TPC-H версия 1.1 показала лучшие результаты, чем версия 0.15. Общая производительность выросла примерно в 4.5 раза, а в некоторых сценариях — более чем в десять раз.

### Оптимизация уплотнения данных и обеспечение его своевременности {#compaction-logic-optimization-and-real-time-guarantee}

В Apache Doris при каждой фиксации изменений создаётся версия данных. При большом числе параллельных операций записи из-за накопления версий и несвоевременного уплотнения могут возникать ошибки -235; производительность запросов при этом также снижается.

В версии 1.1 мы добавили QuickCompaction, который автоматически запускает уплотнение при увеличении числа версий данных. Улучшенное сканирование метаданных фрагментов позволяет быстро находить фрагменты с избыточным числом версий и запускать их уплотнение. Сочетание активного запуска и фонового сканирования решает проблему задержек при объединении данных.

Для частого накопительного уплотнения небольших файлов также реализованы планирование и изоляция задач уплотнения: ресурсоёмкое базовое уплотнение больше не мешает объединению новых данных.

Кроме того, оптимизирована стратегия объединения небольших файлов. Теперь используется поэтапное объединение файлов сопоставимого размера. Это предотвращает объединение версий, размеры которых сильно различаются, сокращает число операций с каждым файлом и значительно снижает нагрузку на CPU.

Когда источник данных поддерживает частоту записи 10w в секунду (20 параллельных задач записи, 5000 строк на задачу и интервал контрольных точек 1s), версия 1.1 показывает следующие результаты:

-   Быстрое объединение данных: число версий планшета остаётся ниже 50, а показатель уплотнения стабилен. По сравнению с предыдущей версией, в которой при большом числе параллельных операций записи часто возникала ошибка -235, эффективность уплотнения выросла более чем в 10 раз.

-   Значительное снижение потребления ресурсов CPU: оптимизирована стратегия уплотнения небольших файлов. В описанном сценарии параллельной записи потребление ресурсов CPU снизилось на 25%.

-   Стабильное время выполнения запросов: данные стали лучше упорядочены, а колебания времени выполнения запросов значительно уменьшились. При параллельной записи запросы выполняются столько же времени, сколько и без записи; по сравнению с предыдущей версией производительность запросов выросла в 3–4 раза.

### Оптимизация чтения файлов Parquet и ORC {#read-efficiency-optimization-for-parquet-and-orc-files}

Благодаря настройке параметров Arrow для чтения каждого row_group используется многопоточность. Переход на модель SPSC и предварительная выборка снижают время ожидания данных по сети. После оптимизации загрузка файлов Parquet ускорилась в 4–5 раз.

### Более надёжные контрольные точки метаданных {#safer-metadata-checkpoint}

Дополнительная проверка файлов образов, созданных после контрольной точки метаданных, и сохранение предыдущих файлов образов устраняют риск повреждения метаданных из-за ошибок в файлах образов.

## Исправления ошибок {#bugfix}

### Исправлена ошибка, из-за которой данные нельзя было запросить при отсутствии версии данных (серьёзная) {#fix-the-problem-that-the-data-cannot-be-queried-due-to-the-missing-data-versionserious}

Эта ошибка появилась в версии 1.0 и могла приводить к потере версий данных у нескольких реплик.

### Исправлена ошибка, из-за которой ограничения ресурсов не применялись к задачам загрузки (умеренная) {#fix-the-problem-that-the-resource-isolation-is-invalid-for-the-resource-usage-limit-of-loading-tasks-moderate}

В версии 1.1 Broker Load и Routine Load используют для загрузки Backends с заданными метками ресурсов.

### Для передачи сетевых пакетов размером более 2GB используется HTTP BRPC (умеренная) {#use-http-brpc-to-transfer-network-data-packets-over-2gb-moderate}

В предыдущей версии передача через BRPC данных размером более 2GB между Backends могла завершаться ошибкой.

## Прочее {#others}

### Отключение Mini Load {#disabling-mini-load}

Интерфейс `/_load` по умолчанию отключён. Используйте интерфейс `the /_stream_load` для всех таких операций.
При необходимости Mini Load можно снова включить, отключив параметр конфигурации FE `disable_mini_load`.

Интерфейс Mini Load будет полностью удалён в версии 1.2.

### Полное отключение формата хранения SegmentV1 {#completely-disable-the-segmentv1-storage-format}

Создавать данные в формате SegmentV1 больше нельзя. Доступ к существующим данным сохраняется.
Проверить, остались ли в кластере данные в формате SegmentV1, можно командой `ADMIN SHOW TABLET STORAGE FORMAT`.
Преобразовать их в SegmentV2 можно с помощью команды преобразования данных.

В версии 1.2 доступ к данным SegmentV1 больше не будет поддерживаться.

### Ограничение максимальной длины типа String {#limit-the-maximum-length-of-string-type}

В предыдущих версиях максимальная длина значения типа String составляла 2GB.
В версии 1.1 максимальная длина значения типа String ограничена 1MB. Более длинные строки записывать больше нельзя.
Кроме того, столбец типа String больше нельзя использовать для секционирования или бакетирования таблицы.

Доступ к уже записанным значениям типа String сохраняется.

### Исправлены уязвимости, связанные с fastjson {#fix-fastjson-related-vulnerabilities}

Версия Canal обновлена для устранения уязвимости fastjson.

### Добавлена команда `ADMIN DIAGNOSE TABLET` {#added-admin-diagnose-tablet-command}

Она позволяет быстро диагностировать проблемы с указанным планшетом.
