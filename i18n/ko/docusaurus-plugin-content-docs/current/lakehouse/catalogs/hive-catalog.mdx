Doris는 Hive Metastore 또는 Hive Metastore와 호환되는 메타데이터 서비스에 연결하여 Hive 데이터베이스와 테이블 정보를 자동으로 가져와 데이터를 쿼리할 수 있습니다.

Hive 외에도 여러 시스템이 메타데이터 저장에 Hive Metastore를 사용합니다. 따라서 Hive Catalog를 통해 Hive 테이블뿐 아니라 Iceberg, Hudi 등 Hive Metastore에 메타데이터를 저장하는 다른 테이블 형식에도 접근할 수 있습니다.

## 적용 시나리오 {#applicable-scenarios}

| 시나리오 | 설명 |
|--------------|--------------------------------------------------------------|
| 쿼리 가속 | Doris의 분산 컴퓨팅 엔진으로 Hive 데이터에 직접 접근하여 쿼리를 가속합니다. |
| 데이터 통합 | Hive 데이터를 읽어 Doris 내부 테이블에 쓰거나 Doris 컴퓨팅 엔진으로 ZeroETL 작업을 수행합니다. |
| 데이터 다시 쓰기 | Doris가 지원하는 모든 데이터 소스의 데이터를 처리하여 Hive 테이블에 다시 씁니다. |

## Catalog 구성 {#configuring-catalog}

### 구문 {#syntax}

```sql
CREATE CATALOG [IF NOT EXISTS] catalog_name PROPERTIES (
    'type'='hms', -- required
    'hive.metastore.type' = '<hive_metastore_type>', -- optional
    'hive.version' = '<hive_version>', -- optional
    'fs.defaultFS' = '<fs_defaultfs>', -- required for write, optional for read-only
    {MetaStoreProperties},
    {StorageProperties},
    {HiveProperties},
    {CommonProperties}
);
```

* `<hive_metastore_type>`

  Hive Metastore의 유형을 지정합니다.

  * `hms`: 표준 Hive Metastore 서비스입니다.
  * `glue`: Hive Metastore 호환 인터페이스를 사용하여 AWS Glue 메타데이터 서비스에 접근합니다.
  * `dlf`: Hive Metastore 호환 인터페이스를 사용하여 Alibaba Cloud DLF 메타데이터 서비스에 접근합니다.

* `<fs_defaultfs>`

  Doris에서 이 Hive Catalog의 테이블에 데이터를 쓸 때 필수인 매개변수입니다. 예:

  `'fs.defaultFS' = 'hdfs://namenode:port'`

* `{MetaStoreProperties}`

  MetaStoreProperties에는 Metastore 메타데이터 서비스의 연결 및 인증 정보를 입력합니다. 자세한 내용은 "지원되는 메타데이터 서비스" 절을 참조하세요.

* `{StorageProperties}`

  StorageProperties에는 스토리지 시스템의 연결 및 인증 정보를 입력합니다. 자세한 내용은 "지원되는 스토리지 시스템" 절을 참조하세요.

* `{HiveProperties}`

  HiveProperties에는 Hive Catalog 관련 속성을 입력합니다.

  * `get_schema_from_table`: 기본값은 false입니다. 기본적으로 Doris는 Hive Metastore에서 테이블 스키마 정보를 가져옵니다. 하지만 `Storage schema reading not supported` 오류처럼 호환성 문제가 발생할 수 있습니다. 이 경우 이 매개변수를 true로 설정하면 Table 객체에서 테이블 스키마를 직접 가져옵니다. 단, 이 방법을 사용하면 열의 기본값 정보가 무시됩니다. 이 속성은 버전 2.1.10 및 3.0.6부터 지원됩니다.

  * `hive.recursive_directories`: 파티션 디렉터리 목록을 가져올 때 하위 디렉터리를 재귀적으로 탐색할지 지정합니다. 버전 3.0.2부터 지원됩니다. 버전 4.0 이전에는 기본값이 `false`였고 이후 버전에서는 `true`입니다. 일부 Hive 테이블의 파티션 경로는 테이블 스키마의 파티션 정보와 일치하지 않을 수 있습니다. 하위 디렉터리의 데이터 파일을 가져오려면 이 매개변수를 true로 설정해야 합니다.

  * `hive.ignore_absent_partitions`: 존재하지 않는 파티션을 무시할지 지정합니다. 기본값은 `true`입니다. `false`로 설정하면 쿼리에서 존재하지 않는 파티션을 만났을 때 오류가 발생합니다. 버전 3.0.2부터 지원됩니다.

  * `hive.staging_dir`: Hive 쓰기 작업에 사용할 임시 스테이징 루트 디렉터리를 설정합니다. 쓰는 동안 데이터는 먼저 이 디렉터리에 기록되고, 작업이 완료되면 최종 Hive 테이블 디렉터리로 이동합니다. Hive 테이블 루트 디렉터리를 기준으로 한 상대 경로나 절대 경로를 지정할 수 있습니다. 기본값은 `/tmp/.doris_staging`입니다. Hive 테이블에 쓸 때 `/tmp` 디렉터리와 테이블 디렉터리가 서로 다른 네임스페이스에 속해 쓰기가 실패하는 경우가 있습니다. 이때 상대 경로를 사용하도록 이 매개변수를 변경하면 문제를 해결할 수 있습니다. 버전 4.0.3부터 지원됩니다.

  * `hive.parquet.time-zone`: FileScannerV2가 Hive 테이블을 읽을 때 이전 방식의 Parquet `INT96` 타임스탬프를 복원하는 데 사용하는 호환 시간대입니다. 기본값은 빈 값이며, 이 경우 시간대 변환 없이 `INT96`에 저장된 날짜와 시간 필드를 그대로 유지합니다. Catalog의 `INT96` 파일을 작성한 쪽에서 알려진 시간대를 사용해 값을 정규화한 경우에만 이 속성을 설정하세요. Hudi 테이블은 이 속성을 의도적으로 무시하고 기존 SQL 세션 시간대 동작을 유지합니다. 자세한 내용은 [Parquet INT96 타임스탬프 호환성](#timestamp-compatibility)을 참조하세요.

* `{CommonProperties}`

  CommonProperties에는 공통 속성을 입력합니다. [Catalog 개요](../catalog-overview.md)의 "공통 속성" 절을 참조하세요.

## 메타데이터 캐시 {#meta-cache}

Apache Doris는 외부 데이터 소스에 접근하는 성능을 높이기 위해 Hive 메타데이터를 캐시합니다. 캐시 대상에는 테이블 객체, 파티션 이름, 파티션 객체, 열 통계, 파일 목록, 파티션 제거를 위해 파생된 구조가 포함됩니다.

:::tip
Doris 4.1.x 이전 버전에서는 메타데이터 캐싱을 주로 FE 구성 항목으로 전역 제어합니다. 자세한 내용은 [메타데이터 캐시](../meta-cache.md)를 참조하세요.
Doris 4.1.x부터 Hive Catalog의 외부 메타데이터 캐시는 통합된 `meta.cache.*` 키로 구성합니다. 아래 항목은 현재 버전을 설명하며, Doris 4.1.x와 4.2.x에서 사용하는 항목 집합은 이 페이지의 4.x 버전에서 설명합니다.
:::

### 캐시 속성 구성 {#meta-cache-unified-model}

각 캐시 항목의 구성 키는 `meta.cache.<engine>.<entry>.{enable,ttl-second,capacity,max-weight}` 형식을 따릅니다. Hive에서 `<engine>`은 `hive`입니다. Iceberg 테이블이 포함된 Hive Metastore Catalog는 `iceberg` 항목도 사용하며, 이는 [Iceberg Catalog](./iceberg-catalog.mdx#meta-cache)에 설명되어 있습니다.

| 속성 | 예 | 의미 |
|---|---|---|
| `enable` | `true/false` | 이 캐시 항목을 활성화할지 지정합니다. |
| `ttl-second` | `600`, `0`, `-1` | `0`은 항목을 비활성화합니다(즉시 적용되며 최신 데이터를 확인할 때 사용할 수 있음). `-1`은 만료되지 않음을 의미합니다. 다른 양의 정수는 접근 시간을 기준으로 한 TTL(초)입니다. |
| `capacity` | `10000` | 캐시 항목의 최대 개수입니다. `0`은 항목을 비활성화합니다. |
| `max-weight` | `1GB` | Doris 4.1.4부터 지원됩니다. 선택적으로 설정하는 항목의 예상 점유 메모리 한도입니다. 양수여야 하며 `0`은 허용되지 않습니다. 아래에 표시된 항목에서만 사용할 수 있습니다. |

**적용 조건:** `enable=true`, `ttl-second != 0`, `capacity > 0`일 때 항목이 적용됩니다. FE 전체, Catalog 또는 항목별 메모리 한도도 예상 메모리를 기준으로 캐시 수용 여부를 결정합니다. 자세한 내용은 [외부 메타데이터 캐시 메모리 관리](../external-meta-cache-memory-management)를 참조하세요.

### 캐시 모듈 {#meta-cache-unified-modules}

Hive Catalog에는 다음 캐시 항목이 포함됩니다. 모든 항목에서 `max-weight`를 사용할 수 있습니다.

| 항목 (`<entry>`) | 속성 키 접두사 | `ENTRY_NAME` | 캐시 내용과 영향 | 기본 enable / TTL / capacity |
|---|---|---|---|---|
| `table` | `meta.cache.hive.table.` | `hive-table` | Hive Metastore의 테이블 객체입니다. 영향: 계획 수립 시 Metastore 왕복 요청을 줄입니다. | `true` / 86400초 / 10000 |
| `partition_names` | `meta.cache.hive.partition_names.` | `hive-partition-names` | 파티션 이름 목록입니다. 영향: 파티션 열거에 사용되며, 비활성화하면 새 파티션이 즉시 표시됩니다. | `true` / 86400초 / 10000 |
| `partition` | `meta.cache.hive.partition.` | `hive-partition` | 위치와 입력 형식 등의 파티션 객체입니다. | `true` / 86400초 / 100000 |
| `column_stats` | `meta.cache.hive.column_stats.` | `hive-column-stats` | Hive Metastore의 열 통계입니다. | `true` / 86400초 / 10000 |
| `file` | `meta.cache.hive.file.` | `hive-file` | 파일 목록입니다. 영향: 원격 LIST 작업을 줄이며, 비활성화하면 파일 변경 사항이 즉시 표시됩니다. | `true` / 86400초 / 10000 |
| `partition_view` | `meta.cache.hive.partition_view.` | `hive-partition-view` | 파티션 이름에서 파생된 파티션 제거 구조입니다. | `true` / 86400초 / 1000 |

Hive 테이블의 열 스키마는 모든 외부 Catalog가 사용하는 공통 `default` 엔진(`meta.cache.default.schema.*`)에 캐시됩니다.

### 이전 매개변수 매핑 및 변환 {#meta-cache-mapping}

통합 키 사용을 권장합니다. 다음 이전 Catalog 속성도 계속 사용할 수 있으며, 아래와 같이 매핑됩니다.

| 이전 속성 키 | 통합 키 | 설명 |
|---|---|---|
| `schema.cache.ttl-second` | `meta.cache.default.schema.ttl-second` 및 `meta.cache.hive.table.ttl-second` | 테이블 스키마 캐시와 테이블 객체 캐시의 만료 시간 |
| `partition.cache.ttl-second` | `meta.cache.hive.partition_names.ttl-second` | 파티션 이름 목록의 만료 시간 |
| `file.meta.cache.ttl-second` | `meta.cache.hive.file.ttl-second` | 파일 목록의 만료 시간 |

### 권장 사례 {#meta-cache-best-practices}

* **최신 데이터에 실시간으로 접근**: 각 쿼리에서 외부 데이터 소스의 최신 파티션 또는 파일 변경 사항을 확인하려면 해당 `ttl-second`를 `0`으로 설정하세요.
  ```sql
  -- Disable the file listing cache to see file changes in real time
  ALTER CATALOG hive_ctl SET PROPERTIES ("meta.cache.hive.file.ttl-second" = "0");
  -- Disable the partition name cache to see new partitions in real time
  ALTER CATALOG hive_ctl SET PROPERTIES ("meta.cache.hive.partition_names.ttl-second" = "0");
  ```
* **성능 최적화**: 메타데이터 변경이 드문 경우 `capacity`와 `ttl-second`를 늘려 Hive Metastore와 파일 시스템에 가해지는 접근 부담을 줄이세요. 매우 큰 테이블에서는 `max-weight`로 파일 목록 캐시와 파티션 제거 캐시의 메모리 사용량을 제한할 수 있습니다.

:::caution
Catalog 속성 변경이 성공하면 영향을 받는 메타데이터 캐시가 삭제되고, 다음 접근 시 새 구성으로 다시 만들어집니다. `meta.cache.max-weight` 또는 `schema.cache.ttl-second`를 변경하면 해당 Catalog의 모든 캐시가 삭제됩니다. `meta.cache.<engine>.<entry>.*`를 변경하면 해당 엔진의 캐시가 삭제됩니다. 이미 실행 중인 쿼리는 영향을 받지 않습니다.
:::

### 관측 {#meta-cache-unified-observability}

`information_schema.catalog_meta_cache_statistics` 시스템 테이블에서 캐시 지표를 확인할 수 있습니다. `ENTRY_NAME`에는 위 표의 이름이 표시되고, `default` 엔진 행은 공통 테이블 스키마 캐시를 나타냅니다.

```sql
SELECT engine_name, entry_name,
       effective_enabled, ttl_second, capacity,
       estimated_size, hit_rate, max_weight, estimated_weight
FROM information_schema.catalog_meta_cache_statistics
WHERE catalog_name = 'hive_ctl'
ORDER BY engine_name, entry_name;
```

이 시스템 테이블에 대한 설명은 [catalog_meta_cache_statistics](../../admin-manual/system-tables/information_schema/catalog_meta_cache_statistics.md)를 참조하세요.

## Parquet INT96 타임스탬프 호환성 {#timestamp-compatibility}

Hive 테이블에는 서로 다른 엔진이 생성한 타임스탬프 파일이 포함될 수 있습니다. 시간대 변환이 필요한지는 물리적 인코딩과 작성 방식에 따라 결정됩니다. Parquet `INT96`에는 시간대 정보가 없으므로 Doris는 `INT96` 값에서 작성자의 시간대를 추론하지 않습니다.

4.1.5부터 `hive.parquet.time-zone`에는 IANA 시간대 또는 `-12:00`부터 `+14:00`까지의 UTC 오프셋을 지정할 수 있습니다. `UTC`와 `GMT`는 허용되지만 `CST`, `PRC`와 같은 짧은 별칭은 허용되지 않습니다. [Parquet](../file-formats/parquet.md#timestamp-and-date-compatibility)을 참조하세요.

### Parquet INT96 타임스탬프 {#parquet-int96-timestamps}

FileScannerV2는 Parquet 타임스탬프를 다음과 같이 처리합니다.

| 물리적 인코딩 | 기본 동작 | `hive.parquet.time-zone`의 효과 |
|---|---|---|
| `INT96`에서 `DATETIMEV2`로 매핑 | 파일에 저장된 날짜 및 시간 필드를 유지합니다. SQL 세션 시간대에 따라 값이 이동하지 않습니다. | 원시 `INT96` 값을 UTC 시점으로 간주하고 구성된 호환 시간대로 변환하여, 이전 작성자가 정규화한 타임스탬프를 복원합니다. |
| 타임스탬프 논리 타입이 있는 `INT64` | Parquet 논리 타입의 의미를 따릅니다. | 영향을 받지 않습니다. |

예를 들어 의도한 현지 타임스탬프가 `Asia/Shanghai` 시간대의 `2021-01-01 10:11:00`이라고 가정합니다.

* 파일이 현지 시각 필드 `10:11:00`을 직접 저장한 경우 `hive.parquet.time-zone`을 설정하지 마세요. SQL 세션이 `Asia/Shanghai`를 사용하더라도 Doris는 `10:11:00`을 반환합니다.
* 이전 작성자가 값을 UTC로 정규화한 다음 `INT96`에 저장했다면 파일에는 `02:11:00`이 들어 있을 수 있습니다. Doris가 `10:11:00`을 복원하도록 `hive.parquet.time-zone`을 `Asia/Shanghai`로 설정하세요.

Catalog를 만들 때 호환 시간대를 구성합니다.

```sql
CREATE CATALOG hive_legacy_int96 PROPERTIES (
    'type' = 'hms',
    'hive.metastore.uris' = 'thrift://127.0.0.1:9083',
    'hive.parquet.time-zone' = 'Asia/Shanghai'
);
```

값에는 `Asia/Shanghai` 같은 IANA 시간대 이름이나 `-12:00`부터 `+14:00`까지의 UTC 오프셋을 사용할 수 있습니다. 잘못된 값을 지정하면 Catalog 생성이 실패합니다.

:::caution
`hive.parquet.time-zone`은 해당 Catalog의 Hive 테이블에서 `DATETIMEV2`로 매핑되는 모든 `INT96` 타임스탬프 열에 적용됩니다. Iceberg는 자체 타임스탬프 의미를 정의하므로, 동일한 Hive Metastore에 있는 Iceberg 테이블에는 영향을 주지 않습니다. Hudi도 이 속성을 의도적으로 무시합니다. 기본 파일을 직접 스캔하거나 JNI로 merge-on-read 스캔을 수행할 때 모두 SQL 세션 시간대로 타임스탬프를 해석하는 기존 동작을 유지합니다. Doris는 Parquet 메타데이터만으로 `INT96` 작성자가 사용한 규칙을 확실하게 판별할 수 없습니다. 단지 SQL 세션 시간대와 맞추기 위해 이 속성을 설정하지 마세요. 하나의 Hive Metastore에 서로 다른 규칙으로 작성된 `INT96` 파일을 포함하는 Hive 테이블이 있다면, 가능하면 별도의 Catalog를 통해 노출하세요.
:::

Parquet 파일을 읽는 파일 테이블 값 함수에서도 동일한 속성을 사용할 수 있습니다. 호환성 변환은 FileScannerV2의 Parquet `INT96` 디코딩에만 적용됩니다. FileScannerV1은 의도적으로 변경되지 않았으며 다른 결과를 반환할 수 있습니다. FileScannerV1로 전환하는 것은 이 변경에 대한 호환성 대책이 아닙니다. Parquet `INT64` 논리 타임스탬프는 영향을 받지 않습니다. `INT96` 열이 `TIMESTAMPTZ`로 매핑되면 Doris는 이 속성을 무시하고 UTC 시점을 유지합니다. 해당 값의 표시는 계속 `TIMESTAMPTZ`와 세션 시간대 의미를 따릅니다.

### 마이그레이션 권장 사항 {#migration-recommendations}

* Doris는 기본적으로 Parquet `INT64` 논리 타임스탬프를 씁니다. Hive 2 또는 Hive 3 같은 이전 버전의 리더에서 `INT96`이 필요할 때만 `enable_int96_timestamps = true`를 설정하세요.
* 이 FileScannerV2 동작이 포함된 버전으로 업그레이드할 때는 배포 전에 기존 Hive 테이블을 확인하세요. 이전 작성자가 정규화한 `INT96` 파일을 포함한 Catalog는 업그레이드 후 다른 현지 시각 값을 반환할 수 있습니다. 대표 값을 비교하고 변환이 필요한 경우 `hive.parquet.time-zone`을 작성자 시간대로 설정하세요. Hudi는 기존 세션 시간대 동작을 유지하므로 이 변경에 따른 마이그레이션이 필요하지 않습니다.
* `hive.parquet.time-zone`을 설정하기 전에 대표 파일을 검사하고 알려진 타임스탬프 값과 비교하세요. 불필요하게 설정하면 바로잡으려던 시간 오프셋과 같은 종류의 오프셋이 발생합니다.
* 서로 다른 `INT96` 작성 규칙을 사용한 파일은 별도의 Catalog에 두거나 일관된 `INT64` 인코딩으로 다시 쓰세요.
* Doris가 `enable_int96_timestamps = true`를 사용하여 `INT96`을 명시적으로 내보낼 때는 내보내기 세션 시간대를 사용하여 타임스탬프를 정규화합니다. FileScannerV2로 파일을 다시 읽으려면 `hive.parquet.time-zone`을 해당 내보내기 세션 시간대로 설정하세요. [내보내기 개요](../../data-operate/export/export-overview.md)를 참조하세요.

## 쿼리 작업 {#query-operations}

### 기본 쿼리 {#basic-query}

Catalog를 구성한 후 다음 방법으로 Catalog의 테이블 데이터를 쿼리할 수 있습니다.

```sql
-- 1. switch to catalog, use database and query
SWITCH hive_ctl;
USE hive_db;
SELECT * FROM hive_tbl LIMIT 10;

-- 2. use hive database directly
USE hive_ctl.hive_db;
SELECT * FROM hive_tbl LIMIT 10;

-- 3. use full qualified name to query
SELECT * FROM hive_ctl.hive_db.hive_tbl LIMIT 10;
```

### Hive 파티션 쿼리 {#querying-hive-partitions}

다음 두 가지 방법으로 Hive 파티션 정보를 쿼리할 수 있습니다.

* `SHOW PARTITIONS FROM [catalog.][db.]hive_table`

  이 문은 지정한 Hive 테이블의 모든 파티션과 각 파티션 값을 나열합니다.

  ```sql
  SHOW PARTITIONS FROM hive_table;

  +--------------------------------+
  | Partition                      |
  +--------------------------------+
  | pt1=2024-10-10/pt2=beijing     |
  | pt1=2024-10-10/pt2=shanghai    |
  | pt1=2024-10-11/pt2=beijing     |
  | pt1=2024-10-11/pt2=shanghai    |
  | pt1=2024-10-12/pt2=nanjing     |
  +--------------------------------+
  ```

* `table$partitions` 메타데이터 테이블 사용

  버전 2.1.7 및 3.0.3부터 `table$partitions` 메타데이터 테이블로 Hive 파티션 정보를 쿼리할 수 있습니다. 이 테이블은 관계형 테이블이며 각 파티션 열이 하나의 열로 표시되므로 모든 SELECT 문에서 사용할 수 있습니다.

  ```sql
  SELECT * FROM hive_table$partitions;

  +------------+-------------+
  | pt1        | pt2         |
  +------------+-------------+
  | 2024-10-10 | beijing     |
  | 2024-10-10 | shanghai    |
  | 2024-10-12 | nanjing     |
  | 2024-10-11 | beijing     |
  | 2024-10-11 | shanghai    |
  +------------+-------------+
  ```

:::caution 동작 변경(4.1.4)

버전 4.1.4부터 Hive의 디렉터리 형식 파티셔닝에 사용되는 기본 파티션 표식 `__HIVE_DEFAULT_PARTITION__`는 문자열 `\N`으로 인코딩되는 대신 실제 **NULL** 값으로 해석됩니다. 동시에 파티션 경로에 실제로 저장된 리터럴 `\N`은 데이터로 그대로 유지됩니다.

4.1.4 이전에는 두 경우를 구분할 수 없었고 쿼리 결과에 모두 `\N`으로 표시되었습니다. 업그레이드 후에는 `WHERE <partition_col> IS NULL`이 Hive 기본 파티션과 올바르게 일치합니다.

:::

### Hive 트랜잭션 테이블 쿼리 {#querying-hive-transactional-tables}

Hive 트랜잭션 테이블은 ACID 의미를 지원합니다. 자세한 내용은 [Hive Transactions](https://cwiki.apache.org/confluence/display/Hive/Hive+Transactions)를 참조하세요.

* Hive 트랜잭션 테이블 지원 현황

  | 테이블 유형 | Hive에서 지원되는 작업 | Hive 테이블 속성 | 지원되는 Hive 버전 |
  | ------------------------------- | ----------------------------------- | ------------------------------------------------------------------- | ---------------------------------------------------------------- |
  | Full-ACID 트랜잭션 테이블 | Insert, Update, Delete 지원 | `'transactional'='true'` | 4.x, 3.x, 2.x(2.x에서는 읽기 전에 Hive에서 Major Compaction 필요) |
  | Insert-Only 트랜잭션 테이블 | Insert만 지원 | `'transactional'='true'`, `'transactional_properties'='insert_only'` | 4.x, 3.x, 2.x(Catalog를 만들 때 `hive.version` 지정) |

* 현재 제한 사항

  Original Files가 있는 경우는 지원되지 않습니다. 테이블을 트랜잭션 테이블로 변환하면 새 데이터 파일에는 Hive 트랜잭션 테이블 스키마가 적용되지만 기존 데이터 파일은 변환되지 않습니다. 이러한 기존 파일을 Original Files라고 합니다.

### Hive 뷰 쿼리 {#querying-hive-views}

Hive 뷰를 쿼리할 수 있지만 다음과 같은 제한이 있습니다.

* Hive 뷰 정의(HiveQL)는 Doris가 지원하는 SQL 문과 호환되어야 합니다. 그렇지 않으면 파싱 오류가 발생합니다.

* HiveQL에서 지원하는 일부 함수는 Doris의 함수와 이름은 같지만 동작이 다를 수 있습니다. 이 경우 Hive와 Doris의 결과가 달라질 수 있습니다. 이런 문제가 발생하면 커뮤니티에 보고해 주세요.

### 관련 매개변수 {#related-parameters}

* 세션 변수

| 매개변수 이름 | 기본값 | 설명 | 지원 시작 버전 |
| ----------| ---- | ---- | --- |
| `hive_parquet_use_column_names` | `true` | Doris가 Hive 테이블의 Parquet 데이터를 읽을 때 기본적으로 Hive 테이블의 열 이름과 같은 이름의 열을 Parquet 파일에서 찾아 데이터를 읽습니다. 이 변수가 `false`이면 열 이름과 관계없이 Hive 테이블의 열 순서에 따라 Parquet 파일에서 데이터를 읽습니다. Hive의 `parquet.column.index.access` 변수와 비슷합니다. 이 매개변수는 최상위 열 이름에만 적용되며 Struct 내부에는 적용되지 않습니다. | 2.1.6+, 3.0.3+ |
| `hive_orc_use_column_names` | `true` | `hive_parquet_use_column_names`와 비슷하며 Hive 테이블의 ORC 데이터에 적용됩니다. Hive의 `orc.force.positional.evolution` 변수와 비슷합니다. | 2.1.6+, 3.0.3+ |

## 쓰기 작업 {#write-operations}

INSERT 문을 사용하여 Hive 테이블에 데이터를 쓸 수 있습니다. Doris가 만든 Hive 테이블과 호환되는 형식의 기존 Hive 테이블을 지원합니다.

파티션 테이블에서는 데이터에 따라 해당 파티션에 자동으로 기록하거나 새 파티션을 만듭니다. 4.1.5부터 `PARTITION (column = literal)`을 사용한 정적 파티션과 정적·동적 파티션 열의 혼합을 지원합니다. 정적 파티션 열은 INSERT 대상 열 목록 및 SELECT 또는 VALUES 출력에서 제외하고, 나머지 동적 파티션 열은 입력 데이터에 포함하세요.

### INSERT INTO {#insert-into}

INSERT 작업은 대상 테이블에 데이터를 추가합니다.

```sql
INSERT INTO hive_tbl VALUES (val1, val2, val3, val4);
INSERT INTO hive_ctl.hive_db.hive_tbl SELECT col1, col2 FROM internal.db1.tbl1;

INSERT INTO hive_tbl(col1, col2) VALUES (val1, val2);
INSERT INTO hive_tbl(col1, col2, partition_col1, partition_col2) VALUES (1, 2, "beijing", "2023-12-12");
```

4.1.5부터 정적 파티션이나 정적 파티션과 동적 파티션의 혼합 쓰기를 지원합니다.

```sql
-- Full Static Partition
INSERT INTO hive_tbl PARTITION (partition_col1='2026-07-30', partition_col2='beijing')
VALUES (val1, val2);
INSERT INTO hive_tbl PARTITION (partition_col1='2026-07-30', partition_col2='beijing')
SELECT col1, col2 FROM source_table;

-- Hybrid Partition Mode: "partition_col1" is static, "partition_col2" comes from SELECT dynamically
INSERT INTO hive_tbl PARTITION (partition_col1='2026-07-30')
VALUES (val1, val2, partition_val2);
INSERT INTO hive_tbl PARTITION (partition_col1='2026-07-30')
SELECT col1, col2, partition_col2 FROM source_table;
```

### INSERT OVERWRITE {#insert-overwrite}

INSERT OVERWRITE는 테이블의 기존 데이터를 새 데이터로 완전히 교체합니다.

```sql
INSERT OVERWRITE TABLE hive_tbl VALUES (val1, val2, val3, val4);
INSERT OVERWRITE TABLE hive_ctl.hive_db.hive_tbl(col1, col2) SELECT col1, col2 FROM internal.db1.tbl1;
```

4.1.5부터 정적 파티션이나 정적 파티션과 동적 파티션의 혼합 쓰기를 지원합니다.

```sql
-- Full Static Partition
INSERT OVERWRITE TABLE hive_tbl PARTITION (partition_col1='2026-07-30', partition_col2='beijing')
VALUES (val1, val2);
INSERT OVERWRITE TABLE hive_tbl PARTITION (partition_col1='2026-07-30', partition_col2='beijing')
SELECT col1, col2 FROM source_table;

-- Hybrid Partition Mode: "partition_col1" is static, "partition_col2" comes from SELECT dynamically
INSERT OVERWRITE TABLE hive_tbl PARTITION (partition_col1='2026-07-30')
VALUES (val1, val2, partition_val2);
INSERT OVERWRITE TABLE hive_tbl PARTITION (partition_col1='2026-07-30')
SELECT col1, col2, partition_col2 FROM source_table;
```

INSERT OVERWRITE의 의미는 Hive와 같으며 다음과 같이 동작합니다.

* 대상이 파티션 테이블이고 소스 테이블이 비어 있으면 작업은 아무 효과가 없습니다. 대상 테이블은 변경되지 않습니다.

* 대상이 비파티션 테이블이고 소스 테이블이 비어 있으면 대상 테이블의 데이터가 모두 지워집니다.

* 4.1.5부터 정적 파티션을 지정한 쓰기와 정적·동적 파티션을 결합한 혼합 모드를 지원합니다. 그러나 정적 파티션을 지정해도 소스 쿼리 결과가 비어 있으면 지정한 파티션은 지워지지 않습니다.

**정적 파티션 전체 예제(4.1.5부터)**

이 페이지에 설명된 Hive Catalog를 구성하고, 기존 `hive_ctl.hive_db` 데이터베이스를 준비한 다음, 테이블 생성·쓰기·쿼리 권한을 부여하세요. 쓰기에 사용하는 Catalog에는 `fs.defaultFS`가 구성되어 있어야 합니다. 다음 예제에서는 정적 날짜와 동적 지역을 결합한 뒤, 완전히 지정된 정적 파티션 하나를 덮어씁니다.

```sql
CREATE TABLE hive_ctl.hive_db.static_write_demo (
    id INT,
    dt STRING,
    region STRING
)
ENGINE=HIVE
PARTITION BY LIST (dt, region) ()
PROPERTIES ("file_format" = "parquet");

INSERT INTO hive_ctl.hive_db.static_write_demo PARTITION (dt='2026-10-01')
VALUES (1, 'beijing'), (2, 'shanghai');

INSERT OVERWRITE TABLE hive_ctl.hive_db.static_write_demo
PARTITION (dt='2026-10-01', region='beijing') VALUES (3);

SELECT id, dt, region FROM hive_ctl.hive_db.static_write_demo ORDER BY id;
```

```text
+----+------------+----------+
| id | dt         | region   |
+----+------------+----------+
|  2 | 2026-10-01 | shanghai |
|  3 | 2026-10-01 | beijing  |
+----+------------+----------+
```

정적 파티션 값은 리터럴이어야 합니다. 동일한 파티션 키를 두 번 이상 지정하거나 명시적인 INSERT 열 목록에 정적 파티션 열을 다시 넣지 마세요. 정적 키 이름은 대소문자를 구분하지 않고 일치 여부를 확인하며, 존재하지 않는 파티션 열을 지정하면 오류가 발생합니다.

### CTAS {#ctas}

`CTAS (CREATE TABLE AS SELECT)` 문으로 Hive 테이블을 만들고 데이터를 삽입할 수 있습니다.

```sql
CREATE TABLE hive_ctas ENGINE=hive AS SELECT * FROM other_table;
```

다음과 같이 CTAS에서 파일 형식, 파티셔닝 방법 등을 지정할 수 있습니다.

```sql
CREATE TABLE hive_ctas ENGINE=hive
PARTITION BY LIST (pt1, pt2) ()
AS SELECT col1, pt1, pt2 FROM part_ctas_src WHERE col1 > 0;

CREATE TABLE hive_ctl.hive_db.hive_ctas (col1, col2, pt1) ENGINE=hive
PARTITION BY LIST (pt1) ()
PROPERTIES (
    "file_format"="parquet",
    "compression"="zstd"
)
AS SELECT col1, pt1 AS col2, pt2 AS pt1 FROM test_ctas.part_ctas_src WHERE col1 > 0;
```

### 관련 매개변수 {#related-parameters-1}

* BE 구성

  | 매개변수 이름 | 기본값 | 설명 |
  | ----------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------- | ----------- |
  | `hive_sink_max_file_size` | 1GB | 데이터 파일의 최대 크기입니다. 데이터 크기가 이 한도를 초과하면 현재 파일을 닫고 새 파일을 만들어 계속 씁니다. |
  | `table_sink_partition_write_max_partition_nums_per_writer` | 128 | BE 노드에서 각 인스턴스가 쓸 수 있는 최대 파티션 수입니다. |
  | `table_sink_non_partition_write_scaling_data_processed_threshold` | 25MB | 비파티션 테이블에서 쓰기 확장을 시작하는 데이터량 임계값입니다. 데이터가 `table_sink_non_partition_write_scaling_data_processed_threshold`만큼 추가될 때마다 새로운 writer(인스턴스)가 쓰기에 사용됩니다. 이 방식은 데이터량에 맞춰 writer(인스턴스) 수를 조정하여 동시 쓰기 처리량을 높이고, 데이터량이 적을 때는 자원을 절약하고 파일 수를 줄입니다. |
  | `table_sink_partition_write_min_data_processed_rebalance_threshold` | 25MB | 파티션 테이블에서 재균형을 시작하는 최소 데이터량 임계값입니다. `현재 누적 데이터량` - `마지막 재균형 또는 초기 누적 이후의 데이터량` >= `table_sink_partition_write_min_data_processed_rebalance_threshold`이면 재균형이 시작됩니다. 최종 파일 크기의 차이가 크다면 이 임계값을 낮춰 균형을 개선하세요. 단, 임계값을 낮추면 재균형 비용이 늘어 성능에 영향을 줄 수 있습니다. |
  | `table_sink_partition_write_min_partition_data_processed_rebalance_threshold` | 15MB | 재균형을 시작하는 최소 파티션 데이터량 임계값입니다. `현재 파티션 데이터량` >= `임계값` \* `해당 파티션에 이미 할당된 작업 수`이면 재균형이 시작됩니다. 최종 파일 크기의 차이가 크다면 이 임계값을 낮춰 균형을 개선하세요. 단, 임계값을 낮추면 재균형 비용이 늘어 성능에 영향을 줄 수 있습니다. |


## 데이터베이스 및 테이블 관리 {#database-and-table-management}

사용자는 Doris를 통해 Hive Metastore의 데이터베이스와 테이블을 만들거나 삭제할 수 있습니다. 이 작업에서 Doris는 Hive Metastore API만 호출하며, Hive 메타데이터 자체를 저장하거나 영구 보관하지 않습니다.

### 데이터베이스 만들기 및 삭제 {#creating-and-dropping-databases}

`SWITCH` 문으로 해당 Catalog로 전환한 다음 `CREATE DATABASE` 문을 실행할 수 있습니다.

```sql
SWITCH hive_ctl;
CREATE DATABASE [IF NOT EXISTS] hive_db;
```

다음과 같이 완전한 이름을 사용하거나 위치를 지정하여 데이터베이스를 만들 수도 있습니다.

```sql
CREATE DATABASE [IF NOT EXISTS] hive_ctl.hive_db;

CREATE DATABASE [IF NOT EXISTS] hive_ctl.hive_db
PROPERTIES ('location'='hdfs://172.21.16.47:4007/path/to/db/');
```

`SHOW CREATE DATABASE` 명령으로 데이터베이스의 위치 정보를 확인할 수 있습니다.

```sql
mysql> SHOW CREATE DATABASE hive_db;
+----------+---------------------------------------------------------------------------------------------+
| Database | Create Database                                                                             |
+----------+---------------------------------------------------------------------------------------------+
| hive_db  | CREATE DATABASE hive_db LOCATION 'hdfs://172.21.16.47:4007/usr/hive/warehouse/hive_db.db'   |
+----------+---------------------------------------------------------------------------------------------+
```

데이터베이스를 삭제하려면 다음을 실행합니다.

```sql
DROP DATABASE [IF EXISTS] hive_ctl.hive_db;
```

:::caution
Hive 데이터베이스를 삭제하려면 먼저 그 안의 모든 테이블을 삭제해야 합니다. 그렇지 않으면 오류가 발생합니다. 이 작업은 Hive의 해당 데이터베이스도 삭제합니다.
:::

### 테이블 만들기 및 삭제 {#creating-and-dropping-tables}

- **테이블 만들기**

  Doris는 Hive에서 파티션 테이블과 비파티션 테이블을 모두 만들 수 있습니다.

  ```sql
  -- Create unpartitioned hive table
  CREATE TABLE unpartitioned_table (
    `col1` BOOLEAN COMMENT 'col1',
    `col2` INT COMMENT 'col2',
    `col3` BIGINT COMMENT 'col3',
    `col4` CHAR(10) COMMENT 'col4',
    `col5` FLOAT COMMENT 'col5',
    `col6` DOUBLE COMMENT 'col6',
    `col7` DECIMAL(9,4) COMMENT 'col7',
    `col8` VARCHAR(11) COMMENT 'col8',
    `col9` STRING COMMENT 'col9'
  )  ENGINE=hive
  PROPERTIES (
    'file_format'='parquet'
  );

  -- Create partitioned hive table
  -- The partition columns must be in table's column definition list
  CREATE TABLE partition_table (
    `col1` BOOLEAN COMMENT 'col1',
    `col2` INT COMMENT 'col2',
    `col3` BIGINT COMMENT 'col3',
    `col4` DECIMAL(2,1) COMMENT 'col4',
    `pt1` VARCHAR COMMENT 'pt1',
    `pt2` VARCHAR COMMENT 'pt2'
  )  ENGINE=hive
  PARTITION BY LIST (pt1, pt2) ()
  PROPERTIES (
    'file_format'='orc',
    'compression'='zlib'
  );

  -- Create text format table(Since 2.1.7 & 3.0.3)
  CREATE TABLE text_table (
      `id` INT,
      `name` STRING
  ) PROPERTIES (
      'file_format'='text',
      'compression'='gzip',
      'field.delim'='\t',
      'line.delim'='\n',
      'collection.delim'=';',
      'mapkey.delim'=':',
      'serialization.null.format'='\\N',
      'escape.delim'='\\'
  );
  ```

  테이블을 만든 후 `SHOW CREATE TABLE` 명령으로 Hive 테이블 생성문을 확인할 수 있습니다.

  Hive의 테이블 생성 구문과 달리 Doris에서 Hive 파티션 테이블을 만들 때는 파티션 열을 테이블 스키마에 포함해야 합니다. 또한 파티션 열을 스키마의 끝에 동일한 순서로 배치해야 합니다.

  :::tip
  ACID 트랜잭션 기능이 기본적으로 활성화된 Hive 클러스터에서는 Doris가 만든 테이블의 `transactional` 속성이 `true`로 설정됩니다. Doris는 Hive 트랜잭션 테이블의 일부 기능만 지원하므로 직접 만든 Hive 테이블을 읽지 못하는 문제가 발생할 수 있습니다. 이를 방지하려면 테이블 속성에 `"transactional" = "false"`를 명시하여 비트랜잭션 Hive 테이블을 만드세요.

  ```sql
  CREATE TABLE non_acid_table(
    `col1` BOOLEAN COMMENT 'col1',
    `col2` INT COMMENT 'col2',
    `col3` BIGINT COMMENT 'col3'
  ) ENGINE=hive
  PROPERTIES (
    'transactional'='false'
  );
  ```
  :::

- **테이블 삭제**

  `DROP TABLE` 문으로 Hive 테이블을 삭제할 수 있습니다. 테이블을 삭제하면 파티션 데이터를 포함한 모든 데이터도 제거됩니다.

- **열 타입 매핑**

  자세한 내용은 [열 타입 매핑] 절을 참조하세요. 다음 제한 사항도 유의하세요.

  - 열은 기본 nullable 타입이어야 하며 `NOT NULL`은 지원되지 않습니다.
  - Hive 3.0은 기본값 설정을 지원합니다. 기본값을 설정하려면 Catalog 속성에 `"hive.version" = "3.0.0"`을 명시적으로 추가하세요.
  - 삽입하는 데이터의 타입이 호환되지 않으면(예: 숫자 타입에 `'abc'` 삽입) 값이 `null`로 변환됩니다.

- **파티셔닝**

  Hive의 파티션 타입은 Doris의 List 파티션에 해당합니다. 따라서 Doris에서 Hive 파티션 테이블을 만들 때는 List 파티션 구문을 사용하되, 각 파티션을 명시적으로 나열할 필요는 없습니다. Doris는 데이터를 삽입할 때 데이터 값에 따라 해당 Hive 파티션을 자동으로 만듭니다. 단일 열 및 다중 열 파티션 테이블을 지원합니다.

- **파일 형식**

  - ORC(기본값)
  - Parquet

    DATETIME 타입을 Parquet 파일에 쓸 때는 INT64 대신 INT96을 물리적 타입으로 사용합니다. 이는 Hive 4.0 이전 버전의 동작과 호환되도록 하기 위한 것입니다.

  - Text(버전 2.1.7 및 3.0.3부터 지원)

      Text 형식은 다음 테이블 속성을 지원합니다.

		  - `field.delim`: 열 구분자입니다. 기본값은 `\1`입니다.
		  - `line.delim`: 행 구분자입니다. 기본값은 `\n`입니다.
		  - `collection.delim`: 복합 타입의 요소 사이에 사용하는 구분자입니다. 기본값은 `\2`입니다.
		  - `mapkey.delim`: 맵 키와 값 사이에 사용하는 구분자입니다. 기본값은 `\3`입니다.
		  - `serialization.null.format`: `NULL` 값의 저장 형식입니다. 기본값은 `\N`입니다.
		  - `escape.delim`: 이스케이프 문자입니다. 기본값은 `\`입니다.

- **압축 형식**

  다음 코덱은 Doris를 통해 테이블을 만들고 데이터를 쓸 때 압축을 선택하는 데 적용됩니다. `plain`은 압축하지 않음을 의미합니다.

  | Doris 버전 | Parquet | ORC |
  | --- | --- | --- |
  | 4.0.x, 4.1.0–4.1.2 | `snappy`(기본값), `zstd`, `plain` | `snappy`, `zlib`(기본값), `zstd`, `plain` |
  | 4.1.3 및 이후 4.1 릴리스 | `snappy`(기본값), `zstd`, `plain`, `lz4` | `snappy`, `zlib`(기본값), `zstd`, `plain`, `lz4` |
  | 4.2.0부터(dev 포함) | `snappy`(기본값), `zstd`, `plain`, `lz4`, `gzip` | `snappy`, `zlib`(기본값), `zstd`, `plain`, `lz4` |

  Hive Text 쓰기는 `gzip`, `bzip2`, `zstd`, `lz4`, `snappy`, `plain`(기본값)을 지원합니다. 기존 파일 읽기의 압축 지원 범위는 [Text/CSV/JSON](../file-formats/text.md)을 참조하세요.

  Doris를 통해 만든 테이블에서는 `compression` 속성으로 코덱을 선택합니다. 기존 Hive 테이블에 쓸 때 Doris는 해당 파일 형식에 따라 테이블 속성 `parquet.compression`, `orc.compress`, `text.compression`을 읽습니다.

- **스토리지 매체**

  - HDFS
  - 객체 스토리지

## Hive Metastore 이벤트 구독 {#subscribing-to-hive-metastore-events}

FE 노드가 HMS의 Notification Events를 주기적으로 읽도록 하면 Doris가 Hive 테이블 메타데이터의 변경 사항을 실시간으로 감지하여 메타데이터의 최신 상태를 유지하는 데 도움이 됩니다. 현재 지원되는 이벤트는 다음과 같습니다.

| 이벤트 | 작업 및 해당 동작 |
| ---------------- | ------------------------------------------------------------------------- |
| CREATE DATABASE  | 해당 데이터 디렉터리에 데이터베이스를 만듭니다. |
| DROP DATABASE    | 해당 데이터 디렉터리에서 데이터베이스를 삭제합니다. |
| ALTER DATABASE   | 주로 데이터베이스 속성, 주석, 기본 스토리지 위치의 변경에 해당합니다. 이러한 변경은 Doris가 외부 데이터 디렉터리를 쿼리하는 데 영향을 주지 않으므로 현재 이 이벤트는 무시됩니다. |
| CREATE TABLE     | 해당 데이터베이스에 테이블을 만듭니다. |
| DROP TABLE       | 해당 데이터베이스에서 테이블을 삭제하고 테이블 캐시를 무효화합니다. |
| ALTER TABLE      | 이름이 변경되면 이전 테이블을 삭제하고 새 이름으로 테이블을 만듭니다. 그 외에는 테이블 캐시를 무효화합니다. |
| ADD PARTITION    | 해당 테이블의 캐시된 파티션 목록에 파티션을 추가합니다. |
| DROP PARTITION   | 캐시된 파티션 목록에서 파티션을 제거하고 파티션 캐시를 무효화합니다. |
| ALTER PARTITION  | 이름이 변경되면 이전 파티션을 삭제하고 새 이름으로 파티션을 만듭니다. 그 외에는 파티션 캐시를 무효화합니다. |

:::tip
1. 데이터 가져오기로 파일이 변경되면 파티션 테이블에서는 `ALTER PARTITION` 이벤트가, 비파티션 테이블에서는 `ALTER TABLE` 이벤트가 발생합니다.

2. HMS를 거치지 않고 파일 시스템을 직접 조작하면 HMS가 해당 이벤트를 생성하지 않으므로 Doris도 메타데이터 변경을 감지하지 못합니다.
:::

`fe.conf`의 다음 매개변수가 이 기능과 관련됩니다.

1. `enable_hms_events_incremental_sync`: 메타데이터 자동 증분 동기화를 활성화합니다. 기본적으로 비활성화되어 있습니다.

2. `hms_events_polling_interval_ms`: 이벤트 읽기 간격입니다. 기본값은 10000밀리초입니다.

3. `hms_events_batch_size_per_rpc`: RPC당 읽는 최대 이벤트 수입니다. 기본값은 500입니다.

이 기능을 사용하려면(Huawei Cloud MRS 제외) HMS의 `hive-site.xml`을 수정하고 HMS와 HiveServer2를 모두 다시 시작해야 합니다.

```xml
<property>
    <name>hive.metastore.event.db.notification.api.auth</name>
    <value>false</value>
</property>
<property>
    <name>hive.metastore.dml.events</name>
    <value>true</value>
</property>
<property>
    <name>hive.metastore.transactional.event.listeners</name>
    <value>org.apache.hive.hcatalog.listener.DbNotificationListener</value>
</property>
```

Huawei Cloud MRS에서는 `hivemetastore-site.xml`을 수정하고 HMS와 HiveServer2를 모두 다시 시작해야 합니다.

```xml
<property>
    <name>metastore.transactional.event.listeners</name>
    <value>org.apache.hive.hcatalog.listener.DbNotificationListener</value>
</property>
```

## 부록 {#appendix}

### 트랜잭션 메커니즘 {#transaction-mechanism}

Hive 쓰기 작업은 별도의 트랜잭션에 포함됩니다. 트랜잭션이 커밋되기 전에는 데이터가 외부에 표시되지 않습니다. 트랜잭션이 커밋된 후에야 관련 테이블 작업이 다른 사용자에게 표시됩니다.

트랜잭션은 원자성을 보장하므로 트랜잭션의 모든 작업은 함께 성공하거나 함께 실패합니다.

트랜잭션이 작업의 격리성을 완전히 보장하지는 못하지만, 파일 시스템 작업과 Hive Metastore 메타데이터 작업을 분리하여 불일치를 최소화하려고 합니다.

예를 들어 Hive 테이블의 여러 파티션을 수정하는 트랜잭션에서 작업을 두 묶음으로 나누면, 두 번째 묶음이 완료되기 전에 첫 번째 묶음이 외부에 표시될 수 있습니다. 이때 첫 번째 묶음의 파티션은 읽을 수 있지만 두 번째 묶음의 파티션은 읽을 수 없습니다.

트랜잭션 커밋 과정에서 예외가 발생하면 HDFS 파일과 Hive Metastore 메타데이터의 변경을 포함한 트랜잭션 전체가 롤백되며, 사용자가 추가로 조치할 필요는 없습니다.

### 동시 쓰기 메커니즘 {#concurrent-writing-mechanism}

현재 Apache Doris는 여러 insert 문을 사용한 동시 쓰기를 지원합니다. 다만 사용자는 동시 쓰기 간에 충돌이 발생하지 않도록 해야 합니다.

일반적인 비트랜잭션 Hive 테이블에는 완전한 트랜잭션 메커니즘이 없습니다. Apache Doris의 트랜잭션 메커니즘은 불일치가 발생할 수 있는 시간을 최소화하지만 진정한 ACID 속성을 보장하지는 못합니다. 따라서 Apache Doris에서 Hive 테이블에 동시에 쓰면 데이터 일관성 문제가 발생할 수 있습니다.

1. **동시 `INSERT` 작업**

2. `INSERT` 작업은 데이터를 추가하므로 동시에 실행해도 충돌하지 않으며 예상한 결과를 생성합니다.

3. **동시 `INSERT OVERWRITE` 작업**

4. 동일한 테이블이나 파티션에서 `INSERT OVERWRITE`를 동시에 실행하면 데이터가 손실되거나 손상되어 결과를 예측할 수 없게 될 수 있습니다.

5. 일반적인 해결 방법은 다음과 같습니다.

   * 파티션 테이블에서는 서로 다른 파티션에 데이터를 씁니다. 서로 다른 파티션에 대한 동시 작업은 충돌하지 않습니다.

   * 비파티션 테이블에서는 충돌을 피하기 위해 `INSERT OVERWRITE` 대신 `INSERT`를 사용합니다.

   * 충돌 가능성이 있는 작업은 애플리케이션 측에서 한 번에 하나의 쓰기 작업만 수행되도록 제어합니다.

### HDFS 파일 작업 {#hdfs-file-operations}

HDFS에 저장된 Hive 테이블 데이터는 일반적으로 먼저 임시 디렉터리에 쓴 다음 `rename`과 같은 파일 시스템 작업으로 확정합니다. 다음은 데이터 작업별 HDFS 파일 작업의 세부 내용입니다.

데이터의 임시 디렉터리 형식은 `/tmp/.doris_staging/<username>/<uuid>`입니다.

작성된 데이터 파일 이름의 형식은 `<query-id>_<uuid>-<index>.<compress-type>.<file-type>`입니다.

다양한 시나리오의 파일 작업 예시는 다음과 같습니다.

1. **비파티션 테이블**

   * **추가(데이터 추가)**

     * 대상 테이블 디렉터리: `hdfs://ns/usr/hive/warehouse/example.db/table1`

     * 임시 파일: `hdfs://ns/tmp/.doris_staging/root/f02247cb662846038baae272af5eeb05/b35fdbcea3a4e39-86d1f36987ef1492_7e3985bf-9de9-4fc7-b84e-adf11aa08756-0.orc`

     * 커밋 단계에서 모든 임시 파일을 대상 테이블 디렉터리로 이동합니다.

   * **덮어쓰기(데이터 교체)**

     * 대상 테이블 디렉터리: `hdfs://ns/usr/hive/warehouse/example.db/table1`

     * 임시 파일: `hdfs://ns/tmp/.doris_staging/root/f02247cb662846038baae272af5eeb05/b35fdbcea3a4e39-86d1f36987ef1492_7e3985bf-9de9-4fc7-b84e-adf11aa08756-0.orc`

     * 커밋 단계의 작업:

       1. 대상 테이블 디렉터리의 이름을 임시 디렉터리로 변경합니다: `hdfs://ns/usr/hive/warehouse/example.db/_temp_b35fdbcea3a4e39-86d1f36987ef1492_table1`

       2. 임시 디렉터리의 이름을 대상 테이블 디렉터리로 변경합니다.

       3. 임시 대상 테이블 디렉터리를 삭제합니다.

2. **파티션 테이블**

   * **추가(새 파티션에 추가)**

     * 대상 테이블 디렉터리: `hdfs://ns/usr/hive/warehouse/example.db/table2/part_col=2024-01-01`

     * 임시 파일: `hdfs://ns/tmp/.doris_staging/root/a7eac7505d7a42fdb06cb9ef1ea3e912/par1=a/d678a74d232345e0-b659e2fb58e86ffd_549ad677-ee75-4fa1-b8a6-3e821e1dae61-0.orc`

     * 커밋 단계에서 임시 디렉터리의 이름을 대상 테이블 디렉터리로 변경합니다.

   * **추가(기존 파티션에 데이터 추가)**

     * 대상 테이블 디렉터리: `hdfs://ns/usr/hive/warehouse/example.db/table2/part_col=2024-01-01`

     * 임시 파일: `hdfs://ns/tmp/.doris_staging/root/a7eac7505d7a42fdb06cb9ef1ea3e912/par1=a/d678a74d232345e0-b659e2fb58e86ffd_549ad677-ee75-4fa1-b8a6-3e821e1dae61-0.orc`

     * 커밋 단계에서 임시 디렉터리의 파일을 대상 테이블 디렉터리로 이동합니다.

   * **덮어쓰기(기존 파티션 교체)**

     * 대상 테이블 디렉터리: `hdfs://ns/usr/hive/warehouse/example.db/table2/part_col=2024-01-01`

     * 임시 파일: `hdfs://ns/tmp/.doris_staging/root/a7eac7505d7a42fdb06cb9ef1ea3e912/par1=a/d678a74d232345e0-b659e2fb58e86ffd_549ad677-ee75-4fa1-b8a6-3e821e1dae61-0.orc`

     * 커밋 단계의 작업:

       1. 대상 파티션 디렉터리의 이름을 임시 파티션 디렉터리로 변경합니다: `hdfs://ns/usr/hive/warehouse/example.db/table2/_temp_d678a74d232345e0-b659e2fb58e86ffd_part_col=2024-01-01`

       2. 임시 파티션 디렉터리의 이름을 대상 파티션 디렉터리로 변경합니다.

       3. 임시 대상 파티션 디렉터리를 삭제합니다.
