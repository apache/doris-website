Doris는 다양한 메타데이터 서비스를 통해 Iceberg 테이블 데이터에 접근할 수 있습니다. 데이터 읽기뿐 아니라 INSERT, INSERT OVERWRITE, UPDATE, DELETE, MERGE INTO를 포함한 Iceberg 테이블 쓰기도 지원합니다.

[Apache Doris와 Apache Iceberg 빠르게 시작하기](../best-practices/doris-iceberg.md).

:::tip
Hive Catalog를 통해 Hive Metastore를 메타데이터 서비스로 사용하는 Iceberg 테이블에 접근할 수 있습니다. 다만 일부 호환성 문제를 방지하려면 Iceberg Catalog를 직접 사용하는 것이 좋습니다.
:::

## 활용 시나리오 {#applicable-scenarios}

| 시나리오    | 설명                                                                 |
| ----------- | --------------------------------------------------------------------------- |
| 쿼리 가속 | Doris의 분산 컴퓨팅 엔진으로 Iceberg 데이터에 직접 접근하여 쿼리 속도를 높입니다.      |
| 데이터 통합  | Iceberg 데이터를 읽어 Doris 내부 테이블에 쓰거나, Doris 컴퓨팅 엔진으로 ZeroETL 작업을 수행합니다. |
| 데이터 다시 쓰기   | Doris가 지원하는 모든 데이터 소스의 데이터를 처리하고 Iceberg 테이블 스토리지에 다시 씁니다.       |

## Catalog 구성 {#configuring-catalog}

### 구문 {#syntax}

```sql
CREATE CATALOG [IF NOT EXISTS] catalog_name PROPERTIES (
    'type' = 'iceberg',
    'iceberg.catalog.type' = '<iceberg_catalog_type>',
    'warehouse' = '<warehouse>', --optional
    {MetaStoreProperties},
    {StorageProperties},
    {IcebergProperties},
    {CommonProperties}
);
```

* `<iceberg_catalog_type>`

  Iceberg Catalog의 유형으로, 다음 옵션을 지원합니다.

  * `hms`: Hive Metastore를 메타데이터 서비스로 사용합니다.

  * `rest`: Iceberg Rest Catalog 인터페이스와 호환되는 메타데이터 서비스입니다.

  * `hadoop`: 파일 시스템에 저장된 메타데이터에 직접 접근합니다.

  * `glue`: AWS Glue를 메타데이터 서비스로 사용합니다.

  * `dlf`: Alibaba Cloud DLF를 메타데이터 서비스로 사용합니다.

  * `jdbc`: Iceberg JDBC Catalog를 메타데이터 서비스로 사용합니다.

  * `s3tables`: AWS S3 Tables Catalog를 사용하여 [S3 Table Bucket](https://aws.amazon.com/s3/features/tables/)에 접근합니다.

* `<warehouse>`

  Iceberg의 웨어하우스 경로입니다. 이 매개변수는 `<iceberg_catalog_type>`이 `hadoop`일 때 반드시 지정해야 합니다.

  `warehouse` 경로는 `Database` 경로의 상위 수준을 가리켜야 합니다. 예를 들어 테이블 경로가 `s3://bucket/path/to/db1/table1`이면 `warehouse`는 `s3://bucket/path/to/`여야 합니다.

* `{MetaStoreProperties}`

  MetaStoreProperties에는 Metastore 메타데이터 서비스의 연결 및 인증 정보를 입력합니다. [지원되는 메타데이터 서비스] 섹션을 참조하세요.

* `{StorageProperties}`

  StorageProperties에는 스토리지 시스템의 연결 및 인증 정보를 입력합니다. [지원되는 스토리지 시스템] 섹션을 참조하세요.

* `{IcebergProperties}`

  IcebergProperties에는 Iceberg Catalog 전용 매개변수를 입력합니다.

    - `list-all-tables`

        Hive Metastore를 메타데이터 서비스로 사용하는 Iceberg Catalog에 적용됩니다. 기본값은 `true`입니다. 기본적으로 `SHOW TABLES` 작업은 현재 데이터베이스에 있는 모든 유형의 테이블을 나열합니다(Hive Metastore에는 Iceberg 이외 유형의 테이블도 저장될 수 있습니다). 이 방식의 성능이 가장 좋습니다.

        `false`로 설정하면 Doris가 각 테이블의 유형을 하나씩 확인하여 Iceberg 유형의 테이블만 반환합니다. 이 모드는 테이블이 많을 때 성능이 떨어집니다.

    - `iceberg.rest.view-enabled`

        버전 4.0.6부터 지원됩니다.

        Iceberg REST Catalog에만 적용됩니다. 뷰 관련 작업(`listViews`, `loadView`, `viewExists`, `dropView` 등)의 활성화 여부를 지정합니다. 기본값은 `true`입니다.

        일부 Iceberg REST Catalog 구현은 테이블 API를 제공하지만 뷰 API는 사용할 수 없거나 오류를 반환합니다. `SHOW TABLES`를 실행할 때 Doris는 `ViewCatalog.listViews()`를 호출하여 테이블 목록에서 뷰를 제외하므로, 이러한 REST 서비스에서는 `SHOW TABLES`와 테이블 메타데이터 로딩이 실패할 수 있습니다.

        이 경우 이 매개변수를 `false`로 설정하면 Doris가 모든 뷰 관련 작업을 건너뛰어 `SHOW TABLES`와 같은 메타데이터 작업을 정상적으로 수행할 수 있습니다.

* `{CommonProperties}`

  CommonProperties에는 일반 속성을 입력합니다. 공통 속성에 대한 자세한 내용은 [Catalog 개요](../catalog-overview.md)를 참조하세요.

## 메타데이터 캐시 {#meta-cache}

Apache Doris는 외부 데이터 소스에 접근하는 성능을 높이기 위해 Iceberg 메타데이터를 캐시합니다. 메타데이터에는 테이블 구조(Schema), 테이블 객체, 스냅샷, 뷰 객체, manifest 세부 정보가 포함됩니다.

:::tip
Doris 4.1.x 이전 버전에서는 주로 FE 구성 항목으로 메타데이터 캐시를 전역 제어합니다. 자세한 내용은 [메타데이터 캐시](../meta-cache.md)를 참조하세요.
Doris 4.1.x부터는 통합된 `meta.cache.*` 키로 Iceberg Catalog의 외부 메타데이터 캐시를 구성합니다.
:::

### 캐시 속성 구성(4.1.x+) {#meta-cache-unified-model}

각 엔진의 캐시 항목은 통합된 구성 키 형식인 `meta.cache.<engine>.<entry>.{enable,ttl-second,capacity,max-weight}`를 사용합니다. 메모리 제한은 메모리 사용량 추정 기능이 있는 항목에만 적용됩니다. [외부 메타데이터 캐시 메모리 관리](../external-meta-cache-memory-management)를 참조하세요.

| 속성 | 예시 | 의미 |
|---|---|---|
| `enable` | `true/false` | 이 캐시 모듈을 활성화할지 여부입니다. |
| `ttl-second` | `600`, `0`, `-1` | `0`은 캐시 비활성화를 의미하며 즉시 적용됩니다(최신 데이터를 확인하는 데 사용할 수 있음). `-1`은 만료되지 않음을 의미합니다. 그 외 양의 정수는 접근 시간을 기준으로 한 TTL(초)을 의미합니다. |
| `capacity` | `10000` | 캐시 항목의 최대 개수입니다. `max-weight`가 활성화된 경우 개수 제한을 동시에 적용하지 않지만, `0`으로 설정하면 여전히 캐시가 비활성화됩니다. |
| `max-weight` | `1GB` | Doris 4.1.4부터 지원됩니다. 선택적으로 설정하는 예상 유지 메모리 한도입니다. Iceberg의 `table`, `snapshot`, `manifest`가 지원하며, `0`으로 설정하면 해당 항목이 비활성화됩니다. |

**적용 조건:** 모듈 캐시는 `enable=true`, `ttl-second != 0`, `capacity > 0`이고, `max-weight`가 설정되지 않았거나 `0`이 아닐 때 적용됩니다.

### 캐시 모듈 {#meta-cache-unified-modules}

Iceberg Catalog에는 다음 캐시 모듈이 포함됩니다.

| 모듈(`<entry>`) | 속성 키 접두사 | 캐시 내용 및 영향 |
|---|---|---|
| `schema` | `meta.cache.iceberg.schema.` | 테이블 구조를 캐시합니다. 영향: 테이블 컬럼 정보의 가시성에 영향을 줍니다. 비활성화하면 쿼리마다 최신 Schema를 가져옵니다. |
| `table` | `meta.cache.iceberg.table.` | Iceberg 테이블 메타데이터 객체를 캐시합니다. 영향: Catalog/Metastore 왕복 요청을 줄입니다. |
| `snapshot` | `meta.cache.iceberg.snapshot.` | 스냅샷 메타데이터와 유지 중인 테이블 세대를 캐시합니다. 영향: 스냅샷과 파티션 프로젝션의 반복 로딩을 줄입니다. 이 항목은 `max-weight`를 지원합니다. |
| `view` | `meta.cache.iceberg.view.` | Iceberg 뷰 메타데이터 객체를 캐시합니다. |
| `manifest` | `meta.cache.iceberg.manifest.` | manifest 세부 정보를 캐시합니다. 영향: manifest에 반복 접근하는 오버헤드를 줄입니다. 참고: 이 모듈은 기본적으로 비활성화되어 있으므로 수동으로 활성화해야 합니다. |

### 기존 매개변수 매핑 및 변환 {#meta-cache-mapping}

버전 4.1.x 이상에서는 통합 키를 사용하는 것이 좋습니다. 다음은 기존 Catalog 속성과 4.1.x+ 통합 키 사이의 매핑입니다.

| 기존 속성 키 | 4.1.x+ 통합 키 | 설명 |
|---|---|---|
| `schema.cache.ttl-second` | `meta.cache.iceberg.schema.ttl-second` | 테이블 구조 캐시의 만료 시간 |

### 모범 사례 {#meta-cache-best-practices}

* **최신 데이터에 실시간 접근**: 쿼리마다 Iceberg 테이블의 최신 스냅샷이나 스키마 변경 사항을 확인하려면 `ttl-second`를 `schema` 또는 `table`에 대해 `0`으로 설정할 수 있습니다.
  ```sql
  -- Disable table object cache to detect snapshot changes
  ALTER CATALOG iceberg_ctl SET PROPERTIES ("meta.cache.iceberg.table.ttl-second" = "0");
  ```
* **성능 최적화**:
    * manifest 캐시를 활성화하면 대형 테이블의 쿼리 계획 수립 속도를 크게 높일 수 있습니다.
      ```sql
      ALTER CATALOG iceberg_ctl SET PROPERTIES (
        "meta.cache.iceberg.manifest.enable" = "true",
        "meta.cache.iceberg.manifest.ttl-second" = "600"
      );
      ```
    * Doris 4.1.4부터는 Catalog 속성 변경이 성공하면 Catalog 실행 컨텍스트가 초기화되고, 해당 Catalog가 라우팅하는 모든 메타데이터 캐시 엔진에서 초기화된 항목이 삭제됩니다. Doris는 다음 접근 시 새 컨텍스트와 구성으로 항목을 다시 생성합니다. 실행 중인 쿼리는 영향을 받지 않습니다.

### 관측 가능성 {#meta-cache-unified-observability}

캐시 메트릭은 `information_schema.catalog_meta_cache_statistics` 시스템 테이블에서 확인할 수 있습니다.

```sql
SELECT catalog_name, engine_name, entry_name,
       effective_enabled, ttl_second, capacity,
       estimated_size, hit_rate, load_failure_count, last_error
FROM information_schema.catalog_meta_cache_statistics
WHERE catalog_name = 'iceberg_ctl' AND engine_name = 'iceberg'
ORDER BY entry_name;
```

이 시스템 테이블의 문서인 [catalog_meta_cache_statistics](../../admin-manual/system-tables/information_schema/catalog_meta_cache_statistics.md)를 참조하세요.

### 메타데이터 및 읽기 오류(4.1.5부터) {#metadata-and-read-errors-since-415}

- `DESCRIBE`, `SHOW COLUMNS`, `SHOW CREATE TABLE`은 현재 Iceberg 스키마의 필수/선택 선언을 보존합니다. 스캔은 스키마 진화로 인해 누락된 필드도 계속 처리합니다. NOT NULL 선언이 표시되더라도 모든 과거 파일에 해당 필드가 존재한다는 의미는 아닙니다.
- 매핑할 수 없는 유형을 포함하는 과거 파티션 사양은 일반 읽기와 행 수준 DML에 서로 다른 영향을 줄 수 있습니다. `DELETE` 또는 `UPDATE`는 Iceberg Row ID를 구성하지 못하고 `Cannot produce Iceberg row IDs with unsupported partition types in spec ...` 오류로 실패할 수 있습니다. 행 수준 변경을 수행하기 전에 테이블 형식에서 지원하는 쓰기 도구로 과거 데이터 파일을 다시 작성하세요.
- 커밋된 스냅샷이 참조하는 데이터 파일이나 삭제 파일이 누락되면 `ignore_not_found_file_in_external_table=true`인 경우에도 쿼리가 실패합니다. 누락된 객체를 복원하거나 파일이 모두 존재하는 유효한 스냅샷을 선택하세요.
- `schema.name-mapping.default`는 유효한 Iceberg Name Mapping JSON 배열이어야 합니다. 값이 유효하지 않으면 현재 컬럼 이름으로 대체하여 NULL을 반환하는 대신 데이터 스캔이 실패합니다. Spark와 같은 쓰기 도구로 속성을 수정하거나 제거한 다음 Doris에서 테이블을 새로 고치세요. 메타데이터 시스템 테이블 쿼리는 이 데이터 스캔 검증을 수행하지 않습니다.

### 지원되는 Iceberg 형식 {#supported-iceberg-formats}

* Iceberg V1/V2 형식을 지원합니다.
* Position Delete와 Equality Delete 읽기를 지원합니다.
* Deletion Vector 읽기를 지원합니다(4.1.0부터).

버전 4.1.4부터는 데이터 파일(split)별로 파일 형식을 결정하므로, **Parquet와 ORC 데이터 파일이 함께 있는 단일 Iceberg 테이블도 정상적으로 쿼리할 수 있습니다**. 테이블 수준의 `write.format.default` 속성이 설정되지 않은 경우, 데이터 파일을 조사하여 형식을 추론하는 대신 기본 형식인 `parquet`을 사용합니다.

버전 4.1.4부터는 모든 split에 Iceberg identity 파티션 메타데이터가 전달되며, 경로 파티션 키에는 모든 파티션 사양에 공통으로 포함된 identity 컬럼만 들어갑니다. 따라서 **파티션 진화**를 거친 테이블에서도 파티션 컬럼 값이 올바르게 반환됩니다.

## 컬럼 유형 매핑 {#column-type-mapping}

Doris 4.2의 전체 매핑 표, 정밀도 규칙, 지원되지 않는 유형에 대해서는 [Iceberg에서 Doris로의 데이터 유형 매핑](iceberg-catalog/doris-type-mapping.md)을 참조하세요.

### 컬럼 이름의 대소문자 {#column-name-case}

Doris는 Iceberg 테이블 컬럼 이름의 원래 대소문자를 보존하고, 읽을 때는 대소문자를 구분하지 않고 컬럼을 매칭합니다. 대문자가 포함되거나 대소문자가 섞인 컬럼 이름(예: `UserId` 또는 `ORDER_ID`)도 정상적으로 쿼리할 수 있습니다.

:::info 버전 참고 사항

4.0.8 이전 버전에서는 읽을 때 정확히 일치하는 이름으로 컬럼을 찾았으므로, 컬럼 이름에 대소문자가 섞인 Iceberg 및 Paimon 테이블에서 잘못된 컬럼을 읽거나 쿼리가 실패할 수 있었습니다. 이 문제는 4.0.8에서 수정되었습니다.

:::

## Namespace 매핑 {#namespace-mapping}

Iceberg의 메타데이터 계층은 Catalog -> Namespace -> Table입니다. Namespace는 여러 수준으로 구성될 수 있습니다(Nested Namespace).

```
      ┌─────────┐             
      │ Catalog │             
      └────┬────┘             
           │                  
     ┌─────┴─────┐            
  ┌──▼──┐     ┌──▼──┐         
  │ NS1 │     │ NS2 │         
  └──┬──┘     └──┬──┘         
     │           │            
┌────▼───┐    ┌──▼──┐         
│ Table1 │    │ NS3 │         
└────────┘    └──┬──┘         
                 │            
          ┌──────┴───────┐    
     ┌────▼───┐     ┌────▼───┐
     │ Table2 │     │ Table3 │
     └────────┘     └────────┘
```


버전 3.1.2부터 Doris는 Iceberg Rest Catalog에서 Nested Namespace 매핑을 지원합니다.

위 예제의 테이블은 다음 규칙에 따라 Doris 메타데이터로 매핑됩니다.

| Catalog | 데이터베이스 | 테이블 |
| --- | --- | --- |
| Catalog | NS1 | Table1 |
| Catalog | NS2.NS3 | Table2 |
| Catalog | NS2.NS3 | Table3 |

Nested Namespace 지원은 명시적으로 활성화해야 합니다. 자세한 내용은 [Iceberg Rest Catalog](../metastores/iceberg-rest.md)를 참조하세요.

### Iceberg Rest Catalog {#iceberg-rest-catalog}

:::caution 동작 변경(4.1.4)

버전 4.1.4부터 `iceberg.rest.signing-name`을 `glue`, `s3tables`, `osstables`와 같은 관리형 서명 서비스로 설정할 때는 `'iceberg.rest.sigv4-enabled' = 'true'`도 **반드시** 설정해야 합니다. 그렇지 않으면 다음 오류와 함께 Catalog 생성이 실패합니다.

```text
Rest Catalog requires sigv4-enabled set to true when signing-name is <name>
```

기존 Catalog에서 `signing-name`만 설정하고 `sigv4-enabled`를 활성화하지 않은 경우, 업그레이드 후 검증이 실패하므로 해당 속성을 추가해야 합니다.

:::

#### Alibaba Cloud OSS Tables {#alibaba-cloud-oss-tables}

> 버전 4.1.4부터 지원됩니다.

`iceberg.rest.signing-name`은 Alibaba Cloud OSS Tables에 연결하기 위한 새 값인 `osstables`를 지원합니다. 이 경우 REST 요청 서명에는 OSS 자격 증명(`oss.access_key`, `oss.secret_key`, `oss.session_token`)을 재사용하며 `s3.*` 자격 증명은 사용하지 않습니다.

```sql
CREATE CATALOG iceberg_osstables PROPERTIES (
    'type' = 'iceberg',
    'iceberg.catalog.type' = 'rest',
    'iceberg.rest.uri' = '<oss_tables_rest_endpoint>',
    'warehouse' = '<your-catalog-name>',
    'iceberg.rest.sigv4-enabled' = 'true',
    'iceberg.rest.signing-name' = 'osstables',
    'iceberg.rest.signing-region' = '<region>',
    'oss.access_key' = '<ak>',
    'oss.secret_key' = '<sk>',
    'oss.endpoint' = 'oss-<region>.aliyuncs.com',
    'oss.region' = '<region>'
);
```

`osstables`를 사용할 때는 `iceberg.rest.signing-region`과 `iceberg.rest.sigv4-enabled = 'true'`가 모두 필요합니다. 그렇지 않으면 다음 오류가 발생합니다.

```text
Rest Catalog requires signing-region and sigv4-enabled set to true when signing-name is osstables
```

## 쿼리 작업 {#query-operations}

### 기본 쿼리 {#basic-query}

```sql
-- 1. switch to catalog, use database and query
SWITCH iceberg;
USE iceberg_db;
SELECT * FROM iceberg_tbl LIMIT 10;

-- 2. use iceberg database directly
USE iceberg.iceberg_db;
SELECT * FROM iceberg_tbl LIMIT 10;

-- 3. use full qualified name to query
SELECT * FROM iceberg.iceberg_db.iceberg_tbl LIMIT 10;
```

### 타임 트래블 {#time-travel}

Iceberg 테이블의 특정 스냅샷을 읽을 수 있습니다.

기본적으로 읽기 요청은 최신 스냅샷 버전에 접근합니다.

`$snapshots` 시스템 테이블을 사용하여 Iceberg 테이블의 스냅샷을 쿼리할 수 있습니다.

:::caution 동작 변경(4.1.4)

버전 4.1.4부터 `iceberg_meta()` 테이블 함수가 제거되었습니다. 대신 Iceberg 시스템 테이블(예: `iceberg_tbl$snapshots`)을 사용하여 메타데이터를 쿼리하세요. 아래 [시스템 테이블](#system-tables) 섹션을 참조하세요.

:::


`FOR TIME AS OF` 및 `FOR VERSION AS OF` 절을 사용하면 스냅샷 ID 또는 스냅샷 생성 시각을 기준으로 과거 데이터를 읽을 수 있습니다. 다음은 몇 가지 예입니다.

```sql
-- Read data as of a specific timestamp
SELECT * FROM iceberg_table FOR TIME AS OF '2023-01-01 00:00:00';

-- Read data as of a specific snapshot ID
SELECT * FROM iceberg_table FOR VERSION AS OF 123456789;
```

4.1.5부터 `FOR TIME AS OF`는 `yyyy-MM-dd HH:mm:ss` 뒤에 1~9자리의 소수 초를 허용하며, 값을 세션 시간대로 해석한 후 밀리초로 변환하여 스냅샷을 선택합니다. 예를 들어 `FOR TIME AS OF '2024-01-01 12:00:00.123456'`를 사용할 수 있습니다. 스냅샷 선택 정밀도는 밀리초입니다. 이 구문을 허용한다고 해서 나노초 단위의 스냅샷 시각이 보존되는 것은 아닙니다.

Doris 4.1.5에서는 컬럼 이름 변경, 삭제, 유형 승격, 파티션 진화 이후의 과거 스냅샷 읽기도 수정되었습니다. 각 파일은 현재 파티션 사양만 사용하는 대신 작성 당시 적용되던 파티션 사양으로 해석됩니다. 과거 데이터를 조회하는 쿼리는 현재 구체화된 뷰를 읽도록 재작성되어서는 안 됩니다.

### 브랜치와 태그 {#branch-and-tag}

> 3.1.0부터 지원됩니다.
>
> 브랜치와 태그의 생성, 삭제 및 관리는 [브랜치 및 태그 관리] 섹션을 참조하세요.

Iceberg 테이블의 특정 브랜치와 태그 읽기를 지원합니다.

Spark/Trino 등의 시스템과 호환되도록 여러 구문 형식을 지원합니다.

```sql
-- BRANCH
SELECT * FROM iceberg_tbl@branch(branch1);
SELECT * FROM iceberg_tbl@branch("name" = "branch1");
SELECT * FROM iceberg_tbl FOR VERSION AS OF 'branch1';

-- TAG
SELECT * FROM iceberg_tbl@tag(tag1);
SELECT * FROM iceberg_tbl@tag("name" = "tag1");
SELECT * FROM iceberg_tbl FOR VERSION AS OF 'tag1';
```

`FOR VERSION AS OF` 구문에서는 Doris가 매개변수가 타임스탬프인지 브랜치/태그 이름인지 자동으로 판단합니다.

### 뷰 {#view}

> 3.1.0부터 지원

Iceberg 뷰 쿼리를 지원합니다. 뷰 쿼리는 일반 테이블 쿼리와 동일하게 작동합니다. 다음 사항에 유의하세요.

### Iceberg V3 숨겨진 컬럼(Row Lineage) {#iceberg-v3-hidden-columns-row-lineage}

:::tip
실험적 기능으로, 버전 4.1.0부터 지원됩니다.
:::

Doris는 Iceberg V3 테이블의 Row Lineage 숨겨진 컬럼 쿼리를 지원합니다. Iceberg V3에는 데이터 변경 기록을 추적하는 데 쓰이는 행 계보 데이터가 담긴 시스템 숨겨진 컬럼이 도입되었습니다. 증분 동기화나 데이터 감사에 적합합니다.

- `_row_id`: 데이터 행을 고유하게 식별하는 숫자 값입니다(데이터가 기록된 파일과 위치를 기반으로 생성됨).
- `_last_updated_sequence_number`: 이 행이 마지막으로 수정된 Sequence Number입니다. `UPDATE` 또는 `MERGE INTO` 작업으로 데이터를 갱신하면 이 숫자 값은 버전 번호와 함께 자동으로 증가합니다.

**숨겨진 컬럼 쿼리 방법:**

기본적으로 숨겨진 컬럼은 `DESC` 또는 `SELECT *`를 사용할 때 표시되지 않습니다. 컬럼 이름을 직접 지정하여 명시적으로 쿼리할 수 있습니다.

```sql
SELECT id, _row_id, _last_updated_sequence_number FROM iceberg_tbl;
```

숨겨진 컬럼을 일반적인 표시 결과(예: `DESC` 및 `SELECT *`)에도 포함하려면 세션 변수 `show_hidden_columns`를 활성화하면 됩니다.

```sql
SET show_hidden_columns = true;
DESC iceberg_tbl;
```

**참고 사항:**

1. 이러한 행 수준 매개변수가 생성되려면 Iceberg 테이블의 형식 버전(`format-version`)을 `3`으로 구성해야 합니다. V1 및 V2 형식 테이블에서 행 계보 컬럼을 쿼리하면 오류가 발생할 수 있습니다.
2. 숨겨진 컬럼은 시스템이 관리합니다. 사용자는 `_row_id` 또는 `_last_updated_sequence_number` 컬럼을 `INSERT`와 같은 쓰기 문에서 명시적으로 지정하거나 해당 컬럼에 쓸 수 없습니다. 버전 4.1.4부터는 `INSERT` 문의 컬럼 목록에 행 계보 컬럼을 지정하면, `format-version >= 3`인 테이블에서 `Cannot specify row lineage column '<name>' in INSERT statement` 오류와 함께 즉시 실패합니다.

### Iceberg V3 기본값 {#iceberg-v3-default-values}

> 버전 4.1.4부터 지원됩니다.

Iceberg V3는 두 종류의 컬럼 기본값을 정의하며, Doris는 두 종류 모두 지원합니다.

- `initial-default`: 컬럼이 추가될 때 **기존 과거 데이터**에 부여되는 기본값입니다. 컬럼이 존재하기 전에 작성된 이전 데이터 파일을 읽을 때 Doris는 NULL 대신 이 기본값을 반환합니다. Parquet와 ORC 모두에서 지원하며, 최상위 컬럼, `STRUCT` 내부의 중첩 하위 필드, 전체가 누락된 복합 상위 컬럼에 적용됩니다. 조건식 평가 시에도 적용됩니다.
- `write-default`: 쓰기 시 **지정되지 않은 컬럼**에 채워지는 기본값입니다. `INSERT INTO t (subset of columns) VALUES (...)`를 사용하면 목록에 없는 컬럼에는 현재 `write-default`가 기록됩니다(이전 버전에서는 NULL을 기록함).

**DDL로 기본값 지정:**

```sql
ALTER TABLE iceberg_tbl ADD COLUMN c1 INT DEFAULT 10;
```

이 문은 Iceberg의 `write-default`와 `initial-default`를 모두 설정합니다. **테이블의 `format-version`이 `3`이어야 합니다**. V1 및 V2 테이블은 NULL이 아닌 기본값이 있는 컬럼을 지원하지 않습니다.

**`DEFAULT()` 표현식:**

버전 4.1.4부터 DML에서 컬럼의 기본값을 명시적으로 참조할 수 있는 `DEFAULT(<column>)` 표현식을 사용할 수 있습니다. `INSERT`, `UPDATE ... SET`, `MERGE INTO`의 각 분기에서 사용할 수 있습니다.

```sql
INSERT INTO iceberg_tbl VALUES (1, DEFAULT(c1));

UPDATE iceberg_tbl SET c1 = DEFAULT(c1) WHERE id = 1;

MERGE INTO iceberg_tbl t USING src s ON t.id = s.id
WHEN NOT MATCHED THEN INSERT VALUES (s.id, DEFAULT(c1));
```

동작 의미:

- 대상이 Iceberg 테이블인 경우 `DEFAULT()`는 이번 쓰기에 고정된 Iceberg 스키마를 기준으로 해석됩니다. 쓰기 대상에 속하지 않는 컬럼을 참조하면 `DEFAULT(<col>) must reference a column in the pinned Iceberg write target` 오류가 발생합니다.
- Iceberg 이외의 컬럼에는 해당 컬럼의 기본값을 사용합니다. 컬럼에 기본값이 없고 NOT NULL이거나 자동 증가 컬럼이면 `Column '<name>' has no default value and does not allow NULL or column is auto-increment` 오류가 발생합니다. NULL을 허용하는 컬럼에 기본값이 없으면 NULL을 사용합니다.
- 기타 오류: `DEFAULT requires a column reference, but got: <expr>`, `Cannot find column information for DEFAULT(<name>)`, `DEFAULT cannot be used on generated column '<name>'`.

:::info 참고

Iceberg의 `write-default`는 쓰기 측 커넥터의 개념입니다. `DESCRIBE`, `SHOW CREATE TABLE`, `information_schema.columns.COLUMN_DEFAULT`에는 **노출되지 않습니다**.

:::

## 시스템 테이블 {#system-tables}

> 3.1.0부터 지원

Doris는 Iceberg 시스템 테이블을 쿼리하여 테이블의 메타데이터 정보를 가져오는 기능을 지원합니다. 시스템 테이블을 사용하면 스냅샷 이력, manifest 파일, 데이터 파일, 파티션 및 기타 메타데이터를 확인할 수 있습니다.

Iceberg 테이블의 메타데이터에 접근하려면 테이블 이름 뒤에 `$` 기호와 시스템 테이블 이름을 붙입니다.

```sql
SELECT * FROM iceberg_table$system_table_name;
```

예를 들어 테이블의 이력을 보려면 다음을 실행합니다.

```sql
SELECT * FROM iceberg_table$history;
```

> `all_manifests` 시스템 테이블은 버전 4.0.4부터 지원됩니다.
>
> `position_deletes` 시스템 테이블은 버전 4.1.4부터 지원됩니다.

:::caution 동작 변경(4.1.4)

버전 4.1.4부터 Iceberg 시스템 테이블은 네이티브 실행 경로(`FileQueryScanNode` -> `IcebergScanNode`)로 쿼리되며, `iceberg_meta()` 테이블 함수는 **제거되었습니다**. 대신 `<table>$<system_table_name>` 시스템 테이블 구문을 사용하세요. [ICEBERG_META](../../sql-manual/sql-functions/table-valued-functions/iceberg-meta.md)를 참조하세요.

시스템 테이블 자체의 접근 구문과 반환 결과는 변경되지 않았습니다. 또한 시스템 테이블에서 이제 `SHOW CREATE TABLE`을 지원합니다.

:::

## 쓰기 작업 {#write-operations}

### INSERT INTO {#insert-into}

INSERT 작업은 대상 테이블에 데이터를 추가합니다.

예:

```sql
INSERT INTO iceberg_tbl VALUES (val1, val2, val3, val4);
INSERT INTO iceberg.iceberg_db.iceberg_tbl SELECT col1, col2 FROM internal.db1.tbl1;

INSERT INTO iceberg_tbl(col1, col2) VALUES (val1, val2);
INSERT INTO iceberg_tbl(col1, col2, partition_col1, partition_col2) VALUES (1, 2, 'beijing', '2023-12-12');
```

버전 3.1.0부터 지정한 브랜치에 데이터 쓰기를 지원합니다.

```sql
INSERT INTO iceberg_tbl@branch(b1) values (val1, val2, val3, val4);
INSERT INTO iceberg_tbl@branch(b1) (col3, col4) values (val3, val4);
```

### INSERT OVERWRITE {#insert-overwrite}

INSERT OVERWRITE 작업은 테이블의 기존 데이터를 새 데이터로 완전히 대체합니다.

```sql
INSERT OVERWRITE TABLE iceberg_tbl VALUES (val1, val2, val3, val4);
INSERT OVERWRITE TABLE iceberg.iceberg_db.iceberg_tbl(col1, col2) SELECT col1, col2 FROM internal.db1.tbl1;
```

버전 3.1.0부터 지정한 브랜치에 데이터 쓰기를 지원합니다.

```sql
INSERT OVERWRITE TABLE iceberg_tbl@branch(b1) values (val1, val2, val3, val4);
INSERT OVERWRITE TABLE iceberg_tbl@branch(b1) (col3, col4) values (val3, val4);
```

버전 4.1.0부터 정적 파티션(또는 혼합 파티션)에 데이터 쓰기를 지원합니다.

```sql
-- Full Static Partition
INSERT OVERWRITE TABLE iceberg_tbl PARTITION (dt='2025-01-25', region='bj')
SELECT id, name FROM source_table;

-- Hybrid Partition Mode: "dt" is static, "region" comes from SELECT dynamically
INSERT OVERWRITE TABLE iceberg_tbl PARTITION (dt='2025-01-25')
SELECT id, name, region FROM source_table;
```

### CTAS {#ctas}

`CTAS`(Create Table As Select) 문으로 Iceberg 테이블을 생성하고 데이터를 쓸 수 있습니다.

```sql
CREATE TABLE iceberg_ctas AS SELECT * FROM other_table;
```

CTAS는 파일 형식, 파티션 및 기타 속성 지정을 지원합니다.

```sql
CREATE TABLE iceberg_ctas
PARTITION BY LIST (pt1, pt2) ()
AS SELECT col1, pt1, pt2 FROM part_ctas_src WHERE col1 > 0;

CREATE TABLE iceberg.iceberg_db.iceberg_ctas (col1, col2, pt1)
PARTITION BY LIST (pt1) ()
PROPERTIES (
    'write-format'='parquet',
    'compression-codec'='zstd'
)
AS SELECT col1, pt1 AS col2, pt2 AS pt1 FROM test_ctas.part_ctas_src WHERE col1 > 0;
```

### INSERT INTO BRANCH {#insert-into-branch}

> 3.1.0부터 지원

```sql
INSERT INTO iceberg_table@branch(b1) SELECT * FROM other_table;
INSERT OVERWRITE TABLE iceberg_table@branch(b1) SELECT * FROM other_table;
```

### DELETE {#delete}

:::tip
실험적 기능으로, 버전 4.1.0부터 지원됩니다.
:::

`DELETE` 작업은 Iceberg 테이블에서 지정한 조건을 만족하는 데이터 행을 삭제합니다. 이 작업은 주로 다음 내부 메커니즘을 기반으로 합니다. V2 형식 테이블에서는 시스템이 Position Delete 파일을 기록하고, V3 형식 테이블에서는 Puffin 형식의 Deletion Vectors 파일을 기록합니다.

**사전 조건:**

- Iceberg 테이블의 형식 버전(`format-version`)은 2 이상이어야 합니다. V1 형식 테이블은 `DELETE` 작업을 지원하지 않습니다.

**구문:**

```sql
DELETE FROM iceberg_tbl WHERE <condition>;
```

**예제:**

```sql
-- Delete a single row
DELETE FROM iceberg_tbl WHERE id = 1;

-- Delete using multiple conditions
DELETE FROM iceberg_tbl WHERE age > 30 AND name = 'Bob';

-- Delete using a subquery
DELETE FROM iceberg_tbl WHERE id IN (SELECT id FROM other_table WHERE status = 'inactive');
```

파티션 테이블에서도 사용법은 동일합니다.

```sql
DELETE FROM iceberg_partition_tbl WHERE id = 10;
```

### UPDATE {#update}

:::tip
실험적 기능으로, 버전 4.1.0부터 지원됩니다.
:::

`UPDATE` 작업은 Iceberg 테이블에서 지정한 조건을 만족하는 데이터 행을 수정합니다. 내부적으로 먼저 삭제 추적 정보(V2에서는 Position Delete 파일, V3에서는 Puffin 형식의 Deletion Vectors 사용)를 기록하여 이전 데이터 행을 무효로 표시한 다음, 갱신된 새 데이터 파일을 추가합니다(V3 형식 옵션이 활성화된 경우 새로 삽입된 행의 추적 값인 `_last_updated_sequence_number`가 자동으로 증가함).

**사전 조건:**

- Iceberg 테이블의 형식 버전(`format-version`)은 2 이상이어야 합니다. V1 형식 테이블은 `UPDATE` 작업을 지원하지 않습니다.

**구문:**

```sql
UPDATE iceberg_tbl SET <column1> = <value1> [, <column2> = <value2>, ...] WHERE <condition>;
```

**예제:**

```sql
-- Update a single column
UPDATE iceberg_tbl SET name = 'Alice_new' WHERE id = 1;

-- Update multiple columns
UPDATE iceberg_tbl SET name = 'Updated', age = 28 WHERE id = 2;

-- Update using expressions
UPDATE iceberg_tbl SET age = age * 2 + 1, name = concat(name, '-modified') WHERE id = 3;

-- Update using a subquery as condition
UPDATE iceberg_tbl SET name = 'UpdatedViaSubquery' WHERE id IN (SELECT id FROM other_table);
```

파티션 테이블에서도 사용법은 동일합니다.

```sql
UPDATE iceberg_partition_tbl SET name = 'Updated' WHERE id = 10;
```

### MERGE INTO {#merge-into}

:::tip
실험적 기능으로, 버전 4.1.0부터 지원됩니다.
:::

`MERGE INTO` 작업은 소스 데이터를 대상 Iceberg 테이블과 매칭한 뒤, 매칭 결과에 따라 삽입, 갱신 또는 삭제 작업을 수행합니다. 데이터 동기화 및 증분 갱신과 같은 시나리오에 적합합니다.

**사전 조건:**

- Iceberg 테이블의 형식 버전(`format-version`)은 2 이상이어야 합니다. V1 형식 테이블은 `MERGE INTO` 작업을 지원하지 않습니다.

**구문:**

```sql
MERGE INTO target_table t
USING <source> s
ON <merge_condition>
[WHEN MATCHED [AND <condition>] THEN DELETE]
[WHEN MATCHED [AND <condition>] THEN UPDATE SET <column1> = <value1> [, ...]]
[WHEN NOT MATCHED [AND <condition>] THEN INSERT (<columns>) VALUES (<values>)]
```

여기서 `<source>`는 하위 쿼리 또는 다른 테이블일 수 있습니다.

**예제:**

- 전체 매칭 작업(갱신, 삭제, 삽입 포함):

    ```sql
    MERGE INTO iceberg_tbl t
    USING (
        SELECT 1 AS id, 'Alice_new' AS name, 26 AS age, 'U' AS flag
        UNION ALL
        SELECT 2, 'Bob', 30, 'D'
        UNION ALL
        SELECT 4, 'Dora', 28, 'I'
    ) s
    ON t.id = s.id
    WHEN MATCHED AND s.flag = 'D' THEN DELETE
    WHEN MATCHED THEN UPDATE SET
        name = s.name,
        age = s.age
    WHEN NOT MATCHED THEN INSERT (id, name, age)
    VALUES (s.id, s.name, s.age);
    ```

    위 예제에서는 다음과 같이 처리됩니다.
    * `id = 2`인 행은 `flag = 'D'`이므로 삭제됩니다.
    * `id = 1`인 행은 새로운 `name`과 `age`로 갱신됩니다.
    * `id = 4`인 행은 대상 테이블에 없으므로 삽입됩니다.

- 매칭된 행의 갱신만 실행:

    ```sql
    MERGE INTO iceberg_tbl t
    USING (SELECT 1 AS id, 'Alice_matched' AS name, 26 AS age) s
    ON t.id = s.id
    WHEN MATCHED THEN UPDATE SET name = s.name, age = s.age;
    ```

- 매칭되지 않은 행의 삽입만 실행:

    ```sql
    MERGE INTO iceberg_tbl t
    USING (SELECT 4 AS id, 'Dora' AS name, 40 AS age) s
    ON t.id = s.id
    WHEN NOT MATCHED THEN INSERT (id, name, age) VALUES (s.id, s.name, s.age);
    ```

- 하위 쿼리를 데이터 소스로 사용:

    ```sql
    MERGE INTO iceberg_tbl t
    USING (SELECT id FROM other_table WHERE id = 2) s
    ON t.id = s.id
    WHEN MATCHED THEN UPDATE SET name = 'UpdatedViaSubquery';
    ```

- 파티션 테이블의 `MERGE INTO` 작업:

    ```sql
    MERGE INTO iceberg_partition_tbl t
    USING (
        SELECT 1 AS id, 'Alice_new' AS name, 26 AS age, DATE '2024-01-01' AS dt, 'U' AS flag
        UNION ALL
        SELECT 2, 'Bob', 30, DATE '2024-01-02', 'D'
        UNION ALL
        SELECT 4, 'Dora', 28, DATE '2024-01-04', 'I'
    ) s
    ON t.id = s.id
    WHEN MATCHED AND s.flag = 'D' THEN DELETE
    WHEN MATCHED THEN UPDATE SET
        name = s.name,
        age = s.age
    WHEN NOT MATCHED THEN INSERT (id, name, age, dt)
    VALUES (s.id, s.name, s.age, s.dt);
    ```

**참고 사항:**

1. 위의 세 작업(`DELETE`, `UPDATE`, `MERGE INTO`)은 모두 Iceberg 테이블의 형식 버전(`format-version`)이 2 이상이어야 합니다. V1 형식 테이블에서 실행하면 `must have format version 2 or higher for position deletes` 오류가 발생합니다. V3 형식 테이블에서 실행하면 시스템은 기존 Position Delete 데이터를 Puffin 형식의 Deletion Vectors로 대체하고, 내용 갱신이 포함된 경우 기록되는 레코드의 계보 수명 주기 속성(`_last_updated_sequence_number`)도 자동으로 조정합니다.
2. 이 작업들은 Parquet와 ORC 파일 형식을 모두 지원합니다.
3. 동시 쓰기 시나리오에서 Iceberg는 낙관적 동시성 제어 메커니즘을 제공합니다. 쓰기 충돌이 발생하면 트랜잭션 충돌 예외가 발생할 수 있습니다.
4. `UPDATE` 작업은 단독으로 실행하거나 `MERGE INTO` 내부에서 실행할 때 모두 `age = age * 2 + 1` 또는 `name = concat(name, '-modified')`와 같은 표현식과 함수 사용을 지원합니다.
5. 이 작업들은 파티션 테이블과 비파티션 테이블에 모두 적용됩니다.
6. **버전 4.1.4부터**(모든 BE를 업그레이드해야 함) `MERGE INTO`는 소스와 대상 테이블 사이의 매칭 관계를 검증합니다. 동일한 대상 행에 여러 소스 행이 매칭되면, 비결정적인 결과를 생성하는 대신 `multiple source rows matched the same target row` 오류로 문이 실패합니다. 일대다 매칭이 예상되는 경우 먼저 소스 측에서 중복을 제거하세요.

## 데이터베이스 및 테이블 관리 {#database-and-table-management}

### 데이터베이스 생성 및 삭제 {#creating-and-dropping-databases}

`SWITCH` 문으로 원하는 Catalog로 전환한 다음 `CREATE DATABASE` 명령을 실행할 수 있습니다.

```sql
SWITCH iceberg;
CREATE DATABASE [IF NOT EXISTS] iceberg_db;
```

전체 이름을 사용하여 데이터베이스를 생성하거나 데이터베이스 속성을 지정할 수도 있습니다. 예:

```sql
CREATE DATABASE [IF NOT EXISTS] iceberg.iceberg_db;

CREATE DATABASE [IF NOT EXISTS] iceberg.iceberg_db
PROPERTIES ('location'='hdfs://172.21.16.47:4007/path/to/db/');
```

**데이터베이스 속성 지원 매트릭스(버전 4.1.4부터 확장):**

| Catalog 유형(`iceberg.catalog.type`) | 일반 데이터베이스 속성 | `location` 속성 |
| --- | --- | --- |
| `hms` | 지원 | 지원 |
| `glue` | 지원(4.1.4부터) | 지원(4.1.4부터) |
| `jdbc` | 지원(4.1.4부터) | 미지원 |
| `hadoop` / `rest` / `dlf` / `s3tables` | 미지원 | 미지원 |

속성이 지원되지 않을 때 발생하는 오류 메시지:

- 일반 속성: `Not supported: create database with properties for iceberg catalog type: <type>`
- `location` 속성: `Not supported: database property 'location' for iceberg catalog type: <type> because it does not determine the default table location`

> REST 프로토콜에서는 서버가 Namespace 속성을 무시할 수 있으므로 REST Catalog는 데이터베이스 속성을 지원하지 않습니다.

`SHOW CREATE DATABASE` 명령으로 데이터베이스의 위치 정보를 확인할 수 있습니다.

```sql
mysql> SHOW CREATE DATABASE iceberg_db;
+-------------+-------------------------------------------------------------------------------------------------+
| Database    | Create Database                                                                                 |
+-------------+-------------------------------------------------------------------------------------------------+
| iceberg_db  | CREATE DATABASE iceberg_db LOCATION 'hdfs://172.21.16.47:4007/usr/hive/warehouse/iceberg_db.db' |
+-------------+-------------------------------------------------------------------------------------------------+
```

데이터베이스를 삭제하려면 다음을 실행합니다.

```sql
DROP DATABASE [IF EXISTS] iceberg.iceberg_db;
```

:::caution
Iceberg 데이터베이스를 삭제하려면 먼저 해당 데이터베이스의 모든 테이블을 삭제해야 합니다. 그렇지 않으면 오류가 발생합니다.
:::

### 테이블 생성 및 삭제 {#creating-and-dropping-tables}

* **테이블 생성**

  Doris는 Iceberg에서 파티션 테이블과 비파티션 테이블 생성을 모두 지원합니다.

  예:
  
  ```sql
  -- Create unpartitioned iceberg table
  CREATE TABLE unpartitioned_table (
    `col1` BOOLEAN COMMENT 'col1',
    `col2` INT COMMENT 'col2',
    `col3` BIGINT COMMENT 'col3',
    `col4` FLOAT COMMENT 'col4',
    `col5` DOUBLE COMMENT 'col5',
    `col6` DECIMAL(9,4) COMMENT 'col6',
    `col7` STRING COMMENT 'col7',
    `col8` DATE COMMENT 'col8',
    `col9` DATETIME COMMENT 'col9'
  )
  PROPERTIES (
    'write-format'='parquet'
  );

  -- Create partitioned iceberg table
  -- The partition columns must be in table's column definition list
  CREATE TABLE partition_table (
    `ts` DATETIME COMMENT 'ts',
    `col1` BOOLEAN COMMENT 'col1',
    `col2` INT COMMENT 'col2',
    `col3` BIGINT COMMENT 'col3',
    `col4` FLOAT COMMENT 'col4',
    `col5` DOUBLE COMMENT 'col5',
    `col6` DECIMAL(9,4) COMMENT 'col6',
    `col7` STRING COMMENT 'col7',
    `col8` DATE COMMENT 'col8',
    `col9` DATETIME COMMENT 'col9',
    `pt1` STRING COMMENT 'pt1',
    `pt2` STRING COMMENT 'pt2'
  )
  PARTITION BY LIST (day(ts), pt1, pt2) ()
  PROPERTIES (
    'write-format'='orc',
    'compression-codec'='zlib'
  );
  ```

  버전 4.1.0부터 Doris는 Iceberg 테이블 생성 시 정렬 컬럼 지정을 지원합니다. 데이터를 쓸 때 지정한 정렬 컬럼을 기준으로 정렬하여 쿼리 성능을 높입니다.

  ```sql
  CREATE TABLE ordered_table (
    `id` int NULL,
    `name` text NULL,
    `score` double NULL,
    `create_time` datetimev2(6) NULL
  )
  ORDER BY  (`id` ASC NULLS FIRST, `score` DESC NULLS LAST)
  PROPERTIES (
    "write-format" = "parquet",
    "write.parquet.compression-codec" = "zstd"
  );
  ```

  - 정렬 컬럼을 지정하지 않으면 쓰기 시 정렬하지 않습니다.
  - 기본 정렬 순서는 ASC NULLS FIRST입니다.

  생성 후 `SHOW CREATE TABLE` 명령으로 Iceberg 테이블 생성문을 확인할 수 있습니다. 파티션 함수에 대한 자세한 내용은 [파티션](#) 섹션을 참조하세요.

* **테이블 삭제**

  `DROP TABLE` 문으로 Iceberg 테이블을 삭제할 수 있습니다. 테이블을 삭제하면 파티션 데이터를 포함한 테이블 데이터도 제거됩니다.

  예:

  ```sql
  DROP TABLE [IF EXISTS] iceberg_tbl;
  ```

* **컬럼 유형 매핑**

  [컬럼 유형 매핑](#) 섹션을 참조하세요.

* **파티션**

    Iceberg의 파티션 유형은 Doris의 List 파티션에 대응합니다. 따라서 Doris에서 Iceberg 파티션 테이블을 생성할 때는 List 파티션 구문을 사용하되, 각 파티션을 명시적으로 나열할 필요는 없습니다. Doris는 데이터 삽입 시 데이터 값을 기반으로 해당 Iceberg 파티션을 자동 생성합니다.

    * 단일 컬럼 또는 다중 컬럼 파티션 테이블 생성을 지원합니다.

    * Iceberg의 암시적 파티션과 파티션 진화를 위한 파티션 변환 함수를 지원합니다. 구체적인 Iceberg 파티션 변환 함수는 [Iceberg 파티션 변환](https://iceberg.apache.org/spec/#partition-transforms)을 참조하세요.

        * `year(ts)` 또는 `years(ts)`

        * `month(ts)` 또는 `months(ts)`

        * `day(ts)` 또는 `days(ts)` 또는 `date(ts)`

        * `hour(ts)` 또는 `hours(ts)` 또는 `date_hour(ts)`

        * `bucket(N, col)`

        * `truncate(L, col)`

* **파일 형식**

    * Parquet(기본값)

        Doris에서 생성한 Iceberg 테이블의 Datetime은 `timestamp_ntz` 유형에 대응합니다.

        3.1.0 이후 버전에서는 Datetime 유형을 Parquet 파일에 쓸 때 물리적 유형으로 INT96 대신 INT64를 사용합니다.

        다른 시스템에서 생성한 Iceberg 테이블에서는 `timestamp`와 `timestamp_ntz` 유형이 모두 Doris의 Datetime 유형으로 매핑됩니다. 다만 쓰기 시에는 실제 유형을 기준으로 시간대 처리 여부를 결정합니다.

    * ORC

* **압축 형식**

    * Parquet: snappy, zstd(기본값), plain(압축 없음).

    * ORC: snappy, zlib(기본값), zstd, plain(압축 없음).

* **스토리지 매체**

    * HDFS

    * 객체 스토리지

### 스키마 변경 {#schema-change}

3.1.0부터 Doris는 Iceberg 테이블의 스키마 변경을 지원하며, `ALTER TABLE` 문으로 수정할 수 있습니다.

지원되는 스키마 변경 작업은 다음과 같습니다.

* **컬럼 이름 변경**

    `RENAME COLUMN` 절로 컬럼 이름을 변경합니다. 버전 4.1.4부터 중첩 유형 내부의 컬럼 이름 변경을 지원하며, `TO` 키워드는 선택 사항입니다.

    ```sql
    ALTER TABLE iceberg_table RENAME COLUMN old_col_name TO new_col_name;

    -- Supported since 4.1.4: TO can be omitted
    ALTER TABLE iceberg_table RENAME COLUMN old_col_name new_col_name;

    -- Supported since 4.1.4: rename a nested field
    ALTER TABLE iceberg_table RENAME COLUMN s.old_field TO new_field;
    ```

* **단일 컬럼 추가**

    `ADD COLUMN`으로 새 컬럼을 추가합니다. 버전 4.1.4부터 점으로 구분된 경로(예: `s.new_field`)를 통해 중첩 유형(STRUCT)에 새 컬럼을 추가할 수 있습니다. 새로 추가하는 중첩 필드는 NULL을 허용해야 합니다.

    새 컬럼을 추가할 때 NULL 허용 속성, 기본값, 주석 및 컬럼 위치를 지정할 수 있습니다.

    ```sql
    ALTER TABLE iceberg_table ADD COLUMN col_name col_type [NULL|NOT NULL, [DEFAULT default_value, [COMMENT 'comment', [FIRST|AFTER col_name]]]];
    ```

    예:

    ```sql
    ALTER TABLE iceberg_table ADD COLUMN new_col STRING NOT NULL DEFAULT 'default_value' COMMENT 'This is a new col' AFTER old_col;
    ```

* **여러 컬럼 추가**

    `ADD COLUMN`으로 여러 컬럼을 추가할 수도 있습니다. 새 컬럼은 테이블의 끝에 추가됩니다. 여러 컬럼을 추가할 때는 컬럼 위치 지정을 지원하지 않습니다. 중첩 유형에 새 컬럼을 추가하는 것은 지원하지 않습니다.

    각 컬럼의 구문은 단일 컬럼을 추가할 때와 같습니다.

    ```sql
    ALTER TABLE iceberg_table ADD COLUMN (col_name1 col_type1 [NULL|NOT NULL, [DEFAULT default_value, [COMMENT 'comment']]], col_name2 col_type2 [NULL|NOT NULL, [DEFAULT default_value, [COMMENT 'comment']]] ...);
    ```

* **컬럼 삭제**

    `DROP COLUMN`으로 컬럼을 삭제합니다. 버전 4.1.4부터 점으로 구분된 경로를 통해 중첩 유형 내부의 컬럼을 삭제할 수 있습니다.

    ```sql
    ALTER TABLE iceberg_table DROP COLUMN col_name;

    -- Supported since 4.1.4: drop a nested field
    ALTER TABLE iceberg_table DROP COLUMN s.field_name;
    ```

* **컬럼 수정**

    `MODIFY COLUMN` 문으로 유형, NULL 허용 여부, 기본값, 주석, 컬럼 위치 등 컬럼 속성을 수정합니다.

    버전 4.0.4부터 Doris는 안전한 유형 승격과 struct 필드 추가를 포함하여 복합 유형(STRUCT, ARRAY, MAP) 수정을 지원합니다.
    
    중첩 유형에서 지원하는 안전한 유형 승격:
    - INT -> BIGINT, LARGEINT
    - TINYINT -> SMALLINT, INT, BIGINT, LARGEINT
    - SMALLINT -> INT, BIGINT, LARGEINT
    - BIGINT -> LARGEINT
    - FLOAT -> DOUBLE
    - VARCHAR(n) -> VARCHAR(m), 단 m > n
    
    복합 유형의 제약 조건:
    - 새 중첩 필드는 모두 NULL을 허용해야 합니다.
    - 선택 필드를 필수 필드로 변경할 수 없습니다.
    - 복합 유형의 기본값은 NULL만 지원합니다.

    참고: 컬럼 속성을 수정할 때는 변경하지 않는 속성도 모두 원래 값으로 명시해야 합니다.

    ```sql
    ALTER TABLE iceberg_table MODIFY COLUMN col_name col_type [NULL|NOT NULL, [DEFAULT default_value, [COMMENT 'comment', [FIRST|AFTER col_name]]]];
    ```

  예:

  ```sql
  CREATE TABLE iceberg_table (
      id INT,
      name STRING
  );
  -- Modify the id column type to BIGINT, set as NOT NULL, default value to 0, and add comment
  ALTER TABLE iceberg_table MODIFY COLUMN id BIGINT NOT NULL DEFAULT 0 COMMENT 'This is a modified id column';
  ```

  복합 유형 수정 예제:

  ```sql
  -- Create Iceberg table with complex types
  CREATE TABLE iceberg_tbl (
      id BIGINT,
      user_info STRUCT<name:STRING, scores:ARRAY<INT>, age:INT>,
      dt STRING
  );

  -- Append a new field (email) to the STRUCT column
  ALTER TABLE iceberg_tbl MODIFY COLUMN user_info STRUCT<name:STRING, scores:ARRAY<INT>, age:INT, email:STRING>;

  -- Promote the nested ARRAY element type from INT to BIGINT
  ALTER TABLE iceberg_tbl MODIFY COLUMN user_info STRUCT<name:STRING, scores:ARRAY<BIGINT>, age:INT, email:STRING>;
  ```

* **컬럼 순서 변경**

    `ORDER BY`에 새 컬럼 순서를 지정하여 컬럼 순서를 변경합니다.

    ```sql
    ALTER TABLE iceberg_table ORDER BY (col_name1, col_name2, ...);
    ```

#### 중첩 컬럼 스키마 변경(4.1.4+) {#nested-column-schema-change-414}

버전 4.1.4부터 `ADD COLUMN`, `DROP COLUMN`, `MODIFY COLUMN`, `RENAME COLUMN`은 모두 점으로 구분된 경로(예: `a.b.c`)를 받아 중첩 필드를 직접 조작할 수 있습니다. 이 기능은 **Iceberg 테이블에만** 적용됩니다. 다른 테이블 유형에서 사용하면 `Nested column path is only supported for Iceberg tables: ...` 오류가 발생합니다.

일반적인 제한 사항 및 오류:

| 오류 메시지 | 설명 |
| --- | --- |
| `New nested field '<path>' must be nullable` | 새로 추가하는 중첩 필드는 NULL을 허용해야 합니다. |
| `Rollup is not supported for Iceberg column operations` | Rollup 절은 지원하지 않습니다. |
| `PROPERTIES are not supported for Iceberg column operations` | PROPERTIES 절은 지원하지 않습니다. |
| `KEY is not supported for Iceberg ADD/MODIFY COLUMN` | KEY 키워드는 지원하지 않습니다. |
| `Generated columns are not supported for Iceberg ADD/MODIFY COLUMN` | 생성 컬럼은 지원하지 않습니다. |
| `Modifying default values is not supported for Iceberg columns` | 기존 컬럼의 기본값 수정은 지원하지 않습니다. |
| `ON UPDATE is not supported for Iceberg ADD COLUMN` | ON UPDATE 절은 지원하지 않습니다. |
| `Modify column type from complex to primitive is not supported` | 복합 유형을 기본 유형으로 변경하는 것은 지원하지 않습니다. |
| `Cannot change MAP key type from ...` / `Cannot <op> MAP key nested column` | MAP 키 유형 변경이나 MAP 키에 대한 중첩 컬럼 작업은 지원하지 않습니다. |
| `Iceberg does not support comments on collection element or value fields` | 컬렉션 요소 또는 MAP 값 필드에 대한 주석은 지원하지 않습니다. |
| `Multiple Iceberg ALTER clauses are not supported when a statement ...` | 중첩 컬럼이 포함된 경우 문에는 ALTER 절을 하나만 포함할 수 있습니다. |

### 테이블 속성 수정 {#modifying-table-properties}

> 버전 4.1.4부터 지원됩니다.

`ALTER TABLE ... SET (...)`으로 Iceberg 테이블의 네이티브 속성을 수정할 수 있으며, **하나의 문에서 여러 속성을 설정할 수 있습니다**.

```sql
ALTER TABLE iceberg_ctl.iceberg_db.iceberg_tbl SET (
    'write.target-file-size-bytes' = '268435456',
    'commit.manifest.min-count-to-merge' = '50'
);
```

참고 사항:

- 모든 속성은 하나의 Iceberg `UpdateProperties` 트랜잭션으로 원자적으로 커밋됩니다. 실패하면 어떤 속성도 적용되지 않으며 FE 메타데이터 새로 고침도 실행되지 않습니다.
- Doris 자체의 `auto_analyze_policy` 속성은 커넥터 네이티브 속성과 같은 문에서 함께 설정할 수 없습니다. 함께 설정하면 `auto_analyze_policy cannot be set with external table properties` 오류가 발생합니다. 단독으로 설정할 때 사용할 수 있는 값은 기존과 같이 `enable` / `disable` / `base_on_catalog`입니다.
- Catalog가 메타데이터 쓰기를 구현하지 않은 경우 `Update table properties operation is not supported for catalog: <name>` 오류가 발생합니다.

### 파티션 진화 {#partition-evolution}

버전 4.0.2부터 Doris는 `ALTER` 문을 통한 Iceberg 테이블의 파티션 진화를 지원합니다.

지원되는 파티션 변환은 다음과 같습니다.

| 변환 | 구문 | 예시 |
|-----------|--------|---------|
| bucket | `bucket(N, column)` | `bucket(16, id)` |
| truncate | `truncate(N, column)` | `truncate(10, name)` |
| year | `year(column)` | `year(ts)` |
| month | `month(column)` | `month(ts)` |
| day | `day(column)` | `day(ts)` |
| hour | `hour(column)` | `hour(ts)` |
| identity | `column` | `category` |

지원되는 작업은 다음과 같습니다.

- **파티션 키 추가**

    ```sql
    -- use optional AS keyword to specify a custom name for the partition field
    ALTER TABLE table_name ADD PARTITION KEY partition_transform [AS key_name];

    -- example
    ALTER TABLE prod.db.sample ADD PARTITION KEY bucket(16, id);
    ALTER TABLE prod.db.sample ADD PARTITION KEY truncate(4, data);
    ALTER TABLE prod.db.sample ADD PARTITION KEY year(ts);
    -- use optional AS keyword to specify a custom name for the partition field 
    ALTER TABLE prod.db.sample ADD PARTITION KEY bucket(16, id) AS shard;
    ```

- **파티션 키 삭제**

    ```sql
    ALTER TABLE table_name DROP PARTITION KEY partition_transform｜key_name;

    -- example
    ALTER TABLE prod.db.sample DROP PARTITION KEY catalog;
    ALTER TABLE prod.db.sample DROP PARTITION KEY bucket(16, id);
    ALTER TABLE prod.db.sample DROP PARTITION KEY truncate(4, data);
    ALTER TABLE prod.db.sample DROP PARTITION KEY year(ts);
    ALTER TABLE prod.db.sample DROP PARTITION KEY shard;
    ```

- **파티션 키 교체**

    ```sql
    -- use optional AS keyword to specify a custom name for the partition field
    ALTER TABLE table_name REPLACE PARTITION KEY key_name WITH partition_transform [AS key_name];

    -- example
    ALTER TABLE prod.db.sample REPLACE PARTITION KEY ts_day WITH day(ts);
    -- use optional AS keyword to specify a custom name for the new partition field 
    ALTER TABLE prod.db.sample REPLACE PARTITION KEY ts_day WITH day(ts) AS day_of_ts;
    ```

### 브랜치 및 태그 관리 {#managing-branch--tag}

> 3.1.0부터 지원

* **브랜치 생성**

  구문:

  ```sql
  ALTER TABLE [catalog.][database.]table_name
  CREATE [OR REPLACE] BRANCH [IF NOT EXISTS] <branch_name>
  [AS OF VERSION <snapshot_id>]
  [RETAIN <num> { DAYS | HOURS | MINUTES }]
  [WITH SNAPSHOT RETENTION { snapshotKeep | timeKeep }]

  snapshotKeep:
    <num> SNAPSHOTS [<num> { DAYS | HOURS | MINUTES }]

  timeKeep:
    <num> { DAYS | HOURS | MINUTES }
  ```

  예제:

  ```sql
  -- Create branch "b1".
  ALTER TABLE tbl CREATE BRANCH b1;
  ALTER TABLE tb1 CREATE BRANCH IF NOT EXISTS b1;
  -- Create or replace branch "b1".
  ALTER TABLE tb1 CREATE OR REPLACE BRANCH b1;
  -- Create or replace branch "b1" based on snapshot "123456".
  ALTER TABLE tb1 CREATE OR REPLACE BRANCH b1 AS OF VERSION 123456;
  -- Create or replace branch "b1" based on snapshot "123456", branch retained for 1 day.
  ALTER TABLE tb1 CREATE OR REPLACE BRANCH b1 AS OF VERSION 123456 RETAIN 1 DAYS;
  -- Create branch "b1" based on snapshot "123456", branch retained for 30 days. Keep the latest 3 snapshots in the branch.
  ALTER TABLE tb1 CREATE BRANCH b1 AS OF VERSION 123456 RETAIN 30 DAYS WITH SNAPSHOT RETENTION 3 SNAPSHOTS;
  -- Create branch "b1" based on snapshot "123456", branch retained for 30 days. Snapshots in the branch are retained for at most 2 days.
  ALTER TABLE tb1 CREATE BRANCH b1 AS OF VERSION 123456 RETAIN 30 DAYS WITH SNAPSHOT RETENTION 2 DAYS;
  -- Create branch "b1" based on snapshot "123456", branch retained for 30 days. Keep the latest 3 snapshots in the branch, and snapshots in the branch are retained for at most 2 days.
  ALTER TABLE tb1 CREATE BRANCH b1 AS OF VERSION 123456 RETAIN 30 DAYS WITH SNAPSHOT RETENTION 3 SNAPSHOTS 2 DAYS;
  ```

* **브랜치 삭제**

  구문:

  ```sql
  ALTER TABLE [catalog.][database.]table_name
  DROP BRANCH [IF EXISTS] <branch_name>;
  ```

  예:

  ```sql
  ALTER TABLE tbl DROP BRANCH b1;
  ```

* **태그 생성**

  구문:

  ```sql
  ALTER TABLE [catalog.][database.]table_name
  CREATE [OR REPLACE] TAG [IF NOT EXISTS] <tag_name>
  [AS OF VERSION <snapshot_id>]
  [RETAIN <num> { DAYS | HOURS | MINUTES }]
  ```

  예제:

  ```sql
  -- Create tag "t1".
  ALTER TABLE tbl CREATE TAG t1;
  ALTER TABLE tb1 CREATE TAG IF NOT EXISTS t1;
  -- Create or replace tag "t1".
  ALTER TABLE tb1 CREATE OR REPLACE TAG t1;
  -- Create or replace tag "t1" based on snapshot "123456".
  ALTER TABLE tb1 CREATE OR REPLACE TAG b1 AS OF VERSION 123456;
  -- Create or replace tag "b1" based on snapshot "123456", tag retained for 1 day.
  ALTER TABLE tb1 CREATE OR REPLACE TAG b1 AS OF VERSION 123456 RETAIN 1 DAYS;
  ```

* **태그 삭제**

  구문:

  ```sql
  ALTER TABLE [catalog.][database.]table_name
  DROP TAG [IF EXISTS] <tag_name>;
  ```

  예:

  ```sql
  ALTER TABLE tbl DROP TAG t1;
  ```

## Iceberg 테이블 작업 {#iceberg-table-actions}

> 이 기능은 버전 4.0.2부터 지원됩니다. 각 작업의 구체적인 버전 요구 사항을 확인하세요.
>
> 실험적 기능입니다.

Doris는 `ALTER TABLE EXECUTE` 구문으로 특정 Iceberg 테이블 작업을 실행할 수 있습니다. 이 구문은 테이블 최적화와 스냅샷 관리 등 다양한 작업을 실행하는 통합 인터페이스를 제공합니다.

```sql
ALTER TABLE [catalog.][database.]table_name
EXECUTE <action_name> ("key1" = "value1", "key2" = "value2", ...)
[WHERE <condition>]
```

* `action_name`: 실행할 작업의 이름
* `("key1" = "value1", ...)`: 키-값 쌍으로 제공하는 작업 관련 매개변수입니다. 매개변수 이름은 큰따옴표로 묶어야 합니다.
* `[WHERE <condition>]`: 작업할 파티션 또는 데이터 범위를 지정하는 선택적 WHERE 조건입니다(일부 작업에서만 지원).

### cherrypick_snapshot {#cherrypick_snapshot}

`cherrypick_snapshot` 작업은 지정한 스냅샷의 변경 사항을 현재 테이블 상태에 병합하고, 원본 스냅샷을 수정하거나 삭제하지 않은 채 새 스냅샷을 생성합니다.

> 지원 버전: 4.0.2+

**구문:**

```sql
ALTER TABLE [catalog.][database.]table_name
EXECUTE cherrypick_snapshot ("snapshot_id" = "<snapshot_id>")
```

**매개변수:**

| 매개변수 | 유형 | 필수 여부 | 설명 |
| -------- | ---- | ---- | ---- |
| `snapshot_id` | Long | 예 | 병합할 스냅샷 ID |

**반환값:**

`cherrypick_snapshot` 작업을 실행하면 다음 2개 컬럼이 있는 결과 집합을 반환합니다.

| 컬럼 이름 | 유형 | 설명 |
| ---- | ---- | ---- |
| `source_snapshot_id` | BIGINT | 병합된 스냅샷 ID |
| `current_snapshot_id` | BIGINT | 병합 작업 후 새로 생성되어 현재 스냅샷으로 설정된 스냅샷 ID |

**예:**

```sql
-- Merge changes from snapshot 123456789 into the current table state
ALTER TABLE iceberg_db.iceberg_table 
EXECUTE cherrypick_snapshot ("snapshot_id" = "123456789");
```

**참고 사항:**

1. 이 작업은 WHERE 조건을 지원하지 않습니다.
2. 지정한 스냅샷이 없으면 작업이 실패합니다.
3. 병합 작업은 새 스냅샷을 생성하며 원본 스냅샷은 삭제하지 않습니다.

### expire_snapshots {#expire_snapshots}

`expire_snapshots` 작업은 Iceberg 테이블에서 오래된 스냅샷을 제거하여 스토리지 공간을 확보하고 메타데이터 성능을 개선합니다. 이 작업은 Apache Iceberg Spark 프로시저 사양을 따릅니다.

> 지원 버전: 4.1.0+

**구문:**

```sql
ALTER TABLE [catalog.][database.]table_name
EXECUTE expire_snapshots ("key1" = "value1", "key2" = "value2", ...)
```

**매개변수:**

| 매개변수 | 유형 | 필수 여부 | 설명 |
| -------- | ---- | ---- | ---- |
| `older_than` | String | 아니요 | 스냅샷 만료 기준 시각입니다. 이 시각보다 오래된 스냅샷을 제거합니다. ISO 날짜/시간 형식(예: `2024-01-01T00:00:00`) 또는 밀리초 타임스탬프를 지원합니다. |
| `retain_last` | Integer | 아니요 | 보존할 조상 스냅샷 수입니다. 단독으로 지정하면 `older_than`을 현재 시각으로 자동 설정합니다. |
| `snapshot_ids` | String | 아니요 | 만료할 특정 스냅샷 ID를 쉼표로 구분한 목록입니다. |
| `max_concurrent_deletes` | Integer | 아니요 | 삭제 작업에 사용하는 스레드 풀의 크기입니다. |
| `clean_expired_metadata` | Boolean | 아니요 | `true`로 설정하면 사용하지 않는 파티션 사양과 스키마를 정리합니다. |

**반환값:**

`expire_snapshots` 작업을 실행하면 다음 6개 컬럼이 있는 결과 집합을 반환합니다.

| 컬럼 이름 | 유형 | 설명 |
| ---- | ---- | ---- |
| `deleted_data_files_count` | BIGINT | 삭제된 데이터 파일 수 |
| `deleted_position_delete_files_count` | BIGINT | 삭제된 Position Delete 파일 수 |
| `deleted_equality_delete_files_count` | BIGINT | 삭제된 Equality Delete 파일 수 |
| `deleted_manifest_files_count` | BIGINT | 삭제된 manifest 파일 수 |
| `deleted_manifest_lists_count` | BIGINT | 삭제된 manifest 목록 파일 수 |
| `deleted_statistics_files_count` | BIGINT | 삭제된 통계 파일 수 |

**예:**

```sql
-- Expire snapshots, keeping only the last 2
ALTER TABLE iceberg_db.iceberg_table 
EXECUTE expire_snapshots ("retain_last" = "2");

-- Expire snapshots older than a specific timestamp
ALTER TABLE iceberg_db.iceberg_table 
EXECUTE expire_snapshots ("older_than" = "2024-01-01T00:00:00");

-- Expire specific snapshots by ID
ALTER TABLE iceberg_db.iceberg_table 
EXECUTE expire_snapshots ("snapshot_ids" = "123456789,987654321");

-- Combine parameters: expire snapshots older than 2024-06-01 but keep at least the last 5
ALTER TABLE iceberg_db.iceberg_table 
EXECUTE expire_snapshots ("older_than" = "2024-06-01T00:00:00", "retain_last" = "5");
```

**참고 사항:**

1. 이 작업은 WHERE 조건을 지원하지 않습니다.
2. `older_than`과 `retain_last`를 모두 지정하면 두 조건이 모두 적용됩니다. 즉, `older_than`보다 오래되었고 최근 `retain_last`개 스냅샷에 포함되지 않는 스냅샷만 삭제됩니다.
3. `snapshot_ids`를 단독으로 사용하여 특정 스냅샷을 삭제할 수 있습니다.
4. 이 작업은 스냅샷과 관련 데이터 파일을 영구적으로 삭제합니다. 주의해서 사용하세요.
5. 실행 전에 `$snapshots` 시스템 테이블을 쿼리하여 테이블의 스냅샷 정보를 확인하는 것이 좋습니다.

### fast_forward {#fast_forward}

### rewrite_data_files {#rewrite_data_files}

`rewrite_data_files` 작업은 Iceberg 테이블의 데이터 파일을 다시 작성하여 작은 파일을 병합하고, 쿼리 성능과 스토리지 효율을 최적화합니다. 동기식 작업입니다.

> 지원 버전: 4.0.2+

**구문:**

```sql
ALTER TABLE [catalog.][database.]table_name
EXECUTE rewrite_data_files ("key1" = "value1", "key2" = "value2", ...) [WHERE <condition>]
```

**매개변수:**

| 매개변수 | 유형 | 기본값 | 설명 |
| -------- | ---- | ------ | ---- |
| `target-file-size-bytes` | Long | 536870912 (512MB) | 바이트 단위의 목표 파일 크기입니다. 출력 파일의 목표 크기입니다. |
| `min-file-size-bytes` | Long | target-file-size-bytes * 0.75 | 바이트 단위의 최소 파일 크기입니다. 이보다 작은 파일은 다시 작성됩니다. 지정하지 않으면 목표 파일 크기의 75%가 기본값입니다. |
| `max-file-size-bytes` | Long | target-file-size-bytes * 1.8 | 바이트 단위의 최대 파일 크기입니다. 이보다 큰 파일은 분할됩니다. 지정하지 않으면 목표 파일 크기의 180%가 기본값입니다. |
| `min-input-files` | Integer | 5 | 다시 작성을 시작하는 최소 입력 파일 수입니다. 다시 작성할 파일 수가 이 임계값에 도달해야 실행됩니다. |
| `rewrite-all` | Boolean | false | 파일 크기와 관계없이 모든 파일을 다시 작성할지 여부입니다. |
| `max-file-group-size-bytes` | Long | 107374182400 (100GB) | 바이트 단위의 단일 파일 그룹 최대 크기입니다. 단일 다시 작성 작업이 처리할 데이터 양을 제한하는 데 사용합니다. |
| `delete-file-threshold` | Integer | Integer.MAX_VALUE | 다시 작성을 시작하는 데 필요한 최소 삭제 파일 수입니다. |
| `delete-ratio-threshold` | Double | 0.3 | 다시 작성을 시작하는 데 필요한 최소 삭제 레코드 비율입니다(삭제된 레코드 / 전체 레코드). 범위: 0.0 - 1.0 |
| `output-spec-id` | Long | 2 | 출력 파일의 파티션 사양 ID입니다. |

**반환값:**

`rewrite_data_files` 작업을 실행하면 다음 4개 컬럼이 있는 결과 집합을 반환합니다.

| 컬럼 이름 | 유형 | 설명 |
| ---- | ---- | ---- |
| `rewritten_data_files_count` | INT | 다시 작성된 데이터 파일 수 |
| `added_data_files_count` | INT | 새로 추가된 데이터 파일 수 |
| `rewritten_bytes_count` | INT | 다시 작성된 바이트 수 |
| `removed_delete_files_count` | BIGINT | 제거된 삭제 파일 수 |

**예제:**

```sql
-- Rewrite data files with default parameters
ALTER TABLE iceberg_db.iceberg_table EXECUTE rewrite_data_files();

-- Specify target file size and minimum input files
ALTER TABLE iceberg_db.iceberg_table 
EXECUTE rewrite_data_files (
  "target-file-size-bytes" = "134217728",
  "min-input-files" = "10"
);

-- Rewrite data in specific partitions using WHERE condition
ALTER TABLE iceberg_db.iceberg_table 
EXECUTE rewrite_data_files (
  "target-file-size-bytes" = "268435456"
)
WHERE date_col = '2024-01-01';

-- Rewrite all files
ALTER TABLE iceberg_db.iceberg_table 
EXECUTE rewrite_data_files (
  "rewrite-all" = "true",
  "target-file-size-bytes" = "536870912"
);
```

**참고 사항:**

1. `rewrite_data_files` 작업은 데이터 파일을 읽고 다시 작성하므로 추가 I/O 및 컴퓨팅 오버헤드가 발생합니다. 클러스터 리소스를 적절히 할당하세요.
2. 실행 전에 [데이터 파일 분포 확인](#view-data-file-distribution) 섹션의 SQL로 다시 작성이 필요한지 평가할 수 있습니다.
3. WHERE 조건으로 다시 작성할 파티션이나 데이터 범위를 제한할 수 있습니다. 이 조건은 WHERE 조건과 일치하는 데이터가 없는 파일을 제외하여 다시 작성할 파일 수와 데이터 양을 줄입니다.
4. 실행 전에 [다시 작성할 파일 선택 로직](#rewrite_data_files-file-selection-strategy) 섹션의 SQL로 어떤 파일이 다시 작성될지 계산할 수 있습니다.

| -------- | ---- | ---- | ---- |
| `snapshot_id` | Long | 둘 중 하나 | 현재 스냅샷으로 설정할 스냅샷 ID |
| `ref` | String | 둘 중 하나 | 현재 스냅샷으로 설정할 참조 이름(브랜치 또는 태그) |

**반환값:**

`set_current_snapshot` 작업을 실행하면 다음 2개 컬럼이 있는 결과 집합을 반환합니다.

| 컬럼 이름 | 유형 | 설명 |
| ---- | ---- | ---- |
| `previous_snapshot_id` | BIGINT | 작업 전 현재 스냅샷의 ID |
| `current_snapshot_id` | BIGINT | 작업 후 스냅샷 ID(`snapshot_id` 매개변수에서 가져오거나 `ref` 매개변수로부터 결정됨) |

**예제:**

```sql
-- Set current snapshot by snapshot ID
ALTER TABLE iceberg_db.iceberg_table 
EXECUTE set_current_snapshot ("snapshot_id" = "123456789");

-- Set current snapshot by branch name
ALTER TABLE iceberg_db.iceberg_table 
EXECUTE set_current_snapshot ("ref" = "feature_branch");

-- Set current snapshot by tag name
ALTER TABLE iceberg_db.iceberg_table 
EXECUTE set_current_snapshot ("ref" = "v1.0");
```

**참고 사항:**

1. 이 작업은 WHERE 조건을 지원하지 않습니다.
2. `snapshot_id`와 `ref` 매개변수는 상호 배타적이므로 하나만 지정할 수 있습니다.
3. 지정한 스냅샷 ID 또는 참조가 없으면 작업이 실패합니다.
4. 현재 스냅샷이 이미 대상 스냅샷이면 새 스냅샷을 생성하지 않고 즉시 반환합니다.

### publish_changes {#publish_changes-1}

`publish_changes` 작업은 WAP(Write-Audit-Publish) 모드에서 지정한 `wap.id`가 있는 스냅샷을 현재 테이블 상태로 게시하는 데 사용됩니다.  
`wap.id`가 주어진 `wap_id`와 일치하는 스냅샷을 찾아 현재 테이블에 체리픽하여, 준비된 데이터를 모든 읽기 작업에서 볼 수 있게 합니다. 

**구문:**

```sql
ALTER TABLE [catalog.][database.]table_name
EXECUTE publish_changes("wap_id" = "<wap_id>")
```

**매개변수:**

**매개변수:**

| 매개변수 이름 | 유형 | 필수 여부 | 설명 |
| -------------- | ---- | -------- | ----------- |
| `wap_id` | STRING | 예 | 게시할 WAP 스냅샷 ID |

**반환값:**

`publish_changes`를 실행하면 다음 2개 컬럼이 있는 결과 집합을 반환합니다.

| 컬럼 이름 | 유형 | 설명 |
| ----------- | ---- | ----------- |
| `previous_snapshot_id` | STRING | 게시 작업 전 현재 스냅샷의 ID(없으면 NULL) |
| `current_snapshot_id` | STRING | 게시 후 새로 생성되어 현재 스냅샷으로 설정된 스냅샷의 ID |

**예제:**

```sql
-- Publish the snapshot whose WAP ID is test_wap_001
ALTER TABLE iceberg_db.iceberg_table 
EXECUTE publish_changes("wap_id" = "test_wap_001");
```

**참고 사항:**

1. 이 작업은 WHERE 절과 PARTITION/PARTITIONS 절을 지원하지 않습니다.
2. write.wap.enabled = true가 설정되고 wap.id를 통해 WAP 스냅샷이 생성된 Iceberg 테이블에서만 의미가 있습니다.
3. 지정한 wap_id에 해당하는 스냅샷을 찾지 못하면 작업이 실패하고 오류가 발생합니다.
4. 게시 후 새 스냅샷이 현재 스냅샷이 됩니다.
5. 게시 전에 스냅샷이 없으면 previous_snapshot_id는 NULL일 수 있습니다.

## Iceberg 테이블 최적화 {#iceberg-table-optimization}

### 데이터 파일 분포 확인 {#view-data-file-distribution}

다음 SQL로 Iceberg 테이블의 데이터 분포와 삭제 파일 수를 분석하여 `rewrite_data_files`와 같은 최적화가 필요한지 판단할 수 있습니다.

- 데이터 파일의 크기 분포를 표시합니다. 작은 파일이 너무 많은지 파악하는 데 도움이 됩니다.

    ```sql
    SELECT
        CASE
            WHEN file_size_in_bytes BETWEEN 0 AND 8 * 1024 * 1024 THEN '0-8M'
            WHEN file_size_in_bytes BETWEEN 8 * 1024 * 1024 + 1 AND 32 * 1024 * 1024 THEN '8-32M'
            WHEN file_size_in_bytes BETWEEN 32 * 1024 * 1024 + 1 AND 128 * 1024 * 1024 THEN '32-128M'
            WHEN file_size_in_bytes BETWEEN 128 * 1024 * 1024 + 1 AND 512 * 1024 * 1024 THEN '128-512M'
            WHEN file_size_in_bytes > 512 * 1024 * 1024 THEN '> 512M'
            ELSE 'Unknown'
        END AS SizeRange,
        COUNT(*) AS FileNum
    FROM store_sales$data_files
    GROUP BY
        SizeRange;

    +-----------+---------+
    | SizeRange | FileNum |
    +-----------+---------+
    | 0-8M      |       8 |
    | 8-32M     |       6 |
    +-----------+---------+
    ```

- 데이터 파일과 삭제 파일의 수를 표시합니다.

    ```sql
    SELECT
        CASE
            WHEN content = 0 THEN 'DataFile'
            WHEN content = 1 THEN 'PositionDeleteFile'
            WHEN content = 2 THEN 'EqualityDeleteFile'
            ELSE 'Unknown'
        END AS ContentType,
        COUNT(*) AS FileNum,
        SUM(file_size_in_bytes) AS SizeInBytes,
        SUM(record_count) AS Records
    FROM
        iceberg_table$files
    GROUP BY
        ContentType;

    +--------------------+---------+-------------+---------+
    | ContentType        | FileNum | SizeInBytes | Records |
    +--------------------+---------+-------------+---------+
    | EqualityDeleteFile |    2787 |     1432518 |   27870 |
    | DataFile           |    2787 |     4062416 |   38760 |
    | PositionDeleteFile |      11 |       36608 |   10890 |
    +--------------------+---------+-------------+---------+
    ```

### Dangling Delete {#dangling-delete}

일부 경우에는 `rewrite_data_files` 작업을 실행한 뒤에도 특정 Position Delete에 대한 참조가 스냅샷 메타데이터에서 제거되지 않을 수 있습니다(Dangling Delete). 이런 상황에서 메타데이터의 행 수 정보를 직접 사용하면 결과가 잘못될 수 있습니다.

따라서 기본적으로 `COUNT(*)` 쿼리에서 Position Delete 파일이 발견되면 COUNT 푸시다운 최적화를 활성화하지 않고 파일을 직접 읽어 실제 `COUNT(*)` 결과를 구합니다. 다만 이 방식은 시간이 오래 걸립니다.

Dangling Delete 문제가 없다고 보장할 수 있다면 Doris 세션 변수 `ignore_iceberg_dangling_delete`로 이 검사를 건너뛸 수 있습니다. 기본값은 `false`입니다. `true`로 설정하면 시스템이 메타데이터의 행 수 정보를 기반으로 `COUNT(*)` 결과를 직접 반환하여 쿼리 효율을 높입니다.

이 기능은 버전 3.1.4 및 4.0.3부터 지원됩니다.

## 부록 {#appendix}

### `rewrite_data_files` 파일 선택 전략 {#rewrite_data_files-file-selection-strategy}

이 섹션에서는 다시 작성할 파일을 선택하는 로직을 설명합니다. 다음 SQL 쿼리로 시스템 테이블 정보를 분석하여 어떤 파일이 다시 작성될지도 확인할 수 있습니다. 실제 다시 작성 작업을 실행하기 전에 동작을 디버깅하고 이해하는 데 도움이 됩니다.

다시 작성 작업은 두 단계의 필터링 및 그룹화 전략을 사용합니다.

1. 1단계: 파일 수준 필터링

    먼저 파일 수준 조건으로 파일을 필터링합니다. 다음 조건 중 하나 이상을 만족하는 파일만 다시 작성 대상으로 고려합니다.

    1. **파일 크기가 범위를 벗어남**: 파일이 `min-file-size-bytes`보다 작거나 `max-file-size-bytes`보다 큽니다.
    2. **삭제 파일이 너무 많음**: 연결된 삭제 파일 수 >= `delete-file-threshold`
    3. **삭제 비율이 높음**: 삭제 레코드 비율 >= `delete-ratio-threshold`

    **삭제 파일 조건에 대한 참고 사항:** 삭제 파일 관련 조건(`delete-file-threshold` 및 `delete-ratio-threshold`)은 다시 작성할 파일 선택에 영향을 주지만, 시스템 테이블 SQL 쿼리로 정확히 계산할 수는 없습니다. 현재 시스템 테이블 정보만으로는 삭제 파일이 어떤 데이터 파일에 영향을 주는지 정확히 판단하기 어렵기 때문입니다. 삭제 파일은 특정 데이터 파일에만 영향을 줄 수 있으며(특히 Position Delete 파일), 삭제 파일과 데이터 파일 사이의 연결 관계를 파악하려면 현재 시스템 테이블에서 제공하지 않는 더 상세한 메타데이터가 필요합니다. 실제 다시 작성 작업은 시스템 테이블에 노출되지 않는 상세 메타데이터를 기반으로 이 조건들을 평가합니다.

2. 2단계: BinPack 그룹화 및 그룹 수준 필터링

    파일 수준 필터링 후 파일을 파티션별로 그룹화합니다. 그런 다음 각 파티션 안에서 파일 크기와 `max-file-group-size-bytes`를 기준으로 **BinPack 알고리즘**을 사용하여 파일을 그룹화합니다. BinPack 알고리즘은 다시 작성 작업을 최적화하도록 파일을 그룹에 효율적으로 배치합니다.

    그룹화 후에는 그룹 수준 조건으로 파일 그룹을 필터링합니다. 다음 조건 중 하나 이상을 만족하는 파일 그룹이 다시 작성됩니다.

    1. **입력 파일 수가 충분함**: 그룹 내 파일 수 > 1이고 파일 수 >= `min-input-files`
    2. **데이터 양이 충분함**: 그룹 내 파일 수 > 1이고 전체 크기 > `target-file-size-bytes`
    3. **데이터 양이 너무 많음**: 그룹 전체 크기 > `max-file-group-size-bytes`
    4. **삭제 파일 문제가 있는 파일 포함**: 그룹에 삭제 파일이 너무 많거나 삭제 비율이 높은 파일이 하나 이상 있습니다.

    **BinPack 그룹화에 대한 참고 사항:** 각 파티션 내에서 파일을 그룹화하는 BinPack 알고리즘은 복잡한 최적화 알고리즘이므로 시스템 테이블 SQL 쿼리로 정확히 모사할 수 없습니다. 이 알고리즘은 파일 크기와 `max-file-group-size-bytes`를 고려하여 파일을 그룹에 효율적으로 배치하므로, 단순한 파티션 기반 그룹화와 결과가 다를 수 있습니다. 따라서 아래 SQL 쿼리는 파일 수준 조건을 만족하는 파일만 식별할 수 있으며, 최종적으로 다시 작성할 파일 그룹을 정확히 계산할 수는 없습니다.

다음은 쿼리 전략의 예입니다.

- 쿼리 1: 파일 수준 조건을 만족하는 파일 식별

    이 쿼리는 파일 수준 조건(파일 크기)을 만족하여 다시 작성 대상으로 고려되는 파일을 식별합니다.

    ```sql
    -- Set parameters (adjust according to your rewrite parameters)
    SET @min_file_size_bytes = 16 * 1024 * 1024;   -- 16 MB (default: target-file-size-bytes * 0.75)
    SET @max_file_size_bytes = 768 * 1024 * 1024;  -- 768 MB (default: target-file-size-bytes * 1.8)

    SELECT 
        file_path,
        `partition`,
        file_size_in_bytes / 1024.0 / 1024.0 AS file_size_mb,
        record_count,
        CASE 
            WHEN file_size_in_bytes < @min_file_size_bytes THEN 'Too small'
            WHEN file_size_in_bytes > @max_file_size_bytes THEN 'Too large'
        END AS size_issue
    FROM iceberg_table$data_files
    WHERE file_size_in_bytes < @min_file_size_bytes 
    OR file_size_in_bytes > @max_file_size_bytes
    ORDER BY `partition`, file_size_in_bytes DESC;
    ```

    **출력 예:**

    ```text
    +----------------------------------------------------------------------------------------+---------------------------+-------------+--------------+------------+
    | file_path                                                                             | partition                 | file_size_mb | record_count | size_issue |
    +----------------------------------------------------------------------------------------+---------------------------+-------------+--------------+------------+
    | s3a://bucket/path/to/table/data/date_col=2024-01-01/00000-0-00000-00000-0.parquet   | {"date_col":"2024-01-01"} |     0.00215  |            5 | Too small  |
    | s3a://bucket/path/to/table/data/date_col=2024-01-01/00001-0-00001-00001-0.parquet     | {"date_col":"2024-01-01"} |     0.00198  |            5 | Too small  |
    | s3a://bucket/path/to/table/data/date_col=2024-01-02/00002-0-00002-00002-0.parquet     | {"date_col":"2024-01-02"} |     0.00231  |            5 | Too small  |
    | s3a://bucket/path/to/table/data/date_col=2024-01-02/00003-0-00003-00003-0.parquet     | {"date_col":"2024-01-02"} |   850.23456  |      1250000 | Too large  |
    | s3a://bucket/path/to/table/data/date_col=2024-01-03/00004-0-00004-00004-0.parquet     | {"date_col":"2024-01-03"} |     0.00245  |            5 | Too small  |
    +----------------------------------------------------------------------------------------+---------------------------+-------------+--------------+------------+
    5 rows in set
    ```

    **참고:** 이 쿼리는 파일 수준 조건(파일 크기)을 만족하는 파일만 식별합니다. 실제 다시 작성할 파일 그룹은 BinPack 그룹화 알고리즘에 따라 결정되며, SQL 쿼리로 정확히 모사할 수 없습니다. 이 쿼리로 식별한 파일도 BinPack 알고리즘에 의해 다르게 그룹화될 수 있고, 일부 그룹은 그룹 수준 조건에 따라 제외될 수 있습니다.

- 쿼리 2: 전체 통계 요약

    이 쿼리는 파일 수준 조건을 만족하는 파일의 전체 통계를 제공합니다.

    ```sql
    -- Set parameters (adjust according to your rewrite parameters)
    SET @min_file_size_bytes = 16 * 1024 * 1024;
    SET @max_file_size_bytes = 768 * 1024 * 1024;

    WITH file_analysis AS (
        SELECT 
            `partition`,
            file_path,
            file_size_in_bytes,
            record_count,
            (file_size_in_bytes < @min_file_size_bytes OR file_size_in_bytes > @max_file_size_bytes) AS meets_file_level_conditions
        FROM iceberg_table$data_files
    )
    SELECT 
        'Total files' AS metric, 
        COUNT(*) AS value
    FROM file_analysis
    UNION ALL
    SELECT 
        'Files meeting file-level conditions', 
        SUM(CASE WHEN meets_file_level_conditions THEN 1 ELSE 0 END)
    FROM file_analysis
    UNION ALL
    SELECT 
        'Total size (GB)', 
        ROUND(SUM(file_size_in_bytes) / 1024.0 / 1024.0 / 1024.0, 2)
    FROM file_analysis
    UNION ALL
    SELECT 
        'Size meeting file-level conditions (GB)', 
        ROUND(SUM(CASE WHEN meets_file_level_conditions THEN file_size_in_bytes ELSE 0 END) / 1024.0 / 1024.0 / 1024.0, 2)
    FROM file_analysis
    UNION ALL
    SELECT 
        'Percentage meeting file-level conditions (%)', 
        ROUND(SUM(CASE WHEN meets_file_level_conditions THEN 1 ELSE 0 END) * 100.0 / COUNT(*), 2)
    FROM file_analysis;
    ```

    **출력 예:**

    ```text
    +----------------------------------------------+--------+
    | metric                                       | value  |
    +----------------------------------------------+--------+
    | Total files                                  |  15.00 |
    | Total size (GB)                              |   2.45 |
    | Files meeting file-level conditions          |  12.00 |
    | Size meeting file-level conditions (GB)      |   1.85 |
    | Percentage meeting file-level conditions (%) |  80.00 |
    +----------------------------------------------+--------+
    5 rows in set
    ```

    **참고 사항:**

    - 예제의 `iceberg_table`을 실제 테이블 이름으로 바꾸세요.
    - 매개변수 값(`@min_file_size_bytes`, `@max_file_size_bytes`)을 실제 다시 작성 매개변수에 맞게 조정하세요.
    - 위에 표시된 기본값은 기본 다시 작성 매개변수(min-file-size-bytes = target-file-size-bytes * 0.75, max-file-size-bytes = target-file-size-bytes * 1.8)에 대응합니다.

- 스냅샷과 브랜치의 관계 확인:

    ```sql
    SELECT
        refs_data.snapshot_id,
        snapshots.committed_at,
        snapshots.operation,
        ARRAY_SORT(refs_data.refs)
    FROM (
        SELECT
            snapshot_id,
            ARRAY_AGG(CONCAT(type, ':', name)) AS refs
        FROM
            iceberg_table$refs
        GROUP BY
            snapshot_id
    ) AS refs_data
    JOIN (
        SELECT
            snapshot_id,
            committed_at,
            operation
        FROM
            iceberg_table$snapshots
    ) AS snapshots
    ON refs_data.snapshot_id = snapshots.snapshot_id
    ORDER BY
        snapshots.committed_at;

    +---------------------+----------------------------+-----------+-------------------------------------+
    | snapshot_id         | committed_at               | operation | ARRAY_SORT(refs_data.refs)          |
    +---------------------+----------------------------+-----------+-------------------------------------+
    | 8272911997874079853 | 2025-07-10 15:27:07.177000 | append    | ["BRANCH:b1", "TAG:t1"]             |
    | 1325777059626757917 | 2025-07-10 15:27:07.530000 | append    | ["BRANCH:b2", "TAG:t2"]             |
    |   76492482642020578 | 2025-07-10 15:27:07.865000 | append    | ["BRANCH:b3", "TAG:t3"]             |
    | 1788715857849070138 | 2025-07-12 04:15:19.626000 | append    | ["BRANCH:main", "TAG:t4", "TAG:t5"] |
    +---------------------+----------------------------+-----------+-------------------------------------+
    ```
