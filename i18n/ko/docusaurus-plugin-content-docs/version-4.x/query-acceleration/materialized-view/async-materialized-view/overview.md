비동기 구체화된 뷰는 뷰의 유연성과 물리적 테이블의 높은 성능을 결합한 쿼리 가속 솔루션입니다. 쿼리 결과를 미리 계산하여 저장하므로, 이후 쿼리는 구체화된 결과 집합을 직접 조회할 수 있어 복잡한 SQL을 반복 실행하는 데 따른 오버헤드를 줄일 수 있습니다.

## 빠르게 살펴보기 {#quick-tour}

비동기 구체화된 뷰를 사용하기 전에 다음 사항을 확인하세요.

- 업무에 쿼리 가속, ETL 간소화, 레이크하우스 외부 테이블 가속 또는 쓰기 최적화가 필요한가요?
- 쿼리가 SPJG(SELECT-PROJECT-JOIN-GROUP-BY) 패턴을 따르나요?
- 데이터에 최종 일관성(실시간이 아닌 동기화)을 적용해도 괜찮은가요?
- 기본 테이블의 Catalog가 지원 범위(Internal/Hive/Iceberg/Paimon/Hudi/JDBC/ES)에 포함되나요?
- 갱신 비용을 줄이기 위해 파티션 단위 증분 갱신이 필요한가요?

## 사용 사례 {#use-cases}

<!-- Knowledge type: scenario description -->

비동기 구체화된 뷰는 주로 다음 네 가지 시나리오에 활용됩니다.

| 시나리오 | 효과 |
| :--- | :--- |
| 쿼리 가속 및 동시 처리 성능 향상 | 쿼리 속도와 동시 처리 성능을 크게 높이고 리소스 사용량을 줄입니다 |
| ETL 워크플로 간소화 | 추출, 변환 및 데이터 적재(ETL) 프로세스를 간소화하고 개발 효율을 높입니다 |
| 레이크하우스 외부 테이블 쿼리 가속 | 레이크하우스 아키텍처에서 외부 데이터 소스에 대한 쿼리 속도를 크게 높입니다 |
| 쓰기 효율 향상 | 리소스 경합을 줄이고 데이터 쓰기 프로세스를 최적화하며 일관성과 무결성을 보장합니다 |

## 제한 사항 {#limitations}

<!-- Knowledge type: limitation description -->

비동기 구체화된 뷰를 사용하기 전에 다음 제한 사항을 확인하세요.

- **데이터 일관성**: 비동기 구체화된 뷰는 기본 테이블과 최종 일관성을 유지하지만, 실시간으로 동기화할 수 없으며 실시간 일관성을 보장하지 않습니다.
- **윈도우 함수**: 현재 윈도우 함수가 포함된 쿼리를 구체화된 뷰 기반의 형태로 투명하게 재작성하는 기능은 지원되지 않습니다.
- **다중 테이블 시나리오**: 구체화된 뷰가 쿼리에 사용된 테이블보다 더 많은 테이블을 조인하는 경우(예: 쿼리는 t1과 t2만 사용하지만 구체화된 뷰에는 t1, t2, t3이 포함된 경우), 현재 투명한 재작성이 지원되지 않습니다.
- **투명한 재작성에서 지원하지 않는 연산자**: 구체화된 뷰에 `UNION ALL`, `LIMIT`, `ORDER BY` 또는 `CROSS JOIN`이 포함되어 있어도 구체화된 뷰를 정상적으로 생성할 수는 있지만, 투명한 재작성에는 사용할 수 없습니다.
- **데이터 타입 제한**: 현재 구체화된 뷰를 생성할 때 `VARBINARY` 타입은 지원되지 않습니다.

## 동작 원리 {#principles}

<!-- Knowledge type: principle description -->

비동기 구체화된 뷰는 본질적으로 MTMV 타입의 내부 테이블입니다. 구체화된 뷰가 생성되면 시스템은 갱신 작업도 함께 등록합니다. 작업이 실행되면 `INSERT OVERWRITE` 문을 통해 최신 데이터를 구체화된 뷰에 기록합니다.

### 갱신 메커니즘 {#refresh-mechanism}

실시간 증분 갱신을 수행하는 동기 구체화된 뷰와 달리, 비동기 구체화된 뷰는 더 유연한 갱신 옵션을 제공합니다.

| 갱신 모드 | 설명 | 적합한 시나리오 |
| :--- | :--- | :--- |
| **전체 갱신** | 구체화된 뷰 정의 SQL이 참조하는 모든 데이터를 다시 계산하고 그 전체를 구체화된 뷰에 기록합니다 | 데이터 양이 적거나 전체 데이터의 일관성을 보장해야 하는 경우 |
| **파티션 단위 증분 갱신** | 기본 테이블의 파티션 데이터 변경을 지능적으로 식별하고 영향을 받는 파티션만 갱신합니다 | 데이터 양이 많고 변경이 특정 파티션에 집중되는 경우 |

- **전체 갱신**: 구체화된 뷰의 데이터가 기본 테이블과 완전히 일치하도록 보장하지만, 더 많은 컴퓨팅 리소스와 시간이 필요할 수 있습니다.
- **파티션 단위 증분 갱신**: 최종 일관성을 보장하면서 갱신에 필요한 리소스와 시간을 크게 줄입니다.

### 투명한 재작성 {#transparent-rewriting}

투명한 재작성은 데이터베이스가 쿼리 성능을 최적화하는 중요한 방법입니다. 사용자 쿼리를 처리할 때 시스템은 적절한 구체화된 뷰를 사용하도록 SQL을 자동으로 재작성하여 실행 효율을 높이고 연산 비용을 줄입니다. 전체 과정은 사용자에게 투명하게 이루어지며, 사용자가 개입할 필요가 없습니다.

Doris 비동기 구체화된 뷰는 SPJG(SELECT-PROJECT-JOIN-GROUP-BY) 패턴에 기반한 투명한 재작성 알고리즘을 사용합니다.

1. SQL의 구조 정보를 심층 분석합니다.
2. 투명한 재작성에 적합한 구체화된 뷰를 자동으로 찾아 선택합니다.
3. 후보 구체화된 뷰가 여러 개 있으면 비용 모델 등의 전략에 따라 쿼리에 응답할 최적의 구체화된 뷰를 선택하여 성능을 더욱 높입니다.

## 데이터 레이크에 비동기 구체화된 뷰 생성하기 {#creating-an-async-materialized-view-on-a-data-lake}

<!-- Use cases: external table acceleration in a lakehouse architecture -->

데이터 레이크에 비동기 구체화된 뷰를 생성하는 구문은 내부 테이블에 생성하는 구문과 동일하지만, 다음 사항에 유의해야 합니다.

- **메타데이터 소스**: 구체화된 뷰 갱신에 필요한 파티션 버전 등의 정보는 외부 환경에서 직접 가져오는 것이 아니라 데이터 레이크의 메타데이터 캐시에서 가져옵니다. 따라서 갱신이 완료된 후 데이터는 Doris를 통해 데이터 레이크를 쿼리한 결과와 일치하지만, 캐시 갱신 상태에 따라 다른 엔진의 결과와는 일치하지 않을 수 있습니다.
- **외부 변경 감지**: Doris가 제어하지 않는 외부 프로세스(예: Spark, Hive 또는 Flink 작업)가 기반 Hive 데이터를 변경했지만 메타데이터는 변경되지 않은 경우(예: `insert overwrite` 실행 시), 구체화된 뷰는 자신이 기본 테이블과 일치한다고 잘못 판단합니다. 그러나 쿼리 결과는 Doris를 통해 데이터 레이크를 쿼리한 결과와 일치하지 않게 됩니다. 구체화된 뷰를 수동으로 강제 갱신하면 이 문제를 해결할 수 있습니다.
- **Iceberg 제한 사항**: Iceberg에 파티션이 있는 구체화된 뷰를 생성할 때는 파티션 컬럼이 하나인 Iceberg 테이블만 지원되며, 파티션 진화는 제한적으로 지원됩니다. 예를 들어 시간 타입 파티션의 시간 범위 변경은 지원되지만, 파티션 필드 자체가 변경되면 구체화된 뷰 갱신에 실패합니다.
- **Hudi 제한 사항**: Hudi에 구체화된 뷰를 생성하면 시스템은 기본 테이블 데이터의 변경 여부를 감지할 수 없습니다. 구체화된 뷰 또는 일부 파티션이 갱신되었다면 기본 테이블과 동기화된 것으로 간주합니다. 따라서 Hudi에 구체화된 뷰를 생성하는 것은 필요할 때 수동으로 갱신하는 시나리오에만 적합합니다.

#### 외부 테이블 기반 구체화된 뷰의 투명한 재작성 활성화 {#enabling-transparent-rewriting-for-external-table-materialized-views}

외부 테이블을 사용하는 구체화된 뷰는 기본적으로 투명한 재작성에 사용되지 않습니다. 활성화하려면 다음을 실행하세요.

```sql
SET materialized_view_rewrite_enable_contain_external_table = true;
```

#### 외부 테이블의 투명한 재작성 성능 최적화 {#performance-optimization-for-external-table-transparent-rewriting}

2.1.11부터 Doris는 외부 테이블이 포함된 사용 가능한 구체화된 뷰를 찾는 성능을 개선하는 데 중점을 두어, 외부 테이블의 투명한 재작성 성능을 최적화했습니다.

외부 테이블이 포함된 파티션 구체화된 뷰의 투명한 재작성이 느리다면 `fe.conf`에서 다음 매개변수를 조정할 수 있습니다.

| 매개변수 | 기본값 | 설명 | 버전 |
| :--- | :--- | :--- | :--- |
| `max_hive_partition_cache_num` | 10000 | Hive Metastore의 테이블 수준 파티션 캐시 최대 개수입니다. Hive 외부 테이블에 파티션이 많으면 `20000` 이상으로 설정하세요 | - |
| `external_cache_expire_time_minutes_after_access` | 10분 | 캐시된 객체에 마지막으로 접근한 시점부터 만료되기까지의 시간입니다. 필요에 따라 늘릴 수 있습니다(외부 테이블 스키마 캐시와 Hive 메타데이터 캐시에 모두 적용) | - |
| `external_cache_refresh_time_minutes` | 10분 | 외부 테이블 메타데이터 캐시 객체의 자동 갱신 주기입니다. 필요에 따라 늘릴 수 있습니다 | 3.1+ |

외부 테이블 메타데이터 캐시의 자세한 설정은 [메타데이터 캐시](../../../lakehouse/meta-cache.md)를 참조하세요.

## 구체화된 뷰와 OLAP 내부 테이블의 관계 {#relationship-between-materialized-views-and-olap-internal-tables}

<!-- Knowledge type: implementation mechanism description -->

비동기 구체화된 뷰의 SQL 정의에 사용하는 기본 테이블 모델에는 제한이 없습니다. Duplicate 모델, Unique 모델(merge-on-write 또는 merge-on-read), Aggregate 모델 등을 사용할 수 있습니다.

구체화된 뷰 자체는 내부적으로 Duplicate 모델의 OLAP 테이블을 기반으로 구현되며, 이론적으로 Duplicate 모델의 모든 핵심 기능을 지원할 수 있습니다. 그러나 구체화된 뷰가 데이터 갱신 작업을 안정적이고 효율적으로 실행하도록 보장하기 위해, 기능에 다음과 같은 필수 제한을 적용합니다.

- **파티션 작업**: 구체화된 뷰의 파티션은 기본 테이블을 바탕으로 자동 생성되고 관리됩니다. 사용자는 구체화된 뷰에 파티션 작업을 수행할 수 없습니다.
- **삭제 및 이름 변경**: 구체화된 뷰에는 관련 작업(JOB)이 연결되어 있으므로 `DROP TABLE` 또는 `RENAME TABLE` 명령을 사용할 수 없습니다. 해당 작업을 수행하려면 구체화된 뷰 전용 명령을 사용하세요.
- **컬럼 데이터 타입**: 구체화된 뷰의 컬럼 데이터 타입은 생성 시 지정한 쿼리 문에서 자동으로 도출되며 수정할 수 없습니다. 수정하면 갱신 작업이 실패할 수 있습니다.
- **속성 수정**: 구체화된 뷰에는 Duplicate 테이블에 없는 속성이 있습니다. 이러한 속성은 구체화된 뷰 전용 명령으로 수정해야 합니다. 그 밖의 공통 속성은 `ALTER TABLE` 명령으로 수정합니다.

## 자주 묻는 질문 {#faq}

<!-- Knowledge type: Q&A -->

**Q1: 비동기 구체화된 뷰가 기본 테이블과의 실시간 데이터 일관성을 보장할 수 있나요?**

아니요. 비동기 구체화된 뷰는 기본 테이블과 최종 일관성을 유지하지만 실시간으로 동기화할 수는 없습니다. 실시간 일관성이 필요하다면 동기 구체화된 뷰를 고려하세요.

**Q2: 윈도우 함수가 포함된 쿼리를 재작성할 수 없는 이유는 무엇인가요?**

현재 투명한 재작성 알고리즘은 아직 윈도우 함수를 지원하지 않습니다. 윈도우 함수가 포함된 쿼리는 구체화된 뷰 기반의 형태로 재작성되지 않습니다.

**Q3: 외부 테이블 기반 구체화된 뷰가 재작성 시 선택되지 않는 이유는 무엇인가요?**

외부 테이블 기반 구체화된 뷰는 기본적으로 투명한 재작성에 사용되지 않습니다. 재작성에 사용하려면 `materialized_view_rewrite_enable_contain_external_table = true`를 설정하세요.

**Q4: 외부 프로세스가 Hive 외부 테이블 데이터를 수정한 후 구체화된 뷰의 쿼리 결과가 일치하지 않는 이유는 무엇인가요?**

Spark, Hive 또는 Flink와 같은 외부 프로세스가 Hive 데이터를 수정했지만 메타데이터가 변경되지 않은 경우(예: `insert overwrite`), 구체화된 뷰는 변경을 감지할 수 없습니다. 구체화된 뷰를 수동으로 강제 갱신하면 이 문제를 해결할 수 있습니다.

**Q5: Hudi 기반 구체화된 뷰를 자동으로 갱신할 수 있나요?**

기본 테이블의 변경을 감지할 수 없으므로, 필요할 때 수동으로 갱신하는 시나리오에만 적합합니다.
