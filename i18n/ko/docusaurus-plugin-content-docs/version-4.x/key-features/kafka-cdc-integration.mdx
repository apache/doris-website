> **요약** Apache Doris는 세 가지 경로를 통해 Kafka 토픽과 CDC 변경 스트림을 기본 기능으로 수집합니다. FE 내부에서 실행되며 외부 서비스가 필요 없는 Kafka consumer를 원한다면 **Routine Load**를 사용하세요. MySQL/Postgres/Oracle 데이터베이스 전체를 동기화하고 [Stream Load](./stream-load) 2PC로 exactly-once를 보장하려면 Flink CDC와 **Flink Doris Connector**를 함께 사용하세요. 이미 Kafka Connect를 실행 중이고 payload가 Avro, Protobuf 또는 Debezium 형식이라면 **Doris Kafka Connector**를 사용하세요. 세 경로 모두 동일한 Unique Key Merge-on-Write 테이블에 데이터를 적재하므로, 어느 경로를 선택하든 순서가 뒤바뀐 이벤트와 [삭제](./data-update-delete)는 같은 방식으로 처리됩니다.

## Apache Doris에서 Kafka 및 CDC 통합을 사용하는 이유는 무엇인가요? {#why}

Apache Doris의 Kafka 및 CDC 통합은 스트리밍 데이터 적재, exactly-once 전달, 순서가 뒤바뀐 이벤트 처리를 엔진 내부에서 수행하므로, 토픽이나 binlog의 데이터가 쿼리 가능한 행이 되기까지의 경로가 짧습니다. 대부분의 데이터 웨어하우스에서는 스트리밍 데이터 적재 기능을 별도로 구성해야 합니다. Kafka consumer를 구축하고 offset 관리, 재시도, 스키마 매핑, 삭제 처리를 다시 구현한 뒤, 웨어하우스가 중단되었을 때 consumer가 정상적으로 종료되기를 기대해야 합니다. 또는 앞단에 Flink를 실행하고 추가 클러스터 비용을 부담해야 합니다. 아니면 "실시간"을 포기하고 [일괄 데이터 적재](./batch-load)로 오 분마다 배치를 전송해야 합니다.

- CDC 파이프라인이 checkpoint 실패 후 마지막 배치를 다시 처리하면서 버퍼에 저장했던 모든 행이 중복됩니다.
- 어느 쓰기가 더 최신인지 엔진에 알려 주는 정보가 없으면, Unique Key 테이블에 순서가 뒤바뀐 업데이트가 들어왔을 때 이전 버전이 적용됩니다.
- Avro나 Protobuf를 담은 Kafka 토픽은 JSON이나 CSV만 지원하는 HTTP 데이터 적재 API에 맞지 않습니다.

Doris는 이러한 처리 대부분을 엔진 내부에서 수행하므로, Kafka 토픽이나 MySQL binlog의 데이터가 쿼리 가능한 행이 되기까지의 경로가 짧고 발생 가능한 장애 유형도 명확합니다.

## Apache Doris의 Kafka 및 CDC 통합이란 무엇인가요? {#what}

Apache Doris의 Kafka 및 CDC 통합은 공통 기반을 공유하는 스트리밍 및 CDC 데이터 적재 경로 모음입니다. 이 기반은 `Label`로 식별하는 트랜잭션 데이터 적재, upsert와 삭제를 위한 Unique Key Merge-on-Write 테이블, 이벤트가 순서와 다르게 도착해도 최종 적용 버전을 결정하는 sequence column으로 구성됩니다. 각 경로는 consumer를 실행하는 주체가 다릅니다.

**주요 용어**

- **`Routine Load`**: FE가 관리하는 장기 실행 Kafka consumer입니다. `CREATE ROUTINE LOAD` 문 하나를 실행하면 FE가 BE에 작업을 예약하고, BE는 배치를 가져와 각 배치를 트랜잭션 데이터 적재로 처리합니다.
- **`Stream Load 2PC`**: `PRECOMMITTED` 상태에서 대기하는 HTTP 데이터 적재입니다. 후속 호출에서 `txn_operation: commit` 또는 `txn_operation: abort`를 보내면 다음 단계로 진행합니다. 이처럼 두 단계로 나누는 방식이 외부 sink의 exactly-once를 가능하게 합니다.
- **`Flink Doris Connector`**: Stream Load 2PC를 구동하고 commit을 Flink checkpoint와 연동하는 외부 Flink sink입니다. Flink CDC와 함께 사용하면 데이터베이스 전체를 동기화하고 DDL을 전파합니다.
- **`Doris Kafka Connector`**: Kafka Connect sink 플러그인입니다. Kafka Connect의 converter 생태계를 그대로 활용하므로, 사용자 정의 serializer 없이 Avro, Protobuf, Debezium payload를 처리할 수 있습니다.
- **`function_column.sequence_col`**: Unique Key MOW 테이블의 테이블별 속성입니다. 행의 최종 적용 버전을 결정하는 값이 담긴 컬럼을 지정합니다. 순서가 뒤바뀐 CDC 이벤트에 대비하는 안전장치입니다.

## Apache Doris의 Kafka 및 CDC 통합은 어떻게 동작하나요? {#how}

Apache Doris의 Kafka 및 CDC 통합 경로는 데이터가 FE에 도달하면 모두 같은 수명 주기를 따릅니다. 배치를 가져오고, label이 지정된 트랜잭션으로 묶고, 확인 후 commit한 다음 모든 복제본에 게시합니다.

1. **consumer가 배치를 가져옵니다.** Routine Load는 BE에 작업을 예약합니다. 이 작업은 Kafka에서 데이터를 가져오며, `max_batch_rows`(기본값 20M), `max_batch_size`(기본값 1 GB), `max_batch_interval`(기본값 60 s) 중 하나에 먼저 도달하면 배치를 마칩니다. Flink CDC는 chunked HTTP Stream Load로 행을 스트리밍하며, 이 연결은 checkpoint 구간 내내 열려 있습니다.
2. **배치가 트랜잭션이 됩니다.** BE는 `Label`을 지정해 트랜잭션을 시작합니다. Routine Load는 label을 생성하고, Flink Doris Connector는 label에 checkpoint ID를 붙입니다. 어느 경우든 같은 label로 다시 제출하면 중복이 제거됩니다.
3. **commit은 확인을 기다립니다.** Routine Load는 배치가 도착하는 즉시 commit하고, 성공한 경우에만 Kafka offset을 이동합니다. Flink CDC는 `PRECOMMITTED`에서 멈춥니다. 다음 checkpoint barrier가 `txn_operation: commit`을 실행하고, checkpoint가 실패하면 `abort`가 실행되어 임시 저장된 데이터를 폐기합니다.
4. **게시 후 행을 쿼리할 수 있습니다.** 백그라운드 데몬이 모든 복제본에 `PublishVersion`을 전송합니다. 트랜잭션이 `VISIBLE`에 도달하면 새 행을 쿼리할 수 있습니다. 같은 트랜잭션에 속한 tablet 중 일부만 반영되는 일은 없습니다.
5. **오류가 발생하면 작업이 일시 중지되고 데이터는 보존됩니다.** Routine Load 배치가 `max_error_number`(기본값 0)를 초과하면 작업은 `PAUSED` 상태로 전환되고 FE에 마지막 오류 URL을 보관합니다. 원본 데이터를 수정한 후 재개하면 됩니다. offset은 기존 위치에 유지됩니다.

## 빠른 시작 {#quick-start}

```sql
CREATE TABLE events (
  user_id BIGINT, event_type STRING, ts DATETIME
)
DUPLICATE KEY(user_id)
DISTRIBUTED BY HASH(user_id) BUCKETS 8;

CREATE ROUTINE LOAD events_kafka ON events
COLUMNS(user_id, event_type, ts)
PROPERTIES (
  "format" = "json",
  "jsonpaths" = "[\"$.user_id\",\"$.event_type\",\"$.ts\"]"
)
FROM KAFKA (
  "kafka_broker_list" = "localhost:9092",
  "kafka_topic" = "events",
  "property.kafka_default_offsets" = "OFFSET_BEGINNING"
);
```

**예상 결과**

```
+--------+--------------+---------+----------------------+
| Id     | Name         | State   | Statistic            |
+--------+--------------+---------+----------------------+
| 100123 | events_kafka | RUNNING | {"loadedRows":4821,..|
+--------+--------------+---------+----------------------+
```

`SHOW ROUTINE LOAD FOR events_kafka`는 작업의 `RUNNING` 상태, partition별 마지막으로 소비한 offset, 데이터가 적재된 행 수를 보여 줍니다. `PAUSE`, `RESUME`, `STOP`은 다른 Doris 작업과 동일하게 동작합니다.

CDC를 사용하려면 consumer를 Flink CDC와 함께 사용하는 Flink Doris Connector로 교체합니다(Flink 작업 하나, MySQL source, Doris sink, `sink.enable-2pc = true`). 스키마와 sequence column은 Doris에서 설정합니다:

```sql
CREATE TABLE orders (
  order_id BIGINT, status STRING, updated DATETIME
)
UNIQUE KEY(order_id) DISTRIBUTED BY HASH(order_id) BUCKETS 8
PROPERTIES ("function_column.sequence_col" = "updated");
```

`sequence_col` 설정은 최신 이벤트가 도착한 뒤 지연된 CDC 이벤트가 들어와도 올바른 결과를 유지하도록 해 줍니다. 이전 `updated` 값은 적용되지 않고 최신 값이 적용되므로, 도착 순서와 관계없이 결과가 같습니다.

## Apache Doris의 Kafka 및 CDC 통합은 언제 사용해야 하나요? {#when}

스트리밍 이벤트나 upstream 데이터베이스의 변경 사항을 오 분 단위 배치가 아닌 exactly-once 전달과 올바른 순서로 Doris에 적재해야 할 때 Apache Doris의 Kafka 및 CDC 통합을 사용하세요.

**적합한 경우**

- CSV나 JSON을 담은 Kafka 토픽을 추가 서비스 없이 Doris에 적재하려는 경우. Routine Load가 가장 짧은 경로입니다.
- MySQL, Postgres 또는 Oracle CDC를 exactly-once 전달과 DDL 전파를 지원하며 Doris에 적재하려는 경우. Flink Doris Connector와 Flink CDC를 함께 사용하세요.
- 이미 시스템에서 Kafka Connect를 실행 중이고 payload가 Avro, Protobuf 또는 Debezium 형식인 경우. Doris Kafka Connector를 사용하면 형식 불일치 문제를 피할 수 있습니다.
- 순서가 뒤바뀐 쓰기도 올바르게 처리해야 하는 Unique Key 테이블 기반의 실시간 대시보드. 위의 어느 경로든 `function_column.sequence_col`과 함께 사용하세요.

**적합하지 않은 경우**

- Routine Load를 통해 Kafka의 Avro를 가져오는 경우. Routine Load는 CSV와 JSON만 읽습니다. upstream에서 변환하거나 적절한 converter를 설정한 Doris Kafka Connector를 사용하세요.
- 마이크로서비스가 이벤트마다 `INSERT INTO ... VALUES`를 실행하는 경우. 이는 Kafka나 CDC의 문제가 아닙니다. BE가 서버 측에서 작은 쓰기를 배치로 묶도록 [Group Commit](./group-commit)을 사용하세요.
- Kafka retention이 짧은 토픽에 Routine Load를 사용하는 경우. retention이 24 h인데 작업이 이틀 동안 일시 중지되면, 저장된 offset이 현재 사용 가능한 가장 이른 offset보다 뒤처져 Kafka가 "out of range" 오류로 재개를 거부합니다. retention을 늘리거나 버퍼링을 지원하는 connector를 사용하세요.
- FE만으로 offset lag을 모니터링하려는 경우. FE는 현재 lag 메트릭을 제공하지 않습니다([미해결 이슈](https://github.com/apache/doris/issues/7113)). Kafka 측 consumer-lag exporter에서 메트릭을 수집하거나 BE 측 처리율을 확인하세요.
- **클라우드 / 스토리지와 컴퓨팅이 분리된 배포 환경에서** Merge-on-Write Unique Key 테이블에 Stream Load 2PC를 사용하는 경우: BE가 이 조합을 거부하므로, 해당 환경에서는 Flink Connector의 exactly-once 경로가 `Label` 기반 중복 제거와 sequence column을 사용하는 방식으로 전환됩니다. 온프레미스 클러스터에서는 MoW에 대해 전체 Stream Load 2PC 경로를 사용할 수 있습니다.

## 성능 및 수치 {#performance}

"Flink의 Apache Doris 실시간 쓰기가 속도와 exactly-once를 모두 보장하는 방법"(2022년 칠월 릴리스 블로그)에 따르면, Stream Load 30개를 동시에 실행하는 환경에서 end-to-end 지연 시간은 일 초 미만으로 유지되었습니다. Flink 작업 20개는 초당 약 100,000건의 upstream 이벤트를 지속적으로 처리했으며, 높은 동시성에서 BE의 CPU 사용량은 기존 데이터 적재 경로에 비해 약 25% 줄었습니다. 출처: [Apache Doris 블로그](https://doris.apache.org/blog/Flink-realtime-write/).
