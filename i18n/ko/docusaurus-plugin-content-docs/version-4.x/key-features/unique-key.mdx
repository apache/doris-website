> **요약** Apache Doris Unique Key 모델은 기본 키마다 행을 하나씩 유지하는 기본 키 테이블 모델로, 트랜잭션 데이터베이스처럼 SQL `UPDATE`와 `DELETE`를 지원합니다. 부분 컬럼 upsert는 [Stream Load](./stream-load.mdx)에서 테이블로 바로 반영됩니다. 버전 2.1부터 Unique Key 모델은 기본적으로 Merge-on-Write로 동작하므로, 쓰기 시점에 중복을 처리하고 쿼리는 읽기 시점에 버전을 병합할 필요가 없습니다.

![Unique Key 소개 일러스트](/images/next/key-features/unique-key.jpg)

## Apache Doris Unique Key 모델을 사용하는 이유는 무엇인가요? {#why}

Apache Doris Unique Key 모델은 OLAP 엔진에 실질적인 기본 키 동작을 제공합니다. 키마다 행을 하나씩 유지하고, 쓰기 즉시 고유성을 보장하며, 파티션을 다시 쓰지 않고도 SQL `UPDATE`/`DELETE`를 실행할 수 있습니다. 대부분의 분석 엔진은 테이블을 추가 전용으로 취급합니다. 그런데 CDC가 필요해지면 상황이 달라집니다. MySQL의 행이 업데이트되고, 사용자가 GDPR에 따라 삭제를 요청하며, 늦게 도착한 이벤트가 이전 이벤트를 덮어써야 합니다. 추가 전용 테이블 모델에서는 이러한 변경 사항을 기록할 수는 있지만, 파티션 전체를 다시 쓰지 않고는 웨어하우스에서 이전 버전을 없앨 수 없습니다.

- MySQL을 감시하는 Flink CDC 작업은 모든 기본 키 업데이트를 수 초 안에 반영해야 합니다.
- 주문 상태 테이블의 상태는 `created`, `paid`, `shipped`, `delivered`로 차례로 바뀌며, 쿼리에는 최신 상태만 보여야 합니다.
- 사용자 프로필 테이블은 실시간 조인에 사용되며, 조인에 어제의 이메일 주소가 나타나서는 안 됩니다.

Unique Key 모델은 이런 상황을 위한 테이블 모델입니다. 기존 키로 새 데이터를 쓰면 이전 행을 대체하고, `UPDATE`와 `DELETE`를 SQL로 실행할 수 있으며, 분석 쿼리는 여전히 컬럼 기반 처리 속도로 실행됩니다. 다른 OLAP 엔진에서 가장 비슷한 기능은 ClickHouse의 `ReplacingMergeTree`이지만, 즉각적인 고유성을 보장하지는 않습니다. 백그라운드 병합이 실행될 때까지 중복 행이 계속 보이며, 그 이후에도 엔진이 보장하는 것은 최종적인 중복 제거뿐입니다. 쓰기 직후의 쿼리에는 여전히 이전 버전이 보일 수 있습니다. 이를 해결하기 위해 `SELECT ... FINAL`로 읽기 시점에 중복 제거를 강제할 수 있지만, 상당한 비용이 듭니다. Unique Key에서는 이런 절충이 필요하지 않습니다. 쓰기 시점에 새 행이 이전 행을 대체하므로, 다음 쿼리에는 키마다 행이 하나씩만 보입니다.

## Apache Doris Unique Key 모델이란 무엇인가요? {#what}

Apache Doris Unique Key 모델은 기본 키마다 정확히 하나의 행을 유지하는 테이블 모델이며, Merge-on-Write 엔진이 쓰기 시점에 이를 보장합니다. `UNIQUE KEY(...)` 절은 `CREATE TABLE`에서 키 컬럼을 지정하며, 나머지는 모두 값 컬럼입니다. 키가 같은 두 행은 공존할 수 없습니다. 기존 키로 새 데이터를 쓰면 해당 행을 대체합니다.

```sql
... UNIQUE KEY(order_id) ...
... UNIQUE KEY(tenant_id, user_id) ...
```

FE Catalog는 이를 `KeysType.UNIQUE_KEYS`로 기록하며, 스토리지 엔진은 이후 이 규약을 준수합니다. 모델은 테이블 생성 시점에 고정되며 나중에 변경할 수 없습니다.

**주요 용어**

- **기본 키**: `UNIQUE KEY(...)`에 지정된 컬럼입니다. 디스크에서 데이터를 정렬하는 기준이 되며 고유성도 보장합니다.
- **값 컬럼**: 키 컬럼을 제외한 모든 컬럼입니다. 집계 없이 쓰인 그대로 저장됩니다.
- **Merge-on-Write (MoW)**: 2.1부터 기본 백엔드입니다. 새 데이터를 쓸 때 기존 행을 찾고, rowset별 삭제 비트맵에서 해당 행 ID의 비트를 켠 다음, 새 행을 새로운 rowset에 추가합니다.
- **Merge-on-Read (MoR)**: 이전 백엔드입니다. 쓰기에서는 행을 추가하고, 읽기에서는 키별로 여러 버전을 즉석에서 병합합니다. 여전히 `enable_unique_key_merge_on_write = false`로 선택할 수 있습니다.
- **삭제 비트맵**: `(rowset_id, segment_id, version)`을 키로 하며, 쿼리가 건너뛰어야 할 행 ID를 담은 Roaring 비트맵입니다. 읽기 시점의 병합을 대체하는 MoW의 자료 구조입니다.
- **시퀀스 컬럼** (`function_column.sequence_col`): 두 업데이트가 같은 키를 가질 때 어느 쓰기를 적용할지 결정하는 값 컬럼입니다. 순서가 뒤바뀐 CDC 이벤트에서도 이를 사용해 더 최신 상태를 유지합니다.
- **부분 컬럼 업데이트**: 일부 컬럼만 쓰는 upsert입니다. Apache Doris는 기존 행에서 나머지 컬럼을 읽어 완전한 행을 다시 씁니다.
- **`__DORIS_DELETE_SIGN__`**: 숨겨진 tinyint 컬럼입니다. 어떤 데이터 적재 경로에서든 이 값을 `1`로 설정하면 해당 행을 소프트 삭제합니다.

## Apache Doris Unique Key 모델은 어떻게 동작하나요? {#how}

Apache Doris Unique Key 모델은 각 upsert를 다섯 단계로 실행합니다. 배치를 버퍼링하고, 세그먼트별 기본 키 인덱스에서 키를 조회하고, 이전 행의 삭제 비트맵 비트를 켜고, 시퀀스 컬럼으로 적용 순서를 결정한 뒤 새 rowset을 공개합니다.

Unique Key MoW 테이블에 대한 upsert를 살펴보겠습니다.

1. **배치를 버퍼링합니다.** BE는 들어오는 행을 memtable에 모아 키를 기준으로 정렬합니다.
2. **각 키를 조회합니다.** 배치의 각 키에 대해 BE는 세그먼트별 기본 키 인덱스를 조회하여 기존 rowset과 행 ID를 찾습니다. 키마다 한 번의 짧은 읽기가 발생합니다. 이 인덱스는 각 세그먼트가 플러시될 때 만들어지는 정렬된 페이지 구조로, 개념적으로 RocksDB의 파티션 인덱스와 비슷합니다.
3. **이전 행을 표시합니다.** 영향을 받는 각 rowset의 삭제 비트맵에서 이전 행 ID의 비트를 켭니다. 비트맵은 `(rowset_id, segment_id, version)`별로 존재하며, compaction이 공간을 회수할 때까지 이전 데이터는 디스크에 남아 있습니다.
4. **시퀀스 컬럼으로 적용 순서를 결정합니다.** `function_column.sequence_col`이 설정되어 있으면 MoW는 들어오는 행의 시퀀스 값과 현재 행의 `__DORIS_SEQUENCE_COL__`을 비교합니다. 더 큰 값이 우선합니다. 값이 같으면 데이터 적재 순서를 따릅니다. 시퀀스 타입은 정수 또는 `DATE`/`DATETIME`이어야 합니다.
5. **새 rowset을 공개합니다.** 트랜잭션이 커밋되면 새 버전이 조회 가능해지고, 이후 쿼리는 병합된 삭제 비트맵으로 행을 필터링합니다. 읽기 시점의 버전 병합 단계는 없습니다.

`DELETE FROM ... WHERE`도 새 rowset이 없다는 점을 제외하면 같은 흐름을 따릅니다. 부분 업데이트에는 한 단계가 추가됩니다. BE는 쓰기 전에 각 키의 변경되지 않은 컬럼을 읽어 완전한 행을 저장할 수 있도록 합니다.

## 빠른 시작 {#quick-start}

```sql
CREATE TABLE orders (
  order_id BIGINT,
  status   VARCHAR(20),
  amount   DECIMAL(10, 2),
  updated  DATETIME
)
UNIQUE KEY(order_id)
DISTRIBUTED BY HASH(order_id) BUCKETS 4
PROPERTIES ("function_column.sequence_col" = "updated");

INSERT INTO orders VALUES
  (1, 'created', 99.50, '2026-05-08 10:00:00'),
  (1, 'paid',    99.50, '2026-05-08 10:05:00'),
  (1, 'created', 99.50, '2026-05-08 09:00:00');  -- late event

SELECT * FROM orders;
```

**예상 결과**

```
+----------+--------+--------+---------------------+
| order_id | status | amount | updated             |
+----------+--------+--------+---------------------+
|        1 | paid   |  99.50 | 2026-05-08 10:05:00 |
+----------+--------+--------+---------------------+
```

세 번 삽입했지만 행은 하나입니다. 두 번째 `INSERT`는 키가 같아서 첫 번째 삽입을 덮어썼습니다. 세 번째 삽입도 다시 덮어쓰려 했지만, `updated` 값이 현재 시퀀스보다 오래되었으므로 MoW는 기존 행을 유지했습니다. `function_column.sequence_col` 속성을 제거했다면 세 번째 행이 순전히 데이터 적재 순서에 따라 최종 행으로 남았을 것입니다. CDC에서는 바라지 않는 동작입니다.

## Apache Doris Unique Key 모델은 언제 사용해야 하나요? {#when}

Apache Doris Unique Key 모델은 CDC 싱크, 실시간 차원 및 룩업 테이블, 자주 변경되는 주문/사용자/잔액 테이블, `store_row_column`과 함께 사용하는 KV 방식 포인트 조회, GDPR에 따른 행 단위 삭제, 여러 업스트림의 데이터를 합치는 와이드 테이블 구성에 적합합니다. 추가 전용 이벤트 스트림, 짧은 주기로 반복하는 단일 행 업데이트, 무작위 값이거나 폭이 매우 넓은 기본 키, 이전 Merge-on-Read 백엔드에서 `count(*)`를 많이 실행하는 워크로드에는 적합하지 않습니다.

**적합한 경우**

- MySQL, Postgres 또는 기본 키가 있는 모든 소스의 CDC 싱크. 소스의 커밋 타임스탬프나 LSN을 시퀀스 컬럼으로 함께 사용합니다. [Kafka CDC 통합](./kafka-cdc-integration.mdx)을 참고하세요.
- 팩트 테이블 쿼리에서 조인하는 실시간 차원 테이블과 룩업 테이블.
- 자주 변경되며 분석 쿼리의 대상이 되는 주문, 사용자, 잔액 또는 세션 상태 테이블.
- MoW를 `store_row_column` 및 prepared statement와 함께 사용할 때의 KV 방식 포인트 조회. [고동시성 포인트 쿼리](./high-concurrency-point-query.mdx)를 참고하세요.
- GDPR에 따른 사용자 ID 기반 행 단위 삭제. 어떤 데이터 적재 경로에서든 `__DORIS_DELETE_SIGN__`을 통한 소프트 삭제도 포함합니다.
- 각 업스트림이 컬럼 그룹을 담당하고 `partial_columns: true` Stream Load를 통해 자신의 컬럼만 쓰는 와이드 테이블 구성. [부분 컬럼 업데이트](../data-operate/update/partial-column-update.md)를 참고하세요.

**적합하지 않은 경우**

- 추가 전용 이벤트 스트림(로그, 클릭스트림, IoT 측정값). 사용하지 않는 기능을 위해 쓰기마다 키 인덱스 조회 비용을 지불하게 됩니다. Duplicate Key 모델을 선택하세요. [데이터 모델](./data-model.mdx)을 참고하세요.
- 단일 행 `UPDATE`를 짧은 주기로 반복하는 작업. 각 문이 별도 트랜잭션이므로 커밋 오버헤드가 대부분을 차지합니다. Stream Load에서 `partial_columns: true`로 배치 처리하거나 [Group Commit](./group-commit.mdx)을 사용하세요.
- 무작위 값이거나 폭이 매우 넓은 기본 키(UUID, 긴 복합 키). 각 데이터 적재 배치에서 PK 인덱스를 탐색하는데, 무작위 키는 캐시 지역성을 해칩니다. 정수를 우선 사용하고, 키를 작게 유지하며, 값을 담을 수 있는 가장 작은 타입을 사용하세요. float, double과 `ARRAY`, `MAP`, `STRUCT`, `JSON`, `VARIANT` 같은 복합 타입은 키 컬럼으로 사용할 수 없습니다.
- 파티션 키가 기본 키의 상위 집합인 경우. 파티션 컬럼은 반드시 고유 키의 부분 집합이어야 하며, 반대여서는 안 됩니다. 그렇지 않으면 같은 키가 두 파티션에 저장되어 중복 제거가 제대로 동작하지 않습니다.
- MoR 방식에서 `count(*)`를 많이 실행하는 워크로드. MoR는 쿼리 시점에 버전을 재구성하므로 개수를 세는 비용이 큽니다. Merge-on-Write(2.1부터 기본값)를 활성화하거나, 데이터가 실제로 추가 전용이라면 Duplicate로 전환하세요.
