> **要約** Apache Doris Table Stream は、MySQL binlog を読むように、Doris テーブルから行レベルの変更（挿入、更新、削除）を読み取るための、公開予定の API です。基盤となる仕組みはすでにコードベースにあります。テーブルごとの changelog、パーティションごとのオフセットを保持する `STREAM` オブジェクト、消費状況のメタデータです。この機能はまだ GA ではなく、`changelog.ttl_seconds` のデフォルトは 86,400 秒（一日）です。Doris からの一般的な CDC には、[Flink Doris Connector](../connection-integration/data-integration/flink-doris-connector) を使用してください。**ステータス: 近日公開（プレビュー）。**

## Apache Doris で changelog と Table Stream を使う理由 {#why}

Apache Doris の changelog と Table Stream は、下流のコンシューマーに行レベルの変更フィードを提供します。これにより、Flink ジョブ、監査ログ、検索インデックスは、テーブルを読み直さずに、すべての挿入、更新、削除に対応できます。Apache Doris は[変更データの取り込み](./kafka-cdc-integration)に適しています。一方、変更データを Doris から取り出すのは難しい作業です。下流のシステム（Flink ジョブ、監査ログ、別の Doris クラスター、検索インデックス）がすべての挿入、[更新、削除](./data-update-delete)に対応する必要がある場合、現在の選択肢には難点があります。

- 定期的にテーブルを読み直して差分を取る。実装は簡単ですが、実行コストが高く、リアルタイムにはなりません。
- プロデューサーから Kafka と Doris の両方に書き込む。書き込み先が二つになり、障害が起こり得る箇所も二つになります。

changelog と Table Stream は、この問題を解消します。changelog は、コミットされた変更をすべて行レベルで記録します。Table Stream は、そのログを指す名前付きのカーソルです。コンシューマーはストリームに接続し、最後のオフセット以降の変更を読み取って、受信を確認します。MySQL binlog、Snowflake Streams、Postgres の論理レプリケーションスロットと同じ考え方を、Doris の独立したオブジェクトとして提供します。

## Apache Doris の changelog と Table Stream とは {#what}

Apache Doris の changelog は、Doris がテーブルごとに保持する行レベルの変更ログです。Apache Doris の Table Stream は、それを行レベルの CDC として公開するコンシューマー向けのオブジェクトです。changelog は、コミットされた各行の変更とそのコミット時刻を記録し、オプションで変更前の値も記録します。これはクラスター間レプリケーション（CCR）で使用する binlog とは別のものです。changelog には専用の `changelog.*` プロパティがあり、同じテーブルで両方を有効にすることはできません。

Table Stream は、changelog の上に構築されるコンシューマー向けのオブジェクトです。ストリームは `CREATE STREAM <name> ON TABLE <base_table>` で作成します。各ストリームはパーティションごとに独自のオフセットを保持し、`SHOW CREATE STREAM` と、消費の進捗を示す `information_schema` ビューから SQL で確認できます。

**主な用語**

- **`changelog.enable`**: テーブルごとのプロパティ。`true` にすると、そのテーブルで changelog が有効になります。テーブル作成時にのみ設定できます。
- **`changelog.need_historical_value`**: テーブルごとのプロパティ。`true` にすると、各更新と削除の前の値も記録します。Unique Key Merge-on-Write テーブルでのみ使用できます。
- **`changelog.ttl_seconds`**: 保持期間の設定。デフォルトの TTL は一日で、テーブルの作成後にも変更できます。
- **`STREAM`**: ベーステーブルを参照し、一つのコンシューマーについてパーティションごとのオフセットを追跡する Doris のカタログオブジェクト。
- **ストリームの消費タイプ**: `detail`、`append_only`、`min_delta`（デフォルト）のいずれか。ストリームがすべての行の変更、挿入のみ、最小限の変更セットのどれを出力するかを制御します。
- **ストリームのラグ**: パーティションの可視バージョンからストリームに記録されたオフセットを引いた値。`LAG` 列に表示されます。

## Apache Doris の changelog と Table Stream の仕組み {#how}

Apache Doris の changelog は BE で行レベルの差分を記録します。Table Stream はそのログにパーティションごとのオフセットを付け、下流のコンシューマーが変更を増分で読み取って受信を確認できるようにします。

1. **テーブル作成時に changelog を有効にします。** `CREATE TABLE t (...) PROPERTIES ("changelog.enable" = "true")`。既存のテーブルで後から changelog を有効にすることはできません。BE は `changelog.ttl_seconds` に従って、tablet データとともに行レベルの差分を保持します。
2. **テーブル上にストリームを作成します。** `CREATE STREAM s ON TABLE t PROPERTIES ("type" = "min_delta")`。FE は `STREAM` オブジェクトを作成し、各パーティションの現在の可視バージョンを開始オフセットとして記録して、データベースに登録します。`show_initial_rows = true` にすると、最初の読み取りで過去の状態を返すようになります。
3. **変更を消費します。** 下流のリーダー（現時点では外部の CDC コネクター、将来的にはネイティブのコンシューマーエンドポイント）がストリームから読み取ります。バッチを読み取るたびに、パーティションごとのオフセットが進み、消費時刻が記録されます。
4. **古い変更を削除します。** すべてのストリームが読み取ったかどうかにかかわらず、`changelog.ttl_seconds` より古い変更は期限切れになり、その後、バックグラウンドの compaction によってストレージが回収されます。オフセットが保持期間の範囲外になったストリームは、新しいスナップショットからリセットする必要があります。
5. **状況を確認します。** `information_schema.table_streams` には、すべてのストリームとそのベーステーブルが一覧表示されます。`table_stream_consumption` は、パーティションごとの `UNIT`（パーティション）、`CONSUMPTION_STATUS`、`LAG`、`LAST_CONSUMPTION_TIME` を報告します。これをラグの監視に使用できます。

## クイックスタート {#quick-start}

```sql
-- 1. Enable the changelog when the source table is created
CREATE TABLE orders (
  order_id   BIGINT,
  order_date DATE,
  status     VARCHAR(16),
  amount     DECIMAL(10, 2)
)
UNIQUE KEY(order_id, order_date)
PARTITION BY RANGE(order_date) (
  PARTITION p_2026_05 VALUES [('2026-05-01'), ('2026-06-01'))
)
DISTRIBUTED BY HASH(order_id) BUCKETS 8
PROPERTIES (
  "enable_unique_key_merge_on_write" = "true",
  "changelog.enable" = "true",
  "changelog.need_historical_value" = "true",
  "changelog.ttl_seconds" = "86400"
);

-- 2. Create a Table Stream over it (planned syntax, subject to change)
CREATE STREAM orders_cdc ON TABLE orders
PROPERTIES ("type" = "min_delta", "show_initial_rows" = "false");

-- 3. Inspect the stream and its lag
SHOW CREATE STREAM orders_cdc;
SELECT * FROM information_schema.table_stream_consumption
WHERE STREAM_NAME = 'orders_cdc';
```

**期待される結果**

```
+---------+------------+-----------+--------------------+-----+----------------------+
| DB_NAME | STREAM_NAME| STREAM_ID | UNIT (partition)   | LAG | LAST_CONSUMPTION_TIME|
+---------+------------+-----------+--------------------+-----+----------------------+
| sales   | orders_cdc | 10042     | p_2026_05          | 0   | 2026-05-09 10:14:33  |
+---------+------------+-----------+--------------------+-----+----------------------+
```

`LAG = 0` は、コンシューマーがパーティションの可視バージョンに追いついていることを意味します。上流で書き込みがコミットされると `LAG` は増え、コンシューマーが読み取ると減ります。消費の遅れが `changelog.ttl_seconds` の保持期間を超えたコンシューマーは、スナップショットを再取得する必要があります。`STALE_REASON` はこのケースを報告しないため、消費の遅れを保持期間と比較してください。

## Apache Doris の changelog と Table Stream を使う場面 {#when}

GA となった後は、下流のシステムがテーブル全体を読み直さずに Doris テーブルから行レベルの変更イベントを取得する必要がある場合に、Apache Doris の changelog と Table Stream を使用してください。

**適した用途（GA 後）**

- テーブルを読み直さずに、Doris 側の変更イベントから下流の Flink ジョブや Spark ジョブを駆動する。
- すべての挿入と削除を反映する必要がある外部の検索インデックス、キャッシュ、監査ログを維持する。
- コンシューマーのオフセットを明示的に管理する必要がある Doris 間のレプリケーション。
- パーティションの `LAG` が変化したときに、外部のマテリアライズドビューの再計算を開始する。

**適さない用途（特に現時点）**

- 現時点での本番環境の CDC パイプライン。`STREAM` オブジェクトはソースツリーに存在しますが、GA は発表されていません。代わりに [Kafka と CDC の統合](./kafka-cdc-integration) を使用してください。
- changelog の保持期間が短い環境で、長期間停止するコンシューマー。消費の遅れが `changelog.ttl_seconds` を超えると、必要な変更が期限切れになり、コンシューマーは初期データを再取得する必要があります。
- ストレージとコンピュートを分離したクラスター。そこでの Table Stream のサポート方針は、まだ検討中です。
- 外部カタログのテーブル（Hive、Iceberg）の読み取り。Table Stream の対象は内部 OLAP テーブルのみです。
