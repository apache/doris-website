Apache Doris は、外部 Catalog、CDC ツール、ファイルからのデータロードによる移行をサポートします。テーブルのデータをコピーしても、移行元のトランザクション、インデックス、制約、プロシージャ、権限、SQL のセマンティクスは移行されません。まず、必要なのが一度限りのスナップショットか、更新と削除の継続的な反映かを決めてください。

## 移行方法 {#migration-paths}

| 移行元 | 一度限りの移行またはバッチ移行 | 継続的な同期 |
| --- | --- | --- |
| [PostgreSQL](./postgresql-to-doris.md) | PostgreSQL JDBC Catalog + `INSERT INTO ... SELECT` | Flink CDC。dev ではネイティブの Streaming Jobs も利用可能 |
| [MySQL](./mysql-to-doris.md) | MySQL JDBC Catalog + `INSERT INTO ... SELECT` | Flink CDC。dev ではネイティブの Streaming Jobs も利用可能 |
| [Elasticsearch](./elasticsearch-to-doris.md) | ES Catalog + `INSERT INTO ... SELECT` | 変更の捕捉、更新、削除の処理を別途設計 |
| [ClickHouse / Greenplum](./other-olap-to-doris.md) | 対応する JDBC Catalog またはファイルからのデータロード | 移行元システムによって異なる |
| [Hive / Iceberg / Hudi](./other-olap-to-doris.md#data-lake) | 対応するレイクハウス Catalog + `INSERT INTO ... SELECT` | 定期的なバッチ処理または適切なコネクター |

Catalog を使うと外部データをクエリできますが、Catalog を作成するだけでは Doris の内部テーブルにデータはコピーされません。バッチ処理の `INSERT INTO ... SELECT` は、その後の更新や削除を継続的に捕捉しません。

## 基本的な手順 {#basic-workflow}

1. 各 FE/BE からの接続、ドライバーの配置、移行元データの読み取り権限、および Catalog とテーブルの作成とデータロードに必要な Doris の権限を確認します。
2. 移行元の安定したスナップショットを確保するか、書き込みを停止する時間帯を設けます。複数のテーブルやバッチにまたがる Catalog クエリによって、全体で整合性のあるスナップショットが自動的に得られるわけではありません。
3. `DESC catalog.database.table` で実際の型の対応関係を確認し、適切な[データモデル](../table-design/data-model/intro.mdx)を使って移行先テーブルを設計します。移行元のキー、エンジン、インデックスをそのままコピーしないでください。
4. 小規模なパイロット移行を一通り実施します。MySQL と PostgreSQL のガイドには、再現可能なテーブル作成、インポート、クエリ結果が記載されています。
5. キーまたは時間で範囲を区切ってインポートし、完了した範囲と CDC の位置を記録します。結果を検証してから、読み取りトラフィックを切り替えます。

## 設定と型 {#configuration-and-types}

| 項目 | 確認する内容 |
| --- | --- |
| Catalog | ドライバー、接続先アドレス、認証、ドライバーの配置場所に関する制御。[JDBC Catalog](../lakehouse/catalogs/jdbc-catalog-overview.md) または [ES Catalog](../lakehouse/catalogs/es-catalog.md) を参照 |
| 移行先テーブル | キーモデル、パーティション、バケット、レプリカ、更新順序 |
| 型のマッピング | マッピングはインポート方法、ドライバー、Doris のバージョンによって異なる。JDBC のマッピングと CDC のマッピングは同一ではない |
| 時刻とバイナリデータ | タイムゾーン、マイクロ秒精度、バイト単位でのデータ保持を確認。一部の JDBC マッピングは 4.1.5 で変更されたため、導入しているバージョンのリファレンスを参照 |
| 増分同期 | スナップショットからログ位置への引き継ぎ、主キー、再実行、更新、削除 |

## 検証と切り替え {#validation-and-cutover}

同じ移行元スナップショットと区切られた範囲について、行数、重複を除いたキー数、NULL の数、数値の合計、最大値と最小値を比較します。タイムスタンプ、小数、バイナリデータ、配列、半構造化データの列は、値を抽出して正確に比較します。行数が一致するだけでは、正しく移行できたことの証明にはなりません。

継続的な同期では、挿入、更新、削除に加え、遅延と再起動後の動作もテストします。検証が済んでからアプリケーションの読み取り先を切り替え、移行元のデータと切り戻しの手段を保持します。

## エラーと注意点 {#errors-and-caveats}

- バッチの INSERT を繰り返すと、特に Duplicate Key テーブルでは行が重複する可能性があります。処理を再開する前に再実行の方針を決めてください。Unique Key テーブルでも、移行元で削除された行が自動的に削除されるわけではありません。
- 複数のバッチの実行中に移行元のデータが変わると、欠落や重複が生じる可能性があります。整合性のあるスナップショット、書き込みを停止する時間帯、または信頼できる CDC への引き継ぎを利用してください。
- サポートされていない型、大文字と小文字の違い、精度の変化がある場合は、`DESC` で外部テーブルを調べ、明示的に変換して再検証してください。互換性のない列を黙って省略しないでください。
- 同期 INSERT、非同期データロードジョブ、Flink、Streaming Jobs では、ステータスを確認するためのインターフェースが異なります。どの方法でも `SHOW LOAD` に頼るのではなく、該当するデータロード方法のリファレンスに従ってください。

## ベストプラクティス {#best-practices}

まず代表的な小規模テーブルから始め、実測したデータ量、クエリ負荷、利用可能なリソースに基づいてバッチサイズと並列数を決めます。切り替え前にクエリ結果と更新のセマンティクスを検証し、完了した範囲と検証記録を保持してください。
