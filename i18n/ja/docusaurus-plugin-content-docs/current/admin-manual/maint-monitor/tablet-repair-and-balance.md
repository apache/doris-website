# データレプリカの管理 {#data-replica-management}

このドキュメントはクラスター管理者向けです。Apache Doris のレプリカのバランシングと修復の仕組み、スケジューリングの優先度、レプリカの状態を確認する方法、レプリカの異常やクラスター負荷の偏りに対処する際の一般的な運用方法を説明します。

バージョン 0.9.0 以降、Doris には最適化されたレプリカ管理戦略が導入され、レプリカの状態を確認するためのツールも充実しました。このドキュメントでは、レプリカのスケジューリングの原則を理解し、レプリカの破損、ノードの停止、ディスク使用量の偏りなどが発生した場合にクラスターを迅速に復旧する方法を説明します。

> Colocation 属性を持つテーブルのレプリカ修復とバランシングについては、[Colocate Join](../../query-data/join#colocate-join) を参照してください。

## 用語 {#terminology}

| 用語 | 意味 |
| --- | --- |
| Tablet | Doris テーブルの論理シャード。テーブルは複数のシャードを持ちます。 |
| Replica | シャードのコピー。デフォルトでは、各シャードに 3 つのレプリカがあります。 |
| Healthy Replica | 所属する Backend が稼働しており、バージョンが完全なレプリカ。 |
| TabletChecker (TC) | 常駐するバックグラウンドスレッド。すべての Tablet を定期的に走査して状態を確認し、その結果に基づいて Tablet を TabletScheduler に送るかどうかを判断します。 |
| TabletScheduler (TS) | 常駐するバックグラウンドスレッド。TabletChecker から送られた Tablet の修復を処理し、クラスター内のレプリカのバランシングも行います。 |
| TabletSchedCtx (TSC) | Tablet をラップするオブジェクト。TC は Tablet を選択した後、TSC にラップして TS に送ります。 |
| Storage Medium | ストレージメディア。Doris ではパーティション単位で異なるメディア（SSD と HDD）を指定できます。レプリカのスケジューリング戦略では、メディアごとに個別にスケジュールします。 |

全体の処理フローは次のとおりです。

```text

              +--------+              +-----------+
              |  Meta  |              |  Backends |
              +---^----+              +------^----+
                  | |                        | 3. Send clone tasks
 1. Check tablets | |                        |
           +--------v------+        +-----------------+
           | TabletChecker +--------> TabletScheduler |
           +---------------+        +-----------------+
                   2. Waiting to be scheduled


```

上の図は簡略化した処理フローです。TabletChecker が Tablet の状態を確認し、修復が必要な Tablet を TabletScheduler に送ります。TabletScheduler はクローンタスクを BE に割り当てます。

## レプリカの状態 {#replica-status}

Tablet の複数のレプリカは、さまざまな要因によって状態が一致しなくなることがあります。Doris は不一致のあるレプリカを自動的に修復し、クラスターをできるだけ早く異常状態から復旧させようとします。

### レプリカの健全性ステータス {#replica-health-status}

| ステータス | 意味 |
| --- | --- |
| BAD | レプリカが破損しています。ディスク障害やバグなどによる回復不能な損傷を含みますが、それらに限りません。 |
| VERSION\_MISSING | バージョンが欠落しています。Doris ではインポートの各バッチがデータバージョンに対応し、レプリカのデータは連続する複数のバージョンで構成されます。インポートエラーや遅延などにより、一部のレプリカでデータバージョンが不完全になることがあります。 |
| HEALTHY | 健全なレプリカです。データが正常で、レプリカが配置された BE ノードも正常な状態です（ハートビートが正常で、ノードはデコミッション中ではありません）。 |

### Tablet の健全性ステータス {#tablet-health-status}

Tablet の健全性は、そのすべてのレプリカの状態によって決まります。ステータスは次のとおりです。

| ステータス | 意味 |
| --- | --- |
| REPLICA\_MISSING | レプリカが不足しています。稼働中のレプリカ数が期待されるレプリカ数より少ない状態です。 |
| VERSION\_INCOMPLETE | 稼働中のレプリカ数は期待される数以上ですが、健全なレプリカ数が期待される数より少ない状態です。 |
| REPLICA\_RELOCATING | 完全なバージョンを持つ稼働中のレプリカ数はレプリカ数の設定値と同じですが、それらを配置した BE ノードの一部が利用できない状態です（デコミッション中など）。 |
| REPLICA\_MISSING\_IN\_CLUSTER | 複数クラスター構成で、健全なレプリカ数は期待される数以上ですが、対応するクラスター内のレプリカ数が期待される数より少ない状態です。 |
| REDUNDANT | レプリカが冗長です。健全なレプリカはすべて対応するクラスター内にありますが、その数が期待される数を超えているか、利用できない余分なレプリカがあります。 |
| FORCE\_REDUNDANT | 特殊なステータスです。「既存のレプリカ数 >= 利用可能なノード数 >= 期待されるレプリカ数」であり、かつ「稼働中のレプリカ数 < 期待されるレプリカ数」の場合にのみ発生します。この場合、新しいレプリカを作成できるノードを確保するために、先にレプリカを削除する必要があります。 |
| COLOCATE\_MISMATCH | Colocation テーブル固有のシャードステータスです。シャードのレプリカ配置が Colocation Group で指定された配置と一致しません。 |
| COLOCATE\_REDUNDANT | Colocation テーブル固有のシャードステータスです。テーブルのシャードレプリカが冗長です。 |
| HEALTHY | 健全なシャードです。上記 1～8 のいずれの条件にも該当しません。 |

## レプリカの修復 {#replica-repair}

常駐バックグラウンドプロセスである TabletChecker は、すべてのシャードの状態を定期的に確認します。異常な状態のシャードは、スケジューリングと修復のために TabletScheduler に渡されます。実際の修復は BE 上のクローンタスクで行われ、FE はクローンタスクの生成のみを担当します。

> 注 1: レプリカ修復では、まずレプリカを作成または補充して期待される数にそろえ、その後に冗長なレプリカを削除します。
>
> 注 2: クローンタスクとは、指定されたリモート BE から指定された宛先 BE に、指定されたデータをコピーする処理です。

### ステータス別の修復方法 {#repair-by-status}

Doris はステータスごとに異なる修復方法を使用します。

1. REPLICA\_MISSING / REPLICA\_RELOCATING

    負荷が低く利用可能な BE ノードを宛先に、健全なレプリカをコピー元に選びます。クローンタスクはコピー元から宛先へ完全なレプリカをコピーします。レプリカの補充では、ストレージメディアを考慮せず、利用可能な BE ノードを直接選択します。

2. VERSION\_INCOMPLETE

    比較的完全なレプリカを宛先に、健全なレプリカをコピー元に選びます。クローンタスクは、コピー元から宛先のレプリカへ欠落したバージョンをコピーしようとします。

3. REPLICA\_MISSING\_IN\_CLUSTER

    REPLICA\_MISSING と同じ方法で処理します。

4. REDUNDANT

    レプリカ修復後は、通常、シャードに冗長なレプリカが存在します。次の優先順位で削除対象のレプリカを一つ選びます。

    1. レプリカを配置した BE がデコミッション済み
    2. レプリカが破損している
    3. レプリカを配置した BE に到達できない、またはデコミッション中
    4. レプリカが CLONE 状態にある（クローンタスクの実行中の中間状態）
    5. レプリカのバージョンが欠落している
    6. レプリカが別のクラスターにある
    7. レプリカを配置した BE の負荷が高い

5. FORCE\_REDUNDANT

    REDUNDANT とは異なり、この場合は稼働中のレプリカ数が期待される数より少ないものの、新しいレプリカを作成するための追加の利用可能なノードがありません。そのため、先にレプリカを削除して、新しいレプリカを作成できるノードを確保する必要があります。削除順序は REDUNDANT と同じです。

6. COLOCATE\_MISMATCH

    Colocation Group のレプリカ配置で指定された BE ノードの一つを、レプリカ補充の宛先ノードとして選びます。

7. COLOCATE\_REDUNDANT

    Colocation Group のレプリカ配置で指定されていない BE ノード上のレプリカを削除します。

Doris はレプリカの配置先を選ぶ際、同じ Tablet のレプリカを同一ホスト上の異なる BE に配置しません。これにより、そのホスト上のすべての BE が停止しても、すべてのレプリカが失われる事態を防ぎます。

### スケジューリングの優先度 {#scheduling-priority}

TabletScheduler でスケジューリングを待つシャードには、状態に応じて異なる優先度が割り当てられます。優先度の高いシャードが先にスケジュールされます。現在の優先度は次のとおりです。

| 優先度 | 条件 |
| --- | --- |
| VERY\_HIGH | REDUNDANT: レプリカが冗長なシャード。緊急度は最も低いものの、最も速く処理でき、ディスク容量などのリソースをすぐに解放できるため、先に処理されます。<br/>FORCE\_REDUNDANT: 上記と同じです。 |
| HIGH | REPLICA\_MISSING でレプリカの大半が不足している場合（3 つのうち 2 つが失われた場合など）。<br/>VERSION\_INCOMPLETE でレプリカの大半にバージョンの欠落がある場合。<br/>COLOCATE\_MISMATCH: Colocation テーブルのシャードはできるだけ早く修復する必要があります。<br/>COLOCATE\_REDUNDANT。 |
| NORMAL | REPLICA\_MISSING だがレプリカの大半が稼働している場合（3 つのうち 1 つが失われた場合など）。<br/>VERSION\_INCOMPLETE だがレプリカの大半のバージョンが完全な場合。<br/>REPLICA\_RELOCATING でレプリカの大半を移動する必要がある場合（3 つのうち 2 つなど）。 |
| LOW | REPLICA\_MISSING\_IN\_CLUSTER。<br/>REPLICA\_RELOCATING だがレプリカの大半が安定している場合。 |

### 手動による優先度の指定 {#manual-priority}

システムはスケジューリングの優先度を自動的に決定します。特定のテーブルやパーティションをより早く修復したい場合は、次のコマンドで優先修復を指定できます。

```sql
ADMIN REPAIR TABLE tbl [PARTITION (p1, p2, ...)];
```

このコマンドは TabletChecker に対し、Tablet の走査中に、優先修復が指定されたテーブルまたはパーティション内の問題のある Tablet に `VERY_HIGH` 優先度を付けるよう指示します。

> 注: このコマンドはヒントにすぎず、修復の成功は保証しません。TabletScheduler によるスケジューリングに伴い、優先度が変わる場合があります。また、Master FE の切り替えまたは再起動後、この情報は失われます。

優先指定を取り消すには、次のコマンドを使用します。

```sql
ADMIN CANCEL REPAIR TABLE tbl [PARTITION (p1, p2, ...)];
```

### 優先度の動的調整 {#dynamic-priority-adjustment}

優先度によって損傷の大きいシャードが先に修復され、システムの可用性が向上します。ただし、優先度の高い修復タスクが失敗し続けると、優先度の低いタスクがいつまでもスケジュールされない可能性があります。そのため、Doris はすべてのタスクがスケジュールされる機会を得られるよう、実行状態に基づいて優先度を動的に調整します。

- スケジューリングに 5 回連続で失敗した場合（リソースを確保できない、適切なコピー元または宛先が見つからない場合など）、優先度を下げます。
- タスクが 30 分間スケジュールされなかった場合、優先度を上げます。
- 同じ Tablet のタスクの優先度は、5 分間につき多くても一度だけ調整します。

初期優先度の重みを維持するため、次のルールを適用します。初期優先度が `VERY_HIGH` の場合は `NORMAL` までしか下がらず、`LOW` の場合は `HIGH` までしか上がりません。この動的調整は、ユーザーが手動で設定した優先度にも適用されます。

## レプリカのバランシング {#replica-balancing}

Doris はクラスター内のレプリカを自動的にバランシングします。現在は **負荷分散** と **パーティション分散** の二つの戦略をサポートしています。

| 戦略 | 主な目的 | 適用シナリオ | 備考 |
| --- | --- | --- | --- |
| 負荷分散 | ノードのディスク使用量とレプリカ数の両方を均等にする | ディスク容量とレプリカの分布の両方を考慮する必要がある場合 | 二つの指標からスコアを計算します |
| パーティション分散 | 各パーティションのレプリカをノード間に均等に配置する | パーティションの読み書きに高い要件があり、ホットスポットを避けたい場合 | ディスク使用量は考慮しないため、ディスク容量に注意が必要です |

戦略は FE の起動前に [tablet_rebalancer_type](../config/fe-config) でのみ設定できます。実行中の切り替えはサポートされません。

どちらの戦略でも、同じ Tablet のレプリカが同一ホスト上の BE に配置されないようにします。

### 負荷分散 {#load-balancing}

負荷分散では、対象のシャードについて、まず低負荷ノードにレプリカを作成し、その後、高負荷ノード上のレプリカを削除します。また、ストレージメディアの種類によって、同じクラスター内の BE ノードが一種類または二種類のメディアを持つ場合があります。メディア A を使用するシャードは、バランシング後も可能な限りメディア A に配置する必要があります。そのため、クラスター内の BE ノードをストレージメディア別に分け、各メディアの BE ノード群に対して個別に負荷分散をスケジュールします。

#### BE ノードの負荷 {#be-node-load}

`ClusterLoadStatistics` (CLS) は、クラスター内の各 Backend の負荷バランスを表します。TabletScheduler はこの統計情報を使用してクラスターのバランシングを開始します。現在は、**ディスク使用量** と **レプリカ数** の二つの指標から各 BE の負荷スコア loadScore を計算します。スコアが高いほど、その BE の負荷が高いことを示します。

ディスク使用量とレプリカ数にはそれぞれ **capacityCoefficient** と **replicaNumCoefficient** という重み係数があり、**合計は常に 1** です。

- 有効な `backend_load_capacity_coeficient` パラメーター（値の範囲は `0.0`～`1.0`）が設定されている場合、`capacityCoefficient = backend_load_capacity_coeficient` です。
- それ以外の場合、`capacityCoefficient` は実際のディスク使用量に基づいて動的に調整されます。
    - BE のディスク使用率全体が 50% 未満の場合、`capacityCoefficient` は 0.5 です。
    - ディスク使用率が 75% を超える場合（FE 設定項目 `capacity_used_percent_high_water` で調整可能）、値は 1 です。
    - 使用率が 50%～75% の場合、重み係数は次の式に従って滑らかに増加します。

```text
capacityCoefficient = 2 * disk usage - 0.5
```

この重み係数により、ディスク使用率が高すぎる場合は Backend の負荷スコアが高くなり、BE の負荷をできるだけ早く減らせます。

TabletScheduler は CLS を 20 秒ごとに更新します。

### パーティション分散 {#partition-balancing}

パーティション分散では、各 Backend 上の各パーティションのレプリカ数の差（パーティションの偏り）を最小化します。そのため、ディスク使用量は考慮せず、レプリカ数のみを考慮します。

移行回数を最小限に抑えるため、パーティション分散では二次元の貪欲戦略を使用し、偏りが最も大きいパーティションからバランシングします。パーティションをバランシングする際は、クラスター全体の Backend 間のレプリカ数の差（クラスターの偏り／全体の偏り）を減らす方向を選ぼうとします。

#### 偏りの統計 {#skew-statistics}

偏りの統計は `ClusterBalanceInfo` で表されます。

- `partitionInfoBySkew`: パーティションの偏りをキーにしてソートされ、偏りが最大のパーティションを見つけやすくします。
- `beByTotalReplicaCount`: 各 Backend の総レプリカ数をキーにしてソートされます。

`ClusterBalanceInfo` も CLS に保存され、20 秒ごとに更新されます。偏りが最大のパーティションが複数ある場合は、計算対象をランダムに一つ選びます。

### バランシング戦略のスケジューリング {#balancing-strategy-scheduling}

TabletScheduler は各スケジューリングラウンドで LoadBalancer を使用し、一定数の健全なシャードをバランシング候補として選びます。次のラウンドで、これらの候補シャードを対象にバランシングのスケジューリングを試みます。

## リソース制御 {#resource-control}

レプリカの修復とバランシングは、いずれも BE 間でレプリカをコピーすることで行われます。同じ BE で多数のタスクを同時に実行すると、IO 負荷が大きくなります。そのため、Doris はスケジューリング時に各ノードで実行できるタスク数を制御します。

| リソース | 説明 |
| --- | --- |
| リソース制御の単位 | 最小単位はディスク、つまり `be.conf` で指定されたデータパスです。 |
| レプリカ修復用スロット | 各ディスクにはデフォルトで 2 つのスロットがあります。クローンタスクはコピー元と宛先でそれぞれ一つのスロットを使用します。空きスロットが 0 の場合、新しいタスクは割り当てられません。スロット数は FE の `schedule_slot_num_per_hdd_path` または `schedule_slot_num_per_ssd_path` で調整できます。 |
| バランシングタスク用スロット | 各ディスクには、バランシングタスク専用の独立したスロットがデフォルトで 2 つあります。修復タスクがスロットを占有しても、高負荷ノードがバランシングによって空き容量を確保できるようにするためです。 |

## レプリカの状態の確認 {#viewing-replica-status}

レプリカの状態の確認は、主にレプリカ自体の状態と、レプリカ修復・バランシングタスクの実行状態を把握するために使用します。これらの状態の大部分は **Master FE ノードにのみ存在する** ため、以下のコマンドは Master FE に直接接続して実行する必要があります。

### レプリカの状態 {#replica-status-1}

#### クラスター全体の状態確認 {#global-status-check}

`SHOW PROC '/cluster_health/tablet_health';` コマンドで、クラスター全体のレプリカの状態を確認できます。

```text
+-------+--------------------------------+-----------+------------+-------------------+----------------------+----------------------+--------------+----------------------------+-------------------------+-------------------+---------------------+----------------------+----------------------+------------------+-----------------------------+-----------------+-------------+------------+
```

## 関連する問題 {#related-issues}

- デフォルトのレプリカ修復・バランシング戦略では、ネットワーク帯域を使い切る場合があります（ギガビットのネットワークカードを使用し、BE あたりのディスク数が多い場合によく発生します）。その場合は、パラメーターを調整して、同時に実行するバランシングタスクと修復タスクの数を減らす必要があります。
- 現在の Colocate テーブル向けのレプリカバランシング戦略では、同じ Tablet のレプリカが同一ホスト上の複数の BE に配置されないことを保証できません。一方、Colocate テーブル向けの修復戦略はこの配置の問題を検出して修正します。修正後、バランシング戦略がレプリカを再び不均衡とみなして再配置する場合があり、この二つの状態が繰り返されて Colocate Group が安定しなくなります。この問題が起きる可能性を減らすため、Colocate 属性を使用する場合はクラスター構成をできるだけ均一にしてください。

### クラスターのレプリカ修復とバランシングの進行状況を制御・管理する {#controlling-and-managing-cluster-replica-repair-and-balancing-progress}

通常、Doris はデフォルトのパラメーター設定でレプリカ修復とクラスターのバランシングを自動的に行えます。ただし、特定のテーブルやパーティションの修復を優先する、クラスター負荷を下げるためにバランシングを無効にする、非 Colocation テーブルのデータ修復を優先するなど、目的に応じて手動でパラメーターを調整する必要がある場合があります。このセクションでは、パラメーターを変更して修復とバランシングの進行を制御・管理する方法を説明します。

#### 1. 破損したレプリカを削除する {#1-delete-corrupted-replicas}

Doris が破損したレプリカを検出できず、そのレプリカでクエリやインポートのエラーが頻繁に発生する場合があります。その場合は、破損したレプリカを手動で削除する必要があります。この方法は、バージョン数が多すぎて -235 エラーを起こすレプリカや、ファイルが破損したレプリカなどの削除に適用できます。

手順:

1. 対象のレプリカに対応する Tablet ID を調べます。ここでは 10001 とします。
2. `show tablet 10001;` を実行し、その結果に表示される `show proc` 文を実行して、Tablet の各レプリカの詳細を確認します。
3. 削除対象のレプリカが配置されている Backend ID を 20001 とします。次の文を実行して、レプリカを `bad` とマークします。

    ```sql
    ADMIN SET REPLICA STATUS PROPERTIES("tablet_id" = "10001", "backend_id" = "20001", "status" = "bad");
    ```

4. `show proc` 文を再度実行し、対象レプリカの `IsBad` 列が `true` になっていることを確認します。

`bad` とマークされたレプリカは、インポートやクエリに参加しなくなります。同時に、レプリカ修復処理によって新しいレプリカが自動的に補充されます。

#### 2. テーブルまたはパーティションの修復を優先する {#2-prioritize-repairing-a-table-or-partition}

`help admin repair table;` を実行してヘルプを確認します。このコマンドは、指定したテーブルまたはパーティションの Tablet の修復を優先しようとします。

#### 3. バランシングタスクを停止する {#3-stop-balancing-tasks}

バランシングタスクはネットワーク帯域と IO リソースを消費します。新しいバランシングタスクが生成されないようにするには、次を実行します。

```sql
ADMIN SET FRONTEND CONFIG ("disable_balance" = "true");
```

#### 4. すべてのレプリカスケジューリングタスクを停止する {#4-stop-all-replica-scheduling-tasks}

レプリカスケジューリングタスクには、バランシングタスクと修復タスクが含まれます。これらはネットワーク帯域と IO リソースを消費します。次のコマンドを実行すると、Colocation テーブルと通常のテーブルの両方で、すべてのレプリカスケジューリングタスクが停止します（実行中のタスクを除く）。

```sql
ADMIN SET FRONTEND CONFIG ("disable_tablet_scheduler" = "true");
```

#### 5. Colocation テーブルのすべてのレプリカスケジューリングタスクを停止する {#5-stop-all-replica-scheduling-tasks-for-colocation-tables}

Colocation テーブルと通常のテーブルのレプリカスケジューリングは独立して動作します。クラスターのリソースを通常のテーブルの修復に使えるよう、Colocation テーブルのバランシングと修復を先に停止したい場合があります。

```sql
ADMIN SET FRONTEND CONFIG ("disable_colocate_balance" = "true");
```

#### 6. より慎重な戦略でレプリカを修復する {#6-use-a-more-conservative-strategy-to-repair-replicas}

Doris はレプリカの欠落や BE の停止などを検出すると、レプリカを自動的に修復します。BE の短時間の停止など、一時的な問題によるエラーを減らすため、これらのタスクの開始を遅らせます。

- `tablet_repair_delay_factor_second` パラメーター: デフォルトは 60 秒です。修復タスクの優先度に応じて、60 秒、120 秒、または 180 秒の遅延後にタスクが開始されます。次のコマンドは遅延を延長し、異常が長引いても不要な修復タスクが開始されないようにします。

    ```sql
    ADMIN SET FRONTEND CONFIG ("tablet_repair_delay_factor_second" = "120");
    ```

#### 7. より慎重な戦略で Colocation Group の再配置を開始する {#7-use-a-more-conservative-strategy-to-trigger-colocation-group-redistribution}

Colocation Group の再配置では、多数の Tablet が移行される場合があります。`colocate_group_relocate_delay_second` は再配置を開始するまでの遅延を制御し、デフォルトは 1800 秒です。BE ノードが長時間オフラインになる可能性がある場合は、不要な再配置を避けるため、この値を増やすことを検討してください。

```sql
ADMIN SET FRONTEND CONFIG ("colocate_group_relocate_delay_second" = "3600");
```

#### 8. レプリカのバランシングを高速化する {#8-faster-replica-balancing}

Doris のレプリカバランシングでは、まず正常なレプリカを追加し、その後に古いレプリカを削除して移行します。バランシングがインポートタスクに影響しないよう、古いレプリカを削除する際には、そのレプリカ上ですでに開始されたインポートタスクの完了を待ちます。ただし、この待機によってバランシングの実行が遅くなります。次のパラメーターを設定すると、待機せずに古いレプリカを直接削除します。

```sql
ADMIN SET FRONTEND CONFIG ("enable_force_drop_redundant_replica" = "true");
```

この操作によってバランシング中に一部のインポートタスクが失敗し、再試行が必要になる場合がありますが、バランシングは大幅に速くなります。

### クラスターを迅速に復旧するための推奨手順 {#recommended-procedure-for-fast-cluster-recovery}

クラスターを速やかに正常な状態へ戻すには、次の方法を検討してください。

1. 優先度の高いタスクでエラーを起こしている Tablet を特定し、問題のあるレプリカを `bad` とマークします。
2. `ADMIN REPAIR` 文を使用して、特定のテーブルの修復を優先します。
3. クラスターのリソース消費を避けるためレプリカのバランシングを停止し、クラスターの復旧後に再度有効にします。
4. BE の頻繁な停止によって修復タスクが一斉に発生する場合は、より慎重な戦略で修復タスクを開始します。
5. 必要に応じて Colocation テーブルのスケジューリングタスクを無効にし、他の優先度の高いデータの修復にクラスターリソースを集中させます。

## FAQ {#faq}

### Q: `SHOW PROC '/cluster_health/tablet_health'` コマンドでエラーが出る、またはデータが不完全な場合はどうすればよいですか？ {#q-the-show-proc-cluster_healthtablet_health-command-reports-an-error-or-shows-incomplete-data-what-should-i-do}

このコマンドを実行するには、Master FE に直接接続する必要があります。現在接続している FE が Master かどうかを確認してください。

### Q: レプリカが長時間 `REPLICA_MISSING` のまま修復されない場合、どう調査すればよいですか？ {#q-a-replica-has-been-in-replica_missing-for-a-long-time-without-being-repaired-how-do-i-troubleshoot}

`ErrMsg` の内容を `SHOW PROC '/cluster_balance/pending_tablets'` で確認してください。よくある原因には、適切なコピー元や宛先が見つからない、ディスク容量が不足している、ノードがデコミッション中であることなどがあります。

### Q: 修復タスクのスケジューリング失敗が多い場合はどうすればよいですか？ {#q-there-are-too-many-scheduling-failures-for-repair-tasks-what-should-i-do}

`SHOW PROC '/cluster_balance/sched_stat'` で失敗の統計を確認してください。`schedule_slot_num_per_hdd_path` または `schedule_slot_num_per_ssd_path` を増やすことを検討するか、ディスク容量不足や利用できないノードなどを調べてください。

### Q: レプリカのバランシングでネットワーク帯域を使い切る場合はどうすればよいですか？ {#q-replica-balancing-is-saturating-the-network-what-should-i-do}

同時に実行するバランシングタスクと修復タスクの数を減らすか、一時的に `ADMIN SET FRONTEND CONFIG ("disable_balance" = "true");` を実行してください。

### Q: Colocate Group が長時間安定しない場合はどうすればよいですか？ {#q-a-colocate-group-cannot-stabilize-for-a-long-time-what-should-i-do}

クラスター構成をできるだけ均一にし、`colocate_group_relocate_delay_second` を増やして不要な再配置を減らしてください。

### Q: BE の停止直後に多数のレプリカが修復され、負荷が急変する場合はどうすればよいですか？ {#q-after-a-be-goes-down-a-large-number-of-replicas-are-repaired-immediately-causing-load-jitter-what-should-i-do}

`tablet_repair_delay_factor_second` を増やして、異常が続いても修復を開始しない猶予期間を延ばしてください。

### Q: `bad` レプリカを削除してもエラーが続く場合はどうすればよいですか？ {#q-after-deleting-a-bad-replica-errors-still-occur-what-should-i-do}

`SHOW PROC '/dbs/.../<tablet_id>'` ですべてのレプリカが補充されたことを確認し、クローンタスクの完了を待ってください。
