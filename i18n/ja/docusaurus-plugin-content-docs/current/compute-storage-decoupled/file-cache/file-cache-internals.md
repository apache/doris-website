## 基本原理

<!-- Knowledge type: Operations -->

### キャッシュの分割とプリフェッチの仕組み

Doris は対象ファイルを **1 MB** 境界に揃えたスライスに分割します。各スライスはダウンロードが完了すると、独立したブロックファイルとしてローカルファイルシステムに保存されます。この細かい分割により、大きなファイル全体をキャッシュすることによる容量の浪費を避け、頻繁にアクセスされるデータのヒット状況の追跡とエビクションをより正確に行えます。

### ローカルファイルのディレクトリ構成

<!-- Knowledge type: Configuration reference -->

キャッシュデータは、複数のディスク上にある複数のディレクトリに分散できます。Doris は対象ファイルのパスのハッシュを計算し、そのハッシュをブロックファイルのパスの最下層ディレクトリ名として使用します。そのディレクトリ内では、各ブロックファイルに対象ファイル内の **offset** を名前として付け、データを複数のディレクトリに均等に分散します。

**例：** 対象ファイルのパスが `/remote/data/datafile1` で、計算されたハッシュが `12345` の場合、対応するブロックファイルのパスは次のとおりです。

```
/cache/123/12345/<offset>
```

ここで `<offset>` は、元のファイル内におけるそのブロックのデータのオフセットです。

### 複数キューの仕組み

<!-- Knowledge type: Configuration reference -->

Doris は、キャッシュの汚染を防ぎヒット率を高めるために、キャッシュデータを種類ごとに異なるキューへ振り分けます。以下に、優先度の高い順にキューを示します。

| キュー | 内容 | 優先度 | 備考 |
|-------|------|--------|------|
| TTL キュー | TTL 属性が設定されたデータ | 最高 | TTL が期限切れになるまではエビクションされません。TTL はテーブルレベルの属性です。たとえば 3600 に設定すると、データは取り込み後最大 1 時間キャッシュに保持されます。ローカルに保持する必要がある、小さく頻繁にアクセスされるテーブルに適しています。 |
| Index キュー | インデックスデータ（転置インデックスを除く） | 高 | クエリのフィルタリングを高速化するために使用します。転置インデックスはサイズが大きいため、Normal キューに配置されます。 |
| Normal キュー | 通常のデータ（TTL 属性なし） | 中 | 大半のデータが格納されるキューです。 |
| Disposable キュー | 一時データ（Compaction 中に読み取られるデータなど） | 最低 | 使用後、最初にエビクションされます。 |

### エビクションの仕組み

<!-- Knowledge type: Operations -->
<!-- When to use: Troubleshooting / Performance tuning -->

#### エビクションが発生する条件

| トリガー | 説明 |
|----------|------|
| 空き容量不足による受動的なエビクション | ローカルディスクの空き容量または inode がなくなった場合や、キャッシュ使用量が設定された容量上限に達した場合に発生します。 |
| 高ウォーターマークでの能動的なエビクション | キャッシュ使用量が高ウォーターマークに達すると、Doris は古いキャッシュエントリを事前に非同期で削除し、同期エビクションによって書き込みがブロックされるのを防ぎます。 |
| ガベージコレクションによるエビクション | Compaction と Schema Change の元データ、インポートのコミット失敗後にロールバックされたデータ、`DROP TABLE` または `DROP PARTITION` 操作による残存データを能動的に削除します。 |
| TTL 期限切れによる降格 | TTL エントリが期限切れになると Normal キューへ移され、通常の LRU エビクションの対象になります。 |

#### エビクション対象の選択方法

**容量配分比率：** 複数のキューでディスク容量を共有し、各キューには使用できる容量の割合について独立した上限があります（たとえば、Normal キューの上限は総容量の 40%）。ほかのキューが割り当て分を使い切っていない場合、あるキューは残りの容量をすべて使用できます。各種類のデータが増えるにつれて、使用割合は設定値に徐々に近づきます。

**エビクションの順序：** キューに書き込み用の十分な空き容量がない場合、Doris は次の順序で配分比率を超えたデータをエビクションします（各キュー内では、LRU によって先にエビクションするエントリを決定します）。

```
Disposable → Normal → Index → TTL
```

ほかのキューからエビクションしても容量が不足する場合は、対象キュー自身のエントリを LRU に従ってエビクションします。

#### 頻繁にアクセスされるデータのエビクションを避けるための推奨事項

- **十分なディスク容量を確保する：** キャッシュのクリーンアップには多少の遅延があるため、常に余裕を持たせてください。経験上、ファイルキャッシュの容量を頻繁にクエリされるデータ量の約 **1.5 倍** に設定すると、高いヒット率が得られます。
- **大規模なクエリを分離する：** 大規模なクエリを専用クラスターに振り分け、キャッシュを占有してほかのクエリのヒット率を下げることを防ぎます。

### ウォームアップの仕組み

<!-- Knowledge type: Operations -->
<!-- When to use: Pre-deployment check / Performance tuning -->

キャッシュのウォームアップは、後続のクエリがローカルキャッシュに直接ヒットして性能が向上するよう、データを事前にキャッシュへ読み込みます。Doris には次の三つのウォームアップ方法があります。

#### 手動ウォームアップ

指定したテーブルまたはパーティションのウォームアップを開始できます。また、別のクラスターのキャッシュ内容を参照して開始することもできます。データの取得元は常にリモートストレージであり、ほかの BE ノードではありません。クエリ処理中にほかの BE のキャッシュから読み取る機能は、別途 [ピアキャッシュ読み取り](./file-cache-peer-read) によって提供されます。ウォームアップの流れは次のとおりです。

1. ウォームアップコマンドを実行します。システムは対象を一連のタブレットに変換し、対応する BE に振り分けます。
2. 各 BE は担当するタブレットのすべてのデータファイルを順次読み取り、ローカルファイルキャッシュへ書き込みます。
3. タスクは最大 **20 GB** のバッチに分けて実行されます。各バッチの完了後にチェックポイントが保存されるため、中断後に再開できます。
4. BE が停止した場合、またはジョブを手動でキャンセルした場合、すべての BE がダウンロードを停止し、ウォームアップが終了します。

タスクの状態（`FINISHED` / `CANCELLED` / `RUNNING`）と全体の進捗は、`SHOW WARM UP JOB` で確認できます。同じテーブルとパーティションを再びウォームアップすると、Doris は既存のデータを自動的に検出し、キャッシュ済みデータを再ダウンロードせずに **増分更新** を行います。

#### データのリバランスを契機とするウォームアップ

負荷のリバランス（スケーリングやノード障害によるもの）でタブレットが新しい BE に移行すると、新しい BE は古い BE に RPC を送信してキャッシュのメタデータを取得し、そのメタデータに基づいてデータをローカルファイルキャッシュに再ダウンロードします。古いノードのキャッシュデータは、タブレット情報がクリーンアップされる際に能動的にエビクションされ、容量が解放されます。

> **注：** 移行が完了してからキャッシュのダウンロードが完了するまでの間は、ファイルキャッシュミスが発生する場合があります。デフォルトで有効な [ピアキャッシュ読み取り](./file-cache-peer-read) を使うと、この間、新しい BE はリモートストレージへ戻らずに、欠けているブロックを移行元 BE のキャッシュから直接取得できます。

#### コンピュートクラスター間の自動ウォームアップ（バージョン 3.1+）

<!-- Knowledge type: Architecture principle -->

コンピュートとストレージを分離したデプロイメントでは、複数のコンピュートクラスター間でファイルキャッシュを自動的に同期できます。Doris は二つの同期方法を提供します。

| 方法 | 使用する場面 | 説明 |
|------|--------------|------|
| 定期的なウォームアップ | リアルタイムのデータ鮮度が重要ではない場合 | `WARM UP` SQL ステートメントで同期間隔を指定します。ジョブは、指定したテーブルとパーティションの増分データを対象クラスターへ定期的に同期します。 |
| 取り込みまたは Compaction を契機とするウォームアップ | リアルタイムのデータ鮮度が必要な場合 | 取り込みジョブがコミット段階に入ると、ソースクラスターの BE が対象クラスターの対応する BE に通知し、新たにアップロードされたデータをダウンロードさせます。Compaction の完了時にも同様の通知が行われます。FE は対象クラスターのタブレット配置情報を管理します。 |

## シナリオ別の動作

<!-- Knowledge type: Operations -->

### クエリ時

<!-- When to use: Performance tuning / Troubleshooting -->

クエリ時のファイルキャッシュ処理の流れは次のとおりです。

1. **Scanner の読み取り要求：** クエリを受け取ると、Scanner コンポーネントが必要なデータファイルの読み取りを準備します。
2. **ローカルキャッシュの確認：** Scanner はまずローカルファイルキャッシュを調べ、ファイルパスとオフセットでキャッシュのメタデータを照合します。
3. **キャッシュヒット：** 一致するキャッシュデータが見つかると、システムは BlockFile ハンドルの集合を返し、Scanner はリモートストレージにアクセスせずにローカルでデータを読み取ります。
4. **キャッシュミス：** キャッシュにない範囲については、Scanner がリモートストレージからデータをダウンロードし、ファイルキャッシュに書き込んでから返します。容量はエビクションポリシーに従って解放されます。[ピアキャッシュ読み取り](./file-cache-peer-read) が有効な場合（デフォルト）、Scanner はまずほかの BE のファイルキャッシュを試し、どの BE にもデータがない場合にのみリモートストレージからダウンロードします。

### データ取り込み時

<!-- When to use: Performance tuning -->

データ取り込み時のファイルキャッシュ処理の流れは次のとおりです。

1. **リモートストレージへのアップロード：** 取り込んだデータは最初にリモートストレージへ書き込まれます。
2. **ローカルキャッシュへの非同期書き込み：** Doris は同時にデータをローカルファイルキャッシュへ非同期で書き込みます。そのため、取り込み直後のクエリはキャッシュに直接ヒットできます。
3. **キャッシュキューへの割り当て：** データの種類と TTL 属性に基づき、対応するキュー（TTL キュー、Index キュー、Normal キュー）へデータを書き込みます。

### Compaction 時

<!-- When to use: Performance tuning -->

Doris には二種類の Compaction があります。

- **Cumulative Compaction：** 増分データのセグメントをマージします。
- **Base Compaction：** ベースとなるデータバージョン（バージョン 0 から始まるもの）と増分データのバージョンをマージします。

二種類の Compaction では、異なるキャッシュ書き込み方法を使用します。

| Compaction の種類 | キャッシュへの書き込み方法 |
|-------------------|----------------------------|
| Cumulative Compaction | 後続のクエリを高速化するために、取り込み時と同様に、出力データをリモートストレージへアップロードすると同時にファイルキャッシュにも書き込みます。 |
| Base Compaction | デフォルトでは、大量のコールドデータによるキャッシュ汚染を避けるため、十分なキャッシュ容量がある場合にのみデータをキャッシュへ書き込みます。BE パラメーター `enable_file_cache_keep_base_compaction_output = true` を設定すると書き込みを強制できますが、ほかの頻繁にアクセスされるデータがエビクションされる可能性があります。 |

ローカルキャッシュの容量が限られている場合は、インデックスのみを書き込むポリシーを有効にし、Compaction の出力に含まれる Segment データが大量のキャッシュ容量を能動的に消費するのを防げます。

- `enable_file_cache_write_index_file_only=true`：Compaction を含む、コンピュートとストレージを分離したモードのすべての rowset 書き込みに適用されます。Segment データは能動的にキャッシュされませんが、Segment のフッターと内部インデックスの範囲、および独立した転置インデックスファイルは引き続きキャッシュへ書き込まれます。
- `enable_file_cache_write_base_compaction_index_only=true` または `enable_file_cache_write_cumu_compaction_index_only=true`：本来キャッシュへ書き込まれる、対応する Compaction の出力だけを制限します。Segment ファイルはスキップし、独立した転置インデックスファイルは保持しますが、Segment のフッターと内部インデックスの範囲は事前に読み込まれません。

パラメーターの優先順位、設定例、制限事項については、[ファイルキャッシュの設定](./file-cache.md) を参照してください。

> **今後の予定：** Doris の将来のバージョンでは、過去のクエリ統計に基づく適応的な書き込み方法が提供される予定です。

### 再起動後のキャッシュの読み込み

<!-- When to use: Troubleshooting -->

バージョン 3.1 より前は、再起動後に LRU キューの順序を復元できず、頻繁にアクセスされるデータがエビクションされてヒット率が低下することがありました。

**バージョン 3.1 では LRU 情報の永続化が導入されました。** 読み込みの流れは次のとおりです。

1. **定期的なダンプ：** 各 LRU キューの順序情報を定期的にディスクへ永続化します。
2. **再起動時の読み込み：** ノードの再起動時にディスクからダンプデータを読み取り、キャッシュキューの状態を復元します。
3. **完全性を確保するためのディスク全体のスキャン：** ダンプの時間差によって生じるメタデータとディスクの不整合を解消するため、再起動後にディスク全体をスキャンしてデータの整合性を確保します。
4. **クエリを契機とする並行非同期読み込み：** ディスク全体のスキャン中も、BE はクエリを処理できます。まだスキャンされていないデータがクエリの対象になった場合、システムはそのデータを先行して読み込み、クエリのレイテンシーを抑えます。

### スケーリング時

<!-- Knowledge type: Configuration reference -->
<!-- When to use: Scaling planning -->

#### 水平スケールアウト

Doris はリバランスによってタブレットを新しい BE ノードへ移行します。移行先の BE は移行元 BE のキャッシュメタデータに基づいてデータをローカルストレージに再ダウンロードするため、新しいノードで実行するクエリもファイルキャッシュにヒットできます。[ピアキャッシュ読み取り](./file-cache-peer-read) を使用すると、ダウンロードが完了する前でも、移行先 BE での最初の読み取り時に移行元 BE のキャッシュからブロックを直接取得できます。

#### 水平スケールイン

タブレットのリバランス後、クラスター全体のファイルキャッシュ容量が実際のキャッシュデータ量を下回る場合、エビクションの仕組みによって超過分のデータが自動的に削除されます。

#### 垂直スケールアウト

| スケールアウトの方法 | 手順 |
|----------------------|------|
| 単一ディスクの容量を増やす | 次のコマンドを実行して容量の変更を BE に通知します：`curl http://<BE_IP>:<WEB_PORT>/api/file_cache?op=reset&capacity=<new capacity in bytes>` |
| ディスクを追加する | **推奨しません。** Doris は現在、再ハッシュを実装しておらず、ディスク間のリバランスもサポートしていません。キャッシュディレクトリの数を変更すると、キャッシュの検索に失敗する可能性があります。ディスクを追加する必要がある場合は、キャッシュをクリアし、必要に応じて再度ウォームアップしてください。 |

#### 垂直スケールイン

ディスク容量を減らす場合も、上記の `reset` コマンドを実行する必要があります。キャッシュ容量が実際のキャッシュデータ量を下回ると、エビクションが発生してデータが自動的に削除されます。

#### スケーリング後のウォームアップに関する注意事項

水平スケールアウトと水平スケールインでは、タブレットのリバランスが行われます。ウォームアップを有効に機能させるため、**移行が安定してからウォームアップを実行してください**。移行の完了は、FE メトリクス `doris_fe_tablet_num` を監視して判断できます。曲線が変動せず、平坦で安定していれば、移行が完了しており、ウォームアップを実行できます。

## よくある質問

<!-- Knowledge type: Troubleshooting -->
<!-- When to use: Troubleshooting / Performance tuning -->

**Q：キャッシュヒット率が低く、クエリ性能が改善しません。どのように調査すればよいですか？**

- ファイルキャッシュ用ディスクに十分な空き容量があるか確認します。推奨されるキャッシュ容量は、頻繁にアクセスされるデータ量の少なくとも 1.5 倍です。
- 大規模なクエリによって、頻繁にアクセスされるデータが繰り返しエビクションされていないか確認します。大規模なクエリの分離を検討してください。
- 再起動直後に短時間ヒット率が低くなるのは正常です（LRU の復元には時間がかかります）。事前に手動ウォームアップを実行できます。

**Q：スケールアウト後にクエリがキャッシュにヒットしません。どうすればよいですか？**

- タブレットのリバランスが完了したことを確認します（`doris_fe_tablet_num` の曲線が平坦で安定していること）。
- 対象のテーブルとパーティションに対して手動ウォームアップコマンドを実行します。
- 水平スケールアウト後、新しい BE でのデータのダウンロードには時間がかかります。この間にキャッシュミスが起きるのは想定どおりです。デフォルトで有効な [ピアキャッシュ読み取り](./file-cache-peer-read) は、この期間の影響を短縮します。無効にされていないことを確認してください。

**Q：Base Compaction によって、頻繁にアクセスされるデータがエビクションされますか？**

- デフォルトでは、Base Compaction は十分な空き容量がある場合にのみキャッシュへ書き込み、頻繁にアクセスされるデータを能動的にエビクションしません。
- `enable_file_cache_keep_base_compaction_output = true` を有効にすると、Base Compaction のデータがキャッシュへ強制的に書き込まれるため、頻繁にアクセスされるデータがエビクションされる可能性があります。実際のワークロードに基づいて、このトレードオフを評価してください。

**Q：TTL が期限切れになると、データは直ちに削除されますか？**

- いいえ、直ちには削除されません。TTL が期限切れになると、データは Normal タイプに降格し、Normal キューに入って通常の LRU エビクションの対象になります。最終的にいつデータが削除されるかは、エビクションの仕組みによって決まります。

**Q：手動ウォームアップでは、キャッシュ済みデータの再ダウンロードを避けられますか？**

- はい。ウォームアップの実行時、Doris はキャッシュ済みデータを自動的に識別し、新規または変更されたデータのみを増分ダウンロードします。
