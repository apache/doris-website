Hive Metastore または Hive Metastore と互換性のあるメタデータサービスに接続すると、Doris はデータのクエリに必要な Hive データベースとテーブルの情報を自動的に取得できます。

Hive 以外にも、多くのシステムがメタデータの保存に Hive Metastore を使用しています。そのため、Hive Catalog を通じて Hive テーブルだけでなく、Iceberg や Hudi など、メタデータの保存に Hive Metastore を使用する他のテーブル形式にもアクセスできます。

## 適用シナリオ {#applicable-scenarios}

| シナリオ | 説明 |
|--------------|--------------------------------------------------------------|
| クエリの高速化 | Doris の分散コンピューティングエンジンから Hive データに直接アクセスし、クエリを高速化します。 |
| データ統合 | Hive データを読み取って Doris の内部テーブルに書き込むか、Doris のコンピューティングエンジンを使用して ZeroETL 操作を実行します。 |
| データの書き戻し | Doris がサポートする任意のソースのデータを処理し、Hive テーブルに書き戻します。 |

## Catalog の設定 {#configuring-catalog}

### 構文 {#syntax}

```sql
CREATE CATALOG [IF NOT EXISTS] catalog_name PROPERTIES (
    'type'='hms', -- required
    'hive.metastore.type' = '<hive_metastore_type>', -- optional
    'hive.version' = '<hive_version>', -- optional
    'fs.defaultFS' = '<fs_defaultfs>', -- required for write, optional for read-only
    {MetaStoreProperties},
    {StorageProperties},
    {HiveProperties},
    {CommonProperties}
);
```

* `<hive_metastore_type>`

  Hive Metastore の種類を指定します。

  * `hms`: 標準の Hive Metastore サービス。
  * `glue`: Hive Metastore 互換インターフェイスを使用して AWS Glue メタデータサービスにアクセスします。
  * `dlf`: Hive Metastore 互換インターフェイスを使用して Alibaba Cloud DLF メタデータサービスにアクセスします。

* `<fs_defaultfs>`

  Doris からこの Hive Catalog 内のテーブルにデータを書き込む場合、このパラメータが必要です。例:

  `'fs.defaultFS' = 'hdfs://namenode:port'`

* `{MetaStoreProperties}`

  MetaStoreProperties セクションには、Metastore メタデータサービスへの接続情報と認証情報を指定します。詳しくは「サポートされるメタデータサービス」を参照してください。

* `{StorageProperties}`

  StorageProperties セクションには、ストレージシステムに関する接続情報と認証情報を指定します。詳しくは「サポートされるストレージシステム」を参照してください。

* `{HiveProperties}`

  HiveProperties セクションには、Hive Catalog に関するプロパティを指定します。

  * `get_schema_from_table`: デフォルト値は false です。通常、Doris は Hive Metastore からテーブルのスキーマ情報を取得します。ただし、`Storage schema reading not supported` エラーなどの互換性の問題が発生する場合があります。その場合はこのパラメータを true に設定すると、Table オブジェクトからテーブルのスキーマを直接取得します。ただし、この方法ではカラムのデフォルト値の情報が無視されます。このプロパティはバージョン 2.1.10 および 3.0.6 以降でサポートされています。

  * `hive.recursive_directories`: パーティションディレクトリを一覧表示する際に、サブディレクトリを再帰的にたどるかどうかを指定します。このパラメータはバージョン 3.0.2 以降でサポートされています。バージョン 4.0 より前のデフォルト値は `false`、それ以降のバージョンでは `true` です。一部の Hive テーブルでは、パーティションパスがテーブルスキーマのパーティション情報と一致しない場合があります。サブディレクトリ内のデータファイルを取得するには、このパラメータを true に設定する必要があります。

  * `hive.ignore_absent_partitions`: 存在しないパーティションを無視するかどうかを指定します。デフォルト値は `true` です。`false` に設定すると、存在しないパーティションが見つかったときにクエリでエラーが報告されます。このパラメータはバージョン 3.0.2 以降でサポートされています。

  * `hive.staging_dir`: Hive への書き込み操作で使用する一時ステージングディレクトリのルートを設定します。書き込み中、データはまずこのディレクトリに書き込まれ、完了後に最終的な Hive テーブルディレクトリへ移動されます。パスには、Hive テーブルのルートディレクトリからの相対パス、または絶対パスを指定できます。デフォルト値は `/tmp/.doris_staging` です。Hive テーブルへの書き込み時に、`/tmp` ディレクトリとテーブルディレクトリが異なる名前空間に属しているため、書き込みに失敗する場合があります。その場合は、このパラメータを相対パスに変更することで解決できます。このパラメータはバージョン 4.0.3 以降でサポートされています。

  * `hive.parquet.time-zone`: FileScannerV2 が Hive テーブルを読み取る際、レガシー Parquet `INT96` タイムスタンプを復元するために使用する互換タイムゾーンです。デフォルト値は空で、この場合はタイムゾーン変換を適用せず、`INT96` に保存された日時の各フィールドをそのまま保持します。Catalog 内の `INT96` ファイルが、既知のタイムゾーンを使ってライターにより正規化されている場合にのみ、このプロパティを設定してください。Hudi テーブルは意図的にこのプロパティを無視し、既存の SQL セッションタイムゾーンの動作を維持します。詳しくは [Parquet INT96 タイムスタンプの互換性](#timestamp-compatibility)を参照してください。

* `{CommonProperties}`

  CommonProperties セクションには共通の属性を指定します。[Catalog の概要](../catalog-overview.md)の「共通プロパティ」を参照してください。

## メタデータキャッシュ {#meta-cache}

外部データソースへのアクセス性能を向上させるため、Apache Doris は Hive メタデータをキャッシュします。メタデータには、テーブルオブジェクト、パーティション名、パーティションオブジェクト、カラム統計、ファイル一覧、そこから構築されるパーティションプルーニング用の構造が含まれます。

:::tip
Doris 4.1.x より前のバージョンでは、メタデータキャッシュは主に FE の設定項目によってグローバルに制御されます。詳しくは[メタデータキャッシュ](../meta-cache.md)を参照してください。
Doris 4.1.x 以降、Hive Catalog の外部メタデータキャッシュは統一された `meta.cache.*` キーで設定します。以下の項目は現行バージョンについて説明しています。Doris 4.1.x と 4.2.x では異なる項目を使用します。詳しくは、このページの 4.x 版を参照してください。
:::

### キャッシュプロパティの設定 {#meta-cache-unified-model}

各キャッシュ項目では、統一された設定キー形式 `meta.cache.<engine>.<entry>.{enable,ttl-second,capacity,max-weight}` を使用します。Hive の `<engine>` は `hive` です。Iceberg テーブルを含む Hive Metastore Catalog では、[Iceberg Catalog](./iceberg-catalog#meta-cache)に記載された `iceberg` の項目も使用します。

| プロパティ | 例 | 意味 |
|---|---|---|
| `enable` | `true/false` | このキャッシュ項目を有効にするかどうか。 |
| `ttl-second` | `600`, `0`, `-1` | `0` は項目を無効にします（即座に反映され、最新データの確認に使用できます）。`-1` は期限なしを意味します。その他の正の整数は、アクセス時刻を基準とする有効期間を秒単位で指定します。 |
| `capacity` | `10000` | キャッシュ項目数の上限。`0` は項目を無効にします。 |
| `max-weight` | `1GB` | Doris 4.1.4 以降でサポートされています。保持されるメモリの推定量に対する任意の上限です。正の値が必要で、`0` は拒否されます。以下で対応が示されている項目のみ指定できます。 |

**有効化の条件:** `enable=true`、`ttl-second != 0`、`capacity > 0` の場合に項目が有効になります。さらに、FE 全体、Catalog、または項目単位のメモリ上限が、推定メモリ使用量に基づくキャッシュへの追加を制御します。[外部メタデータキャッシュのメモリ管理](../external-meta-cache-memory-management)を参照してください。

### キャッシュモジュール {#meta-cache-unified-modules}

Hive Catalog には次のキャッシュ項目があります。いずれも `max-weight` を指定できます。

| 項目 (`<entry>`) | プロパティキーのプレフィックス | `ENTRY_NAME` | キャッシュされる内容と効果 | デフォルトの有効化状態 / TTL / 容量 |
|---|---|---|---|---|
| `table` | `meta.cache.hive.table.` | `hive-table` | Hive Metastore のテーブルオブジェクト。効果: プランニング中の Metastore との通信回数を減らします。 | `true` / 86400 秒 / 10000 |
| `partition_names` | `meta.cache.hive.partition_names.` | `hive-partition-names` | パーティション名の一覧。効果: パーティションの列挙に影響します。無効にすると、新しいパーティションが即座に見えるようになります。 | `true` / 86400 秒 / 10000 |
| `partition` | `meta.cache.hive.partition.` | `hive-partition` | 場所や入力形式などのパーティションオブジェクト。 | `true` / 86400 秒 / 100000 |
| `column_stats` | `meta.cache.hive.column_stats.` | `hive-column-stats` | Hive Metastore のカラム統計。 | `true` / 86400 秒 / 10000 |
| `file` | `meta.cache.hive.file.` | `hive-file` | ファイル一覧。効果: リモートの LIST 操作を減らします。無効にすると、ファイルの変更が即座に見えるようになります。 | `true` / 86400 秒 / 10000 |
| `partition_view` | `meta.cache.hive.partition_view.` | `hive-partition-view` | パーティション名から構築されるパーティションプルーニング用の構造。 | `true` / 86400 秒 / 1000 |

Hive テーブルのカラムスキーマは、すべての外部 Catalog が使用する共有の `default` エンジン（`meta.cache.default.schema.*`）でキャッシュされます。

### 旧パラメータのマッピングと変換 {#meta-cache-mapping}

統一されたキーの使用を推奨します。以下の旧 Catalog プロパティも引き続き受け付けられ、対応するキーにマッピングされます。

| 旧プロパティキー | 統一されたキー | 説明 |
|---|---|---|
| `schema.cache.ttl-second` | `meta.cache.default.schema.ttl-second` および `meta.cache.hive.table.ttl-second` | テーブルスキーマとテーブルオブジェクトのキャッシュの有効期限 |
| `partition.cache.ttl-second` | `meta.cache.hive.partition_names.ttl-second` | パーティション名一覧の有効期限 |
| `file.meta.cache.ttl-second` | `meta.cache.hive.file.ttl-second` | ファイル一覧の有効期限 |

### ベストプラクティス {#meta-cache-best-practices}

* **最新データへのリアルタイムアクセス**: 外部データソースでのパーティションやファイルの変更を各クエリに反映させるには、対応する `ttl-second` を `0` に設定します。
  ```sql
  -- Disable the file listing cache to see file changes in real time
  ALTER CATALOG hive_ctl SET PROPERTIES ("meta.cache.hive.file.ttl-second" = "0");
  -- Disable the partition name cache to see new partitions in real time
  ALTER CATALOG hive_ctl SET PROPERTIES ("meta.cache.hive.partition_names.ttl-second" = "0");
  ```
* **性能の最適化**: メタデータの変更が少ない場合は、`capacity` と `ttl-second` を増やして Hive Metastore とファイルシステムへのアクセス負荷を減らします。非常に大きなテーブルでは、`max-weight` を使用してファイル一覧とパーティションプルーニングのキャッシュを制限します。

:::caution
Catalog プロパティの変更が成功すると、影響を受けるメタデータキャッシュが破棄され、次回のアクセス時に新しい設定で再構築されます。`meta.cache.max-weight` または `schema.cache.ttl-second` を変更すると Catalog のすべてのキャッシュが破棄されます。`meta.cache.<engine>.<entry>.*` を変更すると、そのエンジンのキャッシュが破棄されます。実行中のクエリには影響しません。
:::

### 監視 {#meta-cache-unified-observability}

キャッシュのメトリクスは、システムテーブル `information_schema.catalog_meta_cache_statistics` で確認できます。`ENTRY_NAME` には上の表の名前が表示され、`default` エンジンの行は共有のテーブルスキーマキャッシュを表します。

```sql
SELECT engine_name, entry_name,
       effective_enabled, ttl_second, capacity,
       estimated_size, hit_rate, max_weight, estimated_weight
FROM information_schema.catalog_meta_cache_statistics
WHERE catalog_name = 'hive_ctl'
ORDER BY engine_name, entry_name;
```

このシステムテーブルについては、[catalog_meta_cache_statistics](../../admin-manual/system-tables/information_schema/catalog_meta_cache_statistics.md)のドキュメントを参照してください。

## Parquet INT96 タイムスタンプの互換性 {#timestamp-compatibility}

Hive テーブルには、異なるエンジンが生成したタイムスタンプファイルが含まれる場合があります。タイムゾーン変換が必要かどうかは、物理エンコーディングとライターの動作によって決まります。`INT96` にはタイムゾーンの注釈がないため、Doris は Parquet の `INT96` 値からライターのタイムゾーンを推測しません。

4.1.5 以降、`hive.parquet.time-zone` には IANA タイムゾーン、または `-12:00` から `+14:00` までの UTC オフセットを指定できます。`UTC` と `GMT` は使用できますが、`CST` や `PRC` のような短い別名は拒否されます。[Parquet](../file-formats/parquet.md#timestamp-and-date-compatibility)を参照してください。

### Parquet INT96 タイムスタンプ {#parquet-int96-timestamps}

FileScannerV2 は Parquet タイムスタンプを次のように処理します。

| 物理エンコーディング | デフォルトの動作 | `hive.parquet.time-zone` の効果 |
|---|---|---|
| `INT96` から `DATETIMEV2` へのマッピング | ファイルに保存された日付と時刻のフィールドを保持します。SQL セッションのタイムゾーンによって値はずれません。 | 生の `INT96` 値を UTC の時点として扱い、設定した互換タイムゾーンに変換して、レガシーライターが正規化したタイムスタンプを復元します。 |
| タイムスタンプ論理型を持つ `INT64` | Parquet の論理型の意味に従います。 | 影響を受けません。 |

たとえば、意図した現地時刻のタイムスタンプが `Asia/Shanghai` の `2021-01-01 10:11:00` であるとします。

* ファイルに日時のフィールドがそのまま `10:11:00` と保存されている場合は、`hive.parquet.time-zone` を設定しないでください。SQL セッションで `Asia/Shanghai` を使用していても、Doris は `10:11:00` を返します。
* レガシーライターが `INT96` に保存する前に値を UTC に正規化している場合、ファイルには `02:11:00` が含まれている可能性があります。Doris が `10:11:00` を復元できるよう、`hive.parquet.time-zone` を `Asia/Shanghai` に設定します。

Catalog の作成時に互換タイムゾーンを設定します。

```sql
CREATE CATALOG hive_legacy_int96 PROPERTIES (
    'type' = 'hms',
    'hive.metastore.uris' = 'thrift://127.0.0.1:9083',
    'hive.parquet.time-zone' = 'Asia/Shanghai'
);
```

値には `Asia/Shanghai` などの IANA タイムゾーン名、または `-12:00` から `+14:00` までの UTC オフセットを指定できます。無効な値を指定すると Catalog の作成に失敗します。

:::caution
`hive.parquet.time-zone` は、Catalog 内の Hive テーブルで `DATETIMEV2` にマッピングされるすべての `INT96` タイムスタンプカラムに適用されます。同じ Hive Metastore 内の Iceberg テーブルには影響しません。Iceberg は独自のタイムスタンプの意味を定義しているためです。Hudi も意図的にこのプロパティを無視します。ネイティブのベースファイルスキャンと JNI の merge-on-read スキャンは、どちらも SQL セッションのタイムゾーンでタイムスタンプを解釈する従来の動作を維持します。Parquet メタデータからは、`INT96` ライターがどの方式を使用したかを Doris が確実に判断することはできません。SQL セッションのタイムゾーンに合わせるという理由だけでこのプロパティを設定しないでください。1 つの Hive Metastore に、異なる方式で書き込まれた `INT96` ファイルを持つ Hive テーブルが含まれる場合は、可能であれば別々の Catalog から公開してください。
:::

Parquet ファイルを読み取るファイルのテーブル値関数でも、同じプロパティを指定できます。互換性のための変換は、FileScannerV2 での Parquet `INT96` のデコードにのみ適用されます。FileScannerV1 は意図的に変更されておらず、異なる結果を返す場合があります。FileScannerV1 への切り替えは、この変更に対する互換性確保の手段ではありません。Parquet の `INT64` 論理タイムスタンプには影響しません。`INT96` カラムが `TIMESTAMPTZ` にマッピングされる場合、Doris はこのプロパティを無視して UTC の時点を保持します。その値の表示には、引き続き `TIMESTAMPTZ` とセッションタイムゾーンの意味が適用されます。

### 移行時の推奨事項 {#migration-recommendations}

* Doris はデフォルトで Parquet の `INT64` 論理タイムスタンプを書き込みます。Hive 2 や Hive 3 などのレガシーリーダーで `INT96` が必要な場合にのみ、`enable_int96_timestamps = true` を設定してください。
* この FileScannerV2 の動作を含むバージョンにアップグレードする際は、展開前に既存の Hive テーブルを確認してください。レガシーライターが正規化した `INT96` ファイルを含む Catalog では、アップグレード後に異なる日時が返される可能性があります。代表的な値を比較し、変換が必要な場合は `hive.parquet.time-zone` をライターのタイムゾーンに設定します。Hudi は既存のセッションタイムゾーンの動作を維持するため、この変更に伴う移行は不要です。
* `hive.parquet.time-zone` を設定する前に、代表的なファイルを調べ、既知のタイムスタンプ値と比較してください。不要な設定を行うと、本来修正するはずの時差が生じます。
* `INT96` ライターの方式が異なるファイルは別々の Catalog に配置するか、一貫した `INT64` エンコーディングで書き直してください。
* Doris が `enable_int96_timestamps = true` を指定して明示的に `INT96` をエクスポートする場合、エクスポートセッションのタイムゾーンを使用してタイムスタンプを正規化します。そのファイルを FileScannerV2 で読み戻すには、`hive.parquet.time-zone` をエクスポートセッションのタイムゾーンに設定します。[エクスポートの概要](../../data-operate/export/export-overview.md)を参照してください。

## クエリ操作 {#query-operations}

### 基本的なクエリ {#basic-query}

Catalog を設定したら、次の方法で Catalog 内のテーブルデータをクエリできます。

```sql
-- 1. switch to catalog, use database and query
SWITCH hive_ctl;
USE hive_db;
SELECT * FROM hive_tbl LIMIT 10;

-- 2. use hive database directly
USE hive_ctl.hive_db;
SELECT * FROM hive_tbl LIMIT 10;

-- 3. use full qualified name to query
SELECT * FROM hive_ctl.hive_db.hive_tbl LIMIT 10;
```

### Hive パーティションのクエリ {#querying-hive-partitions}

Hive パーティションの情報は、次の 2 つの方法でクエリできます。

* `SHOW PARTITIONS FROM [catalog.][db.]hive_table`

  このステートメントは、指定した Hive テーブルのすべてのパーティションとその値を一覧表示します。

  ```sql
  SHOW PARTITIONS FROM hive_table;

  +--------------------------------+
  | Partition                      |
  +--------------------------------+
  | pt1=2024-10-10/pt2=beijing     |
  | pt1=2024-10-10/pt2=shanghai    |
  | pt1=2024-10-11/pt2=beijing     |
  | pt1=2024-10-11/pt2=shanghai    |
  | pt1=2024-10-12/pt2=nanjing     |
  +--------------------------------+
  ```

* `table$partitions` メタデータテーブルの使用

  バージョン 2.1.7 および 3.0.3 以降、`table$partitions` メタデータテーブルを通じて Hive パーティションの情報をクエリできます。このテーブルはリレーショナルテーブルとして扱え、各パーティションカラムが 1 つのカラムとして表されるため、任意の SELECT ステートメントで使用できます。

  ```sql
  SELECT * FROM hive_table$partitions;

  +------------+-------------+
  | pt1        | pt2         |
  +------------+-------------+
  | 2024-10-10 | beijing     |
  | 2024-10-10 | shanghai    |
  | 2024-10-12 | nanjing     |
  | 2024-10-11 | beijing     |
  | 2024-10-11 | shanghai    |
  +------------+-------------+
  ```

:::caution 動作の変更（4.1.4）

バージョン 4.1.4 以降、Hive のディレクトリ形式のパーティショニングで使用されるデフォルトパーティションのマーカー `__HIVE_DEFAULT_PARTITION__` は、文字列 `\N` としてエンコードされるのではなく、実際の **NULL** 値に解決されます。同時に、パーティションパスに実際に保存されているリテラルの `\N` はデータとして保持されます。

4.1.4 より前は、この 2 つのケースを区別できず、クエリ結果では両方とも `\N` と表示されていました。アップグレード後は、`WHERE <partition_col> IS NULL` が Hive のデフォルトパーティションに正しく一致します。

:::

### Hive トランザクションテーブルのクエリ {#querying-hive-transactional-tables}

Hive トランザクションテーブルは ACID セマンティクスをサポートします。詳しくは [Hive Transactions](https://cwiki.apache.org/confluence/display/Hive/Hive+Transactions)を参照してください。

* Hive トランザクションテーブルへの対応

  | テーブルの種類 | Hive でサポートされる操作 | Hive テーブルのプロパティ | サポートされる Hive バージョン |
  | ------------------------------- | ----------------------------------- | ------------------------------------------------------------------- | ---------------------------------------------------------------- |
  | Full-ACID トランザクションテーブル | Insert、Update、Delete をサポート | `'transactional'='true'` | 4.x、3.x、2.x（2.x で読み取るには Hive で Major Compaction が必要） |
  | Insert-Only トランザクションテーブル | Insert のみサポート | `'transactional'='true'`, `'transactional_properties'='insert_only'` | 4.x、3.x、2.x（Catalog の作成時に `hive.version` を指定） |

* 現在の制限

  Original Files を含むケースはサポートされていません。テーブルをトランザクションテーブルに変換すると、新しいデータファイルには Hive トランザクションテーブルのスキーマが使用されますが、既存のデータファイルは変換されません。これらのファイルを Original Files と呼びます。

### Hive ビューのクエリ {#querying-hive-views}

Hive ビューをクエリできますが、いくつかの制限があります。

* Hive ビューの定義（HiveQL）は、Doris がサポートする SQL ステートメントと互換性が必要です。互換性がない場合は解析エラーが発生します。

* HiveQL がサポートする関数の中には、Doris の関数と同じ名前でも動作が異なるものがあります。そのため、Hive と Doris で得られる結果が異なる場合があります。このような問題が発生した場合は、コミュニティに報告してください。

### 関連パラメータ {#related-parameters}

* セッション変数

| パラメータ名 | デフォルト値 | 説明 | 対応バージョン |
| ----------| ---- | ---- | --- |
| `hive_parquet_use_column_names` | `true` | Doris が Hive テーブルの Parquet データを読み取る際、デフォルトでは Hive テーブルのカラム名に基づいて Parquet ファイル内の同名のカラムを探し、データを読み取ります。この変数が `false` の場合、カラム名に関係なく、Hive テーブルのカラム順に従って Parquet ファイルからデータを読み取ります。Hive の `parquet.column.index.access` 変数に似ています。このパラメータは最上位のカラム名にのみ適用され、Struct 内部では無効です。 | 2.1.6+、3.0.3+ |
| `hive_orc_use_column_names` | `true` | `hive_parquet_use_column_names` と同様ですが、Hive テーブルの ORC データに適用されます。Hive の `orc.force.positional.evolution` 変数に似ています。 | 2.1.6+、3.0.3+ |

## 書き込み操作 {#write-operations}

INSERT ステートメントを使用して Hive テーブルにデータを書き込めます。Doris が作成した Hive テーブル、および互換性のある形式を使用する既存の Hive テーブルが対象です。

パーティションテーブルでは、データに基づいて対応するパーティションに自動的に書き込むか、新しいパーティションを作成します。4.1.5 以降、`PARTITION (column = literal)` は静的パーティション、および静的パーティションカラムと動的パーティションカラムの組み合わせをサポートします。静的パーティションカラムは INSERT のターゲットカラム一覧と SELECT または VALUES の出力から除き、残りの動的パーティションカラムを入力に含めてください。

### INSERT INTO {#insert-into}

INSERT 操作は、ターゲットテーブルにデータを追加します。

```sql
INSERT INTO hive_tbl VALUES (val1, val2, val3, val4);
INSERT INTO hive_ctl.hive_db.hive_tbl SELECT col1, col2 FROM internal.db1.tbl1;

INSERT INTO hive_tbl(col1, col2) VALUES (val1, val2);
INSERT INTO hive_tbl(col1, col2, partition_col1, partition_col2) VALUES (1, 2, "beijing", "2023-12-12");
```

4.1.5 以降、静的パーティションへの書き込み、および静的パーティションと動的パーティションを組み合わせた書き込みをサポートします。

```sql
-- Full Static Partition
INSERT INTO hive_tbl PARTITION (partition_col1='2026-07-30', partition_col2='beijing')
VALUES (val1, val2);
INSERT INTO hive_tbl PARTITION (partition_col1='2026-07-30', partition_col2='beijing')
SELECT col1, col2 FROM source_table;

-- Hybrid Partition Mode: "partition_col1" is static, "partition_col2" comes from SELECT dynamically
INSERT INTO hive_tbl PARTITION (partition_col1='2026-07-30')
VALUES (val1, val2, partition_val2);
INSERT INTO hive_tbl PARTITION (partition_col1='2026-07-30')
SELECT col1, col2, partition_col2 FROM source_table;
```

### INSERT OVERWRITE {#insert-overwrite}

INSERT OVERWRITE は、テーブル内の既存データを新しいデータで完全に置き換えます。

```sql
INSERT OVERWRITE TABLE hive_tbl VALUES (val1, val2, val3, val4);
INSERT OVERWRITE TABLE hive_ctl.hive_db.hive_tbl(col1, col2) SELECT col1, col2 FROM internal.db1.tbl1;
```

4.1.5 以降、静的パーティションへの書き込み、および静的パーティションと動的パーティションを組み合わせた書き込みをサポートします。

```sql
-- Full Static Partition
INSERT OVERWRITE TABLE hive_tbl PARTITION (partition_col1='2026-07-30', partition_col2='beijing')
VALUES (val1, val2);
INSERT OVERWRITE TABLE hive_tbl PARTITION (partition_col1='2026-07-30', partition_col2='beijing')
SELECT col1, col2 FROM source_table;

-- Hybrid Partition Mode: "partition_col1" is static, "partition_col2" comes from SELECT dynamically
INSERT OVERWRITE TABLE hive_tbl PARTITION (partition_col1='2026-07-30')
VALUES (val1, val2, partition_val2);
INSERT OVERWRITE TABLE hive_tbl PARTITION (partition_col1='2026-07-30')
SELECT col1, col2, partition_col2 FROM source_table;
```

INSERT OVERWRITE のセマンティクスは Hive と同じで、次のように動作します。

* ターゲットテーブルがパーティションテーブルで、ソーステーブルが空の場合、操作は何も変更しません。ターゲットテーブルはそのまま残ります。

* ターゲットテーブルが非パーティションテーブルで、ソーステーブルが空の場合、ターゲットテーブルは空になります。

* 4.1.5 以降、書き込み時に静的パーティションを指定でき、静的パーティションと動的パーティションを組み合わせたモードもサポートされます。ただし、静的パーティションを指定しても、ソースクエリの結果が空の場合、指定したパーティションはクリアされません。

**静的パーティションの完全な例（4.1.5 以降）**

このページで説明した Hive Catalog を設定し、既存の `hive_ctl.hive_db` データベースを用意して、テーブルの作成、書き込み、クエリの権限を付与します。書き込みに使用する Catalog には `fs.defaultFS` の設定が必要です。この例では、静的な日付と動的な地域を組み合わせた後、完全に指定した静的パーティション 1 つを上書きします。

```sql
CREATE TABLE hive_ctl.hive_db.static_write_demo (
    id INT,
    dt STRING,
    region STRING
)
ENGINE=HIVE
PARTITION BY LIST (dt, region) ()
PROPERTIES ("file_format" = "parquet");

INSERT INTO hive_ctl.hive_db.static_write_demo PARTITION (dt='2026-10-01')
VALUES (1, 'beijing'), (2, 'shanghai');

INSERT OVERWRITE TABLE hive_ctl.hive_db.static_write_demo
PARTITION (dt='2026-10-01', region='beijing') VALUES (3);

SELECT id, dt, region FROM hive_ctl.hive_db.static_write_demo ORDER BY id;
```

```text
+----+------------+----------+
| id | dt         | region   |
+----+------------+----------+
|  2 | 2026-10-01 | shanghai |
|  3 | 2026-10-01 | beijing  |
+----+------------+----------+
```

静的パーティションの値にはリテラルを指定する必要があります。同じパーティションキーを複数回指定したり、明示的な INSERT カラム一覧に静的パーティションカラムを重複して含めたりしないでください。静的キーの名前は大文字と小文字を区別せずに照合されます。存在しないパーティションカラムを指定するとエラーになります。

### CTAS {#ctas}

`CTAS (CREATE TABLE AS SELECT)` ステートメントを使用して Hive テーブルを作成し、データを挿入できます。

```sql
CREATE TABLE hive_ctas ENGINE=hive AS SELECT * FROM other_table;
```

次の例のように、CTAS ではファイル形式やパーティション方式などを指定できます。

```sql
CREATE TABLE hive_ctas ENGINE=hive
PARTITION BY LIST (pt1, pt2) ()
AS SELECT col1, pt1, pt2 FROM part_ctas_src WHERE col1 > 0;

CREATE TABLE hive_ctl.hive_db.hive_ctas (col1, col2, pt1) ENGINE=hive
PARTITION BY LIST (pt1) ()
PROPERTIES (
    "file_format"="parquet",
    "compression"="zstd"
)
AS SELECT col1, pt1 AS col2, pt2 AS pt1 FROM test_ctas.part_ctas_src WHERE col1 > 0;
```

### 関連パラメータ {#related-parameters-1}

* BE 設定

  | パラメータ名 | デフォルト値 | 説明 |
  | ----------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------- | ----------- |
  | `hive_sink_max_file_size` | 1GB | データファイルの最大サイズ。データサイズがこの上限を超えると、現在のファイルを閉じ、新しいファイルを作成して書き込みを続けます。 |
  | `table_sink_partition_write_max_partition_nums_per_writer` | 128 | BE ノード上の各インスタンスが書き込めるパーティション数の上限。 |
  | `table_sink_non_partition_write_scaling_data_processed_threshold` | 25MB | 非パーティションテーブルで書き込みをスケールさせるためのデータ量しきい値。`table_sink_non_partition_write_scaling_data_processed_threshold` のデータ量が追加されるたびに、新しいライター（インスタンス）を使用します。この仕組みはデータ量に応じてライター（インスタンス）数を調整し、並列書き込みのスループットを高めるとともに、データ量が少ない場合のリソース使用量とファイル数を抑えます。 |
  | `table_sink_partition_write_min_data_processed_rebalance_threshold` | 25MB | パーティションテーブルでリバランスを開始するための最小データ量しきい値。`current accumulated data volume` - `data volume since last rebalancing or initial accumulation` >= `table_sink_partition_write_min_data_processed_rebalance_threshold` の場合にリバランスが実行されます。最終的なファイルサイズに大きなばらつきがある場合は、このしきい値を下げるとバランスを改善できます。ただし、しきい値を下げるとリバランスのコストが増え、性能に影響する可能性があります。 |
  | `table_sink_partition_write_min_partition_data_processed_rebalance_threshold` | 15MB | リバランスを開始するためのパーティションデータ量の最小しきい値。`current partition data volume` >= `threshold` \* `number of tasks already allocated to the partition` の場合にリバランスが実行されます。最終的なファイルサイズに大きなばらつきがある場合は、このしきい値を下げるとバランスを改善できます。ただし、しきい値を下げるとリバランスのコストが増え、性能に影響する可能性があります。 |


## データベースとテーブルの管理 {#database-and-table-management}

Doris を通じて Hive Metastore 内のデータベースとテーブルを作成、削除できます。これらの操作では、Doris は Hive Metastore API を呼び出すだけで、Hive メタデータ自体を保存または永続化しません。

### データベースの作成と削除 {#creating-and-dropping-databases}

`SWITCH` ステートメントで適切な Catalog に切り替え、`CREATE DATABASE` ステートメントを実行できます。

```sql
SWITCH hive_ctl;
CREATE DATABASE [IF NOT EXISTS] hive_db;
```

次のように、完全修飾名を使用してデータベースを作成したり、場所を指定したりすることもできます。

```sql
CREATE DATABASE [IF NOT EXISTS] hive_ctl.hive_db;

CREATE DATABASE [IF NOT EXISTS] hive_ctl.hive_db
PROPERTIES ('location'='hdfs://172.21.16.47:4007/path/to/db/');
```

`SHOW CREATE DATABASE` コマンドでデータベースの場所を確認できます。

```sql
mysql> SHOW CREATE DATABASE hive_db;
+----------+---------------------------------------------------------------------------------------------+
| Database | Create Database                                                                             |
+----------+---------------------------------------------------------------------------------------------+
| hive_db  | CREATE DATABASE hive_db LOCATION 'hdfs://172.21.16.47:4007/usr/hive/warehouse/hive_db.db'   |
+----------+---------------------------------------------------------------------------------------------+
```

データベースを削除するには、次を実行します。

```sql
DROP DATABASE [IF EXISTS] hive_ctl.hive_db;
```

:::caution
Hive データベースを削除するには、まずそのデータベース内のすべてのテーブルを削除する必要があります。そうしないとエラーが発生します。この操作により、Hive 内の対応するデータベースも削除されます。
:::

### テーブルの作成と削除 {#creating-and-dropping-tables}

- **テーブルの作成**

  Doris は、Hive におけるパーティションテーブルと非パーティションテーブルの両方の作成をサポートします。

  ```sql
  -- Create unpartitioned hive table
  CREATE TABLE unpartitioned_table (
    `col1` BOOLEAN COMMENT 'col1',
    `col2` INT COMMENT 'col2',
    `col3` BIGINT COMMENT 'col3',
    `col4` CHAR(10) COMMENT 'col4',
    `col5` FLOAT COMMENT 'col5',
    `col6` DOUBLE COMMENT 'col6',
    `col7` DECIMAL(9,4) COMMENT 'col7',
    `col8` VARCHAR(11) COMMENT 'col8',
    `col9` STRING COMMENT 'col9'
  )  ENGINE=hive
  PROPERTIES (
    'file_format'='parquet'
  );

  -- Create partitioned hive table
  -- The partition columns must be in table's column definition list
  CREATE TABLE partition_table (
    `col1` BOOLEAN COMMENT 'col1',
    `col2` INT COMMENT 'col2',
    `col3` BIGINT COMMENT 'col3',
    `col4` DECIMAL(2,1) COMMENT 'col4',
    `pt1` VARCHAR COMMENT 'pt1',
    `pt2` VARCHAR COMMENT 'pt2'
  )  ENGINE=hive
  PARTITION BY LIST (pt1, pt2) ()
  PROPERTIES (
    'file_format'='orc',
    'compression'='zlib'
  );

  -- Create text format table(Since 2.1.7 & 3.0.3)
  CREATE TABLE text_table (
      `id` INT,
      `name` STRING
  ) PROPERTIES (
      'file_format'='text',
      'compression'='gzip',
      'field.delim'='\t',
      'line.delim'='\n',
      'collection.delim'=';',
      'mapkey.delim'=':',
      'serialization.null.format'='\\N',
      'escape.delim'='\\'
  );
  ```

  テーブルを作成した後、`SHOW CREATE TABLE` コマンドで Hive テーブルの作成ステートメントを確認できます。

  Hive のテーブル作成構文とは異なり、Doris でパーティションテーブルを作成する際は、パーティションカラムをテーブルスキーマに含める必要があります。また、パーティションカラムはスキーマの末尾に同じ順序で配置する必要があります。

  :::tip
  ACID トランザクション機能がデフォルトで有効になっている Hive クラスターでは、Doris が作成したテーブルの `transactional` プロパティが `true` に設定されます。Doris がサポートする Hive トランザクションテーブルの機能は一部に限られるため、作成した Hive テーブルを Doris が読み取れない場合があります。これを避けるには、テーブルプロパティに `"transactional" = "false"` を明示的に設定して、非トランザクションの Hive テーブルを作成します。

  ```sql
  CREATE TABLE non_acid_table(
    `col1` BOOLEAN COMMENT 'col1',
    `col2` INT COMMENT 'col2',
    `col3` BIGINT COMMENT 'col3'
  ) ENGINE=hive
  PROPERTIES (
    'transactional'='false'
  );
  ```
  :::

- **テーブルの削除**

  `DROP TABLE` ステートメントを使用して Hive テーブルを削除できます。テーブルを削除すると、パーティションデータを含むすべてのデータも削除されます。

- **カラム型のマッピング**

  詳しくは「カラム型のマッピング」を参照してください。次の制限に注意してください。

  - カラムにはデフォルトの NULL 許容型を使用する必要があり、`NOT NULL` はサポートされません。
  - Hive 3.0 はデフォルト値の設定をサポートします。デフォルト値を設定するには、Catalog プロパティに `"hive.version" = "3.0.0"` を明示的に追加します。
  - 挿入するデータの型に互換性がない場合（数値型に `'abc'` を挿入する場合など）、値は `null` に変換されます。

- **パーティショニング**

  Hive のパーティション型は、Doris の List パーティションに対応します。そのため、Doris で Hive パーティションテーブルを作成するときは List パーティション構文を使用しますが、各パーティションを明示的に列挙する必要はありません。Doris はデータの挿入時に、データの値に基づいて対応する Hive パーティションを自動的に作成します。単一カラムと複数カラムのパーティションテーブルをサポートします。

- **ファイル形式**

  - ORC（デフォルト）
  - Parquet

    DATETIME 型を Parquet ファイルに書き込む際に使用される物理型は、INT64 ではなく INT96 です。これは Hive 4.0 より前のバージョンの動作と互換性を保つためです。

  - Text（バージョン 2.1.7 および 3.0.3 以降でサポート）

      Text 形式では、次のテーブルプロパティがサポートされます。

		  - `field.delim`: カラム区切り文字。デフォルトは `\1` です。
		  - `line.delim`: 行区切り文字。デフォルトは `\n` です。
		  - `collection.delim`: 複合型の要素の区切り文字。デフォルトは `\2` です。
		  - `mapkey.delim`: map のキーと値のペアの区切り文字。デフォルトは `\3` です。
		  - `serialization.null.format`: `NULL` 値の保存形式。デフォルトは `\N` です。
		  - `escape.delim`: エスケープ文字。デフォルトは `\` です。

- **圧縮形式**

  - Parquet: snappy（デフォルト）、zstd、plain（非圧縮）
  - ORC: snappy、zlib（デフォルト）、zstd、plain（非圧縮）
  - Text: gzip、deflate、bzip2、zstd、lz4、lzo、snappy、plain（デフォルト、非圧縮）

- **ストレージ媒体**

  - HDFS
  - オブジェクトストレージ

## Hive Metastore イベントの購読 {#subscribing-to-hive-metastore-events}

FE ノードが HMS の Notification Events を定期的に読み取ることで、Doris は Hive テーブルのメタデータの変更をリアルタイムで検出し、メタデータの適時性を高められます。現在、次のイベントをサポートしています。

| イベント | 操作と対応する動作 |
| ---------------- | ------------------------------------------------------------------------- |
| CREATE DATABASE  | 対応するデータディレクトリにデータベースを作成します。 |
| DROP DATABASE    | 対応するデータディレクトリからデータベースを削除します。 |
| ALTER DATABASE   | 主にデータベースのプロパティ、コメント、デフォルトの保存場所の変更に関係します。これらの変更は Doris による外部データディレクトリのクエリに影響しないため、現在このイベントは無視されます。 |
| CREATE TABLE     | 対応するデータベースにテーブルを作成します。 |
| DROP TABLE       | 対応するデータベースからテーブルを削除し、テーブルキャッシュを無効にします。 |
| ALTER TABLE      | 名前が変更された場合は古いテーブルを削除して新しい名前で作成し、それ以外の場合はテーブルキャッシュを無効にします。 |
| ADD PARTITION    | 対応するテーブルのキャッシュ済みパーティション一覧にパーティションを追加します。 |
| DROP PARTITION   | キャッシュ済みパーティション一覧からパーティションを削除し、パーティションキャッシュを無効にします。 |
| ALTER PARTITION  | 名前が変更された場合は古いパーティションを削除して新しい名前で作成し、それ以外の場合はパーティションキャッシュを無効にします。 |

:::tip
1. データのインポートによってファイルが変更されると、パーティションテーブルでは `ALTER PARTITION` イベントが、非パーティションテーブルでは `ALTER TABLE` イベントが発生します。

2. HMS を経由せずにファイルシステムを直接操作した場合、HMS は対応するイベントを生成せず、Doris もメタデータの変更を検出しません。
:::

`fe.conf` の次のパラメータが、この機能に関係します。

1. `enable_hms_events_incremental_sync`: メタデータの自動増分同期を有効にします。デフォルトでは無効です。

2. `hms_events_polling_interval_ms`: イベントを読み取る間隔。デフォルトは 10000 ミリ秒です。

3. `hms_events_batch_size_per_rpc`: RPC ごとに読み取るイベントの最大数。デフォルトは 500 です。

この機能を使用するには（Huawei Cloud MRS を除く）、HMS の `hive-site.xml` を変更し、HMS と HiveServer2 の両方を再起動する必要があります。

```xml
<property>
    <name>hive.metastore.event.db.notification.api.auth</name>
    <value>false</value>
</property>
<property>
    <name>hive.metastore.dml.events</name>
    <value>true</value>
</property>
<property>
    <name>hive.metastore.transactional.event.listeners</name>
    <value>org.apache.hive.hcatalog.listener.DbNotificationListener</value>
</property>
```

Huawei Cloud MRS の場合は、`hivemetastore-site.xml` を変更し、HMS と HiveServer2 の両方を再起動する必要があります。

```xml
<property>
    <name>metastore.transactional.event.listeners</name>
    <value>org.apache.hive.hcatalog.listener.DbNotificationListener</value>
</property>
```

## 付録 {#appendix}

### トランザクションの仕組み {#transaction-mechanism}

Hive への書き込み操作は、個別のトランザクションに置かれます。トランザクションがコミットされる前、データは外部から見えません。コミット後に初めて、関連するテーブル操作が他のユーザーから見えるようになります。

トランザクションは操作の原子性を保証します。つまり、トランザクション内のすべての操作がまとめて成功するか、まとめて失敗します。

トランザクションは操作の分離性を完全には保証できませんが、ファイルシステム操作と Hive Metastore のメタデータ操作を分離することで、不整合を最小限に抑えるようにしています。

たとえば、Hive テーブルの複数のパーティションを変更するトランザクションで、タスクが 2 つのバッチに分割された場合、2 番目のバッチが完了する前に 1 番目のバッチが外部から見える可能性があります。つまり、1 番目のバッチのパーティションは読み取れますが、2 番目のバッチのパーティションは読み取れません。

トランザクションのコミット中に例外が発生した場合、HDFS ファイルと Hive Metastore メタデータへの変更を含め、トランザクション全体がロールバックされます。ユーザーによる追加の対応は不要です。

### 同時書き込みの仕組み {#concurrent-writing-mechanism}

Apache Doris は現在、複数の insert ステートメントによる同時書き込みをサポートしています。ただし、同時書き込みによって競合が発生しないことをユーザーが確認する必要があります。

通常の非トランザクション Hive テーブルには完全なトランザクション機構がないため、Apache Doris のトランザクション機構は不整合が生じる時間を最小限に抑えることを目指していますが、真の ACID 特性は保証できません。そのため、Apache Doris から Hive テーブルへの同時書き込みは、データの整合性に問題を生じさせる可能性があります。

1. **同時に実行する `INSERT` 操作**

2. `INSERT` 操作はデータを追加するため、同時に実行しても競合せず、期待どおりの結果が得られます。

3. **同時に実行する `INSERT OVERWRITE` 操作**

4. 同じテーブルまたはパーティションに対する `INSERT OVERWRITE` 操作を同時に実行すると、データの損失や破損が発生し、結果が予測できなくなる可能性があります。

5. 一般的な対処方法は次のとおりです。

   * パーティションテーブルでは、異なるパーティションにデータを書き込みます。異なるパーティションに対する同時操作は競合しません。

   * 非パーティションテーブルでは、競合を避けるために `INSERT OVERWRITE` の代わりに `INSERT` を使用します。

   * 競合する可能性がある操作については、業務側で一度に 1 つの書き込み操作だけが実行されるようにします。

### HDFS のファイル操作 {#hdfs-file-operations}

HDFS 上の Hive テーブルデータは、通常まず一時ディレクトリに書き込まれ、その後 `rename` などのファイルシステム操作で確定されます。以下では、データ操作ごとに HDFS 上で行われるファイル操作を詳しく説明します。

データの一時ディレクトリの形式: `/tmp/.doris_staging/<username>/<uuid>`

書き込まれるデータファイル名の形式: `<query-id>_<uuid>-<index>.<compress-type>.<file-type>`

さまざまなシナリオでのファイル操作の例を示します。

1. **非パーティションテーブル**

   * **追加（データの追加）**

     * ターゲットテーブルのディレクトリ: `hdfs://ns/usr/hive/warehouse/example.db/table1`

     * 一時ファイル: `hdfs://ns/tmp/.doris_staging/root/f02247cb662846038baae272af5eeb05/b35fdbcea3a4e39-86d1f36987ef1492_7e3985bf-9de9-4fc7-b84e-adf11aa08756-0.orc`

     * コミット時に、すべての一時ファイルがターゲットテーブルのディレクトリへ移動されます。

   * **上書き（データの置き換え）**

     * ターゲットテーブルのディレクトリ: `hdfs://ns/usr/hive/warehouse/example.db/table1`

     * 一時ファイル: `hdfs://ns/tmp/.doris_staging/root/f02247cb662846038baae272af5eeb05/b35fdbcea3a4e39-86d1f36987ef1492_7e3985bf-9de9-4fc7-b84e-adf11aa08756-0.orc`

     * コミット時の手順:

       1. ターゲットテーブルのディレクトリを一時ディレクトリにリネームします: `hdfs://ns/usr/hive/warehouse/example.db/_temp_b35fdbcea3a4e39-86d1f36987ef1492_table1`

       2. 一時ディレクトリをターゲットテーブルのディレクトリにリネームします。

       3. 一時的なターゲットテーブルのディレクトリを削除します。

2. **パーティションテーブル**

   * **追加（新しいパーティションへの追加）**

     * ターゲットテーブルのディレクトリ: `hdfs://ns/usr/hive/warehouse/example.db/table2/part_col=2024-01-01`

     * 一時ファイル: `hdfs://ns/tmp/.doris_staging/root/a7eac7505d7a42fdb06cb9ef1ea3e912/par1=a/d678a74d232345e0-b659e2fb58e86ffd_549ad677-ee75-4fa1-b8a6-3e821e1dae61-0.orc`

     * コミット時に、一時ディレクトリがターゲットテーブルのディレクトリにリネームされます。

   * **追加（既存パーティションへのデータ追加）**

     * ターゲットテーブルのディレクトリ: `hdfs://ns/usr/hive/warehouse/example.db/table2/part_col=2024-01-01`

     * 一時ファイル: `hdfs://ns/tmp/.doris_staging/root/a7eac7505d7a42fdb06cb9ef1ea3e912/par1=a/d678a74d232345e0-b659e2fb58e86ffd_549ad677-ee75-4fa1-b8a6-3e821e1dae61-0.orc`

     * コミット時に、一時ディレクトリ内のファイルがターゲットテーブルのディレクトリへ移動されます。

   * **上書き（既存パーティションの置き換え）**

     * ターゲットテーブルのディレクトリ: `hdfs://ns/usr/hive/warehouse/example.db/table2/part_col=2024-01-01`

     * 一時ファイル: `hdfs://ns/tmp/.doris_staging/root/a7eac7505d7a42fdb06cb9ef1ea3e912/par1=a/d678a74d232345e0-b659e2fb58e86ffd_549ad677-ee75-4fa1-b8a6-3e821e1dae61-0.orc`

     * コミット時の手順:

       1. ターゲットパーティションのディレクトリを一時パーティションディレクトリにリネームします: `hdfs://ns/usr/hive/warehouse/example.db/table2/_temp_d678a74d232345e0-b659e2fb58e86ffd_part_col=2024-01-01`

       2. 一時パーティションディレクトリをターゲットパーティションのディレクトリにリネームします。

       3. 一時的なターゲットパーティションのディレクトリを削除します。
