Doris は、さまざまなメタデータサービスを介して Iceberg テーブルのデータにアクセスできます。データの読み取りに加え、INSERT、INSERT OVERWRITE、UPDATE、DELETE、MERGE INTO による Iceberg テーブルへの書き込みもサポートします。

[Apache Doris と Apache Iceberg のクイックスタート](../best-practices/doris-iceberg.md)。

:::tip
Hive Catalog を使用し、Hive Metastore をメタデータサービスとして Iceberg テーブルにアクセスすることもできます。ただし、互換性の問題を避けるため、Iceberg Catalog を直接使用することを推奨します。
:::

## 適用シナリオ {#applicable-scenarios}

| シナリオ | 説明 |
| ----------- | ----------- |
| クエリ高速化 | Doris の分散コンピューティングエンジンから Iceberg データに直接アクセスし、クエリを高速化します。 |
| データ統合 | Iceberg データを読み取って Doris の内部テーブルに書き込むか、Doris のコンピューティングエンジンで ZeroETL 操作を実行します。 |
| データの書き戻し | Doris がサポートする任意のデータソースのデータを処理し、Iceberg テーブルのストレージに書き戻します。 |

## Catalog の設定 {#configuring-catalog}

### 構文 {#syntax}

```sql
CREATE CATALOG [IF NOT EXISTS] catalog_name PROPERTIES (
    'type' = 'iceberg',
    'iceberg.catalog.type' = '<iceberg_catalog_type>',
    'warehouse' = '<warehouse>', --optional
    {MetaStoreProperties},
    {StorageProperties},
    {IcebergProperties},
    {CommonProperties}
);
```

* `<iceberg_catalog_type>`

  Iceberg Catalog の種類です。次の値を指定できます。

  * `hms`：Hive Metastore をメタデータサービスとして使用します。

  * `rest`：Iceberg Rest Catalog インターフェースと互換性のあるメタデータサービスを使用します。

  * `hadoop`：ファイルシステム上のメタデータに直接アクセスします。

  * `glue`：AWS Glue をメタデータサービスとして使用します。

  * `dlf`：Alibaba Cloud DLF をメタデータサービスとして使用します。

  * `jdbc`：Iceberg JDBC Catalog をメタデータサービスとして使用します。

  * `s3tables`：AWS S3 Tables Catalog を使用して [S3 Table Bucket](https://aws.amazon.com/s3/features/tables/) にアクセスします。

* `<warehouse>`

  Iceberg の warehouse パスです。`<iceberg_catalog_type>` が `hadoop` の場合は必須です。

  `warehouse` パスは `Database` パスの一つ上の階層を指す必要があります。たとえば、テーブルのパスが `s3://bucket/path/to/db1/table1` なら、`warehouse` は `s3://bucket/path/to/` です。

* `{MetaStoreProperties}`

  MetaStoreProperties には、Metastore メタデータサービスへの接続情報と認証情報を指定します。[サポートされるメタデータサービス]のセクションを参照してください。

* `{StorageProperties}`

  StorageProperties には、ストレージシステムへの接続情報と認証情報を指定します。[サポートされるストレージシステム]のセクションを参照してください。

* `{IcebergProperties}`

  IcebergProperties には、Iceberg Catalog 固有のパラメータを指定します。

    - `list-all-tables`

        Hive Metastore をメタデータサービスとして使用する Iceberg Catalog 向けの設定です。デフォルトは `true` です。デフォルトでは、`SHOW TABLES` は現在のデータベース内にあるすべての種類のテーブルを表示します。Hive Metastore には Iceberg 以外のテーブルも格納される場合があります。この方法が最も高性能です。

        `false` に設定すると、Doris は各テーブルの種類を一つずつ確認し、Iceberg テーブルのみを返します。テーブル数が多い場合、このモードの性能は低下します。

    - `iceberg.rest.view-enabled`

        バージョン 4.0.6 以降でサポートされます。

        Iceberg REST Catalog でのみ有効です。View 関連の操作（`listViews`、`loadView`、`viewExists`、`dropView` など）を有効にするかどうかを指定します。デフォルトは `true` です。

        Iceberg REST Catalog の実装によっては Table API は公開されていても、View API が利用できないかエラーを返します。Doris は `SHOW TABLES` の実行時に `ViewCatalog.listViews()` を呼び出してテーブル一覧から View を除外するため、このような REST サービスでは `SHOW TABLES` やテーブルメタデータのデータロードが失敗することがあります。

        この場合は `false` に設定してください。Doris は View 関連の操作をすべて省略し、`SHOW TABLES` などのメタデータ操作を正常に実行できるようになります。

* `{CommonProperties}`

  CommonProperties には共通プロパティを指定します。詳細は [Catalog の概要](../catalog-overview.md)を参照してください。

## メタデータキャッシュ {#meta-cache}

Apache Doris は外部データソースへのアクセス性能を高めるため、Iceberg のメタデータをキャッシュします。対象には、データロード済みのテーブルメタデータ、パーティションデータ、manifest、導出されたパーティション投影、最新の snapshot id、推定されたファイル形式が含まれます。

:::tip
Doris 4.1.x より前のバージョンでは、メタデータキャッシュは主に FE の設定項目でグローバルに制御されます。詳細は[メタデータキャッシュ](../meta-cache.md)を参照してください。
Doris 4.1.x 以降では、Iceberg Catalog の外部メタデータキャッシュを統一された `meta.cache.*` キーで設定します。以下のエントリは現行バージョンについて説明しています。Doris 4.1.x と 4.2.x では異なるエントリ群を使用し、このページの 4.x 版で説明しています。
:::

### キャッシュプロパティの設定 {#meta-cache-unified-model}

各キャッシュエントリには、統一された形式の設定キー `meta.cache.<engine>.<entry>.{enable,ttl-second,capacity,max-weight}` を使用します。Iceberg の `<engine>` は `iceberg` です。`meta.cache.iceberg.table.ttl-second` は共有 TTL 設定であり、`table` と `partition` エントリのデフォルト TTL、および独自の `<entry>` トークンを持たないキャッシュの TTL になります。この値を `0` にすると、これらすべてが無効になり、各クエリが最新のスナップショットを直接読み取ります。

| プロパティ | 例 | 意味 |
|---|---|---|
| `enable` | `true/false` | このキャッシュエントリを有効にするかどうか。 |
| `ttl-second` | `600`, `0`, `-1` | `0` はエントリを無効にします（直ちに反映され、最新データの確認に使用できます）。`-1` は無期限を意味します。その他の正の整数はアクセス時刻を基準とする秒単位の TTL です。 |
| `capacity` | `10000` | キャッシュエントリ数の上限です。`0` はエントリを無効にします。 |
| `max-weight` | `1GB` | Doris 4.1.4 以降でサポートされます。エントリが保持するメモリの推定上限を指定する任意の設定です。正の値が必要で、`0` は拒否されます。以下で対応と記載されたエントリにのみ指定できます。 |

**有効になる条件：** `enable=true`、`ttl-second != 0`、`capacity > 0` の場合、エントリが有効になります。さらに、FE 全体、Catalog、またはエントリ単位のメモリ上限が、推定メモリ使用量に基づく登録可否を制御します。[外部メタデータキャッシュのメモリ管理](../external-meta-cache-memory-management)を参照してください。

### キャッシュモジュール {#meta-cache-unified-modules}

次のエントリには固有の設定キーがあり、`max-weight` を指定できます。

| エントリ（`<entry>`） | プロパティキーのプレフィックス | `ENTRY_NAME` | キャッシュ内容と効果 | デフォルトの enable / TTL / capacity |
|---|---|---|---|---|
| `table` | `meta.cache.iceberg.table.` | `iceberg-table` | データロード済みの Iceberg テーブルメタデータ。Catalog との通信やメタデータファイルの読み取りを減らします。 | `true` / 86400 秒 / 1000 |
| `partition` | `meta.cache.iceberg.partition.` | `iceberg-partition` | テーブルのスナップショットの生のパーティションデータ。 | `true` / `table` と同じ / 1000 |
| `manifest` | `meta.cache.iceberg.manifest.` | `iceberg-manifest` | 解析済みの manifest 内容。スキャン計画で使用されるのは `enable` が `true` の場合のみで、デフォルトは `false` です。 | キャッシュ自体は `true`、使用は `false` / 無期限 / 100000 |
| `partition_view` | `meta.cache.iceberg.partition_view.` | `iceberg.mvcc-partition-view`, `iceberg.list-partitions-view` | 一つのエントリ上限を共有する、導出された二種類のパーティション投影。 | `true` / 86400 秒 / 1000 |

次のキャッシュには `<entry>` トークンがありません。Catalog と FE 全体のメモリ上限に従い、TTL には `meta.cache.iceberg.table.ttl-second` を使用します：`iceberg-latest-snapshot`（最新の snapshot id）、`iceberg-format`（推定されたファイル形式）、`iceberg-comment`（テーブルのコメント。vended credentials を使用する REST Catalog でのみ作成）、`iceberg-equality-delete-field-ids`。

Iceberg テーブルのカラムスキーマは、共有の `default` エンジン（`meta.cache.default.schema.*`）によってキャッシュされます。

:::note
`iceberg.rest.session` が `user` の場合、共有キャッシュがユーザーごとの認可を迂回してしまうため、`table`、`partition`、`partition_view`、latest-snapshot、format の各キャッシュは作成されません。vended credentials を使用する REST Catalog でも `table` キャッシュは作成されません。
:::

### 旧パラメータの対応と変換 {#meta-cache-mapping}

| 旧プロパティキー | 統一キー | 説明 |
|---|---|---|
| `schema.cache.ttl-second` | `meta.cache.default.schema.ttl-second` | テーブルスキーマキャッシュの有効期限 |

### ベストプラクティス {#meta-cache-best-practices}

* **最新データへのリアルタイムアクセス**：各クエリで Iceberg テーブルの最新スナップショットを参照するには、`meta.cache.iceberg.table.ttl-second` を `0` に設定します。
  ```sql
  -- Disable the table, partition, latest-snapshot, and format caches to read the latest snapshot live
  ALTER CATALOG iceberg_ctl SET PROPERTIES ("meta.cache.iceberg.table.ttl-second" = "0");
  ```
* **性能の最適化**：
    * manifest キャッシュを有効にすると、大規模なテーブルのクエリ計画を大幅に高速化できます。manifest が大きい場合は、`max-weight` でメモリ使用量を制限します。
      ```sql
      ALTER CATALOG iceberg_ctl SET PROPERTIES (
        "meta.cache.iceberg.manifest.enable" = "true",
        "meta.cache.iceberg.manifest.max-weight" = "1GB"
      );
      ```
    * Catalog プロパティの変更が成功すると、影響を受けるメタデータキャッシュが破棄され、次回のアクセス時に新しい設定で再構築されます。`meta.cache.max-weight` または `schema.cache.ttl-second` を変更すると Catalog のすべてのキャッシュが破棄され、`meta.cache.<engine>.<entry>.*` を変更すると、そのエンジンのキャッシュが破棄されます。進行中のクエリには影響しません。

### 可観測性 {#meta-cache-unified-observability}

キャッシュのメトリクスは、`information_schema.catalog_meta_cache_statistics` システムテーブルで確認できます。`ENTRY_NAME` には上の表に示した名前が表示され、`default` エンジンの行は共有のテーブルスキーマキャッシュを示します。

```sql
SELECT engine_name, entry_name,
       effective_enabled, ttl_second, capacity,
       estimated_size, hit_rate, max_weight, estimated_weight
FROM information_schema.catalog_meta_cache_statistics
WHERE catalog_name = 'iceberg_ctl'
ORDER BY engine_name, entry_name;
```

このシステムテーブルの詳細は、[catalog_meta_cache_statistics](../../admin-manual/system-tables/information_schema/catalog_meta_cache_statistics.md) を参照してください。

### メタデータと読み取りのエラー（4.1.5 以降） {#metadata-and-read-errors-since-415}

- `DESCRIBE`、`SHOW COLUMNS`、`SHOW CREATE TABLE` は、現在の Iceberg スキーマにある必須・任意の宣言を維持します。スキャンでは、スキーマ進化によって存在しないフィールドも引き続き処理できます。表示された NOT NULL 宣言は、そのフィールドが過去のすべてのファイルに存在することを保証しません。
- 開発版では、行単位の書き込みに使用するパーティションメタデータを、シリアル化されたパーティションデータとして保持します。4.1.5 のエラー `Cannot produce Iceberg row IDs with unsupported partition types in spec ...` は以前の Row ID 表現に関するもので、現在の表現には該当しません。
- コミット済みスナップショットが参照するデータファイルまたは delete file が見つからない場合、`ignore_not_found_file_in_external_table=true` でもクエリは失敗します。欠落したオブジェクトを復元するか、ファイルがすべて揃っている有効なスナップショットを選択してください。
- `schema.name-mapping.default` には有効な Iceberg Name Mapping JSON 配列を指定する必要があります。無効な値の場合、現在のカラム名にフォールバックして NULL を返すのではなく、データスキャンが失敗します。Spark などのライターでこのプロパティを修正または削除し、Doris でテーブルを更新してください。メタデータシステムテーブルへのクエリでは、このデータスキャンの検証は行われません。

バージョン 4.1.4 以降では、Iceberg の identity パーティションメタデータがすべての split とともに渡され、パスのパーティションキーはテーブルにあるすべてのパーティション仕様の identity カラムを網羅します。このため、**Partition Evolution** を経たテーブルでもパーティションカラムの値が正しく返されます。

Doris 4.2 のマッピング表、精度の規則、サポートされない型については、[Iceberg から Doris へのデータ型マッピング](iceberg-catalog/doris-type-mapping.md)を参照してください。

### カラム名の大文字と小文字 {#column-name-case}

Doris は Iceberg テーブルのカラム名の元の大文字・小文字を保持し、読み取り時には大文字・小文字を区別せずにカラムを照合します。大文字や大文字・小文字が混在するカラム名（`UserId` や `ORDER_ID` など）も正常にクエリできます。

:::info バージョンに関する注記

4.0 系のうち 4.0.8 より前のバージョンでは、読み取り時にカラムを完全一致で特定していたため、大文字・小文字が混在するカラム名を持つ Iceberg や Paimon のテーブルで、誤ったカラムが読み取られたり、クエリが失敗したりすることがありました。この問題は 4.0.8 で修正されました。

:::

## Namespace のマッピング {#namespace-mapping}

Iceberg のメタデータ階層は Catalog -> Namespace -> Table です。Namespace は複数階層にできます（Nested Namespace）。

```
      ┌─────────┐
      │ Catalog │
      └────┬────┘
           │
     ┌─────┴─────┐
  ┌──▼──┐     ┌──▼──┐
  │ NS1 │     │ NS2 │
  └──┬──┘     └──┬──┘
     │           │
┌────▼───┐    ┌──▼──┐
│ Table1 │    │ NS3 │
└────────┘    └──┬──┘
                 │
          ┌──────┴───────┐
     ┌────▼───┐     ┌────▼───┐
     │ Table2 │     │ Table3 │
     └────────┘     └────────┘
```


バージョン 3.1.2 以降、Doris は Iceberg Rest Catalog で Nested Namespace のマッピングをサポートします。

上の例のテーブルは、次のように Doris のメタデータへマッピングされます。

| Catalog | データベース | テーブル |
| --- | --- | --- |
| Catalog | NS1 | Table1 |
| Catalog | NS2.NS3 | Table2 |
| Catalog | NS2.NS3 | Table3 |

Nested Namespace のサポートは明示的に有効にする必要があります。詳細は [Iceberg Rest Catalog](../metastores/iceberg-rest.md) を参照してください。

### Iceberg Rest Catalog {#iceberg-rest-catalog}

:::caution 動作の変更（4.1.4）

バージョン 4.1.4 以降、`iceberg.rest.signing-name` に `glue`、`s3tables`、`osstables` などのマネージド署名サービスを設定する場合、`'iceberg.rest.sigv4-enabled' = 'true'` も**必ず**設定する必要があります。設定しないと、Catalog の作成時に次のエラーが発生します。

```text
Rest Catalog requires sigv4-enabled set to true when signing-name is <name>
```

既存の Catalog で `sigv4-enabled` を有効にせずに `signing-name` だけを設定している場合、アップグレード後に検証が失敗するため、このプロパティを追加する必要があります。

`osstables` を使用する場合は、`iceberg.rest.signing-region` と `iceberg.rest.sigv4-enabled = 'true'` の両方が必要です。設定しないと、次のエラーが報告されます。

```text
Rest Catalog requires signing-region and sigv4-enabled set to true when signing-name is osstables
```

## クエリ操作 {#query-operations}

### 基本的なクエリ {#basic-query}

```sql
-- 1. switch to catalog, use database and query
SWITCH iceberg;
USE iceberg_db;
SELECT * FROM iceberg_tbl LIMIT 10;

-- 2. use iceberg database directly
USE iceberg.iceberg_db;
SELECT * FROM iceberg_tbl LIMIT 10;

-- 3. use full qualified name to query
SELECT * FROM iceberg.iceberg_db.iceberg_tbl LIMIT 10;
```

### ファイルメタデータカラム {#file-metadata-columns}

> バージョン 4.2.0 以降でサポートされます。

Doris は Iceberg データテーブルに二つの非表示メタデータカラムを公開します。これらを使用して、クエリ結果の各行の元となった物理データファイルと行を特定できます。

| カラム | 型 | 説明 |
| --- | --- | --- |
| `_file` | `STRING NOT NULL` | Iceberg データファイルに記録された元のパス。 |
| `_pos` | `BIGINT NOT NULL` | データファイル全体の中での、ゼロ始まりの物理的な行位置。 |

前提条件として、前述の例に従って Iceberg Catalog を設定し、`id` カラムを持ち、Parquet または ORC ファイルを使用する Iceberg データテーブルを作成します。次のクエリでは、`iceberg_tbl` に `id` が `1` と `2` の行がすでに存在することを想定します。

```sql
SELECT id, `_file`, `_pos`
FROM iceberg.iceberg_db.iceberg_tbl
ORDER BY `_file`, `_pos`;
```

結果の例（ファイルパスはテーブルの場所によって異なります）：

```text
+----+---------------------------------------+------+
| id | _file                                 | _pos |
+----+---------------------------------------+------+
|  1 | s3://bucket/warehouse/db/table/a.orc |    0 |
|  2 | s3://bucket/warehouse/db/table/a.orc |    1 |
+----+---------------------------------------+------+
```

デフォルトでは、これらのカラムは `SELECT *` や `DESC` に表示されません。

`SELECT *` と `DESC` に非表示カラムを含めるには、セッションで `show_hidden_columns` を有効にします。

```sql
SET show_hidden_columns = true;
```

関連するセッション変数：

| 変数 | 型 | デフォルト | 必須 | 効果 |
| --- | --- | --- | --- | --- |
| `show_hidden_columns` | `BOOLEAN` | `false` | いいえ | `SELECT *` と `DESC` に非表示カラムを含めます。カラムを明示的に参照する場合は不要です。 |
| `enable_file_scanner_v2` | `BOOLEAN` | `true` | いいえ | クエリがこれらのメタデータカラムを参照する場合は、有効のままにする必要があります。 |
| `force_jni_scanner` | `BOOLEAN` | `false` | いいえ | JNI リーダーはこれらのメタデータカラムを生成できないため、無効のままにする必要があります。 |

行位置は物理ファイル全体に対する相対位置です。述語によるフィルタリング、削除処理、スキャンの分割によって、残った行の番号は振り直されません。したがって、`_file` と `_pos` を組み合わせると、現在のテーブルスナップショット内の物理レコードを特定できます。データファイルの書き換えや compaction によって両方の値が変わる可能性があるため、安定した論理行 ID として使用しないでください。

:::caution
これらのカラムを利用できるのは、Iceberg データテーブルを FileScannerV2 のネイティブ Parquet または ORC リーダーで読み取る場合のみです。`enable_file_scanner_v2` が無効、`force_jni_scanner` が有効、または選択されたデータファイルをネイティブ Parquet/ORC リーダーで読み取れない場合、これらのカラムを参照するクエリは失敗します。

`_file` と `_pos` は予約名で、大文字・小文字を区別せずに比較されます。Iceberg テーブルの物理カラム名に使用しないでください。
:::

### タイムトラベル {#time-travel}

Iceberg テーブルの特定のスナップショットを読み取れます。

デフォルトでは、読み取り要求は最新のスナップショットバージョンにアクセスします。

`$snapshots` システムテーブルを使用すると、Iceberg テーブルのスナップショットをクエリできます。

`FOR TIME AS OF` と `FOR VERSION AS OF` 句を使用すると、snapshot ID またはスナップショットの作成時刻に基づいて過去のデータを読み取れます。例を示します。

```sql
-- Read data as of a specific timestamp
SELECT * FROM iceberg_table FOR TIME AS OF '2023-01-01 00:00:00';

-- Read data as of a specific snapshot ID
SELECT * FROM iceberg_table FOR VERSION AS OF 123456789;
```

4.1.5 以降、`FOR TIME AS OF` は `yyyy-MM-dd HH:mm:ss` の後に小数秒を 1～9 桁指定できます。値をセッションのタイムゾーンで解釈し、スナップショット選択用にミリ秒へ変換します。たとえば `FOR TIME AS OF '2024-01-01 12:00:00.123456'` を使用します。スナップショットの選択精度はミリ秒であり、この構文を受け付けてもナノ秒精度のスナップショット時刻が保持されるわけではありません。

Doris 4.1.5 では、カラムの名前変更・削除・型の昇格やパーティション進化後の過去のスナップショットの読み取りも修正されています。各ファイルは、現在の仕様だけでなく、書き込まれた時点で有効だったパーティション仕様に従って解釈されます。過去のクエリを書き換えて現在のマテリアライズドビューを読み取るようにしてはいけません。

### Branch と Tag {#branch-and-tag}

> 3.1.0 以降。
>
> branch と tag の作成、削除、管理については、[Branch と Tag の管理]のセクションを参照してください。

Iceberg テーブルの特定の branch と tag を読み取れます。

Spark や Trino などのシステムとの互換性のため、複数の構文形式をサポートします。

```sql
-- BRANCH
SELECT * FROM iceberg_tbl@branch(branch1);
SELECT * FROM iceberg_tbl@branch("name" = "branch1");
SELECT * FROM iceberg_tbl FOR VERSION AS OF 'branch1';

-- TAG
SELECT * FROM iceberg_tbl@tag(tag1);
SELECT * FROM iceberg_tbl@tag("name" = "tag1");
SELECT * FROM iceberg_tbl FOR VERSION AS OF 'tag1';
```

`FOR VERSION AS OF` 構文では、パラメータがタイムスタンプか Branch/Tag 名かを Doris が自動的に判定します。

### View {#view}

> 3.1.0 以降

Iceberg view のクエリをサポートします。View のクエリは通常のテーブルのクエリと同様に動作します。次の点に注意してください。

- `hms` 型の Iceberg Catalog のみサポートします。
- View 定義の SQL は Doris の SQL 方言と互換性が必要です。互換性がない場合は解析エラーが発生します（方言変換機能は将来のバージョンで提供予定です）。

### Iceberg V3 の非表示カラム（Row Lineage） {#iceberg-v3-hidden-columns-row-lineage}

:::tip
これは実験的な機能で、バージョン 4.1.0 以降でサポートされます。
:::

Doris は Iceberg V3 テーブルの Row Lineage 非表示カラムをクエリできます。Iceberg V3 では、データ変更レコードの追跡に使用する行の lineage データを含むシステム非表示カラムが導入されました。増分同期やデータ監査に特に適しています。

- `_row_id`：データ行を一意に識別する数値です（データが書き込まれたファイルと位置に基づいて生成されます）。
- `_last_updated_sequence_number`：その行が最後に変更されたときの Sequence Number です。`UPDATE` または `MERGE INTO` がデータを更新すると、この数値はバージョン番号とともに自動的に増加します。

**非表示カラムのクエリ方法：**

デフォルトでは、`DESC` や `SELECT *` に非表示カラムは表示されません。カラム名を直接指定すれば、明示的にクエリできます。

```sql
SELECT id, _row_id, _last_updated_sequence_number FROM iceberg_tbl;
```

セッション変数 `show_hidden_columns` を有効にすると、`DESC` や `SELECT *` などの通常の表示にも非表示カラムを含められます。

```sql
SET show_hidden_columns = true;
DESC iceberg_tbl;
```

**注意事項：**

1. これらの行単位のパラメータを生成するには、Iceberg テーブルの形式バージョン（`format-version`）を `3` に設定する必要があります。V1 および V2 形式のテーブルで row lineage カラムをクエリすると、エラーが発生する場合があります。
2. 非表示カラムはシステムが管理します。`INSERT` などの書き込み文で `_row_id` や `_last_updated_sequence_number` カラムを明示的に指定したり、書き込んだりすることはできません。バージョン 4.1.4 以降、`format-version >= 3` のテーブルに対する `INSERT` 文のカラム一覧に row lineage カラムを指定すると、`Cannot specify invisible column '<name>' in INSERT statement` というエラーが直ちに発生します。

### Iceberg V3 のデフォルト値 {#iceberg-v3-default-values}

> バージョン 4.1.4 以降でサポートされます。

Iceberg V3 は二種類のカラムデフォルト値を定義しており、Doris は両方をサポートします。

- `initial-default`：カラム追加時に**既存の過去データ**へ割り当てるデフォルト値です。カラムが存在する前に書き込まれた古いデータファイルを読み取る場合、Doris は NULL の代わりにこのデフォルト値を返します。Parquet と ORC の両方でサポートされ、最上位カラム、`STRUCT` 内のネストしたサブフィールド、全体が存在しない複合型の親カラムに適用されます。述語の評価時にも有効です。
- `write-default`：書き込み時に**指定されていないカラム**へ補完するデフォルト値です。`INSERT INTO t (subset of columns) VALUES (...)` では、一覧にないカラムには現在の `write-default` が書き込まれます（以前のバージョンでは NULL が書き込まれていました）。

**DDL によるデフォルト値の指定：**

```sql
ALTER TABLE iceberg_tbl ADD COLUMN c1 INT DEFAULT 10;
```

この文は Iceberg の `write-default` と `initial-default` の両方を設定します。**テーブルの `format-version` が `3` である必要があります**。V1 と V2 のテーブルでは、NULL 以外のデフォルト値を持つカラムはサポートされません。

**`DEFAULT()` 式：**

バージョン 4.1.4 以降、`DEFAULT(<column>)` 式を使って DML 内でカラムのデフォルト値を明示的に参照できます。`INSERT`、`UPDATE ... SET`、`MERGE INTO` の各分岐で使用できます。

```sql
INSERT INTO iceberg_tbl VALUES (1, DEFAULT(c1));

UPDATE iceberg_tbl SET c1 = DEFAULT(c1) WHERE id = 1;

MERGE INTO iceberg_tbl t USING src s ON t.id = s.id
WHEN NOT MATCHED THEN INSERT VALUES (s.id, DEFAULT(c1));
```

動作：

- 書き込み先が Iceberg テーブルの場合、`DEFAULT()` はその書き込みで固定された Iceberg スキーマに基づいて解決されます。書き込み先に含まれないカラムを参照すると、`DEFAULT requires a target column reference` または `Cannot find column information for DEFAULT(<col>)` が報告されます。
- Iceberg 以外のカラムでは、そのカラムのデフォルト値が使用されます。デフォルト値がなく、カラムが NOT NULL または自動増分の場合、`Column '<name>' has no default value and does not allow NULL or column is auto-increment` というエラーになります。NULL 許容でデフォルト値がない場合は NULL が使用されます。
- その他のエラーには、`DEFAULT requires a column reference, but got: <expr>` と `DEFAULT cannot be used on generated column '<name>'` があります。

:::info 注記

Iceberg の `write-default` は書き込み側コネクタの概念です。`DESCRIBE`、`SHOW CREATE TABLE`、`information_schema.columns.COLUMN_DEFAULT` には公開され**ません**。

:::

## システムテーブル {#system-tables}

> 3.1.0 以降

Doris は、テーブルのメタデータ情報を取得するための Iceberg システムテーブルのクエリをサポートします。システムテーブルを使用して、スナップショット履歴、manifest ファイル、データファイル、パーティションなどのメタデータを確認できます。

Iceberg テーブルのメタデータにアクセスするには、テーブル名の末尾に `$` とシステムテーブル名を続けます。

```sql
SELECT * FROM iceberg_table$system_table_name;
```

たとえば、テーブルの履歴を表示するには、次を実行します。

```sql
SELECT * FROM iceberg_table$history;
```

> `all_manifests` システムテーブルはバージョン 4.0.4 以降でサポートされます。
>
> `position_deletes` システムテーブルはバージョン 4.1.4 以降でサポートされます。

:::caution 動作の変更（4.1.4）

バージョン 4.1.4 以降、Iceberg システムテーブルはネイティブ実行経路でクエリされ、`iceberg_meta()` テーブル関数は**削除されました**。代わりに `<table>$<system_table_name>` 構文を使用してください。[ICEBERG_META](../../sql-manual/sql-functions/table-valued-functions/iceberg-meta.md) を参照してください。

システムテーブル自体のアクセス構文と返される結果は変わりません。また、システムテーブルで `SHOW CREATE TABLE` がサポートされるようになりました。

:::

## 書き込み操作 {#write-operations}

### INSERT INTO {#insert-into}

INSERT 操作は、対象テーブルにデータを追加します。

例：

```sql
INSERT INTO iceberg_tbl VALUES (val1, val2, val3, val4);
INSERT INTO iceberg.iceberg_db.iceberg_tbl SELECT col1, col2 FROM internal.db1.tbl1;

INSERT INTO iceberg_tbl(col1, col2) VALUES (val1, val2);
INSERT INTO iceberg_tbl(col1, col2, partition_col1, partition_col2) VALUES (1, 2, 'beijing', '2023-12-12');
```

バージョン 3.1.0 以降、指定した branch へのデータ書き込みをサポートします。

```sql
INSERT INTO iceberg_tbl@branch(b1) values (val1, val2, val3, val4);
INSERT INTO iceberg_tbl@branch(b1) (col3, col4) values (val3, val4);
```

### INSERT OVERWRITE {#insert-overwrite}

INSERT OVERWRITE 操作は、テーブル内の既存データを新しいデータで完全に置き換えます。

```sql
INSERT OVERWRITE TABLE iceberg_tbl VALUES (val1, val2, val3, val4);
INSERT OVERWRITE TABLE iceberg.iceberg_db.iceberg_tbl(col1, col2) SELECT col1, col2 FROM internal.db1.tbl1;
```

バージョン 3.1.0 以降、指定した branch へのデータ書き込みをサポートします。

```sql
INSERT OVERWRITE TABLE iceberg_tbl@branch(b1) values (val1, val2, val3, val4);
INSERT OVERWRITE TABLE iceberg_tbl@branch(b1) (col3, col4) values (val3, val4);
```

バージョン 4.1.0 以降、静的パーティション（または混合パーティション）へのデータ書き込みをサポートします。

```sql
-- Full Static Partition
INSERT OVERWRITE TABLE iceberg_tbl PARTITION (dt='2025-01-25', region='bj')
SELECT id, name FROM source_table;

-- Hybrid Partition Mode: "dt" is static, "region" comes from SELECT dynamically
INSERT OVERWRITE TABLE iceberg_tbl PARTITION (dt='2025-01-25')
SELECT id, name, region FROM source_table;
```

### CTAS {#ctas}

`CTAS`（Create Table As Select）文を使用して、Iceberg テーブルの作成とデータ書き込みを行えます。

```sql
CREATE TABLE iceberg_ctas AS SELECT * FROM other_table;
```

CTAS では、ファイル形式、パーティション分割、その他のプロパティを指定できます。

```sql
CREATE TABLE iceberg_ctas
PARTITION BY LIST (pt1, pt2) ()
AS SELECT col1, pt1, pt2 FROM part_ctas_src WHERE col1 > 0;

CREATE TABLE iceberg.iceberg_db.iceberg_ctas (col1, col2, pt1)
PARTITION BY LIST (pt1) ()
PROPERTIES (
    'write-format'='parquet',
    'compression-codec'='zstd'
)
AS SELECT col1, pt1 AS col2, pt2 AS pt1 FROM test_ctas.part_ctas_src WHERE col1 > 0;
```

### INSERT INTO BRANCH {#insert-into-branch}

> 3.1.0 以降

```sql
INSERT INTO iceberg_table@branch(b1) SELECT * FROM other_table;
INSERT OVERWRITE TABLE iceberg_table@branch(b1) SELECT * FROM other_table;
```

### DELETE {#delete}

:::tip
これは実験的な機能で、バージョン 4.1.0 以降でサポートされます。
:::

`DELETE` 操作は、指定した条件を満たす Iceberg テーブルのデータ行を削除します。基盤となる主な仕組みは、V2 形式のテーブルでは Position Delete ファイルの書き込み、V3 形式のテーブルでは Puffin 形式の Deletion Vectors ファイルの書き込みです。

**前提条件：**

- Iceberg テーブルの形式バージョン（`format-version`）は 2 以上である必要があります。V1 形式のテーブルは `DELETE` 操作をサポートしません。

**構文：**

```sql
DELETE FROM iceberg_tbl WHERE <condition>;
```

**例：**

```sql
-- Delete a single row
DELETE FROM iceberg_tbl WHERE id = 1;

-- Delete using multiple conditions
DELETE FROM iceberg_tbl WHERE age > 30 AND name = 'Bob';

-- Delete using a subquery
DELETE FROM iceberg_tbl WHERE id IN (SELECT id FROM other_table WHERE status = 'inactive');
```

パーティションテーブルでも使用方法は同じです。

```sql
DELETE FROM iceberg_partition_tbl WHERE id = 10;
```

### UPDATE {#update}

:::tip
これは実験的な機能で、バージョン 4.1.0 以降でサポートされます。
:::

`UPDATE` 操作は、指定した条件を満たす Iceberg テーブルのデータ行を変更します。内部では、まず削除追跡情報（V2 では Position Delete ファイル、V3 では Puffin 形式の Deletion Vectors）を書き込んで古いデータ行を無効としてマークし、更新後の新しいデータファイルを追加します。V3 形式のオプションが有効な場合、新しく挿入された行の追跡値 `_last_updated_sequence_number` は自動的に進みます。

**前提条件：**

- Iceberg テーブルの形式バージョン（`format-version`）は 2 以上である必要があります。V1 形式のテーブルは `UPDATE` 操作をサポートしません。

**構文：**

```sql
UPDATE iceberg_tbl SET <column1> = <value1> [, <column2> = <value2>, ...] WHERE <condition>;
```

**例：**

```sql
-- Update a single column
UPDATE iceberg_tbl SET name = 'Alice_new' WHERE id = 1;

-- Update multiple columns
UPDATE iceberg_tbl SET name = 'Updated', age = 28 WHERE id = 2;

-- Update using expressions
UPDATE iceberg_tbl SET age = age * 2 + 1, name = concat(name, '-modified') WHERE id = 3;

-- Update using a subquery as condition
UPDATE iceberg_tbl SET name = 'UpdatedViaSubquery' WHERE id IN (SELECT id FROM other_table);
```

パーティションテーブルでも使用方法は同じです。

```sql
UPDATE iceberg_partition_tbl SET name = 'Updated' WHERE id = 10;
```

### MERGE INTO {#merge-into}

:::tip
これは実験的な機能で、バージョン 4.1.0 以降でサポートされます。
:::

`MERGE INTO` 操作は、ソースデータを対象の Iceberg テーブルと照合し、照合結果に応じて挿入、更新、削除を行います。データ同期や増分更新などに適しています。

**前提条件：**

- Iceberg テーブルの形式バージョン（`format-version`）は 2 以上である必要があります。V1 形式のテーブルは `MERGE INTO` 操作をサポートしません。

**構文：**

```sql
MERGE INTO target_table t
USING <source> s
ON <merge_condition>
[WHEN MATCHED [AND <condition>] THEN DELETE]
[WHEN MATCHED [AND <condition>] THEN UPDATE SET <column1> = <value1> [, ...]]
[WHEN NOT MATCHED [AND <condition>] THEN INSERT (<columns>) VALUES (<values>)]
```

`<source>` にはサブクエリまたは別のテーブルを指定できます。

**例：**

- 完全な照合操作（更新、削除、挿入を含む）：

    ```sql
    MERGE INTO iceberg_tbl t
    USING (
        SELECT 1 AS id, 'Alice_new' AS name, 26 AS age, 'U' AS flag
        UNION ALL
        SELECT 2, 'Bob', 30, 'D'
        UNION ALL
        SELECT 4, 'Dora', 28, 'I'
    ) s
    ON t.id = s.id
    WHEN MATCHED AND s.flag = 'D' THEN DELETE
    WHEN MATCHED THEN UPDATE SET
        name = s.name,
        age = s.age
    WHEN NOT MATCHED THEN INSERT (id, name, age)
    VALUES (s.id, s.name, s.age);
    ```

    上の例では、次の処理が行われます。
    * `id = 2` の行は `flag = 'D'` のため削除されます。
    * `id = 1` の行は新しい `name` と `age` で更新されます。
    * `id = 4` の行は対象テーブルに存在しないため挿入されます。

- 一致した行の更新のみを実行する：

    ```sql
    MERGE INTO iceberg_tbl t
    USING (SELECT 1 AS id, 'Alice_matched' AS name, 26 AS age) s
    ON t.id = s.id
    WHEN MATCHED THEN UPDATE SET name = s.name, age = s.age;
    ```

- 一致しない行の挿入のみを実行する：

    ```sql
    MERGE INTO iceberg_tbl t
    USING (SELECT 4 AS id, 'Dora' AS name, 40 AS age) s
    ON t.id = s.id
    WHEN NOT MATCHED THEN INSERT (id, name, age) VALUES (s.id, s.name, s.age);
    ```

- サブクエリをデータソースとして使用する：

    ```sql
    MERGE INTO iceberg_tbl t
    USING (SELECT id FROM other_table WHERE id = 2) s
    ON t.id = s.id
    WHEN MATCHED THEN UPDATE SET name = 'UpdatedViaSubquery';
    ```

- パーティションテーブルに対する `MERGE INTO` 操作：

    ```sql
    MERGE INTO iceberg_partition_tbl t
    USING (
        SELECT 1 AS id, 'Alice_new' AS name, 26 AS age, DATE '2024-01-01' AS dt, 'U' AS flag
        UNION ALL
        SELECT 2, 'Bob', 30, DATE '2024-01-02', 'D'
        UNION ALL
        SELECT 4, 'Dora', 28, DATE '2024-01-04', 'I'
    ) s
    ON t.id = s.id
    WHEN MATCHED AND s.flag = 'D' THEN DELETE
    WHEN MATCHED THEN UPDATE SET
        name = s.name,
        age = s.age
    WHEN NOT MATCHED THEN INSERT (id, name, age, dt)
    VALUES (s.id, s.name, s.age, s.dt);
    ```

**注意事項：**

1. 上記の三つの操作（`DELETE`、`UPDATE`、`MERGE INTO`）はいずれも Iceberg テーブルの形式バージョン（`format-version`）が 2 以上であることを必要とします。V1 形式のテーブルで実行すると、`must have format version 2 or higher for position deletes` というエラーが発生します。V3 形式のテーブルでは、システムは従来の Position Delete データを Puffin 形式の Deletion Vectors に置き換えるだけでなく、内容の更新が伴う場合には書き込まれるレコードの lineage ライフサイクル属性（`_last_updated_sequence_number`）も自動的に調整します。
2. これらの操作は Parquet と ORC の両方のファイル形式をサポートします。
3. 同時書き込み時には、Iceberg の楽観的同時実行制御が機能します。書き込み競合が発生すると、トランザクション競合の例外がスローされる場合があります。
4. 単独の `UPDATE` 操作と `MERGE INTO` 内の `UPDATE` 操作では、`age = age * 2 + 1` や `name = concat(name, '-modified')` のような式や関数を使用できます。
5. これらの操作は、パーティションテーブルと非パーティションテーブルの両方に適用できます。
6. **バージョン 4.1.4 以降**、`MERGE INTO` はソースと対象テーブルの照合関係を検証します。同じ対象行に複数のソース行が一致した場合、非決定的な結果を生成せず、`multiple source rows matched the same target row` というエラーで文が失敗します。一対多の一致が想定される場合は、先にソース側で重複を除去してください。

### 関連パラメータ {#related-parameters}

* BE（Backend）

  | パラメータ名 | デフォルト値 | 説明 |
  | ----------------------------------------------------------------------------- | ------------- | ----------- |
  | `iceberg_sink_max_file_size` | 1GB | データファイルの最大サイズです。書き込むデータがこのサイズを超えると、現在のファイルを閉じ、新しいファイルを作成して書き込みを続けます。 |
  | `table_sink_partition_write_max_partition_nums_per_writer` | 128 | BE ノード上で各インスタンスが書き込めるパーティションの最大数です。 |
  | `table_sink_non_partition_write_scaling_data_processed_threshold` | 25MB | 非パーティションテーブルで書き込みのスケーリングを開始するデータ量のしきい値です。データが `table_sink_non_partition_write_scaling_data_processed_threshold` ずつ増えるたびに、新しいライター（インスタンス）が使用されます。この仕組みはデータ量に応じてライター数を調整し、少量のデータではリソースとファイル数を抑えながらスループットを高めます。 |
  | `table_sink_partition_write_min_data_processed_rebalance_threshold` | 25MB | パーティションテーブルでリバランスを開始するデータ量の最小しきい値です。`current accumulated data volume` - `data volume since last rebalancing` >= `table_sink_partition_write_min_data_processed_rebalance_threshold` の場合に開始します。このしきい値を下げると、ファイルサイズの差が大きい場合にバランスを改善できますが、リバランスのコストが増え、性能に影響する可能性があります。 |
  | `table_sink_partition_write_min_partition_data_processed_rebalance_threshold` | | リバランスを開始するパーティションデータ量の最小しきい値です。`current partition data volume` >= `threshold` \* `number of tasks already allocated to the partition` の場合に開始します。このしきい値を下げると、ファイルサイズの差が大きい場合にバランスを改善できますが、リバランスのコストが増え、性能に影響する可能性があります。 |

## データベースとテーブルの管理 {#database-and-table-management}

### データベースの作成と削除 {#creating-and-dropping-databases}

`SWITCH` 文で目的の Catalog に切り替え、`CREATE DATABASE` コマンドを実行できます。

```sql
SWITCH iceberg;
CREATE DATABASE [IF NOT EXISTS] iceberg_db;
```

完全修飾名を使用したり、場所を指定したりしてデータベースを作成することもできます。現在、場所の指定をサポートするのは HMS 型の Catalog のみです。

```sql
CREATE DATABASE [IF NOT EXISTS] iceberg.iceberg_db;

CREATE DATABASE [IF NOT EXISTS] iceberg.iceberg_db
PROPERTIES ('location'='hdfs://172.21.16.47:4007/path/to/db/');
```

`SHOW CREATE DATABASE` コマンドを使用すると、データベースの場所を確認できます。

```sql
mysql> SHOW CREATE DATABASE iceberg_db;
+-------------+-------------------------------------------------------------------------------------------------+
| Database    | Create Database                                                                                 |
+-------------+-------------------------------------------------------------------------------------------------+
| iceberg_db  | CREATE DATABASE iceberg_db LOCATION 'hdfs://172.21.16.47:4007/usr/hive/warehouse/iceberg_db.db' |
+-------------+-------------------------------------------------------------------------------------------------+
```

データベースを削除するには、次を実行します。

```sql
DROP DATABASE [IF EXISTS] iceberg.iceberg_db;
```

:::caution
Iceberg データベースを削除するには、先にそのデータベース内のすべてのテーブルを削除する必要があります。削除していないテーブルがあるとエラーが発生します。
:::

### テーブルの作成と削除 {#creating-and-dropping-tables}

* **テーブルの作成**

  Doris は Iceberg でパーティションテーブルと非パーティションテーブルの両方の作成をサポートします。

  例：

  ```sql
  -- Create unpartitioned iceberg table
  CREATE TABLE unpartitioned_table (
    `col1` BOOLEAN COMMENT 'col1',
    `col2` INT COMMENT 'col2',
    `col3` BIGINT COMMENT 'col3',
    `col4` FLOAT COMMENT 'col4',
    `col5` DOUBLE COMMENT 'col5',
    `col6` DECIMAL(9,4) COMMENT 'col6',
    `col7` STRING COMMENT 'col7',
    `col8` DATE COMMENT 'col8',
    `col9` DATETIME COMMENT 'col9'
  )
  PROPERTIES (
    'write-format'='parquet'
  );

  -- Create partitioned iceberg table
  -- The partition columns must be in table's column definition list
  CREATE TABLE partition_table (
    `ts` DATETIME COMMENT 'ts',
    `col1` BOOLEAN COMMENT 'col1',
    `col2` INT COMMENT 'col2',
    `col3` BIGINT COMMENT 'col3',
    `col4` FLOAT COMMENT 'col4',
    `col5` DOUBLE COMMENT 'col5',
    `col6` DECIMAL(9,4) COMMENT 'col6',
    `col7` STRING COMMENT 'col7',
    `col8` DATE COMMENT 'col8',
    `col9` DATETIME COMMENT 'col9',
    `pt1` STRING COMMENT 'pt1',
    `pt2` STRING COMMENT 'pt2'
  )
  PARTITION BY LIST (day(ts), pt1, pt2) ()
  PROPERTIES (
    'write-format'='orc',
    'compression-codec'='zlib'
  );
  ```

  バージョン 4.1.0 以降、Doris は Iceberg テーブル作成時のソートカラム指定をサポートします。書き込み時に指定したソートカラムに従ってデータを並べ替え、クエリ性能を高めます。

  ```sql
  CREATE TABLE ordered_table (
    `id` int NULL,
    `name` text NULL,
    `score` double NULL,
    `create_time` datetimev2(6) NULL
  )
  ORDER BY  (`id` ASC NULLS FIRST, `score` DESC NULLS LAST)
  PROPERTIES (
    "write-format" = "parquet",
    "write.parquet.compression-codec" = "zstd"
  );
  ```

  - ソートカラムを指定しない場合、書き込み時にソートは行われません。
  - デフォルトのソート順は ASC NULLS FIRST です。

  作成後、`SHOW CREATE TABLE` コマンドで Iceberg テーブルの作成文を確認できます。パーティション関数の詳細は、[パーティション分割](#)のセクションを参照してください。

* **テーブルの削除**

  `DROP TABLE` 文で Iceberg テーブルを削除できます。テーブルを削除すると、パーティションデータを含むデータも削除されます。

  例：

  ```sql
  DROP TABLE [IF EXISTS] iceberg_tbl;
  ```

* **カラム型のマッピング**

  [カラム型のマッピング](#)のセクションを参照してください。

* **パーティション分割**

    Iceberg のパーティション型は Doris の List パーティションに対応します。そのため、Doris で Iceberg パーティションテーブルを作成するときは List パーティション構文を使用します。ただし、各パーティションを明示的に列挙する必要はありません。データ挿入時に、Doris がデータ値に基づいて対応する Iceberg パーティションを自動作成します。

    * 単一カラムまたは複数カラムのパーティションテーブルの作成をサポートします。

    * パーティション変換関数をサポートし、Iceberg の暗黙的なパーティション分割とパーティション進化を利用できます。Iceberg の各パーティション変換関数については、[Iceberg partition transforms](https://iceberg.apache.org/spec/#partition-transforms) を参照してください。

        * `year(ts)` または `years(ts)`

        * `month(ts)` または `months(ts)`

        * `day(ts)`、`days(ts)`、または `date(ts)`

        * `hour(ts)`、`hours(ts)`、または `date_hour(ts)`

        * `bucket(N, col)`

        * `truncate(L, col)`

* **ファイル形式**

    * Parquet（デフォルト）

        Doris が作成した Iceberg テーブルでは、Datetime は `timestamp_ntz` 型に対応することに注意してください。

        3.1.0 より後のバージョンでは、Datetime 型を Parquet ファイルに書き込む際の物理型は INT96 ではなく INT64 です。

        他のシステムが作成した Iceberg テーブルでは、`timestamp` と `timestamp_ntz` はどちらも Doris の Datetime 型にマッピングされますが、書き込み時には実際の型に基づいてタイムゾーン処理の要否が判定されます。

    * ORC

* **圧縮形式**

    * Parquet：snappy、zstd（デフォルト）、plain（圧縮なし）。

    * ORC：snappy、zlib（デフォルト）、zstd、plain（圧縮なし）。

* **ストレージ媒体**

    * HDFS

    * オブジェクトストレージ

### スキーマ変更 {#schema-change}

3.1.0 以降、Doris は Iceberg テーブルのスキーマ変更をサポートし、`ALTER TABLE` 文で変更できます。

サポートされるスキーマ変更操作は次のとおりです。

* **カラム名の変更**

    `RENAME COLUMN` 句を使用してカラム名を変更します。バージョン 4.1.4 以降は、ネストした型の中にあるカラム名も変更でき、`TO` キーワードは省略可能です。

    ```sql
    ALTER TABLE iceberg_table RENAME COLUMN old_col_name TO new_col_name;

    -- Supported since 4.1.4: TO can be omitted
    ALTER TABLE iceberg_table RENAME COLUMN old_col_name new_col_name;

    -- Supported since 4.1.4: rename a nested field
    ALTER TABLE iceberg_table RENAME COLUMN s.old_field TO new_field;
    ```

* **カラムの追加**

    `ADD COLUMN` を使用して新しいカラムを追加します。バージョン 4.1.4 以降は、ドット区切りのパス（`s.new_field` など）を使用してネストした型（STRUCT）に新しいカラムを追加できます。新しく追加するネストしたフィールドは NULL 許容である必要があります。

    新しいカラムを追加するときは、NULL 許容属性、デフォルト値、コメント、カラム位置を指定できます。

    ```sql
    ALTER TABLE iceberg_table ADD COLUMN col_name col_type [NULL|NOT NULL, [DEFAULT default_value, [COMMENT 'comment', [FIRST|AFTER col_name]]]];
    ```

    例：

    ```sql
    ALTER TABLE iceberg_table ADD COLUMN new_col STRING NOT NULL DEFAULT 'default_value' COMMENT 'This is a new col' AFTER old_col;
    ```

* **複数カラムの追加**

    `ADD COLUMN` を使って複数のカラムを追加することもできます。新しいカラムはテーブルの末尾に追加されます。複数カラムの追加では、カラム位置の指定とネストした型へのカラム追加はサポートされません。

    各カラムの構文は単一カラムの追加と同じです。

    ```sql
    ALTER TABLE iceberg_table ADD COLUMN (col_name1 col_type1 [NULL|NOT NULL, [DEFAULT default_value, [COMMENT 'comment']]], col_name2 col_type2 [NULL|NOT NULL, [DEFAULT default_value, [COMMENT 'comment']]] ...);
    ```

* **カラムの削除**

    `DROP COLUMN` を使用してカラムを削除します。バージョン 4.1.4 以降は、ドット区切りのパスでネストした型の中にあるカラムも削除できます。

    ```sql
    ALTER TABLE iceberg_table DROP COLUMN col_name;

    -- Supported since 4.1.4: drop a nested field
    ALTER TABLE iceberg_table DROP COLUMN s.field_name;
    ```

* **カラムの変更**

    `MODIFY COLUMN` 文を使用して、型、NULL 許容、デフォルト値、コメント、カラム位置などのカラム属性を変更します。

    バージョン 4.0.4 以降、Doris は複合型（STRUCT、ARRAY、MAP）の変更をサポートします。これには安全な型の昇格や struct フィールドの追加が含まれます。

    ネストした型でサポートされる安全な型の昇格：
    - INT -> BIGINT, LARGEINT
    - TINYINT -> SMALLINT, INT, BIGINT, LARGEINT
    - SMALLINT -> INT, BIGINT, LARGEINT
    - BIGINT -> LARGEINT
    - FLOAT -> DOUBLE
    - VARCHAR(n) -> VARCHAR(m) where m > n

    複合型の制約：
    - 新しいネストしたフィールドはすべて NULL 許容である必要があります。
    - 任意から必須への変更はできません。
    - 複合型のデフォルト値は NULL のみサポートされます。

    注：カラム属性を変更する場合、変更しない属性も元の値を明示的に指定してください。

    ```sql
    ALTER TABLE iceberg_table MODIFY COLUMN col_name col_type [NULL|NOT NULL, [DEFAULT default_value, [COMMENT 'comment', [FIRST|AFTER col_name]]]];
    ```

  例：

  ```sql
  CREATE TABLE iceberg_table (
      id INT,
      name STRING
  );
  -- Modify the id column type to BIGINT, set as NOT NULL, default value to 0, and add comment
  ALTER TABLE iceberg_table MODIFY COLUMN id BIGINT NOT NULL DEFAULT 0 COMMENT 'This is a modified id column';
  ```

  複合型の変更例：

  ```sql
  -- Create Iceberg table with complex types
  CREATE TABLE iceberg_tbl (
      id BIGINT,
      user_info STRUCT<name:STRING, scores:ARRAY<INT>, age:INT>,
      dt STRING
  );

  -- Append a new field (email) to the STRUCT column
  ALTER TABLE iceberg_tbl MODIFY COLUMN user_info STRUCT<name:STRING, scores:ARRAY<INT>, age:INT, email:STRING>;

  -- Promote the nested ARRAY element type from INT to BIGINT
  ALTER TABLE iceberg_tbl MODIFY COLUMN user_info STRUCT<name:STRING, scores:ARRAY<BIGINT>, age:INT, email:STRING>;
  ```

* **カラムの並べ替え**

    `ORDER BY` で新しいカラム順を指定し、カラムを並べ替えます。

    ```sql
    ALTER TABLE iceberg_table ORDER BY (col_name1, col_name2, ...);
    ```

#### ネストしたカラムのスキーマ変更（4.1.4+） {#nested-column-schema-change-414}

バージョン 4.1.4 以降、`ADD COLUMN`、`DROP COLUMN`、`MODIFY COLUMN`、`RENAME COLUMN` では、ドット区切りのパス（`a.b.c` など）を指定してネストしたフィールドを直接操作できます。この機能が適用されるのは**Iceberg テーブルのみ**です。他の種類のテーブルで使用すると、`Nested column path is only supported for Iceberg tables: ...` が報告されます。

主な制限とエラー：

| エラーメッセージ | 説明 |
| --- | --- |
| `New nested field '<path>' must be nullable` | 新しく追加するネストしたフィールドは NULL 許容である必要があります。 |
| `Rollup is not supported for Iceberg column operations` | Rollup 句はサポートされません。 |
| `PROPERTIES are not supported for Iceberg column operations` | PROPERTIES 句はサポートされません。 |
| `KEY is not supported for Iceberg ADD/MODIFY COLUMN` | KEY キーワードはサポートされません。 |
| `Generated columns are not supported for Iceberg ADD/MODIFY COLUMN` | 生成カラムはサポートされません。 |
| `Modifying default values is not supported for Iceberg columns` | 既存カラムのデフォルト値の変更はサポートされません。 |
| `ON UPDATE is not supported for Iceberg ADD COLUMN` | ON UPDATE 句はサポートされません。 |
| `Modify column type from complex to primitive is not supported` | 複合型からプリミティブ型への変更はサポートされません。 |
| `Cannot change MAP key type from ...` / `Cannot <op> MAP key nested column` | MAP のキー型の変更や、MAP のキーに対するネストしたカラム操作はサポートされません。 |
| `Iceberg does not support comments on collection element or value fields` | コレクション要素や MAP の値フィールドへのコメントはサポートされません。 |
| `Multiple Iceberg ALTER clauses are not supported when a statement ...` | ネストしたカラムを扱う場合、一つの文に含められる ALTER 句は一つだけです。 |

### パーティション進化 {#partition-evolution}

バージョン 4.0.2 以降、Doris は `ALTER` 文による Iceberg テーブルの Partition Evolution をサポートします。

サポートされるパーティション変換は次のとおりです。

| 変換 | 構文 | 例 |
|-----------|--------|---------|
| bucket | `bucket(N, column)` | `bucket(16, id)` |
| truncate | `truncate(N, column)` | `truncate(10, name)` |
| year | `year(column)` | `year(ts)` |
| month | `month(column)` | `month(ts)` |
| day | `day(column)` | `day(ts)` |
| hour | `hour(column)` | `hour(ts)` |
| identity | `column` | `category` |

サポートされる操作は次のとおりです。

- **パーティションキーの追加**

    ```sql
    -- use optional AS keyword to specify a custom name for the partition field
    ALTER TABLE table_name ADD PARTITION KEY partition_transform [AS key_name];

    -- example
    ALTER TABLE prod.db.sample ADD PARTITION KEY bucket(16, id);
    ALTER TABLE prod.db.sample ADD PARTITION KEY truncate(4, data);
    ALTER TABLE prod.db.sample ADD PARTITION KEY year(ts);
    -- use optional AS keyword to specify a custom name for the partition field
    ALTER TABLE prod.db.sample ADD PARTITION KEY bucket(16, id) AS shard;
    ```

- **パーティションキーの削除**

    ```sql
    ALTER TABLE table_name DROP PARTITION KEY partition_transform｜key_name;

    -- example
    ALTER TABLE prod.db.sample DROP PARTITION KEY catalog;
    ALTER TABLE prod.db.sample DROP PARTITION KEY bucket(16, id);
    ALTER TABLE prod.db.sample DROP PARTITION KEY truncate(4, data);
    ALTER TABLE prod.db.sample DROP PARTITION KEY year(ts);
    ALTER TABLE prod.db.sample DROP PARTITION KEY shard;
    ```

- **パーティションキーの置き換え**

    ```sql
    -- use optional AS keyword to specify a custom name for the partition field
    ALTER TABLE table_name REPLACE PARTITION KEY key_name WITH partition_transform [AS key_name];

    -- example
    ALTER TABLE prod.db.sample REPLACE PARTITION KEY ts_day WITH day(ts);
    -- use optional AS keyword to specify a custom name for the new partition field
    ALTER TABLE prod.db.sample REPLACE PARTITION KEY ts_day WITH day(ts) AS day_of_ts;
    ```

### Branch と Tag の管理 {#managing-branch--tag}

> 3.1.0 以降

* **Branch の作成**

  構文：

  ```sql
  ALTER TABLE [catalog.][database.]table_name
  CREATE [OR REPLACE] BRANCH [IF NOT EXISTS] <branch_name>
  [AS OF VERSION <snapshot_id>]
  [RETAIN <num> { DAYS | HOURS | MINUTES }]
  [WITH SNAPSHOT RETENTION { snapshotKeep | timeKeep }]

  snapshotKeep:
    <num> SNAPSHOTS [<num> { DAYS | HOURS | MINUTES }]

  timeKeep:
    <num> { DAYS | HOURS | MINUTES }
  ```

  例：

  ```sql
  -- Create branch "b1".
  ALTER TABLE tbl CREATE BRANCH b1;
  ALTER TABLE tb1 CREATE BRANCH IF NOT EXISTS b1;
  -- Create or replace branch "b1".
  ALTER TABLE tb1 CREATE OR REPLACE BRANCH b1;
  -- Create or replace branch "b1" based on snapshot "123456".
  ALTER TABLE tb1 CREATE OR REPLACE BRANCH b1 AS OF VERSION 123456;
  -- Create or replace branch "b1" based on snapshot "123456", branch retained for 1 day.
  ALTER TABLE tb1 CREATE OR REPLACE BRANCH b1 AS OF VERSION 123456 RETAIN 1 DAYS;
  -- Create branch "b1" based on snapshot "123456", branch retained for 30 days. Keep the latest 3 snapshots in the branch.
  ALTER TABLE tb1 CREATE BRANCH b1 AS OF VERSION 123456 RETAIN 30 DAYS WITH SNAPSHOT RETENTION 3 SNAPSHOTS;
  -- Create branch "b1" based on snapshot "123456", branch retained for 30 days. Snapshots in the branch are retained for at most 2 days.
  ALTER TABLE tb1 CREATE BRANCH b1 AS OF VERSION 123456 RETAIN 30 DAYS WITH SNAPSHOT RETENTION 2 DAYS;
  -- Create branch "b1" based on snapshot "123456", branch retained for 30 days. Keep the latest 3 snapshots in the branch, and snapshots in the branch are retained for at most 2 days.
  ALTER TABLE tb1 CREATE BRANCH b1 AS OF VERSION 123456 RETAIN 30 DAYS WITH SNAPSHOT RETENTION 3 SNAPSHOTS 2 DAYS;
  ```

* **Branch の削除**

  構文：

  ```sql
  ALTER TABLE [catalog.][database.]table_name
  DROP BRANCH [IF EXISTS] <branch_name>;
  ```

  例：

  ```sql
  ALTER TABLE tbl DROP BRANCH b1;
  ```

* **Tag の作成**

  構文：

  ```sql
  ALTER TABLE [catalog.][database.]table_name
  CREATE [OR REPLACE] TAG [IF NOT EXISTS] <tag_name>
  [AS OF VERSION <snapshot_id>]
  [RETAIN <num> { DAYS | HOURS | MINUTES }]
  ```

  例：

  ```sql
  -- Create tag "t1".
  ALTER TABLE tbl CREATE TAG t1;
  ALTER TABLE tb1 CREATE TAG IF NOT EXISTS t1;
  -- Create or replace tag "t1".
  ALTER TABLE tb1 CREATE OR REPLACE TAG t1;
  -- Create or replace tag "t1" based on snapshot "123456".
  ALTER TABLE tb1 CREATE OR REPLACE TAG b1 AS OF VERSION 123456;
  -- Create or replace tag "b1" based on snapshot "123456", tag retained for 1 day.
  ALTER TABLE tb1 CREATE OR REPLACE TAG b1 AS OF VERSION 123456 RETAIN 1 DAYS;
  ```

* **Tag の削除**

  構文：

  ```sql
  ALTER TABLE [catalog.][database.]table_name
  DROP TAG [IF EXISTS] <tag_name>;
  ```

  例：

  ```sql
  ALTER TABLE tbl DROP TAG t1;
  ```

## Iceberg テーブルのアクション {#iceberg-table-actions}

> この機能はバージョン 4.0.2 以降でサポートされます。各操作の具体的なバージョン要件を確認してください。
>
> これは実験的な機能です。

Doris は `ALTER TABLE EXECUTE` 構文による特定の Iceberg テーブルアクションの実行をサポートします。この構文は、テーブル最適化やスナップショット管理などのさまざまな操作を実行するための統一されたインターフェースを提供します。

```sql
ALTER TABLE [catalog.][database.]table_name
EXECUTE <action_name> ("key1" = "value1", "key2" = "value2", ...)
[WHERE <condition>]
```

* `action_name`：実行する操作の名前
* `("key1" = "value1", ...)`：キーと値のペアで指定する操作関連のパラメータ。パラメータ名は二重引用符で囲む必要があります。
* `[WHERE <condition>]`：操作対象のパーティションまたはデータ範囲を指定する任意の WHERE 条件。一部の操作でのみサポートされます。

### cherrypick_snapshot {#cherrypick_snapshot}

`cherrypick_snapshot` 操作は、指定したスナップショットの変更を現在のテーブル状態に統合し、元のスナップショットを変更・削除せずに新しいスナップショットを作成します。

> サポートされるバージョン：4.0.2+

**構文：**

```sql
ALTER TABLE [catalog.][database.]table_name
EXECUTE cherrypick_snapshot ("snapshot_id" = "<snapshot_id>")
```

**パラメータ：**

| パラメータ | 型 | 必須 | 説明 |
| -------- | ---- | ---- | ---- |
| `snapshot_id` | Long | はい | 統合するスナップショット ID |

**戻り値：**

`cherrypick_snapshot` 操作は、次の二つのカラムを持つ結果セットを返します。

| カラム名 | 型 | 説明 |
| ---- | ---- | ---- |
| `source_snapshot_id` | BIGINT | 統合されたスナップショット ID |
| `current_snapshot_id` | BIGINT | 統合操作後に新しく作成され、現在のスナップショットに設定された ID |

**例：**

```sql
-- Merge changes from snapshot 123456789 into the current table state
ALTER TABLE iceberg_db.iceberg_table
EXECUTE cherrypick_snapshot ("snapshot_id" = "123456789");
```

**注意事項：**

1. この操作は WHERE 条件をサポートしません。
2. 指定したスナップショットが存在しない場合、操作は失敗します。
3. 統合操作では新しいスナップショットが作成され、元のスナップショットは削除されません。

### expire_snapshots {#expire_snapshots}

`expire_snapshots` 操作は Iceberg テーブルの古いスナップショットを削除し、ストレージ領域を解放してメタデータの性能を改善します。この操作は Apache Iceberg Spark procedure の仕様に従います。

> サポートされるバージョン：4.1.0+

**構文：**

```sql
ALTER TABLE [catalog.][database.]table_name
EXECUTE expire_snapshots ("key1" = "value1", "key2" = "value2", ...)
```

**パラメータ：**

| パラメータ | 型 | 必須 | 説明 |
| -------- | ---- | ---- | ---- |
| `older_than` | String | いいえ | スナップショットの期限切れを判定するタイムスタンプのしきい値です。これより古いスナップショットを削除します。ISO 日時形式（`2024-01-01T00:00:00` など）またはミリ秒単位のタイムスタンプをサポートします。 |
| `retain_last` | Integer | いいえ | 保持する祖先スナップショットの数です。単独で指定した場合、`older_than` は自動的に現在時刻に設定されます。 |
| `snapshot_ids` | String | いいえ | 期限切れにする特定のスナップショット ID をカンマ区切りで指定します。 |
| `max_concurrent_deletes` | Integer | いいえ | 削除操作に使用するスレッドプールのサイズです。 |
| `clean_expired_metadata` | Boolean | いいえ | `true` に設定すると、使用されていないパーティション仕様とスキーマをクリーンアップします。 |

**戻り値：**

`expire_snapshots` 操作は、次の六つのカラムを持つ結果セットを返します。

| カラム名 | 型 | 説明 |
| ---- | ---- | ---- |
| `deleted_data_files_count` | BIGINT | 削除されたデータファイル数 |
| `deleted_position_delete_files_count` | BIGINT | 削除された position delete file の数 |
| `deleted_equality_delete_files_count` | BIGINT | 削除された equality delete file の数 |
| `deleted_manifest_files_count` | BIGINT | 削除された manifest ファイル数 |
| `deleted_manifest_lists_count` | BIGINT | 削除された manifest list ファイル数 |
| `deleted_statistics_files_count` | BIGINT | 削除された統計ファイル数 |

**例：**

```sql
-- Expire snapshots, keeping only the last 2
ALTER TABLE iceberg_db.iceberg_table
EXECUTE expire_snapshots ("retain_last" = "2");

-- Expire snapshots older than a specific timestamp
ALTER TABLE iceberg_db.iceberg_table
EXECUTE expire_snapshots ("older_than" = "2024-01-01T00:00:00");

-- Expire specific snapshots by ID
ALTER TABLE iceberg_db.iceberg_table
EXECUTE expire_snapshots ("snapshot_ids" = "123456789,987654321");

-- Combine parameters: expire snapshots older than 2024-06-01 but keep at least the last 5
ALTER TABLE iceberg_db.iceberg_table
EXECUTE expire_snapshots ("older_than" = "2024-06-01T00:00:00", "retain_last" = "5");
```

**注意事項：**

1. この操作は WHERE 条件をサポートしません。
2. `older_than` と `retain_last` の両方を指定した場合は両方の条件が適用されます。`older_than` より古く、かつ直近の `retain_last` 個に含まれないスナップショットのみが削除されます。
3. `snapshot_ids` は単独で使用して特定のスナップショットを削除できます。
4. この操作はスナップショットと関連するデータファイルを完全に削除します。慎重に使用してください。
5. 実行前に `$snapshots` システムテーブルをクエリして、テーブルのスナップショット情報を確認することを推奨します。

### rewrite_data_files {#rewrite_data_files}

`rewrite_data_files` 操作は Iceberg テーブルのデータファイルを書き換えて小さなファイルを統合し、クエリ性能とストレージ効率を最適化します。これは同期操作です。

> サポートされるバージョン：4.0.2+

**構文：**

```sql
ALTER TABLE [catalog.][database.]table_name
EXECUTE rewrite_data_files ("key1" = "value1", "key2" = "value2", ...) [WHERE <condition>]
```

**パラメータ：**

| パラメータ | 型 | デフォルト値 | 説明 |
| -------- | ---- | ------ | ---- |
| `target-file-size-bytes` | Long | 536870912 (512MB) | 出力ファイルの目標サイズ（バイト）です。 |
| `min-file-size-bytes` | Long | target-file-size-bytes * 0.75 | 最小ファイルサイズ（バイト）です。これより小さいファイルは書き換えられます。未指定の場合、目標ファイルサイズの 75% がデフォルトです。 |
| `max-file-size-bytes` | Long | target-file-size-bytes * 1.8 | 最大ファイルサイズ（バイト）です。これより大きいファイルは分割されます。未指定の場合、目標ファイルサイズの 180% がデフォルトです。 |
| `min-input-files` | Integer | 5 | 書き換えを開始する入力ファイル数の下限です。書き換え対象のファイル数がこのしきい値に達した場合にのみ実行されます。 |
| `rewrite-all` | Boolean | false | ファイルサイズに関係なく、すべてのファイルを書き換えるかどうか。 |
| `max-file-group-size-bytes` | Long | 107374182400 (100GB) | 単一ファイルグループの最大サイズ（バイト）です。一つの書き換えタスクが処理するデータ量を制限します。 |
| `delete-file-threshold` | Integer | Integer.MAX_VALUE | 書き換えを開始するために必要な delete file 数の下限です。 |
| `delete-ratio-threshold` | Double | 0.3 | 書き換えを開始するために必要な削除済みレコードの比率（削除済みレコード数 / 総レコード数）の下限です。範囲：0.0 - 1.0。 |
| `output-spec-id` | Long | 2 | 出力ファイルのパーティション仕様 ID です。 |

**戻り値：**

`rewrite_data_files` 操作は、次の四つのカラムを持つ結果セットを返します。

| カラム名 | 型 | 説明 |
| ---- | ---- | ---- |
| `rewritten_data_files_count` | INT | 書き換えられたデータファイル数 |
| `added_data_files_count` | INT | 新しく追加されたデータファイル数 |
| `rewritten_bytes_count` | INT | 書き換えられたバイト数 |
| `removed_delete_files_count` | BIGINT | 削除された delete file 数 |

**例：**

```sql
-- Rewrite data files with default parameters
ALTER TABLE iceberg_db.iceberg_table EXECUTE rewrite_data_files();

-- Specify target file size and minimum input files
ALTER TABLE iceberg_db.iceberg_table
EXECUTE rewrite_data_files (
  "target-file-size-bytes" = "134217728",
  "min-input-files" = "10"
);

-- Rewrite data in specific partitions using WHERE condition
ALTER TABLE iceberg_db.iceberg_table
EXECUTE rewrite_data_files (
  "target-file-size-bytes" = "268435456"
)
WHERE date_col = '2024-01-01';

-- Rewrite all files
ALTER TABLE iceberg_db.iceberg_table
EXECUTE rewrite_data_files (
  "rewrite-all" = "true",
  "target-file-size-bytes" = "536870912"
);
```

**注意事項：**

1. `rewrite_data_files` 操作はデータファイルを読み取って書き換えるため、追加の I/O と計算負荷が発生します。クラスターリソースを適切に割り当ててください。
2. 実行前に[データファイル分布の確認](#view-data-file-distribution)の SQL を使用して、書き換えが必要かどうかを評価できます。
3. WHERE 条件を使用して、書き換え対象のパーティションやデータ範囲を制限できます。この条件は一致するデータを含まないファイルを除外し、書き換えるファイル数とデータ量を減らします。
4. 実行前に[書き換え対象ファイルの選択ロジック](#rewrite_data_files-file-selection-strategy)の SQL を使用して、どのファイルが書き換えられるかを計算できます。

### publish_changes {#publish_changes-1}

`publish_changes` 操作は、WAP（Write-Audit-Publish）モードで、指定した `wap.id` を持つスナップショットを現在のテーブル状態として公開します。
指定した `wap_id` に一致する `wap.id` を持つスナップショットを探し、現在のテーブルに cherry-pick して、ステージングされたデータをすべての読み取り操作から参照できるようにします。

**構文：**

```sql
ALTER TABLE [catalog.][database.]table_name
EXECUTE publish_changes("wap_id" = "<wap_id>")
```

**パラメータ：**

**パラメータ：**

| パラメータ名 | 型 | 必須 | 説明 |
| -------------- | ---- | -------- | ----------- |
| `wap_id` | STRING | はい | 公開する WAP スナップショット ID |

**戻り値：**

`publish_changes` は、次の二つのカラムを持つ結果セットを返します。

| カラム名 | 型 | 説明 |
| ----------- | ---- | ----------- |
| `previous_snapshot_id` | STRING | 公開操作前の現在のスナップショット ID（存在しない場合は NULL） |
| `current_snapshot_id` | STRING | 公開後に作成され、現在のスナップショットに設定された新しい ID |

**例：**


2. `write.wap.enabled = true` の Iceberg テーブルで、`wap.id` を使用して生成された WAP スナップショットに対してのみ意味があります。

4. 公開後は、新しいスナップショットが現在のスナップショットになります。
5. 公開前にスナップショットが存在しない場合、`previous_snapshot_id` は NULL になることがあります。

## Iceberg テーブルの最適化 {#iceberg-table-optimization}

### データファイル分布の確認 {#view-data-file-distribution}

次の SQL で Iceberg テーブルのデータ分布と delete file 数を分析し、`rewrite_data_files` などの最適化が必要かどうかを判断できます。

- データファイルのサイズ分布を表示します。小さなファイルが多すぎないか確認できます。

    ```sql
    SELECT
        CASE
            WHEN file_size_in_bytes BETWEEN 0 AND 8 * 1024 * 1024 THEN '0-8M'
            WHEN file_size_in_bytes BETWEEN 8 * 1024 * 1024 + 1 AND 32 * 1024 * 1024 THEN '8-32M'
            WHEN file_size_in_bytes BETWEEN 32 * 1024 * 1024 + 1 AND 128 * 1024 * 1024 THEN '32-128M'
            WHEN file_size_in_bytes BETWEEN 128 * 1024 * 1024 + 1 AND 512 * 1024 * 1024 THEN '128-512M'
            WHEN file_size_in_bytes > 512 * 1024 * 1024 THEN '> 512M'
            ELSE 'Unknown'
        END AS SizeRange,
        COUNT(*) AS FileNum
    FROM store_sales$data_files
    GROUP BY
        SizeRange;

    +-----------+---------+
    | SizeRange | FileNum |
    +-----------+---------+
    | 0-8M      |       8 |
    | 8-32M     |       6 |
    +-----------+---------+
    ```

### Dangling Delete {#dangling-delete}

場合によっては、`rewrite_data_files` アクションの実行後に、特定の Position Delete への参照が Snapshot メタデータから削除されないことがあります（Dangling Delete）。この状態でメタデータの行数情報を直接使用すると、結果が正しくない可能性があります。

そのためデフォルトでは、`COUNT(*)` クエリで Position Delete ファイルが見つかると、COUNT プッシュダウン最適化を有効にせず、ファイルを直接読み取って実際の `COUNT(*)` 結果を取得します。ただし、この方法には時間がかかります。

Dangling Delete の問題がないと確認できる場合は、Doris のセッション変数 `ignore_iceberg_dangling_delete` を使用してこのチェックを省略できます。デフォルトは `false` です。`true` に設定すると、システムはメタデータ内の行数情報に基づく `COUNT(*)` 結果を直接返し、クエリ効率を高めます。

この機能はバージョン 3.1.4 と 4.0.3 以降でサポートされます。

## 付録 {#appendix}

### `rewrite_data_files` のファイル選択戦略 {#rewrite_data_files-file-selection-strategy}

このセクションでは、書き換えるファイルの選択ロジックを説明します。次の SQL クエリを使用して、システムテーブルの情報から書き換え対象となるファイルを分析することもできます。実際の書き換え操作を実行する前に、その動作を調査・理解するのに役立ちます。

書き換え操作では、二段階のフィルタリングとグループ化を使用します。

1. 第 1 段階：ファイル単位のフィルタリング

    まず、ファイル単位の条件でフィルタリングします。次の条件の少なくとも一つを満たすファイルのみが書き換え候補になります。

    1. **ファイルサイズが範囲外**：ファイルが `min-file-size-bytes` より小さい、または `max-file-size-bytes` より大きい。
    2. **delete file が多すぎる**：関連する delete file 数 >= `delete-file-threshold`。
    3. **削除比率が高い**：削除済みレコードの比率 >= `delete-ratio-threshold`。

    **delete file 条件に関する注記：** delete file に関する条件（`delete-file-threshold` と `delete-ratio-threshold`）は書き換え対象ファイルの選択に影響しますが、システムテーブルへの SQL クエリでは正確に計算できません。現在のシステムテーブルの情報だけでは、delete file がどのデータファイルに影響するかを正確に判定できないためです。delete file は特定のデータファイルにのみ影響する場合があり（特に Position Delete ファイル）、delete file とデータファイルの関連付けには、現在のシステムテーブルでは利用できない詳細なメタデータが必要です。実際の書き換え操作では、システムテーブルに公開されない詳細なメタデータに基づいてこれらの条件を評価します。

2. 第 2 段階：BinPack によるグループ化とグループ単位のフィルタリング

    ファイル単位のフィルタリング後、まずパーティションごとにファイルを分け、各パーティション内でファイルサイズと `max-file-group-size-bytes` に基づく **BinPack アルゴリズム**でグループ化します。BinPack アルゴリズムは、書き換え操作を最適化するようファイルをグループへ配置します。

    グループ化後、グループ単位の条件でファイルグループをフィルタリングします。次の条件の少なくとも一つを満たすファイルグループが書き換えられます。

    1. **入力ファイルが十分にある**：グループ内のファイル数 > 1、かつファイル数 >= `min-input-files`。
    2. **内容量が十分にある**：グループ内のファイル数 > 1、かつ合計サイズ > `target-file-size-bytes`。
    3. **内容量が多すぎる**：グループの合計サイズ > `max-file-group-size-bytes`。
    4. **delete file に関する問題を持つファイルが含まれる**：グループ内の少なくとも一つのファイルで、delete file が多すぎるか削除比率が高い。

    **BinPack によるグループ化に関する注記：** 各パーティション内のファイルをグループ化する BinPack アルゴリズムは複雑な最適化アルゴリズムであり、システムテーブルへの SQL クエリでは正確に再現できません。このアルゴリズムはファイルサイズと `max-file-group-size-bytes` を考慮してファイルをグループへ配置するため、単純なパーティション単位のグループ化とは結果が異なる場合があります。そのため、以下の SQL クエリで特定できるのはファイル単位の条件を満たすファイルのみであり、最終的に書き換えられるファイルグループを正確に計算することはできません。

クエリ戦略の例を次に示します。

- クエリ 1：ファイル単位の条件を満たすファイルの特定

    このクエリは、ファイル単位の条件（ファイルサイズ）を満たし、書き換え候補となるファイルを特定します。

    ```sql
    -- Set parameters (adjust according to your rewrite parameters)
    SET @min_file_size_bytes = 16 * 1024 * 1024;   -- 16 MB (default: target-file-size-bytes * 0.75)
    SET @max_file_size_bytes = 768 * 1024 * 1024;  -- 768 MB (default: target-file-size-bytes * 1.8)

    SELECT
        file_path,
        `partition`,
        file_size_in_bytes / 1024.0 / 1024.0 AS file_size_mb,
        record_count,
        CASE
            WHEN file_size_in_bytes < @min_file_size_bytes THEN 'Too small'
            WHEN file_size_in_bytes > @max_file_size_bytes THEN 'Too large'
        END AS size_issue
    FROM iceberg_table$data_files
    WHERE file_size_in_bytes < @min_file_size_bytes
    OR file_size_in_bytes > @max_file_size_bytes
    ORDER BY `partition`, file_size_in_bytes DESC;
    ```

    **出力例：**

    ```text
    +----------------------------------------------------------------------------------------+---------------------------+-------------+--------------+------------+
    | file_path                                                                             | partition                 | file_size_mb | record_count | size_issue |
    +----------------------------------------------------------------------------------------+---------------------------+-------------+--------------+------------+

    | s3a://bucket/path/to/table/data/date_col=2024-01-01/00001-0-00001-00001-0.parquet     | {"date_col":"2024-01-01"} |     0.00198  |            5 | Too small  |
    ```

    **注記：** このクエリで特定できるのは、ファイル単位の条件（ファイルサイズ）を満たすファイルのみです。実際に書き換えられるファイルグループは BinPack アルゴリズムによるグループ化に依存し、SQL クエリでは正確に再現できません。このクエリで特定したファイルが BinPack アルゴリズムによって異なるグループに配置されたり、グループ単位の条件によって一部のグループが除外されたりする場合があります。

- クエリ 2：全体統計の概要

    このクエリは、ファイル単位の条件を満たすファイルの全体的な統計を示します。

    ```sql
    -- Set parameters (adjust according to your rewrite parameters)
    SET @min_file_size_bytes = 16 * 1024 * 1024;
    SET @max_file_size_bytes = 768 * 1024 * 1024;

    WITH file_analysis AS (
        SELECT
            `partition`,
            file_path,
            file_size_in_bytes,
            record_count,
            (file_size_in_bytes < @min_file_size_bytes OR file_size_in_bytes > @max_file_size_bytes) AS meets_file_level_conditions
        FROM iceberg_table$data_files
    )
    SELECT
        'Total files' AS metric,
        COUNT(*) AS value
    FROM file_analysis
    UNION ALL
    SELECT
        'Files meeting file-level conditions',
        SUM(CASE WHEN meets_file_level_conditions THEN 1 ELSE 0 END)
    FROM file_analysis
    UNION ALL
    SELECT
        'Total size (GB)',
        ROUND(SUM(file_size_in_bytes) / 1024.0 / 1024.0 / 1024.0, 2)
    FROM file_analysis
    UNION ALL
    SELECT
        'Size meeting file-level conditions (GB)',
        ROUND(SUM(CASE WHEN meets_file_level_conditions THEN file_size_in_bytes ELSE 0 END) / 1024.0 / 1024.0 / 1024.0, 2)
    FROM file_analysis
    UNION ALL
    SELECT
        'Percentage meeting file-level conditions (%)',
        ROUND(SUM(CASE WHEN meets_file_level_conditions THEN 1 ELSE 0 END) * 100.0 / COUNT(*), 2)
    FROM file_analysis;
    ```

    **出力例：**

    ```text
    +----------------------------------------------+--------+
    | metric                                       | value  |
    +----------------------------------------------+--------+
    | Total files                                  |  15.00 |
    | Total size (GB)                              |   2.45 |
    | Files meeting file-level conditions          |  12.00 |
    | Size meeting file-level conditions (GB)      |   1.85 |
    | Percentage meeting file-level conditions (%) |  80.00 |
    +----------------------------------------------+--------+
    5 rows in set
    ```

    **注意事項：**

    - 例の `iceberg_table` を実際のテーブル名に置き換えてください。
    - 実際の書き換えパラメータに合わせて、パラメータ値（`@min_file_size_bytes`、`@max_file_size_bytes`）を調整してください。
    - 上記のデフォルト値は、デフォルトの書き換えパラメータ（min-file-size-bytes = target-file-size-bytes * 0.75、max-file-size-bytes = target-file-size-bytes * 1.8）に対応します。
