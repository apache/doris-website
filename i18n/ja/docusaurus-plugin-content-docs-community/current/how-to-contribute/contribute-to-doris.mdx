### タスクの探し方

貢献できるタスクは次の場所で探せます。

- Slack：質問、議論の開始、背景の確認、相談相手の探索に適しています。
- [Apache Doris GitHub Issues](https://github.com/apache/doris/issues)：バグ、機能リクエスト、改善案、未着手のタスクを探せます。
- [Apache Doris GitHub Discussions](https://github.com/apache/doris/discussions)：技術的な議論、使い方の質問、設計提案に適しています。
- ロードマップ：長期的な技術課題を探せます。通常は GitHub Issues ページのピン留めされた Issue から確認できます。
- 既存の PR：レビュー、テスト、検証、変更を前に進めるための支援ができます。

初めて貢献する方は、ドキュメントの修正、テストの追加、簡単なバグ修正、Issue の再現、エラーメッセージの改善、サンプルの整理など、小さく範囲の明確なタスクから始められます。大きな機能や動作変更に取り組む場合は、Apache Doris の Slack の `#dev` チャネルで議論を始め、Core Maintainer に背景を確認してください。

### コードへの貢献で求められること

コードを提出する前に、次のことを行うようにしてください。

- `apache/doris` リポジトリをフォークし、最新の main ブランチから別のブランチを作成する。
- 各 PR を明確な一つの問題に絞る。関連のない変更を一つの PR に混ぜない。
- 目的、範囲、検証内容が分かる PR のタイトルと説明を書く。
- 関連する Issue、Discussion、メーリングリストのスレッドをリンクする。
- 必要な単体テスト、回帰テスト、または手動での検証手順を追加する。
- ユーザー向けの動作、設定、SQL の意味、エラーメッセージ、互換性に影響する変更では、ドキュメントを更新する。
- 互換性、性能、安定性、動作に関するリスクを PR の説明に明記する。

一般に、良い PR には次の内容が含まれます。

- 背景：なぜ変更が必要なのか。
- 方針：何を、なぜ変更したのか。
- テスト：実行したテストや検証手順と、その結果。
- リスク：互換性、性能、安定性、ユーザー向けの動作に影響するかどうか。
- ドキュメント：更新が必要かどうか、必要な場合はどこを更新したか。

コミュニティは、コーディング、デバッグ、レビューの補助に AI を使うことを認めています。ただし、貢献者は次のルールに従う必要があります。

- 開発、デバッグ、レビューには十分な能力のあるモデルを使用する。重要な変更を、品質の低い生成コードに頼って行わない。
- 提出するコードには自分で責任を持つ。コミュニティは、人間の責任者がいない AI 生成コードを受け付けません。

### 標準的なマージの流れ

コードの変更は通常、次の手順で進みます。

1. 貢献者が Pull Request を作成する。
2. Committer またはそれ以上の権限を持つ人が CI と AI Review を起動する。支援が必要な場合は Slack の `#dev` チャネルで相談できます。
3. 貢献者が CI やレビューで報告されたビルド、テスト、フォーマットの問題を修正する。AI からのフィードバックもレビューの一部です。有用な提案を取り入れ、当てはまらない提案については PR で理由を説明します。
4. 必要に応じて、貢献者が最新の main ブランチ上にリベースし、競合を解決する。
5. 必須の CI チェックがすべて成功する。
6. Reviewer が PR を承認する。
7. Committer がマージする。

PR をマージするには、必須の CI チェックが成功している必要があります。必須ではないチェックはマージを妨げません。

### レビューを進める方法

貢献者は Reviewer を待つだけでなく、自分の PR を積極的に前に進めてください。Apache Doris の貢献ガイドでも、貢献者が自分の PR の Moderator として、提出からマージまで進めることを推奨しています。

推奨される方法：

- PR の説明に、Reviewer が判断するための十分な背景を書く。
- Slack の `#dev` チャネルで PR のリンクを共有し、レビューを依頼する。
- レビューコメントには速やかに返信する。
- 指摘に対応した後は、解決済みとしてマークする。
- コメントに同意しない場合は、技術的な理由を示す。
- 競合が長引かないよう、定期的にリベースする。
- PR の進行が止まった場合は、PR 上で関連する Reviewer に丁寧に確認する。
- 誰にレビューを依頼すればよいか分からない場合は、適切なモジュール担当者を探せるよう Slack で相談する。

適切な Reviewer を探す方法：

- 同じモジュールで最近マージされた PR を見る。
- 関連ファイルのコミット履歴を確認する。
- 利用できる場合は、GitHub が提案する Reviewer や CODEOWNERS を確認する。
- Slack で適切な Reviewer を探す支援を求める。ただし、重要な技術的結論は GitHub またはメーリングリストでも共有する。

### 提出するものと提出先

#### ブログ記事

適したテーマの例：

- Doris の機能の詳しい解説。
- クエリの最適化、ロードの最適化、運用上のチューニング、トラブルシューティング。
- レイクハウス、リアルタイムデータウェアハウス、ログ分析、ユーザー行動分析などの実践的なシナリオ。
- Elasticsearch、ClickHouse、Hive、Trino などのシステムから Doris への移行経験。
- 本番環境でのトラブルシューティングや性能チューニングの記録。
- 新しいリリースの機能紹介と使い方のアドバイス。

提出方法：

- Slack の `#dev` チャネルで議論を始める。
- `/blog` ディレクトリに Markdown ファイルを提出する。このディレクトリは `apache/doris-website` リポジトリ内にあります。必要に応じて Doris Maintainer が支援します。

#### 事例紹介

適した事例に含まれる内容：

- 企業やチームの業務上の背景。
- チームが Apache Doris を選んだ理由。
- システムアーキテクチャとデータフロー。
- データの規模、クエリのパターン、性能目標。
- 移行や導入の過程で見つかった問題。
- 本番稼働後の結果、効果、得られた教訓。

提出方法：

- コンテンツに企業名、業務データ、アーキテクチャ図が含まれる場合は、先に社内承認を得るか、機密情報を削除する。
- Slack の `#dev` チャネルで議論を始める。コミュニティが事例の編集、翻訳、公開を支援できます。

#### チュートリアル

適したテーマの例：

- 入門。
- デプロイとアップグレード。
- データロード。
- クエリのチューニング。
- マテリアライズドビュー。
- 転置インデックス。
- コンピューティングとストレージの分離。
- レイクハウスクエリ。
- ログ分析と可観測性のシナリオ。

提出方法：

- Slack の `#dev` チャネルで議論を始める。
- 長期にわたって正確性を保てる一般的な内容は、通常、公式ドキュメントに掲載する。
- 実践的なシナリオに基づく内容や、特定バージョンに関する内容は、通常、ブログ記事に適している。
- サンプルコード、スクリプト、設定は、可能な限り再現できるようにする。

#### 動画

適したテーマの例：

- 一分から五分の機能デモ。
- インストールとデプロイの手順紹介。
- ベストプラクティスの解説。
- シナリオに基づくデモ。
- ミートアップやウェビナーの録画。
- ユーザーインタビューや事例紹介の講演。

提出方法：

- Slack の `#dev` チャネルで議論を始める。
- まずコミュニティとテーマ、台本、または構成案を確認する。
- 動画が完成したら、YouTube、Bilibili、その他の公式動画チャンネルへの公開をコミュニティが支援できます。
- 動画に企業名、顧客名、性能データ、社内システムのスクリーンショットが含まれる場合は、先に承認を得るか、機密情報を削除する。

#### 講演

適した形式の例：

- ミートアップでの講演。
- ウェビナーでの講演。
- カンファレンスでの講演。
- リリース機能の紹介。
- 新しい貢献者向けの案内セッション。
- ユーザー事例の紹介セッション。

提出方法：

- Slack の `#dev` チャネルで議論を始める。
- テーマ、概要、対象者、言語、予定時間、登壇者の情報をコミュニティと共有する。
- コミュニティは、テーマの調整、技術的内容のレビュー、セッションの告知、登録ページの支援を行えます。必要に応じて、資金や会場の支援が可能な場合もあります。

#### 翻訳

適した翻訳対象：

- 公式ドキュメント。
- ブログ記事。
- イベントの振り返り記事。
- 動画の字幕。
- チュートリアルとベストプラクティス。

提出方法：

- ドキュメントの翻訳は、`apache/doris-website` への PR として提出する。
- ブログやイベントの翻訳では、対象ページと公開先のチャネルを先にコミュニティと確認する。
- 技術的な意味を正確に保つ。宣伝向けの表現に合わせて意味を変えない。

### 公開チャネル

コンテンツの種類とレビュー結果に応じて、次のチャネルで公開される場合があります。

- Apache Doris 公式ウェブサイト。
- Apache Doris 公式ブログ。
- Apache Doris の Medium。
- Apache Doris の YouTube。
- Apache Doris の LinkedIn。
- Apache Doris の X/Twitter。
- Apache Doris の Slack。
- コミュニティのニュースレター、イベントの振り返り記事、リリースの特集ページ。

公開前には通常、技術的な正確性のレビューが必要です。性能データ、商用の事例、顧客名、企業情報を含むコンテンツには、承認も必要です。

### 参加方法

コミュニティの貢献者は、次のような活動に参加したり、企画したりできます。

- オンラインミートアップ：世界中のユーザーを対象に、テーマを決めてオンラインで情報を共有する。
- オフラインミートアップ：都市や地域ごとに対面で議論する。
- ウェビナー：機能、シナリオ、リリースについてオンラインで解説する。
- ワークショップ：デプロイ、ロード、チューニング、事例を実際に体験する。
- オフィスアワー：ユーザーの質問に答える定期的な Q&A セッション。
- ユーザー事例セッション：実際のユーザーが本番環境での実践例を紹介する。
- リリース紹介：新機能やアップグレードのアドバイスを紹介する。
- 新しい貢献者向けの案内：コードベース、手順、コミュニティのワークフローを理解するためのセッション。
- 地域コミュニティイベント：特定の言語や地域に合わせたイベント。
- ハッカソンまたは貢献スプリント：Issue、ドキュメント、テスト、ツールに集中的に取り組む。

### イベントを提案する方法

イベントの主催者は、次の情報を準備してください。

- イベントのテーマ。
- 対象者。
- イベント形式。
- イベントで使用する言語。
- 日時とタイムゾーン。
- 登壇者または進行役。
- 予定時間。
- コミュニティに必要な支援。

## コミュニティの行動規範

すべての貢献者は、次の原則に従ってください。

- 他者を尊重し、専門的で、友好的かつ建設的なコミュニケーションを心がける。
- 重要な技術的議論やコミュニティの決定は、可能な限り公開チャネルで行う。
- コード、ドキュメント、コンテンツのレビューを受け入れる姿勢を持つ。
- レビューのフィードバックに同意しない場合は、技術的な理由を明確に説明する。
- 公開の場で議論すべきコミュニティの決定を、非公開で行わない。
- オリジナルのコンテンツを提出する。引用または参照した資料は、出典を明記する。
- 誇張された、検証できない、または誤解を招く性能やビジネス上の主張を避ける。
- コードを変更する際は、可能な限りテストを追加する。
- ユーザーから見える動作に影響する変更では、ドキュメントを更新する。
- ユーザーの個人情報、顧客の機密情報、企業の秘密情報を漏らさない。
- セキュリティ上の問題は責任ある開示の手順に従って扱う。問題が対処される前に、公開チャネルで詳細を公表しない。
- Apache コミュニティの価値観と ASF の行動規範を尊重する。

貢献者はオープンソースコミュニティのメンバーとして参加します。活動の中で企業を代表する場合は、必要に応じてそのことを明らかにしてください。貢献は、貢献そのものを重視する Apache の公開性と透明性のある進め方に従う必要があります。
